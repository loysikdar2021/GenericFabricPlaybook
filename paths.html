Learning paths

Seventeen playbooks is too much to read front to back. Each path below is an ordered reading list for one role: the pages that role must know well, why each one is on the list, how long it takes and what you should be able to do at the end. Paths overlap on purpose, because the same decision (a workspace boundary, a deployment rule) is owned by one role and lived with by another.

Which playbooks build on which

The playbooks are written to stand alone, but they assume decisions made elsewhere. A data engineer who reads the load strategy before the medallion design will make different (and usually worse) choices about where MERGE runs; a DevOps engineer who builds deployment pipelines before variable libraries will end up writing per-stage edits by hand. Read the foundations column first.

Shared foundations

Every path starts by touching the medallion workspace pattern (03) and the tenant settings (16), even if only briefly. Those two playbooks fix the names, boundaries and switches that every other playbook refers to.

The first 30 days of a Fabric implementation

The paths above describe what to read. This plan describes what to build, and in which order, when a team starts a new platform. The principle is a single thin vertical slice: two or three tables of one domain, carried from source to a published report in production, before any scope is widened. The slice exercises every boundary in the reference architecture, so problems with identities, bindings and deployment order surface while they are cheap.

  1. Days 1–5 · FoundationsTenant settings, capacities, naming, security groups, repository and rulesets.
  2. Days 6–12 · First slice in DEVWorkspaces per layer, Environment, Bronze and Silver loads for the slice tables.
  3. Days 13–20 · Complete and promote to TSTGold, Warehouse, semantic model, variable libraries, deployment pipelines, validation harness.
  4. Days 21–30 · Harden and releaseHub orchestration, QA gates, UAT, ordered promotion to PRD, org app, runbook.

Do not widen scope early

The most common failure in the first month is onboarding a second domain before the first slice reaches production. Every new domain multiplies workspaces, grants and pipelines by seven; if the promotion path is not proven yet, each multiplication repeats the same mistakes.

Key takeaways

  • Pick the path for your role, but read the foundations column of the dependency graph first.
  • Deployment and the release checklist touch every role; agree on them together.
  • Carry one thin slice to production within the first month before widening scope.
  • Use the reference architecture to see where each playbook sits, and the glossary for terms.
