Playbook 06 · Shared Python Libraries

Designing the library

Before packaging anything, decide where the seam between library and notebook runs. This page defines the transform, projection and call pattern, the load and merge helpers that implement it, and the API rules that keep a shared library from breaking its callers.

The notebook pattern the library comes from

Most silver and gold notebooks follow the same three steps: a transformation function that derives columns, a projection list that fixes the output columns, and a call to a load function that reads, filters, writes and reports. The first two are specific to a table. The third is identical everywhere, which makes it the natural thing to lift into a library.

Step 1: the transformation (stays in the notebook)

A transformation is a pure function from DataFrame to DataFrame. It reads nothing, writes nothing and uses no globals, so it can be unit tested with a three-row DataFrame.

from pyspark.sql import DataFrame
from pyspark.sql import functions as F


def orders_transform(df: DataFrame) -> DataFrame:
    """Derive net amount, order month and a large-order flag."""
    net = F.round(
        F.col("quantity") * F.col("unit_price") - F.coalesce(F.col("discount_amount"), F.lit(0)),
        2,
    )
    return (
        df.withColumn("net_amount", net)
          .withColumn("order_month", F.date_trunc("month", F.col("order_ts")).cast("date"))
          .withColumn("is_large_order", F.col("net_amount") >= F.lit(1000))
    )

Step 2: the projection (stays in the notebook)

The projection is data, not code: the ordered list of columns the target table must have. Keeping it explicit makes schema changes visible in review and lets the load function fail fast when a column goes missing.

ORDERS_SELECT = [
    "order_id", "customer_id", "order_ts", "order_month",
    "quantity", "unit_price", "discount_amount", "net_amount",
    "is_large_order", "is_deleted", "_ingested_at",
]

Step 3: the call (one line of intent)

from contoso_fabric_utils import full_load_overwrite

metrics = full_load_overwrite(
    source_table="orders",            # resolved against the notebook's default lakehouse
    target_table="fact_orders",
    transform_fn=orders_transform,
    select_cols=ORDERS_SELECT,
    row_filter="coalesce(is_deleted, false) = false",   # prune soft-deleted rows early
    validate_required_cols=["order_id", "customer_id", "quantity", "unit_price"],
)
print(metrics)   # {'rows_written': 12840}

Everything the library cannot know (which columns, which filter, which transformation) arrives as an argument. Everything the library can standardize (reading, validating, writing, counting) lives behind the function.

What changes when the code moves out of the notebook

Copying the cell into a module verbatim does not work and, in a few places, would not be good enough if it did. These are the deliberate differences from the notebook version.

Notebook versionLibrary versionWhy
Uses the notebook's global sparkTakes an optional spark argument and falls back to the active sessionA module has no global spark; the import would work and the first call would raise NameError. Injection also makes unit tests and thread pools straightforward.
overwrite_schema=True by defaultFalse by defaultA silent schema change on a gold table breaks downstream semantic models. Make it an explicit choice per call.
Counts the source and the target after the writeCounts the target only, and only if askedCounting the source after the write re-executes the read and filter. That is a second scan of the source for a log line.
Missing columns in a cast list become typed nullsThey raise unless add_missing_as_null=TrueA typed null silently hides an upstream change. Opt in when you really want a stable output schema regardless of the source.
print for the summaryLogs through logging and returns a dictionaryLog lines can be filtered and captured; the return value lets the notebook assert or exit with it.
Module name io.pyModule name loads.pyA module called io shadows the standard library as soon as its folder lands on sys.path, which is exactly what the notebook-resources trick in testing without an Environment does.

Changing a default is a breaking change

Flipping overwrite_schema from True to False changes behavior for every existing caller. Make that kind of change in a major version, say so in the changelog, and search your notebooks for callers before you release. See API design rules.

Incremental helpers

Full overwrite is the right default for small dimensions and for tables that are cheap to rebuild. For large facts you need an incremental path. Two small helpers cover most of it. max_value reads a high-water mark from the target. merge_upsert applies a deduplicated change set to a Delta table with MERGE.

from pyspark.sql import functions as F
from contoso_fabric_utils import max_value, merge_upsert

# 1) High-water mark from the target (None on the very first run)
last_ts = max_value("silver_orders", "_modified_at")

# 2) Pick up only changed rows, with a small overlap to tolerate late arrivals
changes = spark.table("bronze_orders")
if last_ts is not None:
    changes = changes.filter(F.col("_modified_at") > F.lit(last_ts) - F.expr("INTERVAL 1 HOUR"))

# 3) Upsert; rows flagged as deleted at the source are removed from the target
metrics = merge_upsert(
    source_df=changes,
    target_table="silver_orders",
    key_cols=["order_id"],
    delete_when="s.is_deleted = true",   # condition on the source alias s
    ignore_cols=["is_deleted"],          # used by the condition, never written to the target
)
print(metrics)   # {'inserted': 120, 'updated': 31, 'deleted': 4}

Caution

Concurrent merges into the same Delta table can conflict and fail with a concurrency exception. Serialize writers per table in the orchestration layer, or retry with backoff. A merge helper cannot hide that; it can only make it visible by not swallowing the error.

API design rules

A shared library is consumed by people who cannot read its source quickly and who run it unattended. These rules keep it safe to depend on.

RuleWhat it looks likeWhat happens if you ignore it
Keyword-only argumentsdef f(*, source_table, target_table, ...)Adding or reordering a parameter silently changes the meaning of positional calls
No hidden globalsTake a spark argument; never read spark, mssparkutils or notebook variables from the caller's namespaceNameError at call time, or tests that only pass inside Fabric
No environment-specific valuesWorkspace names, lakehouse IDs, endpoints and connection IDs are arguments, supplied from variable librariesA wheel that only works in one stage, and a new release for every configuration change
Pure transformations, explicit side effectsFunctions that write say so in their name and return metricsCallers cannot tell a safe helper from one that overwrites a table
Fail with names, not stack tracesValueError("Missing required columns in 'orders': ['quantity']")A pipeline failure at night with no clue which column or table
Idempotent by designRe-running a load with the same inputs leaves the same target stateRetries double-count or duplicate rows
Minimal dependenciesDepend on nothing the Spark runtime already provides; do not list pyspark or delta-spark as runtime dependenciesThe Environment tries to resolve and install a second PySpark next to the runtime's own
Semantic versions and a changelogBreaking change means a new major version"Works on my Environment" incidents when a minor release changes behavior

Key takeaways

  • Lift the third step of the pattern (the call) into the library; leave transformations and projections in notebooks as arguments.
  • Remove every dependency on notebook globals; accept a spark argument and fall back to the active session.
  • Make risky behavior opt-in: schema overwrite, typed-null columns, counting the source.
  • Give merge_upsert explicit column lists, a duplicate-key check and flag-driven deletes, in a fixed clause order.
  • Never put workspace names, IDs or endpoints in the wheel.
