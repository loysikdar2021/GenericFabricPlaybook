Playbook 06 · Shared Python Libraries

CI/CD with GitHub Actions

Uploading a wheel by hand does not scale past one workspace and one person. This page automates the path from a tagged commit to a published Environment in each stage: tests, one build, OIDC sign-in with no stored secrets, upload and publish through the Fabric REST API, and approvals before TST and PRD.

Pipeline design: build once, promote the same file

The most important design decision is that the wheel is built exactly once, from a tag, and that same file is uploaded to every stage. Rebuilding per stage produces three artifacts that are supposed to be identical and sometimes are not (a changed dependency pin, a different Python patch version, a timestamp). If PRD runs a different file than the one TST approved, TST proved nothing.

  • Pull requests run the tests only. Nothing is built for release and nothing touches Fabric.
  • A version tag (v1.4.0) triggers test, build and the first deployment. The tag must equal the version in pyproject.toml.
  • GitHub Environments named dev, tst and prd hold the per-stage identifiers and the approval rules. Required reviewers on tst and prd are the promotion gate.
  • One Fabric writer. The workflow owns the Environment's custom library list. Nobody edits it by hand and Git sync of that item is not a second writer (see Environments across stages).

Identity, secrets and permissions

The workflow signs in to Microsoft Entra ID with OpenID Connect: GitHub issues a short-lived token for the job, Entra exchanges it for an access token against a federated credential on an app registration, and no client secret is ever stored in GitHub. The access token is then used as a bearer token against the Fabric REST API.

  1. Create an app registration per stage

    One service principal for DEV and TST and a separate one for PRD limits the blast radius of a misconfigured workflow. Note each application (client) ID and the tenant ID.

  2. Add a federated credential

    Trust GitHub's token issuer for the repository and the GitHub environment, for example the subject repo:contoso-org/fabric-etl-utils:environment:prd. A credential scoped to an environment means only jobs that passed that environment's protection rules can obtain a token.

  3. Allow service principals to call Fabric APIs

    In the Fabric admin portal, enable the tenant setting Service principals can call Fabric public APIs and include the service principal (through a security group) in the allowed list.

  4. Grant workspace access

    Add the service principal to each target workspace with a role that can write to the Environment item (for example Contributor). The Environment APIs require write permission on the item.

  5. Create the Environment item once per stage

    The workflow updates an existing Environment; it does not create one. Record each workspace ID and Environment item ID.

  6. Store the identifiers in GitHub

    Create the three GitHub environments and add the names below.

Protect the tag, not just the branch

Whoever can push a v* tag can start a release. Restrict tag creation to maintainers with a tag ruleset, require pull-request review on main, and put required reviewers on the tst and prd GitHub environments. Those three controls together are your change-management record.

Verify against Microsoft Learn

Tenant setting names and the roles required by each API are maintained in Developer admin settings and on each REST reference page. Confirm them for your tenant before the first run; a missing setting shows up as an authorization error, not a clear message.

The Fabric REST sequence

Four documented Environment operations do all the work. The workflow calls them in this order.

StepCallNotes
List staged librariesGET /v1/workspaces/{workspaceId}/environments/{environmentId}/staging/libraries?beta=FalseReturns libraries with name and libraryType (Custom or External). Large lists are paged with a continuation token.
Delete an old wheelDELETE .../staging/libraries/{libraryName}Use the full file name with the extension. One file per call.
Upload the new wheelPOST .../staging/libraries/{libraryName}Body is the file with Content-Type: application/octet-stream. One file at a time. The reference documents a request-size limit; keep the wheel far below it.
PublishPOST .../staging/publish?beta=falseLong-running operation: returns 202 with Location, x-ms-operation-id and Retry-After. Only one publish can run at a time.
Check stateGET .../environments/{environmentId}properties.publishDetails.state is Running, Waiting, Success, Failed, Cancelling or Cancelled.
VerifyGET .../environments/{environmentId}/libraries?beta=FalseThe published library list. The wheel must be in it.

Pass the beta parameter explicitly

The Environment APIs are in a transition from preview contracts to stable ones, controlled by a beta query parameter. Always send beta=false on the calls that document it so your script uses the stable request and response shapes regardless of the service default. Re-check the migration notes in Manage the Environment through public APIs when you maintain the script.

The publish script

Keep the Fabric calls in one small script so you can run it locally while debugging. It needs only curl and jq, both present on GitHub-hosted Ubuntu runners.

#!/usr/bin/env bash
# Upload a wheel to a Fabric Environment, publish it, wait, and verify.
# Usage: publish_to_environment.sh <workspace-id> <environment-id> <wheel-path>
# Needs: FABRIC_TOKEN (bearer token for https://api.fabric.microsoft.com), curl, jq.
set -euo pipefail

workspace_id="$1"; environment_id="$2"; wheel="$3"
name="$(basename "$wheel")"
distribution="${name%%-*}"                  # e.g. contoso_fabric_utils
timeout_seconds="${TIMEOUT_SECONDS:-2400}"
env_url="https://api.fabric.microsoft.com/v1/workspaces/${workspace_id}/environments/${environment_id}"

call() {
  curl --silent --show-error --fail-with-body \
       -H "Authorization: Bearer ${FABRIC_TOKEN}" "$@"
}

echo "1/4 Remove existing ${distribution} wheels from staging"
call "${env_url}/staging/libraries?beta=False" \
  | jq -r --arg d "${distribution}-" \
      '.libraries[]? | select(.libraryType == "Custom") | .name | select(startswith($d))' \
  | while read -r old; do
      echo "    deleting ${old}"
      call --request DELETE --output /dev/null "${env_url}/staging/libraries/${old}"
    done

echo "2/4 Upload ${name}"
call --request POST -H "Content-Type: application/octet-stream" \
     --data-binary "@${wheel}" --output /dev/null \
     "${env_url}/staging/libraries/${name}"

echo "3/4 Publish"
headers="$(mktemp)"
call --request POST --data '' --dump-header "${headers}" --output /dev/null \
     "${env_url}/staging/publish?beta=false"
retry_after="$(awk 'tolower($1) == "retry-after:" {print $2}' "${headers}" | tr -d '\r')"

echo "4/4 Wait for the publish, then verify the wheel is in the published list"
sleep "${retry_after:-30}"
deadline=$(( $(date +%s) + timeout_seconds ))
while true; do
  state="$(call "${env_url}" | jq -r '.properties.publishDetails.state')"
  echo "    publish state: ${state}"
  case "${state}" in
    Success)
      if call "${env_url}/libraries?beta=False" \
           | jq -e --arg n "${name}" '.libraries[]? | select(.name == $n)' > /dev/null; then
        echo "Published ${name}"
        exit 0
      fi
      echo "Publish succeeded but ${name} is not in the published list" >&2
      exit 1 ;;
    Failed|Cancelled)
      echo "Publish ended as ${state}" >&2
      exit 1 ;;
  esac
  if [ "$(date +%s)" -ge "${deadline}" ]; then
    echo "Timed out waiting for the publish" >&2
    exit 1
  fi
  sleep 30
done

Three details are worth knowing. The script deletes every existing wheel of the same distribution before it uploads, which enforces "exactly one version per Environment" and makes a re-run of the same tag idempotent. It waits for the service's Retry-After interval before the first poll so it cannot read a stale Success from the previous publish. And success is defined by the published library list, not by the HTTP status of the publish call.

The workflows

A caller workflow runs tests and the build, then calls a reusable deployment workflow three times. The reusable workflow declares the GitHub environment, which is what triggers the approval rule.

name: release

on:
  pull_request:
    branches: [main]
  push:
    tags: ["v*.*.*"]

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
          cache: pip
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: "17"
      - run: python -m pip install -e ".[test]"
      - run: pytest

  build:
    if: startsWith(github.ref, 'refs/tags/v')
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - name: Tag must equal the project version
        run: |
          version="$(python -c "import tomllib; print(tomllib.load(open('pyproject.toml', 'rb'))['project']['version'])")"
          if [ "v${version}" != "${GITHUB_REF_NAME}" ]; then
            echo "Tag ${GITHUB_REF_NAME} does not match project version ${version}" >&2
            exit 1
          fi
      - name: Build and check
        run: |
          python -m pip install --upgrade build twine
          python -m build
          twine check dist/*
      - name: Smoke-test the wheel in a clean environment
        run: |
          python -m venv /tmp/wheel-check
          /tmp/wheel-check/bin/python -m pip install "$(ls dist/*.whl)[test]"
          /tmp/wheel-check/bin/python -c "import contoso_fabric_utils as m; print(m.__version__)"
      - uses: actions/upload-artifact@v4
        with:
          name: wheel
          path: dist/*.whl
          if-no-files-found: error

  deploy-dev:
    needs: build
    permissions: { id-token: write, contents: read }
    uses: ./.github/workflows/deploy-environment.yml
    with:
      stage: dev
    secrets: inherit

  deploy-tst:
    needs: deploy-dev
    permissions: { id-token: write, contents: read }
    uses: ./.github/workflows/deploy-environment.yml
    with:
      stage: tst
    secrets: inherit

  deploy-prd:
    needs: deploy-tst
    permissions: { id-token: write, contents: read }
    uses: ./.github/workflows/deploy-environment.yml
    with:
      stage: prd
    secrets: inherit
name: deploy-environment

on:
  workflow_call:
    inputs:
      stage:
        description: GitHub environment name (dev, tst or prd)
        required: true
        type: string

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: ${{ inputs.stage }}          # approval rules and per-stage values live here
    concurrency:
      group: fabric-environment-${{ inputs.stage }}
      cancel-in-progress: false               # never cancel a publish half-way
    permissions:
      id-token: write                         # required to request the OIDC token
      contents: read
    steps:
      - uses: actions/checkout@v4             # for scripts/publish_to_environment.sh
      - uses: actions/download-artifact@v4
        with:
          name: wheel
          path: dist
      - uses: azure/login@v2
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          allow-no-subscriptions: true        # the identity needs no Azure subscription
      - name: Get a Fabric access token
        run: |
          token="$(az account get-access-token --resource https://api.fabric.microsoft.com --query accessToken -o tsv)"
          echo "::add-mask::${token}"
          echo "FABRIC_TOKEN=${token}" >> "$GITHUB_ENV"
      - name: Upload and publish
        run: |
          bash scripts/publish_to_environment.sh \
            "${{ vars.FABRIC_WORKSPACE_ID }}" \
            "${{ vars.FABRIC_ENVIRONMENT_ID }}" \
            dist/*.whl

Prove the release with a smoke notebook

After the publish, run a tiny notebook in that stage's workspace through the Fabric Job Scheduler API (the Environment must be attached to it, or be the workspace default). Pass the expected version as a parameter and fail the stage if the import reports a different one. This catches the case the publish check cannot: the Environment is published but the notebook is not attached to it.

# Parameter cell: toggled as "parameters" and overwritten by the caller
expected_version = "0.0.0"

import contoso_fabric_utils as lib

assert lib.__version__ == expected_version, (
    f"Expected contoso_fabric_utils {expected_version}, got {lib.__version__}"
)
print(f"OK: contoso_fabric_utils {lib.__version__}")

Azure Artifact Feed support is labeled preview and carries version and network restrictions; read Manage libraries in Fabric environments for the current list. Release practice

  • Keep a CHANGELOG.md and write breaking changes at the top of the release notes.
  • Use pre-release versions (1.5.0rc1) to try a change in TST without promoting it.
  • Roll back by re-running the deployment for the previous tag; the script replaces the newer wheel with the older one. Keep previous wheels as release assets so rollback does not depend on artifact retention.
  • Allow only one release in flight per Environment (concurrency group) because an Environment accepts a single publish at a time.
  • Set a generous but finite timeout on the publish wait and alert on it; a hung publish blocks every later release.
  • Announce deprecations a release ahead using warnings.warn(..., DeprecationWarning) inside the library.

Key takeaways

  • Build the wheel once from a tag whose name equals the project version, and deploy that exact file to every stage.
  • Use OIDC with a federated credential per GitHub environment; there is no secret to rotate or leak.
  • Define success as "the wheel is in the published library list", not "the publish call returned".
  • Delete older wheels of the same distribution before uploading, and serialize releases per Environment.
  • Gate TST and PRD with required reviewers on the GitHub environment and a protected tag.
