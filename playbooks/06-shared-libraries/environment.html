Installing in a Fabric Environment

An Environment turns the wheel into a durable, workspace-visible dependency. This page walks through upload, publish and attach, explains what Full and Quick publish modes cost you, and shows why pipelines should never depend on %pip install.

What an Environment is, and where it applies

A Fabric Environment is a workspace item that defines the configuration of a Spark session: the runtime, the compute settings, the libraries and a small set of resource files. Libraries come from three places: the built-in set that ships with the runtime, public or private repositories (External repositories), and files you upload under Custom libraries. For a Python library the custom file is a .whl (Fabric also accepts .py and .jar, and .tar.gz for R only).

Two properties matter for how you operate it:

  • Save versus Publish. Saving stages your changes; they are not effective until you publish. An Environment accepts one publish at a time, and you cannot edit libraries or compute while a publish is running. Changes to the Resources folder are the exception: they are real time and need no publish.
  • Attachment decides what a session gets. A notebook or Spark job definition either names an Environment or uses Workspace default. The next figure shows how a session resolves it.

Create the Environment and install the wheel

Do this first in the DEV workspace. Use an Environment per stage and the same item name in each (for example ENV_SALES_SLV_SharedLibs).

  1. Create the Environment

    In the workspace select New item, search for Environment, name it, and select Create.

  2. Select the runtime

    On the Environment's runtime dropdown choose the runtime you tested the wheel against (the one whose Python and Spark versions match requires-python and the test extra). Changing the runtime later needs another publish, and a custom library built for one Python minor version may not work on another.

  3. Upload the wheel

    Open Libraries, then Custom libraries, and use Upload to add contoso_fabric_utils-1.4.0-py3-none-any.whl. Choose Full publish mode for anything that pipelines or scheduled jobs will run.

  4. Add public libraries only if the wheel needs them

    Under External repositories add PyPI or Conda packages. Keep this list short; each one is resolved at publish time and must not conflict with built-in packages.

  5. Save and publish

    On the Home tab select Save, then Publish and Publish all. Watch View progress in the banner and wait for the success notification. A failure notification names the conflicting library.

  6. Attach it

    Per item: open the notebook (or Spark job definition), choose the Environment in the toolbar dropdown, and confirm. For the whole workspace: Workspace settings, Data Engineering/Science, Spark settings, Environment tab, turn Set default environment on, pick the item and save. Only workspace admins can do this, and only admins can change the contents of an Environment that is the workspace default.

  7. Verify in a new session

    Start a session and run the import check below. A session that was already running keeps the libraries it started with.

import contoso_fabric_utils as lib

print(lib.__version__)                 # expect the version you just published
print(lib.full_load_overwrite.__doc__) # confirms you are importing the packaged module

Upgrading to a new version

Wheel files carry their version in the file name, so uploading 1.5.0 does not replace 1.4.0; both would sit in the list. Delete the old file from Custom libraries before you publish, so the Environment contains exactly one version of the distribution. The CI/CD page automates this.

Sharing

When you share a notebook or Spark job definition with someone, also grant Read on the Environment it uses. Recipients of an Environment get Read by default, which is enough to attach it; Edit lets them change its contents.

Publish modes and their effect on session start

When you add custom libraries you pick a publish mode. The choice decides when dependency work happens: once at publish time, or on every session start.

Full modeQuick mode
What publish doesResolves dependencies, validates compatibility and creates a stable library snapshotSkips dependency processing
Publish timeTypically 3 to 6 minutesAbout 5 seconds
Session startAdds roughly 1 to 3 minutes to deploy the snapshot, depending on dependency sizePackages install when the first Python cell runs
Works withNotebooks and Spark job definitions; every library sourceNotebooks only; public repositories and most custom formats (not .jar)
ReproducibilityHigh: every session starts from the same snapshotLower: dependencies are installed per session
Use forPipelines, scheduled runs, shared and production workloads, more than about ten packagesRapid iteration while you develop the library or a notebook

You can mix modes: a validated Full-mode snapshot is applied first and Quick-mode packages install on top, overriding same-named packages for that session only. To move a custom library between modes, download it, remove it, and upload it in the other mode.

Verify against Microsoft Learn

Publish durations, session-start overhead and the availability of Quick mode and custom live pools are documented as typical values and change with the platform. Re-read Select publish mode for libraries before you set a timeout in automation. Older guidance of 15 to 30 minutes per publish no longer matches the documented figures for Full mode, but your own dependency set decides the real number: measure it and poll for the result instead of sleeping for a fixed time.

Why not %pip install in pipelines?

%pip install (and %conda install) are inline commands. They install into the current session of the current notebook, restart the Python interpreter, and are not touched by Environment publishing. That is perfect for a one-off experiment and wrong for unattended work, for four reasons.

  • Disabled by default. Inline library commands are turned off in pipeline notebook runs. You can switch them on by passing a boolean _inlineInstallationEnabled parameter set to true on the notebook activity, but the documentation steers you away from it.
  • Resolved on every run. A fresh dependency resolution can produce a different tree from night to night. A transitive dependency that releases at 01:00 can break the 02:00 run for no change you made.
  • Slower and noisier. Every run spends session time installing, and an interpreter restart discards variables defined before the command, so installs must be the first cells.
  • Unsupported combinations. %pip install is not supported in high concurrency mode, and inline library commands are not supported in notebooks run through a reference run.
%pip install of a wheelEnvironment custom library
ScopeOne session of one notebookEvery notebook or job that attaches it
Dependency resolutionEach time the cell runsOnce, at publish (Full mode)
In pipeline runsOff by default; opt in per activityWorks as is; recommended
Audit trailWhatever the notebook cell saysThe Environment's library list and publish state
Best forInteractive experiments, testing a buildProduction, scheduled and shared work

Remove leftover installs

A notebook that still contains %pip install of the old wheel after you move to an Environment will either be ignored in a pipeline or, if inline installation was enabled, silently replace the Environment's version for that session. Search notebooks for inline installs when you adopt the library.

Use the library in a notebook

With the Environment published and attached, the notebook change is mechanical: delete the cell that defines the helper, add an import, and leave the transformation, projection and call cells as they are.

# Cell 1: 70 lines defining full_load_overwrite(...) pasted from another notebook

# Cell 2: orders_transform(...)
# Cell 3: ORDERS_SELECT = [...]

# Cell 4
metrics = full_load_overwrite(
    source_table="orders",
    target_table="fact_orders",
    transform_fn=orders_transform,
    select_cols=ORDERS_SELECT,
)
# Cell 1
from contoso_fabric_utils import full_load_overwrite

# Cell 2: orders_transform(...)          unchanged
# Cell 3: ORDERS_SELECT = [...]          unchanged

# Cell 4                                 unchanged
metrics = full_load_overwrite(
    source_table="orders",
    target_table="fact_orders",
    transform_fn=orders_transform,
    select_cols=ORDERS_SELECT,
)

Run the notebook once against a scratch target table first. If the import fails, work through this list.

Environments across stages and workspaces

Treat the Environment as a deployable item with its own lifecycle. There are three ways to get the same library set into DEV, TST and PRD, and you should choose exactly one writer per Environment.

MechanismHow it worksWatch for
CI uploads and publishes (recommended for libraries)The pipeline in the CI/CD page calls the Environment REST API in each stageDo not also edit the library list by hand; the next release will overwrite it
Git integrationThe workspace serializes the Environment's libraries (public as YAML, custom as the file itself) and Spark compute settings into the repositoryChanges synced from Git land in staging; publish after every sync. Each commit is limited to 150 MB, and committing wheels puts binaries in your workspace repository
Deployment pipelinesDeploys the Environment item to the next stage and preserves its published stateCustom pools are not carried; compute then falls back to defaults and the item can keep showing a difference. See Deployment Pipelines and Promotion

An Environment can also be attached from another workspace. Both workspaces must share the same capacity and network security settings or the session fails to start, and the other Environment's compute configuration is ignored in favor of the consuming workspace's settings. That makes a single central library Environment feasible inside one capacity, but it couples every consuming workspace to one release schedule; per-stage Environments with a promoted wheel keep PRD insulated from a bad DEV publish.

Locked-down workspaces

If a workspace uses outbound access protection or managed virtual networks, public repositories such as PyPI are not reachable. Custom libraries you upload directly still work, which is another reason to keep the wheel's own dependency list empty. See Manage libraries with limited network access.

Key takeaways

  • Upload the wheel under Custom libraries, publish in Full mode, and attach the Environment; only then do notebooks and pipelines see it.
  • Full mode trades minutes at publish and session start for a reproducible snapshot; Quick mode trades reproducibility for speed. Pipelines get Full mode.
  • Never rely on %pip install for unattended runs: it is off by default there and resolves dependencies on every run.
  • Keep exactly one wheel version in an Environment; delete the old file before publishing the new one.
  • Pick one writer per Environment (CI, Git sync or deployment pipeline) and publish after every change.
