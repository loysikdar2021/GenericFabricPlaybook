Playbook 06 · Shared Python Libraries

Shared Python libraries for Fabric Spark

Package the utilities your teams keep pasting into notebooks as a versioned Python wheel, test it in CI, and deliver it through a Fabric Environment so every notebook and pipeline run imports the same vetted code.

  • Audience data engineers, platform engineers
  • Level intermediate
  • Reading time about 80 minutes

The problem: utilities copied between notebooks

Every team that writes more than a handful of Fabric notebooks ends up with the same helper cells: a full-reload function, a merge wrapper, a column validator, a row-count logger. Without a shared library each notebook carries its own copy. The copies diverge within weeks. One gets a bug fix, one gets an unrelated edit, one is never touched again. Nobody can answer "which version of the merge helper ran last night?", and a defect fixed in one place is still live in ten others.

The cost is not only duplication. Helper code pasted into a notebook cannot be unit tested, cannot be reviewed as a unit, has no version number, and makes every notebook longer than the business logic it exists to express. When a pipeline fails at 02:00 you are debugging a notebook that contains 150 lines of plumbing and 20 lines of intent.

The approach in one paragraph

Write the utilities as an ordinary Python package, declare it in pyproject.toml, build a wheel (.whl) once in CI, upload that wheel to a Fabric Environment as a custom library, publish the Environment, and attach it to notebooks and Spark job definitions (or set it as the workspace default). Notebooks then contain a single import line instead of the helper code. Pipelines do not install anything: they run notebooks whose Environment is already attached, which is exactly why this is the supported way to make libraries available to scheduled work.

  2. Packagepyproject.toml, src layout, tests, a local wheel build.
  3. InstallUpload, publish and attach through a Fabric Environment.
  4. AutomateBuild once in CI, promote the same file to each stage.

When to use a shared library (and when not to)

A shared library pays for itself when the same mechanics appear in several notebooks and someone is willing to own them. The rule of thumb is share mechanics, not business logic: loading, merging, validating, logging and auditing belong in the library; the transformation that turns orders into a gold fact table stays in the notebook (or in a domain library owned by that domain).

Put it in the library whenKeep it in the notebook when
The same logic appears in three or more notebooksIt is specific to one table or one report
You want unit tests and a review process for itIt is exploratory or changes with every run
A defect would be expensive and should be fixed onceOnly one person understands or maintains it
It has no side effects beyond its arguments (read, transform, write)It hard-codes workspace, lakehouse or table names
It is stable enough to version with semantic versionsIt would need a release every time a requirement changes

Watch out

A library is shared infrastructure. A breaking change in 1.x breaks every notebook that attaches the Environment. Treat the public API like a contract: semantic versions, a changelog, deprecation windows, and a staged rollout through DEV and TST before PRD (see the CI/CD page).

Prerequisites

  • A Fabric workspace on a Fabric capacity where you can create Environment items.
  • A Git repository (the examples use GitHub and contoso-org/fabric-analytics) with branch protection on the default branch.
  • Python 3.11 or later on the build machine, matching the Python version of the Spark runtime your Environment selects.
  • For automation: a Microsoft Entra service principal with a federated credential for GitHub Actions, the tenant setting that lets service principals call Fabric public APIs, and a workspace role on each target workspace.
  • A naming convention for Environment items, for example ENV_SALES_SLV_SharedLibs, so a library Environment is recognizable in each stage.

What you will have at the end

  • A package repository with a src/ layout, a PEP 621 pyproject.toml, unit tests and a reproducible wheel build.
  • A small, neutral API (full_load_overwrite, merge_upsert, max_value) you can extend.
  • An Environment per stage with the wheel published, attached to notebooks, and verified by a smoke test.
  • A GitHub Actions workflow that tests, builds once and promotes the same wheel through DEV, TST and PRD with approvals.
  • A decision table for the cases where an Environment is not the right distribution mechanism.

Key facts at a glance

Artifact
A pure-Python wheel (py3-none-any). No compiled extensions, no platform tag.
Where it lives in Fabric
Environment item, Custom libraries. Fabric accepts .whl, .py, .jar and (R only) .tar.gz; use .whl for Python packages.
Publish modes
Full resolves dependencies and builds a snapshot (typically 3 to 6 minutes to publish, plus 1 to 3 minutes of session start). Quick publishes in seconds and installs at notebook session start. See publish modes.
Pipelines
Inline %pip install is disabled by default in pipeline runs. Attach an Environment to the notebook instead.
Automation surface
Environment REST API: upload custom library, publish, read publish state.

Verify against Microsoft Learn

Publish times, Quick mode, Azure Artifact Feed support and the Environment REST API contract evolve. Before you build automation, re-read Manage libraries in Fabric environments and Manage the Environment through public APIs.

Key takeaways

  • Share mechanics (load, merge, validate, log), not business logic.
  • Ship a wheel through an Environment; do not rely on %pip for anything that runs unattended.
  • Build the wheel once in CI and promote the same file through every stage.
  • Version the library with semantic versions and treat its public API as a contract.
