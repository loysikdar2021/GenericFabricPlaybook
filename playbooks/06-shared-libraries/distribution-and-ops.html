Playbook 06 · Shared Python Libraries

Options, operations, checklist

A wheel in an Environment is the default, not the only answer. This page compares every realistic way to share code between Fabric notebooks, shows how to test without publishing anything, and covers the governance, troubleshooting and validation work that keeps a shared library trustworthy.

Distribution options compared

The right mechanism depends on three questions: does the code run unattended, how far does it need to travel, and how much process does it deserve. The matrix lists what each option gives you and what it costs.

OptionSafe in pipeline runsVersionedBeyond one workspaceNotes
Wheel in an Environment, Full modeYesYesPartlyEvery item that attaches the Environment gets the same snapshot. Publish takes minutes and session start gains a dependency-deployment step. Other workspaces attach the same Environment only through your promotion process (see Environments across stages).
Wheel in an Environment, Quick modeNotebooks onlyYesPartlyNotebooks only, not Spark job definitions. Publish takes seconds; the wheel installs at session start. Best for the library's own developers.
Private package feed PreviewYesYesYesFull mode only. Needs a feed, a connection and a republish to pick up new versions. Not supported with Private Link or outbound access protection.

Wheel in Lakehouse Files plus %pip install of the mounted pathInline install rules applyFolder conventionVia the default lakehouseEasy to drift; breaks if the default lakehouse changes. Access control is the lakehouse's, not the library's.
%run a shared notebookYesNoNoSame workspace only. No semantic versions, no unit tests, and everything lands in the caller's namespace.

When each option earns its place

  • Environment, Full mode is the production answer for a single platform team and a handful of workspaces. Everything in this playbook assumes it.
  • Environment, Quick mode is for the library's own developers: change, publish in seconds, retest in a notebook. Promote the validated version to Full mode.
  • A private feed is worth the extra moving parts when the same package is consumed by Fabric and by something else (another Spark platform, a function app) or when you already run an organization-wide feed with its own access rules.
  • Notebook resources and Lakehouse Files are for testing and one-off distribution. They are session-scoped and unmanaged; do not let a production pipeline depend on them.
  • %run suits a few dozen lines of configuration-like code that every notebook in one workspace needs, where a package would be overkill. It copies names into the caller's namespace, nests at most five levels, and accepts only simple parameter types.

Verify against Microsoft Learn

Limits for resources (total size, per-file size, file count), the behavior of %run and the status of private-feed support are documented per article and change over time. Check Notebook resources, Reference run and Manage libraries in Fabric environments before you commit to one.

Testing without creating an Environment

You can try a build before it has an Environment, or iterate on it without waiting for a publish. These techniques are session-scoped on purpose: they cannot affect any other notebook, and they disappear when the session ends.

Install the wheel from notebook resources

Upload the wheel to the notebook's Resources (the built-in folder), then install it in the first cells of the notebook. This is the quickest way to test a release candidate.

%pip install "builtin/contoso_fabric_utils-1.5.0rc1-py3-none-any.whl"
import contoso_fabric_utils as lib
print(lib.__version__)    # 1.5.0rc1

The installation restarts the Python interpreter, so variables defined before it are lost; keep installs at the top. The package is available on the driver and the executors for that session only.

Import source files straight from resources

For a tight edit loop you can skip packaging entirely: upload the package folder (contoso_fabric_utils/ with its __init__.py) to the notebook's built-in resources and put the resources folder on the import path.

import sys

sys.path.insert(0, "builtin")        # folder that CONTAINS contoso_fabric_utils/

import contoso_fabric_utils as lib   # resolves to builtin/contoso_fabric_utils/__init__.py
print(lib.__version__)               # "0+unknown": not installed, so there is no package metadata

Put the parent folder on the path, never the package folder

If you add builtin/contoso_fabric_utils itself to sys.path, every module inside it becomes importable by its bare name. A module called io.py would then shadow the standard library io module and break unrelated imports. This is why the package module is called loads.py and not io.py.

Relative reads and writes against resources do not work in a high concurrency session, so use a standard session for this technique. Each resources folder (built-in and Environment) is limited to 500 MB in total, 100 MB per file and 100 files and folders, which is another reason this is a testing tool and not a distribution channel. Files in either folder are scoped to the session and are not touched by an Environment publish.

Install from Lakehouse Files

If several people need to try the same candidate, put the wheel in a lakehouse folder (for example Files/libs/) and install from the mounted path. The lakehouse must be the notebook's default lakehouse so that it is mounted as a local path.

%pip install "/lakehouse/default/Files/libs/contoso_fabric_utils-1.5.0rc1-py3-none-any.whl"

Share a few functions with %run

%run NB_SALES_SLV_CommonHelpers { "env_name": "dev" }

%run executes another notebook in the current context, so everything it defines is available afterward. It works in interactive and pipeline runs, but only for notebooks in the same workspace, with a limited set of parameter types (integer, float, boolean, string) and a maximum nesting depth. It is also how copy-paste returns in disguise: there is no version number, and a change to the shared notebook affects every caller immediately. A script from the notebook's own resources can be run with %run -b script.py.

TechniqueWhat you give up compared with an Environment wheel
%pip from built-in resourcesPersistence, pipeline support, a single attached version for all notebooks

Lakehouse FilesAccess control specific to the library; anything stops working if the default lakehouse changes

Workspace usage patterns and governance

PatternGood forTrade-off
Workspace default EnvironmentEvery notebook and Spark job in the workspace should get the library without anyone remembering to attach itOnly a workspace admin can choose which Environment is the default, which is a useful control. Items inherit it, including ones that do not need it; if the default is ever changed or removed, imports fail in every item that relied on it
Attach per itemStricter control, or workspaces that host teams with different library setsAn unattached item fails with ModuleNotFoundError; attachment must be reviewed like any other dependency

Rules that keep it trustworthy

  • Ownership. The library repository has named owners and a code-owners file, so a change to the public API cannot merge without them. See Pull-Request Notifications with CODEOWNERS.
  • Semantic versions and a support policy. State which major and minor versions are supported (for example the current major and the previous minor) and how long a deprecated function stays.
  • Review library code as production code. A notebook run from a pipeline executes with the identity of the pipeline's last modifying user, and the library runs inside it. A malicious or careless library change has the same reach as that identity.
  • No secrets, endpoints or IDs in the wheel. Pass them in at call time from variable libraries or Key Vault references, so one wheel works in every stage.
  • Keep dependencies minimal and pinned. Rely on the runtime's preinstalled packages wherever possible. Review the preinstalled list for your runtime in the runtime documentation.
  • Publish on release, not on commit. Environment publishing runs as a Spark job and consumes capacity. A publish per merge to main wastes it and exposes workspaces to unreleased code.
  • Test on each runtime you support. Python, Spark and Delta versions differ between runtimes, so a green test on one runtime does not cover another. Add a CI job per runtime you actually attach.

Validation checklist

Run through this list once per stage when you introduce the library and after every release.

  • The Environment's Custom libraries list contains exactly one wheel of the distribution, at the intended version, and the publish state is Success.
  • A new notebook session with the Environment attached imports contoso_fabric_utils and prints the expected __version__.
  • A test run of full_load_overwrite into a scratch table succeeds and returns the expected row count; merge_upsert reports the expected inserts, updates and deletes on a small change set.
  • A pipeline-triggered run of the smoke notebook passes in the stage, not only an interactive run.
  • CI logs show the upload, the publish and the verification that the wheel is in the published list.
  • The wheel's METADATA declares no runtime dependency on pyspark or delta-spark.
  • No notebook still contains an inline %pip install of the library or a pasted copy of its functions.
  • The Git tag, the project version, the wheel file name and the changelog entry agree.
  • The workspace default or per-item attachment is documented, and Read permission on the Environment is granted wherever notebooks are shared.

Keep the wheel's dependencies minimal

Rely on the Fabric runtime's preinstalled libraries wherever possible; every extra dependency is one more thing that can conflict at publish time and cannot be downloaded at all from workspaces that block public repositories. The list of preinstalled packages per runtime is linked from the Manage libraries in Fabric environments and runtime articles.

Key takeaways

  • Default to a Full-mode Environment wheel; use a private feed only for cross-platform reuse, and treat everything session-scoped as a testing tool.
  • Test candidates with %pip install builtin/...whl or by putting the parent folder on sys.path, never the package folder itself.
  • Give the library owners, a support policy and a release-only publish cadence; review its code like production code.
  • Validate with a pipeline-triggered smoke run in every stage, not just an interactive import.
