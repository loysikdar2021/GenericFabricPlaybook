Consumption and delivery

Consumption presents Gold to each kind of reader in the shape and engine it needs, without changing what the data means. Delivery gives business users reports and apps without giving them the data layers. This page builds both, from the warehouse load to the published app.

  • Audience warehouse developers, BI developers, data scientists
  • Focus serve and publish

Three consumption paths

PathWorkspaceItemsServes
WarehouseDEV_SALES_CNSM_WHLH_SALES_CNSM (Gold shortcuts only), WH_SALES_CNSMT-SQL users and tools, typed and constrained tables, SQL security, the source for semantic models

A small team can collapse these into one DEV_SALES_CNSM workspace (see the workspace pattern). Keep the three paths distinct inside it anyway, because they have different owners and different security.

Is the warehouse needed?

A Direct Lake semantic model can read Gold Delta tables directly (through the shortcut lakehouse or Gold itself), so a warehouse is not required to serve Power BI. Add it when you have T-SQL consumers, need explicit types and constraints, want SQL-based security or stored-procedure loads, or want a stable serving schema decoupled from Gold's physical layout. If none of those apply, build the semantic model on the shortcut lakehouse and skip the copy.

Warehouse from Gold shortcuts

A warehouse can query a lakehouse SQL analytics endpoint in the same workspace with three-part names. It cannot reach a lakehouse in another workspace that way. That is why the warehouse workspace has its own lakehouse whose only content is shortcuts to Gold.

  1. Create the shortcut lakehouse

    In DEV_SALES_CNSM_WH, create LH_SALES_CNSM (schema-enabled). It holds no data of its own.

  2. Create the Gold shortcuts

    Create table shortcuts in its dbo schema to the Gold tables the warehouse loads, as on the Bronze to Silver page. Keep the Gold table names.

  3. Create the warehouse

    In the same workspace use New item and create WH_SALES_CNSM.

  4. Add the lakehouse endpoint to the warehouse explorer

    In the warehouse editor, add an item (the + Warehouses action in the explorer), select the SQL analytics endpoint of LH_SALES_CNSM and confirm. Its tables can now be referenced as LH_SALES_CNSM.dbo.<table>.

  5. Create the tables

    Run the DDL script once per environment, from source control.

  6. Create the load procedures and schedule them

    Wrap each load in a stored procedure and call it from a pipeline Stored procedure or Script activity after the Gold load succeeds.

Names are case-sensitive

The warehouse default collation is case-sensitive, so dbo.Dim_Date and dbo.dim_date are different objects and column names must match exactly. Keep everything lowercase snake_case, as the naming standard requires.

Create tables with explicit types

String columns read through a lakehouse SQL analytics endpoint appear as varchar(8000). A table created with SELECT ... INTO or CREATE TABLE AS SELECT from a shortcut inherits those types, and the semantic model and every client then see 8,000-character columns. Declare the serving schema instead.

-- Run once per environment in WH_SALES_CNSM (Warehouse query editor), ideally from source control.
-- Explicit types: do not inherit varchar(8000) from the lakehouse string columns.

IF OBJECT_ID(N'dbo.dim_date', N'U') IS NULL
BEGIN
    CREATE TABLE dbo.dim_date
    (
        date_key        int          NOT NULL,
        date_value      date         NOT NULL,
        calendar_year   smallint     NOT NULL,
        quarter_number  smallint     NOT NULL,
        month_number    smallint     NOT NULL,
        month_name      varchar(20)  NOT NULL,
        day_of_week     varchar(10)  NOT NULL,
        is_weekend      bit          NOT NULL,
        fiscal_year     smallint     NULL
    );
    ALTER TABLE dbo.dim_date
        ADD CONSTRAINT pk_dim_date PRIMARY KEY NONCLUSTERED (date_key) NOT ENFORCED;
END;

IF OBJECT_ID(N'dbo.dim_customer', N'U') IS NULL
BEGIN
    CREATE TABLE dbo.dim_customer
    (
        customer_id    bigint        NOT NULL,
        customer_name  varchar(200)  NOT NULL,
        segment        varchar(50)   NULL,
        country        varchar(100)  NULL,
        is_active      bit           NOT NULL
    );
    ALTER TABLE dbo.dim_customer
        ADD CONSTRAINT pk_dim_customer PRIMARY KEY NONCLUSTERED (customer_id) NOT ENFORCED;
END;

IF OBJECT_ID(N'dbo.fact_order_lines', N'U') IS NULL
BEGIN
    CREATE TABLE dbo.fact_order_lines
    (
        order_line_id    bigint         NOT NULL,
        order_id         bigint         NOT NULL,
        product_id       bigint         NOT NULL,
        quantity         int            NOT NULL,
        unit_price       decimal(18,2)  NOT NULL,
        gross_amount     decimal(18,2)  NOT NULL,
        discount_amount  decimal(18,2)  NOT NULL,
        net_amount       decimal(18,2)  NOT NULL,
        last_modified_utc datetime2(6)  NULL
    );
    ALTER TABLE dbo.fact_order_lines
        ADD CONSTRAINT pk_fact_order_lines PRIMARY KEY NONCLUSTERED (order_line_id) NOT ENFORCED;
END;

Primary keys in a Fabric warehouse must be NONCLUSTERED and NOT ENFORCED. They document the grain and help the optimizer, but duplicates are not rejected; the load must guarantee uniqueness, which is why Gold reconciliation checks duplicate keys.

Load patterns

The original pattern was a single script per table: if the table does not exist, create it with SELECT ... INTO (renaming columns to display names with spaces), otherwise truncate and insert. It works, but it has three problems: inherited types, display names baked into the warehouse, and a moment between truncate and insert where readers see an empty table if the two run outside a transaction. Use one of the patterns below instead.

-- WH_SALES_CNSM. LH_SALES_CNSM is the consumption lakehouse in the SAME workspace;
-- its SQL analytics endpoint must be added to the warehouse explorer for three-part names to resolve.

CREATE OR ALTER PROCEDURE dbo.usp_load_dim_date
AS
BEGIN
    BEGIN TRANSACTION;          -- table-level locks, snapshot isolation: readers see old or new, never half

    TRUNCATE TABLE dbo.dim_date;

    INSERT INTO dbo.dim_date
        (date_key, date_value, calendar_year, quarter_number, month_number,
         month_name, day_of_week, is_weekend, fiscal_year)
    SELECT
        date_key,
        date_value,
        CAST(calendar_year   AS smallint),
        CAST(quarter_number  AS smallint),
        CAST(month_number    AS smallint),
        CAST(month_name      AS varchar(20)),
        CAST(day_of_week     AS varchar(10)),
        is_weekend,
        CAST(fiscal_year     AS smallint)
    FROM LH_SALES_CNSM.dbo.dim_date;

    COMMIT TRANSACTION;
END;

-- SCD type 1 upsert for a dimension that is too large to reload on every run.
CREATE OR ALTER PROCEDURE dbo.usp_merge_dim_customer
AS
BEGIN
    MERGE dbo.dim_customer AS t
    USING (
        SELECT customer_id,
               CAST(customer_name AS varchar(200)) AS customer_name,
               CAST(segment       AS varchar(50))  AS segment,
               CAST(country       AS varchar(100)) AS country,
               is_active
        FROM LH_SALES_CNSM.dbo.dim_customer
    ) AS s
        ON t.customer_id = s.customer_id
    WHEN MATCHED THEN
        UPDATE SET customer_name = s.customer_name, segment = s.segment,
                   country = s.country, is_active = s.is_active
    WHEN NOT MATCHED THEN
        INSERT (customer_id, customer_name, segment, country, is_active)
        VALUES (s.customer_id, s.customer_name, s.segment, s.country, s.is_active);
END;
-- Full rebuild of a fact table with a name swap, so readers keep using the old table until commit.
-- CREATE TABLE AS SELECT, sp_rename and DROP TABLE are all allowed inside an explicit transaction.

CREATE OR ALTER PROCEDURE dbo.usp_rebuild_fact_order_lines
AS
BEGIN
    BEGIN TRANSACTION;

    IF OBJECT_ID(N'dbo.fact_order_lines_new', N'U') IS NOT NULL
        DROP TABLE dbo.fact_order_lines_new;

    CREATE TABLE dbo.fact_order_lines_new
    AS
    SELECT
        CAST(order_line_id   AS bigint)         AS order_line_id,
        CAST(order_id        AS bigint)         AS order_id,
        CAST(product_id      AS bigint)         AS product_id,
        CAST(quantity        AS int)            AS quantity,
        CAST(unit_price      AS decimal(18,2))  AS unit_price,
        CAST(gross_amount    AS decimal(18,2))  AS gross_amount,
        CAST(discount_amount AS decimal(18,2))  AS discount_amount,
        CAST(net_amount      AS decimal(18,2))  AS net_amount,
        CAST(last_modified_utc AS datetime2(6)) AS last_modified_utc
    FROM LH_SALES_CNSM.dbo.fact_order_lines;

    IF OBJECT_ID(N'dbo.fact_order_lines', N'U') IS NOT NULL
    BEGIN
        EXEC sp_rename 'dbo.fact_order_lines', 'fact_order_lines_old';
    END;
    EXEC sp_rename 'dbo.fact_order_lines_new', 'fact_order_lines';

    IF OBJECT_ID(N'dbo.fact_order_lines_old', N'U') IS NOT NULL
        DROP TABLE dbo.fact_order_lines_old;

    COMMIT TRANSACTION;
END;
PatternUse forNotes
Truncate and insert in one transactionSmall dimensionsReaders keep the old rows until commit under snapshot isolation. The truncate takes a schema-modification lock, so concurrent writers to that table wait.
MERGELarge dimensions, facts with a reliable key and few changesWrites only changed rows. The source must have at most one row per key.
Rebuild and rename swapFacts that are rebuilt in fullNo empty window; the old table stays readable until the swap commits. Permissions granted on the table object do not carry over to a new table; grant on the schema.
Insert of new rows by watermarkAppend-only factsRead MAX(last_modified_utc) from the warehouse table and insert newer rows from the shortcut.

Friendly display names (Month Name rather than month_name) belong in the semantic model, where they can be changed without breaking SQL consumers.

Verify against Microsoft Learn

The T-SQL surface of Fabric Warehouse has grown quickly. Before relying on a statement inside a procedure or transaction, confirm it on T-SQL surface area in Fabric Data Warehouse and Transactions in Warehouse tables: in particular MERGE (now generally available; check the current limitations), TRUNCATE TABLE, CREATE TABLE AS SELECT, sp_rename and DROP TABLE within an explicit transaction, and the locks each takes. Also check whether the lakehouse SQL analytics endpoint has synced the latest Gold commit before the load reads it; the endpoint's metadata sync runs asynchronously and can lag a fresh write.

Semantic models on the warehouse

Fabric no longer creates a default semantic model for every warehouse or lakehouse. Create the models you need explicitly, in the semantic model workspace, and give each a name that says what it models.

  1. Open Power BI Desktop and sign in

    Sign in with your organizational account for the tenant that holds the workspaces.

  2. Open the OneLake catalog

    From the Home ribbon open the OneLake catalog and filter to warehouses.

  3. Select the warehouse and connect

    Pick WH_SALES_CNSM from DEV_SALES_CNSM_WH and choose to create a Direct Lake semantic model.

  4. Name the model and choose its workspace

    Name it by the standard, for example SM_SALES_CNSM_Orders, and select DEV_SALES_CNSM_SM as the target workspace. If you do not select it, the model is created in the warehouse's workspace.

  5. Select tables

    Pick the dimension and fact tables the model needs and confirm.

  6. Build the model

    Create relationships, measures, display names, formatting, hierarchies and security roles. In this flow Desktop edits the model live in the workspace; there is no local file to publish.

The model lives in its workspace

A Direct Lake model created this way is created and changed directly in the target workspace (DEV_SALES_CNSM_SM). Put the workspace under Git integration so model changes are versioned, and use the report development standards for modeling conventions.

Direct Lake variants

Direct Lake loads column data straight from Delta files in OneLake into the model's memory: close to Import performance, without a scheduled import refresh. A refresh of a Direct Lake model is framing: the model repoints to the latest Delta version, which takes seconds. There are two variants, and the difference matters for security and for what happens when a query cannot be served in Direct Lake mode.

AspectDirect Lake on OneLakeDirect Lake on SQL endpoints
Reads metadata and checks permissions throughOneLakeThe SQL analytics endpoint of one lakehouse or warehouse
Tables from several Fabric items in one modelYesNo, one item
Can combine with Import tablesYesCheck current documentation
SQL views as tablesNoYes, but they are queried in DirectQuery
DirectQuery fallbackNone; a query that cannot run in Direct Lake failsFalls back for views, SQL-based security and some guardrail breaches; controlled by the Direct Lake behavior property
Respects SQL row-level and column-level securityNo; uses OneLake securityYes, through fallback to DirectQuery
Typical authoringPower BI Desktop live editing, web modelingFabric web experience

Which variant for this design

  • Default to Direct Lake on OneLake when the model's security is defined in the model itself or in OneLake security, and when the model benefits from tables in more than one item.
  • Use Direct Lake on SQL endpoints when you rely on row-level, column-level or object-level security defined in the warehouse, or need views. Plan for fallback: set the Direct Lake behavior so that unexpected fallback is visible, and test performance in DirectQuery mode too.
  • Mind the identity. As described on the architecture page, Direct Lake over SQL endpoints does not pass the report user's identity through to shortcut targets.
  • Mind the guardrails. Each capacity size limits rows per table, Parquet files and row groups per table, and model memory. Compacted Gold tables stay inside them; tables with thousands of small files do not.

Verify against Microsoft Learn

Direct Lake has changed more than any other part of this design: release status of each variant, which tools can author which variant, fallback rules, guardrail values per capacity SKU and support for composite models. Check Direct Lake overview, How Direct Lake works and Direct Lake in Power BI Desktop before you standardize.

A Gold lakehouse for AI and ML

Data scientists work best in Spark against Delta tables. Give them a lakehouse of Gold shortcuts in their own workspace rather than access to Gold itself: they read current Gold data, write features and experiment outputs to their own tables, and cannot change Gold.

  1. Create the lakehouse

    In DEV_SALES_CNSM_LH, use New item, choose Lakehouse and name it LH_SALES_CNSM_ML.

  2. Create a Gold shortcut schema

    Create a schema shortcut named gld to the Gold lakehouse's dbo schema, or table shortcuts in a gld schema for an approved subset.

  3. Grant read at the source

    Each data scientist's identity needs read access to the Gold tables behind the shortcuts. Use OneLake security roles or item permissions on LH_SALES_GLD, not a Contributor role in the Gold workspace.

  4. Create a notebook

    Name it by the standard, for example NB_SALES_CNSM_ExploreGold, with LH_SALES_CNSM_ML as the default lakehouse.

  5. Test that Gold data is available

    List the shortcut tables, count rows and write a first feature table to the lakehouse's own schema.

# NB_SALES_CNSM_ExploreGold. Default lakehouse: LH_SALES_CNSM_ML; gld is a schema shortcut to Gold.
from pyspark.sql import functions as F

display(spark.sql("SHOW TABLES IN gld"))

for t in ["dim_customer", "dim_product", "fact_orders", "fact_order_lines"]:
    print(f"gld.{t}: {spark.table(f'gld.{t}').count():,} rows")

# A first feature table, written to this lakehouse's own dbo schema, never back to Gold
features = (spark.table("gld.fact_order_lines")
    .groupBy("product_id")
    .agg(F.sum("quantity").alias("units"),
         F.sum("net_amount").alias("net_revenue"),
         F.countDistinct("order_id").alias("orders")))
features.write.format("delta").mode("overwrite").saveAsTable("dbo.product_features")
display(features.orderBy(F.desc("net_revenue")).limit(20))

Treat this workspace as a sandbox with rules: features that become production inputs move into Gold through a reviewed notebook, and ML models that score production data run from a scheduled pipeline, not an exploratory notebook.

Publishing to the Delivery layer

  1. Start a report on the shared model

    In Power BI Desktop, open the OneLake catalog, filter to semantic models, select SM_SALES_CNSM_Orders in DEV_SALES_CNSM_SM and connect. The report gets a live connection; it holds no data and no model of its own.

  2. Build the report

    Use the model's measures. If a report needs a new measure, add it to the model (or as a report-level measure while prototyping) rather than importing data into the report.

  3. Publish to the Delivery workspace

    Publish and select DEV_SALES_DLV. Name the report by the standard, for example RPT_SALES_DLV_Revenue.

  4. Test in the service

    Open the report in the Delivery workspace and test it with an account that has only the access a business user will have.

  5. Publish an app

    Package the reports in a workspace app and assign audiences. Make sure audience members get read access to the semantic model, through the app's permission settings or a direct share; without it the report opens but shows no data. See Organizational Apps.

Thin reports pay off at promotion

Because reports in Delivery contain only visuals and a connection, promoting them is a matter of rebinding to the test or production model, which deployment rules handle. See Deployment Pipelines and Promotion.

Checklist

  • Decided per domain whether the warehouse is needed, and recorded why
  • Shortcut lakehouse in the warehouse workspace holds shortcuts only
  • Warehouse tables created from versioned DDL with explicit types and NOT ENFORCED keys
  • Each table load wrapped in a procedure, transactional, and called after a successful Gold load
  • Semantic models created explicitly in the semantic model workspace and under Git
  • Direct Lake variant chosen deliberately, with security model and fallback behavior documented
  • ML lakehouse reads Gold through shortcuts with read-only access at the source
  • Reports in Delivery are thin and bound to shared models; users reach them through an app

Key takeaways

  • Add a warehouse only for a reason; Direct Lake can serve Gold without it.
  • Declare warehouse tables explicitly and load them transactionally; never inherit varchar(8000) from a shortcut.
  • Choose Direct Lake on OneLake or on SQL endpoints by where your security lives and whether you can accept no fallback.
  • Give data scientists Gold shortcuts in their own workspace, never write access to Gold.
  • Publish thin reports to Delivery and reach users through apps, not workspace roles.
