Bronze to Silver

Moving data from Bronze to Silver takes two actions: make the Bronze tables visible in the Silver lakehouse with shortcuts, then run a notebook that filters, conforms and writes owned Silver tables. This page covers both, how to choose a load pattern per table, and the reusable full-load function with its per-table variants.

  • Focus shortcuts, full loads

Two actions

The Silver workspace never writes to Bronze and never copies Bronze tables. It borrows them through shortcuts in a dedicated schema, and the Silver notebook is the only process that materializes data in the Silver lakehouse. Keeping borrowed and owned tables in separate schemas means anyone reading the lakehouse explorer can tell at a glance which tables Silver is responsible for.

Before you start, the Silver workspace (DEV_SALES_SLV) should have a schema-enabled lakehouse (LH_SALES_SLV) and a published Environment set as the workspace default. See Fabric notebooks and The Environment item for the standards these notebooks follow.

Create shortcuts to the Bronze lakehouse

A OneLake shortcut is a pointer, not a copy. Reads through it go to the Bronze Delta files, so Silver always sees the current Bronze version and you pay for storage once. In a schema-enabled lakehouse you have two ways to create them.

OptionWhat you getUse when
Schema shortcutA new schema (brz) that references a whole schema of the Bronze lakehouse; tables added to Bronze appear automaticallySilver reads most of the Bronze schema. Least maintenance.
Table shortcuts inside a schemaOne shortcut per selected table, created in the schema you chooseSilver should see only an approved subset of Bronze tables, for example when Bronze holds sensitive tables Silver does not need

Naming the shortcuts

Name each shortcut exactly like the Bronze table it points to and let the schema carry the meaning: brz.customers in Silver is the Bronze customers table. An earlier version of this pattern encoded the direction in a long prefix on every shortcut name (a "shortcut to Bronze from Silver" prefix). The schema makes the prefix redundant, keeps names short enough to read in lineage views, and means the notebook code differs from production code only in the schema name, which is a parameter.

  • Letters, digits and underscores only: no spaces, % or +, which break unquoted references and some tools.
  • Keep target paths stable. Renaming or moving a Bronze table breaks every shortcut that points to it; treat Bronze table names as a contract.
  • One shortcut schema per upstream layer: brz in Silver, slv in Gold, gld in Consumption lakehouses (see schema and table names).

Steps in the lakehouse explorer

  1. Open the Silver lakehouse

    In DEV_SALES_SLV, open LH_SALES_SLV.

  2. Start a shortcut under Tables

    In the explorer, open the menu next to Tables (or next to an existing schema) and choose New schema shortcut for a whole schema, or New table shortcut for individual tables. Shortcuts for Delta tables belong under Tables; shortcuts under Files are treated as folders and are not registered as tables.

  3. Choose Microsoft OneLake

    From the internal sources, select Microsoft OneLake. ADLS Gen2, Amazon S3 and other external sources are for data outside Fabric and need a connection.

  4. Select the Bronze lakehouse

    Pick LH_SALES_BRZ in DEV_SALES_BRZ. You can only see items your identity can read.

  5. Select the schema or tables

    For a schema shortcut select dbo; for table shortcuts select each table, then choose Next.

  6. Review names and create

    On the review page, use the edit action to rename a shortcut or set the schema name (brz), then confirm and choose Create.

  7. Validate

    Expand brz and preview a table. Then run spark.table("brz.customers").limit(5) in a notebook with the identity that will run the scheduled load: access is checked at the Bronze side for that identity, not for you.

Access is checked at the target

Holding a role in the Silver workspace does not grant access to Bronze data. The identity that reads the shortcut, including the one that runs the notebook under a pipeline schedule, needs read access on the Bronze lakehouse. See how access works through a shortcut.

Creating shortcuts as code

For more than a handful of tables, or to recreate the same shortcuts in test and production, create them with the OneLake shortcuts REST API from a deployment script or a notebook. The request below creates brz.customers in the Silver lakehouse; path is where the shortcut lives, target.oneLake.path is the Bronze table.

POST https://api.fabric.microsoft.com/v1/workspaces/<silver-workspace-id>/items/<silver-lakehouse-id>/shortcuts?shortcutConflictPolicy=Abort
Authorization: Bearer <token>
Content-Type: application/json

{
  "path": "Tables/brz",
  "name": "customers",
  "target": {
    "oneLake": {
      "workspaceId": "<bronze-workspace-id>",
      "itemId": "<bronze-lakehouse-id>",
      "path": "Tables/dbo/customers"
    }
  }
}

Shortcuts are part of the lakehouse definition in Git integration and deployment pipelines, and deployment rules can repoint them per stage. That is the declarative alternative to scripts once your promotion process is in place; see Deployment Pipelines and Promotion.

Verify against Microsoft Learn

Check the allowed values of shortcutConflictPolicy, whether your caller type (user or service principal) is supported, and how shortcuts in schema-enabled lakehouses are represented in Git, on OneLake Shortcuts: Create Shortcut and OneLake shortcuts.

Set up the load notebook

  1. Create the notebook in the Silver workspace

    Name it by the standard, one notebook per table or per small group of related tables: NB_SALES_SLV_LoadCustomers, NB_SALES_SLV_LoadReference.

  2. Attach the Silver lakehouse as the default

    Unqualified names (dbo.customers, brz.customers) then resolve against LH_SALES_SLV. Keep the default lakehouse the same in every notebook of a run; child notebooks with a different default lakehouse are blocked under runMultiple.

  3. Confirm the Environment

    The notebook should inherit the workspace default Environment. Do not attach a different one per notebook unless you have a reason you can write down.

  4. Lay out the cells

    A Markdown cell that states what the notebook loads, from where and with which pattern; a parameter cell; one cell that defines or imports the load function; one cell per table call. Comments explain why, not what.

  5. Mark development-only cells

    Row-count and preview cells exist to prove the logic during development. Keep them behind a validate or debug parameter that defaults to off, so the scheduled run does not pay for extra full scans.

Choosing a load pattern

Two patterns cover nearly every table. A full load (destructive load) replaces the target with the current source content on every run. An incremental load applies only the rows that changed since the last run, using a watermark and a key. The choice is per table, and the Data Load Strategy playbook gives the full decision framework; the summary is below.

CriterionFull loadIncremental MERGE
LogicRead, filter, overwriteWatermark, key, deduplication, MERGE, delete handling
Cost per runProportional to table sizeProportional to change volume, plus the MERGE join
Correctness riskLow; deletes handled implicitlyHigher; depends on watermark discipline and delete signals
RetryAlways safeSafe if the key is right and the mark only moves after commit
Time travel and historyOne version per run, all files rewrittenSmall versions; untouched files kept
Good fitReference data, small dimensions, any table that fits the load windowLarge facts and dimensions with a reliable modified timestamp or increasing key

No fixed row threshold

Earlier guidance put the switch to incremental at around 100 million rows. Row count alone is a poor rule: a wide 20 million row table can take longer to rewrite than a narrow 200 million row one, and capacity size changes the answer. Measure the full load. When its duration or capacity use no longer fits the window, and the source has a usable watermark, move the table to the incremental MERGE pattern.

The reusable full-load function

Where a full load is appropriate, use one function for every table rather than writing a new cell per table. The same function works in any layer: Silver reading brz, Gold reading slv.

spark
The active SparkSession (the notebook's spark).
target_table
Silver table to create or replace, schema-qualified: dbo.departments.
source_table
Shortcut to read: brz.departments.
filter_condition
Optional SQL predicate applied before the write, for example "is_active = true AND is_deleted = false". Default: no filter.
overwrite_schema
Let the overwrite replace the table schema when Bronze adds or changes columns. Default True; set it to False where downstream consumers depend on a fixed schema and you would rather fail.
validate
Development only. Counts source and target and raises on a mismatch. Each count is a full scan.
from typing import Any, Dict, Optional

from pyspark.sql import SparkSession


def full_load_table(
    spark: SparkSession,
    target_table: str,
    source_table: str,
    filter_condition: Optional[str] = None,
    overwrite_schema: bool = True,
    validate: bool = False,
) -> Dict[str, Any]:
    """Replace target_table with the (optionally filtered) contents of source_table.

    Exceptions are deliberately not caught: a failed load must fail the notebook
    activity so the pipeline run shows the failure.
    """
    df = spark.table(source_table)
    if filter_condition:
        df = df.where(filter_condition)       # SQL predicate, e.g. "is_active = true"

    writer = df.write.format("delta").mode("overwrite")
    if overwrite_schema:
        writer = writer.option("overwriteSchema", "true")
    writer.saveAsTable(target_table)          # creates the table on the first run

    result: Dict[str, Any] = {"source": source_table, "target": target_table}
    if validate:                              # development only: every count() is a full scan
        expected = df.count()
        actual = spark.table(target_table).count()
        result.update(source_rows=expected, target_rows=actual)
        if expected != actual:
            raise AssertionError(f"Row count mismatch: source {expected}, target {actual}")
    return result

Call it once per table. The schemas are parameters, so a pipeline can point the same notebook at a different shortcut schema without code changes.

# Parameters cell (a pipeline can override these through notebook parameters)
SRC_SCHEMA = "brz"      # schema holding the shortcuts to Bronze
TGT_SCHEMA = "dbo"      # Silver tables

full_load_table(
    spark,
    target_table=f"{TGT_SCHEMA}.departments",
    source_table=f"{SRC_SCHEMA}.departments",
    filter_condition="is_active = true AND is_deleted = false",
    validate=True,        # remove once the notebook is tested
)

full_load_table(
    spark,
    target_table=f"{TGT_SCHEMA}.employees",
    source_table=f"{SRC_SCHEMA}.employees",
    filter_condition="is_deleted = false AND department_id IS NOT NULL",
)

Per-table method: Spark SQL or PySpark

Some tables need more than a filter: renamed columns, derived values, a join to a reference table. Write those loads individually, in Spark SQL or PySpark, and follow the same four steps during development.

  1. Count the rows in the source shortcut.
  2. Count the rows the filter and transformation logic will keep, so you know what to expect.
  3. Transform and load the Silver table.
  4. Count the target and confirm it equals the number from step 2.
%%sql
-- Cell 1 (development only): how many rows will the filter keep?
SELECT COUNT(*) AS src_rows FROM brz.customers;

SELECT COUNT(*) AS src_rows_filtered
FROM brz.customers
WHERE customer_id > 0
  AND COALESCE(TRIM(email), '') <> ''
  AND COALESCE(TRIM(customer_name), '') <> '';

-- Cell 2: create or replace the Silver table in one statement
CREATE OR REPLACE TABLE dbo.customers
USING DELTA
AS
SELECT *
FROM brz.customers
WHERE customer_id > 0
  AND COALESCE(TRIM(email), '') <> ''
  AND COALESCE(TRIM(customer_name), '') <> '';

-- Cell 3 (development only): the target must match the filtered count above
SELECT COUNT(*) AS tgt_rows FROM dbo.customers;
from pyspark.sql import functions as F

source_table = "brz.customers"
target_table = "dbo.customers"

def non_empty(c: str):
    """True when the column is neither null nor blank."""
    return F.trim(F.coalesce(F.col(c), F.lit(""))) != ""

src = spark.table(source_table)
filtered = src.filter(
    (F.col("customer_id") > 0) & non_empty("email") & non_empty("customer_name")
)

# Development-only checks: each count() is a full scan.
print(f"source rows: {src.count():,}; after filter: {filtered.count():,}")

# Replaces data and, with overwriteSchema, the schema. Use the SQL variant when you also
# want CREATE OR REPLACE semantics for table properties.
(filtered.write
    .format("delta")
    .mode("overwrite")
    .option("overwriteSchema", "true")
    .saveAsTable(target_table))

print(f"target rows: {spark.table(target_table).count():,}")

From development counts to automated reconciliation

Row-count cells are a development tool. Once a load is tested, switch them off and rely on automated checks: a reconciliation step after each load (see reconciliation), and post-deployment validation in test and production run as a pipeline step or from your CI/CD workflow. The QA Validation Frameworks playbook covers the check catalogue; the deployment playbook covers where the checks run during promotion.

Key takeaways

  • Expose Bronze through a brz shortcut schema with the same table names; let the schema, not a name prefix, say where a table comes from.
  • Test shortcut reads with the identity the schedule will use; access is checked at the Bronze side.
  • Use one full-load function for every table that fits the window; let failures fail the activity.
  • Decide full versus incremental by measured load time and watermark quality, not a row-count rule.
  • Count rows while developing; switch counts off and reconcile automatically afterwards.
