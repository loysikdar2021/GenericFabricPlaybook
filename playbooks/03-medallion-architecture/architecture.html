Layers and strict isolation

A medallion layer becomes enforceable when it is a workspace. This page defines the five layers, makes the case for isolating them, states the cost honestly, compares the alternatives in a decision table and maps the security controls onto the design.

  • Audience architects, security teams

The medallion pattern on Fabric

A medallion architecture organizes data into layers of increasing quality. On Fabric each layer is usually a lakehouse: Delta tables stored in OneLake, readable by Spark, the SQL analytics endpoint and Power BI. Microsoft's medallion guidance recommends a separate lakehouse for each layer, and recommends placing each lakehouse in its own workspace for better control and governance at the layer level, while noting that you can create all of them in one workspace. Data moves between layers by transformation: notebooks, pipelines, Dataflows Gen2 or materialized lake views, with shortcuts exposing one layer's tables inside the next.

This playbook goes one step further than the three classic layers. A medallion stops at Gold, but business users never read Gold directly. They read a semantic model over a warehouse or lakehouse, in a report. Treating those last two steps as layers of their own, Consumption and Delivery, gives them the same isolation as the data layers and gives BI teams a workspace where they are in charge.

Strict isolation

Strict isolation means one Fabric workspace per layer: Bronze, Silver, Gold, Consumption and Delivery, repeated for each domain and each environment. It works because the workspace is the unit to which Fabric attaches the controls that matter for governance.

The five layers

Each subsection states the layer's purpose, what it contains, how it is written and read, and the most common mistake. The workspace pattern page lists the items to create in each.

Bronze layer: raw data

Purpose
Hold data as it arrived from the source, so any downstream layer can be rebuilt from it.
Contents
Source-shaped Delta tables (optionally raw files in the Files section). Only minimal technical changes: schema alignment, type casting where the source type is ambiguous, ingestion metadata such as a load timestamp.
Written by
Ingestion pipelines, Dataflows Gen2, Copy jobs and notebooks. Append-heavy; keep the history.
Read by
Silver notebooks, through shortcuts. A small group of engineers and stewards. Analysts and BI developers should have no role here.
Typical tools
Data pipelines, Dataflows Gen2, Spark notebooks, Copy job, mirroring where the source supports it.
Most common mistake
Cleaning data on the way in. Once Bronze is cleaned, you can no longer replay a fix from the original.

Silver layer: cleansed and enriched data

Purpose
One validated, deduplicated, conformed version of each entity: correct types, standardized codes, soft-deleted rows handled, keys unique.
Contents
Delta tables at source grain, one per entity (customers, orders, order_lines). Shortcuts to Bronze live in a separate schema so owned and borrowed tables never mix.
Written by
Silver notebooks: full reloads for small tables, incremental MERGE for large ones.
Read by
Gold notebooks and data scientists, through shortcuts or direct reads.
Typical tools
Spark SQL and PySpark notebooks orchestrated by pipelines; the Bronze to Silver and incremental loads pages.
Most common mistake
Putting business logic (revenue rules, KPI definitions) here. Silver should be reusable by any consumer; business meaning belongs in Gold.

Gold layer: business-ready data

Purpose
Curated, modeled data at business grain: star-schema facts and dimensions, aggregates and derived measures that downstream consumers can trust.
Contents
Delta tables shaped for consumption: surrogate or durable keys, conformed dimensions, pre-computed attributes, partition and file layout suited to Direct Lake and SQL reads.
Written by
Gold notebooks, with reconciliation against Silver.
Read by
Consumption-layer items only, through shortcuts.
Typical tools
Spark SQL, PySpark and T-SQL over the lakehouse SQL analytics endpoint; see Silver to Gold.
Most common mistake
Letting reports or ad-hoc users read Gold directly "just this once". Every direct reader becomes a dependency on a table layout you now cannot change.

Consumption layer: serve

Purpose
Present Gold data through the engine and shape each consumer needs, without changing the data's meaning.
Contents
A Fabric Warehouse for T-SQL workloads, semantic models for BI, and a lakehouse of Gold shortcuts for AI/ML. Split into several workspaces (_WH, _SM, _LH qualifiers) when the teams or security models differ.
Written by
Warehouse developers and BI modelers. The Warehouse is loaded from Gold shortcuts; semantic models are authored directly in their own workspace.
Read by
Delivery items, analysts using SQL, data scientists using Spark.
Typical tools
T-SQL, DAX, Power BI Desktop, Direct Lake semantic models, notebooks for ML.
Most common mistake
Duplicating transformation logic in DAX or warehouse views that should be in Gold, which creates two versions of the truth.

Delivery layer: user-facing interfaces

Purpose
Give people reports, dashboards and apps, and give external systems an interface, without exposing the data layers.
Contents
Power BI reports bound to shared semantic models, dashboards and workspace apps; optionally pipelines that call REST APIs for system-to-system delivery.
Written by
Report authors.
Read by
Business users, through an app or report permission rather than a workspace role.
Typical tools
Power BI Desktop and service, Fabric REST APIs. See Consumption and delivery and the organizational apps and report development playbooks.
Most common mistake
Giving business users workspace roles. A Viewer role in a workspace is broader than an app audience and it reveals items you did not mean to publish.

Why isolate: the rationale

Isolation is not tidiness; each reason below corresponds to a control you can test.

ReasonWhat isolation gives youHow to verify it
Security boundaryRaw data that may hold sensitive fields sits in a workspace few people can enter; downstream layers hold masked or aggregated dataPick an analyst account; confirm it cannot see Bronze items or read Bronze tables through any engine
Role separationEngineers, analysts and BI developers receive roles per layer, so no one has write access they do not needExport workspace role assignments per layer and compare with the team matrix
Blast radiusA bad notebook, a mistaken delete or a wrong grant is confined to one workspace; later layers keep serving their last good loadFail a Silver load in test and confirm Gold reports still refresh
Controlled promotionEach layer is versioned, tested and released separately; a Bronze change does not reach Gold consumers until Silver and Gold accept itOne deployment pipeline per layer with its own approvers
Lineage and ownershipRaw, curated and published assets have distinct owners; classification and catalog scans can be scoped per layerEach workspace has a named owner and a data steward
Capacity isolationHeavy transformation and interactive BI can run on different capacities and be charged to different cost centersCompare capacity utilization during the Silver load window and the business-hours report window
Optimized consumptionThe Consumption layer is tuned for its readers: a warehouse for SQL, Direct Lake models for BI, a lakehouse for ML, each with its own capacity and settingsTrack query duration and refresh time per consumption item

Workspace-level separation also means a role in one layer never implies a role in another, which is the property auditors ask about most.

Regulated and sensitive data

The isolation design supports regulated-data programs (personal, financial or health data) by confining raw data and limiting who can read it. It does not by itself make a platform compliant with any specific regulation. Map your own control requirements to the controls in the security section and have them reviewed.

What isolation costs

The benefits above are real, and so are the costs. Plan for them or the design will be abandoned under delivery pressure.

CostWhat you experienceMitigation
Object countDozens of workspaces to create, name, secure and decommissionScript workspace creation and role assignment through the Fabric REST API or a CLI; keep the naming standard machine-parseable
Cross-workspace permissionsEvery shortcut needs access at the target; every service principal needs roles in several workspacesUse security groups per layer; document the grant matrix; test the identity that runs production notebooks, not only your own
Orchestration across boundariesOne logical run touches several workspacesUse a hub workspace for orchestration; see Cross-Workspace Orchestration

Lineage view limitsThe workspace lineage view shows one workspace; shortcuts to other workspaces do not appear in itRely on a catalog tool such as Microsoft Purview for end-to-end lineage; keep a diagram of the shortcut edges

The options compared

Strict isolation sits at one end of a range. The alternatives trade isolation for simplicity, and the right choice depends on who must be kept apart, how big the team is and what regulators require.

A. Workspace per layer
Strict isolation as described here. Maximum separation, maximum objects.
B. Merged workspaces
Three workspaces: raw data alone, curated data (Silver and Gold) together, and consumption with delivery. A common compromise when the same engineers own Silver and Gold and the consumption team is separate.
C. One workspace, lakehouse per layer
The simplest option that still gives each layer a distinct lakehouse and shortcuts or direct reads between them. Roles apply to the whole workspace, so any engineer who can write Silver can also read Bronze and write Gold.
D. One lakehouse, schema per layer
Schema-enabled lakehouses let you group tables under brz, slv and gld schemas. It is good for discovery and for four-part queries, and OneLake security roles can scope access by schema. There is no workspace-level boundary, so the blast radius, capacity, deployment and Git history are shared.

Start strict where it is hard to undo

Splitting one workspace into several later is expensive because item identities, shortcuts, Git history and permissions all move. Merging separate workspaces is cheap by comparison. If you are unsure, isolate Bronze and Consumption first, since those boundaries matter most for security and for BI independence, and decide Silver and Gold afterward.

Security controls in this design

Workspace roles are the coarse control. Fabric adds finer controls, and a layered design uses the finest control that fits the requirement.

How access works through a shortcut

A shortcut to another OneLake location is authorized at the target. For a same-tenant OneLake shortcut, the identity of the calling user is used to authorize access, and that user must have permissions at the target; the Silver role alone is not enough. The effective access is therefore the narrower of what the identity is allowed on the shortcut path and on the target path. Roles you hold in the consuming workspace do not widen your rights at the producing workspace.

Some engines do not pass the caller through

Direct Lake over SQL endpoints and T-SQL in delegated identity mode do not pass the calling user's identity to the shortcut target; they use the item owner's identity instead and apply security on top. If the source table has OneLake row or column rules, the SQL analytics endpoint can block access through that shortcut. Direct Lake over OneLake and T-SQL in user identity mode avoid this behavior. Pick the Direct Lake variant with this in mind (see Direct Lake variants).

Verify against Microsoft Learn

OneLake security (table, column and row rules in OneLake security roles) is evolving, including which engines enforce it, how row and column rules combine across roles, and its release status. Before relying on it for a compliance control, read OneLake security roles, permissions, and scopes and Secure and manage OneLake shortcuts. Also confirm which identity runs a notebook when a pipeline invokes it, and grant that identity access at every shortcut target.

Ways to move data between layers

Shortcuts make the previous layer visible; something must still transform and write the next layer. This playbook uses notebooks because they handle arbitrary logic, MERGE and reconciliation. The alternatives suit narrower cases.

MechanismGood forTrade-off
Shortcut plus notebook (this playbook)Any transformation, incremental MERGE, custom QAYou own the code and its tests
Direct cross-workspace read with a four-part name (workspace.lakehouse.schema.table)Ad-hoc joins and one-off loads between schema-enabled lakehousesNo shortcut object, so no lineage entry and no schema-level reuse; the running identity needs access at the source
Materialized lake viewsDeclarative SQL or PySpark transformations that Fabric refreshes in dependency orderLess control over incremental logic and deletes; confirm cross-workspace behavior in a test before choosing it for isolated layers
Dataflows Gen2Low-code ingestion and light transformation, mostly at BronzeHarder to test, review and reuse than code
Copy job or pipeline CopyLanding data from external sources into BronzeA physical copy; not for layer-to-layer moves inside OneLake
MirroringContinuously replicating a supported database into OneLakeAvailable for specific sources; replaces the ingestion step, not Silver and Gold logic

Verify against Microsoft Learn

Materialized lake views and four-part cross-workspace names are newer capabilities. Check their current release status, supported sources and cross-workspace behavior in Overview of materialized lake views and Lakehouse schemas before you standardize on either.

Key takeaways

  • Give each layer, including Consumption and Delivery, its own workspace when data is sensitive, teams differ or auditors will ask who can see what.
  • Count the cost before you commit: objects, grants, orchestration and promotion all multiply; script them.
  • Use the decision table; merged workspaces are a valid compromise, and one lakehouse with schemas is a prototype pattern, not an isolation design.
  • Authorization on a shortcut happens at the target. Test with the identity that will run production notebooks.
  • Business users get apps or report permissions, never workspace roles.
