Silver to Gold

Gold turns conformed Silver entities into facts and dimensions at business grain. The wiring repeats the Bronze to Silver pattern, a shortcut schema and a notebook, but Gold adds two things: business transforms that must be applied identically on every run, and reconciliation that proves the incremental loads still add up.

  • Audience data engineers, analytics engineers
  • Focus facts, dimensions, QA
  • Pages 8 of 10

Wiring the Gold workspace

  1. Create the Silver shortcuts in Gold

    In DEV_SALES_GLD, open LH_SALES_GLD and create a schema shortcut named slv to the Silver lakehouse's dbo schema, or table shortcuts in an slv schema, exactly as on the Bronze to Silver page. Gold reads Silver only, never Bronze.

  2. Create the notebooks

    Name them by the standard and by what they build: NB_SALES_GLD_BuildFactOrderLines, NB_SALES_GLD_BuildDimensions. Attach LH_SALES_GLD as the default lakehouse.

  3. Choose a load pattern per table

    Dimensions are usually small enough to rebuild; facts usually are not. Use the same criteria as in choosing a load pattern and the Data Load Strategy playbook.

  4. Reconcile and fail loudly

    Every Gold load ends with a check that raises on a mismatch, so the pipeline stops before Consumption reads a wrong number.

Where business logic lives

Gold is the first layer allowed to apply business meaning: derived measures, categorizations, keys for the star schema. Keep that logic in named transform functions or SQL statements in Gold, not in Silver and not in DAX, so there is one definition that every consumer inherits.

Full load: Spark SQL and PySpark

The example builds dbo.fact_order_lines from the Silver order_lines table. Each Silver order line carries up to three charge slots, each with a type and an amount (charge_1_type, charge_1_amount and so on). Gold pivots those slots into named measures, discount, shipping, tax and handling, so reports never need to know which slot held which charge. This positional-to-named pivot is a common Gold transform; the same shape appears whenever a source stores categorized values in numbered columns.

%%sql
-- Gold lakehouse. slv.order_lines is a shortcut (created in the Gold lakehouse) to the Silver table.
-- Development only: SELECT COUNT(*) FROM slv.order_lines;

CREATE OR REPLACE TABLE dbo.fact_order_lines
USING DELTA
AS
WITH pivoted AS (
    SELECT
        order_line_id,
        order_id,
        line_number,
        product_id,
        quantity,
        unit_price,
        CAST(quantity * unit_price AS DECIMAL(18,2)) AS gross_amount,
        -- Pivot the three charge slots into named measures (the first matching slot wins)
        COALESCE(CASE WHEN charge_1_type = 'discount' THEN charge_1_amount
                      WHEN charge_2_type = 'discount' THEN charge_2_amount
                      WHEN charge_3_type = 'discount' THEN charge_3_amount END, 0) AS discount_amount,
        COALESCE(CASE WHEN charge_1_type = 'shipping' THEN charge_1_amount
                      WHEN charge_2_type = 'shipping' THEN charge_2_amount
                      WHEN charge_3_type = 'shipping' THEN charge_3_amount END, 0) AS shipping_amount,
        COALESCE(CASE WHEN charge_1_type = 'tax' THEN charge_1_amount
                      WHEN charge_2_type = 'tax' THEN charge_2_amount
                      WHEN charge_3_type = 'tax' THEN charge_3_amount END, 0) AS tax_amount,
        COALESCE(CASE WHEN charge_1_type = 'handling' THEN charge_1_amount
                      WHEN charge_2_type = 'handling' THEN charge_2_amount
                      WHEN charge_3_type = 'handling' THEN charge_3_amount END, 0) AS handling_amount,
        last_modified_utc,
        ingested_at_utc
    FROM slv.order_lines
    WHERE COALESCE(is_deleted, false) = false
)
SELECT
    order_line_id, order_id, line_number, product_id, quantity, unit_price,
    gross_amount, discount_amount, shipping_amount, tax_amount, handling_amount,
    CAST(gross_amount - discount_amount AS DECIMAL(18,2)) AS net_amount,
    last_modified_utc, ingested_at_utc
FROM pivoted;

-- Development only: the count must equal the non-deleted row count of the source.
SELECT COUNT(*) AS tgt_rows FROM dbo.fact_order_lines;
from pyspark.sql import functions as F

source_table = "slv.order_lines"
target_table = "dbo.fact_order_lines"

def pick_slot(kind: str):
    """Amount of the first charge slot whose type equals `kind`, else 0."""
    return F.coalesce(
        F.when(F.col("charge_1_type") == kind, F.col("charge_1_amount"))
         .when(F.col("charge_2_type") == kind, F.col("charge_2_amount"))
         .when(F.col("charge_3_type") == kind, F.col("charge_3_amount")),
        F.lit(0),
    )

src = spark.table(source_table).where(~F.coalesce(F.col("is_deleted"), F.lit(False)))

fact = (src
    .withColumn("gross_amount", (F.col("quantity") * F.col("unit_price")).cast("decimal(18,2)"))
    .withColumn("discount_amount", pick_slot("discount"))
    .withColumn("shipping_amount", pick_slot("shipping"))
    .withColumn("tax_amount", pick_slot("tax"))
    .withColumn("handling_amount", pick_slot("handling"))
    .withColumn("net_amount", (F.col("gross_amount") - F.col("discount_amount")).cast("decimal(18,2)"))
    .select(
        "order_line_id", "order_id", "line_number", "product_id", "quantity", "unit_price",
        "gross_amount", "discount_amount", "shipping_amount", "tax_amount", "handling_amount", "net_amount",
        "last_modified_utc", "ingested_at_utc",
    ))

(fact.write
     .format("delta")
     .mode("overwrite")
     .option("overwriteSchema", "true")
     .saveAsTable(target_table))
  • Deleted rows are excluded with COALESCE(is_deleted, false) = false. Silver keeps the flag precisely so Gold can make this decision per table.
  • Measures are typed explicitly. DECIMAL(18,2) on derived money columns keeps the Gold schema stable, which matters for the Warehouse and semantic model built on it.
  • Missing charges become 0, not NULL, so sums in reports and in reconciliation behave predictably. Choose deliberately: NULL means "unknown", 0 means "none".
  • The column list is explicit. SELECT * in Gold lets every Silver change leak into the business model.
  • Watermark columns are kept (last_modified_utc, ingested_at_utc), so the table can later move to the incremental engine without a rebuild.

Incremental load: a config-driven engine

For large facts, Gold reuses the Silver incremental MERGE utility and adds three things around it: a shared watermark list, a registry of per-table transforms and settings, and reconciliation. Run the cells in this order: helpers and the Silver utility, transforms, configuration, engine, then the calls.

Global watermark and transforms

WATERMARK_COLS_DEFAULT is the priority list every Gold table shares: the first non-null value is the row's last-changed time. A single list works because Silver standardized these columns; if a table needs a different list, pass watermark_cols for that call.

Transform functions take a DataFrame of changed Silver rows and return the Gold shape. Because the engine applies them to the incremental slice only, they must be row-local: the output for a row may depend on that row and on stable reference data, but not on other rows in the slice. Aggregations across rows (daily totals, running balances) do not belong in this engine; build those as full loads, or as a separate step that recomputes the affected periods.

from pyspark.sql import Column, DataFrame
from pyspark.sql import functions as F

# Global watermark priority list, shared by every Gold table (first non-null wins).
WATERMARK_COLS_DEFAULT = ["last_modified_utc", "ingested_at_utc"]

CHARGE_KINDS = ["discount", "shipping", "tax", "handling"]


def _pick_slot(kind: str) -> Column:
    """Value of the first charge slot (1..3) whose type equals `kind`; null if none matches.

    Without .otherwise(), when() returns a NULL of the branch type, so no explicit cast is needed.
    """
    return (F.when(F.col("charge_1_type") == kind, F.col("charge_1_amount"))
             .when(F.col("charge_2_type") == kind, F.col("charge_2_amount"))
             .when(F.col("charge_3_type") == kind, F.col("charge_3_amount")))


def transform_fact_order_lines(df: DataFrame) -> DataFrame:
    """Silver order_lines -> Gold fact_order_lines: pivot charge slots into named measures."""
    amount_type = df.schema["charge_1_amount"].dataType
    zero = F.lit(0).cast(amount_type)
    out = df
    for kind in CHARGE_KINDS:
        out = out.withColumn(f"{kind}_amount", F.coalesce(_pick_slot(kind), zero))
    out = out.withColumn("gross_amount", (F.col("quantity") * F.col("unit_price")).cast("decimal(18,2)"))
    out = out.withColumn("net_amount", (F.col("gross_amount") - F.col("discount_amount")).cast("decimal(18,2)"))
    return out.select(
        "order_line_id", "order_id", "line_number", "product_id", "quantity", "unit_price",
        "gross_amount", "discount_amount", "shipping_amount", "tax_amount", "handling_amount", "net_amount",
        "last_modified_utc", "ingested_at_utc",
    )


def transform_fact_orders(df: DataFrame) -> DataFrame:
    """Silver orders -> Gold fact_orders: add a date key and keep a stable column order."""
    return (df
            .withColumn("order_date_key", F.date_format(F.col("order_ts"), "yyyyMMdd").cast("int"))
            .select("order_id", "customer_id", "employee_id", "order_date_key", "order_ts",
                    "status", "currency_code", "gross_amount",
                    "last_modified_utc", "ingested_at_utc"))
  • _pick_slot leaves out otherwise, so an unmatched slot yields a NULL of the amount's own type and the coalesce turns it into a typed zero. The original cast a NULL literal to the key's data type for the same reason.
  • Both transforms keep the key and watermark columns, which the engine requires.

In the original version the key carried a suffix that did not match the real table name, and the engine fell back to a heuristic key search containing hard-coded column names of one source. Here a table without a configuration entry fails with a KeyError; there is no guessing.

The engine

import math


def qa_reconcile(
    spark: SparkSession,
    source_table: str,
    target_table: str,
    key_candidates: Sequence[Sequence[str]],
    watermark_cols: Sequence[str],
    *,
    row_filter: Optional[RowFilter] = None,
    transform_fn: Optional[Callable[[DataFrame], DataFrame]] = None,
    delete_condition: Optional[str] = None,
    normalize_keys: bool = False,
    tiebreak_cols: Sequence[str] = (),
    sum_columns: Sequence[str] = (),
    raise_on_mismatch: bool = False,
) -> Dict[str, Any]:
    """Compare what the target should hold (latest row per key, transformed) with what it holds.

    Scans the whole source, so schedule it per release or nightly rather than on every run.
    """
    full, key_cols = build_slice(spark, source_table, key_candidates, watermark_cols,
                                 row_filter, normalize_keys)
    expected = latest_per_key(full, key_cols, "_wm", tiebreak_cols).drop("_wm")
    if delete_condition:
        expected = expected.filter(~F.coalesce(F.expr(delete_condition), F.lit(False)))
    if transform_fn is not None:
        expected = transform_fn(expected)

    aggs = [F.count(F.lit(1)).alias("rows")] + [F.sum(c).alias(f"sum_{c}") for c in sum_columns]
    want = expected.agg(*aggs).first().asDict()
    have = spark.table(target_table).agg(*aggs).first().asDict()

    checks = {}
    for name, e in want.items():
        e, a = e or 0, (have[name] or 0)
        checks[name] = {"expected": float(e), "actual": float(a),
                        "ok": math.isclose(float(e), float(a), rel_tol=1e-9, abs_tol=1e-6)}
    result = {"qa_ok": all(c["ok"] for c in checks.values()), "checks": checks}
    if raise_on_mismatch and not result["qa_ok"]:
        raise AssertionError(f"QA mismatch for {target_table}: {checks}")
    return result


def incremental_merge_with_qa(
    spark: SparkSession,
    target_table: str,
    table_config: Dict[str, Dict[str, Any]],
    *,
    watermark_cols: Sequence[str] = WATERMARK_COLS_DEFAULT,
    run_qa: bool = True,
    **overrides: Any,
) -> Dict[str, Any]:
    """Look up a table's settings, run the incremental merge, then optionally reconcile."""
    cfg = {**table_config[target_table], **overrides}
    shared = dict(
        row_filter=cfg.get("row_filter"),
        transform_fn=cfg["transform_fn"],
        delete_condition=cfg.get("delete_condition"),
        normalize_keys=cfg.get("normalize_keys", False),
        tiebreak_cols=cfg.get("tiebreak_cols", ()),
    )
    metrics = incremental_merge_scd1(
        spark, cfg["source_table"], target_table, cfg["key_candidates"], watermark_cols,
        lookback_minutes=cfg.get("lookback_minutes", 0),
        watermark_value=cfg.get("watermark_value"),
        **shared,
    )
    if run_qa:
        metrics["qa"] = qa_reconcile(
            spark, cfg["source_table"], target_table, cfg["key_candidates"], watermark_cols,
            sum_columns=cfg.get("qa_sum_columns", ()), **shared,
        )
    return metrics
results = {}
for target in TABLE_CONFIG:                      # fact_orders, fact_order_lines, ...
    results[target] = incremental_merge_with_qa(
        spark, target, TABLE_CONFIG,
        lookback_minutes=15,                      # tolerate late-arriving rows
        run_qa=True,                              # turn off in production if the scan is too costly
    )
    print(target, results[target])

failed = [t for t, r in results.items() if not r.get("qa", {}).get("qa_ok", True)]
if failed:
    raise RuntimeError(f"Reconciliation failed for: {failed}")   # fail the pipeline activity

The loop runs every configured table, collects the metrics and raises once at the end if any reconciliation failed. That way one bad table does not hide the results of the others, and the pipeline activity still fails. To fail fast instead, pass raise_on_mismatch=True to qa_reconcile.

Reconciliation

Reconciliation answers one question: does the Gold table hold what a full rebuild from Silver would produce? The incremental engine is correct only if every slice was complete, every key unique and every delete applied. Reconciliation catches a failure in any of those without knowing which one happened.

What to compare

CheckExpected sideCatchesCost
Row countLatest row per key, minus deleted keysMissed slices, missed deletes, duplicatesFull source scan
Sum of key measuresSame rows, transformedMissed updates, transform drift, type truncationSame scan, extra aggregates
Duplicate keysZeroWrong key choice, concurrent writersGroup by key on the target
Orphan foreign keysZero, or a known unknown-member countFacts loaded before their dimensionsAnti-join to each dimension
FreshnessMax watermark in Gold close to SilverStalled loads, a stuck markTwo small aggregates

The engine's qa_reconcile covers the first two. Add the integrity checks as a separate step after all tables of a run have loaded, so dimensions and facts are compared at the same point in time.

from typing import Sequence

from pyspark.sql import SparkSession
from pyspark.sql import functions as F


def duplicate_keys(spark: SparkSession, table: str, key_cols: Sequence[str]) -> int:
    """Number of key values that occur more than once (should be 0 after an SCD1 merge)."""
    return (spark.table(table).groupBy(*key_cols).count()
            .filter(F.col("count") > 1).count())


def orphan_rows(spark: SparkSession, fact: str, fk: str, dim: str, pk: str) -> int:
    """Fact rows whose foreign key has no matching dimension row."""
    keys = spark.table(dim).select(F.col(pk).alias(fk))
    return spark.table(fact).join(keys, fk, "left_anti").count()


problems = {
    "dup fact_order_lines": duplicate_keys(spark, "dbo.fact_order_lines", ["order_line_id"]),
    "orphan product_id": orphan_rows(spark, "dbo.fact_order_lines", "product_id", "dbo.dim_product", "product_id"),
}
if any(problems.values()):
    raise AssertionError(f"Gold integrity checks failed: {problems}")

Running reconciliation in production

  • Cost. The expected side scans the whole Silver table. For large facts run it nightly or per release with run_qa=False on intraday runs, or restrict both sides to recent partitions with the same filter.
  • Tolerance. Integer counts must match exactly. Sums of decimals should match exactly too; the tolerance in the code only absorbs floating-point conversion in the comparison.
  • Timing. If Silver is loading while Gold reconciles, the expected side moves. Reconcile right after the Gold load in the same run, before the next Silver load.
  • Recording. Append the checks dictionary to the run log so trends (a slowly growing difference) are visible, and alert on qa_ok = false. The QA Validation Frameworks playbook covers the wider framework.

Gold table layout for consumers

Gold tables feed the Warehouse, Direct Lake semantic models and SQL readers, so their file layout affects every query.

  • Compact after incremental loads; many small files slow Direct Lake framing and SQL scans and count against Direct Lake guardrails.
  • Keep V-Order on for tables that Power BI reads; see the resource profile guidance on the Environment page.
  • Partition only large tables, on a low-cardinality column consumers filter by; see Delta Partitioning.
  • Treat column names and types as a contract with Consumption: add columns freely, rename or retype only with a coordinated change.

Key takeaways

  • Gold reads Silver through an slv shortcut schema and writes only its own tables.
  • Put business logic in named, row-local transforms; aggregate tables are full loads or recompute affected periods.
  • Drive the incremental engine from one configuration entry per table; a missing entry is an error, not a guess.
  • Reconcile against what a full rebuild would produce, not against the raw source count, and fail the run on a mismatch.
