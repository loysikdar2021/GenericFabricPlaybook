Workspace pattern and naming

Strict isolation only stays manageable if every workspace and item name can be generated and parsed. This page fixes the workspace pattern, the naming grammar, the abbreviation tables and the rules for environments, capacity and shortcut edges.

  • Audience platform engineers, architects
  • Focus structure and standards

The workspace pattern

For one domain in one environment the pattern has seven workspaces. Three are data engineering layers (Bronze, Silver, Gold), three are Consumption workspaces split by purpose, and one is Delivery. Sources sit outside and feed Bronze. A separate orchestration hub (<ENV>_ORCH_HUB) sits above all domains and is covered in Cross-Workspace Orchestration.

WorkspaceLayerTypical itemsWho writes
DEV_SALES_BRZBronzeLakehouse, ingestion pipelines, Dataflows Gen2, Copy jobsIngestion engineers
DEV_SALES_SLVSilverLakehouse with Bronze shortcuts, notebooks, Environment, variable libraryData engineers
DEV_SALES_GLDGoldLakehouse with Silver shortcuts, notebooks, reconciliation checksData engineers, analytics engineers
DEV_SALES_CNSM_WHConsumptionWarehouse; its lakehouse of Gold shortcuts is the load sourceWarehouse developers
DEV_SALES_CNSM_SMConsumptionSemantic modelsBI modelers
DEV_SALES_CNSM_LHConsumptionLakehouse of Gold shortcuts, notebooks and experiments for AI and MLData scientists
DEV_SALES_DLVDeliveryReports, dashboards, workspace appReport authors

Seven workspaces per domain per environment, plus the hub, is the count to script and budget for.

One Consumption workspace is also valid

The three CNSM_ qualifiers exist because warehouse developers, BI modelers and data scientists often have different owners and different security needs. A small team can use one DEV_SALES_CNSM workspace and drop the qualifier. Decide per domain, and keep the rule that Delivery never shares a workspace with Consumption.

What lives inside a layer workspace

Every layer workspace follows the same internal shape: one primary store, the compute items that write only into that store, and the supporting items that standardize them. Keeping the shape identical makes new layers and new domains copy-paste work.

ItemPurposeRule
Lakehouse (LH_)Primary store of the layer; schema-enabled so owned tables and shortcuts are separatedOwned tables in dbo; one schema per upstream layer for shortcuts (brz in Silver, slv in Gold)
Notebooks (NB_)Transformations, merges, quality checksWrite only to the workspace's own store; read upstream through shortcuts
Pipelines (PL_)Run the notebooks of this layer, or ingest in BronzeParameterized and callable from the hub; see Control-Table Pipelines
Environment (ENV_)Libraries and Spark properties shared by the layer's notebooksOne per layer; set as the workspace default. See Environment item
Variable library (VL_)Values that differ by environment: shortcut targets, capacity-related names, feature switchesSee Variable Libraries

Who works where

Assign roles to security groups, never to individuals, and give each persona the least access that lets them work. Reading an upstream layer is not the same as writing it: the engineer who builds Silver needs read access to Bronze data, not a Contributor role in the Bronze workspace.

Test with the production identity

A notebook that works when you run it can fail when a pipeline or schedule runs it, because the identity differs and workspace roles do not extend across a shortcut. Grant the production identity access at each shortcut target and test the scheduled run, not only the interactive one.

Naming conventions

Names carry meaning in three places: workspaces, items and the objects inside lakehouses. Each has a grammar, so a name can be built by a script and parsed back into its parts.

Workspace names

Pattern: <ENV>_<DOMAIN>_<LAYER>[_<Qualifier>]

PartValuesNotes
<ENV>DEV, TST, PRDEnvironment type
<DOMAIN>2 to 5 capital letters, for example SALES, FIN, HRMatches the Fabric domain the workspace is assigned to
<LAYER>BRZ, SLV, GLD, CNSM, DLVMedallion layer
[_<Qualifier>]Optional, for example WH, SM, LHSplits a layer into several workspaces by purpose

Examples: PRD_FIN_GLD, DEV_SALES_BRZ, TST_HR_CNSM_SM. The orchestration hub is <ENV>_ORCH_HUB, for example DEV_ORCH_HUB.

Item names

Pattern: <ARTIFACT>_<DOMAIN>_<LAYER>_<Function>

PartValuesNotes
<ARTIFACT>Item type abbreviation from the table belowCapital letters
<DOMAIN>, <LAYER>Same values as the workspaceRepeated on purpose so an item is identifiable outside its workspace, in logs and search results
<Function>PascalCase purpose, for example LoadCustomers, CostAnalysisDescribes what the item does, not how

Examples: NB_SALES_SLV_LoadCustomers, WH_FIN_CNSM_Ledger, SM_SALES_CNSM_Orders, RPT_SALES_DLV_Revenue.

No environment in item names
The workspace already says DEV, TST or PRD. Keeping item names identical across environments is what lets deployment pipelines pair an item in one stage with its counterpart in the next.
Primary store exception
A layer's single primary lakehouse, warehouse or semantic model may omit the function: LH_SALES_SLV. Add a function once a workspace holds more than one item of that type.
Characters
Letters, digits and underscores only. No spaces, no hyphens. Names then work unquoted in Spark SQL, T-SQL, URLs and scripts; a workspace name with spaces or special characters needs quoting in a four-part name.

Two meanings of ENV

<ENV> in angle brackets is the environment type, DEV, TST or PRD. ENV_ as an item prefix is the abbreviation for a Fabric Environment item. The brackets and the position in the name keep them apart.

Schema and table names

ObjectConventionExample
Owned tablesDefault schema dbo; lowercase snake_case entity namesdbo.customers, dbo.order_lines
Shortcut schemaOne schema per upstream layer, named with the layer abbreviation in lowercasebrz in Silver, slv in Gold
Shortcut nameSame as the upstream table, so lineage reads by namebrz.customers
Gold tablesdim_ and fact_ prefixes with a singular entity for dimensionsdim_customer, fact_order_lines
ColumnsLowercase snake_case; the same name for the same business key in every layercustomer_id, order_date

Lowercase matters more than it looks. The Warehouse default collation is case-sensitive, so a column written as CustomerId in one layer and customerid in another produces failures that Spark, which is case-insensitive by default, never shows.

Shortcut edge rules

Naming fixes what things are called. A short set of rules fixes which things may point at which, so the shortcut graph stays a straight line from Bronze to Consumption.

RuleReason
A shortcut lives in the downstream workspace and points to the layer directly upstreamThe owner of the downstream layer chooses what to read, and the upstream owner controls what can be read by granting access
No layer skippingA Gold item that reads Bronze bypasses cleansing and makes Silver optional
No upward shortcutsOutput that flows back into its own input produces circular lineage
Shortcuts are read-only in practiceWriting through a shortcut changes another layer's data and breaks the ownership model; keep write access out of the grant
Name the shortcut after its target tableLineage can then be traced by name in code, logs and catalog tools

Environments

Each layer repeats in three environments. The names differ only in the first token; what differs is below.

AspectDEVTSTPRD
Source controlWorkspace connected to a Git branch; developers work hereNot connected; content arrives by deployment pipelineNot connected; content arrives by deployment pipeline
DataSynthetic or masked samplesRepresentative subset, masked where sensitiveProduction data
Human accessEngineers as ContributorsEngineers and testers, mostly readFew humans; service identities run the loads
SchedulesOff or manualOn the test cadenceOn the production cadence
CapacitySmallest that worksLarge enough to test at realistic volumeSized for the real workload
Shortcut targetsDEV upstream workspaceTST upstream workspacePRD upstream workspace

Never point a lower environment at a higher one

A shortcut or notebook in TST that reads PRD data defeats the purpose of the environment split and exposes production data to test-level access. Each environment's shortcuts must target the same environment's upstream workspace; see the promotion section for how to remap them.

Capacity placement

Every workspace is assigned to a capacity, and capacities are the unit of compute, billing and throttling. Separate layer workspaces let you choose where each kind of work runs. A common recommendation is dedicated capacity for the key layer workspaces and a minimal one for the hub, because the hub only runs light orchestration.

WorkloadShapePlacement guidance
Bronze, Silver, Gold loadsBursty Spark and pipeline work in scheduled windowsOne capacity sized for the peak batch window; it is mostly idle during business hours
Warehouse, models, reportsInteractive queries and scheduled refresh during business hoursA separate capacity so a heavy load cannot slow reports
AI and ML lakehouseExploratory, sometimes large Spark sessionsWhere experiments will not collide with business-hours reporting; often with the engineering capacity
Orchestration hubLight control flowA small capacity or shared with another low-demand workspace
DEV and TSTIntermittentSmaller capacities, separate from PRD

Size by measurement. Monitor capacity utilization through a representative period before settling on a split, and keep production on capacities that development work cannot touch.

Promotion in one page

Each layer workspace is promoted on its own through a deployment pipeline. The full treatment is in Deployment Pipelines and Promotion, with Git setup in GitHub Integration and the release steps in Deployment Checklist. The summary below is the part that matters for the medallion design.

  1. Develop in DEV. The DEV workspace is connected to a Git branch. A pull request is the review gate.
  2. Merge and sync. After merge, the change reaches the DEV workspace through Git integration, directly or from an automated build.
  3. Promote to TST. The layer's deployment pipeline copies the workspace content to the test stage, where automated and manual checks run.
  4. Release to PRD. After approval, the same pipeline copies the validated content to production.

Deployment pipelines can be driven by the Fabric REST API from a build tool such as GitHub Actions, which adds automated tests and approval gates around the same steps.

BehaviorConsequence for the medallion
Deployment copies item definitions, not dataA first deployment of a lakehouse creates an empty lakehouse with the same name in the target. Run the loads in the new stage to populate it.
The number of stages and their names are fixed when the pipeline is created; content deploys between adjacent stages, in either directionThe source describes promotion as strictly one way from DEV to TST to PRD; the product allows deployment in either direction between adjacent stages, so enforce the one-way rule with process and permissions, not by assuming the tool prevents it.
Deploying needs a pipeline admin who is at least a Contributor in both workspacesPipeline permissions and workspace roles are managed separately; plan the grants per layer.
A single deployment can include at most 300 items, and workspaces must be on a Fabric capacityLarge layers may need selective deployment; keep layer workspaces focused.
A deployment overwrites the shortcut definitions in the target lakehouseReview changes before every deployment; shortcuts that point to a different upstream workspace in each stage need remapping.
Notebooks and Spark job definitions are remapped to the lakehouse in the target stageReference lakehouses by item, not by hard-coded workspace names, so remapping works.

Verify against Microsoft Learn

Per the lakehouse deployment documentation, shortcut definitions are carried across stages: external targets keep the same target in every stage, and OneLake shortcuts within the same workspace are remapped automatically. Cross-workspace OneLake shortcuts, which this design uses between layers, are not described as remapped automatically; the documented options are variables in the shortcut definition through a variable library (itself a preview feature) or updating the shortcut after deployment, in the portal or through the OneLake APIs. Confirm the current behavior in Lakehouse git integration and deployment pipelines before you rely on it, and rehearse a full DEV to TST deployment with shortcuts in place.

Key takeaways

  • One domain in one environment is seven workspaces plus a shared hub; script their creation from the naming grammar.
  • Workspace names follow <ENV>_<DOMAIN>_<LAYER>[_<Qualifier>]; item names follow <ARTIFACT>_<DOMAIN>_<LAYER>_<Function> and omit the environment.
  • Shortcut edges run one hop downstream. No skipping, no upward edges.
  • Give each persona access to its own layer and read access to the layer before it, never a role in a layer it does not own.
  • Promote each layer through its own deployment pipeline. Content copies, data does not, and cross-workspace shortcuts need remapping per stage.
