Fabric notebooks in the medallion

Every layer-to-layer move in this playbook is a notebook run by a pipeline. This page covers what notebooks can do, how to size and structure them, how to orchestrate several, which hooks to monitor and which hard limits apply.

What a Fabric notebook is

A Fabric notebook is a web-based, interactive item for developing and running Apache Spark code, with cells that mix code and Markdown. In a medallion it is the main transformation tool: it reads upstream tables through shortcuts, applies logic and writes Delta tables into its own lakehouse. A notebook is also a first-class workspace item. It can be placed under Git source control and deployed across environments with deployment pipelines, which is why notebooks should hold thin, parameterized code and not tangled one-off analysis.

Consolidate after unit testing

Teams working in parallel can each create notebooks while they build. After unit testing, a designated lead should consolidate them into a smaller number of logically grouped notebooks. Each notebook is a workspace item, and a workspace holds at most 1,000 items counting parents and children, so unchecked notebook sprawl runs into that cap and into review fatigue long before it runs into compute limits.

Structure and sizing guidelines

These guidelines protect specific limits (listed in the hard limits table) and keep runs retryable.

GuidelineWhy it mattersHow
One responsibility per notebookSmaller units retry cheaply and stay under the executed-cell and size capsSeparate extract, transform and load notebooks, or thin notebooks that call library functions
Push reusable logic into librariesLess notebook code, faster reviews, testable functions, one fix for every tablePackage Python modules or wheels and attach them through an Environment item; notebooks only set parameters and call
Keep rendered output tinyOutputs count toward the notebook and snapshot size caps and slow the UIUse df.limit(20) or aggregates; write large results to a table; guard every display() behind a debug flag; disable rich output in production runs
Keep parameters small and simplePipeline parameters to notebooks accept int, float, bool and string; the per-activity payload is cappedPass identifiers, dates and flags; for larger configuration pass a JSON string or point to a control table
Limit nesting%run depth and total referenced cells are cappedPrefer library calls to deep notebook chains; keep depth well under five
Right-size the sessionOversized sessions waste capacity; undersized ones spill and failUse the workspace default Environment; override with %%configure only with equal driver and executor core and memory values, from the supported sizes
Manage the session lifecycleAn idle session still holds capacityStop sessions at the end of automated runs; raise the idle timeout only while developing
Respect pipeline timeoutsThe pipeline activity governs when a notebook is invoked from a pipelineSplit long jobs, checkpoint to Delta and make every step resumable
Log compactlyPrint-heavy notebooks bloat snapshotsAppend one structured row per load to a Delta log table

Parameters and orchestration

A parameterized child notebook

The first cell is marked as the parameter cell. Its values are defaults; a pipeline or a parent notebook overrides them at run time. The last cell hands a small result back as a string.

# ---- Cell 1: mark this cell as the parameter cell ("Mark cell as parameters") ----
watermark_value = ""        # ISO-8601 string from the control table; empty means "derive from the target"
debug = False               # guard every display() behind this flag

# ---- Cell 2: imports and shared helpers (or import them from a library in the Environment) ----
from datetime import datetime

# ... helper definitions from the library or a %run cell ...

# ---- Cell 3: the work, thin and parameterised ----
metrics = incremental_merge_scd1(
    spark,
    source_table="brz.orders",
    target_table="dbo.orders",
    key_candidates=[["order_id"]],
    watermark_cols=["last_modified_utc", "ingested_at_utc"],
    watermark_value=watermark_value or None,
    delete_condition="is_deleted = true",
)
if debug:
    display(spark.table("dbo.orders").limit(20))

# ---- Cell 4 (alone in its cell, outside try/except): hand a small result back to the caller ----
import json
notebookutils.notebook.exit(json.dumps({
    "rows_in_slice": metrics["rows_in_slice"],
    "new_watermark": metrics["new_watermark"],
    "mode": metrics["mode"],
}))

Keep exit at the top level

Do not call notebookutils.notebook.exit() inside a try and except block: the exit does not take effect when wrapped in exception handling. Put it alone in its own cell, because it also overwrites that cell's output. In a notebook run by a pipeline, exit completes the run, returns the value to the notebook activity and stops the Spark session.

Choosing how to call another notebook

MechanismSession and scopeParallelBest for
Pipeline notebook activityIts own Spark session per activity unless you configure session sharing; separate retry, timeout and monitoring row per activityYes, by pipeline designLayer-level steps, anything that needs isolation or visible per-step status
%runSame session; variables of the referenced notebook become available; same workspace only; depth up to fiveNoShared helper cells during development; prefer a library in production
notebookutils.notebook.runRuns on the caller's Spark pool; returns the child's exit value; timeout argument; can reference a notebook in another workspace by IDNoSequential children with return values
notebookutils.notebook.runMultipleChildren run as threads in the caller's session and share its computeYes, in a DAG with dependenciesMany small table loads that fit one session

A child run through notebookutils.notebook.run or runMultiple is blocked when it specifies a different default lakehouse from its parent. Let children inherit the parent's lakehouse, or pass useRootDefaultLakehouse: True in the arguments. A %%configure cell in a child called through notebookutils.notebook.run is ignored.

An orchestrator with a dependency DAG

The DAG runs the two dimension loads in parallel, then the order facts, then the order lines. validateDAG catches duplicate names, missing dependencies and cycles before anything runs, and a failure is re-raised after the partial results are inspected so the pipeline activity still fails.

# Orchestrator notebook: NB_SALES_SLV_RunAll. Each child notebook keeps its own parameter cell.
DAG = {
    "activities": [
        {"name": "dims_customers",   "path": "NB_SALES_SLV_LoadCustomers",
         "timeoutPerCellInSeconds": 600, "args": {"watermark_value": ""}},
        {"name": "dims_departments", "path": "NB_SALES_SLV_LoadDepartments",
         "timeoutPerCellInSeconds": 600},
        {"name": "fact_orders",      "path": "NB_SALES_SLV_LoadOrders",
         "timeoutPerCellInSeconds": 1800, "retry": 1, "retryIntervalInSeconds": 60,
         "dependencies": ["dims_customers", "dims_departments"]},
        {"name": "fact_order_lines", "path": "NB_SALES_SLV_LoadOrderLines",
         "timeoutPerCellInSeconds": 1800, "retry": 1, "retryIntervalInSeconds": 60,
         "dependencies": ["fact_orders"]},
    ],
    "timeoutInSeconds": 7200,   # whole DAG
    "concurrency": 4,           # children share ONE Spark session: size the pool for it
}

notebookutils.notebook.validateDAG(DAG)          # fail fast on cycles, duplicates, missing dependencies

from notebookutils.common.exceptions import RunMultipleFailedException

try:
    results = notebookutils.notebook.runMultiple(DAG)
except RunMultipleFailedException as ex:
    results = ex.result                          # partial results for logging
    failed = [name for name, r in results.items() if r["exception"]]
    raise RuntimeError(f"Failed activities: {failed}") from ex   # still fail the pipeline activity
DAG fieldLevelDefaultMeaning
timeoutInSecondsRoot12 hoursMaximum for the whole DAG
concurrencyRootThree times the available CPU coresMaximum notebooks running at once; 0 means unlimited. Set it deliberately, because children share one session
timeoutPerCellInSecondsActivity90 secondsMaximum for each cell in the child; raise it for load cells
retry, retryIntervalInSecondsActivity0Retry for transient failures

The default cell timeout is short

A child cell that merges a large table can exceed the 90 second per-cell default and fail with a timeout even though the Spark job is healthy. Set timeoutPerCellInSeconds per activity from observed run times.

Notebook job history is kept for a limited period, so anything an auditor may ask about later belongs in your own log table. The helper below appends one row per load and re-raises on failure.

import uuid
from datetime import datetime, timezone

from pyspark.sql import Row

RUN_LOG_TABLE = "dbo.etl_run_log"


def log_run(spark, notebook, target_table, mode, rows_in_slice, new_watermark,
            status, started_at, message=""):
    """Append one compact row per load: cheap to write, easy to chart, safe to show to operators."""
    row = Row(
        run_id=str(uuid.uuid4()),
        notebook=notebook,
        target_table=target_table,
        mode=mode,
        rows_in_slice=int(rows_in_slice or 0),
        new_watermark=None if new_watermark is None else str(new_watermark),
        status=status,
        message=message[:500],
        started_at_utc=started_at,
        finished_at_utc=datetime.now(timezone.utc),
    )
    (spark.createDataFrame([row])
          .write.format("delta").mode("append")
          .option("mergeSchema", "true")
          .saveAsTable(RUN_LOG_TABLE))


# ---- usage inside a load notebook ----
started = datetime.now(timezone.utc)
try:
    metrics = incremental_merge_scd1(
        spark,
        source_table="brz.orders",
        target_table="dbo.orders",
        key_candidates=[["order_id"]],
        watermark_cols=["last_modified_utc", "ingested_at_utc"],
        delete_condition="is_deleted = true",
    )
    log_run(spark, "NB_SALES_SLV_LoadOrders", "dbo.orders", metrics["mode"],
            metrics["rows_in_slice"], metrics["new_watermark"], "succeeded", started)
except Exception as ex:
    log_run(spark, "NB_SALES_SLV_LoadOrders", "dbo.orders", "unknown",
            0, None, "failed", started, message=str(ex))
    raise            # the pipeline activity must still fail

Small appends create small files

Each append writes at least one small file. At a few hundred rows a day that is harmless; if it grows, batch the log writes in the orchestrator or compact the log table on a schedule.

Notebook output is not protected by data security

Data security rules apply while a query runs. A cell that has already displayed query results keeps them in the notebook, where anyone who can open the notebook can see them. Do not display sensitive rows in shared notebooks, and clear outputs before committing.

Do and do not

Do

  • Keep rendered outputs tiny and behind a debug flag
  • Checkpoint data to Delta between steps
  • Modularize through libraries in an Environment
  • Keep parameters small and typed as simple values
  • Stop sessions at the end of automated runs
  • Watch executed-cell counts and nesting depth
  • Set per-cell timeouts and retries per DAG activity
  • Test with the identity that the schedule will use

Do not

  • Pass large JSON payloads into notebook activities
  • Nest %run deeply
  • Render full tables or keep heavy images in a notebook
  • Rely on inline %pip in scheduled runs; it is off by default there and versions drift
  • Wrap exit() in try and except
  • Assume a notebook's own run limit overrides the pipeline activity limit
  • Print secrets or sensitive rows to the cell output

Verify against Microsoft Learn

Three figures are stated inconsistently across pages. Pipeline activity timeout: the Data Factory limits table gives 24 hours as the maximum for a pipeline activity run, the activity overview describes a default of 12 hours and a maximum of seven days, and the pipeline definition reference states a different default. The single-file limit in resource storage is 100 MB on the notebook limitations page and 50 MB on the environment resources page. Plan for the stricter value in each case (24 hours, 50 MB) and test the limit you depend on in your own tenant. See Data Factory limitations overview, Activity overview, Fabric Notebook known limitation and Manage the resources in a Fabric environment.

Key takeaways

  • Keep notebooks thin: parameters, one call into a library, a small exit value. Logic lives in an Environment library.
  • Use runMultiple for many small loads in one session and pipeline activities when you need isolation or per-step visibility. Set concurrency and per-cell timeouts deliberately.
  • Design to the governing limit: the smallest one on the path from pipeline activity to Spark session.
  • Log one compact row per load to Delta; run history does not last, and notebook outputs are not access controlled.
  • Consolidate notebooks after unit testing; every notebook counts against the workspace item cap.
