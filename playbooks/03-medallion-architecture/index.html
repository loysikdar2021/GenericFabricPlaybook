Medallion Architecture

How to lay out a Fabric analytics platform as five isolated layers, one workspace each, and how to move data between them with shortcuts, notebooks, MERGE utilities, a warehouse and semantic models, using one naming standard from the first workspace to the last report.

  • Audience data engineers, architects, platform and security teams
  • Level intermediate
  • Reading time 120 min
  • Pages 10

Purpose and scope

The medallion pattern says data should improve in stages: raw in Bronze, cleansed and conformed in Silver, modeled for the business in Gold. Most teams stop there and put all three stages in one workspace. This playbook takes a stricter position that Microsoft's own guidance points toward: each layer gets its own workspace, and so do the two layers that sit after Gold, Consumption (warehouse, semantic models, AI/ML lakehouse) and Delivery (reports and apps). The workspace is the unit of access control, capacity assignment, Git connection and promotion in Fabric, so making it the unit of a layer turns the architecture diagram into something the platform enforces.

The playbook is implementation-oriented. It gives you the workspace and item inventory, the naming standard that makes a hundred items readable, the shortcut-based wiring between layers, reusable notebook code for full and incremental loads, the Warehouse and semantic-model hand-off, and the notebook and Environment standards that keep the Spark side consistent. Every code sample uses a fictional retailer, Contoso, with customers, orders, order lines, products, employees and departments.

Strict isolation is a position, not a default

Five workspaces per domain per environment is the most isolated option, and it has a real cost in objects to create, permissions to grant and orchestration to wire. The decision table compares it with fewer workspaces and with schemas inside one lakehouse so you can choose deliberately and, if you choose less isolation, know what you gave up.

Design principles

  1. One workspace per layer. The workspace is where roles, capacity, Git and deployment are set, so it is the right place to draw a layer boundary.
  2. One hop at a time. A layer reads only the layer immediately before it, through shortcuts that appear as local tables. No skip-level reads, no reads from a later layer.
  3. Each layer owns its writes. Only the notebooks and pipelines of a layer write to that layer's lakehouse. Downstream layers get read access, never write access.
  4. Virtualize, do not copy, between layers' read paths. Shortcuts remove the staging copy; the transformation notebook is the only place data is materialized.
  5. Parameterize every name. Lakehouse, schema and table names are parameters, so the same notebook promotes unchanged from development to production.
  6. Reconcile at every boundary. Row counts and checksum measures are compared when data crosses a layer, in development by hand and afterwards by automated checks.
  7. Use one naming standard. The environment, domain and layer in the workspace name repeat in every item name, so any item identifies its own place in the estate.
  8. Least privilege by layer. Engineers see Bronze; most analysts never do. BI developers work in Consumption and Delivery.

What you will have built

  • Workspaces for each layer, domain and environment, named by one standard and assigned to capacities
  • Lakehouses with shortcuts that expose each upstream layer as local, read-only tables
  • A reusable full-load function and an incremental MERGE utility for Silver, parameterized per table
  • A config-driven Gold engine with built-in reconciliation checks
  • A Warehouse loaded from Gold shortcuts, a semantic model on top of it, and a consumption lakehouse for AI/ML
  • Reports published to a separate Delivery workspace from a shared semantic model
  • One Environment item per workspace so every notebook runs with the same Spark settings
  • A promotion path through deployment pipelines (detailed in the deployment playbook)

Implementation checklist

  • Decide the isolation level using the decision table and record the choice and the reasons
  • Agree environment, domain and layer abbreviations; reserve the naming standard before the first workspace is created
  • Create workspaces for one domain in development, assign roles by layer, and set the capacity
  • Create one schema-enabled lakehouse per lakehouse layer and one Environment item per workspace; publish and set it as the workspace default
  • Create the Silver shortcuts and verify they read through the identity that will run the notebooks
  • Build and unit-test the first Bronze to Silver notebook with row-count checks; then remove the checks and add automated reconciliation
  • Repeat for Gold; create the consumption lakehouse, warehouse and semantic model; publish a report to the Delivery workspace
  • Connect each workspace to source control and create the deployment pipeline for each layer
  • Orchestrate the notebooks with a pipeline and monitor the first scheduled runs

Key takeaways

  • Make the workspace the layer boundary, for Consumption and Delivery as well as Bronze, Silver and Gold, and let the platform enforce it.
  • Read one hop at a time through shortcuts; write only into your own layer.
  • Treat strict isolation as a choice with a cost, and use the decision table before committing a team to it.
  • Parameterize names and promote the same notebook unchanged across environments.
  • Standardize Spark settings in an Environment item, not in notebook snippets.
