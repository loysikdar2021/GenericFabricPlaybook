Playbook 09 · Variable Libraries

Worked example and operations

One end-to-end example for a fictional retailer: a library with a connection, an item reference and stage values; a pipeline and a notebook that consume it; a release that deploys and activates it in TST and PRD; and a guard that fails fast when a stage runs with the wrong value set. The page then covers anti-patterns, troubleshooting and a validation checklist.

The scenario

Contoso's sales domain loads orders from an operational database into a bronze lakehouse. The bronze layer has three workspaces and one deployment pipeline:

Build it in DEV

  1. Create the library.

    In DEV_SALES_BRZ create VL_SALES_BRZ_Config and add the five variables with the DEV values as defaults (see the table above). For the two reference types, pick the DEV database connection and LH_SALES_BRZ in the picker. Save.

  2. Add the stage value sets.

    Add TST and PRD. In each, override only what differs: StageName, OrdersDb, BronzeLakehouse, and LookbackDays for TST. Save.

  3. Bind the pipeline.

    In PL_SALES_BRZ_LoadOrders add library variable references for OrdersDb, BronzeLakehouse and LookbackDays. Run NB_SALES_BRZ_StageGuard as the first activity. In the Copy activity bind the source connection, the destination workspace and lakehouse, and the query to the references as shown below.

  4. Bind the notebook.

    In NB_SALES_BRZ_LoadOrders read FullReload and the lakehouse reference with NotebookUtils, as in Create and consume variables.

  5. Test in DEV

    Use Preview data on each bound activity and run the full pipeline. Then commit to Git.

Destination workspace .... @pipeline().libraryVariables.BronzeLakehouse    (choose the workspace property)

The stage guard

Nothing in the platform stops a TST or PRD workspace from running with the default (DEV) value set. The guard turns that mistake into a failed first activity instead of a quiet load into the wrong place. It compares the stage the workspace's name declares (by the <ENV>_<DOMAIN>_<LAYER> naming convention) with the StageName the active value set reports.

cfg = notebookutils.variableLibrary.getLibrary("VL_SALES_BRZ_Config")

workspace = notebookutils.runtime.context["currentWorkspaceName"]   # for example PRD_SALES_BRZ
expected = workspace.split("_")[0]                                   # DEV, TST or PRD by convention

# Only TST and PRD are protected: DEV and feature workspaces may run the default set.
if expected in ("TST", "PRD") and cfg.StageName != expected:
    raise RuntimeError(
        f"Stage guard failed: workspace {workspace} expects the {expected} value set, "
        f"but the active value set reports StageName={cfg.StageName}. "
        "Activate the stage's value set and run again."
    )

print(f"Stage guard passed for {workspace}: StageName={cfg.StageName}")
  • The guard depends on a disciplined naming convention. If your workspace names do not start with the stage, compare against a value you control instead, for example a variable you pass as a pipeline parameter.
  • Put the same check in the first cell of notebooks that are run on their own, or call it from every pipeline so it runs once per run.
  • The guard cannot verify the other variables, only that the stage's set is active. Keep value sets reviewed in Git so a wrong value in the right set is caught in review.

Release to TST and PRD

  1. Deploy

    In DPLY_SALES_BRZ compare DEV with TST and deploy the library together with the pipeline and notebooks. Expect the library to appear as a new or changed item.

  2. Activate the stage's value set

    Activate TST in the TST workspace by hand, or with the script from the REST section:

    ./scripts/activate_value_set.sh "<tst-workspace-id>" "VL_SALES_BRZ_Config" "TST"
  3. Run the guard and a test load

    Run PL_SALES_BRZ_LoadOrders. The guard passes, the Copy activity reads from the TST database connection, and rows land in LH_SALES_BRZ in TST_SALES_BRZ. Check the lookback window against the TST override (7 days).

  4. Approve and repeat for PRD

    Deploy the same versions to PRD, activate PRD, confirm the guard, then run a smoke load. In the comparison, TST and PRD should show no differences for the library definition; the active value sets differ by design and do not show.

Fold it into the checklist

The deployment, the activation and the guard result belong in the release record. See the Deployment Checklist and the stage-by-stage order in Deployment Pipelines and Promotion.

Anti-patterns

Anti-patternWhy it hurtsInstead
Secrets, tokens or keys stored as variablesAnyone who can view the library can read them, and they sit in GitUse connection references and key vault references; store only identifiers
One library for the whole tenant or workspaceCouples unrelated teams, widens write access and approaches size limitsOne library per domain and layer
Code that branches on the stage name (if stage == "PRD")Behavior differs between stages for reasons hidden in code; TST no longer proves PRDExpress differences as values (flags, sizes, targets); keep code identical
Editing the PRD value set in the PRD workspaceDrifts from Git and from TST; the next deployment of the definition overwrites or conflicts with itChange values in DEV and promote; use the comparison as a drift detector
Assuming deployment activates the right value setThe default set stays active until someone changes itScript activation and add the stage guard
Renaming or retyping variables casuallyConsumers bind by name and type; a type change resets the valuesAdd a new variable, migrate consumers, then delete the old one
Expecting a hub workspace's library to configure spokesLibraries are read in the consumer's own workspace onlyOne library per workspace, deployed with the items that use it
Reference variables copied between stages without checking the targetAn item or connection reference is a static ID; a stale ID points at the wrong stage's resourceReview value set files in pull requests; run the guard; test with Preview data
Adding a variable where Fabric already rebinds the dependencyAn extra moving part for no gainRely on autobinding (for example the default lakehouse of a notebook in the same workspace)
Using a variable for a per-run valueA library edit is a configuration change, not a run inputUse a pipeline or notebook parameter
Mixed conventions: a value set named DEV next to a default that also holds DEV valuesNobody knows which is authoritativePick one convention (see default value set) and apply it everywhere

SymptomLikely causeFix
TST or PRD runs with DEV valuesThe default value set is still active after the first deploymentActivate the stage's set; add the guard and the scripted activation
The library is missing from a pipeline's variable pickerThe library is in another workspace, or the user has no access to itCreate or deploy the library in the consumer's workspace; check the user's workspace role or direct share
A notebook cannot resolve a variableMissing /**/ prefix, or the library or variable name differs in caseUse $(/**/Library/Variable) and the exact names
%%configure does not set the lakehouseThe variables are not String type, or workspaceId is missing for a lakehouse in another workspaceRedefine them as String and add the workspace ID
Number variables are not offered in a pipelinePipelines do not support the Number typeUse Integer, String or read the value in a notebook
Consumers broke after editing a variableA type change resets values; a rename breaks name-based bindingsRestore from Git, then add a new variable and migrate
A value set cannot be deletedIt is the active setActivate another set, then delete
Save fails with a validation errorInvalid name, or a limit exceeded (1,000 variables, 1,000 value sets, 10,000 cells, 1 MB)Fix the reported names or split the library
The library shows as different from source in a comparisonA variable or value set was edited in that stage, or the stages are on different versionsRedeploy from the source stage or update the source, whichever is correct
An active-set change does not appear in a comparisonBy design: the active set is not part of the definitionVerify with the list API or the stage guard
A reference shows a value but no name or detailsThe caller lacks Read permission on the item or connection, or it no longer existsGrant Read, or correct the reference

A copy job still uses the DEV connection after deploymentThe stage's connection value set has not been activatedActivate the value set in the target workspace

Validation checklist

Use this list when you introduce a library and again for every first deployment into a stage.

  • One library per domain and layer, named by convention (VL_<DOMAIN>_<LAYER>_<Purpose>), with a named owner.
  • Value sets are named exactly after the stages, with one default-value-set convention across the organization.
  • Every variable has a decided type and a note; reference types point at items and connections the editor can read.
  • No secrets, tokens or passwords in any value.
  • Consumers contain no hard-coded workspace IDs, item IDs, connection IDs or stage-specific names (search the item definitions in Git).
  • Write access to the libraries is limited, and the library folder has code owners in the repository.
  • The library is deployed together with its consumers in the same deployment.
  • The stage's value set is activated for every library in the stage, by a scripted step, and verified through the list API.
  • The stage guard runs first in every TST and PRD pipeline and passes.
  • Preview data on a bound pipeline activity shows the stage's expected values.
  • After the release, comparing stages shows no unexpected differences for the library definition.
  • The release record names the library versions deployed and the value sets activated.

Key takeaways

  • Model every stage difference as a value, deploy identical items everywhere, and add the two post-deployment steps: activate the stage's set, then confirm with a guard.
  • Keep a stage name in the library and compare it with the workspace's declared stage to catch the default set running in TST or PRD.
  • Most incidents are a wrong active set, an unsaved or undeployed edit, a cross-workspace read, or an unsupported type; check them in that order.
  • Avoid secrets in values, one-library-for-everything, stage-name branching in code and hand edits in PRD.
