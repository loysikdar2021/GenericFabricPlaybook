Playbook 09 · Variable Libraries

Promotion, Git and automation

A variable library is only useful if it travels well. This page explains what a deployment pipeline and Git do and do not carry, the activation step that follows the first deployment into a stage, how variable libraries compare with deployment rules, and how to script activation through the REST API.

Variable libraries in deployment pipelines

The variable library is a deployable item type, so a deployment pipeline copies the library, with all its variables and value sets, from one stage to the next like any other item. The behavior that matters:

  • Every value set travels to every stage, but only one is active in a stage. The active set is chosen independently per stage and can be changed at any time.
  • The first arrival defaults. When a library first lands in a stage (or first reaches a repository), its active value set is the default value set. Change it by opening the new library in the target stage.
  • Deployments do not touch the active choice, although you can keep updating values: the consumers in that stage pick up the right value from the active set automatically.
  • Consumers resolve independently of their own deployment. A consumer reads whatever is active in its workspace when it runs; the order of deployment between a library and its consumers matters less than activating before the first run.

What shows up as a difference

Change in one stageRegisters as "different from source" in a comparison?
Variable added, deleted or editedYes
Value set added or deletedYes
Variable name changedYes
Order of variables changedYes
Active value set changedNo: it is part of the item configuration, not the definition

The practical consequence is that a stage whose library was edited in place (a value tweaked in PRD) shows as different from TST, which is a useful drift detector, while a stage running the wrong active set shows nothing. Detecting the second case is the job of the stage guard.

The step after the first deployment

The first time a library is deployed into a stage, activate that stage's value set before anything that reads a variable runs. This is the only step that is not carried by the deployment and the one most often missed.

  1. Deploy the library with its consumers.

    Deploy the library together with the pipelines, notebooks, dataflows and shortcuts that use it. Follow the layer order in Deployment Pipelines and Promotion: the library belongs with the layer whose items consume it.

  2. Open the library in the target stage.

    Open the new library in the target workspace, either from the workspace or from the item in the deployment pipeline's target stage.

  3. Set the stage's value set as active.

    Use the three-dot menu next to the value set (for example TST in the TST workspace) and select Set as active, then save.

  4. Verify.

    Check the library's active value set, run the stage guard (see the worked example), and use Preview data on a pipeline activity that references a variable to see the resolved value.

  5. Record it.

    Add the step to the release checklist (see the Deployment Checklist) so it is done per stage and per library, and automate it with the script below once the process is stable.

Repeat for every library

The active value set is chosen per library. A workspace with three libraries needs three activations. Name value sets identically across libraries so one script can activate them all by stage name.

Feature workspaces and branch-out

A developer's feature workspace created from a branch receives the library with the default set active. Under the convention in which the default set holds the DEV values, that is the right behavior: feature workspaces work against development resources with no extra step, and they cannot accidentally point at TST or PRD.

Variable libraries and Git

Like other Fabric items, a library is stored in the connected repository as a folder. Item permissions are checked when you commit and when you update from Git, so a user cannot change a library through Git without the permission they would need in the workspace.

PartHolds
variables.jsonEvery variable: name, type, optional note and the default value
valueSets/<name>.jsonOne file per alternative value set, holding only the variables that override the default
settings.jsonUser settings: the order in which value sets are listed
.platformItem metadata, generated automatically

Example files

These examples show the shape of each file with neutral names and placeholder IDs. Treat them as a guide and copy the exact shape from a library you commit from your own workspace.

    {
      "name": "BronzeLakehouse",
      "type": "ItemReference",
      "value": {

        "itemId": "00000000-0000-0000-0000-000000000000"
      }
    }
  ]
}
{
  "$schema": "https://developer.microsoft.com/json-schemas/fabric/item/variableLibrary/definition/valueSet/1.0.0/schema.json",
  "name": "TST",
  "variableOverrides": [
    { "name": "StageName",    "value": "TST" },
    { "name": "LookbackDays", "value": 7 }

}

}
  • The order list can be empty or partial, cannot contain value set names that do not exist, and value sets missing from it are appended in alphabetical order.
  • Because every value set is its own file, a pull request shows exactly which stage's configuration changed. Protect the folder with code owners so the right people review changes (see Pull-Request Notifications with CODEOWNERS).
  • Reordering value sets, bulk edits and copying a set between libraries are quicker in the JSON than in the UI.

Git-only flows without deployment pipelines

If stages are driven only by Git (a branch or folder per stage, each synced to its workspace), the library definition arrives through the sync and the active value set still has to be set in each workspace, because Git does not carry it. Script that step with the API below and run it after the sync.

Variable libraries or deployment rules?

Deployment rules and variable libraries both give a stage its own values. They differ in where the value lives, which items they cover and when they take effect.

AspectDeployment rulesVariable libraries
Where configuredOn the target stage of a deployment pipeline, per itemIn a library item in each workspace, shared by many items
Item typesData source and parameter rules for dataflows Gen1, semantic models, paginated reports (data source) and mirrored databases (data source); a default lakehouse rule for notebooksPipelines, notebooks, Dataflow Gen2, lakehouse shortcuts, copy jobs, user data functions, eventstreams and others
Needs a deployment pipelineYesNo; works with Git-only flows too
Can be set in the development stageNo: rules cannot be created in the development stageYes: DEV values live in the library
Who can set itThe owner of the item the rule is forAnyone with write access to the library
When it takes effectAt the next deployment to that stageWhen the consumer next runs after activation or an edit
What can be lostRules are deleted with the item and lost when a workspace is unassigned and reassignedValues are in the item and in Git
RestrictionsData source rules only switch to a data source of the same type; a rule that references a removed parameter breaks the deploymentPer-consumer limits (types, same workspace); reference variables are static pointers

A rule can override autobinding

Notebook deployment rebinds the default lakehouse and attached Environment automatically when the dependent items are in the same workspace. If you need a specific lakehouse in the target stage, a default lakehouse rule overrides that. Setting the default lakehouse with %%configure from a library (see With %%configure) is the library-based alternative and is the one that works without a deployment pipeline.

REST API and automation

The Fabric REST API manages variable libraries as items. These operations cover the lifecycle:

OperationRequestNotes
List libraries in a workspaceGET /v1/workspaces/{workspaceId}/variableLibrariesEach entry includes properties.activeValueSetName. Pagination uses a continuation token.
Set the active value setPATCH /v1/workspaces/{workspaceId}/variableLibraries/{variableLibraryId} with {"properties": {"activeValueSetName": "TST"}}Caller needs read and write permission on the library. Scopes: VariableLibrary.ReadWrite.All or Item.ReadWrite.All. Users, service principals and managed identities are supported.
Read or replace the definitionThe core item definition operations (get definition, update definition) with the parts variables.json, settings.json, .platform and one part per value setUse these to reorder value sets or to write values from automation. Definitions are base64-encoded parts.
Rate limitingHTTP 429 with a Retry-After headerBack off for the number of seconds returned.

The following script activates a value set by library name, so a release job can call it once per library and stage. It authenticates with the signed-in Azure CLI identity.

#!/usr/bin/env bash
# Activate a value set on a variable library in one workspace.
# Usage: activate_value_set.sh <workspace-id> <library-name> <value-set-name>
set -euo pipefail

WORKSPACE_ID="$1"
LIBRARY_NAME="$2"
VALUE_SET="$3"
API="https://api.fabric.microsoft.com/v1"

TOKEN="$(az account get-access-token --resource https://api.fabric.microsoft.com --query accessToken -o tsv)"
AUTH=(-H "Authorization: Bearer ${TOKEN}")

list_libraries() {
  curl -sS --fail "${AUTH[@]}" "${API}/workspaces/${WORKSPACE_ID}/variableLibraries"
}

# 1. Resolve the library ID from its display name.
LIBRARY_ID="$(list_libraries | jq -r --arg n "$LIBRARY_NAME" '.value[] | select(.displayName == $n) | .id')"
if [ -z "$LIBRARY_ID" ]; then
  echo "Library '${LIBRARY_NAME}' not found in workspace ${WORKSPACE_ID}" >&2
  exit 1
fi

# 2. Set the active value set.
curl -sS --fail -X PATCH "${AUTH[@]}" -H "Content-Type: application/json" \
  -d "{\"properties\": {\"activeValueSetName\": \"${VALUE_SET}\"}}" \
  "${API}/workspaces/${WORKSPACE_ID}/variableLibraries/${LIBRARY_ID}" > /dev/null

# 3. Verify that the change took effect.
ACTIVE="$(list_libraries | jq -r --arg id "$LIBRARY_ID" '.value[] | select(.id == $id) | .properties.activeValueSetName')"
if [ "$ACTIVE" != "$VALUE_SET" ]; then
  echo "Active value set is '${ACTIVE}', expected '${VALUE_SET}'" >&2
  exit 1
fi
echo "Active value set on ${LIBRARY_NAME}: ${ACTIVE}"
param(
  [Parameter(Mandatory)] [string] $WorkspaceId,
  [Parameter(Mandatory)] [string] $LibraryName,
  [Parameter(Mandatory)] [string] $ValueSet
)
$ErrorActionPreference = 'Stop'
$api     = 'https://api.fabric.microsoft.com/v1'
$token   = az account get-access-token --resource https://api.fabric.microsoft.com --query accessToken -o tsv
$headers = @{ Authorization = "Bearer $token" }
$listUri = "$api/workspaces/$WorkspaceId/variableLibraries"

$library = (Invoke-RestMethod -Headers $headers -Uri $listUri).value |
  Where-Object { $_.displayName -eq $LibraryName }
if (-not $library) { throw "Library '$LibraryName' not found in workspace $WorkspaceId" }

$body = @{ properties = @{ activeValueSetName = $ValueSet } } | ConvertTo-Json
Invoke-RestMethod -Method Patch -Headers $headers -ContentType 'application/json' `
  -Body $body -Uri "$listUri/$($library.id)" | Out-Null

$active = ((Invoke-RestMethod -Headers $headers -Uri $listUri).value |
  Where-Object { $_.id -eq $library.id }).properties.activeValueSetName
if ($active -ne $ValueSet) { throw "Active value set is '$active', expected '$ValueSet'" }
"Active value set on ${LibraryName}: $active"

To run it from GitHub Actions, sign in with a federated credential and call the script after the deployment step. The identity needs a role on the workspace that allows editing the library, and the tenant must allow service principals to call Fabric public APIs.

name: activate-value-set

on:
  workflow_dispatch:
    inputs:
      stage:
        description: Stage whose value set to activate
        type: choice
        options: [TST, PRD]

permissions:
  id-token: write
  contents: read

jobs:
  activate:
    runs-on: ubuntu-latest
    environment: ${{ inputs.stage }}          # holds FABRIC_WORKSPACE_ID for that stage
    steps:
      - uses: actions/checkout@v4
      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          allow-no-subscriptions: true
      - name: Activate the stage value set
        run: ./scripts/activate_value_set.sh "${{ vars.FABRIC_WORKSPACE_ID }}" "VL_SALES_SLV_Config" "${{ inputs.stage }}"

Key takeaways

  • Deployment pipelines copy the library and every value set; the active value set is never copied and does not show as a difference.
  • After the first deployment into a stage, activate that stage's value set before anything runs; script it with a PATCH on activeValueSetName and verify.
  • In Git the library is a folder of JSON: default values, one file per value set (overrides only), settings and the platform file. Commit from your own workspace to learn the exact shapes.
  • Use autobinding where Fabric rebinds for you, deployment rules for the item types they cover, and variable libraries for everything else that supports them.
