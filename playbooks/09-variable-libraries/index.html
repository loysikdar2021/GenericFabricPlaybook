Playbook 09 · Variable Libraries

Variable libraries: per-stage configuration without editing items

A variable library is a Fabric item that holds the values that change between DEV, TST and PRD (workspace and item IDs, connections, batch sizes, flags) so that the pipelines, notebooks, dataflows and shortcuts that use them can be promoted unchanged. This playbook covers how it works, how to build and consume one, how it behaves in Git and deployment pipelines, and how to run it safely.

  • Audience data engineers, platform engineers, release managers
  • Level intermediate
  • Reading time about 65 minutes

The problem: stage-specific values buried in items

Every promoted solution carries a handful of values that must differ by stage: the lakehouse a copy activity reads, the connection it uses, the workspace an item points at, how many days of data a test run loads. When those values live inside the items, every promotion needs a human or a script to fix them, and every fix is a chance to ship the DEV value into PRD.

The usual workarounds each break down in a different place:

WorkaroundWhere it breaks
Hard-coded IDs, edited after each deploymentManual, easy to forget, invisible in review, and the edit is lost on the next deployment that overwrites the item
Pipeline parameters with a different default per stageThe default is part of the item, so the item differs between stages and shows as changed in every comparison
A Git branch per stage with edited copies of the same itemsConfiguration drift and merge conflicts; the branches stop being copies of each other
Deployment rulesCover only a few item types (data sources and parameters for dataflows Gen1, semantic models, paginated reports, mirrored databases; the default lakehouse for notebooks); they take effect only from the next deployment and cannot be defined in the development stage
Post-deployment scripts that patch item definitionsYou now maintain a deployment tool, and it must understand every item format

What a variable library is

A variable library is an item in a workspace that contains a list of variables and, for each variable, a value for every stage in the release path. Other items in the same workspace consume the variables. Each consumer resolves the value in its own context, when it runs, so the library does not have to be deployed in lockstep with its consumers.

The design has four parts, covered in depth on the next page:

  1. Variables

    Named, typed values: basic types (Boolean, Integer, Number, String, DateTime, Guid) and two advanced reference types (item reference, connection reference).

  2. Value sets

    A default value set holds every variable's baseline value. Any number of alternative value sets override only the variables that differ, for example TST and PRD.

  3. An active value set

    Exactly one value set is active per library in a workspace. It is workspace state, not part of the item definition, so a deployment does not overwrite it.

  4. Consumers

    Pipelines, notebooks, Dataflow Gen2, lakehouse shortcuts, copy jobs and other items read the active values by library and variable name.

What it is not

  • Not a secret store. Anyone who can view the library can read its values (a workspace Viewer can view the item). Keep credentials in connections or a key vault and store only a reference.
  • Not writable at run time. Notebooks can read variables but not change them. It is configuration, not shared state.
  • Not cross-workspace. Consumers use libraries in their own workspace. A notebook cannot read a library from another workspace.
  • Not automatic on deploy. The first deployment brings the library up with its default value set active. Selecting the right set per stage is a step you perform (and can script) after the library lands in the stage. See the step after deployment.
  • Not a replacement for autobinding. Where Fabric already rebinds a dependency within a workspace (a notebook's default lakehouse, for example), you do not need a variable.

When to use a variable library

Use it whenUse something else when
The same item must point to a different lakehouse, workspace or connection per stageThe value is a credential or token: use a connection or a key vault reference
A value changes with the stage but not with the run (batch size, lookback window, feature flag)The value changes with every run: use a pipeline or notebook parameter
Several items in a workspace share one value and you want to change it onceThe consumer is in another workspace: pass the value as a parameter or resolve it inside the consumer's own workspace
You want per-stage configuration reviewed in Git next to the items it configuresAutobinding or a deployment rule already does the job for that item type
You need to switch a data source for a whole workspace in one actionThe consumer is not on the supported list (see consumers)

Prerequisites

  • A workspace on a Fabric capacity per stage (the examples use DEV_SALES_SLV, TST_SALES_SLV and PRD_SALES_SLV).
  • The tenant setting Users can create Fabric items enabled for the people who build libraries.
  • A workspace role of Contributor or higher to create and edit a library; Viewer is read-only.
  • Items that support variable libraries (pipelines, notebooks, Dataflow Gen2 with CI/CD, lakehouse shortcuts, copy jobs and others; see the supported-items table).
  • For promotion: a deployment pipeline or Git integration (or both) set up as described in GitHub Integration and Branching and Deployment Pipelines and Promotion.
  • For reference variables: Read permission on every item or connection you point a variable at.

What you will have at the end

  • A variable library per domain and layer with a value set per stage, built to a naming convention.
  • Pipelines, notebooks and shortcuts reading their stage values from it, with no hard-coded IDs.
  • A repeatable step that activates the right value set after each first deployment, with a guard that fails fast if a stage runs with the wrong one.
  • A clear rule for when a variable, a deployment rule or autobinding is the right tool.
  • A troubleshooting table and a checklist for the first deployment into each stage.

Key facts at a glance

Scope
A library and its consumers live in the same workspace. One library holds up to 1,000 variables and 1,000 value sets, within 10,000 alternative-value cells and 1 MB in total.
Variable types
Boolean, Integer, Number, String, DateTime (ISO 8601, UTC), Guid, plus item reference Preview and connection reference Preview.
Active value set
Exactly one per library per workspace; not part of the item definition; not overwritten by a deployment.
Consumers
Pipelines, lakehouse shortcuts, notebooks (NotebookUtils and %%configure), Dataflow Gen2, copy jobs, user data functions, eventstreams, deployment plan action parameters and Plan.
Lifecycle
Supported by Git integration and deployment pipelines, and managed through the Fabric REST API.

Key takeaways

  • A variable library moves stage-specific values out of items, so the same item definition can be promoted to every stage.
  • The default value set holds all values; alternative sets override only what differs; one set is active per workspace.
  • The active value set is workspace state: deployments do not set it, so activating the right set is part of every first deployment.
  • It is configuration for items in the same workspace: no secrets, no cross-workspace reads, read-only from notebooks.
