Playbook 09 · Variable Libraries

Create and consume variables

Create a library in a few minutes, then wire it into the items that need stage-specific values. Each consumer reads variables differently and has its own limits, so this page gives the procedure for each and a matrix of what to design around.

Create a variable library

Do this in the development workspace, in the same workspace as the items that will consume the library. Libraries are workspace-scoped, so each stage gets its own copy through deployment, not through a shared library.

  1. Create the item

    In the workspace select + New item, scroll to Develop data and select Variable library. (From the Fabric home page you can also select Create and pick Variable library in the Data Factory section.) Name it by the house convention, for example VL_SALES_SLV_Config, and select Create. An empty library opens.

  2. Define the variables

    Select + New variable. Enter a name, choose a type, enter the default value and, optionally, a note that says what the variable controls and who owns it. Select Save. Saving validates every variable name and value; fix reported errors before the save succeeds. Repeat for each variable.

  3. Add the alternative value sets

    Select Add value set, name it with the stage name (TST, PRD), optionally add a description, and enter the stage's values. You only need to change the variables that differ from the default. Select Save.

  4. Activate the right set in this workspace

    The default value set is active in a new library. To switch, use the three-dot menu next to a value set and select Set as active (the menu also offers Rename and Delete), or select Set as active while creating the set. Changes take effect only after you save.

  5. Reference it from consumers

    Use the procedures below. Test each consumer in this workspace before you deploy.

Edit in DEV, deploy everywhere else

Make value changes for every stage in the development workspace and promote them with the library. Editing the PRD value set directly in the PRD workspace creates a difference the deployment pipeline reports and that Git does not contain.

Pipelines

A pipeline does not read the library directly in an expression. You first add a library variable reference to the pipeline, then use that reference in dynamic content. There is no need to create pipeline parameters and map them to the library: the reference is the link.

  1. Add the reference

    Open the pipeline and select an empty area of the canvas so that no activity has focus. In the bottom panel open Library variables and select + New. Pick the variable from the library picker, give the reference a name (for example SourceTable) and select OK.

  2. Use it in an activity

    On the activity setting to parameterize (a connection, workspace, table name, wait time, query), choose Add dynamic content. In the expression builder open the Library variables tab (if it is hidden, use the three dots next to Functions) and select the reference. The builder inserts @pipeline().libraryVariables.SourceTable.

  3. Reference types need a property

    For a connection reference or an item reference, type a . after the reference in the builder and choose the property you need (the connection ID, the item ID or the item's workspace).

  4. Check the value

    Use Preview data on the activity to see what the reference resolves to, then save and run. The value is whatever the active value set of the workspace contains.

@pipeline().libraryVariables.SourceTable
@pipeline().libraryVariables.LookbackDays
@concat('orders_', pipeline().libraryVariables.StageName)

Pipelines see Boolean as Bool, Integer as Int, and DateTime and Guid as String. Number variables are not supported in pipelines, so model a decimal threshold as an integer in minor units or read it in a notebook.

The connection scenario

The most common use is making a copy activity connect to the stage's own source and destination without editing the pipeline after deployment:

  1. Model the connection as a variable.

    Use a connection reference variable for an external connection, or a String variable holding the lakehouse and workspace IDs for a Fabric destination. Give each stage its value in its value set. Look up a connection's ID in Manage connections and gateways.

  2. Add references on the pipeline.

    Add one library variable reference per value the activity needs (connection, workspace ID, table name).

  3. Bind the activity.

    In the Copy activity, open Source, choose Add dynamic content on the connection (and on workspace and table fields) and select the references. Repeat for Destination.

  4. Test in DEV, deploy, then activate.

    Deploy the pipeline and the library together. In the target stage activate the stage's value set (see the step after deployment) before the first run.

A pipeline's identity runs the activity

When a pipeline runs a notebook, the notebook runs under the identity of the pipeline's last modified user, not the pipeline or notebook owner. A variable that points at an item or connection only works if that identity can use the target. Re-test after someone else edits the pipeline.

Notebooks

Notebooks read a library with NotebookUtils at run time or inject values into the session configuration with %%configure. Both read the active value set of the library in the notebook's own workspace.

With NotebookUtils

cfg = notebookutils.variableLibrary.getLibrary("VL_SALES_SLV_Config")

batch_size = cfg.BatchSize           # property access, typed from the definition
stage = cfg["StageName"]             # bracket access, useful for dynamic names
lookback = cfg.getVariable("LookbackDays")

# One variable by reference path (the "/**/" prefix is required)
full_reload = notebookutils.variableLibrary.get("$(/**/VL_SALES_SLV_Config/FullReload)")

print(stage, batch_size, lookback, full_reload)

An item reference resolves to an object from which you extract the two IDs. Use them to build a OneLake path to the item.

ref = notebookutils.variableLibrary.get("$(/**/VL_SALES_SLV_Config/BronzeLakehouse)")
workspace_id = ref.get("workspaceId").value()
lakehouse_id = ref.get("itemId").value()

orders_path = f"abfss://{workspace_id}@onelake.dfs.fabric.microsoft.com/{lakehouse_id}/Tables/orders"
orders = spark.read.format("delta").load(orders_path)
  • The library must be in the same workspace as the notebook. Cross-workspace access is not supported, and a child notebook in a reference run cannot read libraries across workspaces.
  • Variables are read-only from notebooks. Change them in the Fabric UI or through the API.
  • Names are case sensitive: use the exact library and variable names.
  • NotebookUtils variable library utilities do not support a service principal identity. If the notebook runs under a service principal, test that the read works in that context.

With %%configure

Use %%configure to set the session's default lakehouse from the library, so one notebook can run in every stage without edits. This is the variable-library alternative to a default-lakehouse deployment rule.

%%configure
{
  "defaultLakehouse": {
    "name":        { "variableName": "$(/**/VL_SALES_SLV_Config/LakehouseName)" },
    "id":          { "variableName": "$(/**/VL_SALES_SLV_Config/LakehouseId)" },
    "workspaceId": { "variableName": "$(/**/VL_SALES_SLV_Config/LakehouseWorkspaceId)" }
  }
}
  • Define all three variables as String, including the ID values.
  • workspaceId is required when the lakehouse is in a different workspace from the notebook.
  • Item reference variables are not supported through %%configure; use String variables here.

Passing values into shared code

Keep library code (see Shared Python Libraries) free of workspace names and IDs. Read the values in the notebook and pass them as arguments, so the same wheel works in every stage.

import contoso_fabric_utils as lib   # the shared package from playbook 06
from pyspark.sql import functions as F

cfg = notebookutils.variableLibrary.getLibrary("VL_SALES_SLV_Config")

if cfg.FullReload:
    lib.full_load_overwrite(source_table="bronze_orders", target_table="silver_orders")
else:
    changes = spark.read.table("bronze_orders").where(
        F.col("modified_at") >= F.date_sub(F.current_date(), cfg.LookbackDays)
    )
    lib.merge_upsert(source_df=changes, target_table="silver_orders", key_cols=["order_id"])

Orchestration hubs read their own workspace

A notebook resolves variables in the workspace where it runs. A hub workspace that invokes spoke pipelines (see Cross-Workspace Pipeline Orchestration) does not configure the spokes through its own library. Give each spoke workspace its own library, deployed with its items.

Dataflow Gen2

Dataflow Gen2 with CI/CD can reference variables in filter, replace and column-transformation dialogs through the input widget (turn it on under View, Parameters, Always allow), or directly in M with the variable functions. The identifier must use the $(/**/Library/Variable) format.

// Query: LookbackDays
Variable.ValueOrDefault("$(/**/VL_SALES_SLV_Config/LookbackDays)", 7)
  • Store each variable as a separate query that does not need staging; supported dialogs can then use it as a query input.
  • The default in Variable.ValueOrDefault keeps the formula valid when the dataflow is moved to a workspace without the library. Its data type must match the variable's type.
  • Values are retrieved at the start of a run and kept for the whole run; a change to the library during the run does not affect it.
  • Variables cannot change connection information or destination schema mappings; both stay as authored. Only basic types are supported, and the library must be in the same workspace.
  • Anyone who can edit the library can change the dataflow's output, and lineage views do not show the link between the dataflow and the library.

Lakehouse shortcuts

A shortcut property such as the connection ID or the target location can be bound to a variable, so the same shortcut definition points at test data in TST and production data in PRD.

  1. Open the shortcut.

    In the lakehouse, right-click the shortcut and choose Manage shortcut.

  2. Edit the target.

    Select Edit target and choose the property to parameterize.

  3. Assign the variable.

    Pick a variable from the library. The variable name and its current value appear under the property.

Variable libraries are the only supported way to assign variables to shortcut properties across environments; assignment through the REST API is not supported, so shortcut bindings are made in the UI and then travel with the item through Git and deployment.

Copy jobs and other items

  • Copy job. Create connection variables (with each stage's connection ID in its value set), link the copy job's source and destination connections to them, and after deployment activate the matching value set in each workspace.
  • User data functions. Read variables through the Python programming model, and use item or connection references to connect to data sources.
  • Eventstream. Use connection references to rebind connections when you deploy across workspaces; destinations in some modes still need manual reconfiguration.
  • Deployment plans and Plan. Listed as supported consumers; see their articles for how they use variables.

Key takeaways

  • Create libraries in DEV in the same workspace as their consumers, with value sets named after the stages.
  • Pipelines add a library variable reference and use @pipeline().libraryVariables.Name; there is no parameter mapping step. Number is not supported there.
  • Notebooks read with NotebookUtils (same workspace, read-only, case sensitive) or set the default lakehouse with %%configure using String variables.
  • Dataflows and shortcuts have their own binding rules and cannot change connections or schemas through variables.
