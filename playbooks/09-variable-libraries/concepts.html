Playbook 09 · Variable Libraries

Concepts and anatomy

Before you build anything, get four ideas straight: what types a variable can have, how default and alternative value sets resolve to one set of values, why the active value set belongs to the workspace and not to the item, and who is allowed to change what. Most variable-library incidents come from misunderstanding one of these.

Anatomy of a library

A variable library is a single item that stores everything needed to configure its consumers in every stage. In its definition it has three kinds of content: the variables (name, type, optional note and the default value), one value set file per alternative set (holding only the values that differ from the default), and a small settings part that records the order in which value sets are listed. A platform file with the item's metadata is generated as for any Fabric item. How these parts look in Git is covered in the Git section.

What a consumer sees is always the result of one selection: take the active value set, and for every variable use that set's override if it has one, otherwise the default.

Variable types

Each variable has a name, a type, a default value and an optional note (up to 2,048 characters). The type decides how the value is validated and which consumers can use it.

Changing a type resets the values

Once a variable has a value, changing its type triggers a consent dialog: all of the variable's values are reset, and consumers that depended on the old type can break. Decide types before consumers exist, and add a new variable instead of repurposing one.

Reference types are static pointers

An item reference stores raw workspace and item IDs. It does not follow the item when you deploy: after a deployment to a new stage, the reference still points at the original workspace until you change it. The same holds for a connection reference, which never auto-binds on deployment. That is exactly why they belong in a variable library: the value set for each stage holds that stage's target.

  • The values across value sets should refer to the same kind of item (a lakehouse in each stage, not a lakehouse in DEV and a warehouse in PRD). Fabric recommends it but does not enforce it.
  • The picker only lists items and connections you have at least Read permission on. Only Fabric items and semantic models can be referenced; Dataflow Gen1 and other Power BI items cannot.
  • Only IDs are stored. Names and metadata are resolved at run time.

Verify against Microsoft Learn

The permissions article labels the item reference and connection reference types as preview. The articles on the two types and on pipeline integration list slightly different sets of consumers. Check Variable types, Item reference and Connection reference before you depend on either in production.

Value sets

Every library has a default value set. It always exists, holds every variable's baseline value and cannot be renamed. You add alternative value sets for the stages or scenarios you need. An alternative set is stored as a collection of pointers to the default values, with overrides where you changed them, so a set only records the differences.

  • Value set names are unique within a library, follow the variable naming rules, and can have a description of up to 2,048 characters.
  • You can rename and delete alternative value sets. You cannot delete the active one: activate another set first.
  • Sets appear in the order you added them. The UI cannot reorder them; reorder in the item's JSON (through Git or the update-definition API).
  • A reset button next to a value returns an override to the default value.
  • Value sets support scenarios beyond stages (A/B tests, switching a data source within one workspace), but stage configuration is the dominant use.

What belongs in the default value set

Because every workspace starts with the default set active, the content of the default set decides what an unconfigured stage does. There are two defensible conventions:

ConventionStrengthRisk
Default holds the DEV values. Alternative sets TST and PRD override what differs.Smallest library; DEV works with no extra step; fewest cells against the 10,000 limitA stage where nobody activated its set silently runs with DEV values. Mitigate with the stage guard and an activation step in every release.
Default is a neutral baseline; every stage, including DEV, is an alternative set that is activated explicitly.No stage gets values by accident; the activation step is uniform for all stagesMore cells to maintain, and DEV needs its own activation like any other stage

This playbook's examples use the first convention with a guard. Pick one per organization, and name the alternative sets with the same stage names (TST, PRD) in every library so one script can activate them all.

The active value set is workspace state

This is the single most important behavior to understand. The active value set is not stored in the library's definition. It is a workspace-level setting of the item. Consequences:

  • Deployment does not overwrite it. Deploying a library from TST to PRD copies variables and value sets; the PRD workspace keeps whichever set it had active.
  • It does not appear in comparisons. Changing the active set does not make the item "different from source" in a deployment pipeline.
  • Git does not carry it. A commit contains the definition, not the choice. Syncing a branch into a workspace does not change the active set.
  • The first arrival defaults. When a library is first deployed or committed into a workspace, the default value set is active until someone changes it.
  • Each stage chooses independently, and can change its choice at any time. There is always exactly one active set per library.

Activation is part of the release

Because nothing in the deployment sets the active value set for you, an empty stage that receives a library runs on the default value set until you select the stage's own. Make activation an explicit, ideally scripted, step of the first deployment into each stage. The promotion page shows how.

Naming rules and limits

ItemRules
Library nameNot empty; no leading or trailing spaces; starts with a letter; letters, numbers, underscores, hyphens and spaces; at most 256 characters
Variable nameNot empty; no leading or trailing spaces; starts with a letter or underscore; letters, numbers, underscores and hyphens; at most 256 characters; unique within the library
Value set nameSame rules as a variable name; unique within the library
Variables per libraryUp to 1,000
Value sets per libraryUp to 1,000, with fewer than 10,000 cells in total across the alternative sets and an item size of at most 1 MB (validated when you save)
Note and value set descriptionUp to 2,048 characters each

The same variable name can exist in two different libraries in a workspace; consumers address a variable by library and variable name together.

Case sensitivity

The naming-rules articles say names are not case sensitive, while the NotebookUtils article says library and variable names are case sensitive when you retrieve them. Treat names as case sensitive everywhere: copy the exact casing into every consumer and keep one casing convention. See NotebookUtils variable library utilities.

Permissions and trust

A variable library is a Fabric item, so it follows workspace roles or direct sharing:

Workspace roleWhat it can do with the library
ViewerView the item (and therefore read every value)
ContributorView, add, edit and delete
MemberView, add, edit, delete and reshare
AdminView, add, edit, delete and reshare
  • There is no permission at the level of a single variable: permission on a variable equals permission on the item.
  • If you share a library with someone who has no workspace access but does have access to a consumer item such as a pipeline, the library is not visible or usable from that pipeline.
  • To point a variable at an item or a connection you need at least Read permission on that item or connection. When the library is updated, every item or connection referenced by the active value set must exist and be readable by the caller.
  • When a consumer resolves a reference that the caller cannot read, resolution does not fail; the value is returned without the extended metadata.

Governance practices

  • Grant write on a library only to people and automation you already trust with the consumers' behavior. Audit the assignments regularly.
  • Have items reference only libraries that are designated as trusted, and enforce that by review of the item definitions in Git.
  • Do not store secrets in variables. Because Viewers can see values, store connection references or key vault references instead.
  • Track changes to libraries through the Git history of the library folder. See GitHub Integration and Branching for review rules, including CODEOWNERS for configuration paths.

How to structure your libraries

QuestionRecommendation
How many libraries per workspace?One per concern: for example one config library per domain and layer (VL_SALES_SLV_Config). A single library for everything couples unrelated teams, widens write access and approaches the size limits.
What goes in?Values that differ by stage: IDs, connection references, endpoints, sizes, windows and flags, and a stage name for guards.
What stays out?Secrets, per-run values (use parameters), constants that never differ by stage (keep them in code), and business rules.
How to name variables?Short, stable, descriptive, one casing convention (for example PascalCase). Variable names are part of every consumer's contract, so renaming one is a breaking change.
How to name value sets?Use the stage names exactly (TST, PRD) in every library.
Where does the library live in the workspace?In the same workspace as its consumers, one copy per stage, deployed with the same pipeline as the items that use it.

Key takeaways

  • Value sets store only overrides; consumers always see the active set's override or the default.
  • The active value set is workspace state: deployment and Git do not carry it.
  • Reference types are static pointers to IDs, which is why each stage needs its own value.
  • Treat the library as a control surface: narrow write access, review changes, no secrets.
