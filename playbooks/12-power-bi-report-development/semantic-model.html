Playbook 12 · Power BI Report Development Standards

Semantic model standards

Everything a report inherits is decided here. Pick the storage mode deliberately, change two Desktop defaults before loading any data, shape the tables as a star, hide and document what authors should not guess at, and keep the model in a project format that Git can diff.

Choose the storage mode first

Storage mode is a property of each table, and the choice drives refresh cost, latency, which features you can use, and how you secure the data. On a Fabric platform with a curated Gold layer there are five realistic options. Decide before you build, because switching later changes how measures behave and what has to be re-tested.

ModeChoose it whenWatch for
ImportYou need any connector, Power Query shaping, user-defined aggregations or incremental refresh, or the author cannot write to the lake.Refresh copies data and consumes capacity. Freshness is the refresh schedule.
DirectQueryData must stay in the source or must be current on every query, and the source can absorb report traffic.Each interaction sends queries to the source. Plan query reduction from day one (see report design).
CompositeYou combine storage modes or build a model on top of an existing shared model.Relationships across source groups are limited and are the slowest to evaluate. Keep cross-group joins few.
Direct Lake on OneLakeGold tables are Delta tables in OneLake (possibly from more than one Fabric item) and you want near-Import speed without a data copy refresh.No DirectQuery fallback: when a guardrail is exceeded, refresh fails until the Delta tables are optimized. Cloud connections only; no gateways.
Direct Lake on SQL endpointYou already depend on the SQL analytics endpoint of one lakehouse or warehouse, including views or SQL-based security.It falls back to DirectQuery when it cannot read Delta directly. The model property Direct Lake behavior controls that, and DirectQuery fallback is a performance cliff you should detect, not rely on.

Direct Lake details that change design

  • Refresh means framing. A Direct Lake refresh re-points the model at the Delta table's current files; it does not copy data. Table maintenance (compaction, V-Order, sensible row group sizes) therefore decides query speed. See Delta Lake partitioning and the Microsoft guidance on table optimization.
  • Guardrails depend on the capacity SKU (files, row groups and rows per table, and model size). Queries are evaluated per query; model size on disk is evaluated per model. Right-size Delta tables before you scale the SKU.
  • Calculated tables and columns are restricted. Calculation groups, what-if parameters and field parameters are supported because they create calculated tables implicitly. Other calculated tables and calculated columns depend on the variant, and the OneLake variant lists some of them as preview. Push derived columns into the Gold layer.
  • Row-level security defined in the semantic model works, but Microsoft recommends a fixed-identity cloud connection for it. SQL-endpoint row-level security is applied differently by the two variants, so test it explicitly instead of assuming parity.
  • Create purpose-built models. Auto-created default semantic models on lakehouses and warehouses are no longer generated for new items, and existing ones are independent models. Build and name the model you intend to certify.

Verify against Microsoft Learn

Direct Lake capabilities and limits change often (calculated tables, composite modeling, fallback behavior, per-SKU guardrails). Check Direct Lake overview, the "Considerations and limitations" table, before locking a design, and prototype with representative data volumes.

Two Desktop settings to change before you load data

Power BI Desktop ships with conveniences that are helpful in a ten-minute demo and harmful in a shared model. Both are options, not model properties, so a new file silently picks them up again unless you change the global default. Change them in File > Options and settings > Options, on the Global page (affects new files) and on the Current File page (affects the open model).

Disable auto date/time

With the option on, Desktop creates a hidden calculated date table for every Import date column that is not on the many side of a relationship. Each table is a CALENDAR-based table with Year, Quarter, Month and Day columns, joined to its source column. A model with a dozen date columns carries a dozen hidden calendars, none of which you can see, edit, mark, or reference from non-Power BI tools or Analyze in Excel.

  1. Change the default for new files

    Options > Global > Data Load > Time intelligence > clear Auto date/time for new files. Both the global and current-file options default to on in a new installation.

  2. Change the open model

    Options > Current File > Data Load > Time intelligence > clear Auto date/time. Turning it off removes the hidden tables, so any visual or filter that used a date hierarchy breaks and must be rebuilt on your own date table.

  3. Verify

    No Date Hierarchy drop-downs appear under date columns in the Data pane. In a PBIP project, no auto-generated date table files (typically named LocalDateTable_<guid>) remain in the semantic model's tables folder.

Direct Lake on SQL endpoints does not support auto date/time at all; Direct Lake on OneLake does. A marked custom date table, with relationships on the date column, works in both, so it is the portable answer.

Disable relationship autodetection

On load, Desktop compares column names and may create relationships on its own. In a narrow tutorial model that is convenient. In a model with surrogate keys, role-playing dimensions and a few similarly named columns, it produces relationships you did not choose, and a wrong relationship returns numbers that look reasonable. Three options govern this under Options > Data Load > Relationships:

OptionDefaultStandard
Import relationships from data sources on first loadOnOptional. If the Gold layer declares keys, importing them is a head start, but review every imported relationship.
Update or delete relationships when refreshing dataOffLeave off. Learn warns against turning it on when row-level security depends on relationships, because removing one can weaken security.
Autodetect new relationships after data is loadedOnTurn off, on both the Global and Current File pages.

You can still use Manage relationships > Autodetect on demand as a suggestion engine. The rule is that a person confirms each relationship and sets cardinality and direction on purpose.

Model as a star

Fact tables hold events or measurements at one grain, narrow and tall, with integer keys and numeric columns. Dimension tables hold descriptive attributes, wide and short. Every dimension relates to the fact with a one-to-many relationship that filters from the dimension. This is the shape VertiPaq compresses best, the shape DAX assumes, and the shape that keeps filter paths unambiguous.

Relationship rules

  • One-to-many, single direction, from the dimension. Bidirectional filtering is the exception. It adds ambiguity, can slow queries, and Microsoft's relationship guidance recommends it only when needed. If you need a filter to flow from a fact back to a dimension, a measure with CROSSFILTER or a purpose-built bridge is usually safer than a model-wide switch.
  • Many-to-many relationships sparingly. They are limited relationships: no table expansion, and slower than one-to-many. Prefer a bridge table with one-to-many relationships on both sides.
  • Role-playing dimensions. One active relationship per pair of tables. For Order Date, Ship Date and Due Date, either duplicate the Date table (one per role) when visuals need to filter by different roles at once, or keep one table with inactive relationships and activate them with USERELATIONSHIP in role-specific measures.
  • Integer surrogate keys on both ends, same data type, and a unique key on the one side. A refresh that loads duplicates into a one-side column fails.
  • Plan for unknown members. If a fact row has no matching dimension row, a blank member appears. Add an explicit "Unknown" row in the dimension in the Gold layer instead of letting the engine invent a blank.
  • Disconnected tables are legitimate for parameters and what-if inputs. Name them so nobody tries to relate them.

One date table, marked

Time intelligence functions need a contiguous date table with one row per day and a column of unique dates. Build it once in the Gold layer (or as a single calculated table if the model is Import), mark it with Table tools > Mark as date table and choose the date column, hide the technical columns, and give it columns for the periods your organization reports on (fiscal year, fiscal period, week). For a fiscal calendar that differs from the calendar year, include fiscal attributes in the table rather than writing them into each measure.

Verify against Microsoft Learn

Learn describes calendar-based time intelligence (calendar metadata on a date table, week-based functions, non-Gregorian calendars) as a preview capability behind a Desktop preview feature. If you adopt it, confirm its status and the differences from classic time intelligence in Implement time-based calculations in Power BI. The classic pattern with a marked date table remains the portable baseline.

Decide what authors see

An author who opens the model sees every field you leave visible and has to guess which is right. The model owner's job is to remove the guesses.

PropertyStandardWhy
HiddenHide surrogate and foreign keys, sort-order helpers, technical columns, and numeric columns that a measure already aggregates.Stops authors from summing a key or building visuals on implicit aggregations. Hiding is a usability control, not security: people with Build permission can reveal hidden fields. Use row-level or object-level security for protection.
DescriptionEvery table, every measure, and every column an author might use. State meaning, grain and how it should be used.Descriptions surface as tooltips in the field list, and they are the cheapest documentation that travels with the model.
FormatSet number, percentage and date formats on the field or with a format string; use dynamic format strings when the unit changes with context.Reports stay consistent without every author formatting every visual.
Sort by columnMonth Name sorts by Month Number; Fiscal Period by its ordinal; status labels by an explicit rank.Alphabetical sort on months and ranges is the most common visible defect in a first report.
Default summarizationSet to None on keys, years and codes.Prevents a stray sum of Year when a column is dropped on a visual.
Data categoryMark geography, URL and image columns.Enables the right visuals and behavior without author effort.
Hierarchies and display foldersBuild hierarchies for natural drill paths (Category, Subcategory, Product). Group measures with display folders.Navigation and consistent drill behavior across reports.
Discourage implicit measuresTurn on for shared models.Forces authors to use your measures. It is also required before you can create a calculation group.

Perspectives, calculation groups and field parameters

FeatureUse it forLimits to know
PerspectivesTrimmed views of a large model for a subject area or for personalized visuals.They are a viewing convenience, not security. Desktop has no graphical editor for them, so create them in TMDL view or an external tool.
Calculation groupsReusing one calculation across many measures: time intelligence (current, YTD, prior year), currency conversion, unit switching.Create them in Model view. They need discouraged implicit measures, change measure data types in reports to variant, and are not supported on remote sources inside composite models.
Field parametersLetting report users switch the measure or dimension on a visual.Use explicit measures, not implicit aggregations. There is no "none" selection, and a field parameter cannot be the linked field for a drillthrough or tooltip page.

These features all create or depend on model objects, so they belong in the shared model, not in each report. Direct Lake models accept calculation groups, what-if parameters and field parameters because the calculated tables they create do not reference lake columns.

Keep the model in a project format

A PBIX file is a single binary that Git cannot diff or merge. A Power BI project (PBIP) saves the semantic model and the report as separate folders of text files. The semantic model is stored as TMDL, one file per table plus files for relationships, expressions and the model; the report definition can be stored in the enhanced report format, PBIR, with one file per page, visual and bookmark.

contoso-sales/
├── SM_SALES_CNSM_Core.SemanticModel/
│   ├── definition/              # TMDL: model.tmdl, relationships.tmdl, tables/*.tmdl, ...
│   ├── definition.pbism
│   └── .platform
├── RPT_SALES_DLV_Executive.Report/
│   ├── definition/              # PBIR: pages, visuals, bookmarks as JSON files
│   ├── definition.pbir          # points at the semantic model (byPath or byConnection)
│   └── .platform
├── .gitignore                   # ignores .pbi/localSettings.json and .pbi/cache.abf
└── contoso-sales.pbip
/// Sales fact table. One row per order line.
table Sales

	column 'Customer Key'
		dataType: int64
		isHidden
		summarizeBy: none
		sourceColumn: customer_key

	column 'Net Amount'
		dataType: decimal
		isHidden
		summarizeBy: none
		sourceColumn: net_amount

	/// Net sales after discounts, before tax.
	measure 'Sales Amount' = SUM ( Sales[Net Amount] )
		formatString: #,0
		displayFolder: Sales

Three practices make the project format pay off:

  • Review diffs, not binary files. A pull request that renames a measure or changes a relationship is visible as a few lines in a .tmdl file. Pair this with the review rules in GitHub integration and branching.
  • Use TMDL view for bulk edits. Script a table, find-and-replace with regular expressions, preview the diff, and apply. It is the fastest way to add descriptions, apply a naming prefix, or create a perspective. It changes metadata only; if you change a Power Query expression or a calculated column you must refresh.
  • Edit outside Desktop with care. Save in Desktop first, edit the TMDL in an editor, then apply the external changes (older builds need a restart). Save files as UTF-8 without BOM, keep a short root path because Windows limits path length to 260 characters by default, and set Git line-ending handling because Desktop writes CRLF.

TMDL view in Power BI DesktopGA
TMDL view on the web (service)Preview
Saving as a Power BI project (PBIP)Preview
PBIR report formatPreview, already the default for new reports created in the service
Fabric Git integration for semantic models and reportsPreview

Verify against Microsoft Learn

These statuses move. Microsoft has stated that when PBIR reaches general availability it becomes the only supported report format and conversion becomes mandatory, so plan for it now. Re-check Power BI Desktop projects, the report folder and PBIR format, and the supported-items list in Fabric Git integration before you commit a team process to them. Known project limits include: sensitivity labels are not supported in PBIP, you cannot save a PBIP directly to OneDrive or SharePoint, and row-level security members and incremental-refresh partitions cannot be read or written through the Fabric REST API. Also check the deployment pipeline limitations before you combine PBIR with pipelines; see From change to production.

Semantic model checklist

  • Storage mode chosen on purpose and recorded in the model description.
  • Auto date/time off (global and current file); one date table marked.
  • Relationship autodetection off; every relationship reviewed, one-to-many, single direction unless justified.
  • Star shape: no flat tables, no snowflakes without a reason, Unknown members present in dimensions.
  • Keys and helper columns hidden; summarization set to none where needed.
  • Every table, measure and author-facing column has a description; formats and sort-by columns set.
  • Discourage implicit measures is on; all measures live in a measures table.
  • Security: row-level or object-level security tested for each role, not assumed from the source.
  • Saved as PBIP/TMDL in Git; .gitignore excludes local cache and settings.

Key takeaways

  • Pick the storage mode first. Direct Lake on OneLake is the default for Gold data in Fabric; Direct Lake on SQL endpoint is for teams that depend on SQL features and accept DirectQuery fallback.
  • Turn off auto date/time and relationship autodetection globally and per file, then define the date table and relationships yourself.
  • Hiding is for usability and security is for security. Use descriptions, formats and sort-by columns so authors stop guessing.
  • Store the model as TMDL in Git so reviews see what changed.
