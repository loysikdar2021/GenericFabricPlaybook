Naming, DAX and measures tables

Names are an interface: reports, other developers and Copilot all depend on them, and renaming later breaks things. This page fixes the conventions for measures, columns and tables, the DAX patterns that keep models fast and readable, and the structure that stops measures from scattering.

General naming principles

The naming rules below are house conventions, not Microsoft requirements. They are chosen so that a name tells a report author what a field is, where it comes from and whether it is shared.

  • Be descriptive. The name states what the measure or column does. Total Sales beats Measure 1; Microsoft's own guidance asks for descriptive table, column and measure names because they are what report authors and other consumers see.
  • Avoid abbreviations unless they are standard and widely understood: YoY, MTD, QTD, YTD. Spell out everything else.
  • Use Pascal Case with spaces for fields people read: Total Sales, Customer Count. Spaces are fine for measures and columns because DAX references them in brackets; they do force single quotes around table names in DAX.
  • Be consistent across models. The same concept has the same name in every model: if one model says Customer another must not say Client.
  • Never encode a changing fact in a name. A year, a person or a temporary filter in a measure name is a rename waiting to happen. Prefer a slicer or a calculation group item to Sales (Fiscal Year 20XX Only).
  • Name by business meaning, not by source. Gold-layer physical names such as order_lines become Sales or Order Lines in the model.

Report measures

Measures defined in the shared semantic model are the governed definitions. A thin report may add a few report-level measures of its own for report-specific needs. To make the two distinguishable at a glance, every report-level measure carries the prefix Rpt.

Shared measures do not take the prefix

Measures that live in the shared model are named plainly (Sales Amount, Sales YoY %). The prefix is a signal that a measure is local. When a report-level measure is needed by a second report, promote it into the model, drop the prefix, and delete the local copy.

Calculated columns

Calculated columns are the exception, not the pattern. They are computed at refresh, stored in memory, and are not available on Direct Lake on SQL endpoints. Create one only when the value must be a column (for example to slice or sort by) and cannot come from the Gold layer or Power Query. When you do, make it obvious.

Tables in semantic models

Use clear, descriptive Pascal Case names, and be consistent across models. One rule needs more thought than the rest: prefix tables to show which model or domain they belong to when more than one model can appear in the same report. This is the situation in a composite model that combines several shared models, and also in a report that uses more than one.

Worked example

Suppose the Sales model and the HR model each contain a date table and each is used by a report that combines them. Without a prefix, the report's field list contains two tables called Date, and authors cannot tell which relates to which fact. Because you cannot rename a table from a remote model inside a thin report, the prefix has to be in the model itself.

In DAX, a table whose name contains spaces or brackets must be quoted, so the prefixed date column is referenced as '[Sales] Dates'[Date]. A prefix is a trade-off, so decide per model:

  • If a model will only ever be used on its own, skip the prefix and keep the names clean.
  • If a model might be combined with another (any shared model, any model on the certified list), prefix all its tables. A model with some prefixed and some unprefixed tables is the worst of both.
  • Use a short domain code, not a long name: [Sales], [HR], [Finance].

Test the bracket convention with your tools

Power BI Desktop accepts square brackets in table names, and the convention is used in practice, but some tools and Analysis Services object-naming rules are stricter. Before you standardize on it, confirm that Analyze in Excel, DAX Studio, Tabular Editor and any export or documentation scripts your team uses handle such names. If any fail, use a parenthetical or a delimiter instead, such as Sales - Dates or SALES_Dates, and apply it everywhere.

DAX patterns that stay fast

These are the patterns that matter most in review. Format DAX consistently, with a DAX formatter (for example the Format query command in DAX query view), so diffs show logic changes rather than whitespace.

Use variables

A variable is evaluated once, outside the filter context its RETURN expression applies, and can be reused. That improves readability, avoids repeated evaluation, and removes most reasons to use EARLIER. Microsoft's example of reusing a prior-period calculation roughly halves the query time. You can also debug by temporarily returning a variable.

Sales YoY % =
VAR CurrentSales = [Sales Amount]
VAR PriorSales =
    CALCULATE ( [Sales Amount], SAMEPERIODLASTYEAR ( 'Date'[Date] ) )
RETURN
    DIVIDE ( CurrentSales - PriorSales, PriorSales )

Use DIVIDE when the denominator can be zero

DIVIDE returns BLANK (or an alternate result you supply) instead of an error. Microsoft recommends it whenever the denominator is an expression that could be zero or BLANK, and the plain / operator when the denominator is a constant, because it is faster and cannot fail. Returning BLANK is usually the better behavior, because visuals drop groupings that summarize to BLANK instead of printing zeros.

Avoid nested iterators and unnecessary row-by-row work

Iterators (SUMX, AVERAGEX, FILTER) evaluate an expression per row. One iterator at the grain of the fact table is fine; an iterator inside an iterator multiplies the work. Better still, do the row arithmetic once in the Gold layer and use a plain aggregation.

-- Avoid: an iterator over customers wrapping an iterator over their sales
Sales Amount Slow =
SUMX ( Customer, SUMX ( RELATEDTABLE ( Sales ), Sales[Quantity] * Sales[Unit Price] ) )

-- Prefer: one iterator at the grain of the fact table
Sales Amount =
SUMX ( Sales, Sales[Quantity] * Sales[Unit Price] )

-- Best, when the line amount is computed upstream
Sales Amount = SUM ( Sales[Net Amount] )

Prefer Boolean filter arguments to FILTER

In an Import model, filtering a column with a simple Boolean expression is optimized by the storage engine. Passing FILTER over a whole table forces the engine to evaluate row by row. Keep FILTER for the cases a Boolean cannot express: conditions on a measure, on several columns, or with OR logic. KEEPFILTERS preserves the existing filters on the column the way FILTER over the table would.

-- Slower
Red Sales Slow =
CALCULATE ( [Sales Amount], FILTER ( Product, Product[Color] = "Red" ) )

-- Preferred
Red Sales =
CALCULATE ( [Sales Amount], KEEPFILTERS ( Product[Color] = "Red" ) )

Time intelligence needs a marked date table

Time intelligence functions read a contiguous date table. Mark it, relate it to every fact by date, and reference its date column. Do not use the date column of the fact table.

Sales YTD = TOTALYTD ( [Sales Amount], 'Date'[Date] )
Sales MTD = TOTALMTD ( [Sales Amount], 'Date'[Date] )
Sales PY  = CALCULATE ( [Sales Amount], SAMEPERIODLASTYEAR ( 'Date'[Date] ) )

Each base measure multiplied by each time variant becomes a long list. A calculation group removes the multiplication: define the time variants once and apply them to whichever measure is selected.

Calculation groups for repeated variants

Create the group in Model view with the Calculation group button. If Discourage implicit measures is off, Desktop prompts you to turn it on, because calculation groups require it. Once a calculation group exists, reports treat measure values as the variant data type, so give each item a format string (a dynamic format string expression) when the variant changes the unit, as a percentage does.

Calculation groups are not supported on remote sources inside a composite model, so define them in the shared model that owns the measures, not in a thin report.

Other rules

  • Reference columns with the table name and measures without it: Sales[Net Amount] and [Sales Amount]. The convention makes the difference visible when you read a formula.
  • Document logic in the description field of each measure and column, and organize measures with display folders.
  • Centralize shared logic in the model. A measure used in two reports is defined once, in the model.
  • Prefer measures to calculated columns. Measures are evaluated at query time and respond to filters; calculated columns are stored and evaluated at refresh.
  • Push transforms upstream. Shape in the Gold layer or Power Query, not in DAX.

Verify against Microsoft Learn

DAX is gaining user-defined functions, stored in a functions file in TMDL, and calendar-based time intelligence. Both are described in Learn; check each article for current status before using them in a shared model: Use DAX user-defined functions and Implement time-based calculations in Power BI.

Create a measures table

Keep every measure in a dedicated table that holds no data, so authors find measures in one place, the table sorts to the top of the field list, and the logic is not scattered across fact tables. Name it _Measures in the shared model, and Local Measures in a thin report that needs its own. The two names also make it obvious in a composite model which measures are shared and which are local.

In Power BI Desktop

  1. Create an empty table

    On the Home ribbon, select Enter data. Leave the grid empty (it has a single column named Column1), name the table _Measures (or Local Measures in a thin report) and select Load. The new table appears in the Data pane.

  2. Add measures to it

    Select the table, then Home > New measure (or Table tools in Table view). Enter the DAX, then set the format, display folder and description in the Properties pane.

  3. Move existing measures in

    Select a measure, open Properties > General and change Home table to the measures table. Repeat, or multi-select in Model view and change them together.

  4. Remove the placeholder column

    Delete or hide Column1. When only measures remain visible, Desktop changes the table's icon to the measure icon. If the icon does not change, a visible column is still there.

  5. Check

    The table sits at the top of the field list, has no relationships, and holds only measures. In a shared model also tick Discourage implicit measures.

Which table can be created where

An Enter data table is an Import table. That is fine in an Import model or a composite model, but a Direct Lake on SQL endpoint model cannot mix storage modes. In that case use a calculated table that references no lake columns, or keep measures on a small dimension table. Microsoft lists calculated tables that reference no Direct Lake columns as supported, but treat the limits as volatile and check the Direct Lake overview. A report with a pure live connection cannot add tables at all, so its report-level measures are stored with the report against a table of the remote model; the naming prefix still tells people they are local.

Alternative: with TMDL

For a repeatable result, script the table. In Power BI Desktop open TMDL view, paste the script and select Apply. The same text works as a tables/_Measures.tmdl file in a PBIP project. The table uses a calculated partition so no source data is involved, and the placeholder column is hidden.

createOrReplace

	table _Measures

		/// Net sales after discounts, before tax.
		measure 'Sales Amount' = SUM ( Sales[Net Amount] )
			formatString: #,0
			displayFolder: Sales

		/// Year-over-year change in Sales Amount. BLANK when no prior-year sales.
		measure 'Sales YoY %' =
				VAR CurrentSales = [Sales Amount]
				VAR PriorSales =
					CALCULATE ( [Sales Amount], SAMEPERIODLASTYEAR ( 'Date'[Date] ) )
				RETURN
					DIVIDE ( CurrentSales - PriorSales, PriorSales )
			formatString: 0.0%
			displayFolder: Sales

		column Value
			isHidden
			isNameInferred
			sourceColumn: [Value]
			summarizeBy: none

		partition _Measures = calculated
			mode: import
			source = { 0 }

Confirm property names for your model

TMDL property names depend on the model's compatibility level. Right-click a calculated table that already exists in your model and choose Script TMDL to see exactly which properties your version writes, then align this script to it. TMDL view only changes metadata; it does not refresh anything, and renaming a field there can break report visuals that use it.

Naming and DAX checklist

  • Names are descriptive Pascal Case; abbreviations are only YoY, MTD, QTD, YTD.
  • Report-level measures use Rpt; calculated columns use Col; shared measures have no prefix.
  • No hard-coded years, people or temporary filters in names.
  • Tables in any model that may be combined carry a short domain prefix, consistently.
  • Every measure is in a measures table and has a description; display folders group them.
  • Variables used for repeated expressions; DIVIDE for variable denominators.
  • No nested iterators; Boolean filter arguments where possible.
  • Time intelligence reads one marked date table; repeated variants are a calculation group.

Key takeaways

  • Names are a contract. Use the prefix to say where logic lives: none for shared, Rpt for report-level, Col for calculated columns.
  • Prefix tables with a domain code wherever two models can end up in one report, and make sure your tools accept the form you choose.
  • Variables, DIVIDE, single iterators and Boolean filters cover most DAX review comments.
  • One measures table per model, built once in Desktop or with a TMDL script; promote report measures instead of copying them.
