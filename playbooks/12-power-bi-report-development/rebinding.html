Rebinding reports to a new semantic model

Moving reports onto a new Gold-based model is routine in a Fabric migration. The mechanics are simple (change which model a report points at). The risk is everything inside the report that referred to a field the new model names differently. This page gives you four ways to do it, a gate that finds the gaps first, and a matrix for verifying the result.

When you rebind

  • A legacy Import model is replaced by a Direct Lake or consolidated model with the same business meaning.
  • Reports that carry their own embedded model are being converted into thin reports on a shared model.
  • A shared model is split or merged, or moves to a different workspace.

Rebinding is not how you promote a report between Dev, Test and Production. Deployment pipelines handle that by binding a deployed report to the model in the same stage; see Deployment pipelines and promotion. For the wider estate move, see Power BI to Fabric migration. Paginated reports are rebound differently and are not supported by the API used below; see Paginated report migration.

Do not plan around "Change source" for live connections

Switching a live-connected report to another model through Desktop's data source settings has been reported as unavailable in recent builds. Do not build a plan on it. Use the REST rebind or edit the PBIP.

Gate: compare the schemas first

A rebind to a model with different names produces a report that opens and then shows errors on every affected visual. Find the gaps before you touch the report: list the columns and measures the old model exposes, list what the new model exposes, and decide what to do with every difference. The snippet below runs in a Fabric notebook.

%pip install semantic-link-labs
import sempy.fabric as fabric

OLD_MODEL, OLD_WS = "SM_SALES_CNSM_Legacy", "PRD_SALES_CNSM"
NEW_MODEL, NEW_WS = "SM_SALES_CNSM_Core", "PRD_SALES_CNSM"

def fields(model: str, workspace: str):
    """Return the set of (table, column) and (table, measure) pairs a model exposes."""
    cols = fabric.list_columns(dataset=model, workspace=workspace)
    meas = fabric.list_measures(dataset=model, workspace=workspace)
    # Print cols.columns / meas.columns first if your sempy version names them differently.
    return (set(zip(cols["Table Name"], cols["Column Name"])),
            set(zip(meas["Table Name"], meas["Measure Name"])))

old_cols, old_meas = fields(OLD_MODEL, OLD_WS)
new_cols, new_meas = fields(NEW_MODEL, NEW_WS)

missing_cols = sorted(old_cols - new_cols)
missing_meas = sorted(old_meas - new_meas)
new_measure_names = {m for _, m in new_meas}

print(f"Columns missing in new model: {len(missing_cols)}")
for t, c in missing_cols:
    print(f"  {t}[{c}]")
print(f"Measures missing in new model: {len(missing_meas)}")
for t, m in missing_meas:
    note = "   (same name exists under a different table)" if m in new_measure_names else ""
    print(f"  {t}[{m}]{note}")

The output is your work list. For each missing field choose one of three actions: add it to the new model (usually as a measure or a renamed column), change the report to use the replacement, or retire the visual. A measure that exists under a different table also counts as missing, because report visuals reference a measure through its table. Do not proceed until the list is empty or every entry has an owner.

Rebind with the REST API or semantic-link-labs

The Power BI REST API Reports - Rebind Report In Group binds a report to a target semantic model. Learn documents three conditions that matter: you need Write permission on the report and Build permission on the target model, a model in a different workspace is exposed to the report's workspace as a shared model, and a report that had a live connection ends up with a direct binding to the target. The call does not support paginated reports.

Connect-PowerBIServiceAccount

$workspaceId = "<report-workspace-id>"
$reportId    = "<report-id>"
$body = @{ datasetId = "<target-model-id>" } | ConvertTo-Json

# POST https://api.powerbi.com/v1.0/myorg/groups/{groupId}/reports/{reportId}/Rebind
Invoke-PowerBIRestMethod -Method Post `
    -Url "groups/$workspaceId/reports/$reportId/Rebind" `
    -Body $body

For more than a handful of reports, use the wrappers in semantic-link-labs (sempy_labs.report), which call the same API, resolve names to IDs, and support service principal authentication. report_rebind takes one or more reports; report_rebind_all finds every report bound to a given model and rebinds it, optionally limited to listed workspaces.

from sempy_labs.report import report_rebind, report_rebind_all
import sempy.fabric as fabric

OLD_MODEL, OLD_WS = "SM_SALES_CNSM_Legacy", "PRD_SALES_CNSM"
NEW_MODEL, NEW_WS = "SM_SALES_CNSM_Core", "PRD_SALES_CNSM"
REPORT_WS = "PRD_SALES_DLV"

# 1. Dry run: which reports are bound to the old model today?
old_id = fabric.resolve_dataset_id(OLD_MODEL, OLD_WS)
reports = fabric.list_reports(workspace=REPORT_WS)
affected = reports[reports["Dataset Id"] == old_id]
print(affected[["Name", "Id"]].to_string(index=False))

# 2. Rebind a named subset first (a pilot)
report_rebind(
    report=["RPT_SALES_DLV_Executive"],
    dataset=NEW_MODEL,
    report_workspace=REPORT_WS,
    dataset_workspace=NEW_WS,
)

# 3. After the pilot is verified, rebind everything still on the old model
report_rebind_all(
    dataset=OLD_MODEL,
    new_dataset=NEW_MODEL,
    dataset_workspace=OLD_WS,
    new_dataset_workspace=NEW_WS,
    report_workspace=[REPORT_WS],
)

Verify against Microsoft Learn and the library

Confirm the request and permissions in Reports - Rebind Report In Group. semantic-link-labs is an open-source library that moves quickly; pin a version in your notebook environment and check the function signatures in its documentation before you run bulk changes in production. The column names returned by list_reports can differ between versions.

Rebind in a PBIP project

In a Power BI project the pointer is a property of definition.pbir in the report folder, named datasetReference. It takes one of two forms:

  • byPath: a relative path to a semantic model folder in the same repository. Desktop opens the report and the model together in full edit mode. Fabric Git integration always exports a byPath reference when the model and report share a workspace.
  • byConnection: a connection to a model in a Fabric workspace. Desktop opens it as a live connection and does not open the model for editing. Deployment through the Fabric REST API requires this form; there, only the semanticmodelid is needed.
{
  "$schema": "https://developer.microsoft.com/json-schemas/fabric/item/report/definitionProperties/2.0.0/schema.json",
  "version": "4.0",
  "datasetReference": {
    "byConnection": {
      "connectionString": "semanticmodelid=00000000-0000-0000-0000-000000000000"
    }
  }
}

Commit the change on a branch and let the pull request show the one-line difference. If you want to open the same report in live-connect mode during development, a repository can hold more than one .pbir file (for example definition-liveConnect.pbir); Fabric Git integration processes only definition.pbir and ignores the rest.

Remap manually in Desktop

Use this route when a report owns a local model and must become a thin report, or when the new model's fields differ and every affected visual needs a decision. Always work on a copy.

  1. Copy the report

    Save the report as a new file (or branch the PBIP). Keep the original untouched until the new one passes verification.

  2. Make sure a measures table exists

    If the report has no table dedicated to measures, create one as described in Create a measures table and name it Local Measures. A table with this name separates measures created in the report from measures that come from the shared model.

  3. Move report measures in and rename them

    Move every measure created in the report to Local Measures (select the measure, then change Home table). Apply the Rpt prefix to any that lack it. Check each for hard-coded years or filters in its name or logic.

  4. Remove local queries

    If the report has data queries, open Transform data, delete every query except Local Measures, then Close and apply.

  5. Remove the old data sources

    In Transform data > Data source settings, delete the connections to semantic models or databases that the old model used, close the dialog and apply the changes. At this point the visuals are broken, as expected.

  6. Connect to the new model

    Select Get data > Power BI semantic models, pick the target model from the OneLake catalog, and choose the tables you need. Because the report keeps a local table, this creates a composite model that uses DirectQuery over the shared model; a tenant setting governs that capability, so ask your administrator if the option is unavailable. A report with no local tables stays a pure live connection instead, and its report-level measures are stored with the report.

  7. Fix formulas

    Update the local measures that reference columns by their old names. Reference columns as Table[Column] and use the new table names, including any domain prefix.

  8. Remap the visuals

    Open each broken visual and select See details to see the tables, columns and measures at fault. Remove both the field and any visual-level filter that points to the old column and add the correct field from the Data pane. If a Fix this button appears, select it to update the visual. Repeat for every visual and page.

  9. Verify every dependency

    Use the matrix below. A visual that renders is not necessarily correct.

Verify every dependency

Confirm that every remapped element is fixed. This includes fields, filters, hierarchies, specific column settings, bookmarks, URLs, row-level security and any other dependency that broke after the switch.

Rebinding at scale

For dozens of reports, treat the rebind as a release with gates, not as a loop.

  • Pilot first. Rebind two or three representative reports, verify them with the matrix, and only then run the bulk call.
  • Batch by owner. Group reports by the team that can sign them off and agree a window; people will notice a report that changes numbers.
  • Keep an audit trail. Save the inventory output (report, workspace, old model, new model, time) so every change is traceable and reversible.
  • Check permissions up front. The identity that rebinds needs Write on each report and Build on the target model. A service principal needs both as well, and tenant settings must allow it to call the APIs.
  • Do not retire the old model until usage drops to zero. Use the model's lineage and usage views to confirm nothing still depends on it, including Excel connections and other models built on top.

Key takeaways

  • Rebinding changes a pointer. The danger is in the names inside the report, so run a schema diff before you rebind.
  • REST or semantic-link-labs for thin reports at scale, a one-line PBIP edit for source-controlled reports, a manual remap on a copy when the report owns its model.
  • Verify filters, bookmarks, report-level measures, security and links, not only that visuals render.
  • Keep the old model until sign-off so the rollback is another rebind.
