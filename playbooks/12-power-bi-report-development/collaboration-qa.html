Playbook 12 · Power BI Report Development Standards

Collaboration, endorsement and QA

The earlier pages describe a good model and a good report. This page covers what keeps them good once several people depend on them: where shared models live, who may build on them, how a change travels to production, how you signal trust, and the checklist every release passes before it is published.

Shared semantic models and thin reports

The default pattern is one governed semantic model per subject area, owned by the data team, with many thin reports built on it by whoever needs a view. A thin report has no model of its own: it connects live to a shared model, or at most adds report-level measures or a small local measures table as described on the rebinding page. The benefits are a single definition of every measure, one refresh to schedule and secure, and a place to apply row-level security once.

Who needs what

PersonNeedsHow it is granted
Model ownerContributor or higher on the model workspaceWorkspace role. A Contributor or higher also has Build on the models in that workspace.
Report authorBuild permission on the shared model, and Contributor or higher on the workspace where the report is savedThe model owner assigns Build to a user or a group under Manage permissions; an app can also grant Build to its audiences.
ConsumerAccess to the report or appApp audience or report sharing. A user who loses Build can still view the report but can no longer edit it or export underlying data.
  • Grant Build to groups, not individuals. Use one group per model (for example, a group of everyone authorised to build on SM_SALES_CNSM_Core) so access follows team membership.
  • Make the model discoverable. Name it by the house convention, fill in its description and endorse it, so authors find it instead of building a private copy.
  • Configure the access request. In the model's settings you can send Build requests to an owner mailbox or show instructions for your own process.
  • Do not delete a model that other workspaces use. Power BI blocks deleting a semantic model while a report outside its workspace uses it, which is a reason to find dependents before you retire anything.
  • Treat a composite pattern as an exception. A report with a local table plus a shared model is valid, but it depends on a tenant setting and on the shared model staying stable. See the notes on rebinding.

The workspace layout behind these names (<ENV>_<DOMAIN>_CNSM for models, _DLV for delivery) follows the reference architecture; see the reference architecture and Medallion architecture. To package reports for a business audience, use Organizational apps.

Endorsement and certification

Endorsement tells people which content is safe to reuse. Items with a badge are labelled in the interface and, in some lists, shown first. A badge is a promise, so it has to be backed by the checklist at the end of this page.

BadgeMeaningWho can apply itUse it for
PromotedThe creators consider the item ready for sharing and reuse.Any user with write permission on the item.Reports that passed review; shared models in early use.
CertifiedAn organization-authorized reviewer confirmed the item meets quality standards and is reliable and authoritative.Only reviewers specified by a Fabric administrator. Anyone can request certification.Production shared models and the flagship reports built on them.
Master dataThe item holds a core, authoritative source for a kind of business data.Only users specified by a Fabric administrator.Gold tables and the models that expose reference entities. Applies to items that contain data.

Certification and master data are available only if a Fabric administrator has enabled them for your organization, and certification enablement can be delegated to domain administrators, which allows a different reviewer group per domain. Dashboards cannot be endorsed. The tenant switches are covered in Tenant settings.

  • Certify in production only. A badge on a Dev or Test copy dilutes the signal.
  • Re-apply after deployment. Deployment pipelines do not copy endorsement settings to the target stage, so set the badge in the stage where it applies.
  • Tie certification to the checklist. A reviewer certifies when the checklist below is complete and attached to the request, and withdraws the badge when the model is later changed in a way the checklist would catch.
  • Describe the endorsed item. Fill in the description with the owner, the refresh pattern and the contact route, since the badge itself says nothing about those.

From change to production

A report or model change follows the same route as any other asset: author in a project, review a pull request, sync to Development, promote through the pipeline stages, and publish only after sign-off. The mechanics are in the dedicated playbooks; this page fixes the order and the gates.

  1. Author in a project

    Save the work as a Power BI project so models and reports are text files. See Projects, TMDL and Git.

  2. Review through a pull request

    Use a feature branch, require a reviewer from the owning team, and route notifications by path. The branching model is in GitHub integration; reviewer routing is in Pull-request notifications with CODEOWNERS.

  3. Sync and promote

    Merge, sync the Development workspace from the branch, then promote with a deployment pipeline (DPLY_SALES_DLV). See Deployment pipelines and the Deployment checklist.

  4. Sign off in Test

    Run the checklist below against the Test copy, with production-like data, and attach the result to the pull request or change record. Automated checks are covered in QA validation frameworks.

  5. Promote and finish the stage-specific setup

    Apply the post-deployment setup in the next table, then update any app that exposes the report.

What a deployment carries and what it does not

Deployment pipelines copy metadata, not data or the settings that belong to a stage. Plan the follow-up work for every first deployment and after every change that touches these items.

ItemCopied by deploymentWhat you do in the target stage
Report pages and visuals, model metadata, relationshipsYesNothing; verify the deployment compare view.
Data in the modelNoRefresh the model after deployment.
Data source credentials and refresh scheduleNoSet credentials and the schedule in the target stage.
Row-level security role assignmentsNoAssign members to roles in the target stage, then test with View as.
Endorsement settingsNoPromote or certify in the stage where it applies (Production).
Permissions, URLs, item IDsNoGrant Build and report access in the target stage.
App content and settingsNoUpdate the app manually.
Data source and parameter valuesWith rulesConfigure rules in the target stage so each stage points to its own sources.
  • Ownership. The user who deploys a semantic model for the first time becomes its owner. Use a dedicated account or service principal for deployments so ownership does not tie a model to a person.
  • Models and reports in separate pipelines. Deployment pipelines autobind items that are connected across pipelines when they sit in the same stage position. Both pipelines must have the same number of stages. A report deployment fails if the model it depends on is not in the matching stage of the model pipeline, so deploy the model first.
  • Direct Lake. A Direct Lake model does not automatically bind to the lakehouse in the target stage. Set the binding with data source rules as described in Deployment pipelines.
  • Auto date/time. A semantic model in DirectQuery or composite mode that uses auto date/time or variation tables is not supported by deployment pipelines, one more reason to turn that setting off, as on the model page.

Verify before you standardise on PBIR with pipelines

Learn's limitation list for deployment pipelines states that PBIR reports aren't supported, while new reports created in the service use PBIR by default. Both statements can change, so test a deployment of one PBIR report through a sandbox pipeline before you make it a standard, and read The Fabric deployment pipelines process for the current list.

Changing a shared model safely

Every column, measure and table name in a shared model is a contract with every report that uses it, because report visuals, filters and bookmarks refer to fields by name. Changing the contract without a process is how a single rename breaks a dozen reports.

ChangeEffect on reportsRule
Add a column, measure or tableNoneRelease freely after review.
Hide a fieldExisting visuals keep working; new use is discouragedUse hiding as the first step of any retirement.
Rename a fieldBreaks every visual and filter that refers to itDo not rename in place. Add the new name, keep the old one hidden, retire the old one after usage ends.
Delete a fieldBreaks every dependent visualOnly after lineage shows no dependents and the owners agree.
Change a data type or grainMay not error but can change numbers silentlyTreat as a breaking change; compare totals before and after.
Change a relationship or filter directionChanges which rows reach a measureReview with the report owners; test the headline visuals.
Change a measure definitionChanges numbers in every reportAnnounce, get sign-off from the business owner, and record the change.
  • Find the dependents first. Use the item's View lineage option in the workspace to see which reports and models depend on it, and remember that Excel connections and models built on top of yours will not appear in your own workspace.
  • Announce on a schedule. Publish a change note for each release listing added, hidden and retired fields, and give report owners a notice period before anything is removed.
  • Version through Git. The commit history of the model project is the version history and the rollback point. Tag production releases.
  • Prefer additive evolution. If a model needs a breaking redesign, create a new model, move reports with the rebind process, and retire the old one when usage reaches zero.

Pre-publish QA checklist

Every model and report passes this list before its first publish to Production and after any material change. The reviewer records the result with the change. Items already covered in detail on earlier pages link back to them.

Semantic model

  • Auto date/time and auto relationship detection are off; the date table is marked and covers the needed range. Settings
  • Star schema with single-direction relationships; no ambiguous paths; no bi-directional filtering without a recorded reason. Star schema
  • Storage mode chosen and documented, including the Direct Lake variant. Storage mode
  • Keys, foreign keys, technical columns and unused columns are hidden; descriptions exist on tables and measures. What to expose
  • Format strings and sort-by columns are set; summarization is none for numeric keys and attributes.
  • Model and report items follow the naming convention. Naming

DAX and measures

  • Measures live in a dedicated measures table, grouped in display folders, none in dimension or fact tables. Measures table
  • Variables used for repeated expressions; DIVIDE for ratios; no unnecessary iterators or FILTER over whole tables. DAX guidance
  • Headline measures reconciled to a source figure or to the previous report, using fixed filters.

Report design

  • Shared theme applied; one grid; consistent slicer placement; titles state the question the visual answers. Layout
  • Alt text, contrast, tab order and keyboard operation checked. Accessibility
  • Mobile layout curated where the report is used on phones. Mobile layout
  • Drillthrough and tooltip pages work from every source visual; bookmarks hold no sensitive selections. Interaction

Performance

  • Visual budget respected on every page; tables and matrices are filtered or Top N by default. Visual budget
  • Performance Analyzer log reviewed for the busiest page, with no unexplained DAX query bucket. Performance Analyzer
  • Query reduction options set, with Apply all slicers where pages carry many slicers. Query reduction
  • For Direct Lake models, no fallback to DirectQuery and no guardrail failure at production data volume. Direct Lake notes

Security and governance

  • Row-level security roles defined in the model, members assigned in the target stage, and tested with View as for each role.
  • Sensitivity label applied; no personal or client data in filter values, bookmarks or alt text stored in the project.
  • Build permission granted to the authorised group only; the model description names an owner and a support route.
  • Refresh schedule, credentials and failure notification set in the target stage.

Publishing

  • Item names, workspace and endorsement match the plan; certification requested for shared production models.
  • App updated where an app exposes the report; the audience list matches the intended consumers. Organizational apps
  • Change note published, and the rollback point (the commit or tag) recorded.

Key takeaways

  • Keep models in a consumption workspace and reports in delivery workspaces; grant Build to groups.
  • Promote for "ready to reuse", certify for "reviewed and authoritative", and re-apply badges after each deployment because pipelines do not copy them.
  • Deploy through a repository, a pull request and a pipeline. Credentials, schedules, role members and endorsement are stage-specific and need setting after deployment.
  • Treat field names in a shared model as a contract: add, hide, then retire; never rename in place.
  • No publish to Production without the checklist and a recorded rollback point.
