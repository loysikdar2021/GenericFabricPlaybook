Report design and performance

A report is a set of queries with a layout on top. Design it so the number of queries is small and predictable, the layout is consistent across the estate, and anyone can use it. When it is still slow, measure which of four time buckets is responsible before changing anything.

Layout, theme and consistency

Consistency is the cheapest quality control a report team has. A reader who learns where filters, headline numbers and detail live in one report can use the next one without help, and a reviewer can check a report against a template instead of against taste.

StandardRuleReason
One themeShip a single theme file (colors, fonts, visual defaults) and apply it to every report with View > Themes > Browse for themes. Keep the file in the repository next to the reports.Brand and accessibility decisions are made once. In a PBIR project the theme resource sits under the report's registered resources, so a corporate theme change can be applied across many reports by script.

Titles state the question"Sales by region, last 12 months", not "Sales Amount by Region".Titles are the first thing a screen reader announces and the first thing a reader scans.
Consistent slicersSame type, position, font and size on every page; sync slicers across pages deliberately.Learn lists slicer consistency in its accessibility checklist; it also prevents a reader from thinking a filter applies when it does not.
Semantic colorOne color per meaning (good, bad, neutral, target) used identically on every page.Reduces legend reading and supports color-blind readers when combined with labels or icons.
No decoration that costs queriesSkip images, shapes and background art that duplicate what the theme does. Prefer native visuals; put each custom visual through the same performance test as a native one.A poorly optimized custom visual can slow the whole report.

Accessibility

Power BI gives you the features; accessibility is the author's responsibility. Treat the items below as acceptance criteria, not polish.

  • Text and data labels have at least 4.5:1 contrast against their background; use fewer, higher-contrast colors rather than many pale ones.
  • Color is never the only carrier of meaning: add a label, icon or pattern.
  • Every non-decorative visual has alt text that states the insight to take away. Screen readers already announce the title and visual type, so do not repeat them.
  • Text boxes put their content in alt text as well, so screen readers can read it.
  • Tab order follows reading order, and the whole report can be operated with the keyboard, including bookmark navigation.
  • Key information is not reachable only through a click or a filter: pre-filter so the main conclusion is visible on load.
  • No unexplained jargon or acronyms in titles and labels.

Mobile layout

Mobile is a separate canvas, not a shrunk copy. Open it from the View ribbon (Mobile layout), then either let Desktop auto-create a layout and curate it, or drag visuals in yourself. Auto-create reads the page left to right from the top, so a page that depends on a left-hand navigation column translates poorly.

  • Include only the visuals people actually need on a phone. A mobile page that mirrors a ten-visual desktop page defeats the purpose.
  • Order visuals top to bottom by importance, because the phone layout is a single scrolling column.
  • Size each visual so its contents are not cut off and you avoid nested scroll bars.
  • Formatting changes in the mobile layout do not change the desktop view, and tooltips are disabled there, so do not rely on hover for meaning.

Bookmarks, drillthrough and tooltips

  • Drillthrough sends a reader from a summary to a detail page filtered to what they selected. It is the default way to give detail without putting detail on the first page. Field parameters cannot be the linked field of a drillthrough page; use the underlying fields.
  • Report page tooltips give a small contextual visual on hover. Keep them light: a tooltip page runs queries too.
  • Bookmarks capture the state of a page, including filters and selections. Use them for views (an executive and an analyst view), not as a substitute for page navigation or security. Name and group them; a bookmark saved against a field that is later renamed will break.
  • Persisted values. In a PBIR project, filter values, slicer selections and similar state are stored in the report files. If a filter selects a specific customer name, that name is in the repository. Do not save a bookmark with sensitive selections.

Set a visual budget

Every visual on a page issues at least one query when the page loads and again when a filter changes. Microsoft's optimization guidance is plain: limit the visuals on a page to what is necessary and use drillthrough pages and report tooltips for the rest. It publishes no numeric limit.

A number you may have been given

Some internal guidance quotes a figure such as "10 to 20 fields per visual" as a Microsoft recommendation. No such figure appears in the current Microsoft optimization or visualization guidance. Treat any numeric budget as a house heuristic you set and review, and base it on what Performance Analyzer shows for your model.

A workable house heuristic, to adapt: one row of headline cards, two to four supporting visuals, and at most one detail table per page, with the detail table filtered by default (for example with a Top N filter) rather than listing every row. If a page needs more, split it or move the detail behind drillthrough.

Query reduction settings

Query reduction trades some immediacy for fewer queries. It matters most for DirectQuery sources and for pages with many slicers. For a fast Import or Direct Lake model on a modest page, the default interactive behavior is usually right, so apply it where Performance Analyzer shows a problem.

Open File > Options and settings > Options > Current File > Query reduction. The settings are stored per report:

GroupSettingGuidance
Reduce number of queries sent byDisabling cross highlighting/filtering by defaultTurn on for DirectQuery or heavy pages. Authors can still enable an interaction between two visuals deliberately. Choose it when you first build the report, because changing it later alters behavior readers already know.
SlicersAdd an Apply button to each individual slicerLabelled "not recommended". Add one Apply all slicers button to the page instead (Insert > Buttons > Apply all slicers, or the Buttons menu when editing in the service), usually with a Clear all slicers button beside it.
FiltersInstantly apply basic filter changes, or Apply buttons on basic filters, or a single Apply button on the filter paneThe single Apply button in the filter pane is the usual choice for heavy reports. It is a report-level setting that you configure in Desktop.

The Optimize ribbon bundles these as presets. Query reduction turns off cross-highlighting and cross-filtering and adds an Apply button to the filter pane. Interactivity is the default and allows cross-filtering and live slicer changes. Customize opens the dialog above. The same ribbon has Pause visuals, which stops queries while you rearrange fields so authoring is not slowed by every change; remember to resume before you test.

Measure with Performance Analyzer

Do not tune by intuition. Performance Analyzer records, for each visual, how long each stage took, so you can see whether the DAX, the visual or the queue is the problem.

  1. Open it

    In Desktop, Optimize > Performance analyzer (also on the View ribbon). When editing a report in the service, View > Performance analyzer.

  2. Record a real interaction

    Select Start recording, then do what a reader does: open the page, change a slicer, click a bar. Each interaction is logged as its own section. Use Refresh visuals or Analyze this visual to re-time a page or one visual.

  3. Read the four buckets

    For every visual you get DAX query, Direct query (DirectQuery tables only), Visual display and Other. Field-parameter evaluation appears as a fifth bucket where it applies.

  4. Copy the query

    Select Copy query or Run in DAX query view to execute the visual's DAX against the model and read its result and shape. In the service, paste the copied query into DAX query view in web modeling.

  5. Export and compare

    Export the log as JSON before and after a change so the improvement is a number, not an impression.

Two cautions from the documentation. Durations are the gap between a start and an end timestamp, and most canvas and visual work runs sequentially on one UI thread, so a duration includes time spent queued behind other visuals. And Desktop on your machine is not the service: confirm important findings against the published report on the real capacity, with realistic security roles applied.

Go deeper with external tools

Performance Analyzer shows the report side. For server timings, query plans and model size by column, use an external tool such as DAX Studio, or Tabular Editor with its best-practice analyzer, against the model. They attach to the open Desktop model and to models in a workspace through the XMLA endpoint. The external tools page on Learn lists how they integrate.

Optimization levers

Most slow reports are slow for one of a handful of reasons. The table orders the levers by how often they pay off on a Fabric platform.

LeverApplies toWhat to doTrade-off
Pre-aggregate upstreamAll modes; the main option for Direct LakeBuild summary tables in the Gold layer for the grains reports actually use, and point headline visuals at them.More tables to maintain; define the grain and owner for each.
User-defined aggregationsImport aggregation tables over DirectQuery, composite modelsHold a summarized Import table that answers common queries and falls through to the detail table otherwise.Not supported on Direct Lake tables. Adds model complexity.
Reduce cardinalityImport and Direct LakeSplit date-time into a date and a time (or hour) column, remove GUIDs and free text from the model, use integer keys, drop unused columns and old rows.Needs the data team to agree on what is safe to remove.
Avoid bidirectional relationshipsAllSingle direction from dimensions to facts; use measures with CROSSFILTER where a one-off reverse filter is needed.Some slicer behaviors need a bridge table instead of a single switch.
Replace calculated columnsImportCompute in the Gold layer or Power Query; use measures for anything that should respond to filters.Calculated columns consume memory and are not available on Direct Lake on SQL endpoints.
Incremental refreshImportRefresh only recent partitions of large fact tables.Direct Lake has no model partitions; partition and maintain the Delta table instead (see Delta Lake partitioning).
Restrictive filters on visualsAllApply Top N on tables and ranked charts, and filter the default view to what readers want first. An unfiltered table over a very large fact is the classic memory hog.Readers who want everything need an export or a paginated report.
Tune Delta tables for Direct LakeDirect LakeCompact small files, keep V-Order and row-group sizes within guidance, and stay under the guardrails for your SKU.Needs table maintenance on a schedule; see Medallion Architecture.
Watch the capacityAllUse the Fabric Capacity Metrics app to see which items consume the capacity and when, not just which are slow.A report can be fast for one user and still expensive in aggregate.

For Direct Lake, columns are paged into memory when first queried, so the first query after a refresh or idle period can be slower than later ones. Test cold and warm, and decide whether a warm-up query is worth scheduling after refresh.

Report design checklist

  • Theme applied from the shared file; page grid and slicer placement match the template.
  • Alt text on every non-decorative visual; contrast and keyboard navigation checked.
  • Mobile layout curated if the report is used on phones.
  • Visual budget respected; detail behind drillthrough or tooltip pages; tables filtered by default.
  • Query reduction settings chosen and recorded; Apply all slicers present on slicer-heavy pages.
  • Performance Analyzer log exported for the busiest page; no bucket unexplained.
  • No bookmarks holding sensitive selections.

Key takeaways

  • Make the page cheap before you make it clever: fewer visuals, detail on demand, a single Apply for slicers.
  • No published numeric limit exists for fields per visual; set your own budget and enforce it in review.
  • Performance Analyzer's four buckets tell you where to look. DAX is only one of them.
  • For Direct Lake, the biggest performance levers are in the Delta tables and the SKU guardrails, not the report.
