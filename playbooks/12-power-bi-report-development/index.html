Power BI Report Development Standards

A working standard for building semantic models and reports that stay fast, readable and safe to change. It assumes a Fabric data platform underneath: a curated Gold layer feeds a small number of shared semantic models, and many thin reports sit on top of them.

  • Level Intermediate
  • Audience Power BI developers, BI leads, reviewers
  • Reading time 75 min

What this playbook is for

Power BI makes it easy to produce a working report in an afternoon. The cost shows up later: every analyst ships their own copy of the model, measures are redefined in each report, a column rename breaks forty visuals, and nobody can tell which "Sales" number is the right one. Most of that is avoidable with a handful of agreed settings and conventions applied before the first visual is drawn.

This playbook sets those conventions. It keeps the concrete rules the team already uses (disable auto date/time, define relationships by hand, prefix report measures, keep measures in one table) and adds the reasoning, the current setting names, the failure modes, and the Fabric-specific choices such as Direct Lake. It is deliberately opinionated: where Microsoft documentation gives a hard rule it is cited, and where a rule is a house convention it is labelled as one.

When to use it

Apply it when

  • You build or review semantic models and reports that other people will maintain.
  • Several reports should share one governed model instead of each owning a copy.
  • You are moving reports onto Fabric and want the model design to be right the second time.
  • Report performance or "which number is correct" disputes are already costing time.

Look elsewhere when

  • You need operational, print-ready output. That is a paginated report; see the paginated report migration playbook.
  • You are deciding how to move an existing estate onto Fabric. Start with the Power BI to Fabric migration playbook.
  • The question is how data lands and is shaped upstream. See Medallion Architecture.

Prerequisites

  • An up-to-date Power BI Desktop build and access to a Fabric workspace on a capacity. Direct Lake models require a Fabric capacity.
  • Gold-layer tables that already look like facts and dimensions. The standards below cannot repair a flat, denormalized source; they only avoid making it worse.
  • A workspace layout that separates models from reports. The house naming convention (<ENV>_<DOMAIN>_CNSM for models, <ENV>_<DOMAIN>_DLV for delivered reports) is used in the examples.
  • Agreement on who owns each shared semantic model. A model without an owner cannot be certified or changed safely.

How the layers fit together

Three layers carry the standards, and each has a single accountable owner. The data team owns the Gold tables, a model owner owns the shared semantic model, and report authors own thin reports that connect to it. A report author who needs a new column does not patch it into the report; the request goes to the model owner, who adds it once for everyone.

Key takeaways

  • Settle model design before report design: two Desktop options and a star schema remove most downstream problems.
  • One accountable owner per layer; a thin report never patches the model.
  • Measure first, tune second. Performance Analyzer tells you which of four time buckets is the problem.
  • Treat naming and measure placement as an interface that other people depend on, because they do.
