Playbook 14 · Deployment Checklist

Layer checklists

One checklist per layer. Each item is a single verifiable action; tick them in order, and do not start the next layer until the last item of this one is ticked. The tick state is remembered in your browser, so you can pause and return.

How to use the checklists

  • Run every list twice per release: once for the DEV to TST hop, once for TST to PRD with the PRD values. Reload the page or clear the ticks between hops.
  • Each list has four groups in this order: Deploy, Configure, Hydrate, Verify.
  • Use the same deployment note format everywhere: release reference, layer, from-stage to to-stage.
  • If a verify item fails, stop. Fix the cause, repeat the step that produced it and re-run the verify group.

Bronze

The Bronze layer ingests from external sources into raw tables. Pipeline: DPLY_<DOMAIN>_BRZ.

  • Deploy. Deploy the lakehouse and wait for success; the stage lists it as paired and the target workspace holds a new, empty lakehouse of the same name.
  • Deploy. Deploy the environment and confirm its published state (libraries and Spark settings) matches DEV.
  • Deploy. Deploy the variable library.
  • Deploy. Deploy notebooks, data pipelines and shortcuts only after the three items above succeeded.
  • Configure. Open the variable library in the target workspace, make the stage's value set active and save.
  • Configure. Confirm every connection used by the pipelines exists and is usable by the run identity.
  • Configure. Confirm external shortcuts point at the target stage's sources: they keep the source stage's targets unless the target is a variable.
  • Hydrate. Run the ingestion pipelines and wait for them to finish.
  • Verify. Expected tables exist and row counts are in the expected range.
  • Verify. Shortcuts resolve and nothing is listed under Unidentified.
  • Verify. Notebooks are attached to the target lakehouse and environment.
  • Verify. The last run of each pipeline succeeded and used the target stage's connections.

Silver

Silver cleans and conforms Bronze data. It depends on Bronze being deployed and hydrated in the same stage. Pipeline: DPLY_<DOMAIN>_SLV.

  • Precondition. The Bronze verify group passed in this stage.
  • Deploy. Repeat the Bronze deploy order: lakehouse, environment, variable library, then notebooks, pipelines, shortcuts.
  • Deploy. Redeploy any item that was deployed before the item it depends on existed; binding is evaluated when you deploy, so a second deploy re-evaluates it.
  • Configure. Activate the stage's variable library value set.
  • Configure. Check every reference to the Bronze layer: notebooks, shortcuts and pipeline activities must point at the Bronze workspace of this stage. References across workspaces are not autobound; they come from variable library values, parameters or a default lakehouse rule.
  • Hydrate. Run the Silver transformation pipelines and notebooks.
  • Verify. Tables exist with the DEV schema, and row counts reconcile with the Bronze inputs.
  • Verify. No notebook run read from a lakehouse of another stage (spot-check the run details of one notebook).

Gold

Gold holds business-ready tables. Pipeline: DPLY_<DOMAIN>_GLD.

  • Precondition. The Silver verify group passed in this stage.
  • Deploy. Repeat the Silver deploy order and the redeploy check for items deployed ahead of their dependencies.
  • Configure. Activate the stage's variable library value set and check references to Silver, as for Silver.
  • Hydrate. Run the Gold transformations.
  • Verify. Dimension and fact tables exist; counts and key totals reconcile with Silver.
  • Verify. Every table the warehouse and models will read is present with the expected columns.

Warehouse

The consumption warehouse reads Gold and serves SQL. Pipeline: DPLY_<DOMAIN>_CNSM_WH.

  • Precondition. The Gold verify group passed in this stage.
  • Deploy. Deploy the lakehouse, if the layer has one (for example for staging or shortcuts).
  • Deploy. Deploy the warehouse, then the load pipelines and any stored procedures.
  • Deploy. Redeploy items that were deployed before their dependencies, to fix bindings.
  • Configure. Set per-stage connections and cross-workspace names in the load pipelines through the variable library; a warehouse deployment does not rewrite connection strings.
  • Configure. Grant the warehouse and item permissions for the stage; permissions are not copied by a deployment.
  • Hydrate. Run the load pipelines to populate the warehouse.
  • Verify. Tables, views and procedures exist; row counts match the Gold tables they load from.
  • Verify. A sample query through the SQL endpoint returns data from the target stage.

Semantic model

Semantic models are usually deployed twice: the rule is defined on the target stage's copy of the model, and it applies only at a deployment. Pipeline: DPLY_<DOMAIN>_CNSM_SM.

  • Precondition. The warehouse (or lakehouse) the models read is hydrated and verified in this stage.
  • Deploy. Deploy the semantic models. Do not refresh them yet: they still read the source stage.
  • Configure. As the model owner, open the target stage's deployment rules and add the data source rule for the warehouse or SQL endpoint connection, plus any parameter rules.
  • Configure. Record the rule values you entered, per stage.
  • Deploy. Deploy the models again so the rules apply; the models should no longer show as different.
  • Configure. Set the data source credentials and connection on each target model; credentials are not copied by a deployment. Confirm the identity can read the target source.
  • Configure. Set the refresh schedule and role members; neither is copied.
  • Configure. For Direct Lake on OneLake, which has no data source rule, run the rebind step you chose. See Direct Lake models.
  • Hydrate. Refresh the models.
  • Verify. The model settings show the target stage's data source, and a refresh succeeds.
  • Verify. A count from the model matches the same count from the warehouse.

Consumption lakehouse

Pipeline: DPLY_<DOMAIN>_CNSM_LH. If a Direct Lake model reads this lakehouse, deploy and verify it before the semantic model layer instead.

  • Precondition. The Gold layer is verified in this stage.
  • Deploy. Deploy the lakehouse; its SQL analytics endpoint and default semantic model are provisioned with it.
  • Configure. Check each shortcut: internal shortcuts in the same workspace are remapped, but their target tables and folders are not created for you, and a shortcut to another workspace must be checked by hand.
  • Configure. Create the target tables or folders a shortcut needs, if any are missing.
  • Verify. Shortcuts resolve, nothing sits under Unidentified, and the SQL endpoint answers a query.

Delivery

Reports and paginated reports. Pipeline: DPLY_<DOMAIN>_DLV.

  • Precondition. The models the reports read are deployed and refreshed in this stage.
  • Deploy. Deploy the reports. If you deploy selectively, use Select related so each report's model dependency is included or checked.
  • Configure. For paginated reports with a Fabric semantic model as source, apply the data source rule; they do not autobind.
  • Configure. Update the Power BI app or organizational app in the stage by hand; a deployment does not update app content or settings.
  • Configure. Check sharing, audiences and sensitivity labels for the stage.
  • Verify. Open View lineage on each report and confirm it reads the target stage's model.
  • Verify. Open each report and confirm the visuals load with target stage data.

Make the lists yours

Copy the lists into your own runbook and add your platform's specifics: table names to count, report names to open, the connection names to check. Generic lists get ticked without being read; specific ones catch problems.

Key takeaways

  • Every layer has the same shape: deploy in dependency order, configure per-stage values, hydrate, verify.
  • Cross-workspace references are not autobound; check them explicitly in Silver, Gold and the warehouse.
  • Semantic models are deployed twice, and not refreshed between the two deployments.
  • Credentials, schedules, role members, permissions and app content are not copied; they are configure items on every list.
