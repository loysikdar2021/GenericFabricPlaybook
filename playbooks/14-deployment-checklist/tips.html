Playbook 14 · Deployment Checklist

Tips and watch-outs

Each tip follows the same shape: the rule, why it exists, what to do, and what to do if you already broke it. Four are documented platform behaviour; one (do not click during comparison) is operational experience that Microsoft does not document, and it is labelled as such.

Tip 1: own connections with a service principal

The rule. Every team member who deploys or supports the platform must have access to the connections, models and items it uses. Prefer connections owned by a service principal. If that is impossible, make sure everyone involved has been granted access to the connections that others created.

Why

  • A connection is an item with its own access list. It has roles (User, User with resharing, Owner), and the person who created it is its owner. Someone who is not on the list cannot use it, so their deployment, refresh or pipeline run fails even though they have every workspace role.
  • When the owner leaves the organization, the connection is orphaned. Only a Fabric administrator can reassign it, through the admin connections APIs (preview), so recovery depends on someone outside the team.
  • A deployment also moves ownership. The deploying user becomes the owner of cloned semantic models, so refresh and rules depend on a person unless you plan for it.
  • Many connection types support a service principal as the authentication method. A principal does not leave the company and is not tied to one person's access.

What to do

  • Create connections for pipelines, notebooks and models with the service principal authentication method where the connector supports it.
  • Share each connection with the deployment group (User role), and with a second owner who is not the service principal.
  • List connections per layer in the runbook, with the group that has access.
  • Keep a note of the exceptions: where a connector or item type does not support a service principal, the connection stays user-owned and needs a named backup owner.

If it already happened. A failing refresh or run after a deployment, with an error about credentials or access, usually means the identity that runs it cannot use the connection. Add that identity to the connection, or recreate the connection under the service principal and rebind the items.

Tip 2: lakehouse and environment first

The rule. Deploy the lakehouse and the environment, and check they succeeded, before notebooks, shortcuts and the rest. The environment is an item in its own right: select it explicitly as part of the deployment.

Why

Notebooks bind to the default lakehouse and to the attached environment when the lakehouse and environment are in the same workspace. The pipeline looks for the paired items in the target workspace at the moment the notebook is deployed. If they are not there, there is nothing to bind to: the deployment can fail on the missing dependency, or the notebook is left unbound until it is redeployed. A lakehouse deployment is metadata only and creates an empty lakehouse with the same name; notebooks and Spark job definitions are then remapped to it. Shortcuts follow the same logic: internal shortcut targets are remapped only when the lakehouse exists.

What to do

  • Select the lakehouse, environment and variable library in the first deployment of a layer.
  • Wait for success, then select notebooks, data pipelines and shortcuts in the second deployment.
  • For a selective deployment of a notebook, use Select related to include its dependencies.

If it already happened. Redeploy the affected items now that their dependencies exist. Binding is evaluated at every deployment, so a second deployment of the notebooks fixes the binding. This is the "redeploy objects in lower environments to fix autobinding" step of the layer checklists.

Tip 3: remove deleted objects downstream

The rule. If an object is deleted in one layer, delete it, and anything that depends on it, in the subsequent layers and in every downstream stage. Remove consumers first, then the object.

Why

  • A deployment copies new and changed items and overwrites paired ones. It never deletes. An item deleted in DEV is still in TST, labelled Not in source, and cannot be selected for deployment.
  • Items that still reference the removed object end in error. A shortcut whose target no longer exists is moved to the Unidentified section of the lakehouse, and a "missing target" error is the symptom reported in practice when dependents are left behind (Learn does not document that message).
  • Recreating an object under the same name in DEV creates an unpaired item. The first deployment of a Power BI item fails if the target already holds an item with the same name and type; for other item types you end up with a duplicate.

What to do

  • Record deletions in the release note, in layer order.
  • In each target stage, delete consumers first (later layers), then the stale item (earlier layers).
  • After clean-up, open the lakehouse and confirm the Unidentified section is empty.
  • Compare the stages and confirm nothing unexpected is left under Not in source.

If it already happened. Items listed under Unidentified at the bottom of the lakehouse are the ones with unresolved references; resolve each by deleting it or by creating its target. A duplicate pair is resolved by deleting the unpaired copy in the target workspace.

Tip 4: do not interact during the comparison

Operational experience, not documented behaviour

Microsoft Learn does not describe this limitation. It is reported by practitioners using the new, preview deployment pipelines UI. Treat it as a precaution and check the troubleshooting article and the new UI overview for any change in status.

The rule. While the pipeline is comparing two stages, wait. Do not click items, filters or stage cards until the status labels have loaded.

Why

The compare is computed after you open the stage. The reported failure is that interacting while it runs stops the comparison and leaves the page unresponsive, and that refreshing the browser does not recover it. Because the compare feeds the item list you select from, a stuck compare blocks the deployment.

What to do

  • Open the stage and wait until every item shows a status label.
  • If the page freezes, start again in a new browser session or a private window.
  • If it still freezes, toggle to the original UI with the switch in the upper right corner; this restarts the comparison in most cases.
  • If the UI is not workable, run the deployment through the REST API, which does not depend on the comparison page. See Automation and limits.

Tip 5: verify hydration after every layer

The rule. After a layer is deployed and its pipelines have run, open the workspace you deployed to and confirm the tables and shortcuts before you deploy the next layer. For example, after deploying DEV_SALES_BRZ to TST_SALES_BRZ through DPLY_SALES_BRZ, check the Bronze lakehouse in TST_SALES_BRZ before you start Silver.

Why

Deployment copies definitions, never data. A freshly deployed lakehouse is empty and a freshly deployed model has nothing to read. The next layer will run against empty inputs and succeed with empty outputs, so a green run proves nothing about data. The check has to be explicit.

# Attach the TARGET stage's lakehouse as the default lakehouse of this notebook, then run.
# spark.catalog lists the tables of the current schema; in a schema-enabled lakehouse
# repeat the check for each schema you use.
tables = [t.name for t in spark.catalog.listTables()]
counts = [(name, spark.table(name).count()) for name in tables]
display(spark.createDataFrame(counts, ["table_name", "row_count"]).orderBy("table_name"))

Compare the output with the expected counts for the stage. For a warehouse use a count query per table instead.

SELECT 'dbo.customers' AS table_name, COUNT_BIG(*) AS row_count FROM dbo.customers
UNION ALL
SELECT 'dbo.orders', COUNT_BIG(*) FROM dbo.orders
UNION ALL
SELECT 'dbo.order_lines', COUNT_BIG(*) FROM dbo.order_lines;

What to do

  • Define, per layer, the tables to count and the range each count must fall in.
  • Run the counts in the target workspace, not in DEV, and attach the output to the deployment record.
  • Check shortcuts and the Unidentified section in the same pass.
  • For semantic models, compare one measure from the model with the same figure from its source.

Key takeaways

  • Connections owned by a service principal and shared with the deployment group remove the biggest single point of failure.
  • Deploy lakehouse, environment and variable library first, and redeploy anything that was deployed too early.
  • Deployments never delete: clean up downstream stages yourself, consumers first.
  • Wait for the comparison to finish; if the UI freezes, restart the session, toggle the UI, or use the API.
  • A green deployment is not a hydrated layer: count tables in the target workspace before moving on.
