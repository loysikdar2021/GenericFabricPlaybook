Deployment Checklist

This is the page you keep open on release day. It condenses the deployment pipelines playbook into an ordered runbook: what to deploy, what to configure, what to hydrate and what to verify for each layer, in the order that keeps bindings and data correct.

  • Audience Release managers, data engineers
  • Level Intermediate
  • Reading time about 45 minutes

What this runbook is for

A release across a medallion platform touches seven kinds of workspace and many items. The risk is rarely a single failed deployment; it is a successful deployment of an empty layer, or an item bound to the wrong stage, discovered a layer later. The runbook prevents that by fixing three things: the order in which layers move, the checks that gate each move, and the evidence you leave behind.

It assumes the layout from the Deployment pipelines playbook: one pipeline per layer named DPLY_<DOMAIN>_<LAYER>, each with DEV, TST and PRD workspaces named <ENV>_<DOMAIN>_<LAYER>, and Git connected to DEV only. The explanations for why each step exists are in that playbook; here every step has a one-line reason and a check.

Ground rules

  • One layer at a time. Deploy, hydrate and verify a layer before you touch the next one.
  • TST completes before PRD starts. All seven rows in TST, then all seven in PRD, with the same order and the PRD values.
  • A deployment copies definitions, not data. An empty layer is the normal result of a deployment; hydration is what makes it a working layer.
  • Every deployment gets a note that names the release, the layer and the stage hop. It is the audit trail.
  • Nobody edits TST or PRD by hand. A hand edit is overwritten by the next deployment and hides the defect that caused it.

Prerequisites

  • Seven pipelines exist (or as many as you use), each with its three stage workspaces assigned and items paired. See Pipeline setup and pairing.
  • The release manager has pipeline admin on every pipeline and at least Contributor on every stage workspace; the automation identity, if any, has the same.
  • Connections used by pipelines, notebooks and models are owned by a service principal and shared with the deployment group.
  • Each layer workspace has a variable library with a value set per environment, and you know which value set each stage must activate.
  • The values for deployment rules are recorded per stage. The appendix of the deployment playbook has a collection notebook and a template.
  • Capacity has headroom for the deployment and for the hydration runs that follow it.
  • A test plan exists for each layer: which tables, counts and reports prove the layer works.

Key takeaways

  • Deploy, hydrate and verify one layer at a time, and finish every layer in TST before you start PRD.
  • A green deployment says nothing about data; the verify step after each layer is what you sign off.
  • Keep connections service-principal owned and rule values recorded before release day, not during it.
  • Write a note on every deployment and keep the evidence.
