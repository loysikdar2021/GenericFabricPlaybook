Playbook 14 · Deployment Checklist

Troubleshooting

Start from what you see, not from what you think is wrong. The triage path points to one of four groups; each table gives the symptom, the usual cause and the fix, and links to the page that explains the mechanism.

Triage

Before you work through a table, collect three facts: the deployment ID and status from the deployment history, the list of items that failed or differ, and the deployment note. They tell you which table to open and are what support will ask for.

  • Deploy blocked or failed: the deployment cannot start, or ends with an error.
  • Item duplicated or missing: pairing, deletions and unsupported items.
  • Reads the wrong source: bindings, rules and value sets.
  • Empty or stale data: hydration, credentials and refresh.

Deploy blocked or failed

SymptomLikely causeFix
The deploy button is disabled, or the stage is not listedThe pipeline and the workspaces are permissioned separately. You are missing the pipeline admin permission, or the role on the source or target workspaceGet pipeline admin and the workspace roles listed in Permissions and roles, then reload the page
"Can't assign the workspace"An adjacent stage holds two items of the same type and name, so pairing is ambiguousRename one of the duplicates, then assign again. See Pipeline setup and pairing
The workspace is missing from the assign listYou are not its admin, it is already in another pipeline, or it is not on a Fabric capacityFix the failing condition; the list shows only workspaces that meet all three
The first deployment to an empty stage failsNo permission to create the workspace on the capacity, a missing workspace role, workspace creation disabled by the tenant, or a selective deployment without the linked itemsCheck each in turn. For a selective deployment, select the linked semantic model or dataflow too (Select related)
A "continue the deployment" message appearsA breaking schema change (for example a column type change) would lose data in the target semantic modelIf the change is intended, continue, then refresh the target model. If not, close the message, fix the source and redeploy
"Can't start the deployment" on a model with incremental refreshOnly certain semantic model changes are allowed when incremental refresh is in usePublish the change directly to the target model (this drops partitions and data, so refresh afterwards) or make the change with XMLA tools
Deployment fails with invalid or broken rulesA semantic model was republished and a parameter was removed or renamed, or a data source rule lost its valuesOpen Configure rules, fix or remove the marked rules and redeploy. See Supported items and rules
The rule pane will not save a data source ruleThe data source is controlled by a parameter, or the model has multiple data sources or a function bound to a data sourceUse a parameter rule instead, or simplify the queries so one data source is used
Deployment fails while a dataflow in scope is runningA dataflow that is refreshing blocks the deploymentWait for the refresh to end (or pause its schedule) and redeploy
A semantic model fails to deployA model over 4 GB without the large model format, or a circular or self dependency between items ("two way dependency")Switch the model to the large model format, or remove the dependency, and redeploy
Source and target model formats differThe target model has a higher data modeling format version than the sourceUpgrade the source model with the XMLA read-write endpoint or Power BI Desktop, republish it, and redeploy. Models with legacy metadata are no longer supported, so all models need enhanced metadata
Deploy to the previous stage is disabledA backward deployment works only into an empty stage, and only as a full deploymentFix in DEV and promote forward through the stages (Backward deployment)
A paginated report cannot be deployedYou are not a Member of the source workspaceGet the Member role there. A large batch of paginated reports with rules can also overload the capacity: deploy them selectively or use a larger capacity
Rules are grayed outYou are not the owner of the item, or the item has no data sources or parameters to build a rule onAsk the item owner to set the rule, or take over the item as owner
A pipeline has no owner and nobody can unassign its workspacesThe owner left without transferring ownershipA Fabric administrator adds a new owner with the admin pipelines API, or deletes the pipeline

Item duplicated or missing

SymptomLikely causeFix
A second copy of an item appears in the target stageThe items were not paired: the target item was created by hand or added after the workspace was assigned, or the source item was deleted and recreatedDelete the unpaired copy in the target, deploy again, and check pairing first next time. See pairing consequences
The first deployment of a Power BI item failsThe target stage already holds an item with the same name and type that is not pairedRename or delete the target item, or restore the pairing, before deploying
An item is labelled Not in sourceIt was deleted or renamed in the source. A deployment never deletes, and the item cannot be selected for deploymentDelete it in the target if it is stale, consumers first (Tip 3)
An item you expect to deploy is not in the listThe item type is not supported by deployment pipelinesCheck supported items. Unsupported items are not copied; manage them through Git or code
A shortcut sits under UnidentifiedIts target no longer exists or was never created in this stageCreate the target, or delete the shortcut and its consumers
Items are labelled Different straight after a successful deploymentRules are set but not yet applied; an environment uses a custom pool (not carried over); legacy-format models cannot be compared; or a folder was moved or renamed, which counts as a rename of its itemsDeploy again for rules. Treat the custom pool and model-format differences as known. For folders, deploy so the names match
Items lost their links after you unassigned and deployedFabric could not re-establish the connections between source and target items, for example after an item was deletedUnassign and reassign the same workspace. This discards the stage's history and rules, so record them first

Reads the wrong source

SymptomLikely causeFix
A notebook in TST reads the DEV lakehouseIt was deployed before its lakehouse existed in the target, the lakehouse is in another workspace (not autobound), or no default lakehouse rule is setDeploy the lakehouse first and redeploy the notebook, or set a default lakehouse rule. See Autobinding
A rule is set but the model still reads the source stageRules apply only at the next deployment of the item; until then it shows as differentDeploy the model again, and do not refresh it in between
A paginated report shows data from the source stage's modelPaginated reports do not autobind to Fabric semantic modelsApply a data source rule on the paginated report, and redeploy
A pipeline or notebook uses DEV values in TSTThe variable library's Default value set is active after the first deployment to the stageActivate the stage's value set. See Variable libraries
References between workspaces still point at the source stageCross-workspace references use object IDs and are not rewrittenMove the value into a variable library, a parameter or a rule, per stage
A Direct Lake model reads the source stageA data source rule is available for Direct Lake on SQL endpoint but not for Direct Lake on OneLakeUse one of the options in Direct Lake on OneLake

Empty or stale data

SymptomLikely causeFix
Tables are missing or empty after a deploymentA deployment copies definitions only, never dataRun the layer's loads, then the verify gate (three gates)
Report visuals are empty after deploying a model or dataflowThe data of models and dataflows is not copiedRefresh the dataflow, then the semantic model, in the target stage
A model refresh fails in the targetCredentials are not copied, and the deploying user owns the cloned model; the identity that refreshes may not have access to the connectionSet the data source credentials in the target model, and share the connection with the right identity (Tip 1)
A model refreshes manually but not on scheduleThe refresh schedule is not copiedSet the schedule in the target stage
A report cannot reach on-premises dataGateway mapping is not set automaticallyMap the model's data source to the gateway in the target stage
Users in PRD cannot see content, or see the wrong audiencePermissions, role members and app content are not copiedSet stage permissions, role members and the app by hand (Delivery checklist)
A shortcut returns no rowsAn internal shortcut was remapped, but its target table or folder was not created in the targetCreate the target, hydrate it, and recheck (Lakehouse behaviour)

When to escalate

  • You have the deployment ID, the history entry, the failed item list and the note.
  • You have confirmed the pair, the permissions and the active value set, and the problem persists.
  • The behaviour contradicts the page you were following. Check the status of the Learn article, because some of these features are in preview.
  • Open a support request or a community post with the deployment ID, and describe what you did in order. Do not include tenant URLs, secrets or tokens.

Verify against Microsoft Learn

The rows in these tables come from the Learn troubleshooting article for the lifecycle tools, the deployment limitations and the rules article, plus the operational experience in Tips and watch-outs. Error text and limits change; check the current troubleshooting article before you act on a row that matters.

Key takeaways

  • Pick the table from the symptom: blocked, duplicated or missing, wrong source, or empty.
  • Most blocked deployments are permissions, ambiguous pairing, broken rules or a dataflow refresh.
  • Most wrong-source cases are an order problem, a rule not yet applied, or the wrong active value set.
  • Most empty-data cases are expected: a deployment never copies data, credentials, schedules or permissions.
  • Keep the deployment ID and note for every deployment; they shorten every investigation.
