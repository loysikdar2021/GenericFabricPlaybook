Playbook 14 · Deployment Checklist

Pre-flight and verification

The layer checklists say what to do for each layer. This page wraps them: the pre-flight that makes a failed deployment unlikely, the discipline during the window, and the verification that turns "deployed" into "working", plus the record you leave behind.

Three phases around every release

  1. Pre-flightOnce per release, before the window opens.
  2. DuringFor every layer and every stage hop.
  3. AfterGates before the next layer, then sign-off.

The release manager owns the hand-offs. The pipeline and the target workspace do the mechanical work; nothing moves on until the release manager has seen the evidence that the previous step worked.

Pre-flight checklist

Complete this list before the first deployment of the release. If an item cannot be ticked, fix it or postpone the window.

Scope and approvals

  • The release content is merged to the branch DEV is connected to, and DEV has been synced. Nothing is deployed from an unmerged change.
  • The release is the same content that passed testing: promote through the pipeline, and never edit TST or PRD by hand.
  • A release reference exists, and every person involved knows the layer order and who signs off each layer.
  • Deleted objects are listed, in layer order, so the downstream clean-up is planned (Tip 3).
  • A rollback approach is agreed (see the section on restoring a previous version below).

Access and identities

  • The deployer is a pipeline admin and has at least Contributor on both the source and target workspaces of every pipeline in scope. Replacing an existing semantic model also needs the Member role, and a dataflow can be replaced only by its owner.
  • Connections used by pipelines, notebooks and models exist in the target stage, are shared with the deployment group, and have a named second owner (Tip 1).
  • The semantic model owner is available to set rules and credentials on the target copy.

Platform state

  • Compare each pipeline's stages first. Every item you expect to overwrite sits on the same row as its source; anything labelled Not in source or Only in source is expected.
  • No dataflow is refreshing in the stages you will compare or deploy: a deployment fails while a dataflow in scope refreshes, and a comparison made during a refresh is unpredictable.
  • Variable libraries have a value set for the target stage, and you know which to activate.
  • Rule values for the target stage are recorded (data source, parameter, default lakehouse) so nobody looks them up during the window.
  • Capacity has headroom for the deployment and for the hydration runs that follow. For load testing in TST, use a capacity separate from production.
  • Scheduled loads and refreshes that would run during the window are paused or rescheduled.
  • The browser session is fresh, and nobody will click in the pipeline page while it is comparing (Tip 4).

Test plan

  • For each layer: the tables and expected row-count ranges, the shortcuts, the reports to open and the measure to reconcile.
  • A named person for each sign-off.

During the deployment window

Repeat for each layer, in order. The details of each layer are in the layer checklists.

  1. Open the layer's pipeline and wait for the comparison

    Confirm every item has a status label before you select anything.

  2. Select the items for the first deployment

    Foundations first: lakehouse, environment and variable library. For a selective deployment, use Select related so dependencies are included.

  3. Write the deployment note

    Use the format in the evidence section below. The note is the first thing you will read in the history when something looks wrong.

  4. Deploy, then read the result

    Check the deployment status and the history entry. A deployment can complete with items that failed; read the item list, not just the status icon. Decide in advance whether you allow a deployment to continue when items fail. For a layer with dependencies, stopping on the first failure is usually safer.

  5. Deploy the dependent items

    Notebooks, data pipelines, shortcuts and so on, as a second deployment once the first has succeeded.

  6. Configure the stage

    Activate the variable library value set, apply rules (and redeploy for them to apply), set connections, schedules and permissions.

  7. Run the loads

    Run the layer's pipelines and notebooks, one layer at a time, and wait for them to finish.

  8. Run the gates

    Section below. Do not open the next layer until all three pass.

Do not fix forward by editing the target

A change made directly in TST or PRD is overwritten by the next deployment and hides the defect that caused it. Fix the cause in DEV, promote it, and let the pipeline carry it. This is also Microsoft's guidance for urgent fixes: implement the fix in development and push it through the stages, rather than deploying an untested change to production.

After: three gates between layers

  1. Deployment succeeded

    The history entry for this deployment shows success, no item failed, and the stage compare shows the deployed items as the same as the source (except items you know cannot match, such as an environment with a custom pool).

  2. Hydration completed

    Every load for the layer has finished successfully in the target workspace. Check the run history, not the pipeline's schedule.

  3. Checks passed

    The checks for each item type in the next table. A failed check sends you back to the cause, and you re-run from the failed gate.

The row-count checks are the easiest to automate. This cell runs in a notebook whose default lakehouse is the target stage's lakehouse, compares each count with the range you recorded in the test plan, and stops the run if any table is missing or out of range. A T-SQL count query for warehouses is in Tip 5; a missing table makes it fail, which is itself the signal.

# Replace the names and ranges with the ones from this layer's test plan.
# A high of None means "no upper bound". Use "schema.table" in a schema-enabled lakehouse.
expected = {
    "customers": (1, None),
    "orders": (1, None),
    "order_lines": (1, None),
}

results = []
for name, (low, high) in expected.items():
    try:
        rows = spark.table(name).count()
        ok = rows >= low and (high is None or rows <= high)
    except Exception:
        # Table missing, or not readable from this lakehouse.
        rows, ok = -1, False
    results.append((name, rows, ok))

df = spark.createDataFrame(results, ["table_name", "row_count", "in_range"])
display(df)

failed = [name for name, _, ok in results if not ok]
assert not failed, f"Gate failed for: {failed}"

Evidence and the deployment note

The deployment history is a log of past deployments in a pipeline. Each row records the target stage, the end time, who deployed (a person or a service principal), the item counts by category, any failed items, the note, a deployment ID to quote when you ask for help, and the status. It lists up to 1000 recent deployments, and a renamed item is treated as a new item in the log. Use the note field to tie each row to the release.

REL-<release-id> | <layer> | <FROM> -> <TO> | <pipeline name>
Scope: <items or "full">
Deleted downstream: <objects removed in this stage, or "none">
Config after deploy: value set <name>; rules applied <yes/no>
Operator: <initials>

Restoring a previous version

A deployment overwrites the paired items in the target stage with the source stage's versions. Microsoft's guidance for going back is Git-based: there is no direct way to return to a previous commit in the interface, so promote the older commit to be the head with git revert or git reset, update the DEV workspace from it, and promote it through the pipeline again. Because data is not stored in Git, reverting a data item such as a lakehouse or a warehouse to an older definition can break the existing data and can require dropping data, or the operation can fail. Check that before you need it.

  • Record the last known-good commit for each layer before the window opens.
  • Decide which layers can be reverted by redeploying (notebooks, pipelines, reports) and which need a data plan (lakehouses, warehouses, models).
  • Rehearse the revert in TST before you need it; a rollback you have not run is a hope.

Verify against Microsoft Learn

A backward deployment in a pipeline (from a later stage to an earlier one) is possible only into an empty stage, so it does not replace a previous version. Check Best practices for lifecycle management in Fabric and The manual deployment before you rely on any rollback method.

Key takeaways

  • Pre-flight removes the avoidable failures: access, connections, value sets, rule values, capacity and paused refreshes.
  • During the window: wait for the comparison, deploy foundations first, write a note, read the result item by item.
  • Three gates (deployed, hydrated, checked) separate layers. A failed gate is fixed and re-run, not carried forward.
  • Verification is per item type and leaves evidence: counts, run IDs, lineage and the history entry.
  • Rollback is Git-based and data-sensitive; decide how you would do it before the window, not during an incident.
