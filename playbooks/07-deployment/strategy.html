Playbook 07 · Deployment Pipelines

Deployment strategy

Before you create a pipeline, decide what is the source of truth for each stage and what moves content between stages. This page defines the hybrid pattern, shows the trade-offs against the alternatives and lists the operating rules that stop it degrading into drift.

Two tools, two jobs

Git integration and deployment pipelines overlap in marketing but not in mechanics. Keep the split in mind and most design questions answer themselves.

What it movesItem definitions between a repository branch and one workspaceItem definitions between workspaces that represent adjacent stages

Per-stage configurationNot its job; handled by separate branches, variable libraries or scriptsDeployment rules and autobinding, plus variable library value sets
DataNever versionedNever copied
Who uses itDevelopersRelease managers and automation

The hybrid pattern

The pattern is documented by Microsoft as the option where Git is connected only up to the development stage and deployments from there are workspace to workspace. It separates developer concerns from release concerns, and it is the option that gives you deployment rules and autobinding for per-stage configuration.

  1. Connect only DEV to Git

    The DEV workspace tracks the main branch. All commits and pull-request merges flow into it, so it always holds the latest integrated code.

  2. Develop in feature workspaces

    A developer creates a feature branch and a temporary workspace connected to that branch. The workspace isolates the work completely; after the pull request is merged, delete it. Branch mechanics are covered in the GitHub integration playbook.

  3. Keep TST and PRD disconnected from Git

    They receive content only through the deployment pipeline. Nobody commits to them and nobody edits them by hand.

  4. Create the pipeline and assign one workspace per stage

    Assignment is covered in Pipeline setup and pairing.

  5. Promote along one path

    Merge to main, update DEV from Git, deploy DEV to TST, verify, deploy TST to PRD. Use the pipeline UI or its REST API, and add a note to every deployment.

Why the split matters

  • Developers keep the full Git workflow without exposing TST and PRD to direct commits, force-pushes or accidental syncs.
  • Release managers get a simple, auditable interface: compare two stages, deploy selected items, read the history with the notes.
  • Per-stage configuration has a home. Deployment rules can only be defined in the pipeline, and they are what lets one definition connect to different sources per stage.

Choosing between the options

Microsoft describes four workflow options: Git integration with a branch per stage, code-first deployments through the Fabric Items APIs, deployment pipelines, and a variant of code-first for ISVs. Most real platforms mix them, for example Git for development, a pipeline for platform items and code-first for items the pipeline does not cover. The table compares the three that matter to an enterprise data platform.

How to decide

  • If the people who release are not the people who develop, and they want to see what will change before it changes, choose the hybrid.
  • If policy demands that every production change comes from a reviewed commit and a CI run with gates, choose code-first, or hybrid with the pipeline triggered from CI.
  • If your team already runs Gitflow and wants Git as the only record, choose Git-only, and plan the per-stage configuration with variable libraries from day one.
  • If you manage hundreds of customer workspaces from one codebase, you are in the ISV case, which this playbook does not cover.
  • If you need to run the same release across several workspaces in a strict order with pre- and post-actions, look at deployment plans (next callout).

Verify against Microsoft Learn

Deployment plans attach an explicit order, related items and actions to a deployment between stages, and can be used with either Git integration or deployment pipelines. Check the deployment plan overview for the current status, supported items and whether your automation tooling supports them before you rely on them.

Operating rules for the hybrid pattern

RuleWhy
Protect main and require pull-request reviewDEV mirrors main, and DEV is what you promote. Review is the only quality gate before the pipeline.
Never edit TST or PRD by handA manual edit shows as Different in the compare and is overwritten by the next deployment, so the fix silently disappears.
Fix forward through the whole pathA production bug is fixed on a feature branch, merged, synced to DEV and promoted. Backward deployment is allowed only into an empty stage, so it is not a hotfix mechanism.
Keep item names identical across stagesPairing and rules are name- and type-based, so a renamed item in one stage becomes a duplicate instead of an overwrite.
Add a note to every deploymentIt is stored in the deployment history and is the audit trail for who promoted what and why.
Limit who is a pipeline adminPipeline admin plus Contributor on both workspaces is the right to deploy. Keep it to the release team and the automation identity.
Promote in dependency orderAutobinding and rules assume that upstream items already exist in the target. See Deployment order and layers.

Anti-patterns

Anti-patternWhat goes wrongDo this instead
Connecting TST and PRD to Git branches while also using a pipelineTwo mechanisms can change the same workspace, so you can no longer say which definition is live.Pick one mover per workspace. In the hybrid, only DEV has a Git connection.
Deploying out of a feature workspaceUnreviewed, unmerged content reaches TST and the repository no longer explains the environment.Merge first, sync DEV, then deploy.
One pipeline for the whole platformA single deploy mixes layers, hits the 300-item cap and makes dependency order impossible to control.One pipeline per layer, deployed in order.
Skipping TST for a small changeRules and autobinding behave differently in each stage, and TST is the first place they run.Keep one path; make the path fast instead of shortening it.
Treating deployment as data movementA deployed lakehouse or semantic model is empty until a pipeline hydrates or refreshes it.Hydrate and verify each layer before the next deploy.

Key takeaways

  • Choose the promotion mechanism by who releases and what gates you need, not by habit: hybrid for visible, low-code promotion; code-first for gated, scripted releases.
  • In the hybrid pattern exactly one workspace per pipeline, DEV, is connected to Git.
  • Forbid manual edits in TST and PRD; they are overwritten and they hide defects.
  • Production fixes travel the same path as features. Backward deployment is not a shortcut.
