Deployment Pipelines and Promotion

Git versions your items; deployment pipelines promote them. This playbook shows how to run both together, how pairing, autobinding and deployment rules behave, and how to promote a medallion platform layer by layer without breaking references.

  • Audience Architects, data engineers, release managers
  • Level Advanced
  • Reading time about 2 hours

What this playbook solves

Fabric ships two lifecycle tools that are easy to conflate. Git integration stores item definitions in a repository so you get branches, pull requests and history. Deployment pipelines copy items between workspaces that stand for stages (development, test, production), compare the stages and apply per-stage configuration. Teams that adopt only one of them hit predictable walls: Git alone gives review and rollback but turns promotion into branch merges and syncs, while pipelines alone give promotion but no branching, review or revert of the definitions themselves.

The pattern in this playbook uses each tool for what it is good at: Git for collaboration in the development workspace, a deployment pipeline for everything after that. It then walks the mechanics you must understand before you automate anything: item pairing (which target item a deploy overwrites), autobinding (which references are re-pointed for you), deployment rules (which settings you can override per stage) and the deployment order that keeps all of that predictable across Bronze, Silver, Gold, warehouse, semantic model and delivery workspaces.

The pattern at a glance

QuestionAnswer used throughout this playbook
Where does development happen?In temporary feature workspaces connected to feature branches. The DEV workspace is connected to main.
How do changes reach TST and PRD?Through a deployment pipeline. TST and PRD workspaces have no Git connection.
What differs per stage?Connections, default lakehouses and parameters, set with deployment rules, variable library values or parameterization.
In what order do things move?Layer by layer: Bronze, Silver, Gold, Warehouse, Semantic models, Consumption lakehouse, Delivery. Each layer is hydrated and verified before the next one is deployed.
What does a deployment not copy?Data, item IDs and URLs, permissions, workspace settings, and for semantic models the credentials, refresh schedule and role assignments.

When to use this pattern, and when not to

SituationFitWhy
Separate developers and release managers; stage-by-stage review with a visual compareGood fitThe pipeline gives a compare view, a change review, a deployment history with notes and a single place to configure rules.
Semantic models or paginated reports that must connect to different sources per stageGood fitDeployment rules exist for exactly these items.
Medallion platform with several workspaces per environmentGood fit, with disciplineOne pipeline per layer, deployed in dependency order. See Deployment order and layers.
Hard requirement for approval gates, automated tests and artefact versioning in a CI systemUse code-first, or call the pipeline from CIThe deployment pipeline REST API can be driven from CI, but gates and tests are yours to build. See Automation and limits.
More than 300 items changing in one release, or item types the pipeline does not supportSplit the release, or go code-firstA single deployment is capped at 300 items, and unsupported items are not copied.
Many customer tenants or workspaces generated per customerDifferent designThis is the ISV scenario; Microsoft documents it as a separate option.

Audience and prerequisites

Audience
Platform architects who choose the lifecycle design, data engineers who build and promote items, release managers who run deployments, and reviewers who need to understand what a promotion changes.
Capacity
Every workspace assigned to a pipeline must be on a Fabric capacity.
Roles
Pipeline admin on the pipeline, plus at least Contributor on both the source and target workspaces of each deployment. Assigning a workspace requires workspace Admin.
Naming
Workspaces <ENV>_<DOMAIN>_<LAYER> (for example TST_SALES_SLV) and pipelines DPLY_<DOMAIN>_<LAYER>. The pairing and rule behaviour on the later pages depends on identical item names across stages.
Source control
A Git repository connected to the DEV workspace. Branching mechanics are in the GitHub integration playbook.

What you will be able to do

  • Choose between Git-only, hybrid and code-first promotion, and defend the choice with the trade-offs.
  • Create a pipeline, assign workspaces and explain exactly when items become paired.
  • Run a manual deployment, read the compare labels and review changes before and after.
  • Predict which references autobind and which need a rule, a parameter or a variable library.
  • Configure deployment rules for a notebook's default lakehouse and for a semantic model's data source, including the Direct Lake cases.
  • Promote a medallion platform in dependency order and verify each layer before moving on.
  • Script the same promotion through the REST API and know where manual steps remain.

Key takeaways

  • Use Git for development collaboration and a deployment pipeline for promotion; connect only the DEV workspace to main.
  • A deployment copies definitions, not data: every promoted layer must be hydrated and verified before the next one moves.
  • Pairing decides what a deployment overwrites, autobinding decides what it re-points, and rules decide what it rewrites. Learn all three before the first production release.
  • Deploy in dependency order, one pipeline per layer, and treat any skipped stage as an incident.
