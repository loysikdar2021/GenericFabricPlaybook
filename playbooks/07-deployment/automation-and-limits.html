Playbook 07 · Deployment Pipelines

Automation, limits and permissions

Once the manual deployment is routine, script the same gates. This page shows the deploy API and its long-running behaviour, what to do for items the pipeline cannot configure, the limits worth planning around, and who needs which role.

Automating a deployment

The deployment pipeline is a Fabric feature, but it has a public REST API, so a CI system can call it. This keeps what the pipeline is good at (compare, rules, autobinding, history) and adds what CI is good at (approvals, tests, scheduling). The sequence is the same as the manual one: deploy, wait, verify, hydrate.

The deploy call

The deploy operation is a POST to /v1/deploymentPipelines/{deploymentPipelineId}/deploy. It returns 202 Accepted with a Location header for the operation, an x-ms-operation-id and a Retry-After interval, because the deployment runs as a long-running operation.

Body fieldRequiredMeaning
sourceStageId, targetStageIdYesStage IDs of two consecutive stages. Deploying to a previous stage works only into an empty stage.
itemsNoList of sourceItemId and itemType. Omit it to deploy all supported items. At most 300 items per request.
noteNoUp to 1,024 characters; stored in the deployment history. Put the build number and release reference in it.
createdWorkspaceDetailsWhen the target stage is emptyName and capacity of the workspace to create. Ignored otherwise.
optionsNoFor example allowCrossRegionDeployment (default false) and per-item options keyed by source item ID.
 
import time
import requests
from azure.identity import DefaultAzureCredential

API = "https://api.fabric.microsoft.com/v1"
PIPELINE_ID = "<pipeline-id>"
SOURCE_STAGE_ID = "<source-stage-id>"
TARGET_STAGE_ID = "<target-stage-id>"

# Uses the CI identity: environment variables for a service principal, or a signed-in user.
token = DefaultAzureCredential().get_token("https://api.fabric.microsoft.com/.default").token
headers = {"Authorization": f"Bearer {token}", "Content-Type": "application/json"}

body = {
    "sourceStageId": SOURCE_STAGE_ID,
    "targetStageId": TARGET_STAGE_ID,
    "note": "Release 12: promote Gold to TST (build 345)",
}
resp = requests.post(f"{API}/deploymentPipelines/{PIPELINE_ID}/deploy", headers=headers, json=body, timeout=60)
resp.raise_for_status()

if resp.status_code == 202:
    operation_url = resp.headers["Location"]
    wait = int(resp.headers.get("Retry-After", 30))
    while True:
        time.sleep(wait)
        poll = requests.get(operation_url, headers=headers, timeout=60)
        if poll.status_code == 429:  # throttled: honour Retry-After and try again
            wait = int(poll.headers.get("Retry-After", wait))
            continue
        poll.raise_for_status()
        state = poll.json()
        if state.get("status") in ("Succeeded", "Failed"):
            break
        wait = int(poll.headers.get("Retry-After", wait))
    if state["status"] != "Succeeded":
        raise SystemExit(f"Deployment failed: {state}")
print("Deployment succeeded")

Verify against Microsoft Learn

Check the Deploy Stage Content reference and the long-running operations article for the current payload, status values and how long an operation result is retained. Fetch the result of a finished operation promptly rather than relying on it later.

Identity for automation

  • Required roles. The caller needs the pipeline admin role and at least Contributor on both the source and the target workspace, exactly as for a person.
  • Service principals are supported only when every item involved in the operation supports service principals. A single unsupported item makes the call fail, so test your real item mix, and keep a user-based fallback.
  • Tenant settings. Allow service principals to call the Fabric public APIs, and allow them to create workspaces, connections and deployment pipelines if the automation will do so. Scope both to a security group that holds only your automation identities. See the Tenant settings reference.
  • Ownership. The identity that deploys becomes the owner of cloned semantic models and the admin of a created workspace. Decide whether that should be a service principal, and document how rules and credentials are managed for models it owns.

What to add around the call

  1. Gate before TST and PRD

    Use the approval feature of your CI system on the environment that runs the deploy step. Require the TST deployment note to be referenced in the PRD run.

  2. Verify after the deploy

    Run smoke checks and data quality tests as separate steps that fail the run. They are the automated form of the verification in the Deployment checklist.

  3. Hydrate in order

    Trigger the load pipelines through the Fabric job APIs between layers. Orchestration across workspaces is covered in cross-workspace orchestration.

  4. Fail closed

    If any step fails, stop the sequence. A half-promoted layer is the expensive failure mode.

When the pipeline is the wrong tool

A code-first release keeps definitions in Git and publishes them to each workspace with the Fabric item APIs. The open-source fabric-cicd library wraps that: you describe the workspace, which item types are in scope and which environment is targeted, and a parameter file holds per-environment replacements.

from fabric_cicd import FabricWorkspace, publish_all_items, unpublish_all_orphan_items

target = FabricWorkspace(
    workspace_id="<workspace-id>",
    environment="TST",                      # selects the matching block in parameter.yml
    repository_directory="./workspace",
    item_type_in_scope=["Lakehouse", "Notebook", "DataPipeline", "SemanticModel", "Report"],
)
publish_all_items(target)
unpublish_all_orphan_items(target)          # deletes target items that are no longer in the repository
You getYou give up or must build
Git as the only source of truth, with gated, testable releasesThe pipeline compare view, change review and deployment history
Per-environment replacements in a parameter file, including dynamic lookups of workspace and item IDsDeployment rules and autobinding; you decide what to rewrite
Explicit orphan clean-up with unpublish_all_orphan_itemsSafety: the same call is destructive if the repository folder is wrong
No dependence on the preview UISupport for deployment plans, which the library does not provide

Verify against Microsoft Learn

Read the fabric-cicd and Azure DevOps tutorial and the library documentation for the supported item types and the current parameter file syntax. The Fabric command-line tool also has deployment commands; confirm their status and syntax in its documentation before you put them in a runbook.

Limitations and workarounds

Data pipelines have no deployment rulesA promoted pipeline keeps the connections and item references of the source stageUse a variable library (next section). Do not hard-code connections.
Dataflow Gen2: no autobinding, destinations are absolute referencesA promoted dataflow reads and writes the DEV itemsUse relative references for sources where possible and parameterize destinations; pass values from a pipeline.
Semantic model credentials, refresh schedule and role assignments are not copiedA new model in TST or PRD cannot refresh and has no row-level security membersSet them once per target model, or script them against the Power BI REST API after the first deployment.
Direct Lake on OneLake has no data source ruleThe model keeps reading the source-stage lakehouseParameter rule, post-deployment rebind or scripted release (see the options table).
Semantic models must use the enhanced metadata formatModels in the legacy format cannot be deployedSave and republish from a current Power BI Desktop, or convert through the XMLA endpoint.
At most 300 items per deploymentA large layer cannot go in one deployOne pipeline per layer; selective deployments in batches.
Deleted items are not deleted downstreamItems accumulate as Not in source; name collisions followDelete in each downstream workspace, in layer order.
Backward deployment only into an empty stage, full onlyNo hotfix by backward deploymentFix forward through the whole path.
Items not on the support list are not copiedThey are visible but not deployable in the new UIPublish them with the Items API or fabric-cicd, or recreate them by hand and document it.
Frozen-cell status in notebooks is not preservedFrozen cells are lost on deployDo not rely on frozen cells for production behaviour.

Per-stage values for data pipelines: variable libraries

Older guidance makes pipelines environment-aware by switching on the current workspace ID and setting variables in each case. A variable library replaces that approach: it is a Fabric item with named variables and several value sets, exactly one of which is active per workspace. Pipelines read values through library variables, and the same library can supply connection and item references, shortcut targets and notebook parameters.

  1. Create one library per layer workspace

    For example VL_SALES_BRZ, with variables such as SourceLH and SourceWSID and a value set per environment.

  2. Reference the variables in the pipeline

    In dynamic content choose Library variables, which yields an expression of the form @pipeline().libraryVariables.SourceLH.

  3. Deploy the library first, then the pipeline

    The library is a supported item in both Git and deployment pipelines.

  4. Activate the stage's value set

    After a deployment to an empty stage the Default value set is active. Select the stage's own value set and save before anything that reads a variable runs.

Variable libraries are covered in depth in the Variable libraries playbook.

Permissions and roles

Pipeline permission and workspace permission are granted separately. A pipeline has a single permission, Admin; everything else comes from workspace roles.

ActionRequirement
Create a pipelineA license that allows it (see Learn); pipeline creation can be restricted to a platform group
Assign a workspace to a stagePipeline admin, workspace admin of the workspace, and at least Contributor on the workspaces in adjacent stages
Compare stagesPipeline admin and Contributor or higher on both stage workspaces
Deploy to an existing stagePipeline admin and at least Contributor on both workspaces; for an existing semantic model you must be Member, and where the tenant restricts it, the model owner
Deploy to an empty stagePipeline admin and Contributor on the source workspace, plus capacity permission to create the workspace
Deploy a dataflowOwner of the dataflow
View or set a rulePipeline admin, Contributor or higher on the target workspace, and owner of the item
View deployment historyPipeline admin

A role design that works

  • Developers are Contributor or Member on feature workspaces and DEV, and have no write role on TST or PRD.
  • Release managers hold the pipeline admin role and Contributor on every stage workspace they deploy between. Use a security group so membership is reviewable.
  • Automation identity is pipeline admin and Contributor on the stage workspaces, owner of the items whose rules it must manage, and owner of the connections that unattended runs use.
  • Connections. Connections have their own roles (User, User with resharing, Owner). A connection created by one person is unusable by others until shared, and is orphaned when its owner leaves. Prefer connections owned by a service principal, and grant the deployment team access to the rest.

Key takeaways

  • The deploy API is a long-running operation: post, read Location and Retry-After, poll until Succeeded or Failed, then verify and hydrate.
  • Service principals work only if every item in the deployment supports them; keep a user fallback and scope the tenant settings to a group.
  • Choose code-first when you need gated, testable releases and can give up the compare view and deployment plans.
  • Data pipelines belong on variable libraries; remember to activate the stage's value set after the first deployment.
  • Separate pipeline admin from workspace roles on purpose, and own connections with a service principal.
