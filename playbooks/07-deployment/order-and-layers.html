Deployment order and layers

A layered platform has many workspaces and many cross-references. This page defines the pipeline layout, the order that respects the dependencies, the deploy-hydrate-verify loop, and what each layer needs before the next can follow.

Why the order matters

  • Dependencies must exist in the target. A report cannot deploy without its semantic model, and a notebook binds to the lakehouse and environment that already exist in its workspace.
  • Binding is evaluated against the target as it is when you deploy. Pairing, autobinding and rules all read the current state of the target stage; deploying out of order changes what they find.
  • A deployment copies definitions, not data. A freshly deployed lakehouse is empty. The next layer would read nothing, succeed anyway, and produce empty downstream tables. Hydration and verification are what turn a deployment into a working layer.
  • Blast radius. Sequential promotion confines a failure to one layer instead of leaving seven half-promoted workspaces to untangle.

The rule

Provision the workspaces for every layer of the target environment and assign them to their pipelines up front, so cross-layer references have somewhere valid to point. Then deploy layer by layer in dependency order, and hydrate and verify each layer in the target before deploying the next one. Do this in TST first and repeat the same sequence for PRD.

One pipeline per layer

Create a separate pipeline for each layer, named DPLY_<DOMAIN>_<LAYER>. Each has three stages, each stage holds exactly one layer workspace, and the workspace names follow <ENV>_<DOMAIN>_<LAYER>.

Why one pipeline per layer

  • Layer-sized compare lists you can actually review, well under the 300-item cap.
  • Different owners and release cadences per layer.
  • Rules and history stay scoped to the layer they apply to.
  • Order is explicit: you cannot half-promote a platform by accident.

What it costs

  • Seven pipelines per domain to create, name and secure.
  • Order across pipelines is yours to enforce, in a runbook or in automation.
  • References between layers cross workspaces and are not autobound.

If a Direct Lake model reads the consumption lakehouse, that lakehouse and its data must exist before the model is deployed and refreshed, so step 6 moves ahead of step 5. Draw the dependency edges for your own platform before you freeze the runbook.

The deploy, hydrate, verify loop

Within each layer the order of items matters too, because binding looks for items that must already exist:

  1. Lakehouse and environment first

    Deploy the lakehouse, the environment and any variable library, and wait for success. Notebooks and Spark job definitions then bind to the paired lakehouse and environment in the same workspace.

  2. Then notebooks, data pipelines and shortcuts

    These depend on the items above. For selective deployments use Select related.

  3. Set the stage's variable library values

    A variable library deployed to an empty stage comes up with the Default value set active. Make the stage's own value set the active one and save, before anything that reads a variable runs.

  4. Hydrate

    Run the data pipelines or notebooks that create and populate tables. Deployment never copies data.

  5. Verify

    Check tables, row counts and shortcuts in the target workspace, using the checks in the Deployment checklist and the QA validation playbook. Only then start the next layer.

What a lakehouse deployment does

AspectBehaviour
What is deployedMetadata: name, description, shortcuts and, optionally, data access roles. Tables, views and files are never deployed or overwritten.
First deploymentA new, empty lakehouse with the same name is created in the target workspace. Notebooks and Spark job definitions are remapped to reference it. The SQL analytics endpoint and the default semantic model are provisioned with it.
Internal shortcutsShortcuts whose target is in the same workspace are remapped across stages. The target tables or folders are not created for you.
External shortcutsKeep the same target in every stage. To point different stages at different locations, use variables in the shortcut definition through a variable library.
Invalid shortcut targetsThe shortcut is shown in the Unidentified section until the reference is resolved.
Shortcut stateA deployment overrides the shortcuts in the target lakehouse: all of them are updated or deleted to match the source. Always use Review changes first.

Verify against Microsoft Learn

The lakehouse article describes remapping for internal shortcuts "in the same workspace". Shortcuts that point at a lakehouse in another layer's workspace are the normal case in a layered platform. Test on a throwaway pipeline whether those targets are remapped in your tenant, and check Lakehouse Git integration and deployment pipelines for the current rule before you depend on it. Until you have confirmed it, treat cross-layer shortcut targets as per-stage configuration to set and verify after each deployment.

Environments and promotion lanes

  1. Provision

    Create every layer workspace for DEV, TST and PRD, assign capacity and roles, and assign each to its pipeline stage.

  2. Run the full ordered deployment into TST

    Hydrate and verify after each layer, then run the end-to-end smoke and data quality checks.

  3. Complete acceptance

    Do user acceptance on TST outputs, with the TST semantic models and reports.

  4. Repeat the same sequence for PRD

    Use the same order and the PRD values (rules, variable library value set, connections). Run post-deployment validation and monitoring checks.

  5. Keep one documented path

    DEV to TST to PRD. Do not skip a stage, and do not deploy a layer to PRD that was not verified in TST.

Key takeaways

  • One pipeline per layer, each with DEV, TST and PRD workspaces, deployed in dependency order.
  • Deploy, hydrate, verify, then move on; a deployment is never the end of a layer's promotion.
  • Inside a layer, deploy the lakehouse and environment first, then notebooks, pipelines and shortcuts, then set the stage's variable library values.
  • A lakehouse deployment is metadata only and creates an empty lakehouse; internal shortcut targets and cross-layer references must be checked after every deploy.
  • Remove deleted objects in every downstream stage, in the same order.
