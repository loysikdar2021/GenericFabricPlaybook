Playbook 07 · Deployment Pipelines

The manual deployment

Learn the manual deployment before you automate it. Any automation has to reproduce the same gates: compare, select with dependencies, deploy with a note, then verify and hydrate. This page walks each one in both UIs and states what a deployment does to the target.

Before you deploy

  • The change is merged to main and DEV has been updated from Git (see the hybrid pattern).
  • Items you are about to promote have paired counterparts in the target stage, or you accept that a first deploy creates them.
  • Upstream layers were already deployed to the target stage, hydrated and verified. See Deployment order and layers.
  • Rule values for the target stage (connection strings, lakehouse IDs) are prepared. The appendix notebook collects them.
  • You hold pipeline admin and at least Contributor on both workspaces.
  • No refresh is running on dataflows in the deployment: a deployment that overlaps a dataflow refresh fails.

Compare the stages

The pipeline home page compares each stage with the stage it is deployed from. A green indicator means the metadata of all items is identical; an orange indicator means at least one item was changed, added or removed. Items are matched through pairing, so the compare is only as good as your pairing.

  1. Select the target stage (new UI)

    The source stage is shown in the drop-down next to Deploy. Every item in the target stage is listed next to its paired source item with a status label.

  2. Or select Compare (original UI)

    Under the orange indicator between two stages select Compare. The compare view lists the items of both stages as a flat list; hover an item to see its path.

  3. Read the labels

    Use the table below. Treat every Different from source item you did not expect as a finding to investigate before you deploy.

New UI labelOriginal UI labelMeaningEffect of a deploy
Only in sourceNewThe item exists in the source stage onlyCloned into the target and paired
Different from sourceDifferentThe paired items differ in schema or in a property (name, folder), or a deployment rule was defined but not applied yetThe target item is overwritten by the source, regardless of where the edit was made
Same as source(no label)No difference foundNothing to do
Not in sourceMissing fromThe item exists only in the selected stageNot affected, not selectable. Deleting an item in the source never deletes it in the target.

Different includes your own rules

After you create a deployment rule on a stage, the item shows as Different until you deploy it, because rules are applied only during a deployment. After the deployment the indicator disappears. A semantic model that stays Different after a clean deploy is a symptom worth chasing.

Choose what to deploy

Full deployment

Deploy everything that is new or different in one go. This is the standard for a release: one sprint's worth of reviewed change. In the original UI select Deploy on the source stage card; in the new UI select the target stage, pick the source, select all items and deploy.

Selective deployment

Use it for a hotfix to one item, or when you must promote a layer in parts. Select Show more (original UI) or tick the items (new UI) and deploy; only the selected items move. The Deploy button shows how many items are selected, and a single deployment is limited to 300 items.

  • Select related. Adds the upstream items the selected ones depend on, for example the semantic model behind a report. It works in the flat list view; if you click it in the folder view, the view switches to the flat list automatically.
  • Folders. In the folder view you can select only items at the same folder level. Switch to the flat list view to select across folders. A folder is deployed only as a side effect of deploying one of its items, and deploying one item of a folder also updates the structure of the folder's other items in the target.
  • Dependencies fail loudly. A report cannot be deployed if its semantic model does not exist in the target stage. If the model exists but differs from the source, the result can be surprising, which is another reason to use Select related.

Backward deployment

Deploys from a later stage to an earlier one. It is available only when the target stage is empty and only as a full deployment. Its legitimate use is bootstrapping: you assign an existing production workspace to the last stage and deploy backward to create TST and then DEV. It is not a hotfix path, because as soon as the earlier stage has a workspace the option is disabled.

Execute the deployment

  1. Select the items and start the deploy

    A dialog lists every item you are about to deploy. It warns when items in the target will be replaced.

  2. Add a note

    Expand Add a note. State what is promoted and why, for example Release 12: order margin calculation, ticket 4821. Notes are stored in the deployment history and are your audit trail. A note without a ticket or release reference is nearly useless in six months.

  3. Optionally attach a deployment plan (preview)

    A plan fixes the order of items and can run supported actions before or after an item deploys. Attach one only when ordering matters inside a single deployment.

  4. Deploy

    While the deployment runs you can navigate elsewhere in the portal, but you cannot use the content in the target stage. A success dialog appears when it completes.

  5. Verify

    Reopen the compare. Deployed items should read Same as source. Then hydrate and check, as described below.

Verify against Microsoft Learn

Deployment plans are in preview. Check the deployment plan overview for supported items and actions before you add them to a runbook. The overview also states that plans are not supported by the fabric-cicd library, so a scripted release cannot reproduce them.

DEV to TST, then TST to PRD

The two hops are the same procedure with different consequences. Deploying DEV to TST is where you find missing pairs, unexpected Different items and rules that do not apply. Deploying TST to PRD should then be a repeat of a rehearsed change: compare the stages, expect the same set of differences you promoted to TST, deploy with a note that references the TST note, and verify. If the TST to PRD compare shows items you did not test, stop.

What a deployment does to the target

Deployment copies definitions and the connections between items, then applies the rules for the target stage. The overwrite changes an item's content only; the item's ID, URL and permissions stay. Consequences you must plan for:

  • Data is never copied. A deployed lakehouse schema or semantic model is empty or stale until you run the loads and refresh. Verify hydration layer by layer.
  • Semantic models keep their target-side settings. Role assignments, refresh schedule and data source credentials are not copied, so a first deployment needs credentials and a schedule set on the target model. Gateway mapping is also not automatic after the first deployment; configure it in the target item's settings once.
  • Breaking schema changes stop the deployment. A column type change that would drop data in the target model triggers the continue the deployment dialog. Continue only if you intend to lose that data and plan the refresh.
  • Ownership changes on a first deployment. The deploying user becomes the owner of cloned semantic models, and for a deploy that creates a workspace, its only admin. Deploy as a named release owner, or with a service principal where the items allow it (see Automation and limits), rather than as a developer who may leave.
  • Sensitivity labels follow special rules. They are copied only for new items, for items deployed to an empty stage, or when the source has a protected label and the target does not (with consent). Review labels after the first promotion.

Deployment history and change review

Every deployment is logged and visible to pipeline admins: source and target stage, time, the user who started it, status and the note. The stage cards also show when content was last deployed to that stage. Use the history to answer "what is in production and who put it there".

In-depth change review

  1. Open the compare for the stage pair

    Select the Compare icon (new UI) or hover over a different item and select Change review (original UI).

  2. Read the line-by-line diff

    The left side (red, minus) is the target content that will be removed or overwritten; the right side (green, plus) is the source content that will be applied. Switch between side-by-side and inline views.

  3. Remember the limits

    Change review supports schema changes of textual items: semantic models that use the enhanced metadata format, and dataflows. For other items the button is disabled, and a pure name or folder change is not shown because it is a settings change rather than a schema change.

  4. Know what the diff hides

    Data source and parameter rules are applied to the source side before comparing, so what you see is what will be deployed. Timestamps, role membership and system-managed tables are removed from both sides.

Make the review a gate, not a ritual

Require a second person to read the TST to PRD compare and sign the deployment note. The compare view is cheap to read; most unwanted production changes are visible in it.

After the deployment

  • Compare again: deployed items read Same as source.
  • Run the load pipelines or notebooks that hydrate the layer, then check tables and shortcuts in the target workspace.
  • Refresh dataflows first, then semantic models, and set credentials and the schedule on a new model.
  • Open one report per deployed model and confirm it points at the target model.
  • Record the outcome against the deployment note.

The full per-layer procedure is in the Deployment checklist playbook.

Key takeaways

  • Compare before you deploy and treat unexpected Different from source items as findings.
  • Use Select related for any selective deployment, and remember the 300-item cap.
  • Backward deployment bootstraps an empty stage; it is not a hotfix path.
  • A deployment copies metadata only. Data, IDs, permissions, credentials, schedules and roles stay in the target, so hydrate and configure after every promotion.
  • Write a note that names the release and the ticket; it is the audit trail.
