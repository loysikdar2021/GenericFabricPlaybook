Playbook 07 · Deployment Pipelines

Supported items and deployment rules

Support for lifecycle management is uneven across item types, and deployment rules cover only a handful of them. This page gives the support matrix, explains how rules behave, and walks the two scenarios every layered platform hits: notebooks that read another layer's lakehouse, and semantic models that must read the target stage's data.

The matrix lists the items a data platform typically promotes. Git integration and deployment pipelines have separate support lists, and several Power BI items are still in preview in both. Rules exist for five item types only.

Deployment rules

A rule overrides one property of one item when it is deployed into a stage. Without rules, a deployed item keeps whatever the source stage had, including connections to DEV.

Rule types and the items that support them

ItemData source ruleParameter ruleDefault lakehouse rule
Dataflow Gen1YesYesNo
Semantic modelYesYesNo
Paginated reportYesNoNo
Mirrored databaseYesNoNo
NotebookNoNoYes
  • Data source rule. Replaces a data source's details (for example server and database) with another of the same type. You cannot change the type, and one data source cannot appear in more than one rule. The list of data sources is taken from the source stage.
  • Parameter rule. Sets a parameter's value on each deployment. Parameters that drive a connection must be of type Text.
  • Default lakehouse rule. Notebooks only. Chooses the lakehouse the notebook is attached to in the target stage.

How rules behave

  • Create rules on the target stage, never on the first stage, and only as the owner of the item. The rule pane is greyed out for anyone else.
  • Rules take effect only at the next deployment into that stage. Until then the item shows as Different in compare, and compare already reflects the rule.
  • A rule is valid only while its parameter or data source still exists in the source item. Renaming or removing it makes the deployment fail until you fix or delete the rule.
  • Deleting an item deletes its rules, and unassigning a stage workspace discards that stage's rules. Neither can be restored; keep the values in the appendix template so you can recreate them.
  • Rules take precedence over autobinding.
  • Data source rules are supported for a list of source types, including Azure SQL, SQL Server, Azure Synapse, Analysis Services, OData, Oracle, SAP HANA (import mode only), SharePoint and Teradata. For other sources use a parameter.
  • Not supported: data source rules on semantic models that use Dataflow Gen1 as source, on parametrized data sources, or on models that combine native query and DirectQuery.

Scenario 1: a notebook's default lakehouse

A Gold notebook NB_SALES_GLD_Load in DEV_SALES_GLD uses LH_SALES_SLV_Core in DEV_SALES_SLV as its default lakehouse. After deployment to TST_SALES_GLD it must use LH_SALES_SLV_Core in TST_SALES_SLV. A default lakehouse in the notebook's own workspace is autobound; this one is in another layer's workspace, so you need a rule.

  1. Open the TST stage and select Deployment rules

    Use the stage you are deploying into, and be signed in as the notebook owner. Create the rule on TST, not on DEV.

  2. Select the notebook

    Only item types that support rules are listed. Use search if the list is long.

  3. Add a default lakehouse rule

    Open the Default lakehouse tile. In From pick the source-stage lakehouse. In To choose the target lakehouse from the list, Same with source lakehouse to keep the source setting, N/A to remove the default, or Other to enter it by hand.

  4. If you choose Other, provide the IDs

    The lakehouse ID is required, together with the lakehouse name and its workspace ID. If the list is empty even though the lakehouse exists, community reports describe selecting Other as the workaround.

  5. Save, then deploy the notebook

    The rule applies at the deployment. The notebook shows Different until you deploy.

  6. Verify

    Open the deployed notebook, check the attached lakehouse in the explorer pane, and run a cell that reads a table. Then repeat the rule on the PRD stage with the PRD values.

Scenario 2: re-pointing a semantic model

A semantic model SM_SALES_GLD in DEV reads WH_SALES_CNSM in DEV_SALES_CNSM_WH. In TST it must read the TST warehouse, and in PRD the PRD warehouse. What you can do depends on how the model reads its data.

Direct Lake models

A Direct Lake model does not autobind: after deployment it stays bound to the lakehouse or warehouse of the source stage. The choice of rule depends on the Direct Lake variant.

Model readsRule supportWhat to do
Import or DirectQuery over a warehouse or lakehouse SQL endpointData source ruleFollow the steps below.
Direct Lake on the SQL analytics endpointData source ruleFollow the steps below. The connection expression of the model must reference the SQL endpoint by ID for editing and refresh in the authoring tools.
Direct Lake on OneLakeNo data source ruleDrive the connection from Text parameters and use parameter rules, or rebind after each deployment, or release with a script.

Data source rule for a SQL-based model

  1. Open the TST stage and select Deployment rules

    Select the semantic model (you must own it) and expand Data source rules.

  2. Add a rule for the data source

    The list shows the data sources of the model as they exist in the source stage, as a server and a database. Pick the one to change.

  3. Choose Other and enter the TST values

    Server is the SQL connection string of the TST warehouse or lakehouse endpoint. Database must be in the same form the source shows: copy the form (GUID or name) that you see in the source value rather than guessing.

  4. Save, then deploy the model

    The rule is defined but applies only at the next deployment.

  5. Set credentials and refresh

    Data source credentials are not copied by a deployment. Set them on the TST model, make sure the identity the model uses can read the TST source, then refresh.

  6. Verify

    Open the model settings and read the data source, refresh once, and open a report that uses the model. Repeat on the PRD stage with the PRD values.

Verify against Microsoft Learn

Direct Lake rule behaviour is variant-specific: the Direct Lake overview lists deployment pipeline rules as supported for Direct Lake on SQL endpoints and not supported for Direct Lake on OneLake. The semantic link labs function is a community library, so confirm parameter names against the version you install, and confirm the parameterized-expression option on a test pipeline before you standardize on it.

Key takeaways

  • Rules exist for notebooks (default lakehouse), semantic models, Dataflow Gen1, paginated reports and mirrored databases only.
  • Create rules on the target stage as the item owner; they apply at the next deployment, so deploy, verify and keep the values recorded.
  • A default lakehouse in another workspace needs a rule; one in the same workspace is autobound.
  • Direct Lake on SQL endpoints supports a data source rule; Direct Lake on OneLake does not, so plan a parameter, a rebind or a scripted release.
  • Everything the rules do not cover, notably data pipelines, belongs in a variable library.
