Playbook 07 · Deployment Pipelines

Pipeline setup and pairing

A pipeline is quick to create and hard to change: the stage count and names are permanent, and pairing is created once. This page covers the setup steps, the two user interfaces, how items become paired and a corrected list of known issues.

Prerequisites

  • You have a Fabric license and are an admin of at least one workspace; that is what makes the Deployment pipelines entry point visible.
  • Every workspace you intend to assign resides on a Fabric capacity. Plan the capacity per environment before you create anything.
  • You are admin of each workspace you assign, and at least Contributor on the workspaces in the adjacent stages.
  • Workspace names follow the convention <ENV>_<DOMAIN>_<LAYER> so that a human can tell which workspace is which stage.
  • Items have identical names across the DEV, TST and PRD workspaces you will assign. Pairing depends on it (see Item pairing).

Who creates pipelines

Creating a pipeline needs a license that allows it (see the permissions table on Microsoft Learn), and pipeline permission is separate from workspace permission. In many organizations only a platform group creates pipelines and grants the pipeline admin role to the developers who deploy. That is a reasonable control, but it means pipeline creation is a request you must plan into the schedule.

Create the pipeline

  1. Open the creation dialog

    From the workspaces flyout choose Deployment pipelines, then Create pipeline (or + New pipeline). You can also create a pipeline from inside a workspace you administer; that workspace is then assigned automatically.

  2. Name it

    Use DPLY_<DOMAIN>_<LAYER>, for example DPLY_SALES_SLV, and add a purpose suffix only if you need two pipelines for one layer. Name and description can be edited later in the pipeline settings.

  3. Define the stages

    The dialog proposes Development, Test and Production. You can have 2 to 10 stages; add, delete or rename them before you confirm. The number of stages and their names are permanent, so decide now whether you need a UAT or staging stage.

  4. Create

    Select Create. The pipeline exists with empty stages.

Assign workspaces

  1. Pick the stage

    In an empty stage open Add content to this stage and choose the workspace. Only workspaces that meet the conditions in the prerequisites appear in the list.

  2. Assign

    Select Assign. Fabric scans the workspace and tries to pair its items with items in the adjacent stage.

  3. Repeat for each stage

    Assign DEV first, then TST and PRD. Because pairing happens at assignment, assign workspaces that already contain matching items before you deploy anything.

  4. Review the stage settings

    The last stage is public by default: a consumer without pipeline access sees it as a regular workspace without the stage tag. Change this with Make this stage public in the stage settings if needed.

Pre-create the TST and PRD workspaces, or let a deploy create them?

Deploying to an empty stage creates a new workspace on a capacity and makes the deploying user its only admin. Pre-creating and assigning workspaces instead lets you set the name, capacity, roles and Git or security settings first. Prefer pre-creation for a platform with a naming convention. Unassigning a workspace later discards that stage's deployment history and configured rules, so treat assignments as long-lived.

The original and the new UI

There are two interfaces for the same functionality. The new UI is the default and is in preview; a toggle in the upper right corner switches to the original UI, and your choice is remembered. Both support the same deployment rules, history and change review.

Training your team

Pick one UI for the runbook and teach it. When something looks wrong in one UI, switching to the other is a legitimate diagnostic step, and it is also the fallback this playbook recommends when a preview behaviour blocks a release. Document the UI you used in the deployment note so you can reproduce the steps.

Item pairing

Pairing is the stored link between an item in one stage and its counterpart in the adjacent stage. It decides whether a deployment overwrites an item or creates a second copy, and everything else (compare, autobinding, rules) builds on it.

How items become paired

MomentWhat happens
A workspace is assigned to a stageFabric pairs items of the same type and name in the adjacent stage. Folder location breaks ties only when a stage holds duplicates (same name and type). If one item per stage matches, they pair regardless of folder.
An unpaired item is deployed for the first time (a clean deploy)A copy is created in the target stage and paired with the source item.
A paired item is deployedThe target item is overwritten, including its name if the source was renamed.
An item is added to a workspace that is already assignedIt is not paired with an identical item in the adjacent stage. The next deploy creates a duplicate.

What this means in practice

  • There is no way to pair items manually. Pairing happens only through the two moments above, so align names and types before the first assignment or deploy.
  • A rename does not unpair. Paired items can carry different names, and a rename in the source is applied to the target on the next deploy. Do not rename items directly in TST or PRD.
  • Folders count as part of the name. Moving an item to another folder is a change that shows as Different; the next deploy moves the paired item and creates the folder if it does not exist. Folders are created or updated only as a side effect of deploying one of their items.
  • Duplicates block assignment. If an adjacent stage contains two items with the same type and name, Fabric cannot choose, and the workspace cannot be assigned until you rename one.
  • Same-looking but unpaired items are the usual cause of duplicates. Typical sources are a workspace built by hand and an environment populated by a different pipeline.

Verify pairing before the first real deployment

Open the content list of the target stage and confirm that every item you expect to be overwritten sits on the same row as its source item. Items on a row by themselves are unpaired. Fix names first; it is much cheaper than cleaning up duplicates.

Verify against Microsoft Learn

Preview behaviours move. Before you write a workaround into your runbook, check the lifecycle management troubleshooting article and the new UI overview for the status of the behaviour you are working around.

Key takeaways

  • Stage count and names are permanent; decide on UAT or staging stages before you click Create.
  • Pre-create and assign TST and PRD workspaces so you control names, capacity and roles; unassigning loses history and rules.
  • Pairing is by type and name (folder only breaks ties) and is created only at assignment or at a clean deploy. There is no manual pairing.
  • A disabled Deploy button is almost always a missing pipeline-admin or workspace-role grant, not a bug.
  • Use the UI toggle as a diagnostic, but confirm state through compare and deployment history.
