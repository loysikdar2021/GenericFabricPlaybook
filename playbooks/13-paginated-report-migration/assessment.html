Playbook 13 · Paginated Report Migration

Phase 1: Inventory and assessment

The inventory decides everything that follows: which method you use, how much rework you face, who has to sign off, and how big the target capacity needs to be. Build it from the platform's own metadata and from the RDL files themselves, not from memory.

What to record for each report

A spreadsheet is enough to start, but build the inventory with scripts so you can rerun it after every change. One row per report, with these columns:

ColumnWhy it mattersWhere it comes from
Name, workspace, report IDIdentity and traceability through the migration.Reports API
OwnerData source rules, credentials and take-over depend on the owning identity. The owner also signs off the result.Workspace settings and your own register
Data sources (type, server, database, gateway binding)Decides gateway work, per-environment rules and whether a source is supported at all.Report data sources API, RDL files
Datasets, parameters, stored proceduresShows complexity, timeouts and how much testing each report needs.RDL files
Subreports and drillthrough targetsReports that reference each other must move together and keep their links.RDL files
Custom code, assemblies, images, fonts, mapsThe features most likely to block a report.RDL files
Export formats and delivery (subscriptions, embedding)Defines what the parity test must cover.Owners, subscription settings, audit log
Usage (opens per period, peak times)Separates reports worth migrating from candidates for retirement, and sizes the capacity.Audit log, Fabric Capacity Metrics app
Business criticality and refresh dependenciesOrders the waves and sets the cutover window.Owners
Disposition and reasonThe output of this phase: migrate, modify, redesign or retire.Review with owners

Look for report families

Inventories often show groups of near-duplicates: a chart version, a summary version and a raw-data version of the same query. Decide up front whether to consolidate them. Every report you do not migrate is one fewer to test, convert and support.

Step 1: list the reports and their data sources

The Power BI REST API lists the items in a workspace, and the report type separates paginated reports from Power BI reports. For paginated reports, the Get Datasources In Group call returns each data source, its connection details and, if bound, the gateway it uses. A data source ID that is empty means the data source is not bound to a gateway. The notebook cell below builds the first version of the inventory.

import pandas as pd
import sempy.fabric as fabric

client = fabric.PowerBIRestClient()

# Legacy workspaces that hold paginated reports: friendly name -> workspace ID
LEGACY_WORKSPACES = {
    "LEGACY_SALES_PAGINATED": "<workspace-id>",
}

rows = []
for ws_name, ws_id in LEGACY_WORKSPACES.items():
    resp = client.get(f"/v1.0/myorg/groups/{ws_id}/reports")
    resp.raise_for_status()
    for rpt in resp.json()["value"]:
        if rpt.get("reportType") != "PaginatedReport":
            continue
        ds = client.get(f"/v1.0/myorg/groups/{ws_id}/reports/{rpt['id']}/datasources")
        sources = ds.json().get("value", []) if ds.ok else []
        rows.append({
            "workspace": ws_name,
            "workspace_id": ws_id,
            "report_id": rpt["id"],
            "report_name": rpt["name"],
            "data_source_count": len(sources),
            "source_types": ", ".join(sorted({s.get("datasourceType") or "" for s in sources})),
            "servers": ", ".join(sorted({(s.get("connectionDetails") or {}).get("server") or "" for s in sources})),
            "bound_to_gateway": any(s.get("gatewayId") for s in sources),
        })

inventory = pd.DataFrame(rows)
display(inventory)

For a tenant-wide view, the admin APIs list reports across workspaces, which helps when you do not know where every paginated report lives. Use them to find workspaces, then run the per-workspace calls above.

Verify against Microsoft Learn

Confirm the response fields in Reports - Get Reports In Group and Reports - Get Datasources In Group. The notebook client class and its method names belong to the semantic link library, which evolves; if your runtime differs, send the same requests with any HTTP client and a token for the Power BI API.

Step 2: export and parse the RDL

The API shows how reports are bound, not what is inside them. The RDL file is XML, so a short script can read every file and report the features that decide effort. First export the files; the Export Report In Group call returns the report definition for a paginated report.

import re
from pathlib import Path

export_dir = Path("/lakehouse/default/Files/rdl_export")   # needs a default lakehouse attached
export_dir.mkdir(parents=True, exist_ok=True)

for r in inventory.itertuples():
    resp = client.get(f"/v1.0/myorg/groups/{r.workspace_id}/reports/{r.report_id}/Export")
    if not resp.ok:
        print(f"Skipped {r.report_name}: HTTP {resp.status_code}")
        continue
    safe_name = re.sub(r"[^\w.-]+", "_", r.report_name)
    (export_dir / f"{safe_name}.rdl").write_bytes(resp.content)

Then parse each file. The cell below reads the XML with namespace wildcards, because the RDL namespace differs by schema version, and it deliberately does not store connection strings, which can contain credentials.

import xml.etree.ElementTree as ET

def analyse_rdl(path: Path) -> dict:
    root = ET.parse(path).getroot()
    raw = path.read_text(encoding="utf-8-sig", errors="ignore")

    def texts(xpath):
        return sorted({(e.text or "").strip() for e in root.iterfind(xpath)})

    def count(tag):
        return len(root.findall(f".//{{*}}{tag}"))

    providers = texts(".//{*}DataSource/{*}ConnectionProperties/{*}DataProvider")
    stored_procs = sum(
        1 for e in root.iterfind(".//{*}Query/{*}CommandType")
        if (e.text or "").strip() == "StoredProcedure"
    )
    info = {
        "report": path.stem,
        "providers": ", ".join(providers),
        "shared_data_sources": count("DataSourceReference"),
        "shared_datasets": count("SharedDataSet"),
        "datasets": count("DataSet"),
        "stored_procedures": stored_procs,
        "parameters": count("ReportParameter"),
        "subreports": count("Subreport"),
        "drillthrough_targets": ", ".join(texts(".//{*}Drillthrough/{*}ReportName")),
        "custom_assemblies": count("CodeModule") + count("Class"),
        "code_block": count("Code") > 0,
        "embedded_images": count("EmbeddedImage"),
        "maps": count("Map"),
        "fonts": ", ".join(texts(".//{*}FontFamily")),
        "uses_userid": "User!UserID" in raw,
        "uses_executiontime": "Globals!ExecutionTime" in raw,
    }
    flags = []
    if info["shared_data_sources"] or info["shared_datasets"]:
        flags.append("shared source or dataset")
    if info["custom_assemblies"]:
        flags.append("custom assembly")
    if info["maps"]:
        flags.append("map visual")
    if info["uses_userid"]:
        flags.append("UserID")
    if info["uses_executiontime"]:
        flags.append("ExecutionTime")
    info["flags"] = ", ".join(flags)
    return info

features = pd.DataFrame(analyse_rdl(p) for p in sorted(export_dir.glob("*.rdl")))
display(features)

Join the two tables on the report name and you have the working inventory. Add the owner, usage and criticality columns by hand or from the audit log, then keep the table: the validation phase reuses it as the test list.

Step 3: measure usage

Two sources tell you whether a report is worth moving. The audit log records report views for paginated reports, with a report type field that distinguishes them from Power BI reports, and the Fabric Capacity Metrics app shows what the paginated workload costs on your current capacity. Use the audit data to find reports nobody opens, and the capacity data, with peak render times, to size the target. Microsoft's guidance on retiring unused reports describes a repeatable cadence for the clean-up.

  • Peak concurrency. Paginated reports render on demand, so the hour when everyone runs month-end reports sets the load, not the daily average.
  • Heavy exports. Reports that routinely export very large Excel or PDF files cost more than reports that people only view.
  • Documented limits. The capacity planning article describes limits on concurrent renders for the paginated reports workload; requests over the limit fail with an HTTP 429 error. Check the current figure when you size.

Step 4: check the feature differences

These are the differences that most often change a report's disposition. Check each flagged report against this table.

Feature or behaviorIn the Power BI serviceAction
Shared data sources (.rds) and shared datasets (.rsd)Not supported. The RDL Migration Tool converts them to embedded data sources and datasets.Use embedded sources, cloud connections or shared Power BI semantic models.
Custom assemblies and DLL referencesNot supported. Code blocks and Azure Functions are supported.Move the logic into an embedded code block or a function.
Custom fontsNot supported.Switch to a font available in the service, then test PDF output.
Linked reportsThe paginated reports FAQ lists them as unsupported, while the migration guidance says they migrate and become regular reports.Treat each as an independent report and retest; do not depend on parent-child behavior.
User!UserIDReturns the user principal name, not a domain account name.Revise dataset filters and security tables, then test with real users.
Globals!ExecutionTimeReturns UTC.Convert in expressions, especially in parameter defaults and footers.
Date parametersFetched in US format (month, day, year) regardless of the design-time format.Test parameters with a non-US locale.
Query timeoutStored in the report; the default is 600 seconds and the maximum is 2147483646.Review long-running datasets and set the timeout explicitly.
Data source countAt most 250 per report; above that the report does not publish.Split extreme reports.

Report server items that do not migrateResources such as images, KPIs, mobile reports, report models and report parts.Embed images in the RDL; rebuild KPIs and mobile reports as Power BI reports.

Verify before you rely on these

These behaviors are stated in the paginated reports FAQ and the migration planning guide, and the two disagree on linked reports. Do not assume SSRS-style caching, snapshots or report history carry over: neither article describes them for the service, so test any report that depends on them.

Step 5: decide each report's fate

Apply the same four dispositions to every report and record the reason.

DispositionWhat it meansTypical examples
MigratePublish or reassign without changes to the layout.Reports on supported sources with embedded data sources.
ModifyEdit the RDL, then migrate.Reports with a custom assembly that fits a code block, a UserID filter to revise, a font to swap.
RedesignRebuild, usually as a Power BI report or against a different source.Spatial maps through a gateway, report models, mobile reports.
RetireDo not migrate; archive the RDL and tell the owner.Reports without views in the usage window; duplicates.

Group the migrating reports into waves by owner and criticality, and put reports that reference each other in the same wave. Take the data source list from this phase into the pipelines and gateways page to plan connections for each environment.

Key takeaways

  • Build the inventory from three sources: the reports API for bindings, the RDL for contents, the audit log for usage.
  • Parse every RDL file with a script and flag assemblies, shared sources, maps, UserID and ExecutionTime before anyone opens a report.
  • Retire first: reports nobody opens are the cheapest ones to migrate.
  • Never write connection strings to the inventory; record type, server and database only.
  • Keep the inventory table. It becomes the test list for validation.
