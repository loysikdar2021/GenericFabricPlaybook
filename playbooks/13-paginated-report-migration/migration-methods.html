Playbook 13 · Paginated Report Migration

Phase 2: Migration methods

There are two ways to put paginated reports on Fabric capacity. Reassigning moves the whole workspace in one step and is the simplest. Republishing moves reports one at a time and is the only way to change them on the way. A third route covers reports that still live on a report server.

Prepare the target capacity

Migration is not a tenant-wide switch. You move workspaces, one at a time or in waves, and the Premium capacity keeps serving everything you have not moved. That is what makes a pilot and a rollback possible, and it means both capacities run side by side until you finish.

  1. Buy the Fabric capacity first

    Create the F SKU capacity and add capacity administrators before you reassign anything. Keep the Premium capacity running until every workspace has moved and validated.

  2. Size it from the Premium capacity it replaces

    Use the table below as a starting point, then right-size with the Capacity Metrics app after the first waves.

  3. Choose a pilot workspace

    Pick a low-impact workspace with a handful of reports and an engaged owner. Use it to rehearse the steps, the validation and the rollback.

Method A: reassign the workspace

Choose this when the workspace should move as it stands. The paginated reports, their permissions and their settings stay in the workspace; only the capacity underneath changes.

Steps

  1. Announce a window

    Reassigning a workspace interrupts active queries and refreshes, and running jobs are cancelled when the move happens. Pick a quiet hour and tell the report owners.

  2. Reassign

    As a capacity administrator, open the admin portal, go to Capacity settings, open the Fabric capacity tab and select the target capacity. Choose Assign workspaces and select the specific workspaces to move.

    As a workspace administrator, open the workspace settings, go to License info (labelled Workspace type in some tenants), select Edit, choose Fabric capacity and pick the capacity from the list, then save. The assignment API requires the workspace admin role plus contributor permission on the capacity (or capacity admin), so plan who runs each wave.

  3. Confirm the assignment

    The workspace settings show the new capacity. Open the workspace as a member of the owning team to confirm the reports are listed.

  4. Run the post-move checks

    Open every report, check gateway bindings and credentials, run the scheduled refreshes of any semantic models the reports read, compare item counts with the inventory, and watch the Capacity Metrics app for one to two days.

  5. Hold the Premium capacity

    Do not cancel it until every workspace has moved and passed validation. While it exists, reassigning the workspace back is your rollback.

For many workspaces, script it. The Fabric REST API assigns a workspace to a capacity, and the Capacity Migration notebook in the semantic link labs library automates moving whole capacities.

$token       = "<token>"   # Microsoft Entra token for https://api.fabric.microsoft.com
$workspaceId = "<workspace-id>"
$body        = @{ capacityId = "<fabric-capacity-id>" } | ConvertTo-Json

Invoke-RestMethod -Method Post `
    -Uri "https://api.fabric.microsoft.com/v1/workspaces/$workspaceId/assignToCapacity" `
    -Headers @{ Authorization = "Bearer $token" } `
    -ContentType "application/json" `
    -Body $body

The call returns 202 Accepted: the assignment continues in the background, so confirm the capacity in the workspace settings before you start the checks. Service principals are supported identities for this call.

Verify against Microsoft Learn

Check the request shape and required permissions in Workspaces - Assign To Capacity, and the workspace and capacity roles in Manage your Fabric capacity. The label of the workspace setting differs between tenants and over time, so follow the text in the Learn how-to.

A Fabric workspace can hold more than reports

After reassignment, the workspace can also contain Fabric items. If you do not want that, check the tenant switches and workspace roles for creating them before you move, using Tenant settings.

Method B: republish the RDL files

Choose this when you want new workspaces, different data sources, edits to individual reports or promotion through a pipeline from the start. The goal is to move each paginated report from the legacy workspace into the development workspace of the new environment set, then promote it.

Steps in Report Builder

  1. Download the RDL

    Open the report in the legacy workspace, choose File and then Download report to save the RDL file. For many reports, use the export call in the assessment page instead.

  2. Open it in Power BI Report Builder

    Use an up-to-date version, and sign in to the service with your Microsoft Entra account so you can publish from the tool.

  3. Review the data sources

    Confirm that every data source and dataset is embedded in the report, and that each source is supported in the service. Update connection strings that must point at a different server or database, and re-authenticate where needed. Keep a static connection to the development source in the file; the pipeline rules on the next page swap it for each stage.

  4. Preview

    Run the report with realistic parameters and compare it with the original. Fix anything the assessment flagged.

  5. Publish

    Choose File, then Publish, then Power BI service, and select the development workspace. If the report uses a feature the service does not support, the save fails and the tool lists the reasons; revise the design and publish again.

  6. Set credentials and gateway

    In the service, open the report's menu, then Manage, and use Edit credentials and Manage connections and gateways to supply credentials and map each data source to a gateway or a cloud connection. See Gateways and connections.

Repeat for every report

The steps run once per RDL file. If a report fails to publish, revise the design as the tool instructs and publish again. In the service you can also upload a file with Upload and then Browse in the workspace, but the service uploads a single item at a time, so larger waves use the script below.

Scripted publishing with the REST API

The Power BI REST API imports an RDL file into a workspace. The call is asynchronous: it returns an import ID, and you poll until the import succeeds or fails. The nameConflict parameter decides what happens when a report with the same name already exists: Abort stops, Overwrite replaces.

import time
from pathlib import Path

import requests

TOKEN = "<token>"            # Microsoft Entra token for the Power BI API
BASE = "https://api.powerbi.com/v1.0/myorg"
HEADERS = {"Authorization": f"Bearer {TOKEN}"}
WORKSPACE_ID = "<target-workspace-id>"


def import_rdl(workspace_id: str, rdl_path: Path, conflict: str = "Abort") -> str:
    """Upload one RDL file and return the import ID."""
    params = {"datasetDisplayName": f"{rdl_path.stem}.rdl", "nameConflict": conflict}
    with rdl_path.open("rb") as handle:
        resp = requests.post(
            f"{BASE}/groups/{workspace_id}/imports",
            headers=HEADERS,
            params=params,
            files={"file": (rdl_path.name, handle, "application/octet-stream")},
            timeout=120,
        )
    resp.raise_for_status()
    return resp.json()["id"]


def wait_for_import(workspace_id: str, import_id: str, timeout_s: int = 300) -> dict:
    """Poll the import until it succeeds or fails."""
    deadline = time.time() + timeout_s
    while time.time() < deadline:
        resp = requests.get(f"{BASE}/groups/{workspace_id}/imports/{import_id}", headers=HEADERS, timeout=60)
        resp.raise_for_status()
        body = resp.json()
        if body.get("importState") in ("Succeeded", "Failed"):
            return body
        time.sleep(5)
    raise TimeoutError(f"Import {import_id} did not finish within {timeout_s} seconds")


for rdl in sorted(Path("rdl_ready").glob("*.rdl")):
    result = wait_for_import(WORKSPACE_ID, import_rdl(WORKSPACE_ID, rdl))
    reports = [r["id"] for r in result.get("reports", [])]
    print(f"{rdl.stem}: {result.get('importState')} {reports}")
  • Who owns the result. The identity that imports owns the report. If a service principal imports, run the take-over call so that a person or the service principal can own the data sources, otherwise the report can fail to render. See the scripting section.
  • Credentials still need setting. An import creates the report and its data source entries but not the credentials.
  • Keep the list. Save the output with the inventory so that each source report maps to its new report ID.

Verify against Microsoft Learn

Microsoft's documentation for the import call recommends a .NET client for RDL uploads. The multipart request above shows the pattern; confirm its parameters in Imports - Post Import In Group and test it on a scratch workspace before you run a wave. A Fabric REST item definition API for paginated reports may exist, but its payload was not verified for this playbook, so none is described here.

Reports on SSRS or Power BI Report Server

Reports that still live on a report server follow the same plan, with a different first mile. The server instances can run on premises or on virtual machines in a cloud. Discover them with a free inventory tool, then use the publishing route that fits the version.

SourceRouteWhat it does for you
Power BI Report Server and SQL Server Reporting Services 2022Built-in publish to the Power BI service, for all reports or a selectionPublishes from the server's own portal. An administrator controls the feature through server properties, including a limit on how many reports can be published at once.
Earlier SSRS versions (2012 to 2019)The RDL Migration Tool, an open-source tool from MicrosoftChecks for unsupported features, converts shared data sources and datasets to embedded ones, and publishes passing reports to a workspace. It does not change or remove the source reports.
Small numbers, or reports that need edits firstManual: download, open in Report Builder, publishSame steps as Method B.
Custom scale or logicPublic REST APIs of the report server and the Power BI serviceThe migration tool uses the same APIs; build your own tool only if you need different behavior.
  • Credentials and gateways are not migrated. The tool does not set gateway bindings or store credentials, so plan that work for every report.
  • Folders and permissions do not map one to one. Reproduce report server folders and security with workspaces, roles and apps rather than expecting a copy.
  • Shared semantic models can replace shared data sources. Consider them where several reports used one shared data source on the server.
  • Subscriptions. Report server subscriptions do not move. Recreate them in the service; data-driven subscriptions have no direct equivalent, so list them in the inventory early.

Verify against Microsoft Learn

The publish feature, its server properties and the tool's behavior are described in Publish .rdl files to Power BI and Use the RDL Migration Tool. Check them against your server version before you plan a wave.

Key takeaways

  • Buy the Fabric capacity first and keep the Premium capacity until validation ends; both methods depend on that overlap for rollback.
  • Reassign workspaces whose reports are clean; republish the reports that need change or a new environment layout.
  • Expect running queries and refreshes to be interrupted during a reassignment; schedule it.
  • The RDL carries layout and queries only. Credentials and gateway bindings are recreated in the service.
  • Script bulk publishing, but pilot it on a scratch workspace and verify the import call against Learn first.
