Playbook 13 · Paginated Report Migration

Risks, troubleshooting and checklist

Most paginated report migrations fail in the same handful of places: a feature the service does not support, a credential nobody recreated, a rule applied to the wrong stage, or a license assumption about viewers. This page lists the risks to manage up front, a fast way to localise a failure, and the checklist to run before each wave.

Risk register

RiskEarly signalMitigation
Viewers lose access because the target capacity is below F64Free-license users report that reports will not open after the moveSize at F64 or larger, or confirm that every viewer holds a Pro or Premium Per User license. Test with a free-license user in the pilot.
Unsupported features block publishingPublish fails with a list of reasons; the inventory flags assemblies, shared sources, fontsResolve in the assessment phase; decide modify or redesign per report.
Credentials and gateway bindings are missingReports open and then show a data source errorInclude credentials and binding in the per-report runbook; verify with the data sources API.
An environment reads the wrong dataNumbers in Test match Production, or Production shows test valuesAdd and verify a rule on each target stage; compare the data source on each stage after every deployment.
No hot-fix route in ProductionUrgent change requested and the report cannot be opened in Report Builder from ProductionAgree the change path in advance: fix in development, promote through the pipeline.
Ownership driftDeployments fail or reports lose data access after someone leavesUse one named deployment identity, and run take-over when a service principal imports.
Capacity contentionHTTP 429 errors, slow reports, slow items next to themMeasure peak concurrency; spread schedules; size with headroom; check the Capacity Metrics app after each wave.
Broken linksUsers report old bookmarks, app links or embedded views failingList every entry point in the inventory and update it in the cutover step.
Subscriptions silently droppedRecipients stop receiving scheduled reportsRecreate and test every subscription; keep a list of recipients and formats.
Data exposure through a stored credentialAll viewers see the same rows regardless of rolePrefer single sign-on where source security applies; use a dedicated service identity otherwise.
Locale and time differencesDates off by a day, footers at an unexpected time, user filters returning nothingReview the user ID, execution time and date parameter expressions found by the RDL scan.
Premium subscription lapses mid-migrationThe end date of the subscription is closer than the last wavePlan waves to finish early, and check the behavior of an ended subscription in the migration how-to.

Localise the failure

When a migrated report misbehaves, first decide at which step it fails. The step points at the cause far faster than the error text.

Symptom to fix

SymptomLikely causeFix
Publish from Report Builder is refused with a list of reasonsThe report uses a feature the service does not support: a custom assembly reference, shared data source or dataset, custom font, or too many data sourcesRevise the RDL: move logic into a code block, embed the sources, change the font, then publish again.
Report opens and shows a data source or credential errorCredentials not set, or the data source is not bound to a gateway or connectionUse Edit credentials and Manage connections and gateways. Call Get Datasources In Group and check that the gateway ID is filled in.
Binding to the gateway is not offeredThe server or database name does not match any gateway data source, or you lack rights on the gateway data sourceMatch the names exactly; ask a gateway admin to grant access.
Report renders for the author but not for viewersViewers lack permission at the source under single sign-on, or lack a license on a capacity below F64Test with a typical viewer; grant source access or a license.
Report imported by a service principal fails to renderData sources are owned by an identity that cannot run themCall Take Over In Group, then set credentials.
Rule exists but the report still reads the old sourceRules apply during the next deployment, or the rule was created in the wrong stageRedeploy into the stage that holds the rule; confirm the rule is on the target stage.
Deployment fails after a source changeThe data source changed in the source stage, so the rule is invalid; or a subreport or other dependency was not includedRecreate the rule; select related items when deploying.
The report cannot be opened in Report Builder from Test or ProductionA data source rule was applied thereEdit the development version and promote it; do not download from later stages.
Connection to a Fabric Warehouse failsSQL authentication used; database not named so the connection lands on a system database; port 1433 blocked; MARS requestedUse Microsoft Entra authentication; name the Warehouse as the database; open the port; remove MARS from the connection settings.
Stored procedure dataset fails on a Lakehouse SQL endpointThe stored procedure query type is not offered for that endpointSet the query type to Text and call the procedure with EXEC.
User-specific filters return nothingThe user ID built-in field returns a user principal name, not an account nameChange the filter table or expression to use the principal name.
Dates or footer times are offThe execution time field returns UTC; date parameters arrive in US formatConvert in the expression; test with non-US settings.
Map visual is blank through a gatewaySQL Server spatial types are not supported through the gatewayConvert the spatial data or redesign the visual.
HTTP 429 at busy timesConcurrent renders exceed the workload limitSpread subscriptions and exports; reduce parallelism; size the capacity up.
Query timeoutThe stored timeout (600 seconds by default) is shorter than the queryTune the query; raise the timeout in the dataset properties for known long runs.
Scheduled email never arrivesThe subscription was not recreated, or the attachment is too largeRecreate it; deliver large outputs to OneDrive or SharePoint instead.
Reassigning the workspace is refusedMissing workspace admin or capacity rights, or a region or tenant conditionCheck the roles required by the assignment and the conditions in the migration how-to.
Reports slowed or refreshes were cancelled during a reassignmentActive queries and jobs are interrupted when a workspace movesRerun after the move; schedule the next wave outside busy hours.

Migration readiness checklist

Before a wave

  • Inventory complete, with owner, sources, features, usage and disposition for each report.
  • Target capacity bought, sized and administered; sized at F64 or larger if free-license users view reports.
  • Pilot workspace migrated, validated and rolled back once as a rehearsal.
  • Gateway data sources exist per environment; the people who bind them have rights.
  • A deployment identity is chosen, licensed and able to read every source.
  • Owners know the freeze window and the rollback triggers.

For each report

  • Unsupported features resolved; the RDL publishes without errors.
  • Data sources are embedded, supported and named so that each can have its own rule.
  • Credentials set; gateway or connection bound; data source IDs confirmed through the API.
  • Parity tests pass for layout, data, parameters and every export format in use.
  • Subscriptions recreated and tested; links, apps and embedded views updated.

For each environment

  • Pipeline DPLY_SALES_DLV deploys development to test to production with the data source rules in place.
  • Each stage reads its own source, verified by opening a report and checking the data source.
  • Workspace roles match the plan; a typical viewer and a free-license viewer have been tested.

Cutover and retirement

  • Final validation passed and signed off by each owner.
  • Rollback route documented: assign back, or repoint links to the legacy workspace.
  • Hypercare period set, with a named person watching errors and capacity.
  • Legacy RDL files, inventory and test results archived in source control.
  • No workspace remains on the Premium capacity; its subscription is cancelled by a named person after the last wave.

Key takeaways

  • Most failures sit in four places: unsupported features, credentials and bindings, rules, and viewer licensing.
  • Localise by the failing step first; the step names the family of cause.
  • Rehearse the rollback in the pilot, not during the incident.
  • Treat the checklist as a gate for each wave, not a record written afterwards.
