Playbook 13 · Paginated Report Migration

Phase 3: Validation and cutover

A report that opens is not a report that matches. This phase proves parity with the original, recreates what the platform does not carry over, and ends in a cutover that you can undo until the day you retire the old capacity.

Validation strategy

Reuse the inventory from Phase 1 as the test list. Every migrating report gets a set of parameter values (typical, edge and empty), and every test compares the migrated report with the original under the same inputs. Business owners then confirm the result in user acceptance testing; the automated checks exist so that the owners spend their time on judgement, not on counting rows.

Paginated reports have no refresh to test

A paginated report does not store data, so there is no refresh schedule on the report itself. The queries run each time the report renders. What you can test is the refresh of any semantic model the report reads, and the subscriptions that deliver the report.

Automate parity checks

The REST API can render a paginated report to a file with given parameter values, which is exactly what a parity harness needs. The call is asynchronous: you start an export, poll its status and then fetch the file. Supported formats for paginated reports include PDF, accessible PDF, Excel, Word, PowerPoint, CSV, XML, MHTML and several image formats.

import io
import time

import pandas as pd
import requests
from pypdf import PdfReader      # %pip install pypdf

TOKEN = "<token>"           # Microsoft Entra token for the Power BI API
BASE = "https://api.powerbi.com/v1.0/myorg"
HEADERS = {"Authorization": f"Bearer {TOKEN}"}


def export_report(workspace_id: str, report_id: str, fmt: str, params: dict) -> bytes:
    """Render a paginated report to a file (fmt: 'PDF', 'CSV', 'XLSX', ...) and return its bytes."""
    body = {
        "format": fmt,
        "paginatedReportConfiguration": {
            "parameterValues": [{"name": k, "value": str(v)} for k, v in params.items()]
        },
    }
    start = requests.post(f"{BASE}/groups/{workspace_id}/reports/{report_id}/ExportTo",
                          headers=HEADERS, json=body, timeout=60)
    start.raise_for_status()
    export_id = start.json()["id"]

    while True:
        status = requests.get(f"{BASE}/groups/{workspace_id}/reports/{report_id}/exports/{export_id}",
                              headers=HEADERS, timeout=60).json()
        if status["status"] in ("Succeeded", "Failed"):
            break
        time.sleep(5)
    if status["status"] != "Succeeded":
        raise RuntimeError(f"Export failed for {report_id}")

    file_resp = requests.get(f"{BASE}/groups/{workspace_id}/reports/{report_id}/exports/{export_id}/file",
                             headers=HEADERS, timeout=300)
    file_resp.raise_for_status()
    return file_resp.content
def compare(old: tuple, new: tuple, params: dict) -> dict:
    """old and new are (workspace_id, report_id) pairs rendered with the same parameters."""
    old_csv = pd.read_csv(io.BytesIO(export_report(*old, "CSV", params)), encoding="utf-8-sig")
    new_csv = pd.read_csv(io.BytesIO(export_report(*new, "CSV", params)), encoding="utf-8-sig")

    same_columns = list(old_csv.columns) == list(new_csv.columns)
    same_rows = (
        same_columns
        and old_csv.sort_values(list(old_csv.columns)).reset_index(drop=True)
            .equals(new_csv.sort_values(list(new_csv.columns)).reset_index(drop=True))
    )

    old_pages = len(PdfReader(io.BytesIO(export_report(*old, "PDF", params))).pages)
    new_pages = len(PdfReader(io.BytesIO(export_report(*new, "PDF", params))).pages)

    return {
        "rows_old": len(old_csv), "rows_new": len(new_csv),
        "columns_match": same_columns, "data_match": same_rows,
        "pages_old": old_pages, "pages_new": new_pages,
        "pages_match": old_pages == new_pages,
    }


result = compare(
    old=("<legacy-workspace-id>", "<legacy-report-id>"),
    new=("<target-workspace-id>", "<migrated-report-id>"),
    params={"StartDate": "<start-date>", "EndDate": "<end-date>"},
)
print(result)
  • Reports that read a semantic model need an identity. The export call requires an identity in the paginated report configuration when the report uses a Power BI semantic model or an Azure Analysis Services source. See the API reference for the shape.
  • Compare content, not bytes. Exported PDFs carry timestamps and metadata, so compare page counts and extracted text, or render pages to images and compare them, rather than the file hash.
  • Mind the limits. The export-to-file article lists limits on concurrent exports and sizes. Pace a large run and write results to a table, so a rerun only repeats failures. A results model is described in QA validation frameworks.

Performance and capacity

Compare render times against the baseline you recorded before the move, then watch the capacity for a couple of days under real use. Adding the paginated reports workload to a capacity can slow paginated reports and everything else on it, so treat the target capacity as a shared resource and check both.

Subscriptions, delivery and links

Subscriptions are service settings, not part of the RDL, so they do not move with a report. Recreate each one and run it once.

  • Email subscriptions are supported for paginated reports, with the report attached in a chosen format. Large attachments are limited in size; for big outputs, deliver to OneDrive or SharePoint instead.
  • Per-recipient reports. The service supports subscriptions that vary the report by recipient, but there is no equivalent of SSRS data-driven subscriptions in the same form. Treat each as a redesign item from the assessment.
  • Time zones. The execution time built-in field returns UTC in the service, which can move the date shown in footers and defaults.
  • Links change with new items. Republishing creates a new report item with a new ID, so every saved URL, bookmark, app entry, embedded view and drillthrough link from a Power BI report must be updated. Drilling from a Power BI report to a paginated report works through URL parameters; check them for the new report.
  • Apps. Paginated reports can be added to Power BI apps; republish the app audience after the new reports exist. For app design see Organizational apps.

Permissions and licensing

  • Roles. Under Method A the workspace stays in place, so confirm its roles are intact. New workspaces from Method B start with only the roles you grant, so recreate them from the legacy workspace.
  • Viewers. Users with free licenses can view paginated reports only on a Fabric capacity of F64 or larger, or a Premium capacity of P1 or larger; otherwise they need a Pro or Premium Per User license. Confirm this with a free-license test user.
  • Data access. Test with a person who has only the access a typical viewer has. If the report uses single sign-on, that person's permissions at the source decide what they see.
  • Authors. Publishing to a workspace other than My workspace needs a Pro or Premium Per User license.

Cutover

Cutover is the moment users stop using the old reports. For a workspace reassignment, the move itself is the cutover. For republished reports, it is the day links and apps point at the new items. In both cases, keep the old state intact for a defined rollback window.

  1. Freeze changes

    Stop edits to legacy reports and to the sources they read, so the comparison stays valid.

  2. Run the final validation

    Repeat the parity tests on the frozen state and collect owner sign-off for every report in the wave.

  3. Switch

    Reassign the workspace (Method A), or update links, apps and embedded views to the new items and recreate subscriptions (Method B). Announce the switch with the support route.

  4. Hypercare

    Watch render errors, capacity metrics and support requests for an agreed period. Keep the legacy reports available but unadvertised.

  5. Close the rollback window

    When the period ends without an unresolved issue, record the decision and move to retirement.

Rollback triggerExample threshold to agree in advance
Wrong numbersAny report in the wave with an unexplained data difference
Access problemsUsers who should see a report cannot, and no fix is in hand
Render failuresFailure rate above the agreed limit, or repeated HTTP 429 errors
Capacity pressureOther workloads on the capacity affected beyond tolerance

Retire the old environment

  • Archive first. Export and store every legacy RDL file in source control before you delete a legacy workspace. Keep the inventory and the test results with it.
  • Check no workspace remains on the Premium capacity before you cancel it, and cancel the subscription only after the last wave has passed validation.
  • Do not let the subscription lapse first. Learn describes how a capacity behaves when its subscription ends: throttling and then rejected operations. A lapse before the last workspace has moved is an outage you caused.
  • Cancel in the licensing portal. Cancelling a Premium capacity is a manual step in the Microsoft 365 admin center, so assign it to a named person.
  • Update the runbooks. The support runbook should now describe the Fabric workspaces, the pipeline, the gateways and the rules created here.

Key takeaways

  • Test against the original under identical parameters: row counts, totals, page counts and every export format in use.
  • Automate the comparison with the export-to-file API and compare content, not file hashes.
  • Recreate what the file does not carry: subscriptions, links, roles, credentials and gateway bindings.
  • Agree rollback triggers before the switch, and keep the old state intact until hypercare ends.
  • Cancel the Premium subscription last, after the last workspace has moved and passed validation.
