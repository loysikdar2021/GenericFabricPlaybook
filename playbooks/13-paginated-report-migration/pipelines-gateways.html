Playbook 13 · Paginated Report Migration

Pipelines, gateways and sources

A migrated report is only as good as its connections. This page covers the three things that change per environment: which server and database each stage reads, which gateway or cloud connection carries the query, and which identity runs it.

Environment-specific sources with data source rules

The recommended Fabric-native approach keeps the RDL file untouched. The report is developed against the development source with a static connection, and the deployment pipeline carries a data source rule for each later stage. The rule tells the service to replace the server and database with the stage's own values during deployment. For general pipeline setup and promotion, see Deployment pipelines; this page covers what is specific to paginated reports.

Configure the rules

Paginated reports support data source rules only. Parameter rules and default lakehouse rules do not apply to them. A rule is created in the stage it applies to, never in the first stage.

  1. Create the pipeline and assign workspaces

    Create DPLY_SALES_DLV with development, test and production stages (the number and names of stages cannot be changed afterwards), and assign DEV_SALES_DLV to the first. Workspaces in a pipeline sit on Fabric capacity. You can assign existing workspaces to later stages or deploy to an empty stage and let the pipeline create the workspace.

  2. Deploy to Test

    Select the paginated reports in the development stage and deploy them to the test stage. Rules can only be defined once the items exist in the target stage.

  3. Open the rules pane

    On the test stage card, select the lightning bolt icon to open Deployment rules. The pane lists the items in the stage that support rules.

  4. Select the report

    Find the paginated report and expand it. Under Data source rules, select Add rule.

  5. Choose the data source

    From the data source list, pick the embedded data source to change. The name is the one defined inside the RDL file, and the list is built from the source stage.

  6. Enter the target values

    Enter the server and database for the test environment, for example the test Warehouse's SQL connection string and database name, then save. The new value must be of the same data source type as the original.

  7. Deploy again so the rule applies

    Rules are applied during deployment, so redeploy the report to the test stage. Open the report and confirm that it reads from the test source.

  8. Promote to Production

    Select the test stage as the source and deploy the reports to the production stage. Then open the rules pane on the production stage, add the production rule the same way, and deploy again.

Source and target direction

The promotion that creates production content always runs from the test stage to the production stage. Make sure the person running the deployment selects that direction, because a deployment can go to any adjacent stage in either direction.

Gateways and connections

Each data source in a published report needs a route to its data. For a source in the cloud, the report connects directly or through a shareable cloud connection. For a source on a private network, it goes through a gateway.

Gateway rules that catch migrations

  • Binding needs rights on both sides. The person who binds a report to a gateway needs permission on the gateway and on the data source in it. Plan who does this for each environment.
  • Names must match. The server and database in the report have to match the gateway data source exactly, including the form of the server name. A rule that changes the server also changes which gateway data source matches.
  • Separate data sources per environment. Create one gateway data source per environment, so test reports never reach production data.
  • Clusters. If the gateway is a cluster, the API uses the primary gateway's ID as the gateway ID.
  • Azure Analysis Services does not use a gateway from paginated reports; it connects directly.
  • Single sign-on to on-premises sources with Kerberos is configured on the gateway and the source, not in the report.
  • Stored procedures work through the gateway for SQL Server sources, with or without parameters.
  • Spatial data. A map visual that depends on SQL Server spatial types does not work through the gateway.

Which identity runs the query

The identity a report uses decides what data it can see, and security applied at the source (row-level rules, warehouse permissions) is applied to that identity. Choose it on purpose.

AuthenticationQueries run asSource-side securityUse when
Single sign-onEach viewerApplied per viewerThe source has per-user permissions and every viewer is meant to see only their rows.
Stored credential (for example OAuth2 or basic)The account that stored itEveryone sees what that account seesThe report shows the same data to its whole audience.
Shared cloud connectionThe connection's identityEveryone sees what that identity seesSeveral reports share one governed credential.

A stored credential exposes whatever its owner can read

If a person stores their own OAuth2 credential in a report, every viewer queries as that person. Use a dedicated service identity with the minimum access the report needs, not a person's account, and decide per report whether single sign-on is required. Check the supported authentication methods per source in Supported data sources for Power BI paginated reports.

Cloud connections

A shareable cloud connection holds a source and its credential once, and several reports and items can use it. A connection can be created by someone with the right workspace role and used by others who are granted permission on it. The connections that apply to a workspace's paginated reports are managed from the workspace's Manage experience; confirm the exact navigation and the permissions needed to create and use a connection in the paginated reports data sources article. Use them to avoid typing the same credential for every report in every stage.

Fabric Warehouse and Lakehouse SQL endpoints as sources

Many migrations repoint reports from an on-premises SQL Server to the Gold layer in Fabric. The report reaches a Warehouse or a Lakehouse SQL analytics endpoint over the same T-SQL connection that other tools use.

  1. Copy the connection string

    Open the Warehouse or SQL analytics endpoint in the Fabric portal and copy its SQL connection string. Use it as the server name. The string is unique to the item's workspace, so each environment has its own.

  2. Name the database

    Specify the Warehouse or endpoint name as the initial catalog or database. If you leave it out, the connection lands on a system database rather than your data.

  3. Use a supported identity

    Use Microsoft Entra authentication: a user or a service principal. SQL authentication is not supported, and neither is Multiple Active Result Sets.

  4. Keep port 1433 open

    The TDS endpoint listens on 1433, so a gateway or firewall in between must allow it.

  5. Test every dataset query

    The T-SQL surface of Fabric Warehouse differs from SQL Server. Run each dataset query in the Warehouse query editor and fix anything unsupported before you publish.

  6. Add the rule per stage

    Because each environment has its own SQL connection string, the rule changes the server and, if names differ, the database. The example table below shows the pattern.

StageServer (rule value)Database (rule value)
DEV<dev-sql-endpoint>.datawarehouse.fabric.microsoft.comWH_SALES_CNSM
TST<tst-sql-endpoint>.datawarehouse.fabric.microsoft.comWH_SALES_CNSM
PRD<prd-sql-endpoint>.datawarehouse.fabric.microsoft.comWH_SALES_CNSM
 
-- Same shape as the report dataset; @StartDate and @EndDate are report parameters.
SELECT  o.order_id,
        o.order_date,
        c.customer_name,
        o.order_total
FROM    gld.orders      AS o
JOIN    gld.customers   AS c ON c.customer_id = o.customer_id
WHERE   o.order_date BETWEEN @StartDate AND @EndDate
ORDER BY o.order_date, o.order_id;
  • Lakehouse SQL analytics endpoint and stored procedures. In Report Builder, the stored procedure query type is not offered for the Lakehouse SQL analytics endpoint. Set the query type to Text and call the procedure with EXEC.
  • Semantic models as sources. A report can read a Power BI or Direct Lake semantic model through its XMLA endpoint, using the workspace as the server and the model name as the database. Queries to semantic models carry a fixed timeout, so move heavy extracts to the SQL endpoint instead.
  • Security follows the identity. With single sign-on, a user's permissions on the Warehouse or the semantic model apply. See the table above before you choose between single sign-on and a stored credential.

Verify against Microsoft Learn

Connectivity rules for Warehouse and SQL endpoints change as the feature grows. Confirm authentication options, ports and the stored procedure behavior in Connectivity to data warehousing in Microsoft Fabric and in the Warehouse section of Supported data sources for Power BI paginated reports.

Script the post-publish steps

When you publish many reports, set sources and bindings with the REST API rather than by hand. Four calls cover it.

CallPurposeLimits
Get Datasources In GroupList a report's data sources, with data source and gateway IDs (empty when not bound).Paginated reports only.
Take Over In GroupTransfer ownership of the report's data sources to the caller.Paginated reports only.
Update Datasources In GroupChange the server and database of a data source.Caller must own the data source; old and new source need the same schema; the source type cannot change; ODBC is not supported.
Bind To Gateway In GroupBind named data sources to gateway data sources.On-premises data gateway only; use the primary gateway ID for a cluster.
 
import requests

TOKEN = "<token>"        # Microsoft Entra token for the Power BI API
BASE = "https://api.powerbi.com/v1.0/myorg"
HEADERS = {"Authorization": f"Bearer {TOKEN}", "Content-Type": "application/json"}


def post(path: str, body=None) -> None:
    resp = requests.post(f"{BASE}{path}", headers=HEADERS, json=body, timeout=60)
    resp.raise_for_status()


ws, rpt = "<workspace-id>", "<report-id>"

# 1. Take over the data sources so the caller owns them (paginated reports only)
post(f"/groups/{ws}/reports/{rpt}/Default.TakeOver")

# 2. Point the data source at the target environment (same schema, same source type)
post(f"/groups/{ws}/reports/{rpt}/Default.UpdateDatasources", {
    "updateDetails": [{
        "datasourceName": "SalesSource",
        "connectionDetails": {"server": "<server-name>", "database": "<database-name>"},
    }]
})

# 3. Bind the data source to a gateway data source (on-premises gateway only)
post(f"/groups/{ws}/reports/{rpt}/Default.BindToGateway", {
    "gatewayObjectId": "<gateway-id>",
    "bindDetails": [{
        "dataSourceName": "SalesSource",
        "dataSourceObjectId": "<gateway-data-source-id>",
    }],
})
  • Service principals need take-over. If a service principal imported or deployed the report, run the take-over call, otherwise the report can fail to render.
  • Check afterwards. Call Get Datasources In Group again and confirm the gateway ID and data source ID are filled in.
  • Credentials remain separate. These calls set the target and the binding; the credential is set through the gateway data source or a cloud connection.

Key takeaways

  • Keep the RDL pointing at development and let each pipeline stage carry its own data source rule.
  • Rules apply on the next deployment, belong to the item owner, and lock the report out of Report Builder in that stage: change in development, promote, never hot-fix in production.
  • Deploy with one stable identity; the deployer owns the report and needs the source credentials.
  • Gateways are not mapped by deployment. Create one gateway data source per environment and bind after the first deployment.
  • For Fabric Warehouse and SQL endpoints, use the item's SQL connection string with Microsoft Entra authentication and name the database.
  • Pick single sign-on or a service identity per report; never a person's stored credential.
