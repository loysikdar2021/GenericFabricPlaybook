Playbook 11 · Organizational Apps

Concepts and choosing an app model

Before you build anything, understand what an org app actually stores, why saved changes are live, and how access moves from the app to the items and models underneath it. Then use the decision table to check that an org app is the right distribution model at all.

Anatomy of an org app

An org app is a thin layer. It does not hold copies of reports or notebooks; it holds a structure, an appearance and a set of audiences, and it points at items that live in the same workspace.

Org app item
A Fabric item created with New > Org app. It carries the app's name, description, endorsement, icon, theme color and navigation behavior.
Elements
The ordered entries in the app navigation: an overview page (at most one per app), sections that group other elements, items that reference an included item, and links. The first element is the landing experience.
Included items
Power BI reports, paginated reports, Fabric notebooks, Real-Time Dashboards, Maps and Fabric Apps (preview) from the same workspace. They stay in the workspace as ordinary items; the app references them.
Audience
A child item of the org app that decides which elements a group of users sees, and by default which items they are granted access to. An app always has at least one audience, and audiences exist only in new org apps.
Definition
The app and each audience are stored as JSON definitions. When the workspace is connected to Git, they are committed alongside the items (see Git integration).

Two consequences follow from this structure. First, an org app can only package items from its own workspace; content in other workspaces reaches the app indirectly, as semantic models behind included reports. Second, audience visibility is not just a navigation filter: by default it also drives access, so showing an item can grant access and hiding it can revoke it (see Audiences for the exception).

Live references, not snapshots

A workspace app is a versioned copy: you edit content in the workspace, and consumers see nothing new until you select Update app. An org app has no such step. Included items remain the original items in the workspace, and after you select Save on the app, changes are immediately visible to the people who have access.

How access propagates

The access model is the main reason to use org apps, and also the main source of surprises. When a person is given access to an app, the platform grants, at a minimum, Read on:

  • the org app item itself;
  • each included Power BI report and paginated report, and the underlying semantic model of each, whether the model is in the same workspace or another one;
  • each included notebook, Map and Real-Time Dashboard;
  • each included Fabric App, where the grant is Read and Execute.

Revocation mirrors the grant, but only for access that came from the app. Anything the person received independently, for example a workspace role, a direct share of the report, or membership of another audience or app, stays in place.

Not everything is covered. The documentation names two dependency cases where the app does not propagate or revoke access: a Power BI report that contains a paginated report (RDL) visual depends on a paginated report item that the app does not grant, and a Fabric App's related items (the data it reads and writes) are not managed by the app. The propagation list also stops at items and semantic models; it does not mention the data stores behind them, such as an eventhouse behind a Real-Time Dashboard or a lakehouse behind a Direct Lake model. Treat those as your responsibility and test them (see Integrating Fabric and Power BI items).

Access drift

You can have the rights needed to grant access to a semantic model in another workspace at the moment you add a report, and lose them later. You may still be able to remove the report from the app or hide it, but the access records on the model can remain until someone with the right permissions removes them. If revocation seems incomplete, look at Manage permissions > Access via related items on the semantic model and involve its owner.

Migrating a workspace app to an org app

There is no migration tool and nothing converts automatically. Because audiences are available only in new org apps, you recreate the app rather than upgrade it. Plan it as a parallel run.

  1. Inventory the existing app

    List audiences, the Entra groups behind them, included content, links, sections, branding and whether the app is installed automatically. Flag dashboards and scorecards, which cannot be included in an org app, and report features you rely on, such as comments.

  2. Decide the target shape

    Decide whether each audience family becomes its own org app or whether one app with audiences is enough. Use the design guidance on Build and customize an org app.

  3. Create the org app and add content

    Recreate sections, the overview page and branding. Name the app for its audience, not for the workspace.

  4. Recreate audiences with the same groups

    Assign the same Entra groups so membership stays managed in one place, then test with accounts that belong to a single audience and to several.

  5. Run both in parallel

    Share the org app link and keep the workspace app available. They coexist, and the workspace app is unaffected.

  6. Cut over

    When users have moved, unpublish the workspace app. Users lose their personal bookmarks and comments on that app, so announce the cut-over first.

  7. Clean up access

    Updating a workspace app does not remove permissions that users already received. Review the Direct access tab on the semantic models and remove grants that only existed to support the old app.

Key takeaways

  • An org app stores structure, appearance and audiences; the items stay in the workspace and are referenced, not copied.
  • Saved changes are live. Staging has to come from separate workspaces and pipelines, not from the app.
  • Access follows the app for items and semantic models, and stops there: data stores behind items and some dependencies are yours to manage.
  • Use the decision table before you build: classic dashboards, external consumers, ISV distribution and custom logic each point somewhere else.
  • Migration is a rebuild plus a parallel run, followed by an access clean-up on the semantic models.
