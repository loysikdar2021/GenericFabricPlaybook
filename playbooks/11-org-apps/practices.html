Playbook 11 · Organizational Apps

Practices, pitfalls and roadmap

The practices that keep an org app estate manageable, an operating model with named owners, a symptom-to-fix table for the problems you will actually be asked about, and a method for tracking how the feature set changes, because in this area the documentation moves faster than any playbook.

Best practices

PracticeWhy it mattersHow
Isolate development from productionSaved changes to a report are live in every app that includes itSeparate DEV_, TST_ and PRD_ workspaces and a deployment pipeline; no direct edits in production (ALM)
Design for the audienceOne monolithic app forces everyone through content that is not theirsSeveral small apps from one workspace, or one app with audiences; sections, an overview page and consumer-readable names
Give each app an ownerAn app is a product with users, a backlog and a lifecycle, not a folderName an owner, keep release notes and a feedback channel, and review usage with the audience
Grant through groupsMembership in one place keeps audits and revocation tractableOne Entra group per audience per environment; named group owners; reshare limited to those owners
Own the data-layer decisionThe app grants item and model access, not the data behind itDecide Direct Lake identity and Real-Time Dashboard identity per item and record the decision (Integrating items)
Keep apps smallLong navigation lists hide content and slow down reviewAs a rule of thumb, aim for a dozen elements or fewer per audience view; split an app when sections stop fitting on one screen
Test with real accountsPreview shows a workspace-role view and workspace roles bypass model securityOne test account per audience and one free-licensed account with no role, using the gates in QA Validation Frameworks
Review access on a scheduleReshare, direct shares and access drift accumulateReview Manage access, reshare holders and each model's Access via related items on a regular cadence

The product mindset changes the job. A BI developer who maintains an org app decides what goes in, what stays out, how it is named and when it changes, which is closer to a product manager's role than to a report builder's. Make that explicit in role descriptions, because the platform will not do it for you.

SupportAccess requests and the troubleshooting table below

Say how to ask for access

The org app article does not describe a custom access-request message like the one workspace apps offer. Put a "how to get access" paragraph and the group owner's name in the overview page header or the app description so a person without access finds the answer.

Troubleshooting: symptom, cause, fix

SymptomLikely causeFix
No Org app entry under NewThe org app tenant setting is off for the user, the workspace type is unsupported, or the user is a ViewerCheck the setting and its group scope, the workspace type and the role (Prerequisites)
Save fails with a permissions messageMissing write and reshare on the app, an included item or a semantic model, including a model in another workspaceHave a Member or Admin save, or have the item owner grant the rights; check the owner of the cross-workspace model
A report opens but shows no data or an access errorRead on the model was granted but the data layer was not (Direct Lake with single sign-on), or the model is in another workspace and the author lacked reshareConfirm the identity mode and grant the data-layer rights, or bind a fixed identity; fix reshare rights and re-save
Real-Time Dashboard tiles are empty for consumersPass-through identity and the viewer has no access to the KQL database, or the editor's connection is invalidGrant database access, or switch to the editor's identity and repair the connection
A visual inside a report is blankThe report embeds a paginated report visual and the paginated report item was not grantedInclude the paginated report in the app or grant access to it
A notebook cannot be runOrg apps present notebooks read-only and grant Read onlyExpected behavior; share a separate item if users must run code
The app is missing from My apps on HomeMy apps does not list org appsUse the Apps page, Home Recent or Favorites, or the OneLake catalog
No audience tabs appearThe user belongs to one audience, tabs are hidden in Customize, or the user is on mobileExpected in those cases; adjust Customize if tabs should show
A hidden item is still reachableAccess to hidden content is on for an audience, or a direct link works because the user has app accessTurn the setting off and rely on groups and visibility for separation
A removed user still sees contentAccess came from a workspace role, a direct share, another audience or app, or the data storeWork through the list in Revoking access
Cannot create or rename an audienceThe name collides with an existing audience name, or the name of a deleted audience, in the workspaceChoose a unique name
Deploying to production creates a second appThe stages were not paired and an app with the same name was created by handPair the stages before deploying; delete the hand-made copy
The release job cannot deploy the appOrg apps cannot be deployed across stages with service principalsPromote the app as a user-context step with an approval
Subscription emails link to the report, not the appSubscriptions are tied to the underlying reportExpected; point users to the app link for navigation

Tracking capability changes

Org apps have changed quickly and will keep changing. Statements about what is "coming" age badly and should not drive design. Some capabilities that were once described as upcoming, audiences and paginated report support among them, are now documented in the product articles, while others still carry limitations, such as audience tabs on mobile. The durable skill is not memorizing a feature list; it is having a cheap way to re-check it.

Keep a short capability register: every capability a design depends on, the article that documents it, what you tested and who re-tests it. When something in the register changes, the decision that depended on it is reopened.

Verify against Microsoft Learn

Before each major rollout, re-read the considerations and limitations section of Get started with org apps, the CI/CD for org apps limitations, and the preview labels in the Git and deployment pipeline supported-items lists. Do not tell stakeholders a capability is coming unless it is already documented as available in your tenant.

Final checklist

Before you build

  • An org app is the right model for this audience (decision table in Concepts).
  • Tenant setting, capacity, workspace type, roles and licenses pass the pre-flight checklist and a smoke test.
  • Audiences, Entra groups and group owners are defined for each environment.
  • The workspace layout separates development, test and production, with a pipeline planned.

Before the first share

  • Navigation labels, overview page, icon and theme are reviewed; contrast is checked.
  • Every item opens for an account in each audience, including models in other workspaces.
  • Direct Lake identity and Real-Time Dashboard identity are decided and tested.
  • Notebook outputs and links are reviewed for sensitive content.
  • Access to hidden content is off unless a documented decision says otherwise.

Before each promotion

  • The definition diff was reviewed, including hasAccessToHiddenContent and audience references.
  • The app and its included items deploy in the same run, under a user account with the needed rights.
  • Audience membership is assigned and verified in the target stage.
  • A rollback is possible from Git or the previous stage.

In operation

  • Manage access, reshare holders and models' Access via related items are reviewed on a schedule.
  • The capability register is re-checked on a regular cadence and after announcements.
  • There is a documented retirement path: capture the definition, withdraw access, delete, clean up.

Key takeaways

  • Run each org app as a product: an owner, a release path, group-based access and scheduled reviews.
  • Most support tickets trace back to the data layer, a missing reshare right or access that came from outside the app; the troubleshooting table covers them.
  • Do not design around announced features; keep a capability register and a re-check loop.
  • Consumers reach the app through the Apps page, Home, the OneLake catalog and Teams; not through My apps.
