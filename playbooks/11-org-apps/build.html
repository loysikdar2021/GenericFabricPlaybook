Playbook 11 · Organizational Apps

Build and customize an org app

An org app is a curated, branded data product, not a shared folder. This page starts with the design questions that decide what goes in, then walks through creation, content, navigation, the overview page, branding, preview and save, and ends with a table of what takes effect when.

Design the app before you build it

Because one workspace can host many apps, the useful question is no longer "which reports should we share?" but "which experience does this audience need?" Answer these first; they decide the items, the audiences and the roles.

QuestionWhy it mattersExample answer
Who is the audience and what decision do they make?Defines the audience and keeps the app smallExecutives running a weekly revenue review
Which items answer that decision, and which only support it?Separates primary content from context such as method notesRevenue report first, methodology notebook last
What must each audience not see?Visibility drives access, so hiding an item can remove access to itAnalysts do not get the live store dashboard
Who owns the app, and who may change access?Changing access needs write and reshare on items and modelsThe sales analytics lead as Member; developers as Contributors
What will consumers call it?The app name appears on the Apps page and in Home lists"Sales performance", not a technical identifier
Where does it live, and how does it change?Live references make environments part of the designBuilt in a development workspace, promoted by a pipeline

A single workspace with a dozen items can feed a short "Executive" app with three reports and a separate "Regional operations" app with many reports grouped by territory, a live dashboard and a method notebook. That is the shift from sharing reports to building a targeted experience, and it makes the BI developer the product owner for the app.

Name for the consumer, not for the engineer

The name you type when you create the app is the name consumers see. The house convention (RPT_SALES_CNSM_Revenue and similar) is for items and workspaces; do not apply a technical prefix to the app itself. Because environments are separated by workspace (DEV_SALES_CNSM, TST_SALES_CNSM, PRD_SALES_CNSM), the app can keep the same display name in every stage. You can rename each navigation element, so technical item names never have to appear in the navigation.

The build flow

Step by step

  1. Create the item

    Open the workspace that holds the content and select New > Org app. Enter the consumer-facing name and select Create. The app editor opens. If your tenant has Fabric trials enabled and the workspace is not on a capacity, you are prompted to start a trial.

  2. Add content

    Select Add content, choose items from the workspace in the picker, and select Add to app. Only supported item types appear (see Integrating Fabric and Power BI items). If the app has audiences, a new item is visible to the single audience by default; with several audiences you are asked where it should be visible.

  3. Arrange the navigation

    Use Add > Section to group elements, ... > Move to section to file them, ... > Rename to give business-readable labels, and Move up or Move down to order them. The first element is the landing experience.

  4. Add an overview page and links

    Use Add > Overview for a page that lists everything in the app (one per app), then Add header to set a title, body text and whether the header uses the theme color. Use Add > Link for external or internal URLs such as a data dictionary.

  5. Set the item's settings

    In Settings, open About to set the name and description (and see the owner, creator and last modified time) and Endorsement to set the endorsement level. The level you set applies to the app item, not to the items inside it.

  6. Customize the look

    In Customize > Branding, upload an app image and choose a theme color, then select Apply. Set navigation behavior and, if you use audiences, the audience tab display.

  7. Preview and save

    Select Preview app to see the experience, then Close preview and Save. The confirmation offers View app and a way to manage access.

  8. Share

    Saving persists the definition but does not by itself give anyone access. Share the app through audiences and groups as described in Access, ALM and lifecycle.

Navigation, overview page and links

A flat list of fifteen reports is not an app. Group elements into sections that match how the audience thinks, put the page they need first, and give each element a name they would use in conversation.

Sales performance - Regional operations
├─ Overview                       landing page, header with title and welcome text
├─ Section: Regions
│  ├─ North region                -> report RPT_SALES_CNSM_RegionNorth
│  ├─ South region                -> report RPT_SALES_CNSM_RegionSouth
│  └─ ...
├─ Section: Live operations
│  └─ Store traffic               -> Real-Time Dashboard RTD_SALES_CNSM_StoreTraffic
└─ Section: Method and definitions
   ├─ How sales are calculated    -> notebook NB_SALES_CNSM_Methodology
   └─ Data dictionary             -> link
  • Landing page. Whatever is first in the navigation opens first. If you add an overview page, put it first when you want a welcome and an index; otherwise put the report that answers the audience's main question first.
  • One overview. An app can have only one overview page. In a view for one audience it lists only the content that audience can access; in the All tab it lists everything the user can access across audiences.
  • Sections. Keep one level of sections. Deeply nested navigation hides content and is harder to maintain in the definition file.
  • Links. The definition distinguishes links that open embedded in the app from links that open in a new tab. Use a new tab for anything that is not designed to be framed.
  • Rename, do not expose. Rename elements to business terms; a consumer should not need to know that a report is called RPT_SALES_CNSM_RegionNorth.

Branding and behavior

The Customize pane controls the visual identity and how the navigation behaves.

App image
Upload a .jpg or .png of up to 45 KB. Reset to default removes it. On the previous Apps page, Gallery view shows the default org app icon rather than the custom one.
Theme color
Pick any color with the color picker or enter a hexadecimal or RGB value. The definition stores a small palette: background, foreground and hover, selected and pressed backgrounds.
Preview of the look
A sneak-peek pane shows the effect as you choose. Select Apply before closing; nothing is visible to consumers until you save the app.
Navigation behavior
Options let you hide or collapse the app navigation pane, show report page navigation independently or combined with the app navigation, and hide the report page pane. The definition properties are navigationPane.isHidden, navigationPane.isCollapsed, independentPageNavigation and itemTypeSettings.report.hidePagePane.
Audience tabs
Show or hide the All tab and the audience tabs (hideAllTab, hideAudienceTabs in the audience settings).

Pick contrast, not just a color

The theme color drives the navigation background, so check that the foreground text reaches at least a 4.5:1 contrast ratio against it in the normal, hover, selected and pressed states. Teams tend to approve the logo color and discover the hover state is unreadable only after release.

Verify against Microsoft Learn

The portal labels for the navigation options are not spelled out in the Get started article; the property names above come from the definition documented in CI/CD for org apps in Fabric. If you script or review definition files, match properties to the schema version your tenant writes.

Preview, save and what takes effect when

Preview app shows the app as a consumer would see it, but it is rendered for users who have workspace access, so it reflects the broader access that a workspace role gives, across all audiences. It is a layout check, not an access test. Row-level security is not a good test here either, because workspace Admins, Members and Contributors hold write permission on the models, and write permission bypasses model-level data access rules.

Save persists the app's definition. If the save includes access-affecting changes (added or removed items, audience visibility) and you lack write and reshare on the items or their semantic models, the save fails with a permissions message; see the write-and-reshare rule.

ChangeWhere you make itTakes effect
Name, description, endorsementSettings > About or EndorsementImmediately
App image and theme colorCustomize > Branding, then ApplyWhen you save the app
Add, remove, rename or reorder elements; overview; linksApp editorWhen you save the app
Audience visibility and accessManage audiences, ShareWith the save or share action; confirm behavior in a test workspace
Edits to an included report or notebookThe item itselfWhen that item is saved, with no app step

Quality bar before you share

  • The app name and every navigation label make sense to the audience without explanation.
  • The landing element answers the audience's main question or explains what the app contains.
  • The icon is under 45 KB and the theme passes a contrast check in all four states.
  • Each audience has been tested with an account that belongs to that audience only, not with a workspace Admin.
  • Every report in the app opens for a test consumer, including reports whose models live in other workspaces.
  • Notebooks and dashboards in the app contain nothing you would not want every consumer to read (see notebook outputs).
  • The app has a named owner, a place to ask questions, and a rollback plan (ALM).

Anti-patterns

  • One app for everyone. It forces every audience through content that is not theirs; use audiences or separate apps.
  • Technical names in the navigation. Consumers search by business terms.
  • Building in the production workspace. Every save is live.
  • Treating Preview as the test. It shows the workspace-role view.
  • Hiding as security. Hidden elements are not protected from someone with a direct link when access to hidden content is on.

Key takeaways

  • Design per audience first; the app name and navigation labels are consumer-facing and should read like business terms.
  • Adding items and saving are the moments that change access, so those need write and reshare rights.
  • Settings changes are instant, branding and structure take effect on Save, and item edits are live when the item is saved.
  • Preview is a layout check performed with a workspace-role view; test each audience with its own account.
  • Keep one level of sections, one overview, and a deliberate landing element.
