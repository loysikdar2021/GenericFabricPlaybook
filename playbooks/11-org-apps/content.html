Integrating Fabric and Power BI items

An org app is only as useful as the items you can put in it and only as safe as your understanding of what each item type does to access. This page covers every supported item type, what consumers experience, what the app grants automatically, and what you still have to grant yourself.

What you can include

Items come from the app's own workspace and are picked with Add content. The documentation lists Power BI reports, paginated reports, Fabric notebooks, Real-Time Dashboards, Maps and Fabric Apps (preview), plus navigation elements you add yourself: overview, sections and links.

Classic dashboards and scorecards are not eligible items. Plan around that if your current workspace app leans on them.

Power BI reports and their models

Reports are the common case and the simplest: add them from the picker. When a user is given access to the app, the platform grants Read on the report and on the semantic model behind it. The part that used to be painful is cross-workspace models. If a report in workspace A is built on a model in workspace B, sharing the app from workspace A grants the user access to the model in B, provided the app's author has the right to reshare that model.

Read on the model is not read on the data

Item permissions and data permissions are different layers. The app grants the first. Whether a consumer can actually query the data depends on how the model connects to its source.

Direct Lake models: what consumers need

A common assumption is that consumers always need ReadData on the lakehouse. That is only one of several cases. The identity the model uses to read the data decides what consumers need, and Direct Lake uses single sign-on (the consumer's identity) by default.

Direct Lake configurationIdentity usedWhat a consumer needs beyond the app's grants
On SQL analytics endpoint, single sign-on (default)The consumerRead on the lakehouse or warehouse item and SELECT on the tables through the SQL analytics endpoint; no direct OneLake read is required
On OneLake, single sign-on, OneLake security offThe consumerRead and ReadAll on the Fabric item; workspace Contributors and above have them, Viewers do not
On OneLake, single sign-on, OneLake security onThe consumerMembership in a OneLake security role that grants read; object-level and row-level rules are enforced per user
Either mode, fixed identity (single sign-on disabled on the cloud connection)The connection's identityNothing at the data layer; grant the fixed identity Read and SELECT (or ReadAll) and do not give consumers permissions on the source item

For a broad internal audience that should see curated data only, the fixed-identity pattern with row-level security in the model is usually the cleanest: consumers hold Read on the app, report and model, and nothing on the lakehouse. For audiences who already have governed access to the lakehouse, single sign-on keeps the source in charge. Whichever you choose, the semantic model owner needs read access to the source tables so the model can be framed during refresh.

Row-level security needs Read-only users

Model-level data access rules apply to users with Read, which is what app consumers hold. They are not enforced for users with Write permission, which includes workspace Admins, Members and Contributors. Test security with accounts that match your consumers, not with your own.

Chained and composite models, and the paginated visual exception

  • Chained models. The documentation describes propagation to the semantic model behind each included report. If a model is itself built on other models, treat the upstream models as dependencies, grant or verify access to them explicitly, and test with a consumer account.
  • Reports that embed a paginated report visual. The report depends on a paginated report item that the app does not grant. Include the paginated report in the app, or grant access to it separately.
  • Standards. Report design, naming and testing standards live in Power BI Report Development Standards.

Paginated reports

Paginated reports are the pixel-perfect output for statements, order confirmations and other operational documents. You build them with Power BI Report Builder, typically against a semantic model or a lakehouse SQL analytics endpoint. They are a supported item type in an org app: they appear in the item picker, and access to the report grants access to its semantic model automatically, which workspace apps did not do.

  • Subscriptions. Email subscriptions from within an org app are supported for Power BI reports only, not for paginated reports.
  • Source-controlled and deployable. The Git and deployment-pipeline lists carry a preview label for paginated reports; confirm before you rely on them in a release process (ALM).
  • Direct connections. When a paginated report connects straight to a SQL analytics endpoint instead of a semantic model, there is no model for the app to grant, and the identity and permissions of that connection are your responsibility. Test it with a consumer account.
  • Migration. Moving paginated reports into Fabric is covered in Paginated Report Migration.

Verify against Microsoft Learn

You may still find older guidance that says paginated reports are not a supported item type and calls support a roadmap item. The org app article lists paginated reports as an included item. Re-read the Get started article before you decide, and check the capacity requirements for paginated reports separately.

Notebooks

A notebook in an app is a document: markdown, code, tables, charts and widgets that explain a method or tell a story next to a report. Consumers see it in a read-only mode. Interactive outputs such as rich dataframe previews, built-in charts and outputs from libraries like Plotly remain interactive, but anything a consumer changes is not saved and resets when the page is refreshed.

  • Read, not run. The documentation lists Read access for included notebooks. Running a notebook needs execute permission, which the app does not grant, so design for a read-only experience.
  • What is saved is what is shown. Consumers see the notebook as it was saved, with its saved cell outputs. Treat it like a published document: re-run and save it deliberately, and test how outputs look to a consumer after a change.
  • Outputs are a data surface. Anyone with Read can see tables and charts in saved outputs. Clear outputs that contain sensitive rows, keep secrets and connection strings out of cells and outputs, and review the tenant setting that lets users with read or write permission download data from notebook outputs.
  • Write for readers. Lead with a markdown summary, hide setup cells, keep outputs small, and do not rely on parameters or widgets that need a running session.

Verify against Microsoft Learn

How to integrate notebooks with Org app still shows a preview banner, while the main org app article lists notebooks as an included item without a preview label. Check both before you commit a design to notebook-based storytelling.

Real-Time Dashboards

A Real-Time Dashboard turns streaming or near-real-time data into KQL-driven tiles, typically over a KQL database in an eventhouse fed by an eventstream. In an app it lets one navigation hold both strategic analysis (reports) and operational monitoring (live tiles) for use cases such as store traffic, device telemetry or site activity.

Prerequisites: a workspace on a Fabric-enabled capacity, a KQL database with data, and a dashboard whose data sources are reusable references to databases in the same workspace. Create the dashboard from New item > Real-Time Dashboard, add a data source, then add tiles by KQL query or with Copilot, and use parameters so filters reach the query early.

Verify against Microsoft Learn

Learn tutorials say a tenant administrator must enable creation of Real-Time Dashboards, but the exact setting name is not confirmed in the tenant settings reference and the creation article lists no tenant prerequisite. Look for the setting in your admin portal and check the Create a Real-Time Dashboard article.

Who the dashboard queries as

The app grants Read on the dashboard item. Whether tiles show data depends on a separate setting: the identity model for the data source.

Dashboard permissionData source modelResult for a viewer
ViewPass-through identityOpens the dashboard; sees data only with their own access to the source
ViewDashboard editor's identitySees the data through the editor's connection and cannot edit
EditPass-through identityCan edit; sees tile data only with source access
EditDashboard editor's identityCan view and edit
  • Choose pass-through when the source system should enforce access and consumers already hold it. The app alone will not give them that access.
  • Choose the editor's identity when consumers should get insight without raw access and you want one consistent view. Each editor who changes the dashboard must set up their own cloud connection, and when no valid connection exists viewers see data only with their own access, so treat the connection as an operational dependency with a named owner.
  • Mind the load. Live refresh keeps queries running while the dashboard is open. Set a sensible refresh rate limit, push filters into parameters and base queries, and watch eventhouse load as the audience grows.

Maps

A Fabric map is an item that visualizes real-time event data from an eventhouse and historical or static spatial data from a lakehouse as layers. In an app it gives an operations audience geographic context next to reports. The app grants Read on the map item; viewers also need access to the data sources behind its layers, so apply the same reasoning as for Real-Time Dashboards and test with a consumer account. Check the Learn article for the current status of the Maps workload.

Fabric Apps (preview)

A Fabric App is a different artifact from an org app: a hosted application with a data model defined in TypeScript, a generated GraphQL API and authentication through Fabric single sign-on. You can include one in an org app so it sits in the same navigation as your reports.

  • Adding a user to the org app grants Read and Execute on the Fabric App and removing the user revokes them.
  • The app does not manage access to the Fabric App's related items, the databases it reads or writes. A recipient may be able to open the app and still fail when it touches data, so grant those items directly.
  • Creating Fabric Apps needs a Fabric capacity workspace, a tenant setting (labeled slightly differently on two Learn pages) and a supported region.
  • Preview status means you should plan for change, and own the code and the secrets hygiene in it.

Access you must still verify

  • Every Direct Lake model has a documented identity mode, and consumers hold exactly the data-layer rights that mode requires.
  • Every Real-Time Dashboard and map has a decided identity model and a named owner for any cloud connection it uses.
  • Reports that contain a paginated report visual have the paginated report included or separately granted.
  • Fabric Apps have their related items granted directly.
  • Notebook outputs have been reviewed for sensitive rows, and the notebook download setting is as intended.
  • One account per audience has opened every item in a test run, including items backed by models in other workspaces.

Key takeaways

  • Org apps can include paginated reports, notebooks, Real-Time Dashboards, Maps and Fabric Apps (preview) alongside reports; classic dashboards and scorecards are not eligible.
  • The app grants Read on items and on the semantic models behind reports and paginated reports. It does not grant the data layer behind them.
  • For Direct Lake, decide single sign-on versus a fixed identity per model and grant accordingly; "ReadData on the lakehouse" is only one case.
  • For Real-Time Dashboards, choose pass-through or the editor's identity on purpose; the dashboard grant alone does not show data.
  • Notebooks are read-only documents whose saved outputs everyone with access can see.
