Playbook 11 · Organizational Apps

Access, ALM and lifecycle

Once an app is built, three things decide whether it stays trustworthy: who has access and why, how changes are reviewed and promoted, and how the app is retired. This page covers sharing and audiences, Git integration and deployment pipelines, and the draft-to-deleted lifecycle.

Sharing and managing access

Sharing an org app is item sharing with a propagation layer on top. After you save the app, the Share button gives you four options.

OptionWhat it doesUse it for
Copy link to this appCopies the app link; the recipient lands on the first element. Recipients must already have access.Telling existing users where the app is
Link to this app pageCopies a link to the element you are viewing, with the same access requirementPointing someone at one report in the app
Add person or groupOpens a modal to select audiences for the recipients, optionally grant reshare permission, and notify them by email with a messageGranting access to people without leaving the app
Manage accessOpens the full access page with the Direct access tab and an Add user buttonReviewing, adding and removing access across audiences

You can reach the same page from the workspace with ... > Manage permissions. When the app has audiences, sharing is audience-aware: org-app-level sharing lets you pick which audiences receive the recipients, and sharing from an audience's own child item is scoped to that one audience.

Sending someone a link does not give them access. Share the item first, then send the link, or use the modal so the notification email carries both.

Reshare permission

When you add a person, you can also grant reshare permission for the audiences you select, which lets them pass the app on. Users with share permission on the org app item can share it; a consumer without it can only send links to people who already have access. Reshare is convenient and easy to over-grant. Keep it to named group owners, record who holds it, and review it when you review membership.

Revoking access

From the user or group menu on the permissions page you have two choices. Manage access changes which audiences the user belongs to and their reshare rights. Remove access removes the org-app-derived access to the app, the included items and the underlying semantic models, and Read and Execute on an included Fabric App. Access granted independently of the app remains.

When a removed person can still see something, work through this list before you suspect a bug:

  • They hold a workspace role in the workspace, which gives item access regardless of the app.
  • The report, model or notebook was shared with them directly, or through another app or audience.
  • They belong to a second group that is still assigned to an audience.
  • For a model in another workspace, access drift left records you can only remove from Manage permissions > Access via related items on the model (see access propagation).
  • The data store behind the model grants them access on its own, for example through a lakehouse role.

Audiences in practice

Audiences let one app serve several groups. They are child items of the org app, and you can manage their access without opening the app in edit mode. Audiences are available only in new org apps: if your app predates them, create a new app.

Open Manage audiences in the editor. From there you create audiences with New audience and, from each audience tab's menu, rename, move the tab left or right, duplicate, change the Item access setting, or delete. Duplicating copies item visibility but not membership.

  • Visibility per item. Each item has a checkbox per audience. Checked means the audience sees the item; unchecked means it does not. By default this also drives access: showing an item can propagate access, hiding it can revoke it.
  • Access to hidden content. Each audience has an Item access setting. When it is on for even one audience, users who have access to at least one audience can access all items in the app, even those hidden in their navigation. Turn it on only if you want audiences to shape navigation without restricting access.
  • At least one audience. An app always has one; deleting the last creates a new one. Audience names must be unique in the workspace, and the names of deleted audiences can still collide.
  • New items. With one audience, a new item is visible to it by default. With several you are prompted to choose.
  • Consumer tabs. Users see an All tab plus one tab per audience, unless they belong to a single audience, in which case no tabs are shown. Customize > Audience tabs controls the display. Audience tabs are not supported in the Power BI mobile apps, and deep-linking to a specific audience is not supported.

Mapping audiences to groups

Assign Entra security groups, not individuals, to audiences, and keep one group per audience per environment so test and production membership never mix.

Audiences are not a secrecy mechanism by themselves

If Access to hidden content is on for any audience, a user with access to any audience can reach every item. Hidden elements also remain reachable through a direct link when that setting is on. Use group membership and the visibility checkboxes with that setting off when the content must stay separated.

Application lifecycle management

An org app is a workspace item, so it can be versioned in Git and promoted through deployment pipelines like any other. That matters more here than for most items, because saved changes are live. The practical pattern is: build in a development workspace, review the change in Git, promote through test to production with a pipeline, and assign access separately in each stage.

Verify against Microsoft Learn

Org app items appear in the supported-items lists for both Git integration and deployment pipelines with a preview label, while the CI/CD for org apps article describes the workflows without that label. Confirm the status of each before you make it a release gate.

The lifecycle

Git integration

When a workspace is connected to a Git repository, the org app is part of the synchronization. Supported providers are Azure DevOps, GitHub and GitHub Enterprise (cloud-based only). Connect from workspace settings and use the source control panel to see the branch, the status of each item and the time of the last sync.

Each org app is stored as a set of artifacts: one for the app, which controls content and appearance, and one per audience. Committing creates a folder named {display name}.OrgApp containing a system-generated .platform file, a definition.json file, and a .children folder with one {display name}.OrgAppAudience subfolder per audience, each with its own .platform and definition.json.

The app definition has two parts: static settings (theme, logo and experience settings such as navigation pane behavior) and elements (the structure: overview, sections, items and links). Items are referenced by itemLogicalId, which matches the logicalId in the included item's own .platform file. The audience definition holds a reference to its parent (parentAppId, matching the app's logicalId), its settings (hasAccessToHiddenContent, tabOrder) and a flat list of element references by elementId.

Two definition versions, and no members

Definition version 1.0.0 does not support audiences; version 2.0.0 does, and Learn tells you to use 2.0.0 and create at least one audience artifact. Apps created with audience support always come with a default audience artifact. Note also what the files do not contain: neither the app nor the audience definition lists users or groups. Git carries structure and visibility, not who has access, so membership has to be assigned in each environment and documented outside the repository.

Reviewing definition changes

The definition is human-readable, so review it like code. Route changes through a pull request, ideally with owners for the app folder (see Pull-Request Notifications with CODEOWNERS), and branch as described in GitHub Integration and Branching.

  • hasAccessToHiddenContent did not flip to true without an explicit approval, because it widens access across the whole app.
  • Every elementReferences entry in each audience still points at an existing elementId, and removed elements are removed from all audiences.
  • parentAppId matches the parent's logicalId, and no itemLogicalId points at an item that is not in the repository.
  • Theme colors were changed on purpose and still meet the contrast requirement.
  • Links point at approved destinations, and no personal or test URLs are included.
  • Element and audience names avoid characters that are invalid in folder names, because the folder names are derived from them.

Deployment pipelines

Deployment pipelines promote the app and its content through stages. A pipeline has two to ten stages, three by default (development, test, production). Items in adjacent stages are paired, and a deployment overwrites the paired item in the target stage. Unpaired items with the same name and type are not overwritten; a duplicate is created. Pair stages before the first deployment.

  1. Create the pipeline and assign stages

    Create DPLY_SALES_CNSM and assign the development, test and production workspaces. Pair the stages before the first deployment so an app that was created by hand in a later stage is not duplicated.

  2. Build and review in development

    Make the app and content changes in DEV_SALES_CNSM, commit them to Git and merge through a reviewed pull request.

  3. Deploy the app and its items together

    Select the org app with the reports, notebooks and dashboards it includes. The app refers to items by logical ID, so deploy them in the same run and verify afterwards that every element resolves to the target stage's paired item.

  4. Assign test access and validate

    Add the UAT group to each audience, then test with one account per audience.

  5. Promote to production

    Deploy to PRD_SALES_CNSM under a user account. Because the app's access-management rule requires write and reshare rights, use an account that holds them on the items and models in the target workspace, and confirm the behavior in your test stage first.

  6. Assign production access and smoke test

    Add the business groups to the audiences and open the app as a member of each.

Service principals cannot deploy org apps

Learn lists a limitation: org apps cannot be deployed across stages using service principals. A release job that authenticates as a service principal cannot promote the app, even if it promotes everything else. Keep app promotion as a user-context step with an approval, and plan the automation around that. See Deployment Pipelines and Promotion for the general pipeline design and Deployment Checklist for release gates.

Verify against Microsoft Learn

The CI/CD article says the fabric-cicd library can consume org app definitions from Git. The library's own documentation lists its supported item types, and org apps and org app audiences are not among them in the version reviewed. Do not build release automation on fabric-cicd for org apps until you have confirmed the item type in the current supported item types and tested it with your identity model.

Updating an org app

Users with Admin or Member permissions can edit an app when the update adds or removes items or otherwise changes access management. Contributors can edit when the update does not affect access management. Start from the workspace list (... > Edit) or from the viewing experience (Edit app), change what you need and select Save.

Kind of changeWhereVisible to consumers
Edit an included report or notebookThe itemWhen the item is saved; no app step
Rename, reorder, restructure, overview, brandingApp editorWhen the app is saved
Add or remove items, change audience visibilityApp editor, Manage audiencesWhen saved, with the access changes that go with it
Name, description, endorsementSettings paneImmediately
Add or remove peopleShare, Manage accessImmediately

If you remove items from an app, everyone with access loses their app-derived access to those items and to the underlying models of removed reports and paginated reports. Do that deliberately, and announce it, because a consumer who had the report open sees it stop working.

Urgent fixes. Even a hotfix should go through the pipeline. If someone edits an item directly in production, back-port the change to development straight away: the next deployment overwrites the paired item in the target stage, and the fix is lost if development never received it.

Unpublishing and deleting

In the org app model, unpublishing is deleting the org app item: select ... > Delete on the item in the workspace. Users lose the access the app gave them to the included items and to the underlying models of reports and paginated reports, and Read and Execute on an included Fabric App. Included items stay in the workspace, and access granted independently of the app stays in place.

Plan for deletion as irreversible

The documentation describes deletion but not recovery. A re-created app is a new item, and links to the old one should not be assumed to work again. If the workspace is connected to Git, commit the definition first so the structure is recoverable even if the identity of the item is not.

If you want the effect of unpublishing without losing the item, remove access instead: use Manage access to remove the groups, which takes the app away from consumers and keeps the structure, branding and audiences ready to re-grant.

  1. Announce

    Tell consumers what is being retired, what replaces it and where the new link is.

  2. Capture the definition

    Commit the app and audience definitions to Git, or export your documentation of its structure.

  3. Withdraw access

    Remove the groups and leave the item in place for a soak period. Watch for support requests.

  4. Delete the item

    Delete the app in each stage, starting with production if you are retiring it outright.

  5. Clean up

    Remove lingering independent access, check semantic model permissions for records left behind, remove the Git folder and update any intranet pages, bookmarks or documents that linked to the app.

Key takeaways

  • Share with Entra groups through audiences, restrict reshare to named owners, and expect a removed user to keep access that came from somewhere other than the app.
  • Treat Access to hidden content as a security-relevant switch; review it in every pull request and every audience review.
  • Git stores the app's structure and visibility, not its members. Assign and document membership per environment.
  • Build in development, review in Git, promote with a pipeline under a user account, and never edit production items directly.
  • There is no unpublish step: withdraw by removing access, retire by deleting, and capture the definition first.
