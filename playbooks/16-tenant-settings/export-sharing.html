Playbook 16 · Tenant Settings

Export and sharing settings

Export, download, link-sharing, guest and external-collaboration settings decide how data leaves the service and who can receive it. They carry the highest exposure in most tenants, so they get the most careful scoping.

  • Portal group Export and sharing settings
  • Default stance Specific groups or disable
  • Pairs with Sensitivity labels, audit

How data leaves the service

Every export or sharing setting opens a different door. The useful question is not "is it on" but "how much control travels with the data once it is out". Group the doors by that answer and set each posture accordingly.

  • Labels and audit follow the data. Excel and PowerPoint or PDF exports carry the item's sensitivity label on supported paths, so these are the safest formats to allow.
  • Partly controlled. Live Excel connections run as the user, so row-level security still applies, but copies and downloads are outside Fabric once saved.
  • Weak or no control. CSV, organization-wide links, publish to web and cross-tenant data shares escape label enforcement or authentication. Keep them off or tightly scoped.

Export and download

These settings apply to the Fabric and Power BI service. Several of them (Excel, CSV, PowerPoint, PDF) also depend on sensitivity labels being deployed first, because the label is what protects the exported file.

Copy and paste visuals

Where
Export and sharing settings
Default
Not stated
Typical posture
Enable for specific groups — Useful for business communication, but it is an uncontrolled copy path.
Scope and delegation
Supports specific security groups and exceptions.
What it controls
Lets users copy a visual from a tile or report and paste it as a static image into another application.
Risk or benefit
The pasted image carries no lineage, label or access control. Row-level security applied when the visual rendered, but nothing follows the image afterwards. The benefit is cheap slide and e-mail production; the exposure equals photographing the screen, which no tenant setting can prevent.
Notes
Scope to communicators and analysts and exclude groups that handle regulated data. Treat it as a policy and culture control backed by endpoint DLP, not as a technical barrier.

Export to Excel

Where
Export and sharing settings
Default
Not stated
Typical posture
Enable for specific groups — High business value; the label applied to the file is the real control.
Scope and delegation
Supports specific security groups and exceptions.
What it controls
Lets users export the data behind a visualization (or a paginated report) to an Excel file.
Risk or benefit
The file is a static copy that leaves the service. Fabric applies the item's sensitivity label to the exported file and protects it according to the label's encryption settings, so labels should be rolled out before this setting is widened.

Scope to analysts who need offline data. Users with Build permission can still query the model through other paths (live connection, Execute Queries API), so this setting governs the user interface, not access to the data.

Download reports

Where
Export and sharing settings
Default
Not stated
Typical posture
Enable for specific groups — Restrict the full-copy path to the people who build reports.
Scope and delegation
Supports specific security groups and exceptions.
What it controls
Lets users download .pbix files and paginated report (.rdl) definitions from the service so they can be edited in Power BI Desktop or Report Builder.
Risk or benefit
A .pbix can contain imported data, queries and model logic, so a download is a full copy of the report and possibly of the data. The benefit is that developers can rework reports locally.
Notes
Scope to report authors and developers. For re-use and source control prefer Git integration and deployment pipelines over manual downloads, which leave no history. Track high-risk assets with the admin APIs and export audit events.

Where

On
Typical posture
Enable for specific groups — Governed live access beats static exports, but start with analysts and widen after training.
Scope and delegation
Supports specific security groups and exceptions.
What it controls
Lets users export data to Excel from a report visual or semantic model, or export a semantic model to an Excel workbook with Analyze in Excel, both with a live connection to the XMLA endpoint.

Export reports as PowerPoint presentations or PDF documents

Where
Export and sharing settings
Default
Not stated
Typical posture
Enable for specific groups — Common business need; labels and audit make it manageable for named groups.
Scope and delegation
Supports specific security groups and exceptions. Portal offers delegation to domain admins and workspace admins.
What it controls
Lets users export a report from the Fabric or Power BI portal to a PowerPoint file (one slide per page) or a PDF document. Each page is a static, image-based rendering.
Risk or benefit
Row-level and object-level security and the current filters apply at export time, and the sensitivity label is applied on supported export paths. The file can still be forwarded freely, loses lineage and is stale as soon as data refreshes.
Notes
Scope to business reporting groups and exclude restricted populations. Audit ExportReport and ExportArtifact; ExportArtifactDownload records a completed .pptx or .pdf download. Domain delegation lets domains own their policy when you run a federated model.

Disable — Legacy format with no modern use case.
Scope and delegation
Supports specific security groups and exceptions. Portal offers delegation to domain admins and workspace admins.
What it controls
Lets users export paginated reports (.rdl) as MHTML, a single-file web archive. It does not apply to standard Power BI reports.

MHTML is a legacy single-file web archive format with limited tooling. It adds another copy of report data outside Fabric and gives consumers little reason to prefer it over PDF or Excel.

Allow Excel, restrict CSV

If analysts ask for CSV because Excel feels slow, offer Excel export with a sensitivity label first. The label then protects the file, which CSV cannot do.

Sharing links and Office integration

A link is the most common way content spreads inside a tenant. Three scopes exist, and one tenant setting controls the widest.

Allow shareable links to grant access to everyone in your organization

Where
Export and sharing settings
Default
Not stated
Typical posture
Disable — Default to explicit, named access; org-wide links are hard to audit.
Scope and delegation
Supports specific security groups and exceptions.
What it controls
Controls whether users can create People in your organization links. When the setting is off, users with share permission can share a report only by link to Specific people or People with existing access.
Risk or benefit
An organization-wide link grants access to anyone in the tenant who obtains it, bypassing deliberate access lists. Links forwarded in e-mail or chat spread beyond the intended audience and the audit trail shows the link rather than each recipient. The setting has no effect on external users, who cannot use these links.
Notes
Disable broadly and enable for a small group if a business case exists. The narrower setting that stops protected-label content from being shared by organization-wide link can stay on regardless. Inventory existing organization-wide links with the Widely Shared Artifacts - Links Shared To Whole Organization admin API and the GetArtifactLinkSharedToWholeOrgAsAdmin audit operation.

Enable Power BI add-in for PowerPoint

Where
Export and sharing settings
Default
On
Typical posture
Enable for all — Prefer live, permission-checked embedding to static exports.
Scope and delegation
Supports specific security groups and exceptions.
What it controls
Lets people embed live, interactive Power BI data in PowerPoint. When on, entry points that open a new presentation with the add-in loaded are available in Power BI. It requires the Office admin to allow add-ins.
Risk or benefit
Live embedding is easier to govern than a static export because viewers see data under their own permissions and the content stays connected to the model. The remaining risk is a presenter capturing live data from the screen.
Notes
Turning the setting off only removes the Power BI entry points; people can still start from PowerPoint. To block the add-in completely you must also turn it off on the Office side. Align with your sensitivity-label and Office add-in policies.

Allow DirectQuery connections to Power BI semantic models

Where
Export and sharing settings
Default
On
Typical posture
Enable for specific groups — Powerful for developers, a source of dependency sprawl for everyone else.
Scope and delegation
Supports specific security groups and exceptions.
What it controls
Lets users use DirectQuery to connect to Azure Analysis Services or Power BI semantic models. When off, users can no longer publish new composite models on Power BI semantic models to the service. Existing reports keep working and Desktop can still build the models locally.
Risk or benefit
Composite models chain semantic models together, which can degrade performance through query chaining and obscure where data comes from. The benefit is extending a certified model with local data without copying it.
Notes
Live connections to Power BI semantic models and DirectQuery to Analysis Services are not affected by this switch. Enable for model developers, require endorsement of the base model, apply row-level security on the base model, and monitor lineage.

Publish to web

Publish to web creates a public embed code that anyone, including search engines, can open without signing in. It is the one setting where a mistake becomes world-readable.

Publish to web

Where
Export and sharing settings
Default
Not stated
Typical posture
Disable — Public, unauthenticated access cannot be reconciled with a least-privilege model.
Scope and delegation
Supports specific security groups and exceptions.
What it controls
Lets people publish public reports on the web. Published reports need no authentication to view. Admins review and delete embed codes on the Embed codes page, and can set Choose how embed codes work to Allow only existing embed codes so users must ask an admin for new ones.
Risk or benefit
Anyone with the link, including search engines, can see the report and its underlying data. A leaked embed code cannot be recalled by the report owner alone.
Notes
Disable for the organization. If a public-data use case exists, enable for a small publishing group, use the existing-codes-only option and review embed codes regularly. Audit PublishToWebReport, DeleteEmbedCode and the GetPublishToWebArtifactsAsAdmin operation.

Scoping to groups does not retire existing public reports

Restricting the setting to specific groups stops new codes from non-members, but existing public reports keep rendering. To take them offline, review the Embed codes page and delete the codes, or disable the setting for the entire organization.

  1. Inventory

    Open the Embed codes admin page, or list public reports with the admin APIs, and record each owner.

  2. Remove or approve

    Delete codes that are no longer needed. For ones that stay, record the business owner and the reason the data is public.

  3. Disable

    Set the tenant setting to disabled, or enable for a small publisher group with the existing-codes-only option.

  4. Monitor

    Alert on PublishToWebReport and review DeleteEmbedCode events.

External data sharing

Where
Export and sharing settings
Default
Not stated
Typical posture
Disable — Cross-tenant sharing needs a deliberate, partner-by-partner decision.
Scope and delegation
Supports specific security groups and exceptions.
What it controls
Lets specified users share read-only links to data in OneLake (lakehouses and additional Fabric items) with collaborators in other Fabric tenants. The link creates a shortcut in the recipient's tenant that points back to your data; nothing is copied.
Risk or benefit
Provider governance does not follow the data: sensitivity-label-based access control is not supported in cross-tenant scenarios, and collaborators can view, build on and re-share the data inside and outside their own tenants.
Notes
The provider tenant enables this setting and the consumer tenant enables Users can accept external data shares. It is unrelated to Entra B2B semantic-model sharing. Keep it off until a partner use case is approved; then enable for a small group of data owners and review existing external shares regularly.

Verify against Microsoft Learn

Some Learn articles label the two OneLake external data sharing settings as preview, while the settings index and the feature overview describe them without that label. Confirm the current status before you rely on them: External data sharing.

Guest access needs more than these settings

Guests also need an invitation path (the Microsoft Entra Guest Inviter role for inviters), licensing and workspace or item permissions. The tenant settings only decide what Fabric allows. Conditional access and cross-tenant access settings in Microsoft Entra ID control the rest.

Key takeaways

  • Allow Excel and PowerPoint or PDF export for groups, keep CSV tighter, and restrict full downloads to people who build reports.
  • Disable organization-wide links for most people; keep the protected-label link guard on for everyone.
  • Disable publish to web, then delete leftover embed codes: group scoping alone does not take existing public reports offline.
  • Treat B2B guests, in-place model sharing and OneLake external data sharing as three separate decisions.
  • Deploy sensitivity labels before widening Excel, PowerPoint and PDF export, because the label is the control on the file.
