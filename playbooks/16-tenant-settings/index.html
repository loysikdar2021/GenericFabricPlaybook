Tenant Settings Reference and Decision Guide

Tenant settings are the switchboard that decides which Microsoft Fabric and Power BI features people in your organization can use. This guide explains how the switchboard works, gives you a repeatable way to decide each switch, and documents the settings that matter most with a recommended posture for security-conscious enterprises.

  • Audience Fabric administrators, security and governance leads
  • Role needed Fabric Administrator
  • Format Reference plus decision guide

What this guide gives you

A new Fabric tenant arrives with defaults chosen for broad adoption. Some of those defaults are fine, some quietly open data paths that a regulated or security-conscious organization would not choose, and a few change in meaning as features mature. Administrators then face dozens of switches with short descriptions and no guidance on who should get each one.

This playbook closes that gap in three ways.

  • A mental model. How a setting is evaluated, how groups and exceptions combine, how delegation to domains, capacities and workspaces works, and why tenant settings are governance controls rather than a security boundary.
  • A decision method. A short framework, a security-group pattern and a rollout sequence so every setting is decided once, owned, and reviewed.
  • A reference. For each verified setting: its default, a typical enterprise posture (Enable for all, Enable for specific groups or Disable), what it controls, the risk or benefit, and practical notes.

Verified against Microsoft Learn

Names, locations, defaults, group support and delegation were checked against the Fabric admin documentation and the tenant settings index. Where a default is not documented, the reference says Not stated instead of guessing. Names and preview labels change, so before acting on a setting, confirm it in your own portal and on Tenant settings index.

Where tenant settings live

Tenant settings are managed by someone holding the Fabric Administrator role (assigned in Microsoft 365 or Microsoft Entra ID). Fabric organizes them in groups such as Export and sharing, Integration, Developer, OneLake and Copilot.

  1. Open the OneLake catalog

    Select OneLake catalog, then the Govern tab.

  2. Go to Configurations

    Choose Configurations, then Tenant settings. The same area also surfaces capacity and workspace administration.

  3. Expand a group and a setting

    Each setting shows a toggle, an Apply to choice, optional group pickers and, where delegation is supported, extra options for domain, capacity or workspace admins. Select Apply to save.

Older portal layout

Portal layouts roll out in stages by region. If you do not see the Govern tab, use the gear icon, Admin portal, then Tenant settings. The settings are the same.

The five states of a setting

Most settings can be shaped with groups. A setting is evaluated for each user in the order shown below.

StateMeaningTypical use
Disabled for the entire organizationNobody gets the feature.Features you have decided against, or have not reviewed yet.
Enabled for the entire organizationEverybody gets it.Low-risk convenience features.
Enabled for the entire organization except specific security groupsEverybody except members of the excluded groups.Broadly useful features where a restricted population must be carved out.
Enabled for specific security groupsOnly members of the listed groups.The default pattern for anything that moves data or code out of governed stores.
Enabled for specific security groups except specific security groupsMembers of the allow groups who are not in an exception group.Allow-list with a hard stop for restricted users.

The most restrictive setting wins

When a user falls under both an allow group and an exception group, the exception applies. This is what makes a small, well-owned exception group an effective safety net for the highest-risk population.

Settings that apply to the whole organization

Some settings show a note that they apply to the entire organization and offer no group picker. For these, the toggle is the only control, so the decision is all or nothing. Plan compensating controls such as policy, review and monitoring where you cannot scope them.

  • Block users from reassigning personal workspaces (My Workspace)
  • Create and use Gen1 dataflows
  • Block ResourceKey Authentication
  • Use ArcGIS Maps for Power BI and Users can use the Azure Maps visual
  • Users can view Power BI files saved in OneDrive and SharePoint and Users can share links to Power BI files stored in OneDrive and SharePoint through Power BI Desktop
  • Allow non-Entra ID auth in Eventstream
  • Add and use certified visuals only (block uncertified)
  • Users with view permission can launch Explore
  • Help Power BI optimize your experience
  • Users can sync data in OneLake with the OneLake File Explorer app

Confirm group support in your portal

Scoping options can change as features evolve. A setting that has no group picker in your portal is organization-wide at that point in time, whatever this list says.

Hierarchy and delegation

The tenant is the top of a four-level hierarchy. A Fabric administrator can leave a setting at tenant level, or delegate it so that lower-level administrators can override it for their own scope.

LevelWhoWhere the override livesExamples
TenantFabric administratorTenant settingsEvery setting.
CapacityCapacity adminCapacity settings, Delegated tenant settings tab, with Override tenant admin selectionUsers can create Fabric items (delegated automatically), the Copilot and Azure OpenAI settings, Git switches, Azure AI services processing.
DomainDomain adminDomain settings, Delegated settings tabCertification and Domain admins can set default sensitivity labels for their domains.
WorkspaceWorkspace adminWorkspace settings, only where delegated and supportedOnly show approved items in the standalone Copilot in Power BI experience, Authenticate with OneLake user-delegated SAS tokens, Git switches, workspace network rules.
  • A setting is delegated through domains or through capacities, not both, which keeps ownership unambiguous.
  • After delegating to a domain or capacity, some settings can be delegated again to workspaces. Tenant administrators can also delegate directly to workspaces. Some settings offer no workspace option.
  • An override at a lower level affects only the workspaces or items in that scope.

Delegation moves the decision, not the accountability

A delegated setting can end up different from your tenant choice in individual capacities, domains or workspaces. If you delegate, also schedule a review of the overrides. The administration APIs list capacity, domain and workspace overrides, which makes this checkable (see Snapshot-and-diff).

Propagation, audit and the API

  • Propagation. Changes can take up to about 15 minutes to reach every user. Some features take longer: Block Public Internet Access can take 10 to 20 minutes. Tell users to sign out and in before testing.
  • The settings API. The Fabric administration API returns every tenant setting with its state and group lists, which makes inventory and drift detection scriptable. See the next table.
  • Audit. Delegation changes and many data-movement events appear in the Microsoft Purview audit log. For tenant-level toggles, confirm what your log records and rely on snapshots for state. Operation names are listed on the operations page.
Endpoint
GET https://api.fabric.microsoft.com/v1/admin/tenantsettings, with an optional continuationToken for paging.
Permissions
Caller is a Fabric administrator or a service principal. Delegated scope Tenant.Read.All or Tenant.ReadWrite.All. Limit of 25 requests per minute.
Key fields
settingName, title, enabled, canSpecifySecurityGroups, enabledSecurityGroups, excludedSecurityGroups, delegateToCapacity, delegateToDomain, delegateToWorkspace, properties, tenantSettingGroup.
Overrides
Separate list operations return the overrides set on capacities, domains and workspaces. An update operation changes a tenant setting from code.

Tenant settings are not a security boundary

A tenant setting switches a feature on or off for a population. It does not revoke the underlying permission. A user with Read and Build permission on a semantic model can still query it through any path whose own setting is open, and row-level security still filters the result on every path.

The practical consequences are worth stating plainly.

  • Close the whole family. If your intent is "no bulk extraction", review export, Analyze in Excel, XMLA, Execute Queries and download settings together.
  • Permissions come first. Workspace roles, item permissions, Build permission, row-level security and OneLake security decide what a person can read. Tenant settings decide which tools they may use to read it.
  • Labels and monitoring complete the picture. Sensitivity labels protect exported files on supported paths; audit logs and usage monitoring show what actually happened.

Key takeaways

  • Snapshot every tenant setting with the administration API before you change anything, and keep that snapshot as the baseline.
  • Use Enabled for specific groups as the default pattern for anything that moves data or code out of governed stores, and keep an exception group for restricted populations.
  • Remember that exception groups win and that some settings cannot be scoped at all; plan compensating controls for those.
  • Treat tenant settings as feature gates, not a security boundary: permissions, labels, network controls and audit do the rest.
  • Decide whether to delegate a setting to capacities or domains, and then review the overrides on a schedule.
