Playbook 16 · Tenant Settings

Change control and troubleshooting

How to change tenant settings safely, detect drift with a snapshot-and-diff job, find who changed what in the audit log, handle exceptions, and trace a "user cannot do X" report back to the setting that gates it.

  • Audience Fabric administrators, service desk
  • Includes Python snapshot script, audit event list, troubleshooting table

Change control

A tenant setting change affects every user in scope within minutes, and several are hard to notice when they go wrong. A light process is enough: every change has a record, a snapshot and a check.

  1. Request

    The requester names the setting, the capability and the population affected, and the business reason.

  2. Assess

    The Fabric administrator classifies the setting (egress, identity, third-party processing, creation, guardrail, preview, network) and lists dependent content and groups.

  3. Approve

    The setting owner approves. High-risk classes also need security or governance review.

  4. Snapshot

    Capture the current state with the API, before and after the change.

  5. Change

    Apply the change in a window; for scope changes, update the allow group first, then the setting.

  6. Verify

    After propagation (up to about 15 minutes, longer for network changes), test with a member and a non-member of the scope.

  7. Record

    Store the decision record, snapshot diff and communication. Schedule the next review.

Emergency changes

Some changes, such as disabling publish to web after a leak, cannot wait for approval. Make the change, snapshot it, and complete the record afterwards. Keep a short list of settings you are willing to switch off immediately.

Snapshot-and-diff

The administration API turns tenant settings into data. A scheduled job that stores each result and compares it with the last approved baseline gives you drift detection, an inventory and the evidence for reviews.

import json
import sys
import time

import requests
from azure.identity import DefaultAzureCredential

BASE = "https://api.fabric.microsoft.com/v1/admin/tenantsettings"
KEYS = ["enabled", "enabledSecurityGroups", "excludedSecurityGroups",
        "delegateToCapacity", "delegateToDomain", "delegateToWorkspace", "properties"]


def get_settings():
    token = DefaultAzureCredential().get_token("https://api.fabric.microsoft.com/.default").token
    headers = {"Authorization": f"Bearer {token}"}
    items, url = [], BASE
    while url:
        r = requests.get(url, headers=headers, timeout=60)
        if r.status_code == 429:  # limit is 25 requests per minute
            time.sleep(int(r.headers.get("Retry-After", "30")))
            continue
        r.raise_for_status()
        page = r.json()
        items += page.get("tenantSettings", [])
        nxt = page.get("continuationToken")
        url = f"{BASE}?continuationToken={nxt}" if nxt else None
    return items


def normalize(items):
    out = {}
    for s in items:
        row = {k: s.get(k) for k in KEYS}
        for g in ("enabledSecurityGroups", "excludedSecurityGroups"):
            row[g] = sorted((x.get("name") or x.get("graphId") or "") for x in (row[g] or []))
        out[s["settingName"]] = row
    return out


def diff(old, new):
    for name in sorted(set(old) | set(new)):
        if name not in old:
            yield f"ADDED   {name}"
        elif name not in new:
            yield f"REMOVED {name}"
        elif old[name] != new[name]:
            changed = [k for k in KEYS if old[name].get(k) != new[name].get(k)]
            yield f"CHANGED {name}: {', '.join(changed)}"


if __name__ == "__main__":
    baseline_path, snapshot_path = sys.argv[1], sys.argv[2]
    current = normalize(get_settings())
    with open(snapshot_path, "w", encoding="utf-8") as fh:
        json.dump(current, fh, indent=2, sort_keys=True)
    with open(baseline_path, encoding="utf-8") as fh:
        baseline = json.load(fh)
    lines = list(diff(baseline, current))
    print("\n".join(lines) or "No drift")
    sys.exit(1 if lines else 0)

Verify against Microsoft Learn

Check the response shape, scopes and throttling in List Tenant Settings. The identity must be a Fabric administrator or a service principal; the documentation does not state which admin-API switch must list the service principal, so test with a non-production principal. Handle the 25-requests-per-minute limit.

Running it

  • Store snapshots in Git. One commit per run gives you history, review and rollback evidence. Update the approved baseline through a pull request.
  • Schedule it. Daily is usually enough; run it manually before and after every planned change.
  • Include the overrides. Add calls to the list-overrides operations for capacities, domains and workspaces, and diff those too.
  • Alert on drift. Send a ticket to the setting owner when a setting changes outside a change window.

Handling exceptions

Exceptions are normal; untracked exceptions are the problem. Give them a short path and an end date.

  1. Request

    A form captures person or team, capability, justification and the date the need ends.

  2. Approve

    The setting owner approves; the group owner adds the person to the allow group or removes them from the exception group.

  3. Time-box

    Use an access package with expiry so the membership ends without a manual step.

  4. Review

    Include open exceptions in the quarterly review. Renew with a fresh justification or close.

Operational checklist

  • A snapshot exists for every planned change, before and after.
  • Every setting in the standard has an owner and a decision record.
  • Allow and exception groups have owners, and membership is reviewed on schedule.
  • Capacity, domain and workspace overrides are listed and reviewed.
  • Service principals for admin APIs are in dedicated groups with rotating credentials.
  • The audit log is searched for export, sharing, publish-to-web and delegation events on a schedule.
  • Preview settings are re-checked for status before each review.
  • There is a documented emergency path for network settings and a short list of break-glass switches.

Key takeaways

  • Every change has a request, a snapshot before and after, a verification step and a rollback.
  • Automate snapshot-and-diff with the administration API and store the results in Git.
  • Use the audit operation names for sharing, export, publish-to-web and delegation, and confirm what your log records for tenant toggles.
  • Give exceptions an owner and an end date.
  • Troubleshoot top-down: setting, scope, override, propagation, then item permissions.
