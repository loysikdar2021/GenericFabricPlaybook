Integration, developer and APIs

XMLA endpoints, Analyze in Excel and Execute Queries

Three tenant settings decide which tools and APIs can read semantic models directly. They do not replace permissions: each path still needs Build permission on the model, and row-level security applies on every path.

Allow XMLA endpoints and Analyze in Excel with on-premises semantic models

Where
Integration settings
Default
On
Typical posture
Enable for specific groups — Developer tools need it, but it is an open data path.
Scope and delegation
Supports specific security groups and exceptions.
What it controls
Lets client tools connect to semantic models through XMLA endpoints (Excel, SSMS, DAX Studio, Tabular Editor, ALM Toolkit, third-party tools and scripts) and allows Analyze in Excel. Despite the wording, it governs connectivity to models hosted in the service; the on-premises phrase is a legacy label.
Risk or benefit
XMLA is an open-protocol data path. Build permission is still required and row-level security applies, but a connected tool can issue heavy queries, and with read-write enabled on the capacity, client tools can modify models and run TMSL scripts for users with enough workspace permission.
Notes
Also needs the capacity XMLA Endpoint property: read-only by default, read-write set by the capacity admin. Works with the Excel live-connection setting (truth table on this page). Audit with ConnectFromExternalApplication and related operations.

The capacity-level XMLA endpoint property is a third gate: it is read-only by default, and a capacity admin must set it to read-write before client tools can write to models, deploy or run TMSL scripts. The Excel live-connection setting itself is described in the export and sharing reference.

Semantic Model Execute Queries REST API

Where
Integration settings
Default
Not stated
Typical posture
Enable for specific groups — Valuable for automation, but a data egress channel that needs ownership.
Scope and delegation
Supports specific security groups and exceptions.
What it controls
Lets users query semantic models with DAX through the Power BI REST API (executeQueries). Also described in the API reference as the Dataset Execute Queries REST API setting.
Risk or benefit
It is a programmatic data channel: scripts, Azure Functions, notebooks, CI/CD jobs and AI agents can pull governed data. The API honors the caller's Read and Build permission, but service principals are not supported for models with row-level security or SSO.
Notes
Enable for automation and integration groups, require OAuth with conditional access, monitor in the Capacity Metrics app and audit logs, and treat it like any other data API. Limits are listed below the card.
Query shape
One query per call, DAX only, one table in the result.
Size limits
Up to 100,000 rows or 1,000,000 values per query (whichever is hit first), 15 MB per query.
Rate limit
120 requests per minute per user.
Permissions
Read and Build on the semantic model. Service principals are not supported for models with row-level security or single sign-on.
import requests

token = "<access-token>"  # acquire with your approved app or user flow
workspace = "00000000-0000-0000-0000-000000000000"
model = "00000000-0000-0000-0000-000000000000"
url = f"https://api.powerbi.com/v1.0/myorg/groups/{workspace}/datasets/{model}/executeQueries"
body = {"queries": [{"query": "EVALUATE ROW(\"ok\", 1)"}]}
r = requests.post(url, headers={"Authorization": f"Bearer {token}"}, json=body, timeout=60)
print(r.status_code, r.text[:200])

Service principals and admin APIs

Service principals are non-human identities. They are the right way to automate, but each switch below hands a program power over tenant metadata or workspace creation, so these are the settings that most need an owner, a dedicated security group and a credential lifecycle.

Service principals can call Fabric public APIs

Where
Developer settings
Default
On — For new customers.
Typical posture
Enable for specific groups — Automation identities should be enumerated, not implied.
Scope and delegation
Supports specific security groups and exceptions.
What it controls
Lets service principals with suitable roles and item permissions call Fabric public APIs that do create, read, update and delete operations and are protected by a Fabric permission model.
Risk or benefit
A service principal acts without a human, with whatever workspace roles it was given. Enabled for the entire tenant, any app registration with permissions becomes an automation identity.
Notes
Scope to a dedicated security group of approved service principals, grant them workspace roles like any other identity, and prefer certificate or federated credentials. Required for the MCP server endpoint with non-GitHub clients.

Service principals can create workspaces, connections, and deployment pipelines

Where
Developer settings
Default
Off — For new customers.
Typical posture
Enable for specific groups — No item-level permission model protects these APIs.
Scope and delegation
Supports specific security groups and exceptions.
What it controls
Lets service principals call the Create Workspace, Create Connection and Create Deployment Pipeline APIs, which are not protected by a Fabric permission model.
Risk or benefit
Because these calls have no item-level permission model, only the tenant setting limits who can create them. Unrestricted, an identity can create workspaces and connections at will.
Notes
Enable for the one or two automation identities that provision environments, such as a platform provisioning pipeline, and nothing else.

Operating service principals safely

  1. Create a group per purpose

    For example SG-FAB-SP-Provisioning and SG-FAB-SP-Governance. List only those groups in the tenant settings.

  2. Choose strong credentials

    Prefer a federated credential or a certificate to a client secret. Record where the credential lives and who rotates it.

  3. Keep the app registration clean

    The app must not hold Power BI permissions that need admin consent when it is used for admin APIs. Grant access through workspace roles and item permissions instead.

  4. Grant the least workspace role

    Add the service principal to workspaces with the lowest role that works, and remove it when the automation ends.

  5. Monitor

    Audit workspace and item creation events by the principal and review group membership on the standard cadence.

Verify against Microsoft Learn

The Get Tenant Settings API supports service principals, but the documentation does not say which admin-API switch must list the principal. Test with a non-production principal, and add it only to the groups that your test shows are required.

Maps and location services

Map visuals send location data to a mapping service. The decision is who processes it: Microsoft (Azure Maps) or a third party (Esri). Both settings apply to the whole organization.

Use ArcGIS Maps for Power BI

Where
Integration settings
Default
Not stated
Typical posture
Disable — Third-party processing with no group scoping.
Scope and delegation
Applies to the entire organization only; groups cannot be selected.
What it controls
Enables the ArcGIS Maps for Power BI visual provided by Esri. The visual is a third-party service: data used by the visual is sent to Esri, processed under Esri's terms, and may sit outside your tenant's geographic region or compliance boundary. The portal shows that it applies to the entire organization.
Risk or benefit
Location data leaves the Microsoft boundary and is handled by a third-party processor. If locations are sensitive (addresses of people, facilities with regulatory status) this is a real exposure; otherwise it adds rich geospatial analysis.
Notes
Org-wide only, so scoping to a group is not possible. Enable only after a data-protection review and record Esri as a processor; teach report authors what location data may be used.

Users can use the Azure Maps visual

Where
Integration settings
Default
Not stated
Typical posture
Enable for all — Stays inside Microsoft's boundary; review the two companion data-residency settings.
Scope and delegation
Applies to the entire organization only; groups cannot be selected.
What it controls
Lets users create and view reports that use the Azure Maps visual. Microsoft temporarily stores and processes the data for essential services such as translating location names into coordinates. Two companion settings control processing outside your tenant's region (Data sent to Azure Maps can be processed outside your tenant's geographic region, compliance boundary, or national cloud instance) and processing by Microsoft Online Services subprocessors.
Risk or benefit
Data is processed by Microsoft rather than a third-party provider, but location text is still sent to a mapping service. Where Azure Maps is unavailable in your region, the processing-outside-region setting decides whether data may be processed elsewhere.

OneDrive and SharePoint

These two preview settings move .pbix files into a permission model that Fabric administrators do not control. Both apply to the whole organization.

Users can view Power BI files saved in OneDrive and SharePoint

Where
Integration settings
Status
Preview Labeled preview on Microsoft Learn.
Default
On — Applies to all users when enabled.
Typical posture
Disable — Moves data into a permission model Fabric admins do not control.
Scope and delegation
Applies to the entire organization only; groups cannot be selected.
What it controls
Lets users view .pbix files stored in OneDrive for Business or SharePoint document libraries in the browser, without downloading them. Permissions come from OneDrive and SharePoint rather than from Fabric workspace roles.
Risk or benefit
Anyone with library access can open the file; model-level security inside the file still applies, but a fully imported .pbix with no row-level security exposes all its data to that audience. Files accumulate outside Fabric lineage and governance.
Notes
Org-wide only. Disable until SharePoint libraries that hold .pbix files are governed (restricted membership, sensitivity labels, no external sharing, compliant-device policy). Publish production content to workspaces instead.

Streaming authentication

Allow non-Entra ID auth in Eventstream

Where
Integration settings
Default
Not stated
Typical posture
Disable — Key-based streaming cannot be attributed or revoked per identity.
Scope and delegation
Applies to the entire organization only; groups cannot be selected.
What it controls
Controls whether Eventstream custom endpoints can use key-based authentication alongside Microsoft Entra ID. When off, only Entra ID authentication is allowed. Learn names the setting Allow non-Microsoft Entra ID auth in Eventstream on one page and Allow non-Entra ID auth in Eventstream in the index.
Risk or benefit
Keys can leak and activity cannot be attributed to a specific Entra principal, so logs are weaker. Entra authentication lets a user or service principal produce and consume events with auditable identity.
Notes
Org-wide only. Inventory custom endpoints that still use keys, migrate producers to Entra ID, then disable. Require a documented exception for any key-based endpoint that must remain.

Key takeaways

  • XMLA, Analyze in Excel and Execute Queries are three separate gates; decide them with the export settings as one family.
  • Never enable the admin-API service principal switches for the whole organization; use a dedicated, change-controlled group per purpose.
  • Use federated credentials or certificates for service principals, and keep admin-consent-required permissions off the app.
  • Keep third-party processing (Esri), third-party SSO and key-based streaming authentication off until a use case and owner exist.
  • Keep OneDrive and SharePoint viewing and Desktop link-sharing off until libraries holding .pbix files are governed.
