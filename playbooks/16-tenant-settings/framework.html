Playbook 16 · Tenant Settings

Decision framework and rollout

A repeatable method for deciding each tenant setting, enabling it through security groups, piloting it and keeping it reviewed, so that every switch has an owner, a reason and a way back.

  • Audience Fabric administrators, governance leads
  • Outcome Decided, owned, reviewable settings
  • Pattern Allow group plus exception group

Principles

  • Least exposure for egress, generous guardrails. Anything that moves data, code or tokens outside governed stores starts disabled or scoped. Anything that protects (labels, certified-visual enforcement, workspace guardrails) starts enabled for everyone.
  • Decide capabilities, not toggles. "Bulk data extraction" is one decision that spans export, Analyze in Excel, XMLA, Execute Queries and download settings. Decide the family together so the controls do not contradict each other.
  • One owner per setting. A named role, not a person, is accountable for the decision and for answering exception requests.
  • Groups over everyone. Enabled for the entire organization is a decision you take deliberately, not the path of least resistance.
  • Reversible and recorded. Every change has a record, a before-and-after snapshot and a rollback.
  • Exceptions expire. A temporary need is a time-boxed membership, not a permanent hole.

The decision path

Apply three questions in order. If the setting has no egress and no new identity, enable it for all. Otherwise ask whether there is an approved use case with a named owner; if not, disable it. If there is, enable for specific groups when scoping is supported. When scoping is not supported, either find a compensating control or leave the setting off.

Enable through security groups

For any setting you enable for specific groups, use a pair of Microsoft Entra security groups: an allow group that carries the capability and an exception group that carves out restricted populations. The tenant setting lists the allow group under Apply to and the exception group under Except specific security groups.

Mix granularities

Use per-setting groups for the dozen settings that carry real exposure, capability or persona groups for the rest, and one shared exception group for restricted populations where it makes sense. Keep membership flat, and test nested groups in a pilot before you depend on them.

Plan the lifecycle, not only the switch

A group without an owner, an access path and a review becomes a permanent entitlement. Use access packages for requests and expiry, and access reviews for owners to reconfirm membership. Both are Microsoft Entra ID Governance capabilities; check licensing.

Rollout phases

  1. Snapshot

    Call the Get Tenant Settings API and store the JSON. List capacity, domain and workspace overrides with the companion operations. Record who holds the Fabric administrator role. This is your baseline and your rollback.

  2. Decide

    Classify each setting, record the posture in a decision record, name the owner, and note compensating controls. Settings you leave at their default still need a line saying so and why.

  3. Pilot

    Create the groups, enable the setting for one or two teams in one domain, and keep the pilot open for a fixed period. Measure support requests, capacity impact and audit events, and write down what you learned.

  4. Broaden

    Widen group by group, update training and the published standard, and tell people what changed and who to ask for an exception.

  5. Operate

    Run the review cadence below, handle exceptions, and alert on drift between snapshots.

Tightening a setting that is already open

Many tenants start with defaults on. Moving a setting from enabled for everyone to specific groups can break workflows, so sequence it.

  1. Find real usage

    Use audit events for the capability (for example ExportReport or ExportArtifact for exports) to list who actually uses it.

  2. Seed the allow group

    Create the allow group from that list, remove clear mismatches, and set an owner.

  3. Announce a window

    Tell users the date their access moves to the group and how to request membership. Keep the window short.

  4. Switch the scope

    Change the setting from the entire organization to the allow group, with the exception group excluded. Allow time for propagation.

  5. Watch and adjust

    Review support requests for the first weeks and adjust membership. Keep the previous snapshot ready.

Content that depends on a setting

Some settings, such as Gen1 dataflows, datamarts or Eventstream key authentication, sit under live content. Inventory dependents before disabling so you do not break scheduled refreshes or integrations.

Key takeaways

  • Classify settings into seven risk classes and start from the class posture, then depart from it only with a named owner and a use case.
  • Use an allow group and an exception group for every high-risk capability, and manage membership with access packages and reviews.
  • Roll out in five phases with a snapshot first, a pilot group second and a review loop that never ends.
  • Tighten open settings by seeding the allow group from audit events, announcing a short window and keeping the previous snapshot ready.
  • Review monthly for drift and new settings, quarterly for membership and overrides.
