Workspaces, Git, OneLake and items

Settings that control who can create Fabric items and workspaces, how deleted content is recovered, how workspaces connect to Git, how OneLake data is reached from outside Fabric, and how network and encryption controls apply.

  • Portal groups Microsoft Fabric, Workspace, Git integration, OneLake, Advanced networking, Encryption

Creating items and workspaces

Three switches shape sprawl: who may create Fabric items, who may create workspaces, and whether people can move their personal workspace. They interact, and the first one is delegated to capacity admins automatically.

Users can create Fabric items

Where
Microsoft Fabric
Default
Not stated
Typical posture
Enable for specific groups — Controls who can create governed data assets at all.
Scope and delegation
Supports specific security groups and exceptions. Automatically delegated to capacity admins.
What it controls
Lets users use production-ready Fabric features to create Fabric items (lakehouses, warehouses, notebooks and more). Turning it off does not affect the ability to create Power BI items. It requires a capacity that supports Fabric workloads.
Risk or benefit
Unrestricted creation spreads unmanaged compute, storage and data. Disabled users can still view Fabric items they have read access to.
Notes
Capacity admins can override the tenant choice for their capacity (Delegated tenant settings, Override tenant admin selection), so a tenant restriction is a recommendation to capacities. Related switches, including Git integration, depend on this one for Fabric item types.

Block users from reassigning personal workspaces (My Workspace)

Where
Workspace settings
Default
Not stated
Typical posture
Enable for all — Keeps personal content on the capacity you chose.
Scope and delegation
Applies to the entire organization only; groups cannot be selected.
What it controls
Stops My workspace owners from changing the capacity assignment of their personal workspace. By default owners can reassign it, for example back from a Premium or Fabric capacity to shared capacity.
Risk or benefit
Reassignment can break data-residency commitments and circumvent capacity cost and monitoring decisions made by admins, such as a designated preferred capacity for My workspaces.
Notes
Org-wide only. Pair it with a default capacity designated for My workspaces in capacity settings and a periodic review of My workspace content through the admin APIs; workspace retention keeps deleted My workspaces for 30 days.

Retention and recovery

Two settings define how long a deleted workspace or item can be restored. Retention is the safety net for mistakes, and also for malicious deletion.

SettingDefaultTypical postureWhat it controls; risk or benefitNotes
Define workspace retention periodNot statedEnable for allSets how long a deleted collaborative workspace can be restored before permanent deletion. The minimum is 7 days, My workspaces are kept 30 days automatically and other workspaces can be kept up to 90 days.Pick 30 to 90 days so end-of-period mistakes can still be recovered, and document who may restore a workspace.
Fabric item recoveryOn Minimum retention 3 days, maximum 90.Enable for allRetains deleted Fabric items so they can be recovered; admins choose the retention period (3 to 90 days). Some items do not support recovery. Turning it off makes deletion permanent.Leave on and set a retention that matches your recovery objectives.

Document who may restore

Restoring a deleted workspace is itself a privileged action. Record who may run it, how requests are made, and which retention period you promised to teams.

Git integration

Git integration connects a workspace to a repository so item definitions can be committed, reviewed and deployed. Four tenant switches plus two supporting settings decide whether a user can do it.

Users can synchronize workspace items with their Git repositories

Where
Git integration
Default
On
Typical posture
Enable for specific groups — Source control is desirable but should follow an approved repository standard.
Scope and delegation
Supports specific security groups and exceptions. Capacity admins and workspace admins (delegation options in the portal).
What it controls
Lets users sync workspace items with an Azure DevOps Git repository, commit workspace changes and update workspaces from the repository. It is the base switch for Git integration, including GitHub.
Risk or benefit
Without scoping, any workspace admin can connect a workspace to any repository they can reach, which can move item definitions (code, queries, model metadata) outside governed repositories.
Notes
Enable for the engineering groups that run source control. The setting is evaluated for the Fabric user who performs the Git operation. Disabling it also stops GitHub-based integration because GitHub needs both switches. Needs the Fabric switch on for Fabric items. See the GitHub integration playbook.

Users can sync workspace items with GitHub repositories

Where
Git integration
Default

Typical posture
Enable for specific groups — Enabled only for groups that follow the approved repository model.
Scope and delegation
Supports specific security groups and exceptions. Capacity admins and workspace admins (delegation options in the portal).
What it controls
Lets users pick GitHub as their Git provider and sync workspace items with GitHub repositories.
Risk or benefit
Developers can link workspaces to personal or unapproved GitHub accounts and organizations, which can leak code, queries and dataset references.
Notes
For GitHub, both this switch and the base Git switch must be on for the user. Enable for the engineering group and constrain repositories with GitHub-side controls such as organization policies and branch protection. See the GitHub integration playbook.

Delegation and workspace-only settings

When delegation is turned on for a Git switch, a capacity admin can override the tenant choice for the capacity, and a workspace admin can override both for the workspace. The switches belong to Fabric: for Fabric items they depend on Users can create Fabric items, while workspaces that hold only Power BI items can still use Git when it is off. The option that lets Contributors and above change the connected Git branch is a workspace-level setting rather than a tenant one. For repository design, branching and security hardening, see GitHub Integration and Branching.

Verify against Microsoft Learn

The cross-geography switch cannot be enforced when the provider is GitHub, and the sensitivity-label switch exists because labels are not included in exported item definitions. Read Git integration tenant settings before you rely on either one for compliance.

OneLake access

OneLake is where Fabric data lives. Tenant settings decide whether people can reach it with tools outside Fabric; workspace roles, item permissions and OneLake security decide what they can read once they are in.

Users can access data stored in OneLake with apps external to Fabric

Where
OneLake settings
Default
Not stated
Typical posture
Enable for specific groups — External engines are a legitimate but separately governed access path.
Scope and delegation
Supports specific security groups and exceptions.
What it controls
Lets users reach OneLake data with applications outside Fabric, such as custom ADLS API apps, OneLake file explorer and Databricks. Internal engines such as Spark, Data Engineering and Data Warehouse are not affected.
Risk or benefit
External access moves reads and writes to tools you do not host. It gives engineers flexibility and creates an exfiltration path if unscoped. It must also be on to use shortcuts with OneLake security.
Notes
Scope to data engineering groups that need external tools. Use OneLake diagnostics to audit access and the Fabric audit log for control-plane changes. OneLake security roles and workspace roles still decide what each identity can read.

Users can sync data in OneLake with the OneLake File Explorer app

Where
OneLake settings
Default
Not stated
Typical posture
Disable — File-level sync outside the ingestion pattern.
Scope and delegation
Applies to the entire organization only; groups cannot be selected.
What it controls
Lets users run the OneLake File Explorer Windows app to browse OneLake items as folders and drag files in and out, similar to OneDrive.
Risk or benefit
Users can move files in and out of OneLake from their desktops without ingestion pipelines, which can create ungoverned file copies on endpoints. Activity is harder to attribute than pipeline loads.
Notes
Org-wide only. Disable by default; if data engineers need it, enable it knowingly and rely on workspace roles and OneLake diagnostics. Learn lists OneLake file explorer as an example of an app external to Fabric, so review it together with the external-apps setting.

The delegation-key setting above must be on, and lifetimes cannot exceed one hour.Because workspace admins can override it by default, check overrides with the workspace-overrides API. Include end-user identifiers in OneLake diagnostic logsNot statedEnable for allControls whether OneLake diagnostic logs record end-user identifiable information such as e-mail and IP address. Audit both planes

Use OneLake diagnostics to capture data-plane access (who read or wrote what through any path) and the Fabric audit log for control-plane changes. Diagnostics records can include end-user identifiers; the setting above controls whether those fields are redacted.

Networking and encryption

Network controls change how users, gateways and services reach the tenant. They are strong, and they can lock you out. Treat them as projects, not toggles.

Tenant-level Private Link

Where
Advanced networking
Default
Not stated
Typical posture
Decide per organization — Depends on your network strategy; do not enable without a pilot.
Scope and delegation
Group scoping is not stated in the reference; check the setting panel.
What it controls
Lets people use Azure Private Link to reach your Fabric tenant. Someone must complete the setup in Azure; the setting can grant permission to the right person or group.
Risk or benefit
Private Link moves access from the public internet to private endpoints, with considerations and limitations that affect some features and user experiences.
Notes
Decide per network strategy. Review the considerations and limitations before enabling and test with a pilot subnet. Block Public Internet Access is the companion switch.

Block Public Internet Access

Where
Advanced networking
Default
Not stated
Typical posture
Decide per organization — High impact; enable only after a successful private-link pilot.
Scope and delegation
Group scoping is not stated in the reference; check the setting panel.
What it controls
Blocks access to your Fabric tenant over the public internet. People without Private Link access cannot connect. It can take 10 to 20 minutes to take effect.
Risk or benefit
A strong perimeter control, and an easy way to lock out users, services and tools that are not on the private network.
Notes
Turn on only after Private Link is proven for all user populations and for background services. Plan an emergency path for the Fabric admins.
SettingDefaultTypical postureWhat it controls; risk or benefitNotes
Configure workspace-level inbound network rulesNot statedDecide per organizationLets workspace admins restrict inbound private-link access in workspace settings. Once a workspace restricts inbound access, existing tenant-level private links can no longer connect to it. Turning the setting off reverts all workspaces to their previous configuration.Enable for workspaces with strict isolation needs.
Configure workspace-level outbound network rulesNot statedDecide per organizationLets workspace admins configure outbound access protection. Turning the tenant setting off also turns off outbound protection in every workspace.Powerful for exfiltration control; do not toggle casually.
Configure workspace IP firewall rules PreviewNot statedDecide per organizationLets workspace admins configure IP firewall rules, which can allow access from specific IP ranges even when the tenant blocks public access. Learn's index names it Configure workspace-level IP firewall rules and trusted resource instances.Labeled preview on the networking page; confirm status on Learn.
Apply customer-managed keysNot statedDecide per organizationLets users configure workspace-level encryption with customer-managed keys. When off, Microsoft-managed keys are used.Enable when policy requires key control; it adds key-lifecycle responsibilities.

Safe sequence

  1. Read the considerations

    Review the Private Link considerations and limitations; some features and tools behave differently over private endpoints.

  2. Enable tenant-level Private Link

    Complete the Azure side (private endpoints, name resolution) and test with a pilot subnet and users.

  3. Prove every population

    Test desktop users, Power BI Desktop, gateways, pipelines, notebooks and background services over the private path.

  4. Block public access last

    Turn it on in a change window, allow 10 to 20 minutes for it to take effect, and keep an emergency path for the administrators.

  5. Add workspace controls where isolation is needed

    Use inbound and outbound workspace rules for sensitive workspaces. Remember that turning the tenant setting off reverts the workspace protections.

Workspace identity

A workspace identity is a Microsoft Entra service principal that belongs to a workspace, so the workspace can authenticate to data sources without a person's credentials. It is generally available, created by workspace admins, and not available in My workspace.

  • Review. Fabric administrators can see identities under Govern, Configurations, Fabric identities.
  • Limit. The tenant setting Define maximum number of Fabric identities in a tenant caps how many can be created. If the setting is disabled, the default limit is 10,000.
  • Audit. Look for the Purview audit friendly names Created Fabric Identity for Workspace, Retrieved Fabric Identity for Workspace and Deleted Fabric Identity for Workspace, and the CreateWorkspaceIdentityViaApi operation.

Domain assignment

Domains group workspaces for ownership and delegation. One preview setting controls whether administrators can move workspaces between domains.

Keep a list of overrides

An override can make a capacity or workspace more permissive than the tenant. Use the list-overrides operations of the administration API to enumerate capacity, domain and workspace overrides, and compare them to your standard each quarter.

Key takeaways

  • Scope Fabric item creation to groups, and remember that capacity admins can override the tenant choice.
  • For GitHub you need two switches plus the Fabric switch for Fabric items; disabling the base Git switch also stops GitHub.
  • Scope OneLake access from outside Fabric to engineering groups, keep OneLake File Explorer off, and turn on OneLake diagnostics for audit.
  • Prove Private Link for every population before you block public access.
  • Treat delegation as a review obligation: list overrides on a schedule.
