Reverse-engineering legacy assets

When the people who knew the logic have moved on, the logic still lives in the files. This page shows how to extract it systematically, in a form a developer can rebuild from and a tester can reconcile against, without copying screens or guessing from visuals.

  • Phase II · Build
  • Audience BI developers, analytics engineers, testers
  • Output specification package and golden baselines per asset

Extract intent, not appearance

The best rebuild starts from current business requirements and a subject-matter expert who can say what a number should mean. That is a rebuild, not a lift and shift, and it is the preferred route whenever the expert exists. Reverse-engineering is the safety net: it is how you recover the rules when the expert does not exist, and how you cross-check the rules when they do.

Looking at the visuals and recreating them is the shortcut that fails. It misses the filter hidden in a measure, the join done in Power Query, the role that quietly removes half the rows, and the calculated column nobody documented. Those omissions surface as data differences during testing, when they are expensive to find.

How much to extract depends on the decision recorded for each asset in the rationalization matrix.

Matrix decisionExtraction depthWhy
ReassignLight: model health and dependency check.The asset keeps running as built, so you only need to know what it depends on and whether it is sound.
RebindLight to medium: report-level logic and the model it will point to.The report must keep its meaning against a different model; compare measure names and results.
ModernizeMedium: model, queries and health.You are changing storage mode or the source, so queries and relationships matter more than visuals.
RebuildFull package, plus baselines.Nothing is carried forward except what you document.
ConsolidateDifferences between the duplicates.Compare definitions side by side and decide which rule survives; a schema-compare tool such as ALM Toolkit is built for this.
RetireNone beyond an archived copy of the definition.Keep the file so a late objection can be answered.

The toolbox and three routes

Three routes reach the same artifacts. Choose per asset based on where the file lives and what the workspace allows.

ToolUse it forNotes
Power BI Desktop project (PBIP)Saving a PBIX as text: the model as TMDL files and the report as PBIR files.Human-readable and diff-friendly. PBIR is the default report format. Convert in Desktop with Save as; the conversion cannot be scripted.
TMDL view and DAX query viewReading and scripting model objects, and running DAX, inside Desktop or on the web.DAX query view can open the query behind any visual from Performance Analyzer.
Tabular EditorBrowsing every model object and scripting bulk extraction with C#.A third-party tool launched from the External Tools ribbon or connected through XMLA. Version 2 is free and open source; version 3 is commercial.
DAX StudioRunning and tracing queries, server timings, query plans, model metrics.Open-source. Its metrics view is the Vertipaq Analyzer.
ALM ToolkitSchema comparison between two models, for consolidation.Open-source; also useful later for deployment diffs.
Semantic LinkReading model metadata and running DAX from a Fabric notebook, as DataFrames.Part of the Fabric runtime. Scriptable across hundreds of models.
Semantic Link LabsBest Practice Analyzer, Vertipaq metrics, and migration helpers in a notebook.An open-source extension of Semantic Link, not a Microsoft-supported product; pin the version you test.
Scanner APITenant-wide model expressions and schemas without opening files.See the inventory step; good for triage, not for final detail.

External tools are not Microsoft-supported products

Microsoft documents the public APIs these tools use and supports issues that reproduce with Microsoft tools, but does not support the tools themselves. Treat any change you make through them as you would a change from a script: on a copy, reviewed, and under source control.

Where the logic hides

Business logic is spread across four layers. A complete extraction visits each one, because a rule moved from one layer to another during a past refactor is a classic source of numbers that nearly match.

Step 1: Get the definition

Start by obtaining a faithful copy of each prioritized asset. Several paths exist, each with restrictions that decide which you can use.

PathHowRestrictions to check
Local fileOpen the PBIX in Power BI Desktop; Save as a project (PBIP).You need the file. If the original is lost, download it from the service.
Download from the serviceFile, Download this file, as a report or from a semantic model.Needs at least Contributor on the workspace. Models with incremental refresh, Direct Lake models, models with automatic aggregations, and models migrated from Azure Analysis Services cannot be downloaded as a full PBIX. Large-storage-format models cannot be downloaded through the REST API. Choose the live-connected download for reports whose data is too large.
Model definition APIFabric REST: Get Semantic Model Definition, in TMDL or TMSL format. It is a long-running operation that returns base64-encoded parts.The caller needs read and write permission on the model. The call is blocked for a model with an encrypted sensitivity label. The sensitivity label is not part of the returned definition.
XMLA endpointConnect Tabular Editor, DAX Studio, SSMS or Semantic Link to the published model.The workspace must be on a Premium, Fabric or PPU capacity with the XMLA endpoint enabled for at least read. Models in Pro-only workspaces have no endpoint; use the file route.
Fabric Git integrationConnect a scratch workspace to a repository and publish the model there.Gives you PBIR and TMDL as committed files, which also seeds the target repository.

A PBIX renamed to a ZIP can be unpacked, but the data model inside is a compressed binary that no one can read. Do not build the process on that trick.

Verify against Microsoft Learn

Download limitations and REST permissions evolve. Re-check Download a report from the Power BI service and Get Semantic Model Definition before you commit to a route for the whole estate.

Step 2: Extract the model

The model is where most of the logic lives. Extract it to files you can diff and search, not to a document you retype. Pick one script style per team so outputs are uniform.

// Writes tab-separated files that become part of the specification package.
var outDir = @"C:\spec\SM_SALES_LEGACY\";
System.IO.Directory.CreateDirectory(outDir);

System.Func<string, string> clean = s =>
    (s ?? "").Replace("\r", " ").Replace("\n", " ").Replace("\t", " ");

// Measures
var sb = new System.Text.StringBuilder("Table\tMeasure\tFormat\tFolder\tExpression\n");
foreach (var m in Model.AllMeasures)
    sb.AppendLine(m.Table.Name + "\t" + m.Name + "\t" + m.FormatString + "\t" +
                  m.DisplayFolder + "\t" + clean(m.Expression));
System.IO.File.WriteAllText(outDir + "measures.tsv", sb.ToString());

// Calculated columns
sb = new System.Text.StringBuilder("Table\tColumn\tExpression\n");
foreach (var c in Model.AllColumns.OfType<CalculatedColumn>())
    sb.AppendLine(c.Table.Name + "\t" + c.Name + "\t" + clean(c.Expression));
System.IO.File.WriteAllText(outDir + "calculated_columns.tsv", sb.ToString());

// Query (M) expressions per partition, and shared expressions and parameters
sb = new System.Text.StringBuilder("Table\tPartition\tMode\tExpression\n");
foreach (var t in Model.Tables)
    foreach (var p in t.Partitions)
        sb.AppendLine(t.Name + "\t" + p.Name + "\t" + p.Mode + "\t" + clean(p.Expression));
foreach (var e in Model.Expressions)
    sb.AppendLine("(shared)\t" + e.Name + "\t\t" + clean(e.Expression));
System.IO.File.WriteAllText(outDir + "queries.tsv", sb.ToString());

// Row-level security: role, table, filter. Record intent, never member names.
sb = new System.Text.StringBuilder("Role\tTable\tFilter\n");
foreach (var r in Model.Roles)
    foreach (var t in Model.Tables)
    {
        var f = r.RowLevelSecurity[t];
        if (!string.IsNullOrEmpty(f)) sb.AppendLine(r.Name + "\t" + t.Name + "\t" + clean(f));
    }
System.IO.File.WriteAllText(outDir + "rls.tsv", sb.ToString());
import os
import sempy.fabric as fabric

model = "SM_SALES_LEGACY"        # semantic model name
ws    = "Sales Analytics"        # workspace that hosts it
out   = f"/lakehouse/default/Files/spec/{model}/"
os.makedirs(out, exist_ok=True)

exports = {
    "measures":      fabric.list_measures(model, workspace=ws),
    "columns":       fabric.list_columns(model, workspace=ws, extended=True),
    "relationships": fabric.list_relationships(model, workspace=ws),
    "partitions":    fabric.list_partitions(model, workspace=ws, extended=True),
    "expressions":   fabric.list_expressions(model, workspace=ws),
    "hierarchies":   fabric.list_hierarchies(model, workspace=ws, extended=True),
    "perspectives":  fabric.list_perspectives(model, workspace=ws),
    "calc_items":    fabric.list_calculation_items(model, workspace=ws),
}
for name, df in exports.items():
    df.to_csv(f"{out}{name}.csv", index=False)

# Complete definition in TMSL, for diffing and as the archive copy.
with open(f"{out}model.tmsl.json", "w", encoding="utf-8") as f:
    f.write(fabric.get_tmsl(model, workspace=ws))
import json, pathlib

report = pathlib.Path("RPT_SALES_LEGACY.Report/definition")
rows = []
for vf in report.glob("pages/*/visuals/*/visual.json"):
    page_dir = vf.parents[2]
    page = json.loads((page_dir / "page.json").read_text(encoding="utf-8"))
    vis  = json.loads(vf.read_text(encoding="utf-8"))
    body = vis.get("visual", {})
    fields = []
    for role, state in (body.get("query", {}).get("queryState", {}) or {}).items():
        for proj in state.get("projections", []):
            fields.append(f"{role}: {proj.get('queryRef')}")
    rows.append({
        "page": page.get("displayName", page_dir.name),
        "visual": vf.parent.name,
        "type": body.get("visualType"),
        "fields": "; ".join(fields),
        "has_filters": "filterConfig" in vis,
    })

import csv
with open("visual_inventory.csv", "w", newline="", encoding="utf-8") as f:
    w = csv.DictWriter(f, fieldnames=rows[0].keys())
    w.writeheader()
    w.writerows(rows)

Verify against Microsoft Learn

Semantic Link function signatures are in the sempy.fabric reference; PBIR file layout and JSON schemas are in Power BI Desktop project report folder. The Tabular Editor object names come from its own scripting documentation. Run each script on one model first and compare the output to what the model shows in Desktop.

Prefer TMDL for review

For a single important model, the TMDL folder is the best reading copy: one file per table, measures with their descriptions, and clean diffs between a legacy and a rebuilt model. Use the scripted exports when you need to process many models at once.

Step 3: Extract Power Query logic

Copying M from the Advanced Editor query by query is the slow way, and it is easy to miss shared functions and parameters. The M code is part of the model definition: it sits in the table partitions and shared expressions of the TMDL files, and the Tabular Editor and Semantic Link scripts above export it. For triage across the tenant, the scanner API can return dataset expressions when the detailed-metadata admin settings are on.

For each query, record what a migration needs to know, not just the code:

  • Source and connection. Type, server or path, authentication method, and whether a gateway is involved. This drives connection and credential work in Fabric.
  • Transformation intent. Which steps are cleansing, which are business rules (for example, excluding test accounts), which are joins. Business rules move into the Silver or Gold layer; cleansing moves into Silver.
  • Hard-coded values. Literal filters, date cut-offs, mapping tables typed into the query. These are the usual hidden rules.
  • Parameters and functions. Environment parameters, reusable functions, incremental refresh range parameters.
  • Query folding. Whether the step pushes down to the source. A step that did not fold in the legacy model may have been the performance problem you are about to solve.
  • Dataflow dependence. Whether the query reads from a Gen1 dataflow; see the dataflow options.

Step 4: Extract report logic and visual queries

Report-level logic is easy to overlook because it feels like formatting. It is not: a visual-level filter that hides a status, a page filter that restricts the year, or a report-level measure defined only in the report all change the numbers.

  1. Inventory the visuals from files. Run the PBIR script above. You get every page, visual type and bound field in one table, which replaces image captures as the record of what the report contains.
  2. Capture the filters. Report, page and visual filters, plus slicer defaults and sync groups. Check the report-level measures file for measures that exist only in the report.
  3. Record the interactions. Bookmarks, drillthrough targets, tooltips pages, field parameters, conditional-formatting rules and the buttons that drive them.
  4. Capture the query behind key visuals. In Desktop, record with Performance Analyzer, expand a visual, and copy its query or run it in DAX query view. The same query runs in DAX Studio, where Server Timings and the query plan show how the engine resolves it.
  5. Mark the visuals that matter. Not every visual needs a baseline. Choose the ones the business reads numbers from, and the ones with complex filters.

A fictional example

A "Quarterly Sales Summary" shows revenue that is lower than the finance ledger. The model measure looks simple, but the report carries a page filter that excludes one order type, and a Power Query step removes returns before load. Neither appears in the measure. Without the visual inventory and the M export, the rebuild would have matched the measure and missed the two rules.

Step 5: Assess model health

While you hold the model open, measure it. Model health tells you what to fix rather than carry forward.

  • Vertipaq Analyzer. Table and column sizes, cardinality, encoding and relationship cost. In DAX Studio it is the View Metrics feature. High-cardinality text columns and unused columns are the usual wins, and the figures feed capacity sizing and Direct Lake planning.
  • Best Practice Analyzer (BPA). A rule-based scan of the model. The sample notebook that Microsoft offers from the semantic model checks more than sixty rules in five categories: performance, DAX expressions, error prevention, maintenance and formatting. Tabular Editor and Semantic Link Labs can run the same family of rules in bulk.
  • Unused objects. Columns and measures no report or dependent model uses are candidates for removal. Confirm against the report inventory and the consumption layer first.

Treat BPA output as a to-do list for the rebuild. Fix performance and error-prevention items in the new model; decide consciously about formatting rules rather than applying all of them blindly.

Verify against Microsoft Learn

Microsoft describes the BPA and memory analyzer sample notebooks in Use notebooks with a semantic model. The function names used by Semantic Link Labs for BPA and Vertipaq analysis live in that open-source project, not in Learn; check its documentation for the version you install.

Step 6: Capture golden baselines

Before you rebuild, record what the legacy asset says. A baseline is the result of a defined query under a defined filter context, saved together with a note of which model version and refresh it came from. When the rebuild is ready, replay the same queries and compare. This turns "the numbers look right" into an evidence trail, and it feeds the reconciliation checklist.

import sempy.fabric as fabric

dax = """
EVALUATE
SUMMARIZECOLUMNS(
    'Date'[Fiscal Year],
    'Product'[Category],
    "Net Sales", [Net Sales],
    "Orders",    [Order Count]
)
ORDER BY 'Date'[Fiscal Year], 'Product'[Category]
"""

legacy = fabric.evaluate_dax("SM_SALES_LEGACY",      dax, workspace="Sales Analytics")
legacy.to_csv("/lakehouse/default/Files/baselines/net_sales_by_year_category.csv", index=False)

new = fabric.evaluate_dax("SM_SALES_CNSM_Orders", dax, workspace="DEV_SALES_CNSM")

# Print legacy.columns first and adjust these names to what comes back.
keys    = ["Date[Fiscal Year]", "Product[Category]"]
metrics = ["[Net Sales]", "[Orders]"]

m = legacy.merge(new, on=keys, how="outer", suffixes=("_legacy", "_new"), indicator=True)
missing = m[m["_merge"] != "both"]
both = m[m["_merge"] == "both"]
bad = both[sum((both[f"{c}_legacy"] - both[f"{c}_new"]).abs() > 0.005 for c in metrics) > 0]
print(f"rows only on one side: {len(missing)}; rows with value differences: {len(bad)}")

Decide the tolerance up front. Rounding differences between engines are real, and an agreed tolerance (for example, to the cent for currency totals) avoids an argument at sign-off. Differences beyond tolerance are findings: either the rebuild is wrong, or the legacy asset was wrong and the owner must accept the corrected number in writing.

Step 7: Assemble the specification package

The output of this phase is a specification package per asset: a folder in the repository, not a Word document. It carries the extracted files plus the decisions someone made about them.

ArtifactContentProduced by
Model definitionTMDL folder or TMSL file, kept as the archive copy.PBIP, REST definition or get_tmsl
Measure catalogEvery measure with expression, format, folder, and a plain-language purpose written by a person.Script export plus owner review
Relationship and model diagramRelationship list with cardinality and filter direction; a diagram drawn from it.list_relationships or TMDL
Query catalogM per query, source and connection, hard-coded rules, parameters.Script export, manual review
Security specificationRoles, table filters and the intent of each role. Not member lists.Script export plus owner interview
Visual inventoryPage, visual type, bound fields, filters, interactions. Kept as a table, not as image captures.PBIR script, Performance Analyzer
Health findingsVertipaq summary and BPA results with a decision for each finding.DAX Studio, notebook
BaselinesSaved queries, result files and the tolerance agreed.Semantic Link, DAX Studio
Rebuild notesWhich rules move to Silver, Gold or the semantic layer; which are dropped and why.Developer, with the owner
  • Every measure and calculated column has a documented purpose, or an explicit "undocumented, preserved as is".
  • Hard-coded filters in queries and reports are listed with an owner decision: keep, move upstream, or drop.
  • Security intent is written down and agreed with the data owner before the rebuild.
  • At least one baseline exists for each business-critical visual or KPI.
  • Nothing in the package contains real credentials, connection secrets or personal data.
  • The package is committed to the repository and linked from the matrix row.

Hand the package to the build teams: the data engineers use the query catalog for the medallion build, and the BI developers use the measure catalog, security specification and visual inventory for the semantic model rebuild.

Failure modes

SymptomCauseFix
The rebuilt number is off by a stable percentageA hidden filter in a query, a page filter or a role.Diff the query catalog and visual inventory against the new model; replay the baseline with and without each filter.
Published model cannot be downloadedIncremental refresh, Direct Lake, automatic aggregations or a migrated model.Use the model definition API or XMLA; download only the report in live-connected mode.
Definition API call is refusedMissing read and write permission, or an encrypted sensitivity label on the model.Request the permission through the owner; for labeled models use a route the label policy allows.
External tool cannot connect to a published modelWorkspace not on a capacity, or XMLA endpoint disabled.Use the file route, or move the workspace to a capacity first (see the capacity runbook).
Desktop will not open a project after external editsAn edit outside the supported file set, or an encoding problem.Edit only documented files; save UTF-8 without a byte-order mark; work on a copy.
Extraction drags on without endReverse-engineering assets that the matrix says to retire or reassign.Match depth to the matrix decision; stop at the package.

Key takeaways

  • Rebuild from requirements when you have an expert; extract when you do not, or to cross-check. Match the extraction depth to the decision in the matrix.
  • Visit all four layers: queries, model, report and consumption. Hidden filters in queries and reports cause most mismatches.
  • Prefer text artifacts (PBIP, TMDL, PBIR) and scripted exports over image captures and retyped documents.
  • Check which route is available per asset: download, model definition API, XMLA or Git. Each has restrictions.
  • Capture golden baselines before the legacy asset goes away and agree the tolerance up front.
