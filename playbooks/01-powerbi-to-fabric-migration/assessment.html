Playbook 01 · Power BI to Fabric

Legacy assessment and rationalization

Before anything is rebuilt, know what exists, who uses it and what it costs to keep. This page shows how to automate the inventory, work around the short retention of activity data, decide per asset with an explicit tree, and capture the result in a matrix that business and IT sign.

  • Phase I · Foundation
  • Audience program managers, BI leads, business owners, Fabric admins
  • Output signed-off rationalization matrix and migration backlog

Why this step is mandatory

The most common migration mistake is to migrate every asset. It carries forward years of duplicated reports, abandoned models and logic no one can explain, and it makes the project several times larger than it needs to be. A data-driven rationalization is the cheapest scope reduction available, and it also gives the sponsor an auditable answer to "why did you retire my report?"

Treat the inventory as a small data product in its own right: collected automatically, refreshed during the project, and used again at decommissioning to prove that nothing was left behind.

Step 1: Build the inventory automatically

No single source tells you everything. Combine four, each with its own strengths and limits.

SourceGives youLimits to plan for
Scanner (metadata scanning) APIWorkspaces, reports, semantic models, dataflows, dashboards; lineage; data sources; optionally table, column, measure and expression detail and item users.Up to 100 workspaces per request; a scan is requested, polled, then read; results are available for a limited time; requires admin API access, optionally with service principals and two admin-API tenant settings for detailed metadata.
Activity events APIWho did what: views, shares, exports, refreshes, app installs.About 28 days of history; one UTC day per request; paged with continuation tokens; a rate limit of 200 requests per hour; requires a Fabric administrator.
Purview audit logFabric and Power BI activities with longer retention.Retention depends on your audit license and policies; the default for Fabric and Power BI records is 180 days. Extraction is a separate process from the activity events API.
Capacity Metrics appCU consumption per item on the P capacity: which refreshes and queries are expensive.Limited history; export what you need. It describes cost, not business value.

The retention trap

A common plan is to review report views over 90 to 120 days. The activity events API cannot supply that: it keeps roughly four weeks, and the built-in usage and adoption reports in the admin monitoring workspace reflect a rolling 30-day window. A periodic report (a quarterly pack, a year-end report) can look unused for the whole window and still be critical.

Verify against Microsoft Learn

Retention, rate limits and the tenant settings that gate detailed metadata change over time. Confirm them in Access the Power BI activity log, Manage audit log retention policies, Feature usage and adoption report and Set up metadata scanning.

Collection scripts

Connect-PowerBIServiceAccount

$outDir = '.\pbi-activity'
New-Item -ItemType Directory -Force -Path $outDir | Out-Null

# Yesterday, as a full UTC day. The API accepts one UTC day per request.
$day   = [datetime]::UtcNow.Date.AddDays(-1)
$label = $day.ToString('yyyy-MM-dd')

$events = Get-PowerBIActivityEvent `
    -StartDateTime ($label + 'T00:00:00.000') `
    -EndDateTime   ($label + 'T23:59:59.999')

# Keep the raw JSON; transform later (ELT).
$events | Out-File (Join-Path $outDir "activity-$label.json")
$ids  = @('', '')
$body = @{ workspaces = $ids } | ConvertTo-Json

$scan = Invoke-PowerBIRestMethod -Method Post -Body $body `
    -Url 'admin/workspaces/getInfo?lineage=True&datasourceDetails=True&datasetSchema=True&datasetExpressions=True&getArtifactUsers=True' |
    ConvertFrom-Json

do {
    Start-Sleep -Seconds 30
    $status = Invoke-PowerBIRestMethod -Method Get -Url "admin/workspaces/scanStatus/$($scan.id)" |
        ConvertFrom-Json
} while ($status.status -in 'NotStarted', 'Running')

if ($status.status -eq 'Succeeded') {
    Invoke-PowerBIRestMethod -Method Get -Url "admin/workspaces/scanResult/$($scan.id)" |
        Out-File ".\scan-$($scan.id).json"
}
from pyspark.sql import functions as F

# One JSON array per day, written by the export script.
events = spark.read.option("multiLine", True).json("Files/pbi_activity/*.json")

report_usage = (
    events
    .filter(F.col("Activity") == "ViewReport")
    .groupBy("WorkspaceId", "WorkSpaceName", "ReportId", "ReportName", "DatasetId")
    .agg(
        F.count("*").alias("views"),
        F.countDistinct("UserId").alias("distinct_users"),
        F.max("CreationTime").alias("last_viewed"),
    )
)

report_usage.write.mode("overwrite").saveAsTable("inv_report_usage")

For an exact-date inventory snapshot, store the scan results as dated partitions in your lake. The scanner returns current state, so only your own history shows what changed.

Step 2: Usage and performance analysis

Views are the headline signal, but not the only one. Combine them with what the scan and capacity data tell you.

SignalWhat it tells youBlind spot
Views and distinct viewers in the windowReal demand. Many views from one person is a different story than many viewers.Misses seasonal reports and consumers who use apps, subscriptions, embedded views or Analyze in Excel.
Last viewed, last modified, last refreshedDormant assets and abandoned owners.A scheduled refresh keeps running on unused models and can hide their abandonment.
Semantic-model consumersWhich models serve several reports, Excel workbooks or other models; the real unit of migration.Dependencies through live connections to other models and external XMLA clients.
CU consumption per itemExpensive refreshes and queries; candidates for modernization.Cost is not value.
Refresh health and gateway dependenceFragile or on-premises-bound assets that drive effort.Only covers scheduled refresh.
Complexity indicatorsData sources, M steps, measures, calculated tables, security roles, composite models, custom visuals.Needs the model scan or the reverse-engineering tools to measure.
Owner and sensitivityWhether anyone can answer questions about it; which controls apply.Owners often left; confirm through workshops.

Classify with these signals as parameters, not hard-coded rules: set the usage thresholds with the business, and apply them with a notebook so you can rerun when the window grows.

ClassTypical rule (tune with owners)Default action
CriticalHigh views and distinct viewers, or flagged by an owner as operational, executive or regulatory.Prioritize for rebuild or modernize; assign P1.
RedundantMultiple assets with the same purpose, sources or measure definitions.Consolidate into a survivor.
Unused or obsoleteZero or negligible views across a full cycle and no owner objection.Retire after confirmation.
Dormant but protectedLow views, but periodic, regulatory or archival.Reassign as is; place on an exception register.
ShadowAssets in personal workspaces or unmanaged sources with real usage.Bring into a governed workspace or retire.

Include personal workspaces

Personal workspaces can be assigned to a capacity like any other workspace, and the inventory should include them. They are where the shadow assets live, and where a surprising number of executive reports are published from.

Step 3: Decide with an explicit tree

Step 4: Validate with stakeholders

Usage data is a strong argument, not the final one. For each business area hold a short working session with the report owners and a few heavy consumers.

  • Agenda. Review the proposed outcome for each asset; surface low-use assets that are critical; agree the owner for every survivor; agree the decommissioning window and how users will be told.
  • Outputs. Corrected decisions, an exception register of protected dormant assets, named business and technical owners, and acceptance criteria for rebuilds (the metrics that must reconcile).
  • Rules. Nobody is surprised: a retirement is announced before it happens, with a path to object. An owner who cannot be found is a finding in itself.

Failure modes

SymptomCauseFix
A retired report resurfaces as an escalationWindow shorter than the reporting cycle; no owner confirmation.Extend the window or use the audit log; require owner confirmation; keep an exception register.
Scope grows during the buildMatrix signed without owners, or "Defer" used as a default.Sign with owners; allow one deferral with a trigger; change-control additions.
Inventory counts do not match the admin portalPersonal workspaces, deleted items or unscanned workspaces excluded.Include every workspace type; compare counts per capacity.
Models look unused though reports are notUsage measured per report, consumers use the model from Excel or other models.Analyze consumption per semantic model as well.
Scan returns names but no table or column detailDetailed-metadata admin settings are off.Enable the admin-API tenant settings and wait for them to take effect.

Key takeaways

  • Combine the scanner API, activity events, the audit log and capacity metrics; each fills a gap in the others.
  • The activity events API keeps about 28 days. Start a daily export in week 1 or lean on the audit log for a full business cycle.
  • Decide with an explicit tree and record the reason. Consolidate before you assess, retire only with owner confirmation.
  • Keep an exception register for dormant but protected assets.
  • The signed matrix is the scope. Changes go through a log, and the same inventory proves decommissioning later.
