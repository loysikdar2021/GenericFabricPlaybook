Playbook 01 · Power BI to Fabric

Strategy, licensing and capacity migration

Why the move is worth framing as a platform decision, the three paths an asset can take, how F SKU licensing and capacity behavior change the cost model, and the runbook for moving workspaces off Premium capacity without disruption.

  • Phase I · Foundation
  • Audience sponsors, platform leads, capacity owners
  • Output capacity plan and migration path per asset

The strategic case

A migration funded as "the old SKU is going away" produces a new invoice and an unchanged estate. A migration funded as a platform decision produces both. The case worth making rests on four changes, each of which you can later check against a measurable outcome.

  • One platform for the data lifecycle. Ingestion, engineering, warehousing, science and BI share one SaaS surface, one capacity pool and one governance model. Data engineers, analysts and BI developers work against the same lakehouses and warehouses instead of handing files between tools.
  • One copy of the data in an open format. OneLake stores tables as Delta, which Spark, the SQL engines and the Power BI engine all read. The import model that duplicated the same fact table into forty PBIX files stops being the default.
  • Shared, governed semantic models. A small number of certified models serve many thin reports. Business logic lives once.
  • An operating model you can meter. F SKUs are bought and managed as Azure resources: tagged, budgeted, resized, paused and monitored with Azure tooling.

AI-assisted features such as Copilot also run on Fabric capacity, which is often part of the executive narrative.

Verify against Microsoft Learn

SKU, region and tenant-setting prerequisites for Copilot and other AI features change often. Before you put them in a business case, check How Copilot in Microsoft Fabric works and the Copilot overview for your SKU and region.

Be honest about what a reassignment buys

If you only reassign workspaces, you have changed the license and billing model and gained Azure-native cost control. You have not changed how data is prepared, duplicated or governed. That is a legitimate first milestone, but say so in the plan.

Keep the paths independent

Microsoft's own guidance treats consolidation, cross-region moves and modernization such as Direct Lake conversion as separate workstreams that run after the licensing migration. Adopt the same rule: the capacity move should not wait for, or be blocked by, a rebuild.

Licensing: Premium to F SKU

What is being retired, and what is not

Power BI Premium per-capacity SKUs (P1 to P5) are being retired: Microsoft no longer sells new P SKUs, and each P subscription ends at the end of its current agreement term. The supported path for those workloads is a Fabric capacity (F SKU). Several things are explicitly out of scope of the retirement.

  • Per-user licenses are unchanged. Power BI Pro and Premium Per User (PPU) continue. PPU does not provision a Fabric capacity, so it does not run lakehouses, warehouses or notebooks.
  • Embedded SKUs (EM, A) are unchanged. Embedding is also included in every F SKU, so new embedded work does not need a separate SKU.
  • Sovereign clouds are not affected yet, because Fabric is not available there. Check availability for your cloud before planning.
  • Enterprise Agreement terms vary. Customers with an active agreement may be able to renew existing P capacity through the agreement term. Confirm your contract with your Microsoft account team; do not infer it.

Verify against Microsoft Learn

The grace, throttling and blocking periods, and the renewal rules for Enterprise Agreement customers, are policy and can change. Confirm them in the migration decision guide and the migration FAQ before you fix a schedule.

SKU mapping

Capacity units (CU) are the common currency. Each P SKU v-core corresponds to 8 CU, which gives a one-to-one starting point.

F SKUs also exist below F64 (F2, F4, F8, F16, F32) and above F1024 (F2048 and larger). The Fabric trial capacity behaves like an F64 for the trial period. The mapping is a comparison of compute, not a statement of functional or licensing equivalence; the Learn licensing article says so explicitly.

The F64 line: who needs which license

F64 is the smallest SKU on which a user with only a free Fabric license and the Viewer role can view Power BI content, which matches P SKU behavior. Below F64 every viewer needs Pro or PPU. That rule drives the single most consequential cost decision in the plan.

To compare the options, put one formula in the business case. It uses only prices you can look up for your agreement.

extra_monthly_cost_of_F64 = monthly_cost(F64) - monthly_cost(smaller_F_SKU)
break_even_viewers        = extra_monthly_cost_of_F64 / monthly_price_of_one_Pro_license

If you have more viewers than break_even_viewers, F64 (or larger) is the cheaper way to serve them.
Remember to compare using the SKU your workload actually needs, not only the license math.

A smaller SKU can still be correct. A small team of authors who also consume can run on a small F SKU with Pro licenses for everyone. The formula tells you when that stops being true.

Power BI Report Server

Do not assume Report Server rights disappear with the P SKU, and do not assume they carry over. Microsoft's decision guide says Report Server is included with a Fabric reservation of F64 or higher, and is also available through SQL Server Enterprise with Software Assurance. Verify your Report Server licensing before cancelling the P SKU. After migration the Report Server key is on the Fabric capacity tab of Capacity settings in the admin portal.

How capacity behaves under load

A P SKU model is "size for the peak." Fabric sizes for the average, and absorbs peaks through two mechanisms you need to understand before you size anything.

  • Bursting lets an operation use more compute than the SKU provides while it runs, so work finishes fast.
  • Smoothing spreads the CU consumed by that operation over future 30-second timepoints so the burst does not count as a spike. Interactive operations (report queries, user-triggered actions) are smoothed over a minimum of five minutes and up to 64 minutes. Background operations (refreshes, pipelines, notebooks, most Warehouse work) are smoothed over 24 hours.

The consequence is that scheduled jobs can all start together without creating a cliff, and that "CPU was at 100% for a minute" is not an incident. Throttling begins only when the capacity has already committed its next 10 minutes of future compute.

Guardrails: surge protection and isolation

  • Capacity-level surge protection rejects new background operations when the capacity's 24-hour background percentage reaches a threshold you set, and resumes below a recovery threshold. It protects interactive users from background surges; it does not stop jobs already running.
  • Workspace-level surge protection caps what one workspace may consume in a rolling 24-hour window, can block an offender automatically, and lets you mark mission-critical workspaces as exempt. It is a preview capability; confirm status before relying on it.
  • Isolation beats tuning. Put production serving on its own capacity and run development, test and experimentation on another. Microsoft's own guidance says to isolate critical solutions in a designated capacity because surge protection rejects background work broadly.

Capacity migration runbook

This runbook follows Microsoft's guidance for same-region, same-tenant migration, which is the recommended default. The move happens per workspace; there is no tenant-wide switch.

  1. Inventory workspaces and items

    Record workspace name and ID, owners, item types (reports, semantic models with their storage format, dataflows, paginated reports, dashboards), schedules and gateway dependencies. Include every workspace, even ones you believe are Power BI only: users may have created Fabric items during a trial. Use the admin REST APIs or Semantic Link Labs admin functions; the sample below lists workspaces and item counts for one capacity. Baseline CU consumption on the P capacity with the Capacity Metrics app.

  2. Size and buy the F SKU in Azure

    Start with the equivalent SKU for the P SKU, then adjust using the baseline and the SKU Estimator. Register the Microsoft.Fabric resource provider on the subscription, confirm CU quota in the target region, create the capacity in the same region, choose pay-as-you-go or a reservation, and add capacity admins before you reassign anything. Use a custom Azure role limited to Microsoft.Fabric actions instead of Owner or Contributor where you can.

  3. Pilot a low-impact workspace

    Pick a workspace with at least one report, one scheduled refresh and one gateway connection. Reassign it, validate it as in step 5, and fix prerequisites and quirks before touching business-critical content.

  4. Reassign in batches

    In the admin portal open Capacity settings, choose the Fabric capacity tab, select the new capacity, then assign workspaces under "Workspaces assigned to this capacity". For many workspaces use the admin API or the Semantic Link Labs capacity migration notebook. Reassigning cancels jobs running for the workspace's items, so schedule batches outside refresh windows. Do not pause, delete or resize either capacity during the move.

  5. Validate every batch

    Confirm the workspace shows the new capacity; business-critical reports load; a scheduled refresh succeeds (trigger one on demand); gateway connections work and credentials are still valid; deployment pipelines, workspace apps and CI/CD jobs still publish; item counts match the inventory. Watch the Capacity Metrics app for the first one to two days and for a full business cycle including month end. Overload after migration is often a change in workload, not the migration itself.

  6. Review settings that do not move, then cancel the P SKU

    Reapply capacity-level workload settings (for example, semantic model memory limits), re-check the "Users can create Fabric items" tenant setting and capacity-scoped delegations, assign Azure RBAC on the capacity, and tag it for chargeback. After all workspaces validate, cancel the P SKU in the Microsoft 365 admin center and confirm nothing is still assigned to it. Verify Report Server licensing first if you use it.

After reassignment, users may wait up to an hour before they can create Fabric items in a migrated workspace; that is expected workload initialization, not an error.

Cross-region, multigeo and cross-tenant

ScenarioComplexityWhat changes
Same tenant, same regionLowRecommended default. Reassign each workspace; the only downtime is any refresh running at that moment.
Same tenant, different regionModerate to highStandard Power BI items survive. Large storage format semantic models and every Fabric item (lakehouses, warehouses, notebooks, pipelines, eventstreams, Dataflow Gen2 and their hidden staging items) do not: capture definitions to Git, back up data, delete, reassign, then recreate in a separate workspace on the new capacity. Recreated models get new IDs, so reports must be rebound. Gateways and relay endpoints are region-bound.
MultigeoModerateBuy an F SKU per target region and reassign workspaces region by region; plan governance and sizing per region.
Cross-tenantHighNo workspace reassignment. Recreate gateways, models, workspaces, reports, apps and dashboards manually; consider multigeo within one tenant first.

Git sync can delete items

When you restore Fabric items from Git after a cross-region move, restore into a new, separate workspace. Syncing a workspace with a repository can remove any item that is not present in the repository. Verify item counts before moving items into the target workspace.

Key takeaways

  • Fund the project on the platform case, but sequence it so the capacity move stands alone and finishes before your P SKU subscription ends.
  • Decide per asset between reassign, modernize, rebuild and retire, and record it.
  • Make the F64 viewer-license decision with the break-even formula, not by habit.
  • Size for the smoothed average, isolate production on its own capacity, and baseline before you move.
  • Buy first, pilot, reassign in batches, validate, then cancel. Never cancel the P SKU before validation.
