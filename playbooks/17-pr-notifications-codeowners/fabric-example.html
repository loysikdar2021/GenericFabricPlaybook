Fabric folders and enforcement

A Fabric repository has a natural ownership map: one folder per workspace, and inside each folder one subfolder per item. This page turns that map into a working CODEOWNERS file, shows what a real pull request does with it, and makes the owners' approval mandatory.

  • Audience repository admins, workspace and domain leads
  • Use it for a ready-to-adapt file and the ruleset setting

The example repository

The repository follows the layout recommended in the GitHub integration playbook: one folder per workspace, named like the workspace without its environment prefix, plus a few folders that are not connected to any workspace. Ownership follows the people who answer for each layer.

The CODEOWNERS file

# Ownership for contoso-org/fabric-analytics
# The last matching line wins, so keep the order: general first, specific last.

# Default: anything not claimed below
*                       @contoso-org/data-platform

# One folder per workspace (the folder is the workspace name without DEV_)
/SALES_BRZ/             @contoso-org/data-engineering
/SALES_SLV/             @contoso-org/data-engineering
/SALES_GLD/             @contoso-org/analytics-engineering
/SALES_CNSM_WH/         @contoso-org/analytics-engineering
/SALES_CNSM_SM/         @contoso-org/bi-developers
/SALES_DLV/             @contoso-org/bi-developers

# Deployment parameters decide what each environment binds to.
# Listed after the folders so it overrides them, in any folder.
parameter.yml           @contoso-org/data-platform

# Code that is not connected to a workspace
/_deploy/               @contoso-org/data-platform
/_tests/                @contoso-org/data-engineering

# Workflows, this file, and the pull-request template: platform approval always
/.github/               @contoso-org/data-platform
  • Line order is the design. parameter.yml comes after the folder lines, so a parameter file in SALES_GLD/ goes to the platform team and not to analytics engineering.
  • One line per team per path. Where two teams should share a folder, put both on the same line.
  • Matching an item folder. A Fabric item is a folder named <display name>.<Type>, for example NB_SALES_GLD_ChurnScore.Notebook. A pattern such as *.Notebook/ matches every notebook, wherever it is.

What a real pull request does

A developer's pull request changes a notebook in the gold folder, a semantic model definition, the gold parameter file and a runbook:

Changed fileMatching linesOwner requested
SALES_GLD/NB_SALES_GLD_ChurnScore.Notebook/notebook-content.py*, /SALES_GLD/analytics-engineering (last match)
SALES_CNSM_SM/SM_SALES_CNSM_Sales.SemanticModel/definition/model.tmdl*, /SALES_CNSM_SM/bi-developers
SALES_GLD/parameter.yml*, /SALES_GLD/, parameter.ymldata-platform (last match)
_admin/decisions.md*data-platform

Three teams are asked to review: analytics-engineering, bi-developers and data-platform. When owner approval is mandatory, each owned path in the change needs an approval from one member of its owning team, so all three must approve before the pull request can merge. That is what you want: the people who answer for each part sign off on that part.

Keep pull requests focused

A pull request that touches many folders will ask many teams, which slows it down. The feature-branch workflow in the GitHub integration playbook encourages one change per branch for this reason.

Folders or item types?

You can organise ownership by where an item lives, as above, or by what kind of item it is. Pick one as the main axis, because the last-match rule means the two do not combine.

Renames break paths

In a Fabric repository the folder names are generated from workspace folders and item names. Renaming an item in Fabric renames its Git folder, and the next commit moves it. A pattern that names the old path then matches nothing, and the item silently falls back to the catch-all owner. Pattern on stable parent folders, and revisit the file whenever you rename a workspace folder.

Be careful with .platform files

Every item folder has a .platform file, which is where its identity and display name live. Assigning those to a central team gives them oversight of every new or renamed item, but also makes them a bottleneck for every pull request that adds one. Use it only if the platform team really wants that role.

Making owner approval mandatory

Out of the box, a CODEOWNERS review request is only a request: the owner is asked, but the merge does not wait for them. To make the approval a requirement, turn on one option in the ruleset that already protects main.

  1. Merge the CODEOWNERS file first.

    The option enforces the file on the base branch. Enable it only after the file is in place and tested.

  2. Open the ruleset.

    In the repository choose Settings, then Rules, then Rulesets, and edit the ruleset that targets the default branch. If you have not created it yet, follow creating the ruleset for main.

  3. Require a pull request before merging.

    Make sure this rule is enabled; the code owner option sits inside it.

  4. Select Require review from Code Owners.

    Any pull request that changes owned paths now needs approval from an owner of each.

  5. Tighten the neighbours.

    Also select Dismiss stale pull request approvals when new commits are pushed and Require approval of the most recent reviewable push, so an owner's approval applies to what was actually reviewed.

  6. Save, then test.

    Open a pull request that touches an owned path and confirm the merge box says a review is required.

  • Any one owner is enough. If a line lists two teams, an approval from either satisfies it.
  • Owners need Write. An approval from someone without Write access does not count toward the requirement.
  • Bypass actors skip it. Anyone on the ruleset's bypass list can merge without owner approval. Keep that list short.

When two teams must both approve

CODEOWNERS answers "who is responsible for these files", and a single line cannot demand two independent approvals. If a path needs sign-off from two specific teams, for example gold changes that need both analytics engineering and platform, use the ruleset's own required reviewers rule, either instead of or alongside CODEOWNERS.

Verify against GitHub documentation

The required reviewers rule, including its limits on the number of teams and approvals and its availability by plan, is newer than CODEOWNERS and may change. Read Available rules for rulesets before you design around it.

Keeping it true

  • Add a line when you add a workspace and its folder, in the same pull request, with its owning team already granted Write access.
  • When a team is renamed, merged or retired, update the file before the old name stops resolving.
  • Review the file with the quarterly access review described in the operations page: every team still exists, still has Write access and still owns what it should.
  • Treat a pull request that changes CODEOWNERS like a change to a security setting, because it is one.

Key takeaways

  • One line per workspace folder, a catch-all first and exceptions last, gives a readable Fabric ownership map.
  • Sensitive files such as parameter files get their own line after the folder lines so the platform team keeps them.
  • With owner approval mandatory, every owned path in a pull request needs one approval from its owners.
  • The ruleset option Require review from Code Owners turns the request into a requirement; enable it after the file is merged and tested.
  • When two teams must both approve, add the ruleset's required reviewers rule.
  • Renaming a Fabric item renames its folder, so pattern on stable parent folders.
