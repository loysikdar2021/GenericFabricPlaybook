Playbook 17 · PR Notifications

Pull-Request Notifications with CODEOWNERS

You cannot make GitHub send an email. What you can do is guarantee that the right people are asked to review every change to the files they own, and that nothing merges until they say yes. Whether that request then reaches an inbox, a mailbox or a phone is decided by settings that belong to the team and to each person.

  • Audience repository admins, platform leads, reviewers
  • Level Intermediate
  • Reading time 35 min

What this playbook solves

In a Fabric repository, a pull request can change a notebook, a pipeline, a semantic model and a deployment parameter file in one go. Each of those has a different owner, and the owner is rarely the person who opened the pull request. Relying on authors to remember whom to tag fails in predictable ways: the reviewer is a friend rather than the owner, the owner learns about the change after it has merged, or nobody is asked at all.

GitHub has a native answer, the CODEOWNERS file. It links file paths to people or teams. When a pull request touches a path, the owners of that path are requested as reviewers automatically, and with one ruleset option their approval becomes mandatory. This playbook shows how to set that up for a repository laid out as in the GitHub integration playbook, and how to reason about the notifications that follow.

The request is yours; the email is theirs

As a repository admin you can trigger a review request. You cannot force an email. Whether the request becomes an email, an inbox entry or a mobile alert depends on the team's code review settings and on each owner's own notification settings. Everything on the notifications page follows from this.

From pull request to notification

Who controls what

Most confusion about CODEOWNERS notifications comes from expecting one person to control everything. Three different people control three different layers, and each layer can silently stop the chain.

Two native mechanisms, two different jobs

GitHub has two built-in ways to ask a named person or team for a decision. They are often confused, and the second is not a notification feature at all.

Environment reviewers are asked only when a deployment is actually waiting for approval. They are not told about every merge to main. If you want people to hear about merges, use repository watch settings or a workflow that posts to a chat channel.

Vocabulary

TermMeaning
CODEOWNERS fileA text file that maps path patterns to owners. One file applies to one branch.
Code ownerA user or team named in that file. It must have Write access to the repository.
Review requestGitHub adds the owner to the pull request's Reviewers list. This is the event that generates a notification.
Require review from code ownersA ruleset option on the pull-request rule that makes an owner's approval mandatory for the merge.
Team code review settingsTeam-level options that limit who is notified when the team is requested, and optionally pick individual reviewers.
Notification settingsA person's own choices for how GitHub reaches them: inbox, email, mobile.

Before you start

  • A GitHub organization with teams that mirror ownership, ideally synced from Entra ID groups, as described in the identity section of the GitHub integration playbook.
  • Every owner team has Write access to the repository, and is visible to the people who will open pull requests.
  • A ruleset on main that requires pull requests, so that a pull request is the only way a change lands. See rulesets.
  • A repository layout where ownership follows folders, such as one folder per workspace. See the recommended layout.
  • A GitHub plan that supports code owners and, for team settings, organization-owned repositories. Confirm the current plan rules in the GitHub documentation.

Key takeaways

  • CODEOWNERS assigns reviewers; it does not send mail. Delivery is decided by team settings and by each person's notification settings.
  • Owners must have Write access, and teams must be visible. Prefer teams to individuals.
  • Make approval mandatory with Require review from code owners in the ruleset, or the request is only a suggestion.
  • Environment reviewers are a different mechanism: they approve deployments, not pull requests, and are not notified of every merge.
