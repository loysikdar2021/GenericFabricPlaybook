Playbook 17 · PR Notifications

Notifications and troubleshooting

Once GitHub has asked an owner to review, the message is no longer yours to shape. It passes through the team's code review settings and then through the person's own notification settings. Knowing both layers is the difference between "it should have worked" and a fix.

  • Audience repository admins, team maintainers, reviewers
  • Use it for routing, personal setup, diagnosing silence

A review request is not an email

When a pull request is opened, or moved out of draft, GitHub adds each matching owner to the pull request's Reviewers list. That is the review request. GitHub's notification system then takes the request and delivers it to the people concerned, on the channels they have enabled. An email is one possible result, not a guaranteed one.

You, as repository adminYou cannot
Decide who is requested, with the CODEOWNERS file.Force an email to be sent.
Make the owner's approval mandatory, with the ruleset.Change what an owner has turned off in their own notification settings.
Ask team maintainers to narrow or spread the notification, with team code review settings.See whether a given owner received the email.

Owners are not requested on draft pull requests. When the author marks the pull request ready for review, the owners are requested and notified at that point.

Team settings: who in the team is told

When the owner on a CODEOWNERS line is a team, the request goes to the team, and the team's own Code review settings decide how many of its members are told. There are three behaviours:

SettingEffect
Only notify requested team membersIf someone from the team is also requested by name on the pull request, only that person is notified, not the whole team. Useful when authors often know the right individual.
Enable auto assignmentWhen the team is requested, a chosen subset of members is assigned in its place. You set how many members are assigned.
  Routing algorithmRound robin alternates between members, choosing whoever was asked longest ago. Load balance considers each member's recent and outstanding requests and aims for an even share.
  Never assign certain team membersAlways skips the named members, for example a lead who should only be a backstop.
  Child team membersIncludes members of child teams as candidates.
  Count existing requestsCounts members already requested against the number to assign.
  Team review requestRemoves the team's own request from the pull request when individuals are assigned.
  • Busy members are skipped. Members whose GitHub status is set to Busy are not chosen. If everyone is busy, the pull request stays assigned to the team itself.
  • Required code owner review keeps the team on the request. When the ruleset requires code owner review, the team's request cannot be removed. The assigned individual appears in addition, and the team is removed once that person completes their review.
  • Who can change it. Team maintainers and organization owners, under the team's Settings, then Code review. Availability depends on the plan and on the repository being owned by an organization.

For Fabric repositories a practical rule is: leave small teams on the default, so everyone sees every request; give large teams auto assignment of one or two reviewers with load balancing, so someone is clearly responsible and nobody is pinged for every change.

Personal settings: how each owner is reached

The last layer belongs to each person, and no administrator can change it for them. Every code owner should check the following once.

  1. Open the settings.

    Select the notifications inbox icon, then Manage notifications, then Notification settings.

  2. Enable both channels.

    For Participating and for Watching, select both Email and On GitHub. The notifications inbox only works when both are enabled.

  3. Choose a verified address.

    Set the default email address that receives notifications, and confirm it is verified. If the organization restricts notifications to an approved domain, verify an address in that domain.

  4. Check repository watch settings.

    On the repository page, Watch must not be set to Ignore. Custom with pull requests selected is a good choice for a reviewer.

  5. Consider mobile.

    GitHub Mobile can push alerts for requests to review a pull request and for requests to approve a deployment.

  6. Test it.

    Ask a colleague to request your review on a throwaway pull request. Confirm it appears in the inbox, filter by reason:review-requested, and that the email arrives.

ChannelWhat must be trueNotes
Notifications inboxOn GitHub is enabled, and Email too, for the relevant category.Inbox items are kept for a limited time unless saved. Mark review requests as saved if you need to act later.
EmailEmail is enabled and the address is verified and not blocked by an organization domain restriction.The subject typically carries the repository name and pull request title, and the body links to the pull request. Each message includes a header that states the reason (a review request), which is useful for mail rules.
GitHub MobileThe app is installed and the push types are enabled.Working hours can be scheduled in the app.

Verify against GitHub documentation

Menu labels, default values and the way review requests are classified under Participating and Watching change between releases of GitHub's interface. Treat the steps above as the shape of the setup and check them against Configuring notifications.

What the pull request page shows

WhereWhat you see
Reviewers list, right sidebarThe requested owners and teams, each with a status icon. A pending review shows a yellow indicator; an approval or requested changes replaces it once the person responds.
Merge boxThe ruleset's verdict. With the code-owner option on, it reports that a review is required until an owner approves.
A file's headerHover over the shield icon to see who owns the file and which line of CODEOWNERS says so.
Notifications inboxThe request itself, labelled with the reason it was sent.

For the owner, the review is: open the notification, go to Files changed, read the diff (see what reviewers look for in a Fabric diff), choose Review changes, select Approve or Request changes, and submit.

Deployment approvals are a different notification

Environment required reviewers receive a request when a deployment job is waiting for approval, not when code is merged. They can be notified by email, in the inbox, or on GitHub Mobile, which supports alerts for deployment approval requests. If you want people to hear about every merge to main, use a repository watch setting with pull requests selected, or a workflow step that posts to a chat channel. Troubleshooting: nobody was notified

Work through the layers in order. Each question rules out one layer.

SymptomLikely causeWhat to do
Owner is not on the Reviewers listThe file is not on the base branch; the path pattern does not match (case, renamed folder); the team or user lacks Write access or is not visible; the pull request is a draft; a later line overrides this one.Check each, using the validation steps on the file page. Hover the file's shield icon to see the line that applies.
Only one person of several owners is requestedThe owners are on separate lines, so only the last line applies.Put the owners on one line, or use a team.
The author is the only ownerThe author cannot approve their own pull request, so no valid owner approval exists.Add a second owner or a team. Do not solve it by adding the author to the bypass list.
The pull request cannot merge and no owner is availableAll owners are away, left the company, or busy, and the ruleset requires owner approval.Have an organization owner add a member to the team. Keep teams at three or more people, with a deputy.
The whole team is notified for every changeThe team is on default settings and a broad pattern, such as the catch-all, names a large team.Enable auto assignment, or narrow the patterns.
The owner is requested but gets nothingEmail and On GitHub are off, the repository is ignored, the address is unverified or outside an approved domain, or a mail rule files it away.Walk through the personal setup above, then filter the inbox by review requests.
Requests stopped after a Fabric item was renamedThe item's folder was renamed, so the pattern no longer matches and the catch-all applies.Update the pattern, and prefer stable parent folders.
No request when a team of owners is requestedThe team does not exist, is secret, or has no Write access.Make the team visible and grant it Write access to the repository.

Go-live checklist

  • The CODEOWNERS file is in .github/ on main, with the catch-all first and specific lines last.
  • Every owner is a team, every team has Write access, and every team is visible to contributors.
  • A test pull request touching one path per rule produced exactly the expected Reviewers list.
  • Require review from Code Owners is enabled in the ruleset for main, together with stale-approval dismissal.
  • /.github/ is owned by the platform team.
  • Large teams have auto assignment configured; small teams are on the default.
  • Each owner has confirmed their notification settings and received a test request.
  • The ownership file is part of the quarterly access review.

Key takeaways

  • A review request is not an email. Team settings decide who in a team is told; personal settings decide how.
  • Use auto assignment for large teams and the default for small ones.
  • Each owner must enable Email and On GitHub, use a verified address and check that the repository is not ignored.
  • When nobody is notified, check the Reviewers list first, then team settings, then personal settings, then email delivery.
  • Environment reviewers approve deployments, not pull requests.
