Creating the CODEOWNERS file

The file is a dozen lines of text, and almost every way it goes wrong is silent: a pattern that matches nothing, an owner without Write access, a second owner on a second line. Nothing errors out; nobody is simply asked. This page covers the rules that matter.

  • Audience repository admins, platform leads
  • Use it for writing, placing and validating the file

Where the file lives

GitHub looks for a file named CODEOWNERS (all capitals, no extension) in three places, in this order, and uses the first one it finds:

  • One file, one branch. A CODEOWNERS file assigns owners for the branch it sits on. Review requests are generated from the copy on the base branch of the pull request, which for Fabric work is main.
  • Edits take effect on merge. A pull request that changes CODEOWNERS is itself judged by the version that is already on main.
  • Size. The file must be under 3 MB; a larger file is not loaded at all and no owners are requested. Wildcards keep it small.
  • Who can edit it. Anyone with Write access can propose a change. Because main is protected, the change goes through a pull request like any other.

Creating it

  1. Start a branch.

    Because main is protected by a ruleset, open the repository and create a branch, for example chore/1301-add-codeowners, rather than committing to main.

  2. Create the file.

    Choose Add file, then Create new file. In the name box type .github/CODEOWNERS; typing the slash creates the folder. Use capitals and no extension.

  3. Write the rules.

    Start with the catch-all and add specific lines below it (next sections).

  4. Open a pull request and merge it.

    Have the platform team approve it. From the moment it merges, later pull requests use it.

Syntax

Each line is a path pattern followed by one or more owners. The patterns follow most of the .gitignore rules; # starts a comment.

# Default owners for everything in the repository
*                      @contoso-org/core-team

# Own every SQL file, anywhere
*.sql                  @contoso-org/data-engineering @contoso-org/dba-team

# Own a directory at the repository root and everything below it
/docs/                 @contoso-org/tech-writers
/backend/api/          @contoso-org/backend-team

# Own one specific file
/config/database.yml   @contoso-org/platform-team
PatternMatches
*Every file, unless a later line also matches. The usual catch-all.
*.sqlEvery file with that extension, at any depth.
/docs/The docs directory at the repository root and everything inside it, including subdirectories.
docs/*Files directly in docs, but not files in its subdirectories.
apps/Any directory named apps, wherever it is, and its contents.
**/logsAny logs directory at any depth.
/apps/github with no ownerClears ownership for that path, so the more general line above it no longer applies there.
  • Paths are case sensitive. /Sales_GLD/ does not match SALES_GLD/, even if you work on a case-insensitive system.
  • Some .gitignore features do not work here: negation with !, character ranges with [ ], and escaping a leading # with a backslash.
  • Invalid lines are skipped. Valid lines still work, so a typo costs you one rule, not the file.

Order matters: the last match wins

For each changed file GitHub reads the file from top to bottom and uses the owners of the last line that matches. Earlier matches are discarded, not added. That is what lets you write a broad default and refine it, and it is also the usual reason a pull request goes to the wrong team.

Owners: users, teams and email

FormExampleNotes
Team@contoso-org/data-engineeringRecommended. Membership changes without editing the file. The team must be visible and have Write access to the repository, even if every member already has access some other way.
User@example-userMust have Write access. Use sparingly: when the person leaves, the line silently stops working.
Emailuser@contoso.comResolves to the account that has that address. Not available for Enterprise Managed Users.

Several owners belong on one line

Owners listed on the same line share the pattern, and an approval from any one of them satisfies the requirement. Owners on separate lines do not combine: the last line replaces the earlier ones.

# Wrong: only the last line applies, so only data-platform is the owner
/SALES_GLD/   @contoso-org/analytics-engineering
/SALES_GLD/   @contoso-org/data-platform

# Right: both teams are owners, and either one can approve
/SALES_GLD/   @contoso-org/analytics-engineering @contoso-org/data-platform

A silent failure that is easy to copy

A common first draft lists the members of the owning team one per line under a single *. Only the last person is then the owner, and everyone else is never asked. Put the people in a team and name the team once.

Owners must be able to write

If a named user or team does not exist, or lacks Write access, GitHub assigns nobody for that line and shows no error on the pull request. Check team access before you rely on a line. The troubleshooting guide lists the other silent causes.

If you need two different teams to both approve a change, a single line cannot do it. The ruleset has a separate required reviewers rule for that, covered on the next page.

Protect the file itself

Whoever controls CODEOWNERS controls who must review everything else. If a developer can change the file and approve their own change, the whole mechanism is optional. Close the loop by owning the file, and the folder that holds your workflows:

/.github/   @contoso-org/data-platform

With the code-owner rule enabled, a pull request that edits CODEOWNERS or a workflow now needs the platform team's approval, exactly as it should.

Validate before you rely on it

  • Open the file on GitHub. Invalid lines are highlighted with an explanation.
  • Browse to a file you expect to be owned and hover over the shield icon in its header. The tooltip names the owner and the line of CODEOWNERS it came from.
  • List the errors programmatically if you manage many repositories: the REST API has an endpoint that lists CODEOWNERS errors for a repository.
  • Open a test pull request that touches one path per rule, then read the Reviewers list. Every owner you expect should appear, and nobody else.
  • Confirm that each owning team has Write access and is visible, by opening the repository's access settings and the team page.
MistakeWhat happens

Folder renamed in the repositoryThe old pattern matches nothing. For Fabric, renaming an item or a workspace folder renames the Git folder.

Key takeaways

  • Put CODEOWNERS in .github/ on the branch that pull requests target. Only the first file found is read.
  • The last matching line wins and earlier matches are discarded. Order from general to specific.
  • Name teams, put co-owners on the same line, and give every team Write access.
  • Own .github/ with the platform team so the file cannot be changed without its approval.
  • Failures are silent, so test with a pull request and read the Reviewers list.
