Framework design and decisions

Before you build, decide what the framework is, what it will and will not do, and how it behaves when tasks fail, overlap or need to be re-run. This page covers the principles, the end-to-end flow, prerequisites, the example topology, a decision table against alternatives and the design guidance that the later pages implement.

Principles of control-table-driven orchestration

To orchestrate hundreds of PySpark notebooks and SQL scripts reliably, shift control flow out of hand-built pipeline wiring and into a configuration layer. By separating the what (a row in the control table that defines a task) from the how (a generic engine that executes any task), you get reuse, consistency and a platform that changes by data entry instead of by deployment.

A control-table framework uses configuration data to drive execution. Rather than building one pipeline per source or transformation, you build a small set of reusable pipelines that read their instructions at run time from the control table: which notebook to run, in which workspace, in which stage, owned by whom, notifying which address.

That changes the development lifecycle in four ways:

  • Agility. Onboarding a task is a planned data-entry step. The framework picks the new row up on the next run, so the time to add a workflow drops from days to minutes once the engine exists.
  • Consistency. Every task is logged, retried and reported by the same tested template, so behavior does not drift from one pipeline to the next.
  • Less duplication. One copy of the logging, error handling and notification logic replaces dozens of copies, and one fix repairs all of them.
  • Simpler governance. The control table is a de facto catalog of every data operation. Lineage questions, impact analysis and change review become queries and pull requests against a table or its seed script.

The cost is real and worth naming: you now own a framework. It needs a guard step, tests, versioned seed scripts and an owner, and it constrains how much pipeline logic can depend on run-time data. The decision table below helps you judge whether that trade is right.

What the playbook delivers

  • A control table and a task-dependency table in a Warehouse, with seed scripts. The control table is the system of record for your DAG: each row is a task with its type, stage, order, target IDs, parameters and notification targets.
  • An append-only run log that records every start and end event. Because it never updates in place, it avoids the snapshot-isolation update conflicts that appear when many parallel tasks write status to the same table.
  • Stored procedures the pipeline calls to validate configuration and write log events.
  • A rename-proof notebook launcher that runs notebooks by item ID through the Fabric job-scheduler API and polls the job until it completes, plus an assessment of when the native Notebook activity is the better choice.
  • A master pipeline design using Lookup to fetch a stage's tasks, ForEach to iterate them in parallel or in sequence, Switch to run the right activity for each task type, and failure paths that log and notify.
  • Failure notification through a reusable pipeline that wraps the Office 365 Outlook activity, with recipients taken from the control table.

How it works, end to end

  1. Declare tasks in the control table.

    Each row defines a task: task_type (Notebook, StoredProcedure, Pipeline), stage, sequence_no, the target IDs, and notify_to. This keeps orchestration data-driven and easy to review under change control.

  2. Stage the orchestration.

    The pipeline runs one loop per stage: ingests in parallel, transforms in sequence after the ingests, post-load SQL in sequence after the transforms. Each Lookup filters the table for one stage and each ForEach iterates @activity('Lookup_Stage1').output.value.

  3. Execute the work.

    A Switch on task_type sends notebook tasks to the launcher or the Notebook activity, procedure tasks to a Script activity that runs the named procedure, and pipeline tasks to Invoke pipeline. A failure inside any case is raised to the Switch so the failure path can run.

  4. Log and notify inside the iteration.

    Each iteration writes a Started event on entry and a Succeeded or Failed event on exit, with no in-place updates, and sends a notification on failure to the addresses in the row. Keeping these steps in the same ForEach iteration gives them access to the activity's error output.

  5. Observe and govern.

    Use the Monitor hub for run history and the Gantt view, and the log tables for ad-hoc queries and dashboards.

Why this approach

  • Deterministic and auditable. A single table declares the DAG, the pipeline reads it exactly as it is at run time, and the append-only log is an immutable trail of every attempt and outcome.
  • Parallel where it is safe, sequential where it is needed. ForEach settings balance throughput and dependencies, and the batch count caps concurrency.
  • Rename-proof execution. Referencing items by ID instead of by display name removes a whole class of brittle failures. The dispatcher page covers how and where that holds.
  • Native building blocks. Lookup, ForEach, Switch, Stored procedure, Script, Notebook, Invoke pipeline and the Outlook and Teams activities are all documented Fabric activities, observable in the Monitor hub.

Prerequisites

  • A Fabric workspace with Data Factory and a Warehouse for the control table, logs and procedures (the hub workspace).
  • Permission to run pipelines and to execute procedures in that workspace, and Contributor access (or higher) to every workspace whose notebooks and pipelines you will orchestrate.
  • A mailbox or a Teams channel for failure notifications. With a user connection the Outlook activity sends from that account, so use a team-owned account and not a personal one; a workspace identity or service principal is the alternative and needs admin-consented Microsoft Graph permissions.
  • For hub-and-spoke topologies, an identity authorized to invoke pipelines across workspaces: a service principal or a workspace identity.
  • An Azure Key Vault if any notebook authenticates with a service principal secret.

Scenario and topology

The worked example uses one orchestration hub workspace and two data workspaces. The hub holds the Warehouse with the control table, run log and procedures, the master pipeline and the dispatcher. Ingest notebooks live in the Bronze workspace, the transform notebook in the Silver workspace (see Medallion Architecture for the layout), and the two stored procedures live in the hub Warehouse.

Where do procedures live?

The Script activity that runs a task's procedure uses one Warehouse connection. Keep the procedures the framework calls in the control Warehouse, and let them reach other warehouses in the same workspace with three-part names, rather than multiplying activities per target warehouse.

Combine, do not choose

These approaches compose. A control-table task can be a Copy job activity for ingest, a notebook that runs a small DAG internally, and a child pipeline owned by a spoke team. The hub-and-spoke playbook describes how spokes expose pipelines for a hub to invoke; the control table is a convenient way to drive that hub.

Design guidance

Ordering: stage, sequence and dependencies

Model ordering explicitly. Three columns carry it:

  • stage is a gate. All enabled tasks of stage n must succeed before stage n+1 starts. It maps to one Lookup and ForEach pair.
  • sequence_no orders tasks inside a stage that runs sequentially. It is also the tie-breaker for parallel stages: order long-running tasks first so they start first.
  • ctl.task_dependency records which task depends on which. By itself it documents the DAG and lets the guard step catch mistakes such as a dependency on a later stage. Optionally it drives a per-task gate.

Never order by task name

A common shortcut is to name tasks 01_..., 02_... and rely on ORDER BY task_name. It breaks as soon as a stage mixes tasks or the numbering is reused: in one early build, tasks sorted within a stage by name ran in the reverse of the intended order. A numeric sequence_no column removes the ambiguity.

Idempotency and restarts

Assume every task can be run twice. Pipelines retry, people rerun, and a failed run is restarted. Write notebooks so that a repeat produces the same end state (overwrite a partition or MERGE on a key) and write procedures with TRUNCATE then insert, or MERGE, inside a transaction. The framework itself never promises exactly-once execution.

To restart a failed run without repeating finished work, give the master pipeline a restart_run_id parameter. Each stage's Lookup excludes tasks that already have a Succeeded event in that run:

SELECT c.task_id, c.task_name, c.task_type, c.object_name, c.object_id, c.target_workspace_id,
       c.parameters_json, c.notify_to
FROM ctl.control_table AS c
WHERE c.is_enabled = 1
  AND c.stage = 1
  AND c.task_name NOT IN (
        SELECT s.task_name
        FROM ctl.vw_task_last_status_per_run AS s
        WHERE s.run_id = '@{pipeline().parameters.restart_run_id}'
          AND s.last_event = 'Succeeded')
ORDER BY c.sequence_no, c.task_name;

With an empty restart_run_id the subquery matches nothing and every enabled task runs. Because configuration can change between the failed run and the restart, treat a restart as "run what is enabled now, minus what already succeeded".

Retries and timeouts

  • Use the activity's own retry for transient errors. Pipeline activities can retry automatically (the retry count, interval and optional retry conditions are set per activity). By default a retry fires on any failure; retry conditions, which are in preview and supported for specific activity types including Notebook and Stored procedure, let you retry only on matching error codes or messages such as throttling.
  • Retry counts are static. They are not read from a row. If different tasks need different retry policies, group them into different stages or retry inside the dispatcher, where you can log each attempt.
  • Do not retry logic errors. A schema mismatch fails the same way every time and wastes capacity.
  • Set timeouts below the default. The activity default is 12 hours; a hung task holds a stage and its capacity for that long. Pick a timeout per task type and let a timeout_minutes column drive the dispatcher's own limit.

Concurrency limits

Set the ForEach batch count by the scarcest resource, not by the number of tasks. The scarce resource is rarely the pipeline.

The ForEach batch-count maximum and the nesting rules above are documented for Azure Data Factory; the Fabric ForEach article does not restate them. Confirm in the pipeline editor, and read Job queueing in Apache Spark for Fabric for the current queue limits.

Dynamic parameters and JSON configuration

Tasks differ in small ways: a load window, a table name, a mode flag. Resist adding a column for each. A nullable parameters_json column holds a JSON object that the pipeline passes to the task as one string parameter; the notebook parses it with json.loads and applies defaults. Keep frequently queried settings (load_mode, timeout_minutes) as typed columns, and use JSON for the long tail. Warehouse tables cannot hold a JSON data type, so store it as VARCHAR, and validate it in the notebook or a pre-check rather than relying on database-side JSON functions.

Extensibility to new task types

A task type is a contract: required columns plus one branch in the Switch. To add Spark job definitions, Dataflow Gen2 refreshes, Copy jobs, semantic model refreshes or web calls, you add the type name to the guard procedure's list of valid types, add a Switch case that maps row columns to the activity's settings, and add a row-level rule to the guard (for example, a Copy job task must have object_id). The engine's logging, notification and ordering stay untouched. The master pipeline page shows the Switch.

Key takeaways

  • Use the pattern when many tasks share one run, log and notify shape; use plain pipelines when they do not, and a Copy job when the work is table copy.
  • Model order with stage, sequence_no and a dependency table; never rely on names. Choose stage gates or dependency gates deliberately.
  • Make every task idempotent and support restart by excluding already-succeeded tasks.
  • Size concurrency to Spark capacity and Warehouse conflicts, not to the number of rows.
  • Keep activity retry and timeout static and conservative; put per-task variation into the dispatcher.
