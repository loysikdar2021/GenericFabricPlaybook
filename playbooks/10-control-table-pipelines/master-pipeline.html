Build the master pipeline

The master pipeline is the only pipeline that knows the framework. It validates the configuration, reads the tasks for one stage, loops over them, runs the right activity for each task type, and records every outcome. This page builds it activity by activity, explains the failure semantics that decide whether a stage blocks the next one, and adds a reusable notification pipeline.

The pipeline at a glance

One pipeline, PL_ORCH_HUB_Master, in the hub workspace. It has a guard, then one Lookup and one ForEach per stage. Every arrow between stages is an On success dependency, so a failed stage stops everything after it.

ActivityTypeRuns afterPurpose
Guard_ValidateStored procedureStartFail before any work if the configuration is inconsistent.
Lookup_Stage1LookupGuard succeededRead the enabled tasks of stage 1.
ForEach_Stage1ForEachLookup succeededRun the ingests in parallel.
Lookup_Stage2, ForEach_Stage2Lookup, ForEachStage 1 succeededRun the transform.
Lookup_Stage3, ForEach_Stage3Lookup, ForEachStage 2 succeededRun the stored procedures in sequence.

Activity names must be unique inside the pipeline, so the activities inside each ForEach carry a stage suffix (_S1, _S2, _S3). The child-pipeline variant below removes the triplication once the design is stable.

Before you build

  • The Warehouse objects exist, the control table is seeded and the guard runs clean (previous page).
  • The dispatcher notebook exists, or you have confirmed the native Notebook activity accepts dynamic IDs (dispatcher page).
  • One Warehouse connection to WH_ORCH_HUB_Control for the Lookup, Script and Stored procedure activities.
  • A connection for the Notebook and Invoke pipeline activities, using the identity chosen on the design page.

Guard step

Add a Stored procedure activity named Guard_Validate that runs dbo.usp_validate_control_table. It has no parameters. Every later activity depends on its success.

Give it both outcome paths:

  • On failure: Log_Guard_Failed (Stored procedure, dbo.usp_log_event) with task_name set to (pipeline), event Failed and the guard's error as the message, then Notify_Guard_Failed (Invoke pipeline, the notification pipeline) addressed to default_notify_to.
  • On success: Lookup_Stage1.

The message expression is @activity('Guard_Validate').error.message.

Why a guard at all

Primary key and unique constraints are metadata-only in Warehouse, so the engine will happily accept two rows with the same task name or a task whose ID is blank. The guard turns those into a clean failure at the top of the run instead of a confusing one halfway through.

Stage lookups and ForEach settings

Each stage has a Lookup and a ForEach. The Lookup returns the stage's enabled tasks; the ForEach iterates them.

Settings for Lookup_Stage1: connection to the Warehouse, Use query set to Query, and First row only turned off.

SELECT c.task_id, c.task_name, c.task_type, c.stage, c.sequence_no,
       c.object_name,
       COALESCE(c.object_id, '')           AS object_id,
       COALESCE(c.target_workspace_id, '') AS target_workspace_id,
       COALESCE(c.parameters_json, '{}')   AS parameters_json,
       COALESCE(c.timeout_minutes, 60)     AS timeout_minutes,
       COALESCE(c.max_attempts, 1)         AS max_attempts,
       COALESCE(c.notify_to, '')           AS notify_to
FROM ctl.control_table AS c
WHERE c.is_enabled = 1
  AND c.stage = 1
  AND c.task_name NOT IN (
        SELECT s.task_name
        FROM ctl.vw_task_last_status_per_run AS s
        WHERE s.run_id = '@{replace(pipeline().parameters.restart_run_id, '''', '''''')}'
          AND s.last_event = 'Succeeded')
ORDER BY c.sequence_no, c.task_name;
  • The COALESCE calls fill defaults once, in SQL, so the expressions inside the loop never meet a missing or null property.
  • The restart clause is empty-safe: with no restart_run_id the subquery returns nothing and every enabled task runs. The replace doubles any single quote, so the parameter cannot break out of the string.
  • Lookup_Stage2 and Lookup_Stage3 are identical except for c.stage = 2 and c.stage = 3.
  • A Lookup returns at most 5,000 rows and 4 MB. A stage that large needs splitting into several stages.

The ForEach activity article does not say what a sequential ForEach does after one iteration fails, and the batch-count maximum is documented for Azure Data Factory. Do not assume that stage 3 stops after the first failure: run a test with a failing first task, and use the dependency gate if a task must never run after its prerequisite failed.

The per-task body

Everything inside a ForEach is the same, apart from the stage suffix. It has five activities: log the start, run the right activity for the task type, then either log success or log failure and notify.

Logging activities

All three logging activities are Stored procedure activities that call dbo.usp_log_event through the Warehouse connection, with typed parameters. Typed parameters avoid the quoting problems of building SQL text from an error message. Click Import to load the parameter list, then set the values:

ParameterTypeValue
run_idString@pipeline().RunId
task_nameString@item().task_name
stageInt32@item().stage
activityStringTask
eventStringStarted in Log_Started, Succeeded in Log_Succeeded, Failed in Log_Failed
messageStringNull, except in Log_Failed: @activity('Run_Task_S1').error.message
external_idStringNull. Activities inside a Switch case are not visible from outside it; to record a job instance ID, log from inside the case.

Wire the dependencies: Log_Started first, then Run_Task_S1 on its success. Log_Succeeded_S1 runs on the success of Run_Task_S1. Log_Failed_S1 runs on its failure, and Notify_Failure_S1 on the success of Log_Failed_S1.

Verify against Microsoft Learn

When a Switch fails, the error message on the Switch activity is expected to carry the inner activity's error, but the Fabric articles do not show its exact form. Run a deliberate failure once and read Run_Task_S1's error in the Output pane before trusting the expression. If the text is too generic, move the logging into each case (the dependency-gate variant does this).

Switch on task type

Add a Switch activity named Run_Task_S1. Set Expression to @item().task_type. Cases match the exact text, so they are case-sensitive and must equal the values the guard allows.

Keep each case to one activity. A Switch cannot contain an If, and an If cannot contain a Switch; if a case needs more logic, move it into a child pipeline.

In the activity's General settings, set the retry count to 0, because the dispatcher already retries, and set the timeout explicitly above the longest task's timeout multiplied by its attempts, instead of keeping the 12-hour default.

Natively. If the Notebook activity's workspace and notebook fields accept dynamic content, set them to @item().target_workspace_id and @item().object_id and pass task_name, run_id and parameters_json as base parameters. This avoids the extra session and keeps pipeline queueing.

Verify against Microsoft Learn

The Notebook activity article does not describe the activity's output. Run it once and open the Output pane to see where the notebook's exit value appears (commonly under output.result.exitValue) before writing any expression that reads it, such as @json(activity('Run_Notebook_S1').output.result.exitValue).job_instance_id.

Case StoredProcedure

Use a Script activity named Run_Procedure_S1 on the Warehouse connection, with Script type set to NonQuery and this script:

EXEC @{item().object_name};

The Stored procedure activity binds a procedure when you author it, and its parameter list is fixed at that point, so it cannot serve a table of different procedures. The Script activity can. The name comes from a table, which is why the guard insists that every procedure follows dbo.usp_* and exists: a row can only run a procedure, never arbitrary SQL. If a procedure needs arguments, give them defaults and put non-default values in parameters_json for the procedure to read, or extend the script.

Case Pipeline

Use an Invoke pipeline activity named Run_Pipeline_S1. Set Type to Fabric, choose the connection, and point the workspace and pipeline fields at @item().target_workspace_id and @item().object_id if dynamic content is accepted. Pass the same three values every orchestrated pipeline should accept:

ParameterValue
task_name@item().task_name
run_id@pipeline().RunId
parameters_json@item().parameters_json

Make sure the activity waits for the invoked pipeline to finish, so that a failed child fails the task. Use the new Invoke pipeline activity, because the legacy one only reaches pipelines in the same workspace.

Verify against Microsoft Learn

The Invoke pipeline article shows the workspace and pipeline chosen from dropdowns and does not say whether they accept expressions. If they do not, the Pipeline case needs one Invoke activity per known pipeline, or a dispatcher-style notebook that calls the Job Scheduler API for a pipeline.

Default case

Add a Fail activity named Fail_UnknownType_S1. Message: @concat('Unknown task_type ', item().task_type, ' for task ', item().task_name); error code: UnknownTaskType. The guard should have caught this already. The default case is the backstop for a configuration that bypassed it.

Success and failure paths: what decides the stage result

The most important property of this design is not visible on the canvas: whether a failed task stops the next stage. It is decided by how you wire the two outcome paths.

The rule, as documented for Azure Data Factory pipelines: the pipeline evaluates every leaf activity, and if a leaf was skipped it evaluates that leaf's parent instead. The pipeline succeeds only if every evaluated activity succeeded. With a failure path alone, the handler is the leaf and it succeeds, so the failure is swallowed. With both paths, the success-path leaf is skipped, its parent (Run_Task) is evaluated, and the stage fails.

Define both paths on Run_Task

Attach Log_Succeeded on On success and Log_Failed on On failure. If you leave out the success path, a failed task is logged and notified, but the ForEach still succeeds and the next stage runs on incomplete data.

Verify against Microsoft Learn

The leaf rule is documented in Pipeline failure and error message for Azure Data Factory, and Fabric pipelines use the same dependency model. Confirm it once with a failing test task: the ForEach should show Failed and the next stage's Lookup should show Skipped.

Notifications

Put every notification in one reusable pipeline, PL_ORCH_HUB_Notify, and invoke it from Notify_Failure_S1 (and from the guard). The Fabric documentation recommends exactly this composition for email: a dedicated email pipeline that owns the activity and its connection, called through an Invoke pipeline activity.

Identity and limits

  • Who sends the mail. The Outlook activity supports user (OAuth), workspace identity and service principal connections. With a user connection the content is sent from that user's account, so use a team-owned account. A workspace identity or service principal needs application-level Microsoft Graph permissions with administrator consent, and may need Exchange Online mailbox restrictions. Those permissions can allow sending as other users, so involve the tenant administrator.
  • Deployment. With user authentication, the activity is inactive in a target workspace until you create a connection there. The Teams activity is documented as inactive under CI/CD. Add a post-deployment step that recreates the connections, and test the notification pipeline after every release.
  • One dependency. If you connect more than one activity to an Outlook activity, all the connected conditions must be met before it runs. Give Notify_Failure a single upstream dependency.
  • No sensitivity labels. The activity cannot apply Microsoft Purview sensitivity labels.

Optional: a dependency gate

A stage gate blocks a whole stage when anything before it failed. If independent branches share a stage and one branch's failure should not stall the others, check each task's prerequisites individually. Four changes make the pipeline do that:

  1. Check prerequisites per task.

    Add a Lookup before Run_Task_S1, with First row only on:

    SELECT COUNT(*) AS blocked_by
FROM ctl.task_dependency AS d
WHERE d.task_name = '@{item().task_name}'
  AND NOT EXISTS (
        SELECT 1
        FROM ctl.vw_task_last_status_per_run AS s
        WHERE s.run_id IN ('@{pipeline().RunId}', '@{replace(pipeline().parameters.restart_run_id, '''', '''''')}')
          AND s.task_name = d.depends_on_task_name
          AND s.last_event = 'Succeeded');
  2. Branch on the result.

    Because Switch and If cannot nest, change the Switch expression so that a blocked task selects its own case:

    @if(greater(activity('Check_Prerequisites_S1').output.firstRow.blocked_by, 0), 'Blocked', item().task_type)

    The Blocked case is a Stored procedure activity that logs a Skipped event with the message A prerequisite did not succeed.

  3. Log success inside the cases.

    Move Log_Succeeded into each real case, after its activity, so a blocked task logs Skipped and not Succeeded.

  4. Let the next stage start after a failure, then fail the run at the end.

    Make Lookup_Stage2 run on the completion of ForEach_Stage1. Because the failure is then no longer a leaf, add a final verdict step: a Lookup that counts Failed events for this run, followed by an If Condition that runs a Fail activity when the count is above zero.

Use the gate only when you need it. It adds a Lookup per task, and the final verdict step is easy to forget.

Optional: guard against overlapping runs

Two runs of the master pipeline writing to the same tables will conflict. A schedule that overlaps with a manual run is the usual cause. Add a Lookup after the guard and an If Condition that fails the run:

SELECT COUNT(*) AS running_runs
FROM ctl.vw_run_summary
WHERE run_status = 'Running'
  AND run_id <> '@{pipeline().RunId}'
  AND started_utc > DATEADD(HOUR, -12, SYSUTCDATETIME());

The condition is @greater(activity('Check_Overlap').output.firstRow.running_runs, 0). This is a heuristic. A cancelled run leaves a Started row with no end row, which looks like a run in progress until the time window passes, and a run between stages briefly shows no running task. For an exact answer, query the pipeline run history through the Fabric REST API instead.

Variant: extract the per-task body into a child pipeline

Building the body three times, once per stage, works and is easy to follow, but the copies drift. Once the design is stable, move the body into a child pipeline.

  • Create PL_ORCH_HUB_RunTask with parameters run_id, stage, task_name, task_type, object_name, object_id, target_workspace_id, parameters_json, timeout_minutes, max_attempts, notify_to and default_notify_to. Move the body into it, replacing @item().x with @pipeline().parameters.x and @pipeline().RunId with @pipeline().parameters.run_id.
  • Replace each ForEach body with one Invoke pipeline activity that passes the row's values and waits for completion. The master shrinks to the guard, three Lookups, three ForEach activities and three Invoke activities.
  • Trade-offs. There is one more pipeline run per task in the Monitor hub, the nesting is Master, RunTask, Notify, and an Invoke activity must wait for its child so failures propagate. In return the body exists once, and the 120-activity limit stops being a concern.
  • More than three stages. Add a PL_ORCH_HUB_RunStage child with a stage parameter that holds the Lookup and ForEach for one stage. The master then needs only a sequential ForEach over the distinct stages. You need a place to say which stages run in parallel, such as a small ctl.stage table.

Limits that shape this design

A pipeline can hold up to 120 activities including those inside containers, a ForEach cannot contain another ForEach, and a Switch and an If cannot contain each other. These limits are documented for Azure Data Factory; the three-stage inline build uses about 40 activities, so only larger variants need to care.

Key takeaways

  • One guard, one Lookup and ForEach per stage, and one per-task body: log started, Switch on task type, then log the outcome.
  • Define both the success and failure path on the Switch. A failure path on its own swallows the failure and lets the next stage run.
  • Use the Script activity for the procedure case and the Stored procedure activity, with typed parameters, for logging.
  • Keep notification in one pipeline. Mail identity, consent and deployment behavior then need fixing in one place.
  • Test the failure drill and the restart path before trusting the pipeline with production work.
