Warehouse objects and seed data

Everything the framework stores lives in one Fabric Warehouse: a configuration table, a dependency table, an append-only run log, views over the log and a handful of stored procedures. This page turns your existing scripts into procedures (step 0), creates the objects (step 1) and seeds the first five tasks (step 2).

What you create

All objects go into the hub Warehouse (WH_ORCH_HUB_Control in the example). Configuration and history live in a ctl schema so they are easy to secure and to keep apart from the procedures that do real work, which stay in dbo with a usp_ prefix.

ObjectKindPurpose
ctl.control_tableTableOne row per task: type, stage, order, target item IDs, parameters, notification list.
ctl.task_dependencyTableWhich task needs which. Documents the DAG, is checked by the guard and can drive an optional per-task gate.
ctl.run_logTableAppend-only events (Started, Succeeded, Failed, Skipped) with run ID, task, timestamp and message.
ctl.vw_task_last_status_per_runViewThe latest event for each task in each run. Used by restart logic and health checks.
ctl.vw_task_run_timelineViewOne row per task per run with start, end, duration and status. Feeds timeline and Gantt-style reports.
ctl.vw_run_summaryViewOne row per run with counts of succeeded, failed, skipped and running tasks.
dbo.usp_validate_control_tableProcedureThe guard step. Throws if the configuration is inconsistent.
dbo.usp_log_eventProcedureThe only writer of the run log.
dbo.usp_sync_object_idsProcedureFills item and workspace IDs from the inventory by name.
dbo.usp_create_snapshot, dbo.usp_archive_dataProceduresThe two example task procedures that stand in for your own converted scripts.

Run each block as its own batch

CREATE VIEW and CREATE PROCEDURE must be the first statement in a batch. Run every code block on this page separately in the SQL query editor, or separate them with GO if you use a client that supports it.

Step 0: convert T-SQL scripts into stored procedures

The pipeline can run a stored procedure by name and observe whether it succeeded. It cannot do that with a saved query. So the first step is to turn each script you want to orchestrate into a procedure with the same body. Apply these rules:

  1. One script, one procedure. Name it dbo.usp_<verb>_<noun>. The guard rejects any other pattern, which also keeps the name safe to use in generated SQL.
  2. Remove client-only statements. Delete GO, USE and hard-coded database names for objects in the same Warehouse. Keep three-part names only for items in the same workspace, such as a lakehouse SQL analytics endpoint.
  3. Make it safe to run twice. Replace plain inserts with delete-then-insert for a key range, MERGE, or TRUNCATE and reload. Pipelines retry and operators rerun.
  4. Wrap writes in a transaction and rethrow. An unhandled error must reach the Stored procedure activity so the activity fails and the failure path runs. Swallowing the error in CATCH makes a failed task look successful.
  5. Turn changing values into parameters with defaults. The framework calls procedures with no arguments unless you extend the Switch case, so every parameter needs a default.
  6. Return nothing. Logging belongs to the pipeline. A procedure that returns result sets adds noise and no value.
  7. Use CREATE OR ALTER. The script can then be redeployed without a drop step.

The general shape is:

CREATE OR ALTER PROCEDURE dbo.usp_name_of_task
AS
BEGIN
    SET NOCOUNT ON;

    BEGIN TRY
        BEGIN TRANSACTION;

        -- the body of your original script goes here

        COMMIT TRANSACTION;
    END TRY
    BEGIN CATCH
        IF @@TRANCOUNT > 0
            ROLLBACK TRANSACTION;
        THROW;
    END CATCH;
END;

The example uses two scripts that work on small summary tables in the hub Warehouse. Create the sample tables first (they stand in for your real data), then the two procedures.

Sample tables for the two example procedures 
CREATE TABLE dbo.sales_summary
(
    customer_id  INT           NOT NULL,
    product_id   INT           NOT NULL,
    total_amount DECIMAL(18,2) NOT NULL
);

CREATE TABLE dbo.sales_summary_snapshot
(
    snapshot_date DATE          NOT NULL,
    customer_id   INT           NOT NULL,
    product_id    INT           NOT NULL,
    total_amount  DECIMAL(18,2) NOT NULL
);

CREATE TABLE dbo.sales_summary_archive
(
    snapshot_date DATE          NOT NULL,
    customer_id   INT           NOT NULL,
    product_id    INT           NOT NULL,
    total_amount  DECIMAL(18,2) NOT NULL
);
CREATE OR ALTER PROCEDURE dbo.usp_create_snapshot
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @snapshot_date DATE = CAST(SYSUTCDATETIME() AS DATE);

    BEGIN TRY
        BEGIN TRANSACTION;

        -- idempotent: replace today's snapshot if the task is run again
        DELETE FROM dbo.sales_summary_snapshot
        WHERE snapshot_date = @snapshot_date;

        INSERT INTO dbo.sales_summary_snapshot (snapshot_date, customer_id, product_id, total_amount)
        SELECT @snapshot_date, customer_id, product_id, total_amount
        FROM dbo.sales_summary;

        COMMIT TRANSACTION;
    END TRY
    BEGIN CATCH
        IF @@TRANCOUNT > 0
            ROLLBACK TRANSACTION;
        THROW;
    END CATCH;
END;
CREATE OR ALTER PROCEDURE dbo.usp_archive_data
    @retain_days INT = 30
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @cutoff DATE = DATEADD(DAY, -@retain_days, CAST(SYSUTCDATETIME() AS DATE));

    BEGIN TRY
        BEGIN TRANSACTION;

        -- copy only rows that are not already archived, then remove them from the live table
        INSERT INTO dbo.sales_summary_archive (snapshot_date, customer_id, product_id, total_amount)
        SELECT s.snapshot_date, s.customer_id, s.product_id, s.total_amount
        FROM dbo.sales_summary_snapshot AS s
        WHERE s.snapshot_date < @cutoff
          AND NOT EXISTS (SELECT 1
                          FROM dbo.sales_summary_archive AS a
                          WHERE a.snapshot_date = s.snapshot_date
                            AND a.customer_id   = s.customer_id
                            AND a.product_id    = s.product_id);

        DELETE FROM dbo.sales_summary_snapshot
        WHERE snapshot_date < @cutoff;

        COMMIT TRANSACTION;
    END TRY
    BEGIN CATCH
        IF @@TRANCOUNT > 0
            ROLLBACK TRANSACTION;
        THROW;
    END CATCH;
END;

Test each procedure by hand before it enters the control table: run it twice and check that the second run changes nothing, then force an error halfway through and check that no partial rows remain.

Verify against Microsoft Learn

THROW, TRY...CATCH, MERGE and CREATE OR ALTER for procedures and views are documented as supported in Fabric Warehouse. The pages do not describe how an error inside an explicit transaction interacts with @@TRANCOUNT in a CATCH block in Warehouse, so the failure-path test above is not optional. Step 1: create the control table, run log and procedures

Schema

CREATE SCHEMA ctl;

Run this once. It fails if the schema already exists.

Control table

Each row is a task. The table holds configuration only, so it carries no status or retry counters that the pipeline would have to update. Runtime state belongs in the run log.

CREATE TABLE ctl.control_table
(
    task_id              VARCHAR(64)   NOT NULL,  -- stable key, for example T1
    task_name            VARCHAR(256)  NOT NULL,  -- unique, readable, used in the run log
    task_type            VARCHAR(32)   NOT NULL,  -- Notebook | StoredProcedure | Pipeline
    stage                INT           NOT NULL,  -- gate: stage n must succeed before n+1
    sequence_no          INT           NOT NULL,  -- order inside a stage
    is_enabled           BIT           NOT NULL,
    workspace_name       VARCHAR(256)  NULL,      -- where the item lives (Notebook, Pipeline)
    object_name          VARCHAR(512)  NOT NULL,  -- item name, or dbo.usp_* for procedures
    object_id            VARCHAR(36)   NULL,      -- item ID, filled by usp_sync_object_ids
    target_workspace_id  VARCHAR(36)   NULL,      -- workspace ID, filled by usp_sync_object_ids
    parameters_json      VARCHAR(4000) NULL,      -- JSON object passed to the task as one string
    timeout_minutes      INT           NULL,      -- used by the dispatcher notebook
    max_attempts         INT           NULL,      -- used by the dispatcher notebook
    notify_to            VARCHAR(1024) NULL,      -- semicolon-separated recipients
    config_version       INT           NOT NULL,
    created_at_utc       DATETIME2(6)  NOT NULL,
    modified_at_utc      DATETIME2(6)  NOT NULL
);
ALTER TABLE ctl.control_table
    ADD CONSTRAINT pk_control_table PRIMARY KEY NONCLUSTERED (task_id) NOT ENFORCED;

ALTER TABLE ctl.control_table
    ADD CONSTRAINT uq_control_table_task_name UNIQUE NONCLUSTERED (task_name) NOT ENFORCED;

NOT ENFORCED means metadata only

Warehouse accepts primary key and unique constraints only as NOT ENFORCED (and NONCLUSTERED for a primary key), and the scripts add them with ALTER TABLE. The engine uses them as metadata and will not reject a duplicate row. That is why the guard procedure below checks for duplicates itself.

ColumnNotes
task_typeThe value the Switch activity branches on. Adding a new type means one new Switch case and one new guard rule; see extensibility.
stage, sequence_noOrder is explicit. Do not rely on alphabetical task names. See ordering.
workspace_name, object_nameWhat humans edit and review. IDs are derived from them.
object_id, target_workspace_idWhat the pipeline uses. Stored as VARCHAR(36) in lower case. The uniqueidentifier type is not used because its values cannot be read through a SQL analytics endpoint.
parameters_jsonThe long tail of per-task settings, as a JSON string. Warehouse has no JSON column type, so validate it in the task.
timeout_minutes, max_attemptsRead by the dispatcher notebook. The native Notebook activity ignores them because its timeout and retry settings are static.
notify_toRecipients for the failure notice. Use a team mailbox or distribution list.
config_versionBump it when a seed script changes a row, so a run can be correlated with the configuration it used.

Task dependency table

The source design stored dependencies as a comma-separated list inside the task row. A separate table is easier to validate, query and join, and needs no string parsing.

CREATE TABLE ctl.task_dependency
(
    task_name            VARCHAR(256) NOT NULL,   -- the dependent task
    depends_on_task_name VARCHAR(256) NOT NULL,   -- the prerequisite
    created_at_utc       DATETIME2(6) NOT NULL
);

ALTER TABLE ctl.task_dependency
    ADD CONSTRAINT pk_task_dependency PRIMARY KEY NONCLUSTERED (task_name, depends_on_task_name) NOT ENFORCED;

Run log

The run log is the key design decision on this page. It is insert-only: a task writes a Started row when it begins and one end row (Succeeded, Failed or Skipped) when it finishes. Nothing is ever updated. Parallel iterations therefore never write to the same row, and the Warehouse's snapshot isolation never has an update conflict to report.

CREATE TABLE ctl.run_log
(
    run_id          VARCHAR(64)   NOT NULL,   -- @pipeline().RunId of the master pipeline run
    task_name       VARCHAR(256)  NOT NULL,   -- ctl.control_table.task_name, or (pipeline) for run-level events
    stage           INT           NULL,
    activity        VARCHAR(128)  NOT NULL,   -- which step wrote the event, for example Notebook
    event           VARCHAR(16)   NOT NULL,   -- Started | Succeeded | Failed | Skipped
    event_time_utc  DATETIME2(6)  NOT NULL,   -- set by the procedure with SYSUTCDATETIME()
    message         VARCHAR(4000) NULL,       -- error text for Failed events
    external_id     VARCHAR(64)   NULL        -- for example the job instance ID from the dispatcher
);

Stored procedures

Three procedures belong to the framework itself. The two example task procedures were created in step 0.

usp_log_event

The only writer of the run log. The pipeline calls it through a Stored procedure activity with typed parameters, which avoids building SQL strings from error messages that contain quotes.

CREATE OR ALTER PROCEDURE dbo.usp_log_event
    @run_id      VARCHAR(64),
    @task_name   VARCHAR(256),
    @activity    VARCHAR(128),
    @event       VARCHAR(16),
    @stage       INT           = NULL,
    @message     VARCHAR(4000) = NULL,
    @external_id VARCHAR(64)   = NULL
AS
BEGIN
    SET NOCOUNT ON;

    IF @event NOT IN ('Started', 'Succeeded', 'Failed', 'Skipped')
        THROW 50010, 'Unknown event. Use Started, Succeeded, Failed or Skipped.', 1;

    INSERT INTO ctl.run_log
        (run_id, task_name, stage, activity, event, event_time_utc, message, external_id)
    VALUES
        (@run_id, @task_name, @stage, @activity, @event, SYSUTCDATETIME(), LEFT(@message, 4000), @external_id);
END;

usp_validate_control_table

The guard. Run it at the top of every master pipeline run. Each rule throws with the name of the first offending task, so the pipeline fails before any work starts. The rules cover what NOT ENFORCED constraints cannot: duplicate names, unknown task types, missing or malformed IDs, procedures that do not exist, and dependencies that cannot be honored.

Full guard procedure (T-SQL) 
CREATE OR ALTER PROCEDURE dbo.usp_validate_control_table
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @bad VARCHAR(256);
    DECLARE @msg VARCHAR(1000);

    -- 0. there must be something to run
    IF NOT EXISTS (SELECT 1 FROM ctl.control_table WHERE is_enabled = 1)
        THROW 50000, 'ctl.control_table has no enabled tasks.', 1;

    -- 1. task_name must be unique (the UNIQUE constraint is not enforced)
    SET @bad = NULL;
    SELECT TOP (1) @bad = task_name
    FROM ctl.control_table
    GROUP BY task_name
    HAVING COUNT(*) > 1
    ORDER BY task_name;
    IF @bad IS NOT NULL
    BEGIN
        SET @msg = CONCAT('Duplicate task_name: ', @bad);
        THROW 50001, @msg, 1;
    END;

    -- 2. task_type must be one the Switch activity knows
    SET @bad = NULL;
    SELECT TOP (1) @bad = task_name
    FROM ctl.control_table
    WHERE is_enabled = 1
      AND task_type NOT IN ('Notebook', 'StoredProcedure', 'Pipeline')
    ORDER BY task_name;
    IF @bad IS NOT NULL
    BEGIN
        SET @msg = CONCAT('Unknown task_type for task: ', @bad);
        THROW 50002, @msg, 1;
    END;

    -- 3. notebooks and pipelines need a workspace ID and an item ID (36 characters)
    SET @bad = NULL;
    SELECT TOP (1) @bad = task_name
    FROM ctl.control_table
    WHERE is_enabled = 1
      AND task_type IN ('Notebook', 'Pipeline')
      AND (object_id IS NULL OR LEN(object_id) <> 36
           OR target_workspace_id IS NULL OR LEN(target_workspace_id) <> 36)
    ORDER BY task_name;
    IF @bad IS NOT NULL
    BEGIN
        SET @msg = CONCAT('Missing or malformed object_id or target_workspace_id for task: ', @bad);
        THROW 50003, @msg, 1;
    END;

    -- 4. procedures must follow the naming rule and must exist
    SET @bad = NULL;
    SELECT TOP (1) @bad = task_name
    FROM ctl.control_table
    WHERE is_enabled = 1
      AND task_type = 'StoredProcedure'
      AND (object_name NOT LIKE 'dbo.usp[_]%' OR OBJECT_ID(object_name, 'P') IS NULL)
    ORDER BY task_name;
    IF @bad IS NOT NULL
    BEGIN
        SET @msg = CONCAT('Stored procedure missing or not named dbo.usp_*: ', @bad);
        THROW 50004, @msg, 1;
    END;

    -- 5. dependencies must point at an existing, earlier, enabled task
    SET @bad = NULL;
    SELECT TOP (1) @bad = d.task_name
    FROM ctl.task_dependency AS d
    LEFT JOIN ctl.control_table AS t ON t.task_name = d.task_name
    LEFT JOIN ctl.control_table AS p ON p.task_name = d.depends_on_task_name
    WHERE t.task_name IS NULL
       OR p.task_name IS NULL
       OR p.stage > t.stage
       OR (p.stage = t.stage AND p.sequence_no >= t.sequence_no)
       OR (t.is_enabled = 1 AND p.is_enabled = 0)
    ORDER BY d.task_name;
    IF @bad IS NOT NULL
    BEGIN
        SET @msg = CONCAT('Invalid dependency (unknown task, later stage, wrong order or disabled prerequisite): ', @bad);
        THROW 50005, @msg, 1;
    END;
END;

Two design points. First, because every dependency must point to an earlier stage or an earlier sequence number, a cycle is impossible and no cycle check is needed. Second, rule 4 doubles as protection: the procedure name comes from a table, so insisting on dbo.usp_* and checking it exists stops a bad row from running arbitrary SQL. Add an inventory check (the dangling-ID query on the inventory page) as a further rule once the inventory lakehouse exists.

Dependencies inside a parallel stage

The guard allows a dependency within a stage only when the prerequisite has a lower sequence_no. That is meaningful in a sequential stage. In a parallel stage nothing orders the tasks, so put dependent tasks in a later stage.

usp_sync_object_ids

Looks up each task's workspace ID and item ID in the inventory by name and writes them to the control table. People edit names, which are stable and reviewable; IDs, which differ between environments, are derived. The procedure uses MERGE, because the Warehouse documents UPDATE as single-table only.

CREATE OR ALTER PROCEDURE dbo.usp_sync_object_ids
AS
BEGIN
    SET NOCOUNT ON;

    MERGE ctl.control_table AS t
    USING (
        SELECT workspace_name,
               item_name,
               CASE item_type WHEN 'DataPipeline' THEN 'Pipeline' ELSE item_type END AS task_type,
               LOWER(item_id)      AS item_id,
               LOWER(workspace_id) AS workspace_id
        FROM LH_ORCH_HUB_Inventory.dbo.fabric_inventory
        WHERE item_type IN ('Notebook', 'DataPipeline')
    ) AS s
    ON  t.task_type      = s.task_type
    AND t.workspace_name = s.workspace_name
    AND t.object_name    = s.item_name
    WHEN MATCHED
         AND (t.object_id IS NULL OR t.object_id <> s.item_id
              OR t.target_workspace_id IS NULL OR t.target_workspace_id <> s.workspace_id)
    THEN UPDATE SET
         object_id           = s.item_id,
         target_workspace_id = s.workspace_id,
         modified_at_utc     = SYSUTCDATETIME();
END;
  • The inventory lakehouse (LH_ORCH_HUB_Inventory) must be in the same workspace as the Warehouse so a three-part name can reach it. Add it to the Explorer with + Warehouses before creating the procedure.
  • Names match case-sensitively under the Warehouse's default collation.
  • If two inventory rows match one task (for example two workspaces with the same display name), MERGE raises an error about multiple matches. That is the right outcome; make the names unique.
  • Stored-procedure rows never match, because the inventory only holds items.

Verify against Microsoft Learn

Cross-database reads with three-part names within one workspace and MERGE are both documented, but the pages do not show them combined. If your Warehouse rejects the cross-database source inside MERGE, first copy the inventory rows into a local staging table with INSERT ... SELECT and merge from that. See Query the Warehouse.

If you have not built the inventory yet, skip this procedure and set the IDs by hand after seeding (shown in step 2).

Status views

Three views turn the event stream into status. Each is a separate batch.

CREATE OR ALTER VIEW ctl.vw_task_last_status_per_run
AS
SELECT x.run_id,
       x.task_name,
       x.stage,
       x.activity,
       x.event          AS last_event,
       x.event_time_utc AS last_event_utc,
       x.message
FROM (
    SELECT l.run_id, l.task_name, l.stage, l.activity, l.event, l.event_time_utc, l.message,
           ROW_NUMBER() OVER (
               PARTITION BY l.run_id, l.task_name
               ORDER BY l.event_time_utc DESC,
                        CASE WHEN l.event = 'Started' THEN 0 ELSE 1 END DESC) AS rn
    FROM ctl.run_log AS l
) AS x
WHERE x.rn = 1;
CREATE OR ALTER VIEW ctl.vw_task_run_timeline
AS
SELECT s.run_id,
       s.task_name,
       s.stage,
       COALESCE(b.started_utc, s.last_event_utc) AS started_utc,
       CASE WHEN s.last_event = 'Started' THEN NULL ELSE s.last_event_utc END AS ended_utc,
       CASE WHEN s.last_event = 'Started' THEN NULL
            ELSE DATEDIFF(SECOND, COALESCE(b.started_utc, s.last_event_utc), s.last_event_utc) END AS duration_seconds,
       CASE s.last_event WHEN 'Started' THEN 'Running' ELSE s.last_event END AS status,
       s.message
FROM ctl.vw_task_last_status_per_run AS s
LEFT JOIN (
    SELECT run_id, task_name, MIN(event_time_utc) AS started_utc
    FROM ctl.run_log
    WHERE event = 'Started'
    GROUP BY run_id, task_name
) AS b
  ON b.run_id = s.run_id AND b.task_name = s.task_name;
CREATE OR ALTER VIEW ctl.vw_run_summary
AS
SELECT run_id,
       MIN(started_utc) AS started_utc,
       MAX(ended_utc)   AS ended_utc,
       COUNT(*)         AS tasks_logged,
       SUM(CASE WHEN status = 'Succeeded' THEN 1 ELSE 0 END) AS succeeded,
       SUM(CASE WHEN status = 'Failed'    THEN 1 ELSE 0 END) AS failed,
       SUM(CASE WHEN status = 'Skipped'   THEN 1 ELSE 0 END) AS skipped,
       SUM(CASE WHEN status = 'Running'   THEN 1 ELSE 0 END) AS running,
       CASE WHEN SUM(CASE WHEN status = 'Failed'  THEN 1 ELSE 0 END) > 0 THEN 'Failed'
            WHEN SUM(CASE WHEN status = 'Running' THEN 1 ELSE 0 END) > 0 THEN 'Running'
            ELSE 'Succeeded' END AS run_status
FROM ctl.vw_task_run_timeline
GROUP BY run_id;

A run that is between stages has no task in Running state for a moment, so vw_run_summary can briefly show Succeeded for a run that is still going. For pipeline-level state use the Monitor hub, or compare the number of logged tasks with the number of enabled tasks.

Warehouse behaviors that shaped these scripts

If you adapt scripts from SQL Server or Azure SQL, expect these differences.

BehaviorWhat the scripts do about it
Primary key and unique constraints are accepted only as NOT ENFORCED.A guard procedure checks uniqueness before every run.
No nvarchar, tinyint or datetime columns. uniqueidentifier values cannot be read through a SQL analytics endpoint.Text is VARCHAR, flags are BIT, times are DATETIME2(6) and IDs are VARCHAR(36).
The default collation is case-sensitive.Names compare case-sensitively and IDs are stored in lower case. A case-insensitive collation can only be chosen when the Warehouse is created, through the workspace default collation setting or the REST API, and cannot be changed afterwards.
ALTER TABLE ... ADD accepts nullable columns only.New configuration columns are added as nullable and given a default in the pipeline expression or the dispatcher.
UPDATE supports a single table without a FROM clause. MERGE is available.The sync procedure uses MERGE.
Snapshot isolation with table-level conflict detection: concurrent UPDATE, DELETE, MERGE or TRUNCATE on one table can fail.The run log only inserts. Procedures that modify shared tables run in a sequential stage.
No triggers, and no sequences.The log needs no surrogate key. Ordering comes from the event timestamp.
Queries that mix system catalog views and user tables are not supported.The guard calls OBJECT_ID() instead of joining sys.procedures.

Adding a column to the control table later is a nullable ALTER TABLE ... ADD, which is fine in the Warehouse. If you keep the Warehouse in Git, read the source-control limitations for adding columns and constraints first.

Step 2: seed the control table

The seed script is idempotent: it deletes the five example rows by name and inserts them again inside one transaction, so you can run it repeatedly. It holds names, not IDs. IDs are filled in afterwards by the sync procedure, which is what keeps one script valid for development, test and production.

Replace alerts@example.com with your team's shared mailbox or distribution list.

DECLARE @now DATETIME2(6) = SYSUTCDATETIME();
DECLARE @version INT = 1;
DECLARE @notify VARCHAR(1024) = 'alerts@example.com';

BEGIN TRANSACTION;

DELETE FROM ctl.task_dependency
WHERE task_name IN ('ingest_customers', 'ingest_products', 'transform_sales', 'create_snapshot', 'archive_data');

DELETE FROM ctl.control_table
WHERE task_name IN ('ingest_customers', 'ingest_products', 'transform_sales', 'create_snapshot', 'archive_data');

-- Stage 1: ingests, run in parallel
INSERT INTO ctl.control_table

     object_id, target_workspace_id, parameters_json, timeout_minutes, max_attempts, notify_to,
     config_version, created_at_utc, modified_at_utc)
VALUES
    ('T1', 'ingest_customers', 'Notebook', 1, 1, 1, 'DEV_SALES_BRZ', 'NB_SALES_BRZ_IngestCustomers',
     NULL, NULL, '{"load_mode":"incremental"}', 60, 2, @notify, @version, @now, @now),
    ('T2', 'ingest_products',  'Notebook', 1, 2, 1, 'DEV_SALES_BRZ', 'NB_SALES_BRZ_IngestProducts',
     NULL, NULL, '{"load_mode":"incremental"}', 60, 2, @notify, @version, @now, @now);

-- Stage 2: transform, after both ingests
INSERT INTO ctl.control_table
    (task_id, task_name, task_type, stage, sequence_no, is_enabled, workspace_name, object_name,
     object_id, target_workspace_id, parameters_json, timeout_minutes, max_attempts, notify_to,
     config_version, created_at_utc, modified_at_utc)
VALUES
    ('T3', 'transform_sales', 'Notebook', 2, 1, 1, 'DEV_SALES_SLV', 'NB_SALES_SLV_TransformSales',
     NULL, NULL, '{"window_days":7}', 120, 2, @notify, @version, @now, @now);

-- Stage 3: stored procedures in the hub Warehouse, run in sequence
INSERT INTO ctl.control_table
    (task_id, task_name, task_type, stage, sequence_no, is_enabled, workspace_name, object_name,
     object_id, target_workspace_id, parameters_json, timeout_minutes, max_attempts, notify_to,
     config_version, created_at_utc, modified_at_utc)
VALUES
    ('T4', 'create_snapshot', 'StoredProcedure', 3, 1, 1, NULL, 'dbo.usp_create_snapshot',

    ('T5', 'archive_data',    'StoredProcedure', 3, 2, 1, NULL, 'dbo.usp_archive_data',
     NULL, NULL, NULL, NULL, NULL, @notify, @version, @now, @now);

VALUES
    ('transform_sales', 'ingest_customers', @now),
    ('transform_sales', 'ingest_products',  @now),
    ('create_snapshot', 'transform_sales',  @now),
    ('archive_data',    'create_snapshot',  @now);

Resolve the IDs

With the inventory in place, resolve and validate in one go:

EXEC dbo.usp_sync_object_ids;
EXEC dbo.usp_validate_control_table;

SELECT stage, sequence_no, task_name, task_type, workspace_name, object_name, object_id, target_workspace_id
FROM ctl.control_table
WHERE is_enabled = 1
ORDER BY stage, sequence_no, task_name;

The guard finishes without an error, and the notebook rows now carry lower-case GUIDs. If the guard throws, it names the task to fix.

Changing the plan later

After the engine exists, the plan changes with data entry. Each of these is a single-table statement:

-- switch a task off without deleting it
UPDATE ctl.control_table
SET is_enabled = 0, modified_at_utc = SYSUTCDATETIME()
WHERE task_name = 'archive_data';

-- move a task to another stage
UPDATE ctl.control_table
SET stage = 3, sequence_no = 3, modified_at_utc = SYSUTCDATETIME()
WHERE task_name = 'transform_sales';

Keep the seed script in source control and treat direct edits in production as emergency changes: record them in the script afterwards, bump config_version, and rerun the guard.

Resolve IDs at sync time, not at run time

Do not look up IDs from the inventory inside the master pipeline. An inventory that is a few hours old, or briefly empty during a refresh, would then fail or mis-route a run. Sync into the control table on a schedule or after a deployment, run the guard, and let the pipeline read only the control table.

Key takeaways

  • Turn every orchestrated script into a re-runnable procedure that rethrows errors; test the failure path by hand.
  • Keep configuration and history apart: the control table holds intent, the append-only run log holds facts, and views derive status.
  • Do not trust NOT ENFORCED constraints. Run the guard procedure at the start of every run.
  • Seed names and derive IDs per environment with the sync procedure, so one seed script serves development, test and production.
  • Write the log through a procedure with typed parameters; never build log SQL from error text.
