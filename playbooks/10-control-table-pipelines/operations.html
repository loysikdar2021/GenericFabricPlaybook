Operations, security and checklist

A framework that runs well on the first day still needs someone to watch it, secure it, promote it between environments and fix it at two in the morning. This page covers the health checks to run every day, the monitoring layers, a troubleshooting table, the security model, CI/CD with variable libraries and a go-live checklist.

Quick health checks

All of these read the run log or its views. Save them in the Warehouse query editor, or build a small report on the views. First, one more view that answers "what happened last time" for every task across all runs:

CREATE OR ALTER VIEW ctl.vw_task_latest_status
AS
SELECT x.task_name, x.run_id, x.stage, x.started_utc, x.ended_utc, x.duration_seconds, x.status, x.message
FROM (
    SELECT t.task_name, t.run_id, t.stage, t.started_utc, t.ended_utc, t.duration_seconds, t.status, t.message,
           ROW_NUMBER() OVER (PARTITION BY t.task_name ORDER BY t.started_utc DESC) AS rn
    FROM ctl.vw_task_run_timeline AS t
) AS x
WHERE x.rn = 1;

What is the latest status of every task, enabled or not?

SELECT c.stage, c.sequence_no, c.task_name, c.is_enabled,
       s.status AS last_status, s.started_utc AS last_started_utc, s.duration_seconds
FROM ctl.control_table AS c
LEFT JOIN ctl.vw_task_latest_status AS s ON s.task_name = c.task_name
ORDER BY c.stage, c.sequence_no, c.task_name;

What happened in the last hour?

SELECT TOP (200) *
FROM ctl.run_log
WHERE event_time_utc >= DATEADD(HOUR, -1, SYSUTCDATETIME())
ORDER BY event_time_utc DESC;

What failed in the last day, and why?

SELECT run_id, task_name, event_time_utc, message
FROM ctl.run_log
WHERE event = 'Failed'
  AND event_time_utc >= DATEADD(HOUR, -24, SYSUTCDATETIME())
ORDER BY event_time_utc DESC;

Is anything running longer than its timeout?

SELECT t.run_id, t.task_name, t.started_utc,
       DATEDIFF(MINUTE, t.started_utc, SYSUTCDATETIME()) AS minutes_running,
       COALESCE(c.timeout_minutes, 60) AS timeout_minutes
FROM ctl.vw_task_run_timeline AS t
JOIN ctl.control_table AS c ON c.task_name = t.task_name
WHERE t.status = 'Running'
  AND DATEDIFF(MINUTE, t.started_utc, SYSUTCDATETIME()) > COALESCE(c.timeout_minutes, 60);

Which tasks are getting slower?

SELECT task_name, COUNT(*) AS runs, AVG(duration_seconds) AS avg_seconds, MAX(duration_seconds) AS max_seconds
FROM ctl.vw_task_run_timeline
WHERE status = 'Succeeded'
  AND started_utc >= DATEADD(DAY, -14, SYSUTCDATETIME())
GROUP BY task_name
ORDER BY avg_seconds DESC;

Which enabled tasks have not succeeded for a week?

SELECT c.stage, c.task_name, MAX(t.started_utc) AS last_success_utc
FROM ctl.control_table AS c
LEFT JOIN ctl.vw_task_run_timeline AS t
       ON t.task_name = c.task_name AND t.status = 'Succeeded'
WHERE c.is_enabled = 1
GROUP BY c.stage, c.task_name
HAVING MAX(t.started_utc) IS NULL
    OR MAX(t.started_utc) < DATEADD(DAY, -7, SYSUTCDATETIME())
ORDER BY c.stage, c.task_name;

Do enabled tasks point at items that no longer exist? Use the dangling-ID query on the inventory page, and run usp_sync_object_ids afterwards.

A Started row with no end row

A pipeline run that is cancelled or whose capacity is lost mid-task never writes an end event, so the task shows as Running for ever. The stuck-tasks query finds these. Treat them as failed in your reports once they are older than the task's timeout, and do not let them block anything: the overlap check on the master pipeline uses a time window for the same reason.

Monitoring and observability

Use two layers and join them on the pipeline run ID. The run log tells you what the business process did, task by task. The platform's telemetry tells you how the pipelines and capacity behaved.

QuestionWhere to look
Which task failed, and with what message?The run log and its views.
How long has each task taken over the last month?The run log. Keep the history long enough for trends.
What did the pipeline do in this run, and which child runs did it start?The Monitoring hub. Its hierarchical view lists upstream and downstream runs, and the run detail page lists activity runs.
Can I rerun from the failed activity?The Monitoring hub offers rerun by failed activity or selected activity. The framework's own restart (restart_run_id) works at task level and tolerates configuration changes between runs.
I want pipeline and activity logs in a queryable storeWorkspace monitoring writes them to an eventhouse that you query with KQL.
I want to be told when a pipeline failsPipeline run alerts in the new Monitoring hub, plus the failure notification built into the framework.
Is the framework starving other workloads?The Microsoft Fabric Capacity Metrics app.

Two recommendations. Alert on the absence of success as well as on failure: the stale-tasks query catches a schedule that silently stopped, which no failure alert can. And build one small report on vw_task_run_timeline and vw_task_latest_status so operators have a single page with last status, duration trend and the current failures.

Troubleshooting

A Lookup returns no rowsNo enabled task in that stage, a wrong stage number, or a restart_run_id that excludes everything.Run the Lookup query by hand with the same parameter value.

A notebook task fails with a capacity error (HTTP 430)Capacity is full and a REST-started run is not queued.Lower the batch count, stagger the stage or use the native Notebook activity, which queues. See the dispatcher page.
A procedure fails with an update conflictTwo transactions modified the same table. Warehouse uses snapshot isolation with table-level conflict detection.Run procedures that update the same table in a sequential stage, and retry once.

Security

The control table is a powerful object: whoever can edit it can make the platform run any notebook or procedure the pipeline's identity can reach. Treat edits as code changes.

  • Limit who can write the control table. Keep the seed script in Git and apply it through a reviewed pull request and a release step. Give day-to-day operators read access to the views, not write access to the tables. Workspace roles take precedence, so keep Contributor and higher roles in the hub workspace to the platform team and use item-level permissions for everyone else.
  • Constrain what a row can execute. The guard accepts only procedures named dbo.usp_* that exist, and the Switch accepts only known task types, so a row cannot inject SQL or call an unexpected activity. Escape pipeline parameters that you interpolate into SQL, as the restart clause does.
  • Prefer non-user identities. Use a workspace identity or service principal for the Notebook, Invoke pipeline and (if you can administer the Graph permissions) Outlook activities, and avoid connections owned by a person who may leave. Add the identity to each workspace it must reach, with the least role that works, through a security group per environment.
  • Keep secrets out of everything the framework stores. parameters_json, pipeline parameters and activity outputs are visible to people who can read run details and the log. Put secrets in Azure Key Vault, read them in the notebook with notebookutils.credentials.getSecret and mark activities that handle sensitive values as secure input and output.
  • Audit changes. config_version and modified_at_utc record when a row changed, and Git records who changed the script. For a stricter trail, write control-table changes to an audit table inside the seed and sync procedures.
  • Review on a schedule. Review the identities' workspace roles, the people who can edit the hub workspace, the shared mailbox membership and the Key Vault access policies at least quarterly.

CI/CD of the framework

The framework is a set of items (a Warehouse, pipelines, notebooks and a variable library) plus a body of configuration data. Promote the items through your normal path, and treat the data as environment-specific.

Using a variable library

Create VL_ORCH_HUB_Config in the hub workspace with variables such as EnvironmentName (String), DefaultNotifyTo (String) and KeyVaultUri (String), and a value set for each stage. In the master pipeline, add a library variable reference and use it in dynamic content in place of a hard-coded value, for example @pipeline().libraryVariables.DefaultNotifyTo as the default recipient instead of the default_notify_to parameter's literal value. The Variable Libraries playbook covers creating the library, the supported types, and the activation step that follows the first deployment into each stage.

  • Resolve in the pipeline, pass down. Notebooks that read a library with notebookutils.variableLibrary are limited to the same workspace and do not support a service principal identity. The dispatcher may run under a service principal, so have the pipeline read the variable and pass it as a notebook parameter.
  • Activate before the first run. A library arrives in a new stage with its default value set active. Activate the stage's set before anything reads a variable, and add the step to the release.
  • Keep IDs out of the library. It is tempting to hold notebook IDs as variables. The control table plus sync does the same job per task, with a guard, and without one variable per task.

What to automate in the release

  1. Deploy the Warehouse objects.

    Promote the Warehouse through source control or a deployment pipeline. If you keep the Warehouse in Git, read the source-control limitations for adding columns and constraints first.

  2. Deploy pipelines, notebooks and the variable library.

    Follow the layer order from the Deployment Pipelines and Promotion playbook, and put the library with the items that consume it.

  3. Run the post-deployment steps.

    Activate the value set, recreate the Outlook and Teams connections, run the seed (with the stage's workspace names) and usp_sync_object_ids, then usp_validate_control_table. A small PL_ORCH_HUB_PostDeploy pipeline can run the last three.

  4. Smoke test.

    Run the master pipeline with one enabled no-op task and a test recipient, check the log, then re-enable the real plan.

CREATE OR ALTER PROCEDURE dbo.usp_purge_run_log
    @retain_days INT = 90
AS
BEGIN
    SET NOCOUNT ON;

    DELETE FROM ctl.run_log
    WHERE event_time_utc < DATEADD(DAY, -@retain_days, SYSUTCDATETIME());
END;

The log is insert-only by design, and this is its one delete. Run it only when the master pipeline is idle, because a delete concurrent with inserts into the same table can raise an update conflict.

Go-live checklist

Configuration

  • Every orchestrated script is a procedure that is idempotent, wrapped in a transaction and rethrows its error.
  • The seed script is in Git, holds names and not IDs, and has been reviewed.
  • IDs are filled by the sync procedure and the guard passes in the target environment.
  • Order is set with stage and sequence_no, never by name, and dependencies are recorded.

Pipeline

  • The Switch has both a success path and a failure path, and a default case that fails.
  • A deliberate failure fails the stage and blocks the next one.
  • A restart with restart_run_id reruns only the tasks that did not succeed.
  • Batch counts and activity timeouts are set from capacity tests, not left at defaults.
  • The overlap check is in place, or schedules cannot overlap.

Notifications

  • Failure notification goes through one notification pipeline, tested on its own.
  • The mail sender is a team-owned mailbox or a non-user identity, and the connection will be recreated after each deployment.

Security

  • Only the platform team can edit the control table; operators have read-only access.
  • The identities have the least workspace roles that work, through a security group per environment.
  • No secret appears in the control table, parameters, variables or notebooks.

Observability and operations

  • The health-check queries or an operator report exist, and someone owns them.
  • Alerts cover failure and the absence of success.
  • Log retention is decided and the purge runs when the pipeline is idle.
  • The release includes the five post-deployment steps and a smoke test.

Key takeaways

  • Watch the framework at two layers: the run log for what the process did, and platform telemetry for how the pipelines behaved. Join them on the run ID.
  • Alert on missing success as well as on failure; stale and stuck tasks are the failures nobody notices.
  • Control who can edit the control table as strictly as you control who can deploy code.
  • Promote items, derive IDs, keep environment settings in a variable library and secrets in a vault. Never promote an ID.
  • Make post-deployment steps (activate, reconnect, sync, guard, smoke test) part of the release, not a memory.
