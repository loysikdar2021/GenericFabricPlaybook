Notebook dispatcher (GUID launcher)

A control table that stores notebook names breaks the day someone renames a notebook. This page explains why the framework stores IDs instead, compares the ways a pipeline can start a notebook by ID, and builds a dispatcher notebook that starts a notebook through the Fabric job scheduler API, waits for it, and reports the outcome.

Why IDs and not names

A display name is a label that anyone with the right role can edit. An item ID is assigned when the item is created and never changes. Orchestration that depends on a name is therefore only as stable as the team's naming discipline.

EventReference by nameReference by ID, resolved at sync time
Someone renames a notebookBreaks. The next run cannot find it.Keeps working. The next sync updates the stored name.
Notebook is deleted and a different one is created with the same nameRisky. Runs the new notebook silently.Fails visibly with item-not-found until the sync is run, which is what you want.
Two workspaces hold notebooks with the same nameAmbiguous unless the workspace is part of the reference.Unambiguous. The workspace ID and item ID together are unique.
Same plan deployed to test and productionFragile. Works only if every name is identical in every environment.Works. IDs differ per environment; the sync fills them from names, so one seed script serves all.

The design rule is therefore: people edit names, the framework executes IDs, and a sync step (usp_sync_object_ids) connects the two. The in-session shortcut notebookutils.notebook.run("NB_Name") resolves by name, so it is not rename-proof and is compared below for completeness.

Test this in your pipeline editor before choosing: if the fields accept an expression such as @item().object_id, the native activity is the better choice and the dispatcher is optional. The same applies to the workspace and pipeline fields of the Invoke pipeline activity.

The rest of this page builds the dispatcher, because it is the option that always works, gives row-level control and is easy to reason about. The master pipeline page shows where each option plugs into the Switch.

Identity, permissions and tenant settings

The dispatcher calls the Fabric REST API as whichever identity runs the dispatcher notebook. When a pipeline's Notebook activity starts it, that is the identity of the activity's connection.

  • Permission. The identity must be allowed to run the target notebook. Add a service principal or workspace identity to the target workspace as Contributor, Member or Admin. The job scheduler lists the delegated scopes Item.Execute.All and Notebook.Execute.All.
  • Tenant setting. Service principals and workspace identities call Fabric APIs only if Service principals can call Fabric public APIs is enabled for them.
  • Token. Use the same idioms as the inventory notebook: notebookutils.credentials.getToken('pbi') for the running identity, or MSAL client credentials with secrets from Key Vault when you need the full service scope under a service principal. Never put a secret in the notebook or in a pipeline parameter.
  • Least privilege. Contributor on every workspace the control table can reach is broad. Prefer one security group per environment and review its membership on a schedule.

How the dispatcher works

Job statuses reported by the scheduler are NotStarted, InProgress, Completed, Failed, Cancelled and Deduped. The last means another instance of the same job type was already running and this request was skipped. The dispatcher treats Completed as success and everything else terminal as failure.

Behaviors built into the notebook below:

  • Honors Retry-After. It waits at least the first Retry-After before the first status call, and honors the header on later calls.
  • Retries only what is transient. Throttling (HTTP 429) and a full capacity (HTTP 430) are retried with a wait; a permission or item-not-found error is not.
  • Attempts and timeout from the row. MAX_ATTEMPTS retries a failed child run; TIMEOUT_MINUTES caps one attempt and cancels the child if exceeded.
  • Fails loudly. A failed child raises an exception, so the Notebook activity fails and the failure path in the pipeline runs. The error text carries the scheduler's failure reason.
  • Returns a summary. On success it exits with a small JSON string containing the child job instance ID, which the pipeline can write to the run log.

The dispatcher notebook

Create NB_ORCH_HUB_RunNotebookById in the hub workspace. A Python notebook is enough, because the dispatcher only makes HTTP calls, and it keeps the extra session small. Split the code into the three cells below. Mark the first as the parameter cell.

# Mark this cell as a parameter cell. The Notebook activity overrides these values.
TASK_NAME = "ingest_customers"
RUN_ID = ""                                           # pipeline run ID, for log correlation
TARGET_WORKSPACE_ID = "00000000-0000-0000-0000-000000000011"
NOTEBOOK_ID = "00000000-0000-0000-0000-000000000001"
PARAMETERS_JSON = "{}"                                # task settings, forwarded as one string
TIMEOUT_MINUTES = 60                                  # limit for one attempt
MAX_ATTEMPTS = 1
MIN_POLL_SECONDS = 10
MAX_POLL_SECONDS = 60

# Optional execution context. Leave empty to use what the target notebook defines.
COMPUTE_TYPE = "Spark"                                # "Spark", or "Jupyter" for the Python runtime; must match the target
DEFAULT_LAKEHOUSE_ID = ""
DEFAULT_LAKEHOUSE_WORKSPACE_ID = ""
ENVIRONMENT_ID = ""
ENVIRONMENT_WORKSPACE_ID = ""
SESSION_TAG = ""                                      # reuse a session when high concurrency mode is on

# Identity
USE_SERVICE_PRINCIPAL = False                         # True: MSAL with secrets from Key Vault
KEY_VAULT_URI = "https://<vault-name>.vault.azure.net/"
TENANT_ID_SECRET = "dispatcher-tenant-id"
CLIENT_ID_SECRET = "dispatcher-client-id"
CLIENT_SECRET_SECRET = "dispatcher-client-secret"
import json
import time
import requests

FABRIC_API = "https://api.fabric.microsoft.com/v1"
FABRIC_SCOPE = "https://api.fabric.microsoft.com/.default"
TERMINAL = {"Completed", "Failed", "Cancelled", "Deduped"}

_token = {"value": None, "at": 0.0}

def bearer():
    """Authorization header; the token is cached and refreshed well before it expires."""
    if _token["value"] is None or time.time() - _token["at"] > 45 * 60:
        if USE_SERVICE_PRINCIPAL:
            import msal
            secret = lambda name: notebookutils.credentials.getSecret(KEY_VAULT_URI, name)
            app = msal.ConfidentialClientApplication(
                client_id=secret(CLIENT_ID_SECRET),
                client_credential=secret(CLIENT_SECRET_SECRET),
                authority=f"https://login.microsoftonline.com/{secret(TENANT_ID_SECRET)}",
            )
            result = app.acquire_token_for_client(scopes=[FABRIC_SCOPE])
            if "access_token" not in result:
                raise RuntimeError(f"Token request failed: {result.get('error')}")
            _token["value"] = result["access_token"]
        else:
            _token["value"] = notebookutils.credentials.getToken("pbi")
        _token["at"] = time.time()
    return {"Authorization": f"Bearer {_token['value']}"}

def run_url():
    # Notebook-specific run endpoint. The generic form is
    # f"{FABRIC_API}/workspaces/{ws}/items/{id}/jobs/RunNotebook/instances"; see the callout below.
    return f"{FABRIC_API}/workspaces/{TARGET_WORKSPACE_ID}/notebooks/{NOTEBOOK_ID}/jobs/execute/instances?beta=false"

def run_body():
    body = {"parameters": [
        {"name": "task_name",       "value": TASK_NAME,       "type": "Text"},
        {"name": "run_id",          "value": RUN_ID,          "type": "Text"},
        {"name": "parameters_json", "value": PARAMETERS_JSON, "type": "Text"},
    ]}
    cfg = {}
    if DEFAULT_LAKEHOUSE_ID:
        cfg["defaultLakehouse"] = {"referenceType": "ById", "itemId": DEFAULT_LAKEHOUSE_ID,
                                   "workspaceId": DEFAULT_LAKEHOUSE_WORKSPACE_ID or TARGET_WORKSPACE_ID}
    if ENVIRONMENT_ID:
        cfg["attachedEnvironment"] = {"referenceType": "ById", "itemId": ENVIRONMENT_ID,
                                      "workspaceId": ENVIRONMENT_WORKSPACE_ID or TARGET_WORKSPACE_ID}
    if SESSION_TAG:
        cfg["highConcurrencyModeOptions"] = {"enabled": True, "sessionTag": SESSION_TAG}
    if cfg:
        body["executionData"] = {"compute": COMPUTE_TYPE, "computeConfiguration": cfg}
    return body
def start_run():
    """POST the run request. Returns (Location URL of the job instance, seconds to wait before polling)."""
    for attempt in range(1, 7):
        resp = requests.post(run_url(), headers={**bearer(), "Content-Type": "application/json"},
                             data=json.dumps(run_body()), timeout=60)
        if resp.status_code == 202:
            location = resp.headers.get("Location")
            if not location:
                raise RuntimeError("The run request was accepted but returned no Location header.")
            return location, int(resp.headers.get("Retry-After", 30))
        if resp.status_code in (429, 430) and attempt < 6:     # throttled, or capacity full and not queued
            time.sleep(int(resp.headers.get("Retry-After", min(30 * attempt, 300))))
            continue
        raise RuntimeError(f"Start failed for {TASK_NAME} ({resp.status_code}): {resp.text[:500]}")

def cancel_run(location):
    try:
        requests.post(location.rstrip("/") + "/cancel", headers=bearer(), timeout=30)
    except Exception as exc:                                  # best effort
        print(f"[WARN] Cancel request failed: {exc}")

def wait_for_job(location, first_wait, deadline):
    """Poll the job instance until it reaches a terminal status or the deadline passes."""
    time.sleep(first_wait)                                    # do not poll before the first Retry-After
    delay = MIN_POLL_SECONDS
    while True:
        resp = requests.get(location, headers=bearer(), timeout=60)
        if resp.status_code == 200:
            job = resp.json()
            if job.get("status") in TERMINAL:
                return job
        elif resp.status_code not in (404, 429, 500, 502, 503, 504):
            raise RuntimeError(f"Status check failed ({resp.status_code}): {resp.text[:300]}")
        wait = max(delay, int(resp.headers.get("Retry-After", 0)))
        if time.time() + wait > deadline:
            cancel_run(location)
            raise TimeoutError(f"{TASK_NAME} exceeded {TIMEOUT_MINUTES} minutes and was cancelled.")
        time.sleep(wait)
        delay = min(int(delay * 1.5), MAX_POLL_SECONDS)

started = time.time()
last_error = None
for attempt in range(1, MAX_ATTEMPTS + 1):
    print(f"[INFO] {TASK_NAME}: attempt {attempt} of {MAX_ATTEMPTS}, notebook {NOTEBOOK_ID}")
    location, first_wait = start_run()
    job_id = location.rstrip("/").split("/")[-1]
    job = wait_for_job(location, first_wait, time.time() + TIMEOUT_MINUTES * 60)
    status = job.get("status")
    if status == "Completed":
        summary = {"task_name": TASK_NAME, "job_instance_id": job_id, "status": status,
                   "attempts": attempt, "duration_seconds": int(time.time() - started)}
        print(f"[OK] {summary}")
        notebookutils.notebook.exit(json.dumps(summary))
    reason = job.get("failureReason") or {}
    last_error = f"{status}: {reason.get('errorCode', '')} {reason.get('message', '')}".strip()
    print(f"[WARN] {TASK_NAME} attempt {attempt} ended as {last_error} (job {job_id})")
    if status in ("Cancelled", "Deduped"):                    # do not retry these
        break

raise RuntimeError(f"Task {TASK_NAME} did not complete. Last result: {last_error}")

Verify against Microsoft Learn

The job scheduler documents a generic endpoint (.../items/{itemId}/jobs/{jobType}/instances) and a notebook-specific one (.../notebooks/{notebookId}/jobs/execute/instances) whose request bodies differ; the notebook article also describes an exitValue field returned by a notebook-specific status call. The code keeps the URL and body in two small functions so you can switch after testing in your tenant. Start from Run On Demand Item Job and Manage and execute notebooks with APIs. The cancel call uses the Cancel Item Job Instance operation; confirm its path in the same reference.

The contract for orchestrated notebooks

For the three run parameters to take effect, the target notebook must declare them in a parameter cell with the same names. The parameter list is not broadly supported for every item type; if the API returns FeatureNotAvailable, the target item type does not accept it.

# Mark this cell as a parameter cell.
task_name = ""                  # set by the framework
run_id = ""                     # pipeline run ID
parameters_json = "{}"          # task-specific settings as one JSON string
import json

defaults = {"load_mode": "incremental", "window_days": 7}
settings = {**defaults, **json.loads(parameters_json or "{}")}

One string parameter keeps the pipeline expression stable while the set of settings evolves. Adding a setting means changing the notebook and the row, not the pipeline.

Test the dispatcher before wiring it in

  1. Run it by hand.

    Set TARGET_WORKSPACE_ID and NOTEBOOK_ID to a harmless notebook (one that only prints and returns) and run all cells. Expect a Completed status and a JSON summary.

  2. Break it on purpose.

    Use a random ID (expect item-not-found with no retries), a notebook that raises (expect a failed run and, with MAX_ATTEMPTS above 1, a retry) and a one-minute timeout against a sleeping notebook (expect a cancel).

  3. Run it as the real identity.

    Run it from a pipeline Notebook activity using the connection the framework will use. Permission problems often appear only here.

  4. Check the Monitor hub.

    The child run is visible in the target workspace as its own notebook run, and the dispatcher run is visible in the hub workspace. Both should agree with the summary the dispatcher returned.

Capacity and concurrency

  • Two sessions per task. A parallel ForEach with batch count n keeps up to n dispatcher sessions and n child sessions alive. A Python dispatcher is small, but it is not free; size the batch count with both in mind.
  • No queue for REST-started runs. A pipeline-started notebook queues when the capacity is full. A run started through the REST API does not queue and is rejected, which is why the dispatcher retries HTTP 430 with a wait. If a stage regularly hits that wall, lower the batch count or use the native Notebook activity for that stage.
  • Session reuse. With high concurrency mode enabled for pipelines, a session tag lets several notebook runs share one Spark session. Set SESSION_TAG for tasks that can share a session and leave it empty for tasks that need isolation.
  • Rate limits. The job scheduler returns 429 with a Retry-After header when a caller starts too many jobs. The dispatcher honors it.

Key takeaways

  • Store IDs, edit names, and connect them with a sync step so renames cannot break a run and a deleted item fails visibly.
  • Prefer the native Notebook activity if your tenant accepts dynamic IDs; use the dispatcher for row-level timeout and attempts or when it does not.
  • Honor Retry-After, retry only throttling and capacity errors, and fail loudly on everything else.
  • REST-started runs are not queued: size the batch count to capacity and expect to retry.
  • Keep one parameter contract (task_name, run_id, parameters_json) for every orchestrated notebook.
