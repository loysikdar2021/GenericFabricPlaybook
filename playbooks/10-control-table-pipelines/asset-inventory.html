Asset discovery and inventory

A scheduled notebook can enumerate every workspace and item you are allowed to see, capture where each one lives and how to connect to it, and publish the result as Delta tables. That catalog is the foundation for naming audits, cost attribution, dynamic orchestration and deployment scripts.

What the inventory captures

The discovery notebook connects to the Fabric REST APIs, walks the workspaces it can see and lists the items in each one: lakehouses, warehouses, notebooks, pipelines, semantic models, reports and every other item type the API returns. For each item it records three groups of facts.

What it is
Item type and display name, plus the description and folder when the API returns them.
Where it is
Workspace name and ID, the capacity and domain the workspace is assigned to, and the item ID (GUID). The item's logicalId links the copies of one item across development, test and production when the workspace is under Git or deployment-pipeline control.
How to connect
For lakehouses and warehouses, the SQL connection string and SQL endpoint ID that programmatic clients need.

The output is a handful of Spark tables saved in a lakehouse. That turns scattered assets across potentially hundreds of workspaces into one dataset you can query, join and schedule against.

Choose the right API

Fabric exposes the same facts through four families of APIs. They differ in scope (what the caller can see), cost (how many calls a full inventory needs) and depth (whether you get schema and lineage).

Verify against Microsoft Learn

Both Fabric admin list APIs are documented as preview, and their throttling (documented as 200 requests per hour) is far tighter than the core APIs. Confirm status, limits and response shape in Admin - List Items before you build a production dependency on them. The admin responses use itemEntities and workspaces arrays and a name field, while the core responses use value and displayName; the notebook below normalizes both.

Identity, permissions and tenant settings

A scheduled inventory should not run as a person. Use a service principal that belongs to a security group, grant the group the access it needs, and keep its secret in Azure Key Vault.

No secrets in code

Store the tenant ID, client ID and client secret as Key Vault secrets and read them at run time with notebookutils.credentials.getSecret. Do not print them, pass them as notebook parameters or write them to files. Output redaction in notebooks is best-effort, not a security boundary.

How the notebook works

Three behaviors of the Fabric list APIs shape the code:

  • Pagination. A response that has more data includes continuationToken and continuationUri; the keys are absent on the last page. The original script's $top=5000 query option is not a documented parameter of the Fabric list-items API, so it silently returns whatever the default page holds. Always loop on the token.
  • Throttling. A 429 response carries a Retry-After header in seconds. Honor it instead of using a fixed sleep, and cap parallel detail calls well below the per-minute quota.
  • Different shapes. Core responses use value and displayName; admin responses use itemEntities or workspaces and name. Normalize once, at the edge.

The inventory notebook

Create a notebook named NB_ORCH_HUB_Inventory in the hub workspace, attach LH_ORCH_HUB_Inventory as its default lakehouse, and split the code into cells as shown. The first cell is a parameter cell so a pipeline or schedule can override values.

# Mark this cell as a parameter cell.
SCOPE = "workspace-api"           # "workspace-api" (per workspace) or "admin-api" (tenant-wide, preview)
USE_SERVICE_PRINCIPAL = False     # True: acquire tokens with MSAL and secrets from Key Vault
KEY_VAULT_URI = "https://<vault-name>.vault.azure.net/"
TENANT_ID_SECRET = "inventory-tenant-id"
CLIENT_ID_SECRET = "inventory-client-id"
CLIENT_SECRET_SECRET = "inventory-client-secret"
INCLUDE_TYPES = None              # for example ["Notebook", "Lakehouse"]; None keeps every item type
FETCH_SQL_DETAILS = True          # one extra GET per Lakehouse and Warehouse
MAX_WORKERS = 8                   # parallel detail calls; the platform quota is 500 calls per minute
KEEP_HISTORY = True               # append every snapshot to fabric_inventory_history
TABLE_PREFIX = "fabric_"
import time
import requests
from concurrent.futures import ThreadPoolExecutor
from urllib.parse import unquote
from pyspark.sql import functions as F
from pyspark.sql.types import StructType, StructField, StringType

FABRIC_API = "https://api.fabric.microsoft.com/v1"
FABRIC_SCOPE = "https://api.fabric.microsoft.com/.default"

_tokens = {}   # scope -> (token, acquired_at)

def get_token(scope=FABRIC_SCOPE):
    """Bearer token for the Fabric REST API (or another scope, such as the Power BI API)."""
    if USE_SERVICE_PRINCIPAL:
        import msal   # add msal to the notebook environment if it is not already installed
        secret = lambda name: notebookutils.credentials.getSecret(KEY_VAULT_URI, name)
        app = msal.ConfidentialClientApplication(
            client_id=secret(CLIENT_ID_SECRET),
            client_credential=secret(CLIENT_SECRET_SECRET),
            authority=f"https://login.microsoftonline.com/{secret(TENANT_ID_SECRET)}",
        )
        result = app.acquire_token_for_client(scopes=[scope])
        if "access_token" not in result:
            raise RuntimeError(f"Token request failed: {result.get('error')}")
        return result["access_token"]
    # Identity of the running notebook: your user, or the identity set on the pipeline activity.
    return notebookutils.credentials.getToken("pbi")

def bearer(scope=FABRIC_SCOPE):
    token, acquired = _tokens.get(scope, (None, 0.0))
    if token is None or time.time() - acquired > 45 * 60:      # refresh well before expiry
        token = get_token(scope)
        _tokens[scope] = (token, time.time())
    return {"Authorization": f"Bearer {token}", "Accept": "application/json"}

def api_get(url, params=None, retries=6):
    for attempt in range(1, retries + 1):
        resp = requests.get(url, headers=bearer(), params=params, timeout=60)
        if resp.status_code == 200:
            return resp.json()
        if resp.status_code in (429, 500, 502, 503, 504) and attempt < retries:
            time.sleep(int(resp.headers.get("Retry-After", min(5 * attempt, 60))))
            continue
        raise RuntimeError(f"GET {url} failed: {resp.status_code} {resp.text[:300]}")

def get_all(url, items_key, params=None):
    """Follow continuationToken until the API stops returning one."""
    params = dict(params or {})
    rows = []
    while True:
        page = api_get(url, params)
        rows.extend(page.get(items_key) or [])
        token = page.get("continuationToken")
        if not token:
            return rows
        params["continuationToken"] = unquote(token)   # tokens can arrive URL-encoded
def list_workspaces():
    if SCOPE == "admin-api":
        raw = get_all(f"{FABRIC_API}/admin/workspaces", "workspaces", {"state": "Active"})
        return [{"workspace_id": w["id"], "workspace_name": w.get("name"), "workspace_type": w.get("type"),
                 "capacity_id": w.get("capacityId"), "domain_id": w.get("domainId")} for w in raw]
    raw = get_all(f"{FABRIC_API}/workspaces", "value")
    return [{"workspace_id": w["id"], "workspace_name": w.get("displayName"), "workspace_type": w.get("type"),
             "capacity_id": w.get("capacityId"), "domain_id": w.get("domainId")} for w in raw]

def items_for_workspace(ws):
    raw = get_all(f"{FABRIC_API}/workspaces/{ws['workspace_id']}/items", "value")
    return [{**ws, "item_id": i["id"], "item_type": i.get("type"), "item_name": i.get("displayName"),
             "description": i.get("description"), "folder_id": i.get("folderId"),
             "logical_id": i.get("logicalId")} for i in raw]

def items_tenant_wide(workspaces_by_id):
    raw = get_all(f"{FABRIC_API}/admin/items", "itemEntities")
    rows = []
    for i in raw:
        ws = workspaces_by_id.get(i.get("workspaceId"), {"workspace_id": i.get("workspaceId")})
        rows.append({**ws, "item_id": i["id"], "item_type": i.get("type"), "item_name": i.get("name"),
                     "description": i.get("description"), "last_updated_utc": i.get("lastUpdatedDate"),
                     "creator_principal_id": (i.get("creatorPrincipal") or {}).get("id")})
    return rows

workspaces = list_workspaces()
by_id = {w["workspace_id"]: w for w in workspaces}
print(f"Workspaces returned: {len(workspaces)}")

if SCOPE == "admin-api":
    items = items_tenant_wide(by_id)
else:
    targets = [w for w in workspaces if w["workspace_type"] == "Workspace"]   # skip personal and admin workspaces
    items = []
    for ws in targets:
        try:
            items.extend(items_for_workspace(ws))
        except Exception as exc:   # one inaccessible workspace must not stop the run
            print(f"Skipped workspace {ws['workspace_id']}: {exc}")

if INCLUDE_TYPES:
    items = [i for i in items if i["item_type"] in INCLUDE_TYPES]
print(f"Items returned: {len(items)}")
def sql_details(row):
    ws, item = row["workspace_id"], row["item_id"]
    try:
        if row["item_type"] == "Lakehouse":
            props = api_get(f"{FABRIC_API}/workspaces/{ws}/lakehouses/{item}").get("properties") or {}
            ep = props.get("sqlEndpointProperties") or {}
            return {"sql_endpoint_id": ep.get("id"), "sql_connection_string": ep.get("connectionString"),
                    "sql_provisioning_status": ep.get("provisioningStatus")}
        if row["item_type"] == "Warehouse":
            props = api_get(f"{FABRIC_API}/workspaces/{ws}/warehouses/{item}").get("properties") or {}
            return {"sql_connection_string": props.get("connectionString"),
                    "collation_type": props.get("collationType")}
    except Exception as exc:
        return {"detail_error": str(exc)[:500]}
    return {}

if FETCH_SQL_DETAILS:
    needs_detail = [r for r in items if r["item_type"] in ("Lakehouse", "Warehouse")]
    with ThreadPoolExecutor(max_workers=MAX_WORKERS) as pool:
        for row, extra in zip(needs_detail, pool.map(sql_details, needs_detail)):
            row.update(extra)
COLUMNS = ["workspace_id", "workspace_name", "workspace_type", "capacity_id", "domain_id",
           "item_id", "item_type", "item_name", "description", "folder_id", "logical_id",
           "last_updated_utc", "creator_principal_id",
           "sql_endpoint_id", "sql_connection_string", "sql_provisioning_status", "collation_type", "detail_error"]
schema = StructType([StructField(c, StringType(), True) for c in COLUMNS])

inventory_df = (spark.createDataFrame([tuple(r.get(c) for c in COLUMNS) for r in items], schema)
                .withColumn("snapshot_utc", F.current_timestamp()))
workspaces_df = (spark.createDataFrame(
        [(w["workspace_id"], w["workspace_name"], w["workspace_type"], w["capacity_id"], w["domain_id"]) for w in workspaces],
        "workspace_id string, workspace_name string, workspace_type string, capacity_id string, domain_id string")
    .withColumn("snapshot_utc", F.current_timestamp()))

def save(df, name, mode="overwrite"):
    writer = df.write.mode(mode).format("delta")
    writer = writer.option("overwriteSchema", "true") if mode == "overwrite" else writer.option("mergeSchema", "true")
    writer.saveAsTable(f"{TABLE_PREFIX}{name}")

save(inventory_df, "inventory")
save(workspaces_df, "workspaces")
if KEEP_HISTORY:
    save(inventory_df, "inventory_history", mode="append")

# Narrow, purpose-named tables that orchestration and deployment code can join to directly.
TYPED = {"notebooks": ("Notebook", "notebook"), "lakehouses": ("Lakehouse", "lakehouse"),
         "warehouses": ("Warehouse", "warehouse"), "pipelines": ("DataPipeline", "pipeline"),
         "semantic_models": ("SemanticModel", "semantic_model"), "reports": ("Report", "report")}
for suffix, (item_type, prefix) in TYPED.items():
    narrow = (inventory_df.filter(F.col("item_type") == item_type)
              .selectExpr("workspace_id", "workspace_name", f"item_id as {prefix}_id", f"item_name as {prefix}_name",
                          "logical_id", "snapshot_utc"))
    save(narrow, suffix)

display(inventory_df.groupBy("item_type").count().orderBy(F.desc("count")))
assert inventory_df.count() > 0, "The inventory is empty: check permissions and tenant settings."

When you need lineage and schema: the scanner flow

The list APIs return item names and IDs. If you also need lineage, data source details or the tables and columns of semantic models, use the scanner, which is asynchronous and works on chunks of workspaces. Take a full scan first, then run incremental scans for workspaces that changed.

Scanner variant: schema, lineage and data sources (Python)

Use this when you need what the list APIs cannot return. It calls the Power BI admin host, so request a token for that resource when you use MSAL (https://analysis.windows.net/powerbi/api/.default). Run it for at most 100 workspace IDs per call and no more than 16 scans at once.

PBI_ADMIN = "https://api.powerbi.com/v1.0/myorg/admin/workspaces"
PBI_SCOPE = "https://analysis.windows.net/powerbi/api/.default"

def modified_workspace_ids(modified_since_iso=None):
    """Full list when modified_since_iso is None; otherwise only workspaces changed since then (within 30 days)."""
    params = {"excludePersonalWorkspaces": "True"}
    if modified_since_iso:
        params["modifiedSince"] = modified_since_iso
    resp = requests.get(f"{PBI_ADMIN}/modified", headers=bearer(PBI_SCOPE), params=params, timeout=60)
    resp.raise_for_status()
    return [w["id"] for w in resp.json()]

def scan(workspace_ids, poll_seconds=30):
    assert 0 < len(workspace_ids) <= 100, "getInfo accepts 1 to 100 workspace IDs"
    flags = {"lineage": "True", "datasourceDetails": "True", "datasetSchema": "True", "datasetExpressions": "True"}
    resp = requests.post(f"{PBI_ADMIN}/getInfo", headers={**bearer(PBI_SCOPE), "Content-Type": "application/json"},
                         params=flags, json={"workspaces": workspace_ids}, timeout=60)
    resp.raise_for_status()
    scan_id = resp.json()["id"]
    while True:
        status = requests.get(f"{PBI_ADMIN}/scanStatus/{scan_id}", headers=bearer(PBI_SCOPE), timeout=60).json()["status"]
        if status == "Succeeded":
            break
        if status not in ("NotStarted", "Running"):
            raise RuntimeError(f"Scan {scan_id} ended with status {status}")
        time.sleep(poll_seconds)          # 30 to 60 seconds is the recommended polling interval
    result = requests.get(f"{PBI_ADMIN}/scanResult/{scan_id}", headers=bearer(PBI_SCOPE), timeout=120)
    result.raise_for_status()
    return result.json()                  # available for 24 hours; persist what you need

Inventory tables

Running the notebook creates the tables below in the default lakehouse. They are snapshots: each run overwrites the current tables and, when KEEP_HISTORY is on, appends the inventory to a history table so you can detect items that appeared or disappeared.

TableGrainKey columns
fabric_inventoryOne row per itemworkspace_id, workspace_name, capacity_id, item_id, item_type, item_name, logical_id, sql_connection_string, sql_endpoint_id, snapshot_utc
fabric_workspacesOne row per workspaceworkspace_id, workspace_name, workspace_type, capacity_id, domain_id, snapshot_utc
fabric_notebooks (and _lakehouses, _warehouses, _pipelines, _semantic_models, _reports)One row per item of that typeworkspace_id, workspace_name, notebook_id, notebook_name, logical_id, snapshot_utc
fabric_inventory_historyOne row per item per runSame columns as fabric_inventory; use snapshot_utc to diff runs

Schedule the notebook at the cadence you need (daily is typical), run it under the service principal, and surface freshness by checking max(snapshot_utc) in your health checks. If you run it from a pipeline, add it as the first activity of a nightly "platform housekeeping" pipeline rather than as part of the business loads.

How the inventory is used for administration

A current, queryable inventory changes administration from workspace-by-workspace clicking into a data-driven practice. Five uses come up repeatedly.

1. Governance and auditing

  • Complete asset visibility. The first question of any audit is "what do we have and where?". The inventory answers it with a query.
  • Enforcing standards. Find workspaces and items that do not follow the naming convention, or workspaces created outside the standard process.
  • Identifying unused assets. Join the inventory to activity data (the admin activity events, or monitoring data kept in your own tables) to flag notebooks, reports or whole workspaces nobody touches. With the admin items API you also get last_updated_utc and the creator principal ID, which helps find orphaned items.
SELECT workspace_name, item_type, item_name
FROM fabric_inventory
WHERE item_type IN ('Notebook', 'DataPipeline', 'Lakehouse', 'Warehouse')
  AND NOT item_name RLIKE '^(NB|PL|LH|WH)_[A-Z0-9]+_[A-Z]+_[A-Za-z0-9]+$'
ORDER BY workspace_name, item_name;

SELECT workspace_name
FROM fabric_workspaces
WHERE workspace_type = 'Workspace'
  AND NOT workspace_name RLIKE '^(DEV|TST|PRD)_[A-Z0-9]+_(BRZ|SLV|GLD|CNSM|DLV|HUB)(_[A-Za-z0-9]+)?$';

2. Automation and dynamic orchestration

This is the use that connects the two halves of the playbook. Instead of copying a notebook's ID into a pipeline by hand, you resolve it from the inventory when you seed or synchronize the control table.

  • Control-table-driven pipelines. fabric_notebooks, fabric_pipelines and the other typed tables are the source for object_id and target_workspace_id in the control table.
  • Cross-workspace operations. A central pipeline in an orchestration workspace needs the workspace ID and item ID to start work in a Bronze or Silver workspace. The inventory supplies both.
SELECT workspace_id, workspace_name, notebook_id, notebook_name, logical_id
FROM fabric_notebooks
WHERE workspace_name IN ('DEV_SALES_BRZ', 'DEV_SALES_SLV')
  AND notebook_name IN ('NB_SALES_BRZ_IngestCustomers', 'NB_SALES_BRZ_IngestProducts', 'NB_SALES_SLV_TransformSales');

Record the workspace ID and the notebook ID, not just the name. When you seed the control table, the sync procedure copies both from the inventory into the control table.

SELECT c.task_name, c.object_id
FROM ctl.control_table AS c
LEFT JOIN LH_ORCH_HUB_Inventory.dbo.fabric_inventory AS i
       ON LOWER(i.item_id) = LOWER(c.object_id)
WHERE c.task_type = 'Notebook'
  AND c.is_enabled = 1
  AND i.item_id IS NULL;

The warehouse reads the lakehouse inventory through a three-part name because both items sit in the same workspace and cross-database queries are supported there. Run this check as part of the pipeline's guard step so a deleted notebook is caught before the run, not during it.

3. Cost management and optimization

  • Resource sprawl. Count workspaces and items per capacity and per domain, and list workspaces that hold zero or one item.
  • Capacity planning. The mix of item types (many large warehouses versus many small notebooks) is a first-order signal when you forecast capacity. The inventory gives you the mix; pair it with the capacity metrics for actual consumption.
SELECT w.capacity_id, i.item_type, COUNT(*) AS items
FROM fabric_inventory i JOIN fabric_workspaces w ON w.workspace_id = i.workspace_id
GROUP BY w.capacity_id, i.item_type
ORDER BY w.capacity_id, items DESC;

SELECT w.workspace_name, w.capacity_id, COUNT(i.item_id) AS items
FROM fabric_workspaces w LEFT JOIN fabric_inventory i ON i.workspace_id = w.workspace_id
WHERE w.workspace_type = 'Workspace'
GROUP BY w.workspace_name, w.capacity_id
HAVING COUNT(i.item_id) <= 1;

4. Security and compliance

  • Defining the security scope. You cannot review access on assets you do not know exist. The inventory is the checklist of items whose permissions and sensitivity labels need review.
  • Auditing footprint. Security teams can use the inventory (and, for lineage and sensitivity details, the scanner output) to confirm that every asset falls under the right governance policy.

5. CI/CD and DevOps enablement

A deployment script usually needs the ID of a target workspace or item. Instead of hard-coding it, query the inventory. When workspaces are connected to Git or deployment pipelines, the logical_id identifies the same item across environments, so you can translate a source ID to the target environment's ID.

SELECT d.item_name, d.item_id AS dev_item_id, p.item_id AS prd_item_id
FROM fabric_inventory d
JOIN fabric_inventory p ON p.logical_id = d.logical_id AND p.item_type = d.item_type
WHERE d.workspace_name = 'DEV_SALES_SLV' AND p.workspace_name = 'PRD_SALES_SLV';

Verify against Microsoft Learn

The item's logicalId is null when no logical ID has been assigned. Confirm in Items - List Items which of your items carry one before relying on it for environment mapping.

Resolve IDs at sync time, not at run time

It is tempting to let the production pipeline look up each notebook ID in the inventory on every run. Do not: a stale or partial inventory then breaks the run. Resolve IDs when you seed or synchronize the control table, validate them in the guard step, and let the run read only the control table.

Key takeaways

  • Pick the API by the question: scanner for schema and lineage, admin list for tenant-wide, core list for everything scoped to what the identity can see.
  • Run the inventory as a service principal with secrets in Key Vault; use MSAL when the notebook token's scope is too narrow.
  • Follow continuation tokens and honor Retry-After; never rely on a page-size query option.
  • Store IDs and logical_id, key joins on IDs, and keep a history table.
  • Resolve IDs into the control table at sync time and validate them in the guard step.
