Playbook 10 · Half B · Scale-out

Extended scenario and workshop

The first plan has five tasks. This page grows it to twenty without touching the pipeline, which is the point of the framework: new work is a data-entry step. It shows the full plan, the script that populates the control table, what each stage lookup returns, and what the run looks like on a timeline. It ends with a workshop outline you can use to teach the build.

The initial plan

The first plan is the five tasks seeded on the Warehouse objects page: two ingests in parallel, one transform after both, and two stored procedures in sequence. It is small enough to read on one screen and large enough to exercise every part of the framework: a parallel stage, a dependency between stages and a sequential stage of a different task type.

Do not move on until this plan runs end to end, logs every task and sends an email when you break a task on purpose (the failure drill on the master pipeline page).

The expanded plan

The extended scenario adds fifteen tasks: seven notebooks that simulate data-preparation steps and eight stored procedures that build a small dimension table. They do trivial work on purpose, so the whole run takes minutes and the timeline is easy to read.

Order is a column, not a name

The eight procedures are named in the order the dimension is built, and sequence_no repeats that order. In an earlier build the procedures were numbered in reverse and the lookup ordered them by name within a stage, so the cleanup ran before the load that fed it. The lookup on the master pipeline page orders by sequence_no first and uses the name only to break ties.

Populate the control table

Four things have to exist before the rows can be inserted. Create the demo items, then run the populate script.

1. Demo notebooks

Create seven notebooks with the names in the table above: four in the Bronze workspace and three in the Silver workspace. Each has the same two cells, which simulate work so the timeline has something to show. The first cell is the parameter cell and matches the orchestrated-notebook contract.

# Mark this cell as a parameter cell.
task_name = ""
run_id = ""
parameters_json = "{}"
import json
import time

settings = {"sleep_seconds": 20, **json.loads(parameters_json or "{}")}
print(f"[{task_name}] run {run_id}: simulating {settings['sleep_seconds']} seconds of work")
time.sleep(settings["sleep_seconds"])
print(f"[{task_name}] done")

The sleep length comes from parameters_json, so you can make one task slow, or force one to fail, without opening the notebook.

2. Demo procedures

Create a small log table, then eight procedures that each insert one row. The procedures run in sequence, so there is no write conflict.

CREATE TABLE dbo.demo_proc_log
(
    proc_name  VARCHAR(128) NOT NULL,
    ran_at_utc DATETIME2(6) NOT NULL
);
CREATE OR ALTER PROCEDURE dbo.usp_create_dim_table
AS
BEGIN
    SET NOCOUNT ON;

    INSERT INTO dbo.demo_proc_log (proc_name, ran_at_utc)
    VALUES ('usp_create_dim_table', SYSUTCDATETIME());
END;

Create the other seven from the same template, changing the name in both places: usp_insert_staging_data, usp_apply_data_type_cast, usp_calculate_aggregate, usp_apply_hardcoded_filter, usp_parameterized_load, usp_update_dim_flag and usp_cleanup_staging_table.

3. Refresh the inventory

Run the inventory notebook so the new notebooks appear in fabric_inventory. The sync procedure resolves IDs from there.

4. Insert the fifteen rows

The script follows the same pattern as the seed: delete by name, insert inside one transaction, no IDs.

Then resolve the IDs, run the guard and count the plan:

EXEC dbo.usp_sync_object_ids;
EXEC dbo.usp_validate_control_table;

SELECT stage, task_type, COUNT(*) AS tasks
FROM ctl.control_table
WHERE is_enabled = 1
GROUP BY stage, task_type
ORDER BY stage, task_type;

The count should be 6 notebooks in stage 1, 4 notebooks in stage 2 and 10 stored procedures in stage 3. If the guard throws, read which task it names: the usual causes are a notebook that is not in the inventory yet, or a procedure that was not created.

Then check the one pipeline setting that this scenario stresses: stage 1 now has six parallel tasks, so raise the ForEach_Stage1 batch count from 2 to 3 and keep an eye on capacity, because each parallel task holds a dispatcher session and a notebook session.

Run it and read the timeline

Run the master pipeline. When it finishes, the log answers three questions: what ran, in what order and how long each part took.

SELECT task_name, stage, started_utc, ended_utc, duration_seconds, status
FROM ctl.vw_task_run_timeline
WHERE run_id = (SELECT TOP (1) run_id FROM ctl.vw_run_summary ORDER BY started_utc DESC)
ORDER BY started_utc, task_name;

How to read it:

  • Stage 1 is a plateau. The bars overlap, limited by the batch count. Raising the batch count shortens the stage until capacity, not the pipeline, becomes the limit.
  • Stages 2 and 3 are staircases. Each bar starts when the previous one ends. A long step stands out immediately, which is the cue to look at that task.
  • The gaps between stages are start-up time. A large gap at a stage boundary points at session start-up or capacity queueing, not at the task.

The Monitor hub shows the same run from the pipeline's side. Open the run's detail page and switch from the list of activity runs to a Gantt view, if your tenant's view selector offers it, to compare the two. A failed run looks different on both: the failed task has a Failed row and a message, and no rows exist for the stages after it.

Prove the framework: add a task without touching the pipeline

Insert one more procedure task into stage 3, run the guard and run the pipeline again. It appears on the timeline with no change to any activity. Then set is_enabled = 0 on it and run again to see it disappear. That round trip is the whole value of the pattern in two minutes.

Turn it into a workshop

The pipeline is small enough to build by hand in a half day, and building it is the best way to understand it. This outline works for a group of data engineers. It does not depend on a pre-built pipeline file: participants build the pipeline from the master pipeline page and compare it with the description of the finished canvas. A pipeline exported from source control is tied to one workspace's item IDs and connections, so if you keep your own exported copy for instructors, expect to rebind every connection and workspace reference after importing it.

Facilitator notes

  • Set up shared mail early. The notification lab needs a mailbox or Teams channel that every participant can send to, and an admin may have to approve the connection.
  • Give each participant their own hub workspace. Shared control tables make parallel exercises collide.
  • Watch capacity. Twenty participants each running six parallel notebooks will saturate a small capacity. Stagger the extension lab, or keep stage 1 at two parallel tasks.
  • Break things on purpose. The failure drill is where participants understand why both outcome paths matter. Do not skip it.
  • Close with the decision table. Ask each participant which of their own workloads belongs in a control table and which does not, using the decision table.

Clean-up

Disable the demo tasks (is_enabled = 0) when the workshop ends, rather than deleting them, so the timeline and run history stay readable. Drop the demo tables and notebooks when the workspace is retired.

Key takeaways

  • Growing the plan from five to twenty tasks was a data-entry step: rows in the control table and the dependency table, plus a sync and a guard run.
  • Order belongs in sequence_no. Never rely on names, which are sorted alphabetically.
  • Preview each stage lookup before the run; check count, order and nulls.
  • A timeline derived from the run log shows plateaus, staircases and start-up gaps at a glance.
  • Teach the framework by building it, and include a deliberate failure and a restart.
