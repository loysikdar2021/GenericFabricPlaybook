Control-Table-Driven Pipelines and Asset Discovery

Replace pipelines full of hard-coded notebook names and stored-procedure calls with a small set of generic pipelines that read their work from a Warehouse table, and keep the item IDs that table needs fresh with an automated inventory of everything in your tenant.

  • Audience platform engineers, Fabric admins
  • Level Advanced
  • Runs on Data Factory pipelines, Warehouse, notebooks
  • Reading time about 100 min

The problem this playbook solves

Once a platform grows past a few dozen notebooks and SQL scripts, orchestration becomes the bottleneck. Every new load or transformation means opening a pipeline, dragging another activity onto the canvas, wiring dependencies by hand, and promoting the change through every environment. The same eight-activity pattern (log start, run, log end, notify) is copied dozens of times, and no two copies drift in the same way.

Three things go wrong at scale:

  • Brittle references. A notebook is selected by display name or pinned by a value copied into an activity. Rename it, or recreate it in another workspace, and the pipeline fails on a Monday morning.
  • No single picture of the flow. The order of execution lives in canvas wiring spread over many pipelines. Nobody can query "what runs after this task?" or "which tasks failed last night?".
  • Change cost. Adding a task is a development exercise rather than a data-entry task, so platform teams become a queue.

This playbook has two halves that reinforce each other.

HALF A

Automated asset discovery

A scheduled notebook enumerates workspaces and items through the Fabric and Power BI REST APIs and lands them in queryable Delta tables: what exists, where it lives, and how to connect to it.

 HALF B

Control-table orchestration

A Warehouse table describes every task. Generic pipelines look rows up, iterate them, run the right kind of activity, write an append-only run log and notify owners on failure.

What changes when work moves into a table

The control-table pattern separates the what (a row that names a task, its type, its stage and its owner) from the how (a generic engine that knows how to run any task type, log it, and raise an alarm). Adding the twentieth notebook to the nightly run becomes an INSERT, not a pipeline change.

When to use it, and when not to

A good fit when

  • You orchestrate dozens or hundreds of notebooks, procedures or child pipelines with the same run, log and notify pattern.
  • People other than pipeline authors need to add or disable tasks under change control.
  • You need an audit trail of every attempt that you can query with SQL.
  • Tasks live in several workspaces and you want one place that knows their IDs.

A poor fit when

  • You have fewer than a handful of stable tasks. A plain pipeline is simpler to read.
  • Branching depends on data values produced mid-run. Use a notebook DAG or pipeline logic.
  • The job is bulk table copy. A Copy job already covers it.
  • Nobody on the team can maintain T-SQL and pipeline expressions.

Prerequisites in brief

  • A Fabric workspace on a capacity that hosts the Warehouse, the inventory lakehouse, the notebooks and the pipelines (the hub workspace).
  • Permission to create and run pipelines and to execute procedures in the Warehouse.
  • A service principal (or, for activities that support it, a workspace identity) with access to every workspace you orchestrate, plus the tenant settings that let it call Fabric APIs. The details are on the design page.
  • A shared mailbox or Teams channel for failure notifications, owned by the team rather than a person.
  • An Azure Key Vault if you authenticate the notebooks with a service principal secret.

How this fits with the other playbooks

  • Playbook 03, Medallion Architecture: the ingest and transform notebooks that the control table orchestrates live in the layer workspaces defined there. The control table supplies the stage ordering across those layers.
  • Playbook 04, Cross-Workspace Pipeline Orchestration: the hub-and-spoke pattern decides where pipelines live. This playbook makes the hub data-driven, so spokes are invoked from rows instead of from canvas wiring.
  • Playbook 09, Variable Libraries: use a variable library for the environment-specific values (hub workspace ID, warehouse connection, default recipients) that the framework itself needs when you promote it.
  • Playbook 07, Deployment Pipelines and Promotion: how the pipelines and notebooks of the framework move from development to production.

Key takeaways

  • Move the facts about each task (type, order, target ID, owner) into a Warehouse table and keep the pipeline generic.
  • Reference items by ID, not by name, and refresh those IDs from an automated inventory.
  • Log every attempt with append-only inserts. Derive "current status" with views instead of updating rows in place.
  • Treat the framework as a product: guard step, tests, versioned seed scripts and an owner.
