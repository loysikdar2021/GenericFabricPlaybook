Playbook 05 · GitHub Integration

Sync model and supported items

After the first sync, day-to-day work is a loop of commits and updates. The rules of that loop explain almost every message the source control pane shows you, and most of the surprises: why Commit greys out, why a file changed that nobody touched, why an item is silently missing from the repository.

  • Audience developers, workspace admins
  • Use it for understanding status, conflicts, branch operations and limits

Two directions, never at the same time

Commit moves workspace changes to Git. Update moves Git changes into the workspace. You can only do one at a time, and the two are asymmetric in ways that matter:

Commit (workspace to Git)Update (Git to workspace)
GranularityYou choose which changed items to commit. Some items also allow committing individual files from the compare experience (a preview capability).Always the whole branch folder, up to the tip of the branch. You cannot select items.
Blocked whenThe branch has incoming updates you have not taken, or the item is in conflict.The same item changed on both sides and the conflict is unresolved.
Destructive toThe Git folder only in the first-sync case; otherwise adds a commit.The workspace: items not in Git are removed, and existing items are overwritten.
Recoverable byReverting the commit in Git.Only by getting the content back into Git first, or from a backup.

The Git integration state of a workspace is visible in three places: a Git status column in the item list, a Source control icon that shows how many items differ, and, at the bottom of the screen, the connected branch, the time of the last sync and a link to the commit the workspace is synced to. The Source control panel has tabs for Commits and updates (the Changes and Updates lists), Branches, and, for GitHub-connected workspaces, Account details.

The life of an item: Git status

StatusMeaningWhat to do
SyncedThe item is the same in the workspace and in the connected branch.Nothing.
Uncommitted changesThe workspace item differs from Git; the change is not yet committed.Commit it, or undo it.
Update requiredThe branch has a newer version of the item.Update the workspace.
ConflictThe item changed in both places since the last sync.Resolve (see below). Commit is disabled and update will not run until you do.
Identical but needs updateThe item is the same in both, but the workspace must move to the tip of the branch.Update; no content changes.
Unsupported itemFabric cannot version this item type.Ignored by commit and update, and never deleted by them.

The change lists use a second vocabulary: new, modified, deleted, conflict and same changes (the same edit was made on both sides).

Resolving conflicts

A conflict occurs only when the same item changed in both places. Choose the lightest resolution that is safe.

  • Accept incoming changes overwrites the workspace item; the workspace change is lost and the status becomes Synced.
  • Keep current content keeps the workspace version; after the update the status is Uncommitted changes and you still have to commit it.
  • Resolve in Git is the right choice when you cannot tell which side to keep. Check out a new branch from the last synced commit (the status bar shows it), commit your changes there, resolve and merge in Git, then switch the workspace back to the original branch. Checking out a branch keeps your current workspace state, so uncommitted work survives.
  • If one or more items fail to update, Microsoft documents a manual partial update path for them.

Branch operations in the Source control pane

The Branches tab collects the operations that change which branch a workspace is attached to. They are easy to confuse, and the difference between them is whether they change the workspace content, the connection, or both.

OperationWhat it doesWorkspace contentWho can
Branch out to another workspaceCreates a new branch from the tip of the source workspace's connected branch, then creates a new workspace (or uses an existing one) connected to it.The new workspace is populated; the source is untouched.Admin, Member, Contributor. Needs capacity. Existing-workspace targets need admin, or contributor rights plus the branch-switching setting.
Checkout new branchCreates a branch from the last synced commit and repoints the current workspace to it.Unchanged, including uncommitted changes.Admin (or Contributor with the setting).
Switch branchConnects the workspace to another new or existing branch and syncs it.Overwritten by the target branch; items not in the target branch are deleted. Blocked while uncommitted changes exist.Admin (or Contributor with the setting).
Commit to new branchCreates a fresh branch and commits the selected changes to it, without leaving your branch.Unchanged. The new branch is based on the last synced state and is not connected to this workspace.Anyone who can commit. Also works when updates are pending.
UndoReverts selected items to the last synced state.Reverted. A deleted item comes back as a new item (labels lost, owner reset); an undone new item is deleted for good.Anyone who can commit.
DisconnectRemoves the Git connection and any branched-workspace relationships.Unchanged.Admin.

The Related branches list shows workspaces that were branched from this one, or that share the same connection properties, so you can jump between them without hunting through the workspace list.

Supported and unsupported items

Git integration supports a growing but incomplete list of item types, grouped by workload. An item that is not supported does not block the connection: it stays in the workspace, appears in the source control pane, and is ignored by commit and update. The consequence for design is simple: anything that must be reproducible from Git has to be an item type on the list. Inventory the unsupported items in each workspace before you connect it.

Everything here has an API

Status, commit, update, connect and initialize connection all have Fabric REST equivalents with the same rules (same permissions, same limits, long-running operations that you poll). They are used on the automation page.

Key takeaways

  • Commit is selective and additive; Update is whole-branch and destructive to the workspace, so always check the Updates list before pressing it.
  • Resolve conflicts in the UI when the answer is obvious, undo when your edit is disposable, and use a new branch in Git when you are unsure; never reconnect to "fix" a conflict.
  • Know the four branch operations: only branch out creates a workspace, only switch branch overwrites content, and checkout new branch and commit to new branch leave it alone.
  • Check the live supported-item list for every item type you depend on, and keep custom files out of item folders.
