Rolling back a bad change

Version control makes a bad change recoverable, but only if you pick the right tool. The deciding question is whether anyone else has already pulled the commit.

git revert versus git reset

git revertgit reset --hard
What it doesAdds a new commit that applies the inverse of an earlier one.Moves the branch pointer back and discards the commits after it.
HistoryPreserved. The mistake and its undo are both visible.Rewritten. The discarded commits disappear from the branch.
Shared branchesSafe.Dangerous. Everyone who pulled the old commits now has a diverged copy.
Needs a force pushNo.Yes.
Allowed on mainYes, through a pull request.No. The ruleset blocks force pushes.
Effect on FabricThe branch moves forward, so a normal Update applies it.The workspace's last synced commit may no longer exist on the branch; behaviour is not something to rely on.

Method 1: revert (the default)

Because main is protected, the revert travels the same road as any other change.

  1. Find the change.

    Open the merged pull request that introduced the problem. If it was squash-merged it is a single commit; if it was merged with a merge commit, you will revert that merge commit.

  2. Create the revert.

    On the merged pull request choose Revert. GitHub creates a branch and opens a new pull request containing the inverse change. Or do it locally, as below.

  3. Review and merge it under the normal rules. If the incident demands speed, ask the reviewers for a fast-track review rather than asking an administrator to bypass the ruleset.
# start from a current main
git switch main
git pull origin main
git switch -c revert/1234-orders-load

# find the commit
git log --oneline -n 15

# squash or rebase merge: an ordinary commit
git revert <commit-sha>

# merge commit: name the parent to keep (1 is the main side)
git revert -m 1 <merge-commit-sha>

# several commits: oldest^..newest reverts them newest first
git revert <oldest-sha>^..<newest-sha>

# publish the branch and open a pull request into main
git push -u origin revert/1234-orders-load

Restoring one item from an earlier commit

Often only one notebook or pipeline needs to go back. Restore that folder from a known-good commit onto a new branch, and send it through review as a normal change. This works for a changed item and for one that was deleted.

git switch -c restore/1234-churn-notebook main
git restore --source=<good-sha> -- SALES_GLD/NB_SALES_GLD_ChurnScore.Notebook
git add SALES_GLD
git commit -m "Restore ChurnScore notebook from <good-sha>"
git push -u origin restore/1234-churn-notebook

Method 2: reset (private branches only)

Reset suits one case: a feature branch that only you use, where you want to throw away the last few commits and start over from a good one. It rewrites history, so it needs a force push, and the ruleset will not allow that on main.

git switch feature/1234-add-churn-model
git log --oneline
# discard every commit after the good one, and any uncommitted changes
git reset --hard <good-sha>
# overwrite the remote branch, but only if nobody added commits to it
git push --force-with-lease origin feature/1234-add-churn-model
  • Prefer --force-with-lease to --force. It refuses to overwrite commits you have not seen.
  • Hard reset discards uncommitted work in your clone. Check git status first.
  • The feature workspace. A workspace connected to the rewritten branch is now pointing at history that no longer exists. Because feature workspaces are disposable, the clean fix is to start again: delete it and branch out from the corrected branch, or switch it to a fresh branch. Uncommitted changes in a workspace are not a Git matter at all: use Undo in the source control pane.

Never reset a branch that a shared workspace follows

The DEV workspace follows main, and any shared feature workspace follows its branch. Rewriting either leaves people and workspaces on commits that are no longer in the branch. This is the practical reason the ruleset blocks force pushes on main.

Restoring in Fabric after the branch is fixed

Once the branch is correct, bring Fabric to match:

  1. Open the Fabric workspace connected to the branch, then Source control, then the Updates tab. Fabric detects that the branch moved and lists the items that will change.
  2. Read the list. Items the reverted change added will be deleted from the workspace; items it removed will be created again.
  3. Choose Update all, then confirm every item shows Synced.
  4. For TST and PRD, let the deployment workflow run for the reverted commit. The workspace is not rolled back until the pipeline has deployed the corrected definitions.

Code rolls back; data does not

Reverting definitions does not undo data changes. A notebook that already rewrote a table, or a schema change that already ran, is still done after the revert. Plan data recovery separately, for example with Delta table restore, and decide up front whether an incident is a revert or a fix-forward.

Restored items are new items

An item that an update re-creates gets a new object ID, and a re-created lakehouse or warehouse is empty. If the item is still within the recycle bin retention window, restoring it from the workspace recycle bin keeps its original ID and its data; use that route for data-bearing items, and delete the re-created duplicate if both exist. Check the current recycle bin retention on Microsoft Learn.

Running it day to day

Auditing and monitoring

  • GitHub. Review the audit log for changes to repository settings, team membership, rulesets, environments and secrets, and for any use of a bypass.
  • Fabric. Use the monitoring hub for run history and the activity log for who did what, including calls made by the service principals.
  • Entra ID. Watch sign-in logs for the service principals: unexpected locations or failures are the earliest sign of a misused or broken credential.
  • Together. A change should be traceable from a Fabric item version to a commit, to a pull request, to a reviewer, to a deployment run. If any link is missing, find out why.

Testing as a gate

  • Unit tests for helper code used by notebooks run in pr-validation with a test framework such as pytest, and the result is a required status check.
  • Data quality checks run against test data in TST after each deployment. Add a test job between deploy-tst and deploy-prd so PRD is only offered for approval when the checks pass.
  • Regression tests are added with every fix, so the same incident cannot recur silently.

Scaling to many repositories

  • Define the baseline once in an organization-level ruleset and apply it to every Fabric repository.
  • Package the deployment steps as a reusable workflow that each repository calls, so every team deploys the same way and a fix lands everywhere at once.
  • Keep a template repository with the standard layout, CODEOWNERS, workflows and pull-request template, and create new repositories from it.
  • Keep one service principal per environment per repository group, not one shared by everything.

Go-live checklist

Foundation

  • Fabric tenant settings for Git integration are enabled for the right groups, and the service principal API setting is scoped to the automation group.
  • The GitHub organization enforces single sign-on and two-factor authentication, with teams synced from Entra ID groups.
  • A token policy exists, developers use fine-grained tokens, and the owner of each Fabric GitHub connection is documented.

Repository

  • The folder layout matches the workspace layout, and each connected folder was empty or intentionally non-empty before the first sync.
  • The baseline is committed to main, and the safety-net clone is in place until the baseline is proven.
  • The ruleset on main is active: pull request, approvals, stale approvals dismissed, conversations resolved, code owners, no force push, no deletion.
  • CODEOWNERS covers every item folder and .github/; the owning teams have Write access.
  • Feature branches are not covered by pull-request rules, so Fabric can commit to them.

Automation

  • One service principal per environment, in the automation group, with the lowest workspace role that works.
  • Federated credentials are bound to environment subjects, and no client secret exists.
  • Environments tst and prd exist with required reviewers, prevent self-review, and deployment branches limited to main.
  • Workflows declare minimal permissions, pin actions to commit SHAs, and the validation job is a required status check.
  • A TST deployment has succeeded end to end, and a deliberate rollback has been rehearsed there.

Operations

  • The recurring review calendar exists with named owners.
  • Developers know the workflow: branch out, small commits, pull request, delete the feature workspace afterwards.
  • The rollback procedure, including who approves a fast-track revert, is written down where the on-call team will find it.

Key takeaways

  • One picture: developers work in feature workspaces, GitHub enforces review on main, DEV follows main, and a pipeline with OIDC and approvals promotes to TST and PRD.
  • Revert by default, through a pull request. Reset only on private feature branches, with --force-with-lease.
  • Rolling back code is not rolling back data. Read the Updates list before applying it, and expect restored items to be new, empty items unless you use the recycle bin.
  • Schedule the boring reviews: bypass use, access, expiry, versions. Most failures are drift.
  • Rehearse a rollback in TST before you need it in PRD.
