GitHub Flow for Fabric

One branch is always deployable, every change starts on a short-lived branch, and nothing reaches that branch without a pull request. Fabric adds one twist: every branch that holds work in progress also gets its own workspace, and that workspace is where the work is actually done.

  • Audience developers, reviewers, workspace admins
  • Use it for daily workflow, branch naming, pull requests, cleanup

GitHub Flow, adapted to workspaces

GitHub Flow is deliberately small. It has three rules, and they fit analytics development well because most Fabric changes are modest, frequent and independently shippable:

  1. main is always deployable. It is the source of truth, and anything merged into it is safe to promote.
  2. All work happens on a descriptive, short-lived branch created from main.
  3. Changes return to main only through a pull request, which is where review, automated checks and discussion happen.

Compared with Gitflow, there are no long-lived develop, release or hotfix branches to reconcile. Environments are not branches here: TST and PRD are reached by promoting what is in main (see the deployment playbook), not by merging into environment branches.

DEV follows main; it does not write to it

Once the main ruleset requires pull requests (see rulesets), a commit from the workspace connected to main is rejected, because Fabric pushes the commit straight to the connected branch with the user's own token. Treat that workspace as update-only: nobody edits items in it. Edits happen in feature workspaces and arrive through pull requests.

Branch naming

A branch name is the first thing a reviewer sees. Make it carry the purpose and a pointer to the work item, and keep it boring enough to type.

PrefixUse forExample
feature/New capability or an enhancementfeature/1234-add-churn-model
bugfix/Defect fix for something not yet in productionbugfix/1250-fix-sales-report-filter
hotfix/Urgent production fix, expedited reviewhotfix/1301-orders-load-timeout
chore/Housekeeping: renames, cleanup, documentationchore/1262-rename-gold-notebooks

Recommended pattern: <prefix>/<work-item-id>-<short-description>, lowercase, hyphens between words.

  • Lead with the work item ID. It makes the branch traceable and sorts related branches together. A date in the name goes stale and says nothing about intent.
  • Keep it short. Fabric accepts branch names up to 244 characters, but the name also appears in the workspace status bar and in PR lists.
  • Use one slash only. Git cannot hold a branch named feature and another named feature/x at the same time. Never create a branch that equals a prefix.
  • Avoid spaces and special characters. Branch names are carried through URLs, scripts and API calls.

The feature workspace follows the house workspace convention with the work item as the qualifier: DEV_SALES_BRZ_F1234 for the workspace that holds feature work on DEV_SALES_BRZ.

Getting a feature workspace

There are two ways to end up with a branch and a workspace connected to each other. Both produce the same result; they differ in who needs which permission.

HowIn the source control pane, Branch out to another workspace. Fabric creates the branch from the connected branch, creates the workspace, connects them and populates it.Create the branch in GitHub, create or reuse a workspace, connect the workspace to the new branch, and sync.

Branch-out starts from what is committed on the source branch. Uncommitted work in the source workspace is not carried over, and neither are workspace settings, access assignments or data. The new workspace is a clean sandbox.

The feature loop

  1. Start from a current DEV workspace.

    Before branching out, make sure the DEV workspace shows no pending updates. A feature that starts from an old commit begins life with conflicts.

  2. Branch out.

    Name the branch with the pattern above and the workspace with the qualifier. Wait for the sync to finish; it can take a few minutes for large workspaces.

  3. Develop in the feature workspace.

    Change items in the Fabric UI as usual. Commit small, logical groups of items with a message that says why, not only what. Several small commits review better than one large one.

  4. Test against isolated data.

    See Data is not copied. A feature workspace that still points at shared DEV data is not isolated.

  5. Open a pull request into main.

    Describe the change and how it was tested. Details are in the pull-request section.

  6. Respond to review in the same branch.

    Commit fixes from the feature workspace. Do not open a second pull request for the same work.

  7. Merge, then update DEV and clean up.

    See after the merge.

The pull-request process

The pull request is where the repository's rules become visible. It is the one place where the author, the reviewers, the automated checks and the ruleset all meet.

Opening the pull request

  1. In the repository, open Pull requests and choose New pull request, or use the Compare & pull request prompt that appears after a push.
  2. Set the base to main and the compare branch to your feature branch.
  3. Write a title that states the outcome, and fill in the description (template below).
  4. Check the Files changed tab yourself first. A surprise in your own diff, such as a deleted folder or a changed logicalId, is cheaper to catch now.
  5. Choose Create pull request. Use a draft pull request if you want early feedback before it is ready to merge.

What reviewers look for in a Fabric diff

Item definitions are text, so they can be reviewed, but the formatter produces noise. Knowing where the signal is makes reviews short.

Look atWhy
Folders added or removedDeleting an item folder deletes the item in DEV at the next update. For a lakehouse, that includes its data.
.platform changesA changed logicalId on an existing item breaks dependency binding. A changed display name renames the item and its folder.
Hard-coded IDsWorkspace, lakehouse, warehouse and connection GUIDs in pipelines and notebooks bind the item to one environment. They belong in variables or parameters.
Secrets and tokensCredentials pasted into a notebook cell or a parameter file stay in history after they are deleted.
Semantic model definitionsRead the measure, relationship and partition changes. Large reorderings are the formatter, not the author.
Files outside item foldersWorkflow, parameter and ownership files change how the pipeline and the review itself behave. Treat them as security-relevant.

Merging

MethodResult on mainFit
SquashOne commit per pull request, with a message you write.Default for feature branches. Keeps history readable and makes a revert a single step.
Merge commitAll branch commits plus a merge commit.When individual commits carry meaning and you want them preserved.
RebaseBranch commits replayed onto main, no merge commit.Linear history, but the commit IDs change, which confuses anyone still on the branch.

Restrict the allowed methods in the ruleset so everyone merges the same way. The pull-request section of the ruleset page shows where.

After the merge

  1. Update the DEV workspace.

    Open Source control on the DEV workspace. It shows Update required. Review the Updates list, choose Update all, and confirm every item returns to Synced. Update is whole-branch, so the list also shows other people's merged work.

  2. Promote.

    DEV now matches main. Promotion to TST and PRD is the job of deployment pipelines or automation, covered in the deployment playbook and verified with its checklist.

  3. Delete the feature workspace.

    Its job is over, and every leftover workspace is capacity and clutter. Disconnect or delete it before deleting the branch.

  4. Delete the feature branch.

    Use Delete branch on the merged pull request. A workspace that is still connected to a deleted branch can no longer commit or update.

  5. Start the next change from a new branch.

    Never reuse a merged branch. After a squash merge, its history no longer matches main, and further commits on it produce conflicts.

The same cleanup applies to the safety-net clone workspaces created during the first connection (see the backup clone): delete them once source control is stable and the baseline is proven.

Keeping a long-running branch current

Short branches rarely need this. If main moves while your pull request is open, GitHub shows the branch as out of date. Use Update branch on the pull request to merge main into the feature branch, then run Update all in the feature workspace to receive the result. If two people changed the same item, resolve it as described on the conflict section; prefer small, frequent pull requests over heroic merges of notebooks and pipelines.

Data is not copied

Branch-out copies definitions, never data

A new feature workspace has item definitions, and lakehouses and warehouses in it are empty. A notebook that is bound to a specific lakehouse or workspace by ID keeps pointing at the original, so a test run in the "isolated" feature workspace can read, and write, shared DEV data.

Two practices make a feature workspace honest:

  1. Make every item environment-aware. No hard-coded workspace names, lakehouse IDs or connection strings. Read them from environment configuration; variable libraries are the Fabric mechanism for this. A feature workspace then resolves to its own values.
  2. Seed the data. A script or pipeline, triggered when the feature workspace is created, loads a small, anonymised and representative data set. Test data must not contain real personal or confidential data.

Also remember that the new branch does not carry over workspace-level settings and access. Reapply anything your organisation requires on the feature workspace, such as roles and sensitivity labels.

Key takeaways

  • Environments are workspaces, not branches. main feeds DEV, and promotion carries it onward.
  • DEV follows main and is update-only; all editing happens in feature workspaces connected to feature branches.
  • Name branches prefix/work-item-short-description and use the work item as the workspace qualifier.
  • One branch, one pull request, one merge. Delete the feature workspace before the branch, and never reuse a merged branch.
  • Review Fabric diffs for deleted folders, changed logicalId values, hard-coded IDs and secrets.
  • Branch-out copies definitions only. Parameterise the bindings and seed test data, or the sandbox is not a sandbox.
