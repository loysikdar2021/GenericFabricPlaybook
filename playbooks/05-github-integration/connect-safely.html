Playbook 05 · GitHub Integration

Connecting safely

The moment you click Connect and sync is the only point in the integration where a single wrong choice can delete a workspace's content with no way back. Everything after it is recoverable from Git. This page is the procedure that makes the first sync boring: back up, connect to an empty folder, commit a baseline at once, and only then turn on the guard rails.

  • Audience workspace admins
  • Risk highest of any step in this playbook
  • Time about 30 minutes per workspace

What the first sync does

When you connect, Fabric makes the workspace and the branch folder match. The direction depends on what each side holds. If one side is empty and the other has content, content is copied from the non-empty side to the empty one. If both have content, you must choose, and the choice overwrites one of them.

An empty folder is a destructive source

The same logic applies after the connection. Update pulls what is in Git and removes workspace items that do not exist there. If the folder is empty or lacks your items, an update aligns the workspace to "empty". Never press Update against a branch or folder that does not yet contain your baseline.

Preflight safeguards

Do these before the first connection to a workspace that already holds work. For a brand-new, empty workspace most of them do not apply.

1 · Clone the workspace as a safety net

The most dependable backup that works before source control exists is a deployment pipeline: deploy the DEV workspace into a new, differently named workspace (for example BAK_DEV_SALES_BRZ). Fabric copies the item definitions into the target workspace. Data is the catch: a deployed lakehouse arrives as a new, empty lakehouse, and shortcut definitions are synced while their contents are not, so the clone is only a true backup after you hydrate it.

2 · Record what Git will not hold

  • Workspace access (roles and groups), capacity assignment and workspace-level settings. Deployment pipelines are separate objects and are not in the repository.
  • Data: lakehouse files and tables, warehouse tables. Git stores definitions, not data.
  • Items that are not supported for Git. They stay in the workspace, appear in the source control pane, and cannot be committed. Inventory them now (see the supported items section).
  • Connections and credentials used by items. Document owners and where the secrets live.
  • Sensitivity labels. Labelled items either cannot be exported or are exported without the label, depending on the tenant switch.

3 · Freeze changes and check the size

  • Announce a short freeze: nobody edits the workspace during the connection and baseline commit.
  • Confirm the workspace is under 1,000 items and that no single commit will exceed 50 MB for GitHub. If it might, plan to commit in several batches.
  • Confirm the repository exists, main exists (initialize the repository with a README at the root), and the folder you will use does not exist yet.
  • Confirm the person connecting has the Admin role, a fine-grained token scoped to the repository, and a repository URL ready.

Do not pre-create the workspace folders in GitHub

Let Fabric create each folder on first sync. Pointing at an existing folder, even one that holds only a placeholder file, puts you in the "both sides have content" case and forces the direction prompt. Microsoft's documentation does not define precisely what counts as empty, so use a folder name that does not exist and avoid the question.

Establishing the connection

Run these steps as the workspace admin, once per workspace. The example connects DEV_SALES_BRZ to the SALES_BRZ folder of main.

  1. Open Git integration

    In the workspace, open Workspace settings and select Git integration. Choose GitHub as the provider. If GitHub is missing, the GitHub tenant switch is still off for you (see the tenant settings).

  2. Add your account

    Select Add account. Enter a display name that is unique to you, paste your fine-grained token, and enter the repository URL, for example https://github.com/contoso-org/fabric-analytics. The URL is optional for github.com and mandatory for a ghe.com enterprise domain. Select Connect. If you use a token scoped to one repository, the URL is filled in and locked.

  3. Choose branch and folder

    Select the branch (main for a DEV workspace) and type the new folder name SALES_BRZ. Leaving the folder blank would use the repository root. You can connect to only one branch and one folder.

  4. Connect and sync, and read the dialog

    Select Connect and sync. For an existing workspace and an empty folder, Fabric copies the workspace into Git without deleting anything. If instead you are asked to choose a direction, stop: the folder is not empty. Cancel, find out why, and do not select Update workspace with Git content.

  5. Verify the result

    The Git status of each item should read Synced, the Source control icon should show 0, and the status bar should show the connected branch, the time of the last sync and a link to the last commit. In GitHub, open the folder and check that every supported item appears as a subfolder.

  6. Commit anything left over

    Open Source control and, if the Changes tab lists any item, commit it to the connected branch with a clear message such as "Baseline: DEV_SALES_BRZ". From now on use Commit for workspace to Git, and Update only when the branch has incoming changes you intend to take.

  7. Repeat for each workspace

    Connect the remaining workspaces to their own folders of the same branch, one at a time, verifying after each.

Baseline first, guard rails second

Fabric commits directly to the connected branch with the user's token. A ruleset that requires pull requests on main will reject the baseline commit. Do the baseline commits, verify them, and only then switch the main ruleset on. If you must protect main earlier, connect each workspace to a temporary baseline branch, merge it by pull request, then switch the workspace to main; the switch requires that the directory exists on the target branch.

Connecting a layered estate

With one workspace per layer, connect them in dependency order (Bronze, Silver, Gold, then consumption and delivery) so a failed step does not leave downstream workspaces connected to nothing. After the last one, the repository should look like the layout in the previous page: one folder per workspace, plus the folders and files you added by hand that sit outside any workspace folder. Mark the state with a Git tag (for example baseline) so that "known good" is one command away.

The folder-change hazard

Workspace subfolders are part of the synchronized structure. If you create or reorganize folders in the workspace and the Git folder does not yet have them, the two are considered different. Update then lets the Git structure overwrite the workspace structure, which removes the new folders and, with them, the items inside.

If you cannot commit to the connected branch because a ruleset or permission blocks it, use Checkout new branch in the source control pane. It creates a branch from the last synced commit, keeps the current workspace state including uncommitted changes, and lets you commit the folder changes there. Merge that branch with a normal pull request, then update the shared workspace.

If a workspace was already overwritten

SituationFirst moveNotes
Items disappeared after an Update against an empty folderStop. Do not commit from the workspace.A commit now would push the emptied state into Git. Work from the backup workspace and from Git history instead.
A backup clone existsDeploy from the clone back to the live workspace, or reconnect from the clone's items.Hydrated data in the clone saves the most time. Re-point connections and schedules afterwards.
The items were committed to Git before the overwriteRestore the commit in Git (see the rollback appendix), then Update the workspace.Git recreates definitions only; it does not restore data.
Items are in the workspace recycle binRestore from the recycle bin.A restore keeps the original item ID and brings data back. A Git update re-creates an item with a new ID and definition only, and having both can leave duplicates; delete the re-created one.

Verify against Microsoft Learn

Item recovery behavior and retention differ by item type. Before you rely on the recycle bin as a recovery path, confirm what is recoverable for your item types, and read "Differences between Git Integration and recycle bin item recovery behavior" in Git integration process.

Key takeaways

  • Back up and hydrate a clone first, connect the content-bearing workspace to a folder that does not exist yet, and make sure the dialog never asks you to pick a direction.
  • Commit the baseline immediately, tag it, and only then enable the ruleset on main.
  • Commit workspace folder changes to a branch and merge them before any Update; use Checkout new branch when you cannot commit to the connected branch.
  • If something goes wrong, stop committing: a commit from an emptied workspace writes the damage into Git.
