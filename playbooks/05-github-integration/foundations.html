Playbook 05 · GitHub Integration

Prerequisites and authentication

Most failed first connections come down to one of four things: a tenant switch that is still off, a workspace role that is too low, a token with the wrong scope, or a GitHub plan that quietly lacks a feature you planned to rely on. This page is the checklist that prevents all four, and the reasoning behind the two-tier identity model used for the rest of the playbook.

  • Audience Fabric admins, workspace admins, GitHub org owners
  • Outcome a verified, least-privilege starting position

Core concepts in three sentences

Git integration keeps the definition of each supported item in a Git folder and gives developers branches, history and review. Deployment moves those definitions between environments, either with Fabric deployment pipelines or with code (the Fabric Git and Items REST APIs, or the fabric-cicd library). Automation is whatever triggers that movement, here GitHub Actions. The first is the subject of most of this playbook; the other two are covered in playbook 07 and on the service principals and Actions page.

Supported Git providers and GitHub variants

Fabric supports Azure DevOps and GitHub, and in both cases only the cloud-hosted products. The details matter when your organization runs GitHub in a non-default way.

Verify against Microsoft Learn

Provider support is one of the most frequently updated statements in the Git integration documentation. Before committing to an architecture that depends on a GitHub Enterprise variant, read the "GitHub Enterprise limitations" section of Git integration process, and run a proof of concept on the exact tenant and organization you will use.

Tenant settings checklist

These switches live in the Fabric admin experience under tenant settings. They are organization-wide unless you scope them to security groups, which is usually the right call for Git integration: start with a pilot group, then widen.

Setting (label in the portal)Why you need itNotes
Users can create Fabric itemsRequired whenever the workspace holds Fabric (non-Power BI) items such as notebooks, lakehouses and pipelines.Part of the Fabric enablement switch; Git integration for Fabric items only works if Fabric is enabled.
Users can synchronize workspace items with their Git repositoriesThe primary Git integration switch.Enabled by default. Disable it to stop users syncing at all.
Users can synchronize workspace items with GitHub repositoriesThe additional switch that allows GitHub specifically.Disabled by default. This is the one people miss. Some articles abbreviate the label to "sync".
Create workspacesNeeded for the branch-out workflow, because branching out creates a new workspace.Not needed if developers branch out into pre-provisioned workspaces.
Users can export workspace items with applied sensitivity labels to Git repositoriesSensitivity labels are not exported to Git. This switch decides whether labelled items may be committed at all.Allowing it means the committed definition carries no label. Decide this together with your information-protection owner.
Users can export items to Git repositories in other geographical locationsControls commits when the workspace capacity and the Azure DevOps repository are in different regions.GitHub does not support enforcement of this switch, so it gives you no control over where GitHub data resides.
Service principals can call Fabric public APIsRequired for any automation that authenticates as a service principal.Covered on the service principals page.

Two behaviors apply to every one of these switches. First, Apply to lets you target the entire organization, specific security groups, or everyone except specific groups, and the settings apply to the Fabric user who performs the Git operation, not to the account used to connect to the repository. Second, the tenant admin can delegate a switch so that capacity admins and then workspace admins can override it for their scope.

Verify against Microsoft Learn

Setting labels and the navigation path to tenant settings are renamed from time to time, and individual articles do not always use the same wording (for example "synchronize" versus "sync"). Match by meaning, and confirm against Git integration tenant settings and the prerequisites in Get started with Git integration.

Capacity and workspace prerequisites

  • The workspace is assigned to a Fabric capacity (a trial capacity works). Power BI Premium capacities can be used, but some Power BI SKUs only support Power BI items.
  • The workspace is a regular workspace. My workspace cannot connect to Git, and neither can a workspace with template apps installed.
  • There is capacity headroom for feature workspaces. Branching out creates a workspace and must have capacity available.
  • Workspace admins are named and are the only people who will connect and disconnect Git, unless you deliberately enable the contributor branch-switching setting (below).

Who needs what: workspace role and GitHub permission

Every Git operation is gated twice: by the person's role in the workspace, and by what the stored GitHub credential is allowed to do in the repository. The table combines both, using fine-grained token permissions for the GitHub column.

OperationWorkspace roleFine-grained token (Contents)
Connect, disconnect or change the connectionAdminRead (disconnect needs nothing)
Initial syncAdminRead to import; read and write to commit the workspace
View connection details and Git statusAdmin, Member, ContributorRead (details: read or none)
Update from GitContributor with write permission on all items; item owner if the tenant restricts updates to owners; Build permission on external dependenciesRead
Commit to GitSame as updateRead and write; the branch policy must allow the commit
Create a branch from Fabric (checkout, switch)Admin; Member or Contributor only if the workspace setting below is onRead and write to create a branch
Branch out to another workspaceAdmin, Member, ContributorRead and write

Viewers cannot do anything with Git and do not see Git information in the workspace. A workspace admin can switch on Allow users with at least Contributor role to change Git branch to let Members and Contributors who have write access to all items switch branches and create branches under their own identity. The setting is per workspace, requires an active Git connection, and does not extend connect or disconnect to anyone other than admins.

A commit needs more than "Contents: write"

If a ruleset on the connected branch requires pull requests, a commit from Fabric to that branch is rejected, because Fabric pushes directly with the user's token. That is exactly what you want for the DEV workspaces on main (they should only receive updates), and exactly what you do not want on a feature branch. Plan the rulesets with the workspace-to-branch mapping in mind; the hardening page shows how.

Verify against Microsoft Learn

Microsoft has announced that Git integration will require read-write permission on workspace items, with consequences for items that carry sensitivity labels and protection policies. Check the permissions note in Git integration process for the effective timing and plan any viewer-level contributors accordingly.

Authenticating the Git connection

When a developer connects a workspace to GitHub, Fabric stores a credential for that developer. The credential is a personal access token (PAT). The documented options are narrower than the GitHub ecosystem as a whole.

CredentialUse for Fabric Git connection?Notes
Fine-grained personal access tokenRecommendedScope it to the one repository and grant Contents: read and write. A token scoped to a single repository also pre-fills and locks the repository URL in Fabric.
Classic personal access tokenWorks, avoidNeeds the repo scope, which reaches every repository the user can access. In organizations that enforce SAML SSO the token must be authorized after creation, and an organization can disable classic tokens entirely.
GitHub App or OAuth appNot documentedMicrosoft documents only PATs for the GitHub credential. Do not plan around an app-based credential without a written confirmation.
Service principal or managed identityNot for the GitHub credentialService principal credentials for the Git connection exist for Azure DevOps. A service principal can call the Fabric Git APIs, but for GitHub it must use a configured connection that itself holds a PAT.

Create the fine-grained token

  1. Open the token settings

    In GitHub, go to Settings > Developer settings > Personal access tokens > Fine-grained tokens and choose to generate a new token.

  2. Choose the resource owner

    Select the organization that owns the repository, not your personal account. A token is bound to one resource owner. If the organization requires approval for fine-grained tokens, the token stays pending, and can only read public resources, until an organization owner approves it.

  3. Set an expiry you can operate

    Pick the shortest lifetime you will actually rotate, and put the rotation in a calendar. An expired token surfaces as a failed commit or update in Fabric, usually at the worst moment.

  4. Scope to the repository

    Under Repository access choose Only select repositories and pick the Fabric repository, for example contoso-org/fabric-analytics.

  5. Grant the one permission

    Under Repository permissions set Contents to Read and write. That is the minimum for commit and branch operations. Metadata: read is added automatically.

  6. Store it, then paste it into Fabric once

    Copy the token into your password manager; GitHub shows it only once. In the workspace, Workspace settings > Git integration > GitHub > Add account, give it a unique display name, paste the token, and optionally enter the repository URL.

Per-user means per-user

The Fabric Git connection belongs to the user who created it. Each developer who works in a connected workspace configures their own connection, and the documentation is explicit that for GitHub you should not share one token among users. Shared tokens also destroy the audit trail: every commit would appear to come from one person.

The two-tier identity model

Because the Git credential for GitHub is a user token, the cleanest design splits identities by purpose instead of trying to make one identity do both jobs.

Why the automation lane skips the Git sync APIs

The Fabric Git REST APIs do accept service principals, but the connect call accepts them only through a configured connection, and for GitHub that connection holds a PAT. Commit and update work for a service principal only when all items involved support service principals. Definition-based deployment (fabric-cicd or the Items APIs) has neither limitation, which is why the later pages use it for TST and PRD and reserve Git sync for DEV.

Constraints that surface late

  • MFA parity. The authentication method in Fabric must be at least as strong as the one required for Git. If GitHub requires multifactor authentication, Fabric must require it too, through Entra ID conditional access.
  • Guest users. B2B guests are not supported in Git integration scenarios.
  • Workspace identity. An item that uses a workspace identity and is committed to Git can only be updated back into a workspace that has the same identity. This also affects branch-out.
  • Network security. Workspace-level inbound and outbound protections interact with CI/CD tools. Read Microsoft's network security guidance for CI/CD before you lock a workspace down.

Key takeaways

  • Enable both Git switches, and remember the GitHub one is off by default; scope them to a pilot security group first.
  • Give each developer their own fine-grained token, scoped to one repository with Contents read and write, and never share it.
  • Keep people and automation on separate identities: user tokens for Git sync in DEV, a service principal with OIDC for deployment.
  • Confirm the GitHub variant and plan before you design; Enterprise Server, IP allow lists and some private-repository controls change the answer.
