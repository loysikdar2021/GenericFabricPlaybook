Playbook 05 · GitHub Integration

GitHub Integration and Branching

A Fabric workspace is a shared runtime, and nothing in it is versioned until you connect it to Git. This playbook shows how to connect workspaces to GitHub without losing work, branch the way GitHub Flow intends, lock the repository down with rulesets, and give automation its own identity instead of borrowing a developer's.

  • Audience platform leads, DevOps and data engineers, workspace admins
  • Level Intermediate
  • Reading time 110 min

What this playbook solves

Fabric Git integration works at workspace level: you connect a workspace to one branch and one folder of a repository, and Fabric keeps item definitions (notebooks as .py, semantic models as TMDL, pipelines as JSON, and so on) in sync with that folder. That gives you history, review and rollback for analytics assets. It does not, on its own, give you a safe way of working. Teams that stop at "we connected the workspace" typically hit the same problems within a few weeks:

  • Silent data loss. The first sync after connecting, or an Update against an empty folder, overwrites the workspace with whatever Git holds. A Git branch can always be restored; a workspace cannot.
  • Everyone edits the same workspace. The workspace is a shared runtime environment. Without feature workspaces, one developer's save is every developer's change.
  • Review without teeth. Pull requests that nobody is required to approve, or that can be bypassed by anyone with write access, are a convention and not a control.
  • Borrowed identities. A deployment that runs as a developer's token breaks when they leave, and has far more reach than the deployment needs.

The playbook is deliberately opinionated about the default path: GitHub Flow, one repository per data product, one workspace per folder, fine-grained tokens for people, and a service principal with OIDC for automation. It also tells you where the platform's own documentation says otherwise, so you can choose a different path knowingly.

The model in one picture

Operating principles

Every later page is an application of one of these.

  1. Git is recoverable; a workspace is not.

    Whenever a direction has to be chosen, choose the one that overwrites the workspace only after the workspace content is safely in Git or in a backup workspace.

  2. One workspace, one branch, one folder.

    A workspace connects to a single branch and a single folder. Keep that mapping boring and documented.

  3. main is the only branch that feeds shared workspaces.

    Developers never commit to main from a shared workspace. Changes arrive by pull request and enter the DEV workspaces through Update.

  4. People and automation use different identities.

    Developers use their own fine-grained token for the Git connection. Pipelines use a service principal, authenticated by OIDC where possible, with secrets scoped to environments.

  5. Enforce with rulesets, not with etiquette.

    Required reviews, code-owner approval and status checks belong in a ruleset that applies to main, with a short, audited bypass list.

  6. Treat the supported-item list as a moving target.

    Check it before you design, and again before every release plan that depends on an item type.

When to use it, and when not to

A good fit when

  • More than one person edits Fabric items and you need review and history.
  • You promote content through DEV, TST and PRD and want the definition of "what is deployed" to be a commit.
  • Your organization already runs GitHub (including GitHub Enterprise Cloud) for code.
  • You want a single place to review notebooks, pipelines, models and reports as text.

Think twice when

  • Your GitHub is self-hosted (GitHub Enterprise Server) or sits behind an IP allow list; Fabric Git integration supports cloud GitHub only.
  • You are in a sovereign cloud; Git integration is not supported there.
  • Your estate is mostly items that are not yet supported, so most of the workspace would stay outside Git.
  • You already standardized on Azure DevOps. The Fabric side is nearly identical, but the credential model differs (see the foundations page).

Prerequisites at a glance

  • A Fabric capacity and workspaces assigned to it, with a named workspace admin per workspace.
  • A Fabric admin who can enable the Git integration tenant settings (the GitHub-specific one is off by default).
  • A GitHub organization and repository (or a plan to create them), with a GitHub plan that supports rulesets and environments on private repositories.
  • A decision on who creates workspaces and repositories. If only a central admin team can, the branch-out workflow needs a process (see the branching page).
  • A Microsoft Entra service principal for automation, and a Fabric admin willing to allow it.

The foundations page turns this list into exact settings, permissions and token scopes.

Key takeaways

  • Connect the workspace that has content to an empty folder, commit a baseline at once, and never press Update against an empty branch or folder.
  • Feed shared workspaces only from main; do all development in branched workspaces that are deleted after the merge.
  • Use a ruleset for main, a service principal with OIDC for automation, and environment-scoped secrets for anything that cannot be secret-less.
  • Confirm tenant setting names, token types and the supported-item list on Microsoft Learn before you rely on them.
