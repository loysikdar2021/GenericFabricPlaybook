Repository and workspace layout

The folder structure in your repository is not a documentation choice. Fabric mirrors it, in both directions, so it decides what a commit touches, what a pull request reviewer sees, what an Update can delete and which dependencies survive a deployment. Decide it before you connect the first workspace.

  • Audience architects, platform leads, workspace admins
  • Decisions repository count, folder mapping, naming

The mapping rules

A workspace connects to one branch and one folder. Inside that folder, every Git-supported item is a subfolder, and workspace subfolders become Git subfolders. The relationship is symmetrical: items you save in a workspace folder appear in the matching Git folder on commit, and items added to the Git folder appear in the workspace on update.

For a medallion layout with one workspace per layer (see playbook 03), the natural mapping is one repository per data product and one folder per workspace, with every DEV workspace connected to main:

RuleConsequence
A workspace connects to one branch and one folder.You cannot split a workspace across folders or branches. If two teams need independent release cadence, they need separate workspaces.
Several workspaces can connect to the same branch, each to its own folder.A commit from one workspace advances the branch, but other workspaces only see an update if their own folder changed.
A folder left blank in the connection dialog means the repository root.Fine for a single-workspace repository; a trap in a shared one, because the root also holds .github/.
Unsupported items in the workspace are ignored, not deleted.They appear in the source control pane but cannot be committed or updated, and they never travel with the folder.

How an item is stored

Each item becomes a directory named {display name}.{public facing type}, containing the item's definition files and a .platform file that Fabric generates. Knowing this layout is what lets reviewers read a pull request and lets you write sensible CODEOWNERS rules (see playbook 17).

SALES_GLD/
├── LH_SALES_GLD.Lakehouse/
│   ├── .platform
│   ├── lakehouse.metadata.json
│   └── shortcuts.metadata.json
├── NB_SALES_GLD_BuildCustomerDim.Notebook/
│   ├── .platform
│   └── notebook-content.py
├── PL_SALES_GLD_Refresh.DataPipeline/
│   ├── .platform
│   └── pipeline-content.json
└── VL_SALES_GLD.VariableLibrary/
    ├── .platform
    └── variables.json

The format varies by item type: a notebook is a .py file; a semantic model is a definition.pbism plus a definition/ folder of TMDL files; a report is a definition.pbir plus its report definition; a paginated report is an .rdl file; a mirrored database is a .json definition. The file names inside an item folder are generated by Fabric and can change between format versions, so treat the listing above as an illustration.

The .platform file and logical IDs

{
  "version": "2.0",
  "$schema": "https://developer.microsoft.com/json-schemas/fabric/platform/platformProperties.json",
  "config": {
    "logicalId": "00000000-0000-0000-0000-000000000000"
  },
  "metadata": {
    "type": "Notebook",
    "displayName": "NB_SALES_GLD_BuildCustomerDim",
    "description": "Builds the conformed customer dimension"
  }
}

The logicalId is what links an item in a workspace to its folder in Git. Items with the same logical ID are assumed to be the same item, even if the name or folder changed. A branch can be synced to several workspaces, so the same logical ID can exist in different workspaces, but never twice in one workspace. Three practical rules follow:

  • Never edit a logical ID or the type field (it is case sensitive).
  • When you copy an item folder to create a new item, change both the logical ID and the display name to something unique in the repository, or Fabric will treat the copy as the original.
  • Rename in Fabric, not in Git. Renaming an item in the workspace renames its folder on the next commit. Renaming the folder in Git does not rename the item, and it does not trigger an incoming change, so the two drift apart and dependent files (for example a report's path to its semantic model) can break.

Items whose display name is over 256 characters, ends with a dot or space, or contains forbidden characters get a Git folder named after the logical ID and type instead. Keep item names short and plain and you never see this.

One repository or many?

The repository is the unit of access control, of pull request scope and of CODEOWNERS. Choose it by asking what must change together and who must approve it, not by how many workspaces you have.

OptionBest whenStrengthsRisks
One repo per data product, one folder per workspace (default)One team (or tightly coupled teams) owns a domain end to end.Atomic cross-layer changes; one set of rulesets and CODEOWNERS; one place to search.Repository permissions apply to all folders; use CODEOWNERS to differentiate reviewers.
One repo per workspaceWorkspaces have different owners, security boundaries or release cadence.Strong isolation; simple permissions; small blast radius.Cross-workspace changes need multiple coordinated pull requests; configuration drift between repositories.
One repo for the whole organizationA small organization with a single platform team.Simplest governance and search.Noisy history, slow CI, and one permission boundary for unrelated products.
A separate repo for shared code (libraries, deployment tooling)Python packages or scripts used by several data products.Versioned, independently released; fits playbook 06.Consumers must pin versions deliberately.

Recommended repository layout

fabric-analytics/
├── .github/
│   ├── CODEOWNERS
│   ├── pull_request_template.md
│   └── workflows/
│       ├── pr-validation.yml
│       └── deploy.yml
├── SALES_BRZ/              # connected to DEV_SALES_BRZ
├── SALES_SLV/              # connected to DEV_SALES_SLV
├── SALES_GLD/              # connected to DEV_SALES_GLD
├── SALES_CNSM_WH/          # connected to DEV_SALES_CNSM_WH
├── SALES_CNSM_SM/          # connected to DEV_SALES_CNSM_SM
├── SALES_DLV/              # connected to DEV_SALES_DLV
├── _deploy/                # parameter files, deployment scripts
├── _tests/                 # unit and data-quality tests, run in CI only
├── _admin/                 # runbooks, decisions, repository conventions
└── README.md
  • Folder names follow the workspace convention minus the environment. SALES_GLD serves DEV_SALES_GLD, TST_SALES_GLD and PRD_SALES_GLD.
  • Non-workspace folders start with an underscore. They sort together and are visibly not connected to anything.
  • Keep custom files out of item folders. When Fabric commits an item it deletes files inside that item's folder that are not part of the definition. Files outside item folders are left alone.
  • Workflows and CODEOWNERS live under .github/ in the repository root, outside every workspace folder, so Git sync never touches them.

Folders inside a workspace

Workspace subfolders are mirrored into Git, up to 10 levels deep. Empty folders are not copied to Git, and empty folders in Git are removed automatically. Two operational rules matter more than the depth limit:

  • Use shallow, functional subfolders (for example ingest/, transform/, orchestration/) and keep them stable. Moving items between folders changes paths, produces noisy diffs and breaks any CODEOWNERS pattern that referenced the old path.
  • Treat a folder change as a commit-first operation. If the workspace has folders that the Git folder lacks, they are considered different, and an Update before the commit lets the Git structure overwrite the workspace structure. The connecting page shows the safe sequence.

Dependencies across workspaces

A layered design puts related items in different workspaces, and that is where Git integration is least forgiving. Fabric resolves dependencies through logical IDs, but only for references to items in the same workspace. A reference to an item in another workspace is stored as an object ID, and after a deployment it still points at the source workspace.

This has direct consequences for the medallion layout, and it is the main reason environment-aware items matter (see playbook 09):

ReferenceBinds through Git?What to do
Notebook to a lakehouse in the same workspaceYes, if "Lakehouse Auto-Binding in Git" is enabled in the notebook settings (off by default)Enable it per notebook, or parameterize the default lakehouse.
Notebook to an environmentYesNothing to do.
Pipeline to a notebook, pipeline, dataflow or lakehouseYesNothing to do within a workspace.
Pipeline to a Spark job definition, semantic model or warehouseNo (object ID or endpoint)Parameterize the activity values.
Report to its semantic modelPartial (relative path)Keep the report and model in the same relative location.
Semantic model to a SQL endpoint, warehouse or KQL databaseNo (workspace-specific URL)Parameterize the connection expression.
Anything in another workspace, and any connectionNoUse a variable library with a value set per environment.

Verify against Microsoft Learn

Binding behavior is item-type specific and changes as item types mature. Check Understand dependency binding in cross-workspace deployment for every item type you actually use before you finalize the workspace split.

Limits that shape the layout

  • A workspace holds at most 1,000 items. If a Git branch holds more than that for the connected folder, syncing to the workspace fails; split by workspace or by folder.
  • Folder structure is kept to 10 levels, the full path of a file may not exceed 250 characters, and a branch name may not exceed 244 characters.
  • The directory you connect to cannot begin or end with a space or tab and cannot contain " / : < > \ * ? |.
  • Item folders cannot contain : < > \ * ? |. A folder renamed to include one of them breaks the sync.
  • Display names must be unique per item type within a workspace, even where Power BI would allow duplicates.

The size limits that apply to commits and files are on the sync page.

Key takeaways

  • One workspace, one branch, one folder; name the folder like the workspace without the environment prefix.
  • Default to one repository per data product so cross-layer changes are a single reviewed unit.
  • Keep custom files, workflows and CODEOWNERS outside item folders, and rename items in Fabric rather than in Git.
  • Expect references that cross a workspace boundary to stay pinned to the source; parameterize them from day one.
