Access model and repository hardening

The workflow on the previous page is only as safe as the controls behind it. This page covers who gets which role, how identity flows from Entra ID, and how to make main impossible to change except through a reviewed pull request.

  • Audience repository admins, platform and security owners
  • Use it for role design, SSO, rulesets, hardening, scanning

Least privilege, in two tiers

A Fabric developer needs two independent sets of permissions: a GitHub role that decides what they can do in the repository, and a Fabric workspace role that decides what they can do in the workspace. Neither implies the other (see the two-tier identity model). Design both from the same functional roles, and give each person the smallest role that lets them do their job:

  • Developers and analysts write item changes on feature branches and open pull requests.
  • Leads and architects review and approve, and own the merge decision.
  • Platform and DevOps owners configure the repository, rulesets, environments and pipelines. This is a small group.
  • Auditors, project managers and business analysts need to see the code and the history, not change it.

Teams and repository roles

TeamRoleWho and why
fabric-adminsAdminPlatform owners and DevOps leads: repository settings, rulesets, environments and secrets, team access. Keep this to a few people and review it regularly.
fabric-maintainersMaintainTech leads who manage merge settings and day-to-day repository hygiene without access to security settings, secrets or the rulesets.
fabric-developersWriteData engineers and analysts: push to feature branches, open pull requests, review and merge once the rules allow it.
fabric-auditorsReadCompliance, project management and business stakeholders: view code, history and pull requests only.

The roles in the table behave as follows. Note two points that are commonly misunderstood:

ActionReadWriteMaintainAdmin
View code, history, pull requests and rulesetsYesYesYesYes
Push to branches that no rule protectsNoYesYesYes
Submit a review that counts toward required approvalsNoYesYesYes
Merge a pull request that satisfies every ruleNoYesYesYes
Configure merge methods and other merge settingsNoNoYesYes
Create or edit rulesets, secrets, variables and environmentsNoNoNoYes
  • Write can merge. What stops a developer merging their own change into main is not the role, it is the ruleset: required approvals, required checks and, where used, code owner review. Without a ruleset, Write is enough to merge anything.
  • Reviewers need Write, not Maintain. Only reviews from people with at least Write count toward required approvals, so Maintain is a convenience for settings, not a prerequisite for reviewing.
  • Bypass is not a role. Rulesets are bypassed only by the actors named in each ruleset's bypass list, so keeping that list short and explicit matters more than the role names.

Identity: Entra ID, single sign-on and team sync

Individual role assignments do not scale and leave stale access behind. Drive membership from Microsoft Entra ID instead:

CapabilityWhat you get
Single sign-onPeople sign in to GitHub with their corporate identity and the policies attached to it, such as MFA and conditional access.
SCIM provisioningJoiners are provisioned and leavers are deprovisioned automatically, which closes the most common gap: a departed developer's access lingering.
Team syncA GitHub team follows the membership of an Entra group. Once connected, membership is managed only in the identity provider.
AuditingAccess questions are answered from one place, and membership changes made through the provider are recorded in the GitHub audit log.

Verify against GitHub documentation

Single sign-on, SCIM and team sync depend on the GitHub plan and on the account model (organization with SAML, or Enterprise Managed Users). Team sync has limits, for example on the number of groups per team, and a team that is a parent of other teams cannot be synced. Confirm the current requirements in Synchronizing a team with an identity provider group before you design the team layout.

Single sign-on and tokens

When the organization enforces SAML single sign-on, a personal access token must be authorized for that organization before it can reach its repositories. A token that works for a personal repository and fails for the organization is almost always this. Tokens also belong to the person who created them: when that person leaves, the Fabric connection that uses the token stops working, which is one more reason automation uses a service principal. See the automation page.

Review access on a schedule

  • Review membership of the admin and maintainer groups, and the bypass lists of every ruleset, at least quarterly. Use Entra access reviews for the groups.
  • List outside collaborators and installed GitHub Apps and remove those without an owner.
  • Review active personal access tokens and approved token requests for the organization.
  • Check that nobody holds access through an individual assignment that a team already covers.

Rulesets: protecting main

A ruleset is a named set of rules that applies to a set of branches or tags. It is the current replacement for classic branch protection rules, and it should be your only mechanism for protecting main.

Why rulesets

  • Layering. Several rulesets can apply to the same branch at once. GitHub aggregates them and, where they overlap, the most restrictive rule applies. Classic protection allowed only one rule per pattern.
  • Visibility. Anyone with read access can view the active rulesets, so a developer can see why an action is blocked without asking an admin.
  • Manageability. Rulesets have an enforcement status (active, disabled and, on plans that offer it, evaluate) so you can trial them, and they have an explicit bypass list.
  • Reach. Rulesets can be defined at organization level and applied to many repositories, subject to plan.

Creating the ruleset for main

  1. Open the rules.

    In the repository, go to Settings, then Rules, then Rulesets, and choose New ruleset followed by New branch ruleset.

  2. Name it and choose the enforcement status.

    Name it for what it protects, such as protect-main. Start as Active if the baseline is already committed (see the callout below); use Evaluate first on plans that offer it if you want to see what would be blocked.

  3. Keep the bypass list nearly empty.

    Add only an explicitly named admin team or a deployment app that genuinely must write to main, and record why. Anyone on the list can ignore every rule.

  4. Target the default branch.

    Use the default-branch target rather than a pattern. Do not target all branches: feature branches must stay open, because Fabric commits straight to them.

  5. Select the rules in the table below, then Create.
  6. Test it.

    As a normal developer, try a direct push to main (it must fail), then merge a pull request that has an approval (it must succeed).

RuleSettingWhy, and the Fabric angle
Restrict deletionsOnThe branch that feeds every environment cannot be removed.
Block force pushesOnHistory stays immutable and auditable. Recover with a revert, not a rewrite (see the rollback page).
Require a pull request before mergingOnThis rule, not Restrict updates, is what stops direct pushes while still allowing merges.

  Dismiss stale approvals on new commitsOnAn approval applies to the code that was reviewed, not to whatever is pushed later.
  Require approval of the most recent pushOnThe last person to push cannot be the only approver.

Restrict updates also blocks the merge button

Older guidance enables both Restrict updates and Require a pull request. Restrict updates allows only bypass actors to update the branch, and a merged pull request is an update, so reviewers who are not on the bypass list may find the merge rejected. Require a pull request already prevents direct pushes. Enable Restrict updates only when you deliberately route every merge through a named bypass actor, and test it before you roll it out.

Commit the baseline before you enable the ruleset

Fabric's first commit goes straight to the connected branch with the connecting user's token, so a ruleset on main that already requires pull requests blocks it. Commit the baseline to main first, then turn the ruleset on. If the ruleset must exist from day one, connect the workspace to a temporary baseline branch, commit there, merge it through a pull request, and then use Switch branch to attach the workspace to main. Details are in the first-sync rules.

Hardening the repository

The ruleset protects one branch. The rest of the repository and its surroundings need protecting too, and each control assumes the others may fail.

Organization controls

  • Require two-factor authentication or single sign-on for every member, and remove members and outside collaborators who no longer need access.
  • Set the base repository permission to No permission, so access comes only from team grants.
  • Set a personal access token policy: allow fine-grained tokens, restrict or disable classic tokens, and require approval of tokens that reach organization resources. See the authentication section.
  • Allow only approved GitHub Actions and reusable workflows, and set the default workflow token to read-only.
  • Restrict who can create repositories and teams, so the repository and team layout stays deliberate.

Repository controls

  • Keep one default branch (main), enable Automatically delete head branches so merged branches do not accumulate, and disable forking for private repositories.
  • Add a CODEOWNERS file that assigns each item folder, and the .github/ folder that holds workflows, to the right team. Workflow files are code that runs with your credentials, so they deserve the strictest review.
  • Add a .gitignore that keeps local tooling output and credentials out of the repository, and a short SECURITY.md that says where to report a leaked secret.
  • Give workflows the least privilege: declare permissions explicitly, grant only what each job needs, and pin third-party actions to a full commit SHA.
  • Never store connection strings, keys or tokens in notebooks, pipelines or parameter files. Use Key Vault references and variable libraries.

Optional automated scanning

Automated scanning catches mistakes that reviewers miss, and a ruleset can make the result a merge requirement.

ControlWhat it catchesFabric relevance
Secret scanning and push protectionTokens, keys and connection strings committed to the repository; push protection stops them before they land.The most likely leak is a credential pasted into a notebook cell or a parameter file. Fabric commits are pushes, so push protection applies to them too.
Code scanning (for example CodeQL)Vulnerability patterns in source code.Notebook and script items are stored as text source, so code in supported languages can be scanned like any other code.
Dependency alertsKnown-vulnerable libraries in manifests.Applies to repositories that hold requirement files for environments or custom libraries.
Custom validation workflowThings only you know to check: hard-coded GUIDs, malformed JSON, missing .platform files, forbidden item types.Cheap to write and the best fit for Fabric-specific rules. Make it a required status check.

Verify against GitHub documentation

Which scanning features are available for private repositories, and how they are licensed, changes over time. Several ruleset rules that gate on scanning results are marked as preview in GitHub's documentation. Check Available rules for rulesets and your plan before relying on them.

Key takeaways

  • Grant roles to teams, drive team membership from Entra ID, and give each person the smallest GitHub and Fabric role that works.
  • Write can merge. The ruleset, not the role, is what makes review mandatory.
  • Protect main with a ruleset: pull request required, approvals, stale approvals dismissed, conversations resolved, code owners, no force pushes, no deletion.
  • Do not enable Restrict updates by reflex, do not target feature branches, and commit the baseline before enabling the ruleset.
  • Harden around the branch: token policy, approved actions, code owners on workflows, no secrets in items, and scanning with push protection.
