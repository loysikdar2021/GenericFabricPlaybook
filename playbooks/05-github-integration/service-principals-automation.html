Playbook 05 · GitHub Integration

Service principals and Actions

Developers use their own identity in the Fabric UI. Everything that runs without a person, such as validation, deployment to TST and PRD and scheduled housekeeping, needs an identity of its own. This page shows how to give automation exactly the access it needs and no stored password at all.

  • Audience platform and DevOps engineers, security reviewers
  • Use it for service principals, OIDC, secrets, environments, workflows

Who authenticates to what

A pipeline run touches three separate trust relationships. Keeping them separate is what keeps the blast radius small.

Step in the runCredentialLifetime and scope
Check out the repository, post a statusGITHUB_TOKEN, issued automatically for each runExpires when the job ends. Scope is whatever the workflow's permissions block grants.
Sign in to Microsoft Entra IDA GitHub OIDC token, presented by azure/loginMinutes. Valid only for the repository, environment or branch named in its subject claim.
Call the Fabric REST APIsAn Entra access token for the service principalAbout an hour. Powerless unless the service principal has a workspace role.
Drive the Fabric Git APIs (optional)The service principal, plus a Fabric connection that holds a GitHub tokenThe GitHub token is long-lived and tied to a person. This is the weak link, so avoid the Git APIs in the pipeline where you can.

Creating and authorising the service principal

Create one service principal per environment, for example sp-fabric-deploy-tst and sp-fabric-deploy-prd. A credential that can only reach TST cannot damage PRD, and each identity shows up separately in audit logs.

  1. Register the application.

    In Microsoft Entra ID, register a single-tenant application. Record the Application (client) ID and the Directory (tenant) ID. These are identifiers, not secrets.

  2. Do not create a client secret.

    Add a federated credential instead (next section). If an exceptional case forces a secret, see the fallback in the secrets section.

  3. Put the service principals in a security group.

    For example grp-fabric-automation. Tenant settings can then be scoped to that group rather than opened to the whole organization.

  4. Enable the tenant setting.

    A Fabric administrator turns on the Developer setting that lets service principals call Fabric public APIs, restricted to the security group. Without it every call returns an authorization error, whatever roles the principal holds.

  5. Grant a workspace role.

    Add each service principal to the target workspaces and give it the lowest role that works: Contributor for publishing items, higher only if a specific call demands it. Connecting a workspace to Git requires Admin, which is one more reason deployment pipelines should not do it.

  6. Grant access to dependencies.

    Items deployed to a workspace often reference connections, gateways or Key Vault secrets. The service principal needs permission on each connection it must bind, and the items it creates will be owned by it, so decide who owns refresh and data source credentials.

  7. Verify with a read-only call.

    Sign in as the service principal and list the workspace. Only then wire it into a workflow.

Verify against Microsoft Learn

The setting is named Service principals can call Fabric public APIs in the admin portal's Developer settings, and some older articles use a different wording. Support also varies by API and by item type: each API reference page states whether service principals are supported, and a supported API still fails when it touches an item type that does not support them. Check Identity support and the reference page of every call before you commit to a design.

OIDC federation instead of a stored secret

With OpenID Connect, GitHub issues each job a signed token that states exactly where the job came from. Entra ID trusts that token if its claims match a federated credential configured on the application. Nothing needs to be stored in GitHub, so there is nothing to leak, rotate or expire.

Client secretOIDC federated credential
Stored in GitHubYes, as a secretOnly the client and tenant IDs, which are identifiers
LifetimeMonths, until it expires or is rotatedMinutes, per job
Can be reused elsewhereYes, by anyone who obtains itNo. It only works from a matching job.
Operational burdenRotation, expiry alerts, secret sprawlA one-time credential per environment

Configuring the federated credential

On the application registration, add a federated credential for GitHub Actions deploying Azure resources. The values that matter are the issuer, the audience and the subject:

FieldValue
Issuerhttps://token.actions.githubusercontent.com
Audienceapi://AzureADTokenExchange
Subject, job that targets an environmentrepo:<org>/<repo>:environment:<environment>
Subject, job on a branchrepo:<org>/<repo>:ref:refs/heads/main
Subject, pull request jobrepo:<org>/<repo>:pull_request

The subject must match exactly. Bind each service principal to the environment subject: it is the strongest claim, because the environment's required reviewers and branch restrictions are enforced before GitHub issues a token that carries it.

GitHub secrets: scope matters

GitHub stores encrypted secrets at three scopes. Choosing the wrong one is the most common way production credentials end up readable by people who should never see them.

ScopeReadable byUse forFor Fabric
RepositoryEvery workflow in the repository, on any branchLow-sensitivity values needed everywhereNot for deployment credentials. A workflow pushed to a feature branch could read them.
EnvironmentOnly jobs that target that environment, and only after its protection rules passAnything that differs by environmentThe default home for client and tenant IDs and, in a fallback, any secret.
OrganizationThe repositories you selectValues genuinely shared across repositoriesAvoid, unless many repositories deliberately share one identity.

Use variables, not secrets, for non-sensitive configuration such as workspace IDs, so they stay visible in logs and reviews. Define them on the environment too: WS_SALES_GLD in tst and in prd hold different IDs, and the workflow file stays identical.

NameKindWhereHolds
AZURE_CLIENT_IDSecret (or variable)Each environmentClient ID of that environment's service principal
AZURE_TENANT_IDSecret (or variable)Each environmentThe Entra tenant ID
WS_SALES_GLD and the other workspace variablesVariableEach environmentWorkspace ID of that environment's workspace

If you must use a client secret

Create it for the environment service principal only, store it as an environment secret, give it the shortest practical expiry, assign a named owner and a calendar reminder for rotation, and turn on secret scanning with push protection so a copy cannot be committed by accident. Treat this as a temporary exception with an end date, not a design.

Environments with required reviewers

A GitHub environment is a named deployment target with its own secrets, variables and protection rules. A job that declares environment: prd pauses until the rules are satisfied, and only then receives the environment's secrets and an OIDC token carrying that environment in its subject.

Setting up an environment

  1. Create it.

    Repository Settings, then Environments, then New environment. Create tst and prd. Names are not case sensitive and must be unique in the repository.

  2. Required reviewers.

    Add the people or teams who approve deployments to that environment, up to six; one approval is enough to proceed. These reviewers approve deployments, not pull requests: pull-request review is governed by the ruleset.

  3. Prevent self-review.

    Select it so the person who triggered the run cannot approve their own deployment.

  4. Restrict deployment branches.

    Choose Selected branches and tags and allow only main for tst and prd. Without this, a workflow on any branch can target the environment.

  5. Decide on administrator bypass.

    For prd, deselect Allow administrators to bypass configured protection rules unless you have a documented break-glass process, and record who may use it.

  6. Add the environment's secrets and variables.

    Client and tenant IDs and the workspace IDs for that environment. Secrets and variables are released to the job only after the protection rules pass.

Anyone who can edit workflows can create environments

A workflow that names an environment that does not exist creates it, with no reviewers, no branch restrictions and no secrets. A typo in a workflow can therefore produce an unprotected environment that looks like the real one. Pre-create every environment you use, and require code owner review on .github/workflows/ (see the CODEOWNERS playbook) so changing a deployment workflow needs the platform team's approval.

Verify against GitHub documentation

On GitHub Free, Pro and Team plans, required reviewers and wait timers are available only for public repositories, and for private repositories they need GitHub Enterprise. If your plan lacks them, rely on the ruleset, the branch restriction and OIDC subjects, and add a manual approval step elsewhere. Confirm in Managing environments for deployment.

Choosing how the pipeline deploys

Fabric can reach TST and PRD by several routes. The service principal and OIDC pattern above is the same for all of them; the difference is what the job does once it is signed in.

MechanismWhat it doesFits whenWatch for
Deployment pipelines (Fabric)Promote content between stages inside Fabric, with deployment rules per stage.You want Fabric-native promotion and stage-level rules.Deployment rules and supported items differ from Git. See the deployment playbook.
fabric-cicdOpen-source Python library that publishes item definitions from a repository folder into a workspace, with find-and-replace parameterisation per environment.The repository is the source of truth and you want code-first, repeatable releases to TST and PRD.Orphan cleanup deletes items missing from the repository. Item-type coverage and options change between releases.
Fabric REST item APIs or the Fabric CLICreate and update items from their definitions, one call at a time.You need an operation the library does not cover, or want full control.You own the ordering, dependency handling and retries.
Fabric Git APIsConnect a workspace, initialize it and run update from Git.Downstream workspaces are deliberately connected to Git.For GitHub, the service principal still needs a connection that holds a GitHub token. See below.

Verify against the tools' own documentation

fabric-cicd and the Fabric CLI evolve quickly: supported item types, parameter-file features and authentication options all change. Read the current fabric-cicd documentation and the Fabric CLI documentation, and pin the version you tested. The CLI signs in non-interactively as a service principal, including with a federated token passed through environment variables.

Workflows

Two workflows are enough to start. Both live in .github/workflows/, which is outside every connected workspace folder, so Git sync never touches them.

Validation on pull requests

This workflow needs no Fabric access at all: it reads the repository and reports a status. Name the job validate and add it as a required status check in the ruleset.

name: pr-validation
on:
  pull_request:
    branches: [main]

permissions:
  contents: read

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Every item folder has a valid .platform file
        run: |
          status=0
          for d in $(find . -type d -regextype posix-extended \
              -regex '.*\.(Notebook|DataPipeline|Lakehouse|Warehouse|SemanticModel|Report|Environment)'); do
            if [ ! -f "$d/.platform" ]; then
              echo "Missing .platform in $d"; status=1
            elif ! python3 -m json.tool "$d/.platform" > /dev/null; then
              echo "Invalid JSON in $d/.platform"; status=1
            fi
          done
          exit $status

Grow it with the checks only you know to write: forbidden item types, hard-coded workspace names, a unit-test run for the notebook helper code in _tests/.

Deployment after merge

The deployment workflow runs on every push to main. It deploys to TST automatically, then waits at the prd environment's gate. The folders are listed in dependency order and run one at a time, so a layer never deploys before the layer it reads from.

name: deploy
on:
  push:
    branches: [main]

permissions:
  contents: read

concurrency:
  group: fabric-deploy
  cancel-in-progress: false

jobs:
  deploy-tst:
    runs-on: ubuntu-latest
    environment: tst
    permissions:
      id-token: write
      contents: read
    strategy:
      max-parallel: 1
      matrix:
        folder: [SALES_BRZ, SALES_SLV, SALES_GLD]
    steps:
      - uses: actions/checkout@v4
      - uses: azure/login@v3
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          allow-no-subscriptions: true
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install fabric-cicd
      - run: python _deploy/deploy.py --folder "$FOLDER" --workspace-id "$WORKSPACE_ID" --environment TST
        env:
          FOLDER: ${{ matrix.folder }}
          WORKSPACE_ID: ${{ vars[format('WS_{0}', matrix.folder)] }}

  deploy-prd:
    needs: deploy-tst
    runs-on: ubuntu-latest
    environment: prd          # pauses here until a required reviewer approves
    permissions:
      id-token: write
      contents: read
    strategy:
      max-parallel: 1
      matrix:
        folder: [SALES_BRZ, SALES_SLV, SALES_GLD]
    steps:
      # identical to deploy-tst, but with --environment PRD
      - uses: actions/checkout@v4
      - uses: azure/login@v3
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          allow-no-subscriptions: true
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install fabric-cicd
      - run: python _deploy/deploy.py --folder "$FOLDER" --workspace-id "$WORKSPACE_ID" --environment PRD
        env:
          FOLDER: ${{ matrix.folder }}
          WORKSPACE_ID: ${{ vars[format('WS_{0}', matrix.folder)] }}
  • id-token: write only on the deploy jobs. Every other job gets read-only access. Without this permission azure/login cannot request the OIDC token.
  • allow-no-subscriptions: true because the service principal has Fabric roles but no Azure subscription. Without it the login step fails looking for a subscription.
  • Secrets only appear as inputs and environment variables. Never build a shell command by pasting ${{ }} expressions that contain untrusted text such as branch names or pull-request titles; pass them through env as shown.
  • Pin actions to a full commit SHA. The version tags above keep the example readable; in your repository replace them with the SHA of the release you reviewed.
  • concurrency stops two merges from deploying over each other.

The deployment script

The script signs in through the Azure CLI session that azure/login created, then publishes one workspace folder. It lives in _deploy/, outside every workspace folder.

import argparse
from azure.identity import AzureCliCredential
from fabric_cicd import FabricWorkspace, publish_all_items, unpublish_all_orphan_items

parser = argparse.ArgumentParser()
parser.add_argument("--folder", required=True)
parser.add_argument("--workspace-id", required=True)
parser.add_argument("--environment", required=True)
args = parser.parse_args()

workspace = FabricWorkspace(
    workspace_id=args.workspace_id,
    environment=args.environment,
    repository_directory=args.folder,
    item_type_in_scope=["Notebook", "DataPipeline", "Environment"],
    token_credential=AzureCliCredential(),
)

publish_all_items(workspace)
unpublish_all_orphan_items(workspace)

Environment-specific values are swapped at publish time by a parameter file in the folder, so the item definitions in Git stay identical across environments:

find_replace:
  - find_value: "<dev-lakehouse-id>"
    replace_value:
      TST: "<tst-lakehouse-id>"
      PRD: "<prd-lakehouse-id>"

Orphan cleanup deletes items

unpublish_all_orphan_items removes items from the target workspace that are not in the repository. That is how a deletion in Git reaches PRD, and also how a mistake does. Keep data-bearing types such as lakehouses and warehouses out of item_type_in_scope unless you have thought it through, run the script in TST first, and consider excluding specific names. The cross-workspace binding rules on the repository page still apply.

Driving the Git APIs from automation

Everything the source control pane does has a REST equivalent. That is useful for reconnecting a rebuilt workspace, scripting branch-out, or keeping a downstream workspace connected to Git. It comes with one catch for GitHub.

Connecting a workspace to a GitHub branch looks like this. The connection ID comes from a connection created once, by a person, that stores a GitHub token; the call cannot use the automatic credential source for GitHub or for a service principal.

{
  "gitProviderDetails": {
    "gitProviderType": "GitHub",
    "ownerName": "contoso-org",
    "repositoryName": "fabric-analytics",
    "branchName": "main",
    "directoryName": "SALES_GLD"
  },
  "myGitCredentials": {
    "source": "ConfiguredConnection",
    "connectionId": "<connection-id>"
  }
}
  • Who may call it. The caller must be an admin of the workspace and have permission on the connection. A service principal is supported only through a configured connection.
  • The token problem. For GitHub the configured connection holds a personal access token, so the service principal is only as safe as that token. Use a fine-grained token limited to the one repository with read access to contents, give it an expiry, and plan its renewal. If you can, avoid the problem: deploy definitions with fabric-cicd instead of connecting TST and PRD to Git.
  • Enterprise Cloud with data residency. Add customDomainName to gitProviderDetails for a ghe.com domain. Other custom domains are not supported.
  • Same rules as the UI. The API has the same limits, the same conflicts and the same quirks as the pane. Updates also fail on logical ID conflicts, which you resolve by renaming the item or aligning the ID in Git.

Key takeaways

  • Automation gets its own identity: one service principal per environment, in a security group, with the lowest workspace role that works.
  • Use OIDC federation so no Azure secret is stored. Bind each credential to an environment subject, and a feature branch cannot reach production.
  • Keep deployment credentials in environment scope, never repository or organization scope, and keep workspace IDs as environment variables.
  • Environments add the human gate: required reviewers, prevent self-review, deployment branches limited to main, and protected workflow files.
  • Prefer definition-based deployment to TST and PRD. If you drive the Git APIs, remember that GitHub still needs a connection holding a personal token.
