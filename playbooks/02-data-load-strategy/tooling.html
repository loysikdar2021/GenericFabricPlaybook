Playbook 02 · Data Load Strategy

Choosing the right tool

Fabric offers several items that can load data. They overlap, so the choice is rarely about capability alone: it is about the layer, the volume, the change-tracking source, the team's skills and how much of the state you want to own.

The landscape

Think of the tools in two groups. One group moves data from a source into the lake with little or no transformation. The other transforms data that is already in the lake. A data pipeline sits above both as the orchestrator. Using each tool for its own job, rather than stretching one tool across everything, is what keeps pipelines maintainable.

Data pipelines and Copy activity

Strengths

  • The orchestration engine: sequence notebooks, dataflows, Copy activities and stored procedures with dependencies, parameters, retries and alerts
  • Copy activity is built for high-throughput, metadata-driven movement with minimal transformation
  • The natural first choice for landing raw files from a wide range of sources into Bronze

Weaknesses

  • Copy activity transformation is limited to type conversion, column mapping and file handling, which is not enough for Silver and Gold business logic
  • Incremental state is yours to design (control table, Lookup activity)
  • Row-level merge logic stays outside the tool unless you use the Upsert table action

Lakehouse table actions

When the Copy activity writes to a Lakehouse table, the table action decides the load pattern. This is where a pipeline can implement Bronze loads directly, with no notebook.

Table actionWhat it doesFitsCaution
AppendAdds rows to the tableIncremental Bronze, one batch per runNot idempotent: a retried run appends twice unless you guard it
OverwriteReplaces the data and the schema with the new values; previous versions remain in the Delta logSmall full-load tables, Bronze full snapshotsReplaces every file, which is the worst case for Direct Lake on large tables
UpsertInserts new rows and updates existing ones, matched on the key columns you chooseSimple Silver-style tables with a reliable keyPartition columns cannot overlap key columns; no delete handling and no history, so it is not SCD2

The Copy activity also writes Lakehouse tables with V-Order applied by default, with an option to turn it off. Remember that the default for Spark in new workspaces is the opposite (see Gold and Direct Lake), so a table written by Copy and a table written by Spark can differ in file layout even when both are intended for Direct Lake. Partitioning can be enabled on the destination too, but follow the partitioning guidance before you do.

Orchestration patterns

A pipeline run is the natural unit of a load: it owns the batch identifier, passes it to every step, and decides what happens on failure. A typical structure per source or domain is a Lookup of the last committed watermark, a Copy activity to the landing zone, a notebook activity that loads Bronze and then Silver, a notebook or stored procedure for Gold, and a final step that stores the new watermark and refreshes the semantic model.

// Notebook activity, base parameters
{
  "batch_id": "@activity('Lookup_NextBatch').output.firstRow.next_batch_id",
  "load_type": "@pipeline().parameters.load_type"
}

// Downstream activity reading the notebook's exit value
@activity('Run_Silver_Orders').output.result.exitValue
import json

# Parameters cell: overwritten by the pipeline's base parameters
batch_id = 0
load_type = "incremental"

# ... load and MERGE ...

notebookutils.notebook.exit(json.dumps({"batch_id": batch_id, "rows_merged": rows_merged}))

Prefer a metadata-driven pipeline for many similar tables: a control table lists each source, target, load type and key columns, and a ForEach activity applies one parameterized pattern to every row. Adding a table then becomes a data change, not a new pipeline. The control-table pipelines playbook covers this design in depth.

Copy job

Copy job is a wizard-driven item for repeatable copies: choose the source tables, the destination and a mode (full, or incremental through a watermark column or native change data capture), then schedule it. It keeps the incremental state for you, which removes the Lookup, query and update activities from the pipeline you would otherwise build.

Use it when

  • You need incremental copy or replication of many tables with minimal build effort
  • The source has native CDC and you want the initial full load followed by incremental loads in one job
  • The people maintaining it are analysts or integrators rather than Spark engineers

Look elsewhere when

  • The load needs custom orchestration around it (conditional logic, custom retries, downstream triggers) beyond what a job offers on its own
  • Rows must be cleansed, deduplicated or modeled during the load
  • You need behavior that the documented incremental modes do not cover, such as hard-delete detection with a watermark

Copy job output normally lands in Bronze or the landing zone; the Silver MERGE still belongs in Spark or a materialized lake view. The incremental modes, their limits and preview items are covered in Change tracking.

Dataflows Gen2

Strengths

  • Low-code Power Query authoring with 300+ transformation functions and 150+ connectors
  • Productive for analysts and data engineers who know Power Query and need transformation logic quickly
  • Built-in incremental refresh with automatic bucketing, so common date-driven patterns need no code

Weaknesses

  • Rarely the right choice at terabyte scale, where tuned Spark code usually performs better
  • Visual development integrates less easily with code review, testing and CI/CD than notebooks
  • Incremental refresh has restrictions that matter for lakehouse loads (below)

How Dataflow Gen2 incremental refresh behaves

You pick a date or datetime column, how far back to extract, a bucket size, and a column whose maximum value signals change. At each run the dataflow compares maximum values per bucket, fetches only changed buckets, and for each one deletes the bucket's rows in the destination and inserts the fresh rows. Data outside the bucket range is untouched. That is the affected-slice pattern from the Gold page, implemented as a feature.

ConstraintWhy it matters
Destination must be Fabric Lakehouse, Fabric Warehouse or Azure SQL Database for native supportOther destinations need a second query that reloads from staged data in full
Update method is replace only, with a fixed destination schemaNo merge semantics; schema drift must be handled deliberately
The source query should fully fold, and needs a Date, DateTime or DateTimeZone columnWithout folding the dataflow can pull unfiltered data and lose the benefit
Up to 50 buckets per query and 150 per dataflow; at most 10 concurrent bucket evaluations for a Lakehouse destinationChoose bucket size and window together
Other writers (for example Spark) can interfere, and OPTIMIZE or REORG TABLE are not supported on tables that use incremental refreshGive the table a single writer, and plan compaction differently
Converting a table that already holds overlapping data to incremental refresh is not supportedLoad history first, with a filter that stops before the earliest incremental bucket
Using one column for both filtering and change detection can duplicate rows if data moves between bucketsUse a stable event date to bucket, and a separate modified timestamp to detect change

Single-writer rule

A Dataflow Gen2 destination table with incremental refresh should be written by that dataflow only. A Spark job that also writes to it, or a maintenance job that compacts it, can corrupt the dataflow's bookkeeping or be unsupported outright.

Spark notebooks

Strengths

  • Maximum power, flexibility and scale: the right place for Delta MERGE, SCD Type 2, delete handling and heavy aggregation
  • Code-first: version control, review, automated tests and CI/CD fit naturally
  • Direct access to Delta features: change data feed, replaceWhere, Structured Streaming with checkpoints
  • Parameterizable and callable from pipelines, with exit values for hand-offs

Weaknesses

  • Requires Python, Scala or Spark SQL skills, a steeper curve than low-code options
  • You own the state, idempotency and error handling, so shared frameworks and standards matter
  • Session startup and capacity use are overkill for tiny tables

For this playbook, Spark is the default for Bronze-file-to-Delta loads, Silver MERGE and SCD2, and Gold slice recomputes. Environment and notebook structure conventions are covered in the medallion architecture playbook.

Warehouse T-SQL and T-SQL notebooks

If the Gold layer is a Fabric Warehouse, set-based T-SQL is often the simplest and most performant tool: stored procedures that load dimensions and facts, MERGE for upserts, and CTAS for rebuilds. Fabric Warehouse supports MERGE, including WHEN NOT MATCHED BY SOURCE, and multi-statement transactions. A period-scoped refresh is simply a delete and insert for the same range in one transaction.

CREATE PROCEDURE gold.usp_refresh_daily_sales
    @from_date DATE,
    @to_date   DATE        -- exclusive
AS
BEGIN
    BEGIN TRANSACTION;

    DELETE FROM gold.daily_sales
    WHERE order_date >= @from_date AND order_date < @to_date;

    INSERT INTO gold.daily_sales (order_date, region, revenue, units)
    SELECT order_date, region, SUM(line_amount), SUM(quantity)
    FROM   silver_lh.silver.order_lines          -- cross-item three-part name
    WHERE  order_date >= @from_date AND order_date < @to_date
    GROUP BY order_date, region;

    COMMIT TRANSACTION;
END;
  • Parameters. Call procedures from a pipeline so dates and batch identifiers arrive as parameters. T-SQL notebooks are convenient for interactive work and scheduled SQL, but their documentation lists limitations, such as no parameter cell and no service principal or workspace identity support.
  • Concurrency. Warehouse tables are protected by snapshot isolation with conflicts detected at the table level, so avoid running concurrent UPDATE, DELETE or MERGE statements against the same table.
  • Reading the lake. A Warehouse reads Lakehouse tables through the SQL analytics endpoint, which updates asynchronously. If a procedure must see Silver data written moments earlier, make sure the endpoint has caught up before it runs.

Verify against Microsoft Learn

T-SQL notebook limitations are listed in Author and run T-SQL notebooks and have been shrinking over time. Check the current list, the MERGE reference for Fabric, and the SQL analytics endpoint metadata-sync guidance before you depend on any of them.

Materialized lake views

A materialized lake view (MLV) is a declarative way to build a Silver or Gold table. You write the SQL query once; Fabric persists the result as a Delta table, tracks dependencies between views, orders refreshes and enforces data quality rules. It turns a hand-built chain of notebooks into a dependency graph that refreshes itself.

On each scheduled refresh the engine picks one of three strategies:

No refresh
No new Delta commits on the sources, so the run is skipped and costs nothing.
Incremental
Only changed data is processed. Requires change data feed (CDF) enabled on every source table or view, and a query that uses only supported constructs.
Full
The whole view is recomputed. Used when CDF is missing, when the query uses unsupported constructs, when changes cannot be applied incrementally, or when a full recompute is cheaper.
ALTER TABLE silver.order_lines
  SET TBLPROPERTIES (delta.enableChangeDataFeed = true);

CREATE MATERIALIZED LAKE VIEW IF NOT EXISTS gold.daily_sales
(
  CONSTRAINT valid_units CHECK (units >= 0) ON MISMATCH DROP
)
TBLPROPERTIES (delta.enableChangeDataFeed = true)
AS
SELECT order_date,
       region,
       SUM(line_amount) AS revenue,
       SUM(quantity)    AS units,
       COUNT(*)         AS line_count
FROM silver.order_lines
GROUP BY order_date, region;

What incremental refresh supports

ConstructIncremental?Notes
Filters, projections, deterministic built-in functionsYesrand(), uuid() and current_timestamp() are not supported
Inner joins, UNION ALL, CTEsYesSubqueries and CTEs must use only supported clauses
Left outer and left semi joinsConditionallyOnly when the right-hand table does not change in the cycle; otherwise full refresh
SUM, MIN, MAX, COUNT (no DISTINCT) with GROUP BYYesNo partitioning requirement
Other aggregates such as AVGConditionallyEvery source must be partitioned, with the partition column in the GROUP BY
DISTINCT, window functionsNoForces a full refresh; fine for small views, costly for large ones
Source rows that are updated or deletedNeeds a refresh hintAppend-only sources work directly; for updates and deletes the view must declare row identity or Fabric falls back to a full refresh
Non-Delta sources, PySpark-authored viewsNoAlways a full refresh

MLVs fit

  • Stateless SQL transformations: joins, filters, projections and additive aggregates
  • Multi-stage medallion chains where dependency ordering and data quality constraints matter
  • Teams that prefer SQL and want Fabric to own refresh logic and monitoring

MLVs do not fit

  • Stateful logic: SCD Type 2 history, hard-delete handling against a snapshot, custom watermarks
  • Non-SQL work: API calls, machine-learning inference, complex Python
  • Sub-second streaming freshness, where Real-Time Intelligence is the better fit

Because the refresh engine decides the strategy, check the run history to see which one was used. A view that silently falls back to full refresh on every run is a design smell: look for DISTINCT, a window function, a missing CDF property on one source, or updates and deletes without a refresh hint. A manual full refresh is also available (REFRESH MATERIALIZED LAKE VIEW ... FULL) for troubleshooting or after a correction.

Verify against Microsoft Learn

SQL authoring of materialized lake views is documented without a preview label on the overview page, while PySpark authoring is marked Preview and always performs a full refresh. Supported constructs, refresh hints and file-ingesting views are still evolving. Check the overview and optimal refresh before standardizing on them.

A decision flow for the tool

The flow reflects the matrix: first decide whether the step moves or transforms data, then walk down the questions until one answers yes. The fall-through at the bottom of each column is the safe default for that kind of step.

CriterionQuestion to askLeans toward
Team skillsWho will maintain this at 2 a.m.?Power Query team: Dataflow Gen2. SQL team: Warehouse T-SQL or MLV. Python or Spark team: notebooks.

Change-tracking sourceDo you have CDC, a trustworthy watermark, or neither?CDC: Copy job, mirroring or Eventstreams. Watermark: pipeline or Copy job. Neither: full load or snapshot comparison in Spark.

Anti-patternWhy it hurtsInstead

Two tools writing the same Delta table (dataflow plus notebook, or Copy job plus MERGE)Conflicts, lost bookkeeping, unsupported maintenance operationsOne owner per table; hand over through a separate staging table
One bespoke pipeline per tableDozens of near-identical pipelines that drift apartMetadata-driven pipeline with ForEach and a control table

Key takeaways

  • Separate movement tools from transformation tools, and let a data pipeline orchestrate both.
  • Copy activity and Copy job are for getting data in; Spark, Warehouse T-SQL and materialized lake views are for shaping it.
  • Use Spark for stateful logic (MERGE, SCD2, delete handling, slice recompute); use materialized lake views for stateless SQL with a clear incremental fit.
  • Dataflow Gen2 incremental refresh is bucket replace with fixed schema and a single-writer requirement; it suits moderate volumes, not terabyte tables.
  • Give every Delta table exactly one owning tool, and choose tools whose writes preserve file layout for Direct Lake.
  • Prefer metadata-driven pipelines and durable control tables to per-table pipelines and in-memory state.
