Playbook 02 · Data Load Strategy

Full vs incremental loads

The choice between replacing a table and applying changes to it is a strategic trade-off between simplicity, freshness and cost. This page defines both patterns, gives explicit thresholds for when a full load is still the right answer, and lists how each approach fails.

Why this decision matters

Load style is not an implementation detail. It sets how fresh the data can be, how much capacity each refresh consumes, how much logic you must build and monitor, and how the pipeline recovers from a bad run. The wrong default is expensive in both directions: incremental logic on a tiny lookup table is maintenance for no benefit, and a nightly full reload of a billion-row fact table eventually stops fitting in its window.

Full load (destructive refresh)

A full load extracts the entire dataset from the source and uses it to replace the contents of the target table, so the target becomes a point-in-time snapshot of the source. In a Delta lakehouse there are three ways to do it, and they are not equivalent.

TechniqueWhat happensUse it when
Overwrite (mode("overwrite") or INSERT OVERWRITE)One atomic Delta commit. Readers see the previous version or the new one, never an empty table, and the previous version stays available for time travel until vacuumed.The default for full reloads
Truncate then insertTwo commits. Between them the table is empty, and a failed load leaves it that way.Avoid. There is no benefit over overwrite
Drop and recreateRemoves the table definition, permissions and properties as well as the data.Only when you deliberately change the schema and have scripted everything that is lost
 
from pyspark.sql import functions as F

# One row per product_id: a complete snapshot of the source, already landed in Bronze.
snapshot = spark.table("bronze.products_snapshot")

(snapshot
    .withColumn("_loaded_at", F.current_timestamp())
    .write.format("delta")
    .mode("overwrite")                 # single atomic commit
    # .option("overwriteSchema", "true")  # add only when you intend to accept a changed schema
    .saveAsTable("silver.products"))

What a full load gives you. There is no change-tracking logic to build, which makes the pipeline easy to write, test and debug. The target is a faithful copy of the source at run time, so schema drift, data drift and the accumulated errors of a faulty incremental process all disappear on the next run. That makes a full load the standard recovery tool: when anything is in doubt, rebuild.

What it costs. Every run extracts and writes the whole table, so cost scales with total size rather than change volume. It loads the source system, uses capacity for the full duration, and wipes any history you were accumulating in that table unless you archive it separately. Because every Parquet file is replaced, a Direct Lake model that reads the table must reload its column data after each run (see Gold layer and Direct Lake).

Where it fits. Initial population of any table, small tables, periodic resynchronization of tables that are otherwise loaded incrementally, snapshot sources that offer nothing else, and rebuilds after a logic change.

Full-load eligibility: all of these must hold

Incremental load (delta processing)

An incremental load identifies, extracts and applies only the data created or changed since the last successful run. It preserves what is already in the target and changes it by appending new records, updating existing ones or marking records deleted. That is what makes it cheap and frequent, and also what makes it fragile: the target is only as correct as the change signal and the logic that applies it.

  • Efficiency. Work scales with the volume of change, not the size of the table, which is what keeps large tables loadable at all.
  • History retention. Because the table is not overwritten, history needed for audit, trend analysis and slowly changing dimensions survives.
  • Freshness. Small runs can execute hourly or more often, so data reaches consumers sooner.

It is the default for large, frequently updated tables such as orders, web events and sensor readings, and for any latency target that a nightly rebuild cannot meet. For sources with a log-based change feed it is also the better fit for finance and logistics-style near real-time needs, with streaming tools taking over below minute-level latency.

Incremental is not automatically cheap

Delta rewrites whole Parquet files that contain a changed row. If updates are scattered across the table, a MERGE touching 0.5 percent of rows can still rewrite most files. Co-locate changes with a partition or clustering column that matches how rows change (for example the order date), keep deletion vectors enabled on runtimes where they are the default, and measure numTargetFilesRemoved in DESCRIBE HISTORY rather than assuming.

The trade-off, and the hybrids that resolve it

A full load buys ease and integrity at the cost of performance, resource use and latency. An incremental load buys speed and freshness at the cost of complexity and a higher inherent risk of inconsistency when change detection and reconciliation are not designed and monitored with care. Real platforms rarely pick one for everything. Four hybrids cover most needs.

  • Incremental plus periodic full resync. Run frequent incremental loads and a scheduled full comparison (weekly, say) that repairs drift and handles hard deletes. This is the standard answer when the source offers only a watermark.
  • Partition-scoped micro-full. Rebuild one partition or period, such as a restated month, with replaceWhere. The blast radius is one slice, not the table (see Silver reloads).
  • Full on first load and on schema change, incremental otherwise. Tools such as Copy job do the initial full copy automatically and let you reset a table back to full on demand.
  • Incremental in Bronze, full rebuild of Silver and Gold from Bronze. Possible only while Silver and Gold remain small, or when history logic changes and a deliberate rebuild is planned.

Record the decision per table

Keep a small table in your control metadata with table_name, load_pattern (full, incremental-watermark, incremental-cdc, snapshot-merge), change_signal, last_reviewed and the numbers that justified it. Reviews then compare against thresholds instead of memory. The control-table playbook shows how to drive pipelines from such a table.

Key takeaways

  • Use overwrite, not truncate and insert, for full reloads: it is one atomic commit.
  • A table stays on full loads only while all six eligibility checks pass; re-run the checks as it grows.
  • Incremental correctness depends on the change signal: design for late data, duplicates, out-of-order updates and deletes up front.
  • Scattered changes can make a small incremental load rewrite most of a table, so align layout with how rows change.
  • Pair incremental loads with a tested reset-to-full path and scheduled reconciliation.
