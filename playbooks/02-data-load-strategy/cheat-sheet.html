Defaults by layer

The optimal strategy is a hybrid, chosen table by table and layer by layer. A small, static reference table does not deserve an incremental pipeline; a fact table with billions of rows cannot be fully reloaded. These are the defaults to start from.

Rules of thumb

Treat the figures below as starting points. Only the Direct Lake and Delta defaults are documented platform values; the load thresholds are practitioner guidance to calibrate against your own capacity and SLAs.

Stay on full load while
The table is under roughly 20 to 30 GB or 50 million rows, runs end to end in roughly 10 to 15 minutes, and has no history to protect. Reassess as it grows.
Watermark overlap
Re-read a small window behind the stored watermark and let MERGE dedupe, to catch late-arriving rows. Advance the watermark only after the write succeeds.
Resync cadence
Run a full key comparison for incrementally loaded tables on a schedule that matches how much drift the business tolerates, often weekly or monthly.
Change data feed retention
Readers can only see changes while the log and data files exist. A VACUUM with the default seven-day retention bounds how far a consumer can fall behind.
Direct Lake row groups
Roughly 1 to 16 million rows per row group, with limited variation, and a file count inside the SKU guardrails.
Partitioning
Avoid by default. Where a low-cardinality column (fewer than about 100 to 200 values) limits rewrite scope, it can help; see the partitioning playbook.

Design checklist for each table

  • The table is classified as full or incremental against explicit thresholds, and the decision is written down.
  • The change signal is identified (CDC, watermark column, snapshots) and its blind spots, especially deletes, are documented.
  • Bronze appends with batch id, load type, source file and ingest time, and a rerun of the same batch changes nothing.
  • Silver deduplicates the source before MERGE, guards updates with a version column, and uses a unique business key.
  • Delete handling matches the signal: CDC deletes, a soft-delete flag, or a guarded snapshot comparison.
  • The watermark or processed version is stored durably and advanced only after a successful write.
  • Gold measures are classified additive or not; ratios live in DAX measures over additive columns.
  • Large Gold tables are updated by append or slice replacement, not by full overwrite, and V-Order is enabled where Direct Lake reads them.
  • Each Delta table has exactly one owning tool, and the tool matches the team's skills and the volume.
  • Reconciliation checks, file-health monitoring and a scheduled full resync exist, with owners and alerts.

Key takeaways

  • Decide per table and per layer: full load for small and simple, incremental for large and busy, and a hybrid wherever the source cannot see deletes.
  • Bronze appends everything, Silver upserts with guards, and Gold recomputes the smallest correct slice.
  • The change signal the source exposes, not preference, selects the mechanism.
  • Every incremental table needs a periodic reconciliation, because incremental logic hides drift.
  • Check the result of each write pattern for consumers, especially Direct Lake, instead of assuming it is harmless.
