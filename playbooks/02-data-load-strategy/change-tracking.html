Change tracking options

An incremental pipeline is only as reliable as its answer to one question: what changed? This page covers the mechanisms available in a Fabric platform, from a simple high-watermark to log-based CDC, mirroring and Delta change data feed, and gives you a way to choose between them.

Start with the source, not the tool

The feasibility and reliability of an incremental load depend entirely on how accurately you can identify changed data. That capability is set by the source system, not by your pipeline tool, so the first design question is "what change information does the source provide?" Adopting this source-first view prevents the most common production surprise: an incremental pipeline that works for months and then reveals that deletes were never propagated.

There are three situations, in order of preference:

  1. The source exposes a change log (database CDC, a replication feed). You can capture inserts, updates and deletes in order.
  2. The source has a reliable "last changed" marker (a modified timestamp, row version or increasing key). You can find inserts and updates since the last run, but not deletes.
  3. The source offers only snapshots. You must compare the new snapshot with what you hold, which costs a full scan each time.

High-watermarking (HWM)

The high-watermark method tracks progress with a column in the source table, such as a last_modified timestamp, a SQL Server ROWVERSION or a monotonically increasing integer. Each run uses the highest value seen last time as a bookmark.

  1. Read the stored high-water mark

    Fetch the maximum watermark value from the last successful run out of a durable control table. On the first run there is none, which means a full initial load.

  2. Query the window

    Select rows whose watermark is greater than the stored value and no greater than an upper bound captured when the run starts. The upper bound stops rows committed during extraction from being half-read and then skipped.

  3. Write the batch

    Append it to Bronze (or merge it into the target) and wait for the commit.

  4. Advance the watermark last

    Store the new maximum only after the write succeeds, so a failed run is simply repeated.

Watermark in a pipeline

In a data pipeline the pattern is a Lookup activity that reads the stored value, a Copy activity whose source query uses it, and a final activity that stores the new value on success. Copy job implements the same state handling for you (see Copy job incremental modes), so hand-built pipelines are worth it only when you need custom queries or orchestration around the copy.

SELECT *
FROM sales.orders
WHERE modified_at >  '@{activity('Lookup_LastWatermark').output.firstRow.watermark_value}'
  AND modified_at <= '@{pipeline().parameters.RunUpperBound}'

Set RunUpperBound to the pipeline's start time (or the source's current maximum) and write the same value to the control table when the copy succeeds.

Watermark in a notebook

For Bronze-to-Silver processing, track progress with an ingestion batch id that the orchestrator assigns in increasing order, not with wall-clock time. Concurrent ingestion runs can finish out of order, and a timestamp watermark would then skip the slower run's rows.

from pyspark.sql import functions as F
from delta.tables import DeltaTable

WM_TABLE = "ops.watermarks"   # source_name STRING, watermark_value STRING, updated_at TIMESTAMP

spark.sql(f"""
CREATE TABLE IF NOT EXISTS {WM_TABLE} (
  source_name STRING, watermark_value STRING, updated_at TIMESTAMP
) USING DELTA""")

def get_watermark(source_name):
    row = (spark.table(WM_TABLE)
                .where(F.col("source_name") == source_name)
                .select("watermark_value").first())
    return int(row["watermark_value"]) if row else None

def set_watermark(source_name, value):
    new = (spark.createDataFrame([(source_name, str(value))], "source_name string, watermark_value string")
                .withColumn("updated_at", F.current_timestamp()))
    (DeltaTable.forName(spark, WM_TABLE).alias("t")
        .merge(new.alias("s"), "t.source_name = s.source_name")
        .whenMatchedUpdateAll()
        .whenNotMatchedInsertAll()
        .execute())

last_batch = get_watermark("bronze.orders")          # None on the first run
batch = spark.table("bronze.orders")
if last_batch is not None:
    batch = batch.where(F.col("_batch_id") > last_batch)

new_high = batch.agg(F.max("_batch_id")).first()[0]
if new_high is None:
    print("Nothing new to process")
else:
    # ... deduplicate and MERGE `batch` into silver.orders (see the Silver page) ...
    set_watermark("bronze.orders", new_high)         # only after the MERGE has committed

Change data capture (CDC)

Change data capture records every insert, update and delete directly from the source database, usually by reading its transaction log, and delivers an ordered stream of change events. It is more accurate than a watermark because deletes are first-class events, and it puts little load on the source because it reads the log rather than querying tables. The price is setup and operations: the source must have the feature enabled (for example SQL Server's native CDC), you manage permissions and log retention, and you need a consumer that applies the events correctly.

In Fabric you have several ways to consume change streams. They differ in what they produce and how much of the pipeline they take over.

OptionWhat it doesResult in FabricTypical use

Mirroring is a replica, not a history

A mirrored database gives you the current state of each source table, merged for you. It is not an append-only change history: Fabric vacuums old files automatically, with a short default retention that you can adjust in the mirrored database settings, and you cannot configure the Delta layout or table properties. If you need an immutable record of every change for audit or reprocessing, land the change stream with Copy job (append, with audit columns) or keep your own Bronze history, and treat the mirror as the current-state source for Silver.

Supported mirroring sources and their release status vary and change often; some sources are labeled preview. Check What is Mirroring in Fabric? before committing. Mirroring storage and background replication compute are free up to a capacity-based limit; confirm the current terms on the same page.

Copy job incremental modes

Copy job is a Data Factory item that moves data from many sources to many destinations without building a pipeline. It supports full copy and incremental copy, and manages the state of the last successful run for you. For database sources it chooses between two incremental modes per table.

  • Watermark-based incremental copy. You pick an incremental column. Supported types include ROWVERSION, datetime, date, strings interpretable as datetime and integers; for an unsupported type you can cast in the source query. Date-only columns get an automatic delayed extraction so same-day changes are not lost. Rows with a NULL watermark are skipped after the initial load. Deletes are not detected.
  • CDC-based incremental copy. When CDC is enabled on a supported source table, Copy job detects it, replicates inserts, updates and deletes, and applies them to the destination with merge (SCD Type 1) or SCD Type 2 (with soft-deleted history).
  • File sources. Subsequent loads copy only files created or modified since the last successful run.

Useful operational features: Copy job resumes from the end of the last successful run, you can reset incremental state to a full copy per job or per table, it can add audit columns (extraction time, run id, incremental window bounds) to every row, and for Lakehouse destinations it can enable Delta change data feed on the tables it creates. Reset does not clear the destination: with the Append write method, a reset followed by a run duplicates rows unless you truncate first.

Verify against Microsoft Learn

CDC replication in Copy job is documented as a preview capability with a limited connector list, SCD Type 2 is marked preview, only net-change capture and the default capture instance are supported, and a job that mixes CDC and non-CDC tables treats all of them as watermark-based. Check Change data capture in Copy job for current sources, status and limitations before designing around it.

Delta change data feed (CDF)

Once data is in a Delta table you can get row-level change tracking from Delta itself. Delta change data feed records, for each commit, which rows were inserted, updated or deleted. It is off by default and records only changes made after you enable it.

-- Enable on a new or existing table
ALTER TABLE silver.orders SET TBLPROPERTIES (delta.enableChangeDataFeed = true);

-- Read changes from a table version onward
SELECT order_id, order_date, amount, _change_type, _commit_version, _commit_timestamp
FROM table_changes('silver.orders', 42);
_change_type
insert, update_preimage, update_postimage or delete. The pre-image is the row before an update, which lets you correct aggregates keyed on an old value.
Storage
Change rows for UPDATE, DELETE and MERGE are written under a _change_data folder. Insert-only commits and whole-partition deletes are served from the transaction log. Overhead is small.
Retention
Change data follows the table's retention, so VACUUM removes it. A consumer that falls further behind than the retention period loses changes and must fall back to a rebuild.
Maintenance commits
OPTIMIZE rewrites files without changing data and produces no change rows.

Where CDF helps, and where it does not

CDF is most valuable on tables that are updated and deleted, typically Silver tables maintained with MERGE, feeding Gold. It is also how materialized lake views decide to refresh incrementally (see materialized lake views). On an append-only Bronze table it adds little, because every change is an insert. To process only new Bronze rows without a hand-written watermark, read Bronze as a stream and let the checkpoint keep the state.

from delta.tables import DeltaTable
from pyspark.sql import functions as F, Window

silver_cols = spark.table("silver.orders").columns

def upsert_batch(micro_df, batch_id):
    w = Window.partitionBy("order_id").orderBy(F.col("modified_at").desc(), F.col("_ingest_ts").desc())
    latest = (micro_df.withColumn("_rn", F.row_number().over(w))
                      .where("_rn = 1")
                      .select(*silver_cols))              # drop Bronze metadata columns
    (DeltaTable.forName(micro_df.sparkSession, "silver.orders").alias("t")
        .merge(latest.alias("s"), "t.order_id = s.order_id")
        .whenMatchedUpdateAll(condition="s.modified_at >= t.modified_at")
        .whenNotMatchedInsertAll()
        .execute())

(spark.readStream.table("bronze.orders")                  # Bronze must be append-only
    .writeStream
    .foreachBatch(upsert_batch)
    .option("checkpointLocation", "Files/_checkpoints/silver_orders")
    .trigger(availableNow=True)                           # process all new data, then stop
    .start()
    .awaitTermination())

The checkpoint (kept in the lakehouse Files area) records which Bronze commits were processed, so a rerun after failure resumes where it stopped. If Bronze ever receives updates or deletes, a stream over it fails by default; handle that deliberately (for example with the source option skipChangeCommits) rather than disabling the check blindly.

Choosing a mechanism

The ideal mechanism is log-based CDC because it gives a complete, unambiguous stream of changes and simplifies every downstream transformation. If CDC is not available, a watermark is a viable alternative with one structural constraint: it cannot see hard deletes, so you must combine it with a periodic full comparison to resynchronize the target. If neither CDC nor a reliable watermark exists, true incremental loading is very difficult, and you fall back to hashing or comparing full snapshots, which gives up much of the performance benefit.

Test the signal before you trust it

Before building on a watermark column, run a one-off reconciliation: take a sample of recent source rows, change a few through the normal application path (insert, update, soft delete, bulk correction) and confirm each one moves the column and appears in the next increment. Repeat the test whenever the source application changes.

Key takeaways

  • The change signal is set by the source; ask what it provides before choosing a tool.
  • Watermark loads must write first and advance the watermark last, with an upper bound and an idempotent write.
  • Track Bronze-to-Silver progress with monotonically increasing batch ids or a stream checkpoint, not wall-clock time.
  • Watermarks cannot see deletes; plan a periodic full comparison or move to CDC.
  • Mirroring gives you current state, not history; keep your own Bronze history if you need audit or replay.
  • Use Delta CDF on updated Silver tables to drive incremental Gold refresh, and respect VACUUM retention.
