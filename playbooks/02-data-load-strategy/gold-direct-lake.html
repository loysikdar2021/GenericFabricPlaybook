Gold layer and Direct Lake

Gold is the business-ready layer, modeled for analytics and consumed by semantic models. The central loading decision is how to keep aggregates and facts correct without recomputing everything, and the consumption layer, especially Direct Lake, adds constraints that reach back into how you write.

Objective: optimized for analytics and reporting

Gold takes conformed Silver data and prepares it for specific business uses. The work is usually a mix of three things.

  • Aggregation. Summarize to a coarser grain, such as daily or monthly sales from individual order lines.
  • Data modeling. Shape the data into a dimensional model, most often a star schema: central fact tables of measurements surrounded by dimension tables of descriptive attributes. That design matches the query patterns of BI tools.
  • Business logic. Apply final calculations, KPIs and classifications, such as customer segments and fiscal period labels.

The tables that result should give fast queries and an intuitive model for analysts, which makes Gold the layer where load design and consumption design meet.

The aggregation dilemma

The core Gold decision is how to create and maintain aggregated, modeled tables. There are two classic answers and one practical middle path.

Full recalculation: pros

  • Simple logic, highly reliable
  • Exactly correct each run, including complex or non-additive measures
  • Doubles as the periodic integrity refresh

Full recalculation: cons

  • Slow and capacity-hungry when Silver is large
  • Too slow for high-freshness or near real-time needs
  • Rewrites every file, which is the worst case for Direct Lake (see below)

Incremental aggregation: pros

  • Much faster and cheaper, since it processes a small slice
  • Supports frequent refreshes and fresher data

Incremental aggregation: cons

  • Considerably more complex logic
  • Non-additive measures such as distinct counts need careful design
  • A logic flaw causes subtle, accumulating errors

Use full recalculation for small data marts, dimension tables, logic that is too complex to make incremental reliably, initial builds and periodic integrity refreshes. Use incremental processing for large fact tables and performance-critical systems where both volume and freshness matter.

The middle path: recompute the affected slice

"Incremental" does not have to mean adding deltas to existing numbers, which is fragile. A more robust approach finds which slices of the Gold table (dates, periods, regions) the new Silver changes touch, recomputes those slices completely from Silver, and replaces them atomically. Because each affected slice is rebuilt from source rows, the result is correct for any measure, additive or not, and rerunning is safe.

from pyspark.sql import functions as F

last_version = 41        # last Silver version processed, from the control table
changes = (spark.read.format("delta")
             .option("readChangeFeed", "true")
             .option("startingVersion", last_version + 1)
             .table("silver.order_lines"))

# Include pre-images and deletes so a row that moved between dates refreshes its old date as well
dates = [r["order_date"] for r in
         changes.where("_change_type IN ('insert','update_preimage','update_postimage','delete')")
                .select("order_date").distinct().collect()]

if not dates:
    print("No Silver changes; Gold is up to date")
elif len(dates) > 400:
    raise RuntimeError("Too many affected dates for a slice refresh; run the full recalculation")
else:
    date_list = ", ".join(f"DATE'{d.isoformat()}'" for d in dates)
    daily = (spark.table("silver.order_lines")
               .where(F.col("order_date").isin(dates))
               .groupBy("order_date", "region")
               .agg(F.sum("line_amount").alias("revenue"),
                    F.sum("quantity").alias("units"),
                    F.countDistinct("customer_id").alias("customers")))   # non-additive, still correct

    (daily.write.format("delta")
          .mode("overwrite")
          .option("replaceWhere", f"order_date IN ({date_list})")
          .saveAsTable("gold.daily_sales"))
    # then store the new Silver version in the control table

A date whose source rows were all deleted produces no rows in daily, so replaceWhere correctly removes it from Gold. The guard on the number of dates keeps a historical restatement from turning into an accidental near-full rewrite, and the change feed requires CDF to be enabled and retained (see Change tracking).

Which measures can be incremental?

Measure typeExamplesMerge deltas?Recommended approach
AdditiveRevenue, units, line countsYes, with signed deltasSlice recompute, or delta merge if volumes demand it
Distinct countsCustomers per day or per monthNoCounts cannot be summed across slices. Recompute the whole affected period at the target grain, for example the affected month
RatiosMargin percent, average order valueNo: ratios cannot be summedStore additive numerator and denominator in Gold; compute the ratio as a DAX measure
Rank and percentileCustomer rank by total salesNoOne new order can re-rank everyone. Recompute the full population on a schedule, or compute in the model
Snapshots and balancesMonth-end inventoryDependsPeriod-scoped recompute, closing periods as they complete

If you do merge deltas, build them from the change feed with signs (post-image and insert positive, pre-image and delete negative), and remember that the merge is not idempotent: applying the same delta twice double-counts. Store the processed version transactionally with the write, or prefer slice recompute.

from pyspark.sql import functions as F

signed = (changes
    .withColumn("sign", F.when(F.col("_change_type").isin("insert", "update_postimage"), 1)
                         .when(F.col("_change_type").isin("delete", "update_preimage"), -1)
                         .otherwise(0))
    .groupBy("order_date", "region")
    .agg(F.sum(F.col("sign") * F.col("line_amount")).alias("revenue_delta"),
         F.sum(F.col("sign") * F.col("quantity")).alias("units_delta")))
signed.createOrReplaceTempView("delta_by_day")

spark.sql("""
MERGE INTO gold.daily_sales AS t
USING delta_by_day AS d
  ON t.order_date = d.order_date AND t.region = d.region
WHEN MATCHED THEN UPDATE SET t.revenue = t.revenue + d.revenue_delta, t.units = t.units + d.units_delta
WHEN NOT MATCHED THEN INSERT (order_date, region, revenue, units)
     VALUES (d.order_date, d.region, d.revenue_delta, d.units_delta)
""")

Direct Lake: what it needs from your loads

Direct Lake is a Power BI semantic model storage mode that loads columns from Delta tables in OneLake into memory on demand and queries them with the same VertiPaq engine as Import mode. It avoids an import refresh, but it ties query performance to the physical state of your Delta tables, so Gold loading decisions become BI performance decisions. Five concepts explain nearly all of it.

Transcoding
On the first query that needs a column, Direct Lake loads the whole column from Parquet into memory, merging the per-file Parquet dictionaries into one global dictionary. Many small row groups mean many dictionaries to merge, which makes a cold load slower.
Framing
A refresh of a Direct Lake model is a metadata operation that points the model at the latest Delta log version and its Parquet files. It takes seconds, sets a point-in-time baseline, and evicts only the memory whose underlying files changed.
Incremental framing
If a table changed only by added files, resident data stays valid and only new data is loaded. If files were replaced, the corresponding memory is evicted and must be transcoded again.
Automatic updates
The model setting "Keep your Direct Lake data up to date" is on by default and reframes whenever it detects table changes. Turn it off when you need a pipeline to finish before consumers see new data, then trigger a refresh yourself after the load.
Fallback
Only Direct Lake on SQL analytics endpoints can fall back to DirectQuery. Direct Lake on OneLake never does, and is the documented option for new models.

Fallback control and diagnosis

For Direct Lake on SQL analytics endpoints, the Direct Lake behavior model property controls what happens when Direct Lake conditions are not met: Automatic (default) falls back silently, DirectLakeOnly fails the query so you find and fix the cause, and DirectQueryOnly always uses DirectQuery. Use DirectLakeOnly in development and consider keeping fallback available in production for user continuity. To see which tables fall back and why, run this DAX query against the model.

EVALUATE TABLETRAITS()

The DirectLakeFallbackInfo column shows the reason per table, and None means the table is served by Direct Lake. Typical causes and fixes:

Guardrails

Each capacity SKU caps files, row groups and rows per table, evaluated per query, plus a model size limit on smaller SKUs. For Direct Lake on OneLake, exceeding a guardrail makes refresh fail and blocks queries until you optimize; on SQL analytics endpoints the model falls back to DirectQuery if fallback is enabled. A single table over a limit disables Direct Lake mode for the entire model.

Table layout Direct Lake rewards

FactorGuidance
V-OrderApply it to Gold tables that Direct Lake reads. It improves compression and loading speed. New Fabric workspaces default to the write-heavy resource profile with V-Order off, so enable it explicitly: set spark.sql.parquet.vorder.default to true, use the readHeavyForPBI resource profile, or set the delta.parquet.vorder.enabled table property. Existing files keep their layout until rewritten (for example by OPTIMIZE ... VORDER).
Row groupsDirect Lake generally performs best with row groups of roughly 1 million to 16 million rows. Very small row groups cause performance problems; larger ones are acceptable. Avoid large variation in size.
File countFewer, larger files transcode faster and stay within guardrails. Let adaptive target file size and compaction manage sizes rather than hand-setting row limits.
Data typesComplex Delta types and binary or GUID semantic types are unsupported; convert to strings or other supported types. Prefer integers over integer-like strings, and keep high-cardinality columns to those you need.
Partitioning and clusteringDirect Lake does not use Parquet statistics to skip row groups or files when loading, so layout features that exist for file skipping do not speed up Direct Lake. Low-cardinality partitions can still limit how much a rewrite disturbs (below). See the partitioning playbook.

Write patterns: what keeps framing incremental

Parquet files are immutable, so an update or delete is a rewrite. What matters to Direct Lake is how much of the table's file set changes in one commit.

Update patternEffect on Direct LakeGuidance
Incremental appendExisting files and row groups untouched; incremental framing worksBest case. Partitioning is not needed. Compact periodically
Streaming or frequent micro-batchesMany small files and row groupsPartitioning is not needed, but run OPTIMIZE often (daily or more) to stay inside guardrails
Batch with delete or update, unpartitionedDeleting one day of thirty can rewrite nearly every file, forcing a near-total reloadAvoid for large tables, or isolate the change to a slice
Batch with delete or update, partitioned by a low-cardinality columnThe rewrite is limited to the partitions touchedChoose a column with fewer than about 100 to 200 distinct values (a month, not a day, for multi-year tables); more partitions inflate files and row groups
Overwrite of a large tableAll files replaced, so every column segment is evictedUse only for small tables; otherwise replace slices with replaceWhere

OPTIMIZE is itself a rewrite: it replaces small files with large ones, which invalidates the matching in-memory segments and costs a short cold-state penalty in exchange for better long-term performance. Run it after loads during quiet periods, scoped to the partitions touched by the latest load where possible. VACUUM has one more constraint: a framed model references a specific Delta version, and removing files that version needs causes query errors until the next framing. Keep the retention period longer than the longest gap between framings (the default of seven days is usually safe).

Because every Gold write you choose either preserves or discards what Direct Lake has loaded, check the result rather than assuming. The Delta Analyzer in the semantic-link-labs library, or a DAX query over INFO.STORAGETABLECOLUMNSEGMENTS() after a load, shows whether segments were reused or evicted.

Business logic: what must be materialized

Direct Lake on SQL analytics endpoints does not support calculated columns or calculated tables on Direct Lake tables, and Direct Lake on OneLake supports them only in limited, preview form (calculated columns with user context only). Plan as if derived columns must be produced upstream and stored in the Gold Delta table. The practical rule is more precise than "pre-compute everything":

  • Materialize row-level and attribute derivations that models slice by: customer segment, age band, fiscal period label, a customer's rank, a product category rollup.
  • Keep ratios and aggregates as DAX measures over additive base columns. A profit margin percentage is (SUM(revenue) - SUM(cost)) / SUM(revenue) computed at query time at whatever grain the visual uses. Storing a per-row margin percentage and summing or averaging it gives wrong totals.

This is also where the load strategy feels the constraint: a materialized column that depends on the whole population, such as a customer's sales rank, changes for many rows whenever one order arrives. Such tables often justify a scheduled full recalculation even when the rest of Gold is incremental, trading pipeline efficiency for correct, queryable columns.

Verify against Microsoft Learn

Support for calculated columns, calculated tables and composite models in Direct Lake is evolving and differs between the two Direct Lake options. Check the comparison and limitations tables in the Direct Lake overview before you commit a design.

After the load: reframing

With automatic updates on, the model reframes itself when it sees new Delta versions, which suits independent tables and small models. When a load writes several tables that must be consistent (a fact and its aggregates), a model that reframes between the writes can show a mixed state. In that case turn automatic updates off, run the whole load, and finish the pipeline with a refresh of the semantic model through a pipeline refresh activity, the REST API or semantic link. That gives consumers one consistent cut-over.

Key takeaways

  • Prefer affected-slice recompute for incremental Gold: it is correct for non-additive measures and safe to rerun.
  • Store additive base columns in Gold and compute ratios as DAX measures; materialize only attribute-level derivations.
  • For Direct Lake, append or replace slices; do not overwrite large tables, because every file replaced is data the model must reload.
  • Enable V-Order for Gold tables read by Direct Lake, keep row groups large, and stay within SKU guardrails.
  • Use Direct Lake on OneLake for new models, and design out fallback if you use SQL analytics endpoints.
  • Turn automatic updates off and refresh once at the end of multi-table loads that must be consistent.
