Playbook 02 · Data Load Strategy

Silver: MERGE, SCD2 and deletes

Silver turns raw Bronze history into a single, trustworthy current state. This is where deduplication, upserts, dimension history and delete handling happen, and where most data-correctness bugs are made. The patterns below are idempotent, and each delete strategy is tied to the change signal that makes it safe.

Goal: cleansed, conformed, integrated

Silver takes the append-only data in Bronze and improves its quality and usability. Typical work falls into three groups.

  • Cleansing. Handle nulls and missing values, correct data types, and validate against business rules. Route failing rows to a quarantine table with a reason code instead of dropping them silently.
  • Conforming. Standardize formats and build master entities such as customers and products by merging records from several source systems.
  • Integration. Join datasets to give a fuller picture, for example orders with customers.

The output is a set of validated, de-duplicated Delta tables that represent the current state of the business, ready to feed Gold. Whether Silver is loaded by full reload or incrementally follows the criteria on the full vs incremental page.

Full and partition-scoped reloads

A full Silver reload is appropriate only while a table meets every eligibility check: small footprint, short run time, low downstream ripple, no history to protect, a friendly source and calm capacity. For small reference tables it is the simplest correct answer, and the overwrite pattern is on the full load section.

A wider class of reloads is worth doing on large tables too, scoped to a table or a slice. Use them when most of these are true:

SituationWhy a reload is the right toolMechanism
Transformation logic changed historicallyA KPI or derivation (net versus gross, a reclassification) must apply to past data. Rebuild Silver deterministically from Bronze and leave Bronze untouchedFull rebuild, or period by period
Repartition or clustering refactorChanging the physical layout to fix scan cost is cleaner as a controlled rebuild than as in-place mutationRewrite into the new layout (see the partitioning playbook)
Snapshot restatementsA vendor restates a month or quarter. Prefer a slice rebuild, not a table-wide onereplaceWhere on the affected range
SCD1 only, or SCD2 rebuilt deliberatelyIf you are not preserving type-2 history, or are intentionally regenerating it, a rebuild is viable. Otherwise prefer MERGE incrementalsOverwrite or replaceWhere
Operational windowA safe window with low contention and clear duration and CU targets. If those degrade, pivot to incrementalSchedule outside peak; measure CU burn
 
# Parameters set by the pipeline for the restated period
month_start = "<first day of month>"      # e.g. yyyy-MM-01
month_end   = "<first day of next month>"

pred = f"order_date >= '{month_start}' AND order_date < '{month_end}'"

# build_silver_orders() is your deterministic Bronze-to-Silver transformation
rebuilt = build_silver_orders(spark.table("bronze.orders")).where(pred)

(rebuilt.write.format("delta")
    .mode("overwrite")
    .option("replaceWhere", pred)      # atomic; the write fails if any row falls outside the predicate
    .saveAsTable("silver.orders"))

replaceWhere replaces only the rows matching the predicate in one atomic commit and rejects the write if the DataFrame contains rows outside it, which is the safety net that keeps the blast radius to one slice. Dynamic partition overwrite (spark.sql.sources.partitionOverwriteMode=dynamic) does similar work implicitly for partitioned tables, but silently replaces whatever partitions the DataFrame happens to touch, so the explicit predicate is the safer habit.

Incremental upserts with Delta MERGE

MERGE is the workhorse of Bronze-to-Silver loading. It compares a source dataset (the new Bronze rows) with a target (the Silver table) on a join condition and runs different actions depending on whether a match is found.

WHEN MATCHED
The key exists in both. Typically UPDATE the Silver row with the new values, guarded so that only a newer version wins.
WHEN NOT MATCHED
The key exists in the source only. INSERT a new Silver row.
WHEN NOT MATCHED BY SOURCE
The key exists in the target only. Use it to DELETE or flag rows removed at the source, but only when the source is a complete snapshot. On an incremental batch it removes every row the batch did not mention.
from delta.tables import DeltaTable
from pyspark.sql import functions as F, Window

silver_cols = ["order_id", "customer_id", "order_date", "status", "total_amount", "modified_at"]
last_batch = 1041                         # from the watermark table (see Change tracking)

new_rows = spark.table("bronze.orders").where(F.col("_batch_id") > last_batch)

# 1. Exactly one row per key: the most recent version wins
w = Window.partitionBy("order_id").orderBy(F.col("modified_at").desc(), F.col("_ingest_ts").desc())
latest = (new_rows.withColumn("_rn", F.row_number().over(w))
                  .where("_rn = 1")
                  .select(*silver_cols))

# 2. Upsert; the guard makes reruns and out-of-order batches harmless
(DeltaTable.forName(spark, "silver.orders").alias("t")
    .merge(latest.alias("s"), "t.order_id = s.order_id")
    .whenMatchedUpdateAll(condition="s.modified_at > t.modified_at")
    .whenNotMatchedInsertAll()
    .execute())
-- latest_orders: temp view with exactly one row per order_id and exactly the Silver columns
MERGE INTO silver.orders AS t
USING latest_orders AS s
  ON t.order_id = s.order_id
WHEN MATCHED AND s.modified_at > t.modified_at THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *;

Rules that keep MERGE correct and cheap

ConcernWhat to do
Unique source keysIf several source rows match one target row, the merge fails. Deduplicate on the merge key first, as above. Also guard against NULL keys, and normalize case and whitespace in keys during cleansing.
Do not rewrite unchanged rowsCondition the update on a version column (modified_at) or a hash of tracked attributes, so replays and no-op updates do not rewrite files.
Reduce files scannedAdd a predicate on a partition or clustering column to the ON clause when that column cannot change for a given key (an order date, for instance). If it can change, pruning produces duplicates.
Write amplificationA merge rewrites every file that holds a changed row. Keep deletion vectors and auto compaction enabled where your runtime supports them, and align layout with how rows change (see the partitioning playbook). Check numTargetFilesRemoved in DESCRIBE HISTORY.
Concurrent writersTwo merges that touch the same files conflict, and one fails. Serialize them, or isolate them by a partition column that is part of the merge condition in both statements.
Schema evolutionNew source columns are ignored by default. If you want them added, enable schema auto-merge deliberately for the session and review what it adds; do not enable it globally.
IdempotencyThe same batch applied twice must give the same table. The version guard and a deterministic deduplication rule provide that.

Slowly changing dimensions (Type 2)

For many dimensions it is not enough to overwrite old values. Analyzing sales by the customer's address at the time of the order, not just the current one, needs history. Type 1 updates in place and loses history. Type 2 keeps it by:

  1. Expiring the old record. Mark the existing row as no longer current: set is_current = false and close its validity interval with a valid_to timestamp.
  2. Inserting a new record. Add a new row for the same business key with the changed attributes, valid_from set to the change time, valid_to empty and is_current = true.

A single MERGE can do both steps if you stage each changed row twice: once with the real business key (matches the current row and expires it) and once with a NULL merge key (never matches, so it inserts). New keys are staged only for insertion.

from datetime import datetime, timezone
from delta.tables import DeltaTable
from pyspark.sql import functions as F

tracked = ["customer_name", "email", "city", "segment"]
effective_ts = datetime.now(timezone.utc)          # one timestamp for the whole run

# 1. One row per customer from the new Bronze batch (deduplicated as in the upsert example), plus a hash
src = (latest_customers
        .withColumn("row_hash", F.sha2(F.concat_ws("||", *[F.coalesce(F.col(c).cast("string"), F.lit("")) for c in tracked]), 256)))

dim = DeltaTable.forName(spark, "silver.dim_customer")
current = dim.toDF().where("is_current").select("customer_id", F.col("row_hash").alias("current_hash"))

# 2. Keep only new customers and customers whose tracked attributes changed
changes = (src.join(current, "customer_id", "left")
              .where("current_hash IS NULL OR current_hash <> row_hash")
              .withColumn("is_new", F.col("current_hash").isNull())
              .drop("current_hash"))

# 3. Stage changed rows twice: keyed (to expire) and with a NULL key (to insert)
key_type = src.schema["customer_id"].dataType
to_expire = changes.where(~F.col("is_new")).withColumn("merge_key", F.col("customer_id"))
to_insert = changes.withColumn("merge_key", F.lit(None).cast(key_type))
staged = to_expire.unionByName(to_insert)

# 4. Expire and insert in one atomic MERGE
(dim.alias("t")
    .merge(staged.alias("s"), "t.customer_id = s.merge_key AND t.is_current = true")
    .whenMatchedUpdate(set={"is_current": F.lit(False), "valid_to": F.lit(effective_ts)})
    .whenNotMatchedInsert(values={
        "customer_id": "s.customer_id", "customer_name": "s.customer_name", "email": "s.email",
        "city": "s.city", "segment": "s.segment", "row_hash": "s.row_hash",
        "valid_from": F.lit(effective_ts), "valid_to": F.lit(None).cast("timestamp"),
        "is_current": F.lit(True)})
    .execute())

Rerunning the same batch finds no hash differences, so the job is idempotent. Query a version in force at a given time with the validity interval:

SELECT *
FROM silver.dim_customer
WHERE customer_id = 'C-1001'
  AND valid_from <= TIMESTAMP '<as_of_timestamp>'
  AND (valid_to IS NULL OR valid_to > TIMESTAMP '<as_of_timestamp>');
  • Effective time. The example uses load time. If the source carries a business effective date and changes can arrive late or out of order, use that date for valid_from and valid_to and process changes per key in effective-date order.
  • Surrogate keys. Writing Delta identity columns is not supported in Fabric Delta tables, so generate surrogate keys in code (for example a hash of business key and valid_from) and test for collisions.
  • Deletes. A source delete expires the current row (set valid_to and an is_deleted flag) rather than removing history.
  • Low-code alternatives. Dataflow Gen2 offers a visual route to SCD-style logic. Copy job offers a built-in SCD Type 2 write method for CDC sources, which is marked preview and has connector and schema constraints; check its documentation before relying on it. Code-first notebooks remain the better choice when you need custom matching rules or testing in CI.

Handling deletes

Propagating source deletions to Silver is one of the hardest parts of incremental loading, and the right approach depends entirely on the change detection mechanism you used at ingestion. A delete strategy that does not match the change signal produces a Silver table that quietly stops representing the source.

Change signalWhat Silver receivesDelete strategy
Soft delete flag in the sourceAn update with is_deleted = trueCarry the flag into Silver, or physically delete on the flag
Log-based CDCAn explicit delete event per deleted rowApply the delete event with MERGE ... THEN DELETE
WatermarkNothing: a deleted row simply stops appearingPeriodic full snapshot and a snapshot merge with WHEN NOT MATCHED BY SOURCE
Snapshot-only sourceA complete snapshot each timeThe same snapshot merge, on every load

Soft deletes

If the source flags rows as inactive instead of removing them, the delete arrives as an ordinary update and the merge handles it. You choose whether Silver keeps the flag (consumers filter on it) or removes the row.

MERGE INTO silver.orders AS t
USING latest_orders AS s
  ON t.order_id = s.order_id
WHEN MATCHED AND s.is_deleted = true THEN DELETE
WHEN MATCHED AND s.modified_at > t.modified_at THEN UPDATE SET *
WHEN NOT MATCHED AND s.is_deleted = false THEN INSERT *;

To keep the flag instead, drop the first clause and the condition on the insert clause; the is_deleted column then flows through UPDATE SET * like any other attribute. Keeping flagged rows is safer for audit; physical deletion is required when erasure obligations apply.

Hard deletes with CDC

When ingestion used log-based CDC, the change stream carries an explicit operation per row. Keep the last event per key, then apply deletes, updates and inserts in one merge.

from delta.tables import DeltaTable
from pyspark.sql import functions as F, Window

w = Window.partitionBy("order_id").orderBy(F.col("_commit_seq").desc())
cdc_latest = (events.withColumn("_rn", F.row_number().over(w)).where("_rn = 1"))   # last event per key

cols = {c: f"s.{c}" for c in silver_cols}

(DeltaTable.forName(spark, "silver.orders").alias("t")
    .merge(cdc_latest.alias("s"), "t.order_id = s.order_id")
    .whenMatchedDelete(condition="s.op = 'D'")
    .whenMatchedUpdate(set=cols)                          # remaining matches are inserts or updates
    .whenNotMatchedInsert(condition="s.op <> 'D'", values=cols)
    .execute())

Hard deletes with a watermark: the snapshot merge

A watermark cannot see deleted rows, so the only way to find them is to compare a complete source extract with Silver and remove the rows that are missing. That is a MERGE with WHEN NOT MATCHED BY SOURCE, where the source is the full extract. A watermark-based pipeline therefore needs a hybrid: frequent incremental merges for inserts and updates, plus a less frequent, heavier snapshot merge dedicated to deletes.

from pyspark.sql import functions as F

snap = spark.table("bronze.customers").where(
    (F.col("_batch_id") == full_batch_id) & (F.col("_load_type") == "full"))
snap.createOrReplaceTempView("full_snapshot")

silver_live = spark.table("silver.customers").where("NOT is_deleted")
snap_rows, live_rows = snap.count(), silver_live.count()
to_remove = silver_live.join(snap, "customer_id", "left_anti").count()

# Guards: never delete from an empty, implausibly small or implausibly destructive snapshot
if snap_rows == 0 or snap_rows < 0.9 * live_rows or to_remove > 0.1 * live_rows:
    raise ValueError(f"Snapshot rejected: {snap_rows} rows vs {live_rows} live; would remove {to_remove}")

spark.sql("""
MERGE INTO silver.customers AS t
USING full_snapshot AS s
  ON t.customer_id = s.customer_id
WHEN MATCHED AND s.row_hash <> t.row_hash THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *
WHEN NOT MATCHED BY SOURCE AND NOT t.is_deleted
  THEN UPDATE SET t.is_deleted = true, t.deleted_at = current_timestamp()
""")

Gate every delete clause

Run WHEN NOT MATCHED BY SOURCE only against a batch that is verified to be a complete snapshot: recorded _load_type = 'full', a manifest or control row confirming completeness, and sane row counts against the previous snapshot. Prefer flagging over physical deletion first, so a wrongly rejected snapshot can be undone with an update, not a restore. The thresholds above are examples; set them from your own table's normal variation.

Because Delta keeps previous versions, a bad delete can be reverted with RESTORE TABLE while the old files still exist, but that reverts every later commit too, so treat it as an emergency measure and rely on the guards.

Key takeaways

  • Deduplicate to one row per key and guard updates with a version comparison; that makes MERGE idempotent and safe against out-of-order data.
  • Use replaceWhere to rebuild a slice, because it is atomic and refuses rows outside the predicate.
  • Implement SCD2 with one MERGE using a double-staged source, a hash of tracked attributes, and an explicit effective time.
  • Match the delete strategy to the change signal: flags, CDC events, or a snapshot merge for watermark and snapshot sources.
  • Never run WHEN NOT MATCHED BY SOURCE on anything that is not a verified complete snapshot, and prefer soft deletion first.
