Data Load Strategy

A table-by-table framework for deciding how data enters and moves through a Fabric medallion lakehouse: when a destructive full reload is the right answer, when you need incremental loads, how to detect changes at the source, and which Fabric tool should do the work at each layer.

  • Audience data engineers, architects
  • Level intermediate
  • Reading time 80 min
  • Pages 8

Purpose and scope

How you load data decides three things you will live with for years: how fresh the data is, how much capacity the platform burns to keep it fresh, and how many ways the pipeline can quietly go wrong. A full reload is simple and self-healing but cost grows with table size. An incremental load is cheap per run but is only as correct as the change signal behind it. Most platforms need both, chosen per table.

This playbook gives you the decision logic and the implementation patterns for each medallion layer: Bronze (raw history), Silver (conformed current state) and Gold (business-ready models). It covers full versus incremental loads, change tracking (high-watermark, log-based CDC, mirroring, Copy job incremental modes, Delta change data feed), Delta MERGE upserts, slowly changing dimensions, delete handling, aggregate refresh, the way Direct Lake reacts to your write patterns, and a tool choice matrix for pipelines, Copy job, Dataflows Gen2, Spark and T-SQL.

It is a framework, not a rulebook. The medallion pattern is flexible, and the right answer depends on data volume, source capabilities, latency requirements, team skills and capacity budget. Each decision table in this playbook marks a recommended default and names the conditions under which you should depart from it.

The strategy in one picture

Every hop in the medallion flow has a default pattern. Departures from the default are deliberate, per-table decisions that the following pages walk through.

Six principles behind the framework

  1. Ask the source first

    The first design question is not "how do we build it" but "what change information does the source give us": log-based CDC, a reliable modified-timestamp or row version, or nothing but snapshots. If you skip this, you discover missing deletes in production.

  2. Bronze keeps what was delivered

    Append every delivery, whether it was a full extract or a delta, and tag it with a batch id and load type. Bronze is how you rebuild Silver and Gold when logic changes. A Bronze table that was updated in place cannot do that.

  3. Reconcile in Silver, not Bronze

    The Bronze-to-Silver step knows whether a batch is a delta or a complete snapshot, and applies MERGE, SCD2 and delete logic accordingly. Putting reconciliation in Bronze couples your archive to one interpretation of the data.

  4. Re-derive the smallest slice that is still correct

    In Gold, incremental does not have to mean clever arithmetic. Recomputing the affected dates or partitions from Silver and replacing just those is usually simpler, safer and fast enough.

  5. Make every load restartable

    Advance watermarks only after the write commits, make MERGE keys unique, and design so that re-running a batch produces the same result. Failures then cost a retry, not a repair.

  6. Decide per table, not per platform

    A 5,000-row country table does not justify an incremental pipeline. A billion-row fact table does not survive a nightly full reload. A healthy platform mixes patterns and records the choice for each table.

What you will be able to do

  • Classify every table as full-load or incremental using explicit thresholds rather than habit.
  • Select a change tracking mechanism from what the source exposes, and know what each one cannot see.
  • Implement append-only Bronze with batch metadata, including the mixed full-and-incremental feed case.
  • Write idempotent Delta MERGE upserts, an SCD Type 2 dimension and delete handling that matches the change signal.
  • Refresh Gold aggregates without drift, and avoid write patterns that force Direct Lake into cold reloads.
  • Choose between data pipelines, Copy job, Dataflows Gen2, Spark notebooks, T-SQL, mirroring and materialized lake views for each task.

Key takeaways

  • Pick the load pattern per table and per layer, and write the decision down next to the table.
  • Start every incremental design by asking what change signal the source provides.
  • Keep Bronze append-only, and do reconciliation, deduplication and delete handling in Silver.
  • In Gold, replace the affected slice instead of inventing incremental arithmetic, unless measures are purely additive.
  • Avoid write patterns that make Direct Lake reload everything, and verify what your tool actually writes.
