Playbook 02 · Data Load Strategy

Bronze layer patterns

Bronze is the raw, auditable foundation of the medallion architecture. The decisions you make here, files or Delta, append or replace, how you tag a batch, set what you can reprocess later and how complicated Silver has to be. This page covers the patterns and the metadata that make Bronze rebuildable.

Mandate: raw, immutable, auditable

Bronze ingests data from source systems in its original, unaltered form and keeps it as a historical archive. It is the single place from which Silver and Gold can be rebuilt if business logic changes or a defect is found downstream. To do that job, Bronze is treated as immutable and loaded append-only: every delivery from the source is kept, in the order it arrived, so a complete chronological record exists for audit, debugging and reprocessing.

Two practical consequences follow. First, Bronze holds what was delivered, which is not always what the source contains: a delta file is not a snapshot. Second, because Bronze is not the place for interpretation, it should be agnostic to how the source delivers data. Interpretation, such as "this batch is complete, so absent rows were deleted", belongs in Silver.

Landing as files vs loading into Delta tables

The foundational Bronze decision in a lakehouse is whether to keep raw data as files in the Lakehouse Files area (Parquet, CSV, JSON in their native form) or to load it straight into Delta tables in the Tables area.

ApproachStrengthsWeaknesses
FilesMaximum fidelity, a true 1:1 copy of the source. Resilient to schema drift, because validation is deferred to the Bronze-to-Silver step and ingestion does not fail on unexpected changes. Simple ingestion (often a plain copy) with clean separation between acquisition and transformation. Easy remediation: delete a failed batch's folder.Not directly queryable through the SQL analytics endpoint. Needs an extra step, usually Spark, to parse and load into a table format. No transactions, schema enforcement or time travel on the raw layer.
Delta tablesStructured and queryable immediately, useful for profiling and validation. Delta features from the first write: ACID transactions, time travel, schema enforcement, change data feed and streaming reads for incremental Silver loads.Parsing is already a first transformation, which slightly breaks the "pure raw" principle. Ingestion can be more fragile, failing when the source schema changes incompatibly. Remediating a bad append needs a plan (see below).

The landing zone pattern (pre-Bronze)

The trade-off between architectural purity and operational efficiency has a well-established resolution: do both. Extend the layer in two stages. The ingestion tool lands data as files in a dedicated landing area, which satisfies the requirement for a pure, replayable archive. A Spark step then reads those files and appends them to append-only Bronze Delta tables, which enables SQL access, time travel and efficient incremental processing into Silver. You get the audit and resilience of files plus the performance of tables.

Landing layout and conventions

Treat the landing area as an API between ingestion and processing. Predictable paths let any tool write and any notebook read, and let you tell full and incremental deliveries apart without opening a file.

Files/landing/<source_system>/<entity>/load_type=<full|incremental>/batch_id=<n>/part-0000.parquet

Files/landing/sales/orders/load_type=incremental/batch_id=1042/part-0000.parquet
Files/landing/sales/orders/load_type=full/batch_id=1050/part-0000.parquet
  • One batch, one folder. A batch id from the orchestrator, increasing and never reused, is the unit of load, replay and cleanup.
  • Encode the load type in the path. Silver needs to know whether a batch is a delta or a complete snapshot; do not make it infer that from row counts.
  • Prefer Parquet over CSV or JSON where the source allows. Keep the original format when bit-for-bit fidelity is a requirement.
  • Write a batch completely, then publish it. Land into a temporary name or write a completion marker so the notebook never reads a half-written batch.
  • Define a retention rule for landing files. Bronze Delta tables hold the processed history, so the landing area usually needs a shorter or archived retention, set by your audit requirements.

Appending a batch to Bronze

The notebook receives the batch id and load type as parameters from the pipeline, reads the batch folder, adds standard metadata columns and appends. The metadata columns are what let Silver deduplicate, order and interpret batches later.

from pyspark.sql import functions as F

# Parameters set by the pipeline
batch_id = 1042                  # monotonically increasing, assigned by the orchestrator
load_type = "incremental"        # 'full' or 'incremental'
landing_path = f"Files/landing/sales/orders/load_type={load_type}/batch_id={batch_id}/"

# Idempotency guard: skip if this batch is already in Bronze (keeps the table append-only)
if spark.catalog.tableExists("bronze.orders") and \
   spark.table("bronze.orders").where(F.col("_batch_id") == batch_id).limit(1).count() > 0:
    print(f"Batch {batch_id} already loaded; nothing to do")
else:
    raw = (spark.read.format("parquet").load(landing_path)
             .withColumn("_batch_id", F.lit(batch_id).cast("long"))
             .withColumn("_load_type", F.lit(load_type))
             .withColumn("_source_file", F.col("_metadata.file_path"))
             .withColumn("_ingest_ts", F.current_timestamp()))

    (raw.write.format("delta")
        .mode("append")
        .option("mergeSchema", "true")   # accept additive columns; fail on incompatible changes
        .saveAsTable("bronze.orders"))

Delta also supports idempotent writes through the txnAppId and txnVersion writer options, which make a repeated commit of the same version a no-op; see the Delta documentation if you prefer that to an explicit check. If the landing area receives a steady flow of files rather than orchestrated batches, a Structured Streaming file source with a checkpoint and trigger(availableNow=True) discovers each new file exactly once.

Standard metadata columns

ColumnPurpose
_batch_idUnit of load, ordering, replay and remediation; also the watermark for Bronze-to-Silver processing
_load_typefull or incremental; tells Silver whether absent rows can imply deletes
_ingest_tsWhen the row reached Bronze; breaks ties when the same key arrives more than once
_source_fileRow-level lineage back to the landed file
_source_systemNeeded when several systems feed one conformed entity

Loading patterns for Bronze

The loading pattern follows from Bronze's role: preserve a complete historical record.

PatternVerdictDetails
Incremental appendDefault, recommendedAll incoming data, whether it came from a full or an incremental extraction, is appended. Nothing in Bronze is updated or deleted. Files go to a new folder per batch; Delta tables use append mode. The result is a re-playable log of what the source delivered over time.
Full reload (truncate or drop and reload)Generally discouragedIt destroys the previous state and breaks the archive principle. Acceptable for very small, non-volatile reference tables where history is explicitly not required, and for transient staging tables that are not part of the permanent archive.
Merge or SCD2 in BronzeAvoid, or label honestlyReconciling in Bronze couples the archive to one interpretation. If your ingestion tool already writes with merge or SCD Type 2 (Copy job can), that table is a current-state or history replica rather than a raw archive. Either accept that and document it, or add an append-only landing zone in front of it.

Handling mixed full and incremental source feeds

A common real-world situation: a source sends daily incremental files containing only new and changed records, plus a periodic full file that represents the complete table. The problem appears when reconciliation logic built for full extracts meets a small incremental file. A MERGE with WHEN NOT MATCHED BY SOURCE THEN DELETE treats every row missing from the small file as deleted, and wipes the target.

  1. Segregate at ingestion

    Use separate folders or metadata tags to distinguish full from incremental files, as in the landing convention above. This gives downstream logic the context it needs.

  2. Append everything to Bronze

    Whatever the file type, append it to the Bronze store, preserving the raw history of every delivery.

  3. Defer reconciliation to Silver

    The Bronze-to-Silver job reads _load_type and applies the matching logic: an upsert for incremental batches, and a full-snapshot merge that also removes missing rows for complete files. The code is on the Silver page.

This separation keeps Bronze a simple, pure archive while Silver holds the business logic that consolidates the feeds into one accurate current state.

Remediating a bad batch

Because each batch is tagged and written to its own files, undoing a bad load is routine, but the method depends on where the batch lives.

WhereRemediationNotes
Landing filesDelete the batch folder and re-landNothing else is affected
Bronze Delta tableDELETE FROM bronze.orders WHERE _batch_id = <n>Cheap when each batch occupies its own files. It writes a delete commit, so streaming readers of Bronze need to be configured to skip change commits
Bronze Delta table (nothing else has written since)RESTORE TABLE bronze.orders TO VERSION AS OF <v>Reverts everything after that version, so use it only when no other batch has committed
Silver already processed the bad batchFix Bronze, then rebuild the affected Silver keys or partitionsThis is the case Bronze immutability exists for

Table settings and layout for Bronze

Bronze is write-heavy and rarely queried interactively, so tune for ingestion. Do not partition by default: a small daily append into many partitions produces small files, and Fabric guidance is to avoid partitioning unless a specific requirement justifies it (see the Delta partitioning playbook). Enable auto compaction so small appends are consolidated without a separate job, and do not rely on V-Order for Bronze; it benefits read-heavy consumption, mainly Direct Lake on Gold. Avoid building Direct Lake models directly on raw Bronze tables unless you have designed the model and data shape for that.

Protect sensitive values in Bronze

Raw means raw: Bronze may hold personal, financial or health data exactly as received. Keep identifiers out of folder and partition names, restrict Bronze workspace access to the pipelines and engineers who need it, and plan retention and erasure (for example DELETE by key followed by VACUUM) before the first load, not after the first request.

Key takeaways

  • Land raw files first, then append them to Bronze Delta tables; each stage has one job.
  • Append every delivery with _batch_id, _load_type, _ingest_ts and _source_file; never update Bronze in place.
  • Encode full versus incremental in the landing path so Silver never has to guess.
  • Never apply "delete what is missing" logic to a batch that is not a verified full snapshot.
  • Make loads idempotent and remediation a DELETE by batch id, not a rebuild.
