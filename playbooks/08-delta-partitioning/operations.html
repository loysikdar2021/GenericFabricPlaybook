Playbook 08 · Delta Partitioning

Validation and operations

A layout is only as good as its maintenance. This page shows how to measure file and partition health, confirm that pruning works, diagnose the common problems, and run maintenance on a cadence that matches each class of table.

Measure layout health

Start with the table's own metadata. DESCRIBE DETAIL reports the file count, total size, partition columns, clustering columns and table properties, including the evaluated delta.targetFileSize.adaptive target. DESCRIBE HISTORY shows every commit with its operation metrics, which is how you see what a write, merge or OPTIMIZE actually did.

DESCRIBE DETAIL  silver.orders;   -- numFiles, sizeInBytes, partitionColumns, clusteringColumns, properties
DESCRIBE HISTORY silver.orders;   -- operation, operationMetrics (files added and removed, rows written)
details = spark.sql("DESCRIBE DETAIL silver.orders").first()

size_gb  = details["sizeInBytes"] / 1024**3
n_files  = details["numFiles"]
avg_mb   = details["sizeInBytes"] / n_files / 1024**2 if n_files else 0
target   = details["properties"].get("delta.targetFileSize.adaptive", "not evaluated")

print(f"{size_gb:.1f} GB in {n_files} files, average {avg_mb:.0f} MB (adaptive target: {target})")

An average can hide skew between partitions or between recent and previously compacted files, so follow up with a per-partition view. The script below lists the data files of each partition directory and reports how many there are and how large they are.

import pandas as pd

table = "silver.orders"
root = spark.sql(f"DESCRIBE DETAIL {table}").first()["location"]

rows = []
def walk(path, label=""):
    entries = notebookutils.fs.ls(path)
    files = [e for e in entries if not e.isDir and e.name.endswith(".parquet")]
    if files:
        rows.append((label or "(root)", len(files), sum(f.size for f in files)))
    for d in entries:
        if d.isDir and not d.name.startswith("_"):          # skip _delta_log
            walk(d.path, f"{label}/{d.name.rstrip('/')}" if label else d.name.rstrip("/"))

walk(root)

report = pd.DataFrame(rows, columns=["partition", "files", "bytes"])
report["gb"] = report["bytes"] / 1024**3
report["avg_file_mb"] = report["bytes"] / report["files"] / 1024**2
print(report.sort_values("avg_file_mb").head(20).to_string(index=False))
print(f"Partitions: {len(report)}; listed files: {report['files'].sum()}")

Listing is not the table

The script lists storage, which can include files that the current table version no longer references and that VACUUM has not yet removed. Treat it as a diagnostic and compare the file total with numFiles from DESCRIBE DETAIL.

Confirm that pruning and skipping work

Layout is only useful if queries benefit from it. Read the physical plan and look for the partition filters on the scan, then compare the files the scan read with the table's total.

spark.sql("""
EXPLAIN FORMATTED
SELECT SUM(amount) FROM silver.orders WHERE order_month = '2026-03'
""").show(truncate=False)
# In the FileScan node, look for PartitionFilters on order_month,
# and compare "number of files read" in the Spark UI with numFiles from DESCRIBE DETAIL.
  • Liquid clustered tables. From Runtime 2.0 the Scala clusteringQuality() method reports per-column overlap and estimated skipping effectiveness. Compare before and after OPTIMIZE, and validate against files scanned in the Spark UI.
  • Direct Lake. Use Delta Analyzer (a notebook, also in the semantic-link-labs library) to see row groups, files and the effect of updates, and a DAX query over INFO.STORAGETABLECOLUMNSEGMENTS() after a load to check whether segments were reused.
  • SQL analytics endpoint. Where auto compaction is not used, the sys.sp_get_table_health_metrics stored procedure identifies tables that need OPTIMIZE.
  • Write blast radius. In DESCRIBE HISTORY, compare files removed with files added for each MERGE, UPDATE or DELETE. A small change that removes many files signals a layout that does not match the write pattern.

Health signals and what to do

Treat these as indicators to investigate, not universal thresholds: validate them against the table's write pattern and its consumers' performance.

Triage for small files

Keep the SQL analytics endpoint in step

The SQL analytics endpoint reads the same Delta tables as Spark, kept in step by a background metadata sync. Normally the lag is under a minute, but spikes in file or partition counts lengthen it. Watch sync time alongside file counts after large loads, schedule regular maintenance rather than relying on the sync to cope, and use the on-demand metadata sync or the refresh SQL endpoint metadata REST API when a downstream step must see the latest commit. Not every Delta feature is supported by the automatic sync, so check the Delta Lake interoperability page before adopting a new layout feature on tables the endpoint serves.

Operations cadence

Match maintenance to how the table is written and read. The cadence below is a starting point: automatic compaction does the continuous work, and scheduled jobs handle what needs a window.

Table classCompactionLayoutVACUUM and refresh
Bronze, append-only, high volumeAuto compaction and optimize writeV-Order not needed; partition by ingest month only if retention or writers justify itVACUUM on the retention policy
Silver, mergedAuto compaction, deletion vectors on; periodic OPTIMIZE to purge themPartition column in merge conditions; Z-Order or clustering for secondary filtersVACUUM weekly to monthly
Gold read by Direct LakeScheduled OPTIMIZE at quiet times, scoped to recent partitionsV-Order on; row groups of 1 to 16 million rowsRetention longer than the framing gap; refresh the model after maintenance
Liquid clustered, Runtime 2.0Auto compaction or OPTIMIZE after loadsCheck clusteringQuality(); OPTIMIZE FULL only after changing keysVACUUM on the retention policy

Maintenance can be run from the Lakehouse maintenance experience, from a pipeline Lakehouse maintenance activity, from notebooks, or through the Lakehouse REST API, so it can be orchestrated alongside the loads that create the files.

Layout checklist

  • The decision tree was walked and the answer recorded next to the table: unpartitioned, partitioned (with the reason) or clustered.
  • If partitioned: the partition column is low-cardinality, stable, known at write time, and each partition is at least about 1 GB.
  • Partition values contain no sensitive identifiers, and null or malformed values are rejected before the write.
  • Optimize write and auto compaction are on for Spark-written tables, or a scheduled OPTIMIZE exists where write latency rules them out.
  • V-Order is enabled on tables Direct Lake reads and not forced elsewhere without a reason.
  • Merge and update conditions include the partition column, and concurrent writers have a bounded retry.
  • Large Direct Lake tables are updated by append or slice replacement, and OPTIMIZE is scoped and scheduled for quiet periods.
  • VACUUM retention exceeds the longest gap between model refreshes and the time-travel requirement.
  • A file health report runs on a schedule, with owners for the signals it raises, and a quarterly review of layout decisions is on the calendar.

Key takeaways

  • Measure before you tune: file count, average file size against the adaptive target, per-partition size and the plan's partition filters.
  • Compare files removed and added in DESCRIBE HISTORY to see the real blast radius of each write.
  • Compaction repairs small files, but only a layout of right-sized partitions stops them from being created.
  • Scope OPTIMIZE to recent partitions for Direct Lake tables, and keep VACUUM retention longer than the framing gap.
  • Writers that bypass Spark defaults, such as pipelines and dataflows, need their own scheduled maintenance.
  • Review layout decisions regularly: tables outgrow their partition schemes.
