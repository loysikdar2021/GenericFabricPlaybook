Playbook 08 · Delta Partitioning

Implementation examples

The code behind the decisions: creating partitioned and clustered tables, appending with sensible settings, replacing one slice atomically, running concurrent merges that do not collide, and changing a layout without taking the table offline.

The examples use a neutral orders domain: silver.orders partitioned by order_month, a gold.sales table for clustering and a bronze.device_events table for telemetry. Table names, columns and settings are illustrative; adapt them to your standards. Run the examples in a notebook attached to a lakehouse on Fabric Runtime 2.0, unless a note says otherwise.

Create tables

A partitioned table

Declare the partition column as part of the schema. For a monthly grain, add a derived order_month column rather than partitioning by the raw date, and enable the write-time features that keep partitioned writes healthy.

CREATE TABLE silver.orders (
    order_id    BIGINT,
    customer_id BIGINT,
    order_ts    TIMESTAMP,
    order_date  DATE,
    order_month STRING,          -- 'YYYY-MM', derived by the pipeline
    region      STRING,
    status      STRING,
    amount      DECIMAL(18,2)
)
USING DELTA
PARTITIONED BY (order_month)
TBLPROPERTIES (
    'delta.autoOptimize.optimizeWrite' = 'true',
    'delta.autoOptimize.autoCompact'   = 'true'
);
-- Daily partitions are reasonable here only because each day holds tens of GB
CREATE TABLE bronze.device_events (
    event_id    STRING,
    device_id   STRING,
    event_ts    TIMESTAMP,
    event_date  DATE,
    payload     STRING
)
USING DELTA
PARTITIONED BY (event_date)
TBLPROPERTIES (
    'delta.autoOptimize.optimizeWrite' = 'true',
    'delta.autoOptimize.autoCompact'   = 'true'
);

A liquid clustered table

When the goal is faster selective reads rather than writer isolation, cluster instead of partitioning. Clustering is applied by OPTIMIZE, so schedule it or rely on auto compaction on Runtime 2.0.

CREATE TABLE gold.sales (
    order_id    BIGINT,
    order_date  DATE,
    region      STRING,
    product_id  BIGINT,
    amount      DECIMAL(18,2)
)
CLUSTER BY (order_date, region)
TBLPROPERTIES (
    'delta.parquet.vorder.enabled'     = 'true',     -- Direct Lake reads this table
    'delta.autoOptimize.autoCompact'   = 'true'      -- Runtime 2.0 or later
);

Pick one scheme per table

A table cannot be both partitioned and liquid clustered. Combining PARTITIONED BY with CLUSTER BY is not supported, and Z-Order is also incompatible with clustering. On Runtime 1.3, do not pair clustering with auto compaction.

Append with the right settings

Appends are the friendliest write pattern: they add files and leave existing ones alone. Derive the partition column in the pipeline so every row lands in the right directory, and set the session options that suit the table.

from pyspark.sql import functions as F

# Session hints; adjust per workload. For a Gold table read by Direct Lake:
spark.conf.set("spark.sql.parquet.vorder.default", "true")
# Optimize write is not on by default under the writeHeavy profile; set it explicitly
spark.conf.set("spark.databricks.delta.optimizeWrite.enabled", "true")

(df_new_orders                                          # columns include order_date
    .withColumn("order_month", F.date_format("order_date", "yyyy-MM"))
    .write.format("delta")
    .mode("append")
    .partitionBy("order_month")                         # must match the table's existing partitioning
    .saveAsTable("silver.orders"))
  • When appending to an existing partitioned table, partitionBy must match the table or be omitted; a mismatch fails.
  • Check for a null or malformed partition value before the write. A single bad date creates a stray partition such as order_month=__HIVE_DEFAULT_PARTITION__.
  • V-Order applies to files written in this session when the session setting is on, and to the table's future writes when the table property is set.

Replace one slice atomically

To rebuild one month, use replaceWhere. It replaces only the rows matching the predicate, in a single atomic commit, and leaves every other file untouched, which is exactly what keeps Direct Lake's loaded data valid for the other months.

(df_feb2026                                              # only rows for 2026-02
    .write.format("delta")
    .mode("overwrite")
    .option("replaceWhere", "order_month = '2026-02'")
    .saveAsTable("silver.orders"))
ApproachBehaviorUse whenCaution
replaceWhereReplaces rows matching an explicit predicate in one atomic commit; works on partitioned and unpartitioned tablesRebuilding a month, a date range or a region from a recomputed DataFrameRows in the DataFrame outside the predicate are rejected by default, which is a useful safety check
Dynamic partition overwriteReplaces every partition that appears in the DataFrame, with no explicit predicateA job that always writes complete partitionsOne stray row from another month silently replaces that whole month. Partitioned tables only; not combinable with replaceWhere
MERGERow-level upsert and deleteChanges are a small share of each partitionInclude the partition column in the condition
DELETE then appendTwo separate commitsAlmost neverReaders can see the gap between the commits; use replaceWhere instead
 
spark.conf.set("spark.sql.sources.partitionOverwriteMode", "dynamic")

# insertInto matches columns by position, so select in the table's column order
cols = spark.table("silver.orders").columns
df_month.select(*cols).write.mode("overwrite").insertInto("silver.orders")

Run merges concurrently without conflicts

Two merges into one table can proceed side by side when each targets a different partition and says so in the condition. Both the target and the source predicate belong in the ON clause, as literals or parameters, not only in the source data.

-- Table is partitioned by region
MERGE INTO silver.orders_by_region AS t
USING staged_orders_emea AS s
   ON t.order_id = s.order_id
  AND t.region   = 'EMEA'
  AND s.region   = 'EMEA'
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *;
import time
from delta.tables import DeltaTable

def merge_region(region: str, source_df, attempts: int = 3):
    target = DeltaTable.forName(spark, "silver.orders_by_region")
    for i in range(attempts):
        try:
            (target.alias("t")
                .merge(source_df.alias("s"),
                       f"t.order_id = s.order_id AND t.region = '{region}' AND s.region = '{region}'")
                .whenMatchedUpdateAll()
                .whenNotMatchedInsertAll()
                .execute())
            return
        except Exception as e:
            # Concurrent-modification exceptions name themselves in the message
            if "Concurrent" not in str(e) or i == attempts - 1:
                raise
            time.sleep(5 * (i + 1))                      # back off, then retry the whole merge
  • Without the partition column in the condition Delta cannot prove the file sets are disjoint, and the second commit can fail even though the rows differ.
  • Partitioning removes conflicts between disjoint slices, not all conflicts. Schema changes, OPTIMIZE over the same files and writers that overlap on a partition can still collide, so keep a bounded retry.
  • Pruning is a free benefit. The same predicate lets a single merge read only the target files it needs, even with no concurrency.

Change a layout with a rewrite

Delta does not support changing partition columns in place. Moving from daily to monthly partitions, from one partition column to another, or between partitioning and liquid clustering is a rewrite. Treat it as a planned operation with validation, not an overwrite you run and hope for.

CREATE TABLE silver.orders_v2
USING DELTA
PARTITIONED BY (order_month)
AS
SELECT *, date_format(order_date, 'yyyy-MM') AS order_month
FROM   silver.orders_v1;                  -- previously partitioned by order_date
SELECT
  (SELECT COUNT(*) FROM silver.orders_v1)                    AS old_rows,
  (SELECT COUNT(*) FROM silver.orders_v2)                    AS new_rows,
  (SELECT SUM(hash(order_id, amount)) FROM silver.orders_v1) AS old_checksum,
  (SELECT SUM(hash(order_id, amount)) FROM silver.orders_v2) AS new_checksum;
-- Partitioning and clustering are incompatible, so write a new, clustered table
CREATE TABLE silver.orders_clustered
CLUSTER BY (order_date, region)
AS
SELECT order_id, customer_id, order_ts, order_date, region, status, amount   -- order_month dropped
FROM   silver.orders;

OPTIMIZE silver.orders_clustered;          -- applies the clustering
  • Switching consumers means repointing notebooks, pipelines, SQL views and semantic models, then reframing any Direct Lake model that read the old table. Use a short freeze on writes, or load the new table in parallel until the last batch is reconciled.
  • Unpartitioned to clustered needs no rewrite: ALTER TABLE ... CLUSTER BY (...) followed by OPTIMIZE reorganizes files over time.
  • Keep partitioning, add skipping: on an existing partitioned table, Z-Order within recent partitions instead of changing the scheme: OPTIMIZE silver.orders WHERE order_month >= '2026-01' ZORDER BY (region).
  • Retire the old table only after its retention period has passed and consumers have run cleanly on the new one.

Verify against Microsoft Learn

The documentation states that partitioning and liquid clustering are incompatible and that changing partition columns needs a full rewrite. Behavior at the edges, such as the error returned when you try to add clustering to a partitioned table, can vary by runtime, so test on a scratch table. See Partitioning for Delta tables and Liquid clustering.

Key takeaways

  • Derive the partition column in the pipeline, keep partitionBy consistent with the table, and guard against null or malformed partition values.
  • Use replaceWhere to rebuild a slice atomically; avoid dynamic partition overwrite unless every write is a complete partition set.
  • Put the partition column in the MERGE condition for pruning and for concurrent merges, and keep a bounded retry for the conflicts that remain.
  • Changing a partition scheme is a rewrite: write a new table, validate, switch, then retire the old one.
  • Moving from partitioning to liquid clustering is also a rewrite; moving an unpartitioned table to clustering is not.
