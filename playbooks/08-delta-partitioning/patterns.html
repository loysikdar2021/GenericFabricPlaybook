Playbook 08 · Delta Partitioning

Patterns by layer and consumer

Bronze, Silver and Gold describe the purpose of data, not the layout it needs. This page turns the principles into layout recommendations for each layer, explains what Direct Lake, the SQL analytics endpoint and Warehouse each ask of a table, and works through neutral examples.

Layout by medallion layer

The medallion layers do not determine whether a layout is user-managed or system-managed, and they do not require a separate copy of a table for each consumer. Use one shared table where its requirements are compatible, and let the layer tell you the priority: write throughput in Bronze, reuse in Silver, read performance in Gold.

Bronze: landing and raw history

  • Default to no partitioning. Bronze is append-heavy, so the priority is write throughput. Optimize write and auto compaction keep the file count in check.
  • Ingest-month partitions (for example ingest_month) are a good choice when retention is by month and old months are dropped with a partition-aligned DELETE, or when several source-specific pipelines write to one table. They are simple and robust, and they accept late or messy data safely because the partition value comes from the load, not the content.
  • A trusted event date (for example event_month) is acceptable only if it is always present and always valid. A null or wildly wrong date in a partition column creates stray partitions.
  • Never partition by a sensitive identifier. Partition values become folder names that appear in storage listings.
  • Avoid building Direct Lake models directly on raw Bronze tables unless you have deliberately shaped the data for that use. Bronze is for fidelity and throughput, not serving.

Silver: conformed, reusable data

  • Partition by the business time that drives most filters, but only when each partition is large enough: order_month for orders, posting_month for ledger entries, event_date for very high-volume telemetry.
  • Otherwise cluster. If the table is smaller than the partition arithmetic allows, or the dominant filter is a high-cardinality column, use liquid clustering on one to four filter columns instead (Runtime 2.0 and later).
  • Two-level schemes (a month plus a coarse region) only if they meaningfully reduce scans and every combination still holds about 1 GB. Cardinality multiplies, so confirm the count first.
  • Put the partition column in the MERGE condition. It lets Delta prune target files, and it is the requirement for concurrent merges to run side by side. See Implementation examples.
  • Reuse the table across consumers where compatible, and enable V-Order only when Direct Lake is a primary consumer.

Gold: serving

  • Keep partitioning minimal, often none and at most a month. Small aggregate tables should be unpartitioned.
  • Favor file layout over more partitions: V-Order on tables that Direct Lake reads, regular OPTIMIZE, and liquid clustering or Z-Order on the hot predicates (for example region or product category) for the Spark and SQL consumers.
  • Update by append or by replacing a slice, so Direct Lake can reuse what it has already loaded. See the Gold layer and Direct Lake page of the data load playbook.
  • Prefer Gold for Direct Lake semantic models. It is the layer shaped for dimensional queries and the layer where you control the layout.

Direct Lake

Direct Lake loads whole columns from Delta tables into memory on demand, and the physical layout decides how fast that is and how much has to be reloaded after an update. Row groups become column segments in the semantic model, so many tiny row groups mean many tiny segments and many Parquet dictionaries to merge. Direct Lake does not use Delta or Parquet statistics to skip files or row groups while loading, so layouts built purely for skipping, such as clustering, do not speed up the load itself.

Reconcile this with "avoid partitioning"

The two statements are consistent. Fabric guidance says to avoid partitioning by default because it is costly, and to use it where a specific requirement justifies the cost. Bounding rewrites for a large Direct Lake table that gets rolling-window deletes or updates is such a requirement. An append-only fact table is not.

SQL analytics endpoint

Every lakehouse has a SQL analytics endpoint that a background process keeps in sync with the Delta tables. Under normal conditions the lag is under a minute, but it grows with the number of files and partitions the process has to scan. Parquet files are immutable, so updates and deletes add files over time, and without maintenance that adds read overhead and slows the sync.

  • Avoid high-cardinality partition columns. Choose a column that produces partitions close to or greater than 1 GB.
  • Maintain the tables. Auto compaction or scheduled OPTIMIZE keeps file counts down; VACUUM reclaims storage but does not improve the active layout.
  • Do not over-tune for it. The endpoint performs well on the same adaptive layout as Spark. Do not set static target file sizes, arbitrary row limits or V-Order solely for its benefit.
  • Force a refresh when you must. If a downstream step needs the latest commit, start an on-demand metadata sync from the portal or use the refresh SQL endpoint metadata REST API instead of waiting.
  • Find tables that need care. The sys.sp_get_table_health_metrics stored procedure helps identify tables for maintenance when you are not using auto compaction.

Warehouse

Fabric Data Warehouse manages its own physical layout and compaction. You do not choose Hive-style partitions for Warehouse tables. Keep the default V-Order setting for read-oriented and mixed workloads, and consider data clustering (Preview) for large tables with recurring selective predicates. When a Warehouse reads Lakehouse tables through the SQL analytics endpoint or shortcuts, the lakehouse layout guidance on this page applies to those tables.

Why the telemetry example partitions by day

Daily partitions fail for a modest table because they dip below 1 GB. They are reasonable here because each day holds tens of gigabytes. The rule is the size per partition, not the calendar unit. Always run the sizing arithmetic with your own volumes.

Key takeaways

  • Bronze optimizes for writes, Silver for reuse and merges, Gold for reads; partition least where reads matter most.
  • Put the partition column in MERGE conditions for pruning and for concurrent merges.
  • Direct Lake wants large row groups, V-Order and append-friendly updates; a low-cardinality partition is justified only to bound batch rewrites.
  • The SQL analytics endpoint needs a small, healthy file and partition count; do not over-tune for it.
  • Warehouse tables use system-managed layout and optional data clustering, not Hive partitions.
  • Judge a grain by size per partition, not by calendar unit.
