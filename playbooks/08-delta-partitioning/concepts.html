Playbook 08 · Delta Partitioning

Why and when to partition

Partitioning trades flexibility for the ability to skip, isolate and bound work. This page explains what you gain, what you pay, how to check the arithmetic before you commit, and why concurrent writers are now the main reason to partition at all.

What partitioning does

Hive-style partitioning divides a Delta table into physical subdirectories by the values of one or more partition columns. Each distinct value (or combination of values) gets its own directory, such as order_month=2026-03/. When a query filters on the partition column, the engine reads only the matching directories. This is partition pruning, and it can cut both latency and cost.

Pruning only happens when the query filters on the partition column itself. A predicate on a different column, or a function applied to a column, does not prune partitions even if it selects the same rows logically.

-- Prunes: the predicate is on the partition column
SELECT SUM(amount) FROM silver.orders WHERE order_month = '2026-03';

-- Does not prune: order_month is not in the predicate
SELECT SUM(amount) FROM silver.orders
WHERE date_format(order_date, 'yyyy-MM') = '2026-03';

What you gain, and what you pay

What partitioning buys

  • Pruning for queries that filter on the partition column
  • Concurrent-writer isolation: operations on different partitions touch different files and do not conflict
  • Bounded rewrites: an update, delete or OPTIMIZE limited to one partition leaves the rest untouched
  • Cheap retention: a DELETE that matches whole partitions removes files without rewriting data

What partitioning costs

  • At least one file per partition touched by every write, which breeds small files
  • More row groups and files, which strains Direct Lake and SQL endpoint metadata sync
  • A rigid scheme: partition columns cannot change without rewriting the table
  • Skew: uneven partitions give uneven task sizes and uneven performance

For read performance alone, current Fabric guidance prefers liquid clustering over partitioning: it avoids the small-file risk of high-cardinality columns and lets you change the clustering columns later. Partitioning remains the right tool when you need the isolation and bounded rewrites in the left column. See Fabric layout features.

Size partitions before you create them

Two rules of thumb from the Fabric documentation keep partitioned tables healthy: the partition column should have low to moderate cardinality (tens to hundreds of distinct values, not thousands), and each partition should hold at least about 1 GB of data. Larger tables can accommodate more partitions. Older Delta guidance often adds a total-size floor of roughly 1 TB below which partitioning is not worth it; treat that as a rough hint, because the per-partition target is the figure that actually protects you from small files.

The check is simple arithmetic: divide the table's size by the number of partitions a granularity would create.

Run the same check against reality, not intention. The snippet below counts the distinct values a candidate column would create and divides the table size by that count.

from pyspark.sql import functions as F

table = "silver.orders"
candidate = F.date_format("order_date", "yyyy-MM")        # the grain you are considering

detail = spark.sql(f"DESCRIBE DETAIL {table}").first()
size_gb = detail["sizeInBytes"] / 1024**3

partitions = spark.table(table).select(candidate.alias("p")).distinct().count()
print(f"{partitions} partitions, about {size_gb / partitions:.2f} GB each (target: 1 GB or more)")

Files, not just partitions

Each write creates at least one file in every partition it touches. A single batch containing late-arriving rows that span 24 months creates at least 24 files, which may each be tiny. Partition size is necessary but not sufficient: the write pattern decides whether partitions stay healthy.

Concurrent-writer isolation

Delta Lake uses optimistic concurrency control. Two operations that rewrite the same files conflict, and one of them fails or must retry. Concurrent appends generally do not conflict, but updates, deletes and merges can, even when they logically modify different rows, because the engine works at file granularity.

Partitioning makes it possible for concurrent operations to touch disjoint file sets. Two MERGE operations on a table partitioned by region do not conflict as long as each targets a different region and the partition column is stated explicitly in the merge condition. Having the column in the source data is not enough; Delta can only prove the operations are disjoint if the condition itself says so.

That is why Fabric now frames concurrent-writer isolation as the primary reason to partition. Use it for scenarios such as several pipelines processing different business units or regions into one table at the same time. If your pipelines run one after another, or each writes its own table, you do not need it.

Choosing the partition column

  • The column is filtered on, or written by one writer at a time, in the large majority of operations.
  • Its cardinality is low to moderate: tens to hundreds of values, with each value holding at least about 1 GB.
  • Its values are stable. A column whose value changes after the row is written forces rows to move between partitions.
  • Its values are known at write time, since the partition is chosen as the file is written.
  • It does not expose sensitive values: directory names appear in storage paths and listings, so never partition by a person, account or device identifier.

Key takeaways

  • Partition pruning only helps queries that filter on the partition column itself.
  • Size first: table size divided by partition count should be at least about 1 GB, and the count should be tens to hundreds.
  • A month is the usual grain for time-series tables; daily partitions need roughly 1 GB a day.
  • Concurrent-writer isolation works only if the partition column appears in the operation's condition.
  • Never partition by identifiers or by columns whose values change after the row is written.
