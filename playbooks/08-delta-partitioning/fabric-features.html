Playbook 08 · Delta Partitioning

Fabric layout features

Partitioning is only one of several layout controls. Fabric adds write-time features, automatic compaction, adaptive file sizing and liquid clustering, and most of the time they do more for you than partition columns can. This page explains what each one does, which combine and what changes with the runtime.

Three moments, three kinds of feature

Layout features act at different times. Knowing which moment a feature acts at tells you where its cost lands and what it cannot fix.

V-Order and resource profiles

V-Order is a write-time optimization for Parquet files. It reorganizes row-group distribution, encoding and compression to improve read efficiency across Fabric engines, and it pays off most in read-heavy patterns such as dashboards and repeated scans. Files remain open-source Parquet, and Delta features such as Z-Order stay compatible. The usual trade-off is slower writes, often around 15 percent on average.

V-Order is disabled by default in new workspaces. New workspaces use the writeHeavy resource profile, which favors ingestion. Enable V-Order deliberately for tables that Direct Lake reads; it is not needed for Spark or SQL analytics endpoint performance alone.

V-Order can be controlled at three levels. A session setting applies to every Parquet write in the session; a table property sets a table default for future INSERT, UPDATE and MERGE writes; and a DataFrame writer option controls a single write. Changing a setting affects only future writes: existing files keep the ordering they were created with until compaction rewrites them.

-- Session level: all Parquet writes in this session
SET spark.sql.parquet.vorder.default = TRUE;

-- Table level: future INSERT, UPDATE and MERGE writes to this table
ALTER TABLE gold.daily_sales SET TBLPROPERTIES ('delta.parquet.vorder.enabled' = 'true');

-- Rewrite existing files with V-Order applied
OPTIMIZE gold.daily_sales VORDER;
spark.conf.set("spark.fabric.resourceProfile", "readHeavyForPBI")   # V-Order on, 1 GB optimize-write bins

Other writers

The Copy activity in data pipelines writes Lakehouse tables with V-Order applied by default, with an option to turn it off, so tables loaded by Spark and by Copy can differ in layout even in the same workspace. Check the layout of each writer's output. Note also that in Fabric Runtime 1.3 and later the older spark.sql.parquet.vorder.enable setting is removed; use the settings above.

Optimize write

Optimize write does pre-write compaction: it shuffles in-memory data into optimally sized bins before Spark writes the Parquet files, so the write produces fewer, larger files without a cleanup step afterwards. The shuffle costs time, so use it selectively. It is most valuable for:

  • Partitioned tables, where each write otherwise creates at least one file per partition touched
  • Tables with frequent small inserts, including streaming and micro-batch writes
  • Operations that touch many files, such as MERGE, UPDATE and DELETE

Do not assume optimize write is on. Its default depends on the resource profile, as the table above shows, and tables written by pipelines or dataflows do not inherit Spark session settings at all.

Adaptive target file size

Fabric can choose the target file size per table, so you do not have to tune it by hand. Adaptive target file size estimates the ideal size from table heuristics such as total size and updates it as the table grows: tables under about 10 GB target 128 MB files, scaling linearly up to 1 GB for tables beyond about 10 TB. Small tables thereby keep enough files to benefit from file skipping, and large tables keep files big enough to avoid metadata overhead.

  • Where it applies. It is evaluated at CREATE TABLE AS SELECT, overwrite writes, writes that create a new table, and at the start of every OPTIMIZE. The result is stored in the delta.targetFileSize.adaptive table property, visible in DESCRIBE DETAIL, and optimize, auto compaction and optimize write all use it.
  • Defaults. Enabled by default from Runtime 2.0; opt in on Runtime 1.3 with spark.microsoft.delta.targetFileSize.adaptive.enabled. Bounds default to 128 MB and 1 GB and can be tuned within that range.
  • File-level compaction targets (spark.microsoft.delta.optimize.fileLevelTarget.enabled) avoid rewriting files that already met an earlier target, which limits write amplification as the target grows. They are enabled by default from Runtime 2.0 and recommended on 1.3.
  • Manual targets. delta.targetFileSize overrides adaptive sizing but exists mainly for legacy compatibility. Do not add arbitrary row-count limits either: row width varies, so a row cap creates tiny files for narrow tables.

This changes the 1 GB per partition guidance in a useful way. A partition should hold enough data to produce well-sized files, which for tables of tens of GB means files of roughly 128 MB: the 1 GB partition floor guarantees at least a handful of right-sized files in each partition instead of one runt.

Auto compaction and OPTIMIZE

Auto compaction evaluates partition health after each write. If it finds excessive fragmentation (too many small files) it runs a synchronous OPTIMIZE immediately after the commit. Because it only runs when needed, it is the recommended default maintenance strategy for Spark-written tables and removes the need for a separate table-health check before maintenance jobs.

-- For new tables created in the session
SET spark.databricks.delta.autoCompact.enabled = TRUE;

-- For one table
ALTER TABLE silver.orders SET TBLPROPERTIES ('delta.autoOptimize.autoCompact' = 'true');

-- Runtime 2.0: defer the health check to log checkpoints to reduce per-commit overhead
SET spark.microsoft.delta.autoCompact.onCheckpointOnly.enabled = TRUE;

OPTIMIZE is the foundational compaction command, and it has several forms. Spark applies combined options in the order bin compaction, then Z-Order, then V-Order.

OPTIMIZE silver.orders;                                          -- compact; also clusters if liquid clustered
OPTIMIZE silver.orders WHERE order_month >= '2026-01';           -- limit to recent partitions
OPTIMIZE silver.orders WHERE order_month >= '2026-01'
         ZORDER BY (region, product_id) VORDER;                  -- compact, Z-Order, then V-Order
OPTIMIZE gold.sales_clustered FULL;                              -- after changing clustering keys (Runtime 2.0)

Fast optimize (spark.microsoft.delta.optimize.fast.enabled) skips candidate bins that are unlikely to reach the minimum file size, which reduces write amplification and makes repeated OPTIMIZE runs closer to idempotent. It does not apply to liquid clustering or Z-Order operations and does not change auto compaction.

VACUUM and deletion vectors

VACUUM removes files that the Delta log no longer references once they are older than the retention period (seven days by default). It reclaims storage but does not improve the active file layout. Do not shorten the retention period without checking time-travel needs and concurrent readers, and, for Direct Lake, remember that a framed semantic model references a specific table version that must still exist until the model is reframed.

Deletion vectors let DELETE, UPDATE and MERGE mark rows as removed instead of rewriting whole files. They are enabled by default from Runtime 2.0 and opt-in on Runtime 1.3. OPTIMIZE purges a file's deletion vectors when more than 5 percent of its records are referenced by them. Auto compaction purges them only when the partition also meets its small-file trigger, so a table with many updates but few new files still needs a periodic OPTIMIZE. Use REORG TABLE ... APPLY (PURGE) only when you must physically purge records, for example for a compliance requirement.

Z-Order

Z-Order colocates related rows in the same files by applying a space-filling curve across one or more columns, tightening the file-level min and max ranges so selective filters skip more files. It is applied as part of OPTIMIZE, and the columns are not stored in table metadata: you specify them on every run. It has no incremental mode, so each run rewrites all eligible files unless you add a WHERE predicate.

  • With partitioning: Z-Order is applied within each partition independently, which makes it the natural tool for secondary filters on an already partitioned table.
  • With liquid clustering: incompatible. Use one or the other on a table.
  • Choosing columns: 1 to 4 columns that appear frequently in WHERE clauses; you cannot Z-Order by a partition column.
  • When to prefer it: established workflows, older runtimes, or partitioned tables where you want multi-column skipping without more partitions. For new unpartitioned tables on Runtime 2.0, liquid clustering is recommended.

Liquid clustering

Liquid clustering organizes data so rows with similar values in the clustering columns sit in the same files, with tight, rarely overlapping value ranges. Queries that filter on those columns read only the files whose ranges match. Unlike partitioning it creates no directories, handles high-cardinality columns without small-file problems and lets you change the columns later. For most read-performance workloads starting in Runtime 2.0 it is the recommended layout strategy.

-- New table
CREATE TABLE gold.sales (
    order_id   BIGINT,
    order_date DATE,
    region     STRING,
    amount     DECIMAL(18,2)
) CLUSTER BY (order_date, region);

-- Add clustering to an existing unpartitioned table
ALTER TABLE gold.sales_txn CLUSTER BY (order_date, region);

-- Change the columns later; the new layout applies on the next OPTIMIZE
ALTER TABLE gold.sales CLUSTER BY (region, product_category);

-- Remove clustering
ALTER TABLE gold.sales CLUSTER BY NONE;

-- Apply the layout (clustering happens in OPTIMIZE, not on ordinary writes)
OPTIMIZE gold.sales;

Runtime matters

Runtime 1.3: use liquid clustering with caution

On Runtime 1.3 every OPTIMIZE rewrites all files in each Z-Cube smaller than 100 GB, even those already well clustered, causing severe write amplification. Do not combine it with auto compaction on that runtime, and run OPTIMIZE deliberately and infrequently. Incremental liquid clustering, which processes only unclustered, small, unhealthy or deletion-vector files and re-clusters overlapping ones automatically, is available from Runtime 2.0 and is the default there.

  • Columns. Choose 1 to 4 columns that appear frequently in WHERE clauses. More columns dilute the effect of the space-filling curve, and column order has no impact. Eligible types include numeric, date, timestamp and string types; binary and boolean types are not eligible.
  • Maintenance. Clustering is applied only when OPTIMIZE runs. Ordinary writes do not cluster, so schedule OPTIMIZE or use auto compaction (Runtime 2.0 and later). After changing columns, OPTIMIZE FULL reclusters everything; use it sparingly.
  • Quality. From Runtime 2.0 the clusteringQuality() method reports per-column overlap and skipping effectiveness so you can judge whether clustering helps.
  • Limits. Incompatible with partitioning and with Z-Order on the same table. Compatible with V-Order, optimize write, adaptive target file size and deletion vectors.

Warehouse data clustering Preview

Warehouse tables have their own, system-managed layout. Data clustering in Fabric Data Warehouse (Preview) groups rows by up to four columns with CLUSTER BY at table creation, applies during ingestion with no later maintenance, and cannot be added to or changed on an existing table. It suits large tables with repeated selective predicates on mid-to-high cardinality columns. It is a Warehouse feature and does not apply to lakehouse tables.

Verify against Microsoft Learn

Defaults, configuration names and runtime availability in this area change between releases, and a few Learn pages differ on the Delta version that Runtime 2.0 ships. Check the Fabric runtime pages, Tune file size, Table compaction and Liquid clustering for the version your workspace uses, and test the behavior on a copy of a table before relying on it.

Key takeaways

  • Prevent small files at write time (adaptive target size, optimize write), repair them after the commit (auto compaction) and keep scheduled OPTIMIZE for clustering, Z-Order and purging.
  • V-Order is off by default in new workspaces; enable it for Direct Lake tables, not everywhere.
  • Optimize write is not on by default under the writeHeavy profile (except for partitioned tables), and Copy activity and dataflows do not inherit Spark settings.
  • Liquid clustering is the recommended read layout on Runtime 2.0; it is incompatible with partitioning and Z-Order and needs caution on Runtime 1.3.
  • Z-Order remains the tool for secondary filters on tables that are already partitioned.
  • VACUUM reclaims storage and never improves layout; mind retention for time travel and Direct Lake.
