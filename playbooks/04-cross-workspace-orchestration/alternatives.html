Playbook 04 · Hub and spoke

Alternatives and recommendations

Hub and spoke is one way to orchestrate Fabric, not the only one and often not the cheapest. This page compares it honestly with notebook DAGs, Apache Airflow jobs, event-driven triggers and run conditions, gives a decision path, and closes with the recommendations, anti-patterns and checklist for a production hub.

Notebook orchestration

Fabric notebooks can call other notebooks with notebookutils.notebook.run and run many of them as a dependency graph with notebookutils.notebook.runMultiple. When the whole job is Spark code, this removes the per-activity overhead of a pipeline and keeps the logic in one reviewable place.

exit_value = notebookutils.notebook.run(
    "nb_silver_orders",                     # notebook item name
    600,                                    # timeout_seconds (the default is 90)
    {"batch_id": batch_id, "run_date": run_date},
    "<spoke-workspace-id>",                # optional: workspace ID for a cross-workspace call
)
# exit_value is exactly the string the child passed to notebookutils.notebook.exit(...)
# or an empty string when the child never called exit.
from notebookutils.common.exceptions import RunMultipleFailedException

DAG = {
    "activities": [
        {"name": "Customers", "path": "nb_load_customers",
         "args": {"batch_id": batch_id}, "timeoutPerCellInSeconds": 600,
         "retry": 1, "retryIntervalInSeconds": 30},
        {"name": "Orders", "path": "nb_load_orders",
         "args": {"batch_id": batch_id}, "timeoutPerCellInSeconds": 600,
         "retry": 1, "retryIntervalInSeconds": 30},
        {"name": "OrdersEnriched", "path": "nb_build_orders_enriched",
         "args": {"batch_id": batch_id}, "timeoutPerCellInSeconds": 900,
         "dependencies": ["Customers", "Orders"]},
    ],
    "timeoutInSeconds": 7200,   # whole DAG; the default is 12 hours
    "concurrency": 4,           # the default is 3 x CPU cores; 0 means unlimited
}

notebookutils.notebook.validateDAG(DAG)     # duplicate names, missing dependencies, cycles

try:
    results = notebookutils.notebook.runMultiple(DAG)
except RunMultipleFailedException as ex:
    results = ex.result                      # partial results survive a failure
    failed = [name for name, r in results.items() if r["exception"]]
    raise Exception(f"Activities failed: {failed}")   # fail the notebook so a pipeline sees red

What to know before you choose it

Shared compute
Child notebooks share one Spark session. A heavy child starves the others, and the DAG cannot give a step its own pool or environment.
Lakehouse rule
A referenced notebook runs only if it uses the same lakehouse as the parent, inherits it, or defines none. A child with a different default lakehouse is blocked unless you pass useRootDefaultLakehouse: True in the arguments.
Cross-workspace calls
Supported by passing the workspace ID (or, in a DAG activity, name or ID), on runtime 1.2 and above. The child still runs on the caller's Spark pool, so this crosses a naming boundary, not a compute or capacity boundary.
Timeouts
The per-activity timeout in a DAG is per cell (default 90 seconds), not per notebook. Long-running cells need an explicit value.
Exit values
Always strings. Do not call exit() inside a try/except block, because it will not take effect.
Parameters
The child needs a parameter cell, marked with Mark cell as parameters. Values passed by the parent replace the defaults.
Not for Spark job definitions
The notebook utilities apply to notebooks, not to Spark job definitions.

Verdict. Use a notebook DAG when the work is Spark, lives in one lakehouse, and the steps are small enough that a pipeline activity per step is overhead. Use pipelines (and hub and spoke) when steps use different engines, different capacities, different owners or different deployment cycles. A common split is a spoke pipeline whose single Notebook activity runs a runMultiple driver for that layer.

Verify against Microsoft Learn

The config argument of runMultiple is available in Python only, not in Scala or R, and validateDAG raises an exception rather than returning false when a DAG is invalid. NotebookUtils notebook run and orchestration.

Apache Airflow job

The Apache Airflow job item hosts managed Airflow, so a team that already writes Python DAGs can orchestrate Fabric items without running its own cluster. A Microsoft-provided operator runs Fabric items (pipelines, notebooks, Spark job definitions, copy jobs, semantic model refresh and others) in any workspace the connection's service principal can reach.

from datetime import datetime
from airflow import DAG
from apache_airflow_microsoft_fabric_plugin.operators.fabric import FabricRunItemOperator

with DAG(dag_id="sales_daily", schedule="0 2 * * *",
         start_date=datetime(2000, 1, 1), catchup=False) as dag:

    bronze = FabricRunItemOperator(
        task_id="run_bronze", fabric_conn_id="fabric_conn",
        workspace_id="<bronze-workspace-id>", item_id="<bronze-pipeline-id>",
        job_type="Pipeline",            # case sensitive
        wait_for_termination=True, deferrable=True)

    silver = FabricRunItemOperator(
        task_id="run_silver", fabric_conn_id="fabric_conn",
        workspace_id="<silver-workspace-id>", item_id="<silver-pipeline-id>",
        job_type="Pipeline", wait_for_termination=True, deferrable=True)

    bronze >> silver

What Learn documents today:

  • Airflow version 2.10.5 and Python 3.12; the version of an existing job cannot be changed.
  • Git sync, Azure Key Vault as a secrets backend, private package requirements, autoscale, high availability and deferrable operators.
  • Private networks and virtual networks are not supported. Diagnostic logs and metrics are not available either, which the comparison with Azure Data Factory's Workflow Orchestration Manager lists explicitly.
  • To trigger Fabric items from a DAG: enable the tenant setting that lets service principals call Fabric public APIs, create a service principal with the Fabric item read and execute permissions that the tutorial lists, add it as Contributor on each workspace whose items the DAG runs, and enable triggers in the job's environment configuration to use deferrable operators.

Verdict. Airflow is a good fit when the team already owns Airflow skills, wants DAGs in code review, and orchestrates across Fabric and non-Fabric systems. It does not remove the item-ID problem: workspace_id and item_id are still literals you must resolve per environment, for example from Airflow variables. If your network posture requires private connectivity, check the Learn limitation first: it may disqualify Airflow. For a Fabric-only estate with no existing Airflow investment, it is a second orchestrator to secure and operate for little gain over the Invoke pipeline activity.

Verify against Microsoft Learn

The concept article does not show a release-status label for the Apache Airflow job item. Check its current status and your region's availability before committing, and treat the operator's name and import path as subject to change. Event-driven triggers

A pipeline can start when something happens instead of on a clock. Learn lists three event families: file events (OneLake and Azure Blob Storage), job events (a Fabric item run changing state) and workspace events. The trigger is built on Eventstream and Activator: you choose Trigger on the pipeline's Home ribbon, define the event in the Set alert panel, and the result is an Activator (Reflex) item that starts the pipeline, optionally with parameter values.

Use events forAvoid events for
Starting the hub when a source file lands, instead of polling on a scheduleExpressing a multi-step order that must be reviewed and audited
Reacting to a job state change, for example notify or start a follow-up when a named pipeline succeedsGating on "all of A, B and C finished" (you would build a join by hand)
Decoupling teams that should not know each other's item IDsAnything where absence of an event must raise an alarm; nothing fires when nothing happens

Two practical details. First, storage events surface file and folder names to the pipeline as trigger parameters, for example @pipeline()?.TriggerEvent?.FileName; the null-safe ?. is needed because a manual test run has no event, so those values are null. Second, a trigger is an Activator item with its own life cycle in Git and deployment, so treat triggers as deployable code and re-verify them after promotion.

Combine, do not choose

The best pattern is usually "event starts the hub, the hub orders the spokes". You keep the one-screen answer to "what ran, in what order, and what failed" and still avoid fixed-time polling. Add a freshness check (the batch is not complete by the agreed time) so that a missing event is noticed; see Alerts.

A decision path

Work down the questions and stop at the first yes. If you reach the bottom, hub and spoke is the default for cross-team, cross-workspace work.

The hybrid pattern

Real platforms combine these. Events start the day, the hub orders the layers and logs the outcome, and each spoke uses whichever engine suits its work.

Recommendations

The whole playbook condensed into decisions. Each line points to the page that explains it.

Design
Make the hub a control plane only: it orders, passes parameters, logs and alerts, and moves no data. Treat each spoke pipeline's parameters and failure behaviour as an API contract and version it. See the contract.
Granularity
Invoke at the unit a team can own and re-run independently (a layer or a domain), not at the unit of a single copy. Do not nest hubs inside hubs.
Activity
Use the new Invoke pipeline activity for cross-workspace calls and keep the legacy activity only for same-workspace helpers you have not migrated. See two activities.
Identity
Use a service principal or workspace identity connection for scheduled hubs, not a person's account. Grant it Contributor on each spoke, and test the scheduled run, not only the manual one. See connection and identity.
Parameters
Pass the parent context explicitly (batchId, runDate, parentRunId) and never assume the child can see it. Derive batchId deterministically so a re-run is idempotent. See idempotency.
Return values
Do not depend on the Invoke activity returning data. Have the spoke write its outcome and metrics to the run log keyed by batchId, and let the hub read them. See return values.
Control flow
Fan out with ForEach driven by a metadata table, cap parallelism deliberately, and remember that retries multiply (activity retries times parent retries). Make failure propagate: a hub that shows green over a failed spoke is worse than no hub. See ForEach and failure handling.
Observability
Keep a run log for the business view, route workspace monitoring or job events for the technical view, and alert on the hub's outcome and on a missed SLA. See monitoring options.
CI/CD
Never let workspace or pipeline IDs travel with a pipeline. Resolve them per stage with a variable library or at deployment time, deploy spokes before the hub, and keep schedules off until a verified run. See the item-ID problem.
Alternatives
Use the simplest orchestrator that fits each layer, and put events in front of the hub rather than in place of it. See the decision path.

Anti-patterns

Anti-patternWhy it hurtsDo this instead
Hard-coded workspace and pipeline IDs in the hubPromoted copies silently call the previous environmentVariable library value sets or deployment-time replacement
A personal account on the Invoke connectionScheduled runs fail when the token expires or the person leavesService principal or workspace identity with Contributor on spokes
A "god hub" that holds business logicEvery change is a hub release; teams lose independenceKeep logic in spokes; the hub orders and records
Hub failure path that ends in a successOperations sees green while data is staleEnd failure paths with a Fail activity, or leave the failed activity as a leaf
Non-idempotent spokesA re-run duplicates rowsDeterministic batchId and replace-or-merge writes
Retries at every layerThree retries at three levels is nine attempts and nine times the costRetry at the lowest level that is safe; none above it
One-second polling waits across hundreds of childrenBillable orchestration runs and capacity consumed by waitingWait on completion in the Invoke activity, or poll at a sensible interval
Notebook DAG for steps that need different engines or capacitiesOne shared Spark session becomes the bottleneck and the blast radiusSpoke pipelines per engine or capacity

Production-readiness checklist

  • The hub moves no data and holds no business logic; spokes' parameters and outcomes are documented as a contract.
  • The Invoke connection uses a service principal or workspace identity, is named per environment, and has Contributor on every spoke.
  • The tenant setting that lets service principals call Fabric public APIs is enabled and scoped to a security group.
  • The scheduled run, not only a manual run, has been tested end to end in the target environment.
  • Every Invoke activity waits on completion, and a deliberate spoke failure turns the hub red.
  • batchId is deterministic and every spoke write is safe to repeat.
  • Retries and timeouts are set at one level, with the multiplication worked out.
  • A run log records start, success and failure per stage and batch, including the error text.
  • Alerts exist for hub failure and for a missed completion time, and go to a monitored channel.
  • Workspace and pipeline IDs resolve per stage from a variable library or deployment rules; none is hard-coded.
  • Spokes deploy before the hub, connections and role assignments are scripted, and schedules are disabled outside production.
  • Capacity consumption of the hub (waits, polling, monitoring) has been reviewed after the first month.

Key takeaways

  • Pick the simplest orchestrator that fits each layer: one pipeline, a notebook DAG, an event trigger or Airflow before hub and spoke.
  • A notebook DAG is threads in one Spark session: efficient, but shared compute, lakehouse rules and per-cell timeouts are real limits.
  • Apache Airflow adds a second platform and does not remove the item-ID problem; Learn lists private and virtual networks as unsupported for it.
  • Events start work well and express order badly. Put an event in front of the hub, not in place of it.
