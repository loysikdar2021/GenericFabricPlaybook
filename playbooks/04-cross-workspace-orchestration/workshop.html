Playbook 04 · Hub and spoke

Workshop: build hub and spokes

Build a small but real hub and spoke: two spoke workspaces that each copy a CSV file into a Delta table, and a hub workspace whose master pipeline invokes them in order. Then replace your personal sign-in with a workload identity, break a spoke on purpose to prove the hub turns red, and keep the troubleshooting table for later. About 90 minutes.

What you will build

The spokes do almost nothing on purpose. The workshop teaches orchestration mechanics: invoking across workspaces, waiting for completion, passing a parameter and propagating failure. Domain logic can be added to the spokes later without changing the hub, which is the point of the pattern.

An honest simplification

In this exercise the Silver pipeline does not consume the Bronze table, so the dependency is a sequencing exercise rather than a data dependency. Stage 7 makes the dependency real with a shortcut and a notebook, without changing a single hub setting.

Prerequisites. A Fabric capacity you may assign workspaces to, the right to create workspaces and connections, and the permissions listed in the next section. You do not need Git or a deployment pipeline for this workshop.

Request workspaces and permissions

In most organizations someone else controls capacity, tenant settings and Entra objects, so start the requests first. The hub's connection identity is the one that matters most: it needs Contributor on every spoke, and that role assignment is what you will test in Stage 5.

Stage 1: Create the spoke workspaces and lakehouses

  1. Create the workspaces

    In the Fabric portal choose Workspaces, then + New workspace. Create DEV_SALES_BRZ and DEV_SALES_SLV, and assign each to the Fabric capacity you were given (Advanced settings, License mode). If designated spoke workspaces already exist, use them instead.

  2. Create a lakehouse in each

    In each workspace choose + New item, then Lakehouse. Name them LH_SALES_BRZ and LH_SALES_SLV. Leave the schema option at its default; if your lakehouse shows a schema box in a later step, keep the default schema.

  3. Upload the files

    Open LH_SALES_BRZ, hover over the Files folder, choose the ellipsis, then Upload, Upload files, and select customers.csv. Repeat in LH_SALES_SLV with orders.csv. Refresh and confirm each file appears under Files.

Stage 2: Build the two spoke pipelines

Each spoke pipeline is a single Copy data activity with one parameter. The parameter is the pipeline's public contract: the hub will pass it explicitly.

  1. Create the pipeline

    In DEV_SALES_BRZ choose + New item, Data pipeline, name it PL_SALES_BRZ_Ingest and choose Create. When the start screen appears, choose Pipeline activity and then Copy data (or add Copy data from the Activities tab).

  2. Name the activity

    On the General tab set the name to Copy customers.

  3. Add the parameter

    Click an empty part of the canvas, open the Parameters tab and add sinkTable, type String, default value customers.

  4. Configure the source

    Select the Copy activity and open Source. Connection: LH_SALES_BRZ. Root folder: Files. File path type: File path. File path: customers.csv (use Browse). File format: DelimitedText, and in the format settings make sure First row as header is selected, otherwise the columns arrive as generic names.

  5. Configure the destination

    Open Destination. Connection: LH_SALES_BRZ. Root folder: Tables. Table: choose Add dynamic content and enter @pipeline().parameters.sinkTable. Table action: Overwrite. Leave the Advanced section at its defaults and do not enable partitioning: these are tiny tables, and partitioning a small table produces many tiny files (see the Delta partitioning playbook).

  6. Save and validate

    Choose Save on the Home tab, then Validate. A Fabric pipeline has no separate publish step: saving is what makes it runnable by the hub. Optionally choose Run once to confirm that the customers table appears under Tables.

Repeat the same steps in DEV_SALES_SLV. Only the names change:

Stage 3: Create the hub and its master pipeline

  1. Create the hub workspace

    Choose Workspaces, + New workspace, name it DEV_ORCH_HUB, add a description such as "Control plane for the sales workshop", assign the capacity and choose Apply.

  2. Create the master pipeline

    In DEV_ORCH_HUB create a Data pipeline named PL_ORCH_HUB_SalesDaily.

  3. Add the first Invoke activity

    On the Activities tab choose Invoke pipeline. Use the new activity, not the one labelled Legacy. The legacy activity cannot cross workspaces. Name it Invoke Bronze.

  4. Create the connection

    On the Settings tab open the Connection list and choose Browse all. Under New sources choose Fabric Data Pipelines. Name the connection CONN_FabricPipelines_DEV, set Authentication kind to Organizational account for this first run (you will replace it in Stage 5), choose Sign in, complete the sign-in and choose Connect.

  5. Point the activity at the spoke

    Select the connection, then Workspace DEV_SALES_BRZ and Pipeline PL_SALES_BRZ_Ingest. Keep Wait on completion selected. In the pipeline's parameter list set sinkTable to customers.

  6. Add the second Invoke activity

    Add another Invoke pipeline activity named Invoke Silver, reuse the same connection, choose Workspace DEV_SALES_SLV and Pipeline PL_SALES_SLV_Conform, keep Wait on completion selected and set sinkTable to orders.

  7. Connect them

    Drag from the On success (green check) handle of Invoke Bronze to Invoke Silver. Silver now starts only if Bronze succeeds. Save the pipeline.

The four output states

On success runs the next activity when the previous one succeeded; On fail when it failed; On completion when it finished either way; On skip when it was skipped. An activity with no incoming connection starts immediately, in parallel with every other such activity. Choosing the wrong state is the commonest cause of a hub that runs Silver after a Bronze failure.

Stage 4: Run and monitor

  1. Run

    Open the Output tab first so you can watch from the start, choose Save, then Run (accept Save and run if prompted).

  2. Watch the Output tab

    You should see Invoke Bronze in progress, then Succeeded, then Invoke Silver in progress, then Succeeded. Total time is the sum of the children plus start-up for each.

  3. Open the Monitoring hub

    From the left navigation open Monitor. You should see three pipeline runs: PL_ORCH_HUB_SalesDaily, PL_SALES_BRZ_Ingest and PL_SALES_SLV_Conform. Open the hub run to see its activity runs and select Gantt to see the timeline.

  4. Verify the data

    Open LH_SALES_BRZ: the table customers exists with five rows and the expected columns. Open LH_SALES_SLV: the table orders exists with six rows. If a table is missing, refresh the lakehouse explorer first.

  5. Check the lineage

    Switch the hub workspace to the Lineage view. If the cross-workspace relationships appear, note which are shown; if they do not, that is normal and is one reason to keep the run log in operations.

Stage 5: Replace your account with a workload identity

The run above worked because you are Admin everywhere and your sign-in is on the connection. That is the configuration that fails at 02:00, when your token has expired or you have left. Swap it now, using the permission map from the request section.

  1. Create the workspace identity

    In DEV_ORCH_HUB open Workspace settings, the Workspace identity tab, and choose + Workspace identity. Only a workspace Admin can do this, and the identity is created with no workspace role. If you were given a service principal instead, skip this step.

  2. Confirm the tenant setting

    Ask the Fabric admin to confirm that Service principals can call Fabric public APIs is enabled for a group that contains the identity.

  3. Grant Contributor on both spokes

    In DEV_SALES_BRZ choose Manage access, Add people or groups, search for the identity (a workspace identity carries the name of its workspace), choose Contributor and Add. Repeat in DEV_SALES_SLV.

  4. Create the new connection

    In Invoke Bronze Settings choose Browse all, then Fabric Data Pipelines, name it CONN_FabricPipelines_DEV_WI and set Authentication kind to Workspace identity (or Service principal, which also asks for tenant ID, client ID and secret). Select this connection in Invoke Silver too. Anyone else who edits the hub needs permission to use the connection.

  5. Run twice

    Run once manually. Then open Schedule, add a schedule that fires a few minutes from now (a start and an end date are required), and confirm the scheduled run also succeeds. Turn the schedule off afterwards. A manual run uses your session; a scheduled run is the real test of the identity.

If the identity run fails

The two likeliest causes are a missing Contributor assignment on one spoke and the tenant setting not covering the identity. Workspace identity is listed as an authentication kind for this connection in one Learn article but is described only for specific activities in another; if it still fails after the roles are correct, use a service principal on the same connection. See connection and identity.

Stage 6: Prove that failure propagates

A hub that stays green while a spoke fails is worse than no hub. Test both failure positions.

  1. Experiment A: break Silver

    In PL_SALES_SLV_Conform change the source file path to orders_missing.csv and save. Run the hub. Expected: Bronze succeeds, Invoke Silver fails with the child's error visible in its output, and the hub run is Failed. The customers table is still refreshed, which is the correct behaviour for a sequence of independent spokes.

  2. Restore it

    Set the path back to orders.csv, save, and run the hub again. Expected: both succeed. Because the spokes overwrite, a re-run is safe.

  3. Experiment B: break Bronze

    Change the source path in PL_SALES_BRZ_Ingest to customers_missing.csv and save. Run the hub. Expected: Invoke Bronze fails, Invoke Silver is skipped, and the hub run is Failed.

  4. Experiment C: turn Wait off

    Restore Bronze. On Invoke Bronze clear Wait on completion, break Bronze again and run. Expected: the hub reports Bronze as Succeeded the moment the child starts and Silver runs, even though the child fails later. That is why Wait on completion is not optional. Re-enable it and restore the file path.

For why leaf activities decide the status and how a catch path can mask a failure, see failure handling.

Stage 7 (optional): Log runs and make the dependency real

  1. Add the run log

    Create a Warehouse in DEV_ORCH_HUB, run the ops.pipeline_run_log script from the run log section, and add a Stored procedure activity before and after each Invoke (Started, Succeeded, and Failed on the On fail path). Re-run the failure experiments and check the log tells the same story as the Monitoring hub.

  2. Add a shortcut to the Bronze table

    In LH_SALES_SLV choose New shortcut under Tables, then Microsoft OneLake, select LH_SALES_BRZ and the customers table, and name the shortcut customers_bronze. Reading through a shortcut is evaluated against the caller, so the identity that runs the notebook also needs read access to the Bronze lakehouse; plan that permission as you planned Contributor.

  3. Add a notebook and use it

    Create a notebook in DEV_SALES_SLV with LH_SALES_SLV as its default lakehouse and the cell below. In PL_SALES_SLV_Conform add a Notebook activity after Copy orders on its On success path and save.

orders = spark.read.table("orders")
customers = spark.read.table("customers_bronze")      # shortcut to LH_SALES_BRZ / customers

(orders.join(customers, "customer_id", "left")
       .write.mode("overwrite")
       .saveAsTable("orders_enriched"))

Run the hub again. The hub definition has not changed, but Silver now reads Bronze output, and a Bronze failure now has a real consequence rather than a symbolic one.

A spoke workspace is missing from the Workspace list in the Invoke activityThe connection's identity has no role there, or the workspace is not visible to itAdd the identity as Contributor on the spoke and reopen the list
Forbidden or "not authorized" on the child runContributor missing on one spoke, or the tenant setting does not cover the identityCheck the role on both spokes and the setting's security group
Manual run works, scheduled run failsThe connection uses a person's sign-in and its token has expired or the person lost accessSwitch to a workspace identity or service principal and re-test on a schedule (Stage 5)
The hub shows Succeeded while the child is still running or later failsWait on completion is offSelect Wait on completion on every Invoke activity
Silver runs even though Bronze failedThe two activities are connected with On completion, or there is no connection at allUse On success; an unconnected activity starts in parallel
The table has the default name instead of the one you passedThe parameter name in the Invoke activity does not match the child's, so the value is ignoredMatch the name exactly (sinkTable) and re-select the pipeline so parameters reload

Clean up

  • Delete the schedule you created in Stage 5, or confirm it is off.
  • Remove the workspace identity or service principal's Contributor role from the spokes if the workshop identity will not be reused.
  • Delete the workshop connections you no longer need.
  • Delete the three workspaces if they were created only for this workshop.

Key takeaways

  • The spoke pipeline's parameter is its contract: the hub passes sinkTable explicitly and the spoke can change inside without the hub changing.
  • Wait on completion and On success together make the hub honest. Test both failure positions, and with Wait off, to see why.
  • The first run proves the wiring; the scheduled run with a workload identity proves the design.
  • Contributor for the hub's identity on every spoke is the permission to request first, because everything else depends on it.
