Playbook 04 · Hub and spoke

Control flow and failure handling

How the hub decides what runs, in what order, how often and what happens when something fails. The page builds from dependency connectors to metadata-driven fan-out, then covers retries, failure semantics, idempotent re-runs and run conditions for cases where a central master is the wrong tool.

The dependency model

A hub pipeline is a graph of activities joined by connectors. Each activity has four output paths, and which one fires decides what runs next.

Output pathNext activity runs when the previous oneTypical use in a hub
On successsucceededAdvance to the next stage
On failfailedLog the failure, notify, fail the hub with a clear message
On completionfinished, whether it succeeded or failedBest-effort steps such as notifications that must never block the flow
On skipwas skipped because something upstream did not runRarely needed; used to shape pipeline status (see below)

Three rules cover most surprises:

  • No incoming connector means "start now". Every activity without one starts when the run starts, all in parallel.
  • Several incoming connectors mean "all of them". An activity with three On success connectors waits for all three. This is your fan-in.
  • One path fires per activity per run. In the Azure Data Factory documentation of the same engine, an On completion path cannot coexist with On success or On fail paths from the same activity.

Sequential execution

The foundation of a medallion flow: Silver must not start until Bronze has finished successfully. In a hub it is expressed by connecting the On success output of one Invoke pipeline activity to the next, with Wait on completion enabled on each. Without the wait, "success" would mean only that the child was started (see Wait on completion).

Parallel execution: fan-out and fan-in

Independent work should not queue behind itself. Ingesting three domains is the classic case: the three Invoke activities have no dependency on each other, so they start together, and the stage that needs all three has three On success connectors, so it waits for the slowest.

Two design points matter more than the drawing:

  • Parallelism competes for capacity. Three spokes that each start a Spark session or a large copy at the same minute can throttle one another, especially when they share a capacity. Parallelize across spokes on separate capacities freely; cap it when they share one.
  • The join needs a failure policy. If one of three ingests fails, should Silver run on the two that succeeded? The default (On success from all three) says no. If the answer is "yes, for the domains that loaded", use On completion connectors into an If condition that checks each outcome, as in the pattern below.

Where parameter values come from

Spoke pipelines should be generic black boxes with no hard-coded server names, paths or tables; the hub supplies the concrete values on every call. The values can come from:

  • Hub pipeline parameters, set by the trigger or a manual run (for example runDate when re-running a past window).
  • Hub variables, set by a Set variable activity earlier in the run and used for values computed once.
  • Lookup outputs, for metadata-driven calls from a control table.
  • System values and functions, such as @pipeline().RunId and @utcnow().
  • Variable library values, for settings that differ per environment: referenced as library variables in the pipeline and used in dynamic content.

The effect is a clean separation: the spoke's logic never knows its execution context, and the hub owns that context explicitly and visibly.

Metadata-driven fan-out with ForEach

Hard-wiring one Invoke activity per spoke does not scale past a handful, and every new spoke needs a hub deployment. The alternative is a control table that lists what to run, a Lookup activity that reads it, and a ForEach that invokes one pipeline per row. This is the pattern behind the control-table pipelines playbook, applied to orchestration.

CREATE SCHEMA ops;

CREATE TABLE ops.orchestration_plan (
    plan_name     VARCHAR(100) NOT NULL,  -- for example 'sales_daily'
    stage         INT          NOT NULL,  -- 1 ingest, 2 conform, 3 model
    logical_name  VARCHAR(200) NOT NULL,  -- stable name such as 'PL_SALES_BRZ_Ingest'
    workspace_id  VARCHAR(36)  NOT NULL,  -- differs per environment
    pipeline_id   VARCHAR(36)  NOT NULL,  -- differs per environment
    enabled       BIT          NOT NULL
);

INSERT INTO ops.orchestration_plan VALUES
 ('sales_daily', 1, 'PL_SALES_BRZ_Ingest', '<workspace-id>', '<pipeline-id>', 1),
 ('sales_daily', 2, 'PL_SALES_SLV_Conform', '<workspace-id>', '<pipeline-id>', 1);
Lookup  (query):    SELECT logical_name, workspace_id, pipeline_id
                    FROM ops.orchestration_plan
                    WHERE plan_name = '@{pipeline().parameters.planName}'
                      AND stage = 1 AND enabled = 1
Lookup  (first row only): off
ForEach (Items):    @activity('LookupStage1').output.value
ForEach (Batch count): 4        Sequential: off
Invoke  (Workspace): @item().workspace_id
Invoke  (Pipeline):  @item().pipeline_id
Invoke  (Parameters): batchId = @item().logical_name + the run date key

Constraints to design around:

  • ForEach handles up to 100,000 items with a default parallelism of 20 and a maximum of 50; the Lookup that feeds it is limited to 5,000 rows.
  • A ForEach cannot directly contain another ForEach. When you need a loop inside a loop, put the inner loop in a child pipeline and invoke it from the outer one.
  • Variables are scoped to the pipeline run, not to a ForEach iteration. Setting a variable inside a parallel ForEach produces races; write results to the run log from the child instead.
  • Putting the plan table in a Warehouse or Lakehouse per environment gives you the logical-name-to-ID mapping that also solves part of the item-ID problem.

Verify against Microsoft Learn

Confirm in your tenant that the Invoke activity's Workspace and Pipeline fields accept @item() expressions, and re-check the nesting rule for ForEach, before building a plan-driven hub. ForEach activity and Data Factory limitations.

Retries and timeouts

Retry and timeout are per-activity policies on the General tab. For an Invoke pipeline activity they apply to the whole child run, which changes how you should use them.

SettingBehaviourGuidance
TimeoutDefault 12 hours, in D.HH:MM:SS formatSet it to the child's SLA plus margin. A hung child that holds the default for half a day blocks every downstream stage and its capacity.
Enable retries / RetryNumber of retries, 1 to 1,000; the default is 1Retry transient failures at the leaf activity (Copy, Notebook) first.
Retry interval typeFixed (default, 30 seconds) or Increasing delay (exponential back-off from the interval up to a maximum, default 3,600 seconds, with random jitter)Fixed for brief, predictable blips; increasing delay for throttling and outages. Interval fields must be static values, not expressions.
Retry conditions PreviewRetry only when the error message, failure type or error code matches (for example code 429)Avoid wasting retries on authentication or permission errors. The retry interval is waited before the condition is evaluated. Supported for specific activity types, including Copy, Notebook, Dataflow and Stored procedure.
Secure input / outputHide activity input or output from logsTurn on wherever parameters carry anything sensitive.

Verify against Microsoft Learn

A timeout on an Invoke activity fails the activity, but the documentation does not say whether the running child is cancelled. Set timeouts on the child's own activities as well, and test cancel behaviour in your tenant. Activity retries and Activity overview.

Failure handling and pipeline status

How a pipeline ends depends on how you wired its failure paths, and the obvious wiring is wrong. The engine decides pipeline status from the leaf activities: it evaluates every leaf (an activity with no outgoing connectors), looks at the parent instead when a leaf was skipped, and reports success only if everything it evaluates succeeded. The Azure Data Factory documentation of the same engine names three shapes.

For the hub, adopt one rule: define both the On success and On fail paths of every Invoke (the Do-If-Else shape), and end the failure path with a Fail activity when you want a specific error message and code in the run history. Use On completion only for best-effort steps such as notifications. Verify the behaviour with a deliberate failure in the workshop before you trust it.

Idempotency and re-runs

In a distributed batch, re-running is routine: a transient fault, a late file, a fixed bug. Design every spoke so that running it twice with the same parameters leaves the same result as running it once. Then a re-run is an operation, not an incident.

TechniqueWhereHow it makes a repeat harmless
Deterministic batchIdHub to every spokeDerived from the logical window, not the run ID, so every repeat targets the same slice.
Overwrite the sliceCopy sink on small tables; partition or window overwrite in SparkThe repeat replaces the slice instead of appending to it.
Merge on a business keySilver and Gold loadsThe repeat updates existing rows; see the data load strategy playbook.
Advance watermarks after commitIncremental loadsA failed run leaves the watermark where it was, so the next run covers the gap.
Skip-if-done checkHub, before an expensive stageThe log says this batchId already succeeded here, so the stage is skipped.

Re-run mechanics. From the Monitoring hub you can re-run a pipeline run. The new Monitoring hub (preview) documents re-running the entire pipeline, only the failed activities, or selected activities. A re-run of an Invoke activity starts a new child run, so plan for the child to start from its first activity again; that is the other reason children must be idempotent. When you re-run a past window, pass the explicit runDate so the batchId matches the original.

Run conditions: dependencies without a central master

Run conditions let a pipeline declare what it is waiting for before it starts, instead of a hub invoking it. They suit cases where spokes are scheduled by their own teams but still need to respect each other.

TypeWaits forExample
CustomOne or more upstream pipelines whose runs match a run dimension (processing date, region, batch, tenant) and a connectionTransform after ingest and validation both finish for the same region and date

Preview, with semantics to design around

Run conditions are in preview. A run dimension value is evaluated once for a downstream pipeline: if the downstream already ran for that value, later upstream runs with the same value do not start it again, so a re-run needs a new dimension value. Cross-workspace dependencies require access to both pipelines, and renaming or moving an upstream pipeline breaks the dependency silently until you review it. Run conditions in Fabric pipelines.

Key takeaways

  • Express order with On success connectors and Wait on completion; express "all of these first" with several connectors into one activity.
  • Define both On success and On fail on every Invoke, end failures with a Fail activity, and test that a broken spoke turns the hub red.
  • Retry at the leaf, not at every level. Stacked retries multiply; set timeouts to the SLA, not the 12-hour default.
  • Drive fan-out from a control table and cap the ForEach batch count to what the capacity can absorb.
  • Make every spoke idempotent with a deterministic batchId, so re-running is an operation and not an incident.
