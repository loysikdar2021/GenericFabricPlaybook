Playbook 04 · Hub and spoke

Hub-and-spoke architecture

What the hub and the spokes each own, why the contract between them is the part that needs governance, how to decide where to draw spoke boundaries, and how capacity and permissions fit together.

From network topology to data topology

Hub and spoke comes from network design: a central hub virtual network hosts shared services such as the firewall, DNS and gateways, and workload networks (spokes) connect to it. Policy is centralized, workloads are isolated, and adding a spoke does not disturb the others. The same shape maps well onto Fabric workspaces, with one important difference.

Network conceptFabric equivalentWhere the analogy holds or breaks
Hub virtual networkHub workspace (<ENV>_ORCH_HUB)Holds shared services. Unlike a network hub, no data is routed through it.
Shared services (firewall, DNS)Master pipelines, shared connections, run log, alert rulesHolds: policy and observability are centralized.
Spoke virtual networkSpoke workspace per domain or layerHolds: the isolation boundary for roles, capacity and Git.
PeeringInvoke pipeline activity plus a role assignmentPeering opens a route; here you authorize one identity to start jobs in another workspace.
Transitive routingNoneBreaks by design: a spoke should not invoke another spoke. Cross-spoke order belongs in the hub.

Roles and responsibilities

The pattern works only if both sides stay on their half of the line. The most common failure is a hub that slowly accumulates transformation logic, or a spoke that quietly starts calling its neighbour.

The contract between hub and spokes

Hub and spoke is often described as giving teams full autonomy. In Fabric it gives managed decentralization. The hub's Invoke pipeline activity references a spoke pipeline by workspace and item ID and passes parameters by name. That is tight coupling: rename a parameter or recreate a pipeline and the hub breaks. Spoke teams therefore have to treat the signature of a spoke pipeline the way an API owner treats an endpoint.

Contract elementRuleWhy
Pipeline nameLogical name PL_<DOMAIN>_<LAYER>_<Function>, stable over timeThe hub and the logging dashboards identify spokes by name; a rename is a breaking change.
ParametersTyped, documented, with defaults. Always accept batchId, a run date or window, and parentRunId.Adding a parameter with a default is non-breaking; renaming or removing one is not. Explicit parent context avoids depending on system variables that may be empty.
StatusThe pipeline fails whenever the data is not safe for the next stageThe hub's dependency gates read pipeline status. A spoke that catches its own errors and ends green poisons everything downstream.
IdempotencyThe same parameters always produce the same end stateRetries and re-runs are normal operations, not incidents (see idempotency and re-runs).
LoggingThe hub writes the run envelope; the spoke writes business metrics keyed by batchIdEach side logs what only it can know.
Change policyAdd, do not change; announce deprecations; release hub and spoke changes together when a signature changesThe two sides deploy independently, so the contract has to carry the compatibility promise.

Keep one contract document per spoke

A short table in the spoke's repository (parameters, defaults, example values, what "failed" means, typical duration) is enough. It is the first thing a hub engineer needs when wiring a new Invoke pipeline activity, and the first thing a reviewer should diff when a spoke pipeline changes.

How to cut spokes

There is no single correct granularity. Choose the boundary that matches how you deploy and who owns the work, then let the hub express the dependencies. The naming convention <ENV>_<DOMAIN>_<LAYER> supports both layouts below.

LayoutStrengthsWeaknessesChoose when
By layer
DEV_SALES_BRZ, _SLV, _GLD		Matches the medallion model; permissions differ per layer (engineers write Bronze, analysts read Gold); hub order equals layer orderOne domain change can touch three workspaces and three deployments; more invoke edges to maintainRegulated or sensitive data, separate teams per layer, per-layer capacity
By domain
DEV_SALES, DEV_FINANCE		A domain team deploys as one unit; fewer workspaces; the hub stays smallWeaker layer-level isolation; one capacity absorbs ingest bursts and modelling togetherSmall domain teams who own the whole flow
HybridLayer spokes for the domains that need isolation, domain spokes for the rest, shared platform spokes (reference data, ingestion platform)Hardest to explain; needs a written conventionLarger organizations; the common end state

See the medallion architecture playbook for the trade-offs behind workspace-per-layer. Whatever you choose, keep the hub in its own workspace: a master pipeline that lives inside one of its spokes is a spoke with opinions, and it cannot be promoted or secured independently.

Capacity and permissions

Capacity

For a small platform one capacity can host the hub and every spoke. As load grows, the usual move is to give heavy spokes (typically ingestion) their own capacity so a burst of copy activity cannot throttle modelling or reporting. Microsoft's deployment-pattern guidance describes both options: multiple workspaces on one capacity is simpler to administer, multiple workspaces on separate capacities gives performance isolation and per-team chargeback at the price of more administration, and a hybrid is common.

Verify against Microsoft Learn

Pipeline orchestration activity runs are billed per activity run, and activities such as Copy and Notebook consume capacity where they execute. Confirm in the Capacity Metrics app which capacity a child pipeline's consumption lands on in your topology before you size anything. Pricing for pipelines.

Permissions

The hub does not need to read any spoke data. It needs the right to start and observe pipeline runs in each spoke, granted to a single non-human identity.

A tenant setting also matters: for service principal and workspace identity authentication the tenant setting Service principals can call Fabric public APIs must be enabled (it is off by default). Scope it to a security group rather than the whole tenant.

Benefits and what they cost

What you gain

  • Governance: one place for order, failure policy, audit trail and alert routing.
  • Reuse: parameterised spoke pipelines serve many callers; a new spoke is one more invoke edge, not a rewrite.
  • Autonomy within limits: spoke teams build and deploy independently while the contract holds.
  • Isolation: roles, capacity and Git history per spoke.

What you pay

  • Coupling: hub and spokes share IDs and parameter names, so spoke teams must coordinate signature changes.
  • ID management: workspace and pipeline IDs differ per environment and must be resolved during promotion.
  • Monitoring overhead: run history lives where the run happens, so you must build the central view.
  • One more identity to secure and more workspaces to administer.

Key takeaways

  • The hub is a control plane only. If data or transformation logic accumulates there, move it to a spoke.
  • Spokes never call spokes. Cross-spoke order belongs in the hub, where it is visible and logged.
  • Treat each spoke pipeline's parameters and failure behaviour as a versioned API, and document it.
  • Grant the hub identity Contributor on spokes, not Admin, and keep the hub on a small capacity.
  • Pick the spoke granularity that matches how you deploy and who owns the work; write the convention down.
