Playbook 04 · Hub and spoke

Logging, monitoring and CI/CD

The two things that are painful to retrofit: one place that answers "did it finish?", and a way to promote hub and spokes between environments without hard-coded workspace and pipeline IDs. This page compares the monitoring options, shows an explicit run log, covers alerting, and then solves the item-ID problem.

The fragmentation problem

Run history lives in the workspace where a run executes. In hub and spoke that means the hub shows that its master pipeline ran, each spoke shows its own runs, and nothing shows the end-to-end story unless you build it. Earlier guidance solved this by enabling workspace monitoring in the hub and streaming each spoke's job events through an Eventstream into the hub's Eventhouse. That still works, but there are now native ways to route telemetry centrally, and a simple explicit log table remains the most portable answer for business-level questions. The right design usually uses two of them: a technical view and a business view.

An explicit run log in a Warehouse

Whatever the platform logs, keep a small table you control. It carries what no system log knows: the logical batch, the stage name your operations team uses, rows written, and the error text you chose to keep. The hub writes the envelope (started, succeeded, failed for each stage); spokes add their own metrics keyed by the same batchId.

CREATE SCHEMA ops;

CREATE TABLE ops.pipeline_run_log (
    event_id        VARCHAR(36)   NOT NULL,
    event_time_utc  DATETIME2(6)  NOT NULL,
    hub_run_id      VARCHAR(36)   NOT NULL,   -- @pipeline().RunId of the hub run
    pipeline_name   VARCHAR(200)  NOT NULL,
    stage           VARCHAR(50)   NULL,
    batch_id        VARCHAR(100)  NOT NULL,
    status          VARCHAR(20)   NOT NULL,   -- Started | Succeeded | Failed
    error_message   VARCHAR(4000) NULL,
    rows_written    BIGINT        NULL
);

CREATE PROCEDURE ops.usp_log_event
    @hub_run_id    VARCHAR(36),
    @pipeline_name VARCHAR(200),
    @stage         VARCHAR(50),
    @batch_id      VARCHAR(100),
    @status        VARCHAR(20),
    @error_message VARCHAR(4000) = NULL,
    @rows_written  BIGINT = NULL
AS
BEGIN
    INSERT INTO ops.pipeline_run_log
        (event_id, event_time_utc, hub_run_id, pipeline_name, stage,
         batch_id, status, error_message, rows_written)
    VALUES
        (CONVERT(VARCHAR(36), NEWID()), SYSUTCDATETIME(), @hub_run_id, @pipeline_name,
         @stage, @batch_id, @status, LEFT(@error_message, 4000), @rows_written);
END;

In the hub, call the procedure with a Stored procedure or Script activity before each Invoke (status Started), on its On success path (Succeeded) and on its On fail path (Failed, with the error text). The error text of a failed activity is available as @activity('Invoke Bronze').error.message.

WITH ranked AS (
    SELECT *,
           ROW_NUMBER() OVER (PARTITION BY pipeline_name, batch_id
                              ORDER BY event_time_utc DESC) AS rn
    FROM ops.pipeline_run_log
    WHERE status IN ('Succeeded', 'Failed')
)
SELECT pipeline_name, batch_id, status, event_time_utc, error_message
FROM ranked
WHERE rn = 1
ORDER BY event_time_utc DESC;

Right-size the log

A Warehouse takes single-row inserts comfortably for a few hundred events per hub run. If you log per file or per partition (thousands of rows per run), write to a Lakehouse table from a notebook or send the events to an Eventhouse instead, and keep the Warehouse for the stage-level envelope.

Verify against Microsoft Learn

Learn's examples filter on ItemKind in one article and JobType in another, and the expected values differ. The documented JobStatus values are Not started, In progress, Completed and Failed, so a success is Completed, not Succeeded. Before you build an alert, inspect your own table: ItemJobEventLogs | summarize count() by ItemKind, JobType, JobStatus. When telemetry is routed to a central monitoring item, each source workspace gets its own KQL database there, so a cross-spoke query unions the same table across those databases. Create alerts for pipeline runs.

What to alert on. Alert on the hub's outcome and on a missed SLA (the batch is not complete by the agreed time), not on every spoke event. One message that says which stage stopped, for which batch, with a link to the run, is actionable; a flood of per-activity failures during one incident is not. Keep per-spoke alerts for the spoke teams' own channels.

Cost visibility. Orchestration activity runs are billed per run and each child pipeline's activities consume capacity where they execute. A hub that polls with one-second waits across hundreds of children, or workspace monitoring left on in every development workspace, shows up in the Capacity Metrics app. Review it after the first month of production traffic.

The item-ID problem

The most awkward technical problem in hub and spoke is that Fabric item IDs are not stable across workspaces. A pipeline deployed from development to test becomes a new item with a new ID. A hub pipeline whose Invoke activity carries the development workspace ID and pipeline ID will, after promotion, happily call the development spoke from the test hub, which is both a silent correctness bug and a data-isolation problem.

ApproachHow it worksStrengthsWeaknesses
Variable library, basic variablesStore each spoke's workspace ID and pipeline ID as Guid variables with a value set per stage; reference them from the hub as library variables in the Invoke activity's dynamic contentNative; visible; no JSON editing; same hub definition in every stageYou maintain the value sets; confirm the Invoke fields accept dynamic content in your tenant
Variable library, item reference PreviewA variable that holds a workspace ID and item ID as a pair, picked from a list of itemsNo hand-typed GUIDsPreview; the documented consumers are shortcuts, user data functions and notebooks, so confirm pipeline use; reference is static per value set

Metadata-driven lookupA per-environment plan table maps logical name to IDs; the hub Looks up and invokes dynamicallyAdd or remove spokes without redeploying the hubThe table has to be populated per environment (script it by name); IDs still live somewhere
Deployment pipelines alonePromote the hub and spokes between stagesBuilt in, simpleRebinding of cross-workspace references is not documented for the Invoke activity; related limitations are documented for other item types, so test it

Recommendation. Default to a variable library with basic Guid variables and one value set per stage, and verify the Invoke fields accept library variables. If they do not in your tenant, or you promote through Git rather than deployment pipelines, use deployment-time replacement. Reach for the plan-table approach when the set of spokes changes often. See the variable libraries playbook for value-set mechanics and the deployment playbook for promotion.

Deploying hub and spokes

Order matters because the hub's references must resolve to things that already exist. Deploy foundations first, spokes second, the hub last, then verify before anything runs on a schedule.

  1. Foundations

    Create the workspaces, assign capacity, set roles, create the workspace identity (or register the service principal) and add it as Contributor on every spoke. Roles, identities and tenant settings are not items, so automate them with the Fabric REST API or your infrastructure tooling, not with deployment pipelines.

  2. Connections

    Create the Fabric Data Pipelines connection and the source connections in each environment, and note their IDs. Connections are not deployed with items; Git-based deployment tools expect them to exist and ask you to parameterize their IDs. Activities that use OAuth connectors such as Teams or Outlook require a manual sign-in after promotion. A service principal connection holds a client secret, so keep that secret in Azure Key Vault in your provisioning scripts rather than in a ticket or a repository; whether the Fabric Data Pipelines connection can reference a Key Vault secret directly is not confirmed here, so check the connection documentation before relying on it.

  3. Spokes

    Deploy storage items first (lakehouses, warehouses), then notebooks and dataflows, then pipelines. Learn documents a limitation: a pipeline that invokes a dataflow keeps pointing at the dataflow in the previous workspace after promotion, because dataflows are not supported in deployment pipelines, so check such references in the target.

  4. Resolve IDs

    Activate the right variable library value set for the stage, or run the replacement rules.

  5. Hub

    Deploy the hub's master pipelines and variable library last.

  6. Verify, then enable

    Run the hub against one small window in the target environment and read the run log. Schedules are stored with the pipeline in Git, so keep them disabled outside production through a deployment-time rule and enable them deliberately.

Git and ownership

Keep the hub in its own repository or folder with stricter review than the spokes, since a hub change affects every schedule. Route its pull requests to the platform team with CODEOWNERS (see the pull-request notifications playbook and the GitHub integration playbook). Related release-day checks are in the deployment checklist.

Key takeaways

  • Run history stays in the workspace where a run executes; centralizing it is a design task, not a default.
  • Keep an explicit run log for the business view and route monitoring telemetry for the technical view; alert on the hub's outcome and on missed SLAs.
  • Never let workspace or pipeline IDs travel with the pipeline. Resolve them per stage from a variable library or by name at deployment time.
  • Deploy foundations, connections and spokes before the hub; keep schedules off until a verified run.
