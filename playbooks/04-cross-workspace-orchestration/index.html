Cross-Workspace Pipeline Orchestration (Hub and Spoke)

A pattern for running end-to-end data workflows that span many Fabric workspaces. One hub workspace owns order, retries and the run log; domain or layer spokes own their data and their pipelines. This playbook covers the design, the Invoke pipeline activity that makes it work, control flow, central monitoring, CI/CD, the alternatives, and a hands-on workshop.

  • Audience data engineers, platform architects
  • Level advanced
  • Reading time 90 min
  • Includes hands-on workshop

The problem this pattern solves

A platform with one workspace per layer or per domain (see the medallion architecture playbook) gives every team its own pipelines, schedules and capacity. It also removes the one thing a monolith gave you for free: a single place that knows what must run before what.

Without a coordinating layer, teams fall back to schedules that guess. Silver is scheduled "an hour after Bronze, because Bronze usually finishes by then". The failure modes are predictable:

  • Silver reads a half-loaded Bronze table, and nobody sees an error because every pipeline "succeeded" on its own terms.
  • An ingest fails overnight and the first alert is a business user asking why the dashboard is stale.
  • Nobody can answer "did last night's load finish?" without opening five workspaces and comparing timestamps.
  • One team renames a pipeline and breaks a neighbour's schedule that nobody knew depended on it.

The opposite extreme, one large pipeline in one workspace, trades those problems for others: a single point of failure, an activity ceiling per pipeline, and every domain team editing the same artifact. Hub and spoke is the middle path. A dedicated hub workspace holds the master pipelines that define order and failure policy. Spokes keep ownership of their data and expose small, parameterised pipelines that the hub calls.

How hub and spoke works in Fabric

Hub workspace
A dedicated workspace named <ENV>_ORCH_HUB. It holds master pipelines, shared connections, the run log and alert rules. It does not hold business data or transformation logic.
Spoke workspaces
Domain or medallion-layer workspaces (DEV_SALES_BRZ, DEV_SALES_SLV). Each holds its lakehouses or warehouses, notebooks, and small pipelines that take parameters and fail loudly.
The link
The Invoke pipeline activity with Wait on completion enabled, authorized by a reusable connection. It is what lets a pipeline in one workspace start and track a pipeline in another.
The contract
Parameter names, status semantics and the run-log schema. It is the only thing the hub and a spoke team must agree on, and it is the thing that couples them (see the contract).

When to use it, and when not to

Use hub and spoke when

  • Three or more workspaces have ordering dependencies between their jobs.
  • Different teams own different spokes and need to deploy independently.
  • One place must answer "did the nightly load finish, and if not, where did it stop?"
  • Spokes run on separate capacities for isolation or chargeback.
  • The same orchestration must run in DEV, TST and PRD with different targets.

Prefer something simpler when

  • Everything lives in one workspace with one owner: one pipeline with folders is simpler.
  • Jobs are independent and reactive (file arrival, upstream success): use event-driven triggers.
  • The whole flow is Spark in one lakehouse: a notebook DAG is cheaper than a pipeline per step.
  • Security forbids giving any single identity access to every spoke.
  • You need streaming latency: use Real-Time Intelligence, not batch orchestration.

The alternatives page compares these options in detail with an honest decision table. Most mature platforms end up hybrid: hub-and-spoke pipelines for the nightly batch, event triggers for file arrival, notebook DAGs inside a spoke.

Audience and prerequisites

  • A Fabric capacity (trial or paid) and permission to create at least three workspaces on it.
  • Working knowledge of Fabric pipelines: Copy data, Lookup, parameters and the expression language.
  • For the workshop: Admin on the three workspaces, and either a tenant admin who can enable the service-principal API setting or an account you can sign in with for a user connection.
  • For the CI/CD material: familiarity with Git integration and deployment pipelines (GitHub integration and deployment playbooks).

What you will be able to do

  • Decide whether hub and spoke is the right orchestration pattern, and cut spokes by domain, layer or both.
  • Configure the Invoke pipeline activity with a durable identity, correct permissions and explicit parent context.
  • Build sequential, parallel, conditional and metadata-driven flows with retries, timeouts and failure policy that surface errors instead of hiding them.
  • Centralize run logging and alerting so one dashboard answers "did it finish?".
  • Promote hub and spokes across DEV, TST and PRD without hard-coded workspace or pipeline IDs.
  • Build and test a working two-spoke, one-hub orchestration end to end.

Key takeaways

  • Hub and spoke gives managed decentralization: spokes own data and deployment, the hub owns order and failure policy, and the contract between them is the coupling you must govern.
  • The new Invoke pipeline activity, with a service principal or workspace identity connection and Wait on completion, is the default link; keep a REST fallback for edge cases.
  • Do not design around preview features without a fallback, and do not rely on child return values; write status to a log table instead.
  • Solve logging and environment IDs on day one. They are the two things that are painful to retrofit.
