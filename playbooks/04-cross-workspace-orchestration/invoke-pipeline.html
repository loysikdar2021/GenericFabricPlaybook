Playbook 04 · Hub and spoke

The Invoke pipeline activity

The activity that lets a pipeline in one workspace start and track a pipeline in another. This page separates the two activities that share the name, explains the connection and identity model, and turns the old list of "preview limitations" into what to do about each one.

Two activities with the same name

Fabric has two Invoke pipeline activities. Pipelines built early on use the legacy activity, which only reaches pipelines in the same workspace. The new activity adds a connection and a workspace selector, and with them cross-workspace calls and child-run monitoring. A hub-and-spoke design needs the new one; the old one is still useful for modularising logic inside a single workspace.

Invoke pipeline (Legacy)Invoke pipeline (new)
ReachFabric pipelines in the same workspace as the parentFabric pipelines in any workspace the connection identity can use; Azure Data Factory and Synapse pipelines
Connection objectNot usedRequired; stored in the secure Fabric credentials store
Child run monitoringOnly the parent run is monitoredChild pipeline runs can be monitored
Wait on completionSupportedSupported
ParametersSupportedSupported
Use forModular logic inside one workspaceHub-and-spoke across workspaces

Spot the difference on the canvas

The new activity has Type, Connection and Workspace fields on its Settings tab; the legacy activity shows only an invoked-pipeline selector. If you open an older pipeline you may be prompted to upgrade the activity. Upgrading adds the connection and workspace properties; review the result, because those are exactly the properties your CI/CD process will need to handle (see the item-ID problem).

Connection and identity

Every new Invoke pipeline activity needs a connection, and the connection's identity is what Fabric authorizes when the hub starts a child run. When you create the connection you choose an Authentication kind: organizational account, service principal, or workspace identity.

Authentication kindStrengthsWeaknessesUse for
Organizational accountFastest to set up; fine for a first testTied to one person. A password change, disabled account or role change breaks the connection. Pipelines do not refresh authentication in the background, so a cached token can go stale.Workshops and prototypes only
Service principalNot tied to a person; scoped by a security group; well understood by security teamsA secret or certificate to rotate; needs the tenant setting for service principals to call Fabric APIs; must be added to every spoke workspaceProduction, especially where service principals are already managed
Workspace identityFabric-managed identity with no secret to store or rotateMust be created in the same workspace as the pipeline; needs the same tenant setting; not compatible with cross-tenant requests; Conditional Access policies for workload identities must exclude itProduction where you want zero secrets; verify first (see callout)

Set up a workspace identity connection

  1. Create the workspace identity

    In the hub workspace, open Workspace settings, select the Workspace identity tab and choose + Workspace identity. Only a workspace admin can do this, and the identity should live in the same workspace as the pipeline that will use it.

  2. Enable the tenant setting

    A Fabric admin turns on Service principals can call Fabric public APIs (disabled by default) and scopes it to a security group that contains your orchestration identities.

  3. Grant the identity access to each spoke

    In every spoke workspace choose Manage access and add the hub's workspace identity (or service principal) as Contributor. Learn states Contributor is sufficient for most scenarios.

  4. Create the connection

    In the Invoke pipeline activity open the Connection list, choose Browse all, select Fabric Data Pipelines under New sources, give the connection an environment-specific name, and set Authentication kind to workspace identity (or service principal, which also asks for tenant ID, client ID and secret).

  5. Select it in the activity and test twice

    Pick the workspace and pipeline, then run once manually and once from the schedule. The scheduled run is the one that exposes the run-identity check.

Verify against Microsoft Learn

The Invoke pipeline article lists workspace identity as an authentication kind, while the general workspace-identity article describes pipeline support for the Copy, Lookup and GetMetadata activities. Treat workspace identity for Invoke pipeline as "test before you standardize" and keep a service principal connection as the fallback. Authenticate with workspace identity.

Wait on completion, parameters and results

Wait on completion

This one checkbox decides whether a dependency means anything. With it on, the activity stays running until the child finishes and takes the child's outcome, so the On success path really means "the child succeeded". With it off, the activity completes as soon as the child is started, and the On success path means only "the child was started".

Leave it off only when you genuinely want fire-and-forget, for example a notification pipeline whose outcome nothing depends on.

Parameters and parent context

Parameters on the activity map to parameters declared on the child pipeline, by name. Treat the list as the spoke's contract (see the contract) and always pass explicit parent context, so the child can log which orchestrated run it belongs to even if system variables are empty.

Child parameterValue the hub passes (pipeline expression)Purpose
runDate@variables('runDate')The logical data window, computed once per hub run in a Set variable activity with @if(empty(pipeline().parameters.runDate), formatDateTime(utcnow(), 'yyyy-MM-dd'), pipeline().parameters.runDate). An empty hub parameter means today; an explicit value re-runs a past window.
batchId@concat('sales-', replace(variables('runDate'), '-', ''))A deterministic key for the logical batch, so a re-run overwrites rather than duplicates. Do not derive it from the run ID.
parentRunId@pipeline().RunIdLinks child log rows to the hub run.
parentPipeline@pipeline().PipelineNameHuman-readable origin for the log.
hubWorkspaceId@pipeline().DataFactoryThe ID of the workspace the hub pipeline runs in.

Learn documents @pipeline()?.TriggeredByPipelineName and @pipeline()?.TriggeredByPipelineRunId as populated when a run is started by an invoking activity (note the question mark, which makes the expression null-safe). Earlier guidance recorded these as null with the preview activity. Passing the values explicitly costs nothing and survives any change in that behaviour.

Return values

The Set variable activity can set a pipeline return value, and the intent is that a calling pipeline can consume it. The documentation does not describe how the new Invoke pipeline activity exposes it, and community reports describe the value as missing from the new activity's output.

Verify against Microsoft Learn

Test a return value end to end in your tenant before using one. Reference: Set Variable activity. Until you have proved it, design as if child pipelines return nothing except success or failure.

The robust alternative is to treat the run log as the return channel: the spoke's last activity writes its metrics (rows written, high-water mark) keyed by batchId, and the hub reads them with a Lookup activity when it needs them. It works for every activity type, survives retries, and doubles as an audit trail.

Early limitations, rewritten

Guidance written when the cross-workspace activity first appeared listed three problems: token expiry, missing parent context, and settings that could not be parameterized. Here is each one, plus the others people hit in practice, with the response that holds today.

Reported issueWhat to do
User tokens in the connection expire, so runs fail intermittentlyUse a service principal or workspace identity. If you must keep a user connection, remember that pipelines do not refresh authentication in the background: after a password change, make a trivial edit to the pipeline and save it so a fresh token is cached.
Parent pipeline and run context is null in the childPass parentRunId, parentPipeline and batchId as explicit parameters. Treat system variables as a bonus.
Workspace and connection are fixed in the UI, so promotion needs manual JSON editsDrive the workspace and pipeline selectors with dynamic content from a variable library, or rewrite the values at deployment time with a tool such as fabric-cicd. Create the connection once per environment. Details in the item-ID problem.
Pipeline return values are missingWrite results to the run log and read them back with Lookup.
Child runs were hard to findThe new activity lets you monitor child runs; the new Monitoring hub shows upstream and downstream runs. Also write parentRunId to the log.
A workspace or pipeline is missing from the selectorThe connection identity has no role in that workspace, or the workspace identity was created in a different workspace than the pipeline's.
Transient failures when many invokes start togetherEnable retries with increasing delay on the Invoke activity, keep children idempotent, and stagger parallel branches (see retries and timeouts).

When the native activity is not enough: the REST fallback

Some cases fall outside what the activity handles: calling from outside Fabric (an external scheduler, a release pipeline), starting a run without any pipeline in between, or needing custom polling. The Fabric REST API for running an item on demand covers them. Run-on-demand returns 202 Accepted immediately with a Location header for the job instance, so a caller that must wait has to poll.

From outside Fabric, the shape is a short script. This example (Python, runs anywhere with network access) authenticates as a service principal that has Contributor on the workspace, starts a pipeline and waits for a terminal state.

import os
import time

import requests
from azure.identity import ClientSecretCredential

BASE = "https://api.fabric.microsoft.com/v1"
WORKSPACE_ID = "<workspace-id>"
PIPELINE_ID = "<pipeline-id>"

credential = ClientSecretCredential(
    tenant_id=os.environ["AZ_TENANT_ID"],
    client_id=os.environ["AZ_CLIENT_ID"],
    client_secret=os.environ["AZ_CLIENT_SECRET"],
)
token = credential.get_token("https://api.fabric.microsoft.com/.default").token
headers = {"Authorization": f"Bearer {token}"}

# Start the run: 202 Accepted, with the job-instance URL in the Location header
start = requests.post(
    f"{BASE}/workspaces/{WORKSPACE_ID}/items/{PIPELINE_ID}/jobs/instances",
    params={"jobType": "Pipeline"},
    headers=headers,
    timeout=60,
)
start.raise_for_status()
status_url = start.headers["Location"]
delay = int(start.headers.get("Retry-After", "30"))

# Poll until the job instance reaches a terminal status
TERMINAL = {"Completed", "Failed", "Cancelled", "Deduped"}
while True:
    time.sleep(delay)
    poll = requests.get(status_url, headers=headers, timeout=60)
    poll.raise_for_status()
    job = poll.json()
    if job["status"] in TERMINAL:
        break
    delay = 30

if job["status"] != "Completed":
    raise RuntimeError(f"Pipeline run ended as {job['status']}: {job.get('failureReason')}")
print("Pipeline run completed")

Inside a pipeline, the equivalent is a Web activity for the start call (method POST, the URL built from the workspace and item IDs, a connection to the Fabric API base URL), an Until activity containing Wait, a Web activity for the status call and a Set variable activity, and a final If condition. A Fabric actions activity (preview) can run a Fabric REST operation from a pipeline without hand-building the request.

Verify against Microsoft Learn

Check the exact job-instance status values and the Location header handling in the Fabric REST reference, and where your Web activity exposes response headers in its output JSON. Run on demand item job, REST API capabilities for pipelines and Fabric actions activity. Parameter passing for on-demand pipeline runs is "not broadly supported" in the generic reference, so test it for pipelines.

Do not make REST the default

The REST path trades a first-class activity for hand-built polling, secrets in the caller, and a monitoring view that shows an unrelated Web activity instead of a linked child run. Use it when you need it, and keep the native activity for everything else.

Key takeaways

  • Use the new Invoke pipeline activity for cross-workspace calls; the legacy activity stays in its own workspace.
  • Authenticate with a service principal or workspace identity, grant Contributor on each spoke, and test a scheduled run, not only a manual one.
  • Always enable Wait on completion for anything a dependency relies on, and pass explicit parent context as parameters.
  • Do not rely on child return values. Use a run log as the return channel.
  • Keep a REST fire-and-poll fallback for callers outside Fabric, with a final step that fails loudly.
