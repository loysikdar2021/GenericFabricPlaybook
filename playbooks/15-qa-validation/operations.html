Playbook 15 · QA Validation

Governance and troubleshooting

A validation framework earns trust slowly and loses it quickly. This page covers what keeps it trustworthy: who owns what, how checks change, how the framework itself is tested and versioned, what it costs to run, and how to diagnose it when a verdict is missing, wrong or slow.

Ownership and roles

The roles below are generic. One person can hold several, and in a small team all of them. What matters is that each decision has exactly one accountable role, written down, so that a tolerance is never relaxed by whoever happens to be annoyed by a red run.

Framework ownerThe harness, the results schema, the framework version, the self-test suite and the reporting modelPlatform or data engineering lead
Check authorWriting and maintaining checks: the claim, the SQL, the tolerance proposal and the example outputData engineer or QA analyst
Data ownerDeciding what "correct" means for a domain (SALES, FINANCE, HR): rules, tolerances, severity, waiversBusiness or domain data steward
ReviewerIndependent review of changes to checks and configurationA second engineer who did not write the change
OperatorRunning schedules, watching alerts, triaging blocked gates, escalatingOn-call data engineer or support rota

Change control

Treat checks and configuration as production code, because a changed check changes what the platform is allowed to publish. They live in source control, change through pull requests (see GitHub Integration and Branching) and reach TST and PRD through the same promotion path as everything else (see Deployment Pipelines and Promotion). Where the harness is shared across workspaces, package it as a library rather than copying cells (see Shared Python Libraries).

If the control table is writable by many people, that history is the audit trail; restrict write access to the framework owners and let everyone else propose changes through source control.

Check lifecycle

New checks rarely belong in front of a release on day one. A check that blocks releases and turns out to be wrong damages trust in all checks. Introduce it quietly, watch it, and promote it when the evidence supports it.

Adding a validation

  1. State the claim in one sentence

    For example, "every order that is not void in Silver exists once in Gold". If you cannot, the check has no defined expected value yet.

  2. Pick the check type and the severity

    Use the type matrix to choose. Start as info unless the data owner already knows the check is stable.

  3. Write the expected and actual queries

    Both must reduce to one number each, built from source-side facts, not from the target being tested.

  4. Choose the tolerance with the data owner

    Use the guidance in tolerance design, and count expected rejects explicitly rather than widening the tolerance.

  5. Seed a defect and prove the check fails on it

    Use the self-test cell: a check that passes on both clean and damaged data proves nothing.

  6. Add it to the configuration, with an owner role and a note

    Fill owner_role and notes so that whoever sees the failure at night knows who decides and what the check protects.

  7. Review, deploy and shadow-run

    Promote through the lifecycle once it has run cleanly for long enough that a failure would be news.

Testing the framework itself

The quality of the verdicts is the quality of the framework. After every harness change, and when a check is added, run each check type against a copy of a clean table and against copies with a known defect injected. Each must return PASS on the clean copy and the expected status on the damaged copy. Run this only in DEV and write only to a scratch schema.

Injected defectCheck that must catch it
About 1 % of rows removedRow count
A derived value altered for some rowsTransformation
A column dropped or its type changedSchema
Load timestamps moved back several daysFreshness
A few rows duplicatedKey uniqueness
A share of a required column set to NULLCompleteness
Keys pointing at dimension members that do not existReferential integrity
A measure scaled by a few percentMetric reconciliation or drift
 
assert env == "DEV", "Defect injection runs only in DEV"
SCRATCH = "qa_selftest"                               # scratch schema in the default (schema-enabled) lakehouse
spark.sql(f"CREATE SCHEMA IF NOT EXISTS {SCRATCH}")

# Assumed columns of the clean table: customer_id, customer_code, customer_label, loaded_at
clean = spark.table(quote_name(f"{GLD}.dim_customer"))

DEFECTS = [   # (case, damaged copy, check configuration, status the check must return)
    ("rows_missing", clean.where(F.rand(7) > 0.01),
     {"check_type": "rowcount", "source": f"{SLV}.customers", "min_rows": 1}, "FAIL"),
    ("label_changed",
     clean.withColumn("customer_label", F.when(F.col("customer_id") % 50 == 0,
                                               F.concat("customer_label", F.lit(" x")))
                                         .otherwise(F.col("customer_label"))),
     {"check_type": "transformation", "source": f"{SLV}.customers", "key": ["customer_id"],
      "expected_expr": "concat(customer_code, ' - ', customer_name)", "target_column": "customer_label"}, "FAIL"),
    ("column_dropped", clean.drop("customer_label"),
     {"check_type": "schema", "columns": [{"name": "customer_label", "type": "string"}]}, "FAIL"),
    ("stale_load", clean.withColumn("loaded_at", F.col("loaded_at") - F.expr("INTERVAL 3 DAYS")),
     {"check_type": "freshness", "timestamp_column": "loaded_at", "max_age_hours": 6, "fail_threshold": 6}, "FAIL"),
    ("duplicate_keys", clean.unionByName(clean.limit(5)),
     {"check_type": "unique", "key": ["customer_id"]}, "FAIL"),
    ("null_codes",
     clean.withColumn("customer_code", F.when(F.rand(11) < 0.02, F.lit(None).cast("string"))
                                         .otherwise(F.col("customer_code"))),
     {"check_type": "completeness", "columns": ["customer_code"]}, "FAIL"),
]

clean.write.format("delta").mode("overwrite").saveAsTable(f"{SCRATCH}.t_clean")
outcome = []
for case, damaged, cfg, must_return in DEFECTS:
    damaged.write.format("delta").mode("overwrite").saveAsTable(f"{SCRATCH}.t_{case}")
    for variant, table, wanted in (("clean", f"{SCRATCH}.t_clean", "PASS"),
                                   (case, f"{SCRATCH}.t_{case}", must_return)):
        got = run_check({**cfg, "test_name": f"selftest.{case}.{variant}", "target": table})[0].status
        outcome.append((case, variant, wanted, got, "ok" if got == wanted else "WRONG"))

display(spark.createDataFrame(outcome, "test_case string, variant string, wanted string, got string, verdict string"))
wrong = [o for o in outcome if o[4] != "ok"]
assert not wrong, f"Checks that did not behave as intended: {wrong}"

When the clean copy fails

If a clean control does not return PASS (for example because the DEV data is genuinely stale), the self-test stops, and that is correct. Fix the data or the check before trusting either side of the comparison.

Versioning

ArtifactHow it is versionedRule
Harness (cells 1-3, runner, writer)FRAMEWORK_VERSION in semantic versioning, written to every row of validation_runsPatch: bug fix with no change in verdicts. Minor: new check type or optional field. Major: changed meaning of a status, rule or tolerance, or a changed results schema.
Check configurationSource control history, or Delta history for a control tableEvery change traceable to a pull request or ticket.
Results schemaAdditive changes only (ALTER TABLE ... ADD COLUMNS) within a major versionRenaming or removing a column is a major change that includes the semantic model and reports.

Because the framework version is stored with every run, a change in verdicts can be tied to a framework change rather than to the data. When you must compare runs across a major version, filter on framework_version.

When the gate blocks

  1. Read the alert and open the run

    The alert carries environment, suite, run id and counts. Query the failing rows for that run.

    SELECT test_name, status, severity, expected, actual, variance, message
FROM qa.validation_results
WHERE run_id = '<run id from the alert>'
  AND status IN ('FAIL', 'ERROR')
ORDER BY (severity = 'blocker') DESC, test_name;
  2. Classify the failure

    A data defect, an environment problem (ERROR, SKIPPED), a defective check (false positive), or an accepted deviation. Each has a different owner and a different fix.

  3. Act on the class

    Data defect: fix upstream, reload, rerun the suite. Environment: fix and rerun the suite only. Defective check: demote it through change control while it is repaired. Accepted deviation: the data owner approves a time-boxed severity change in source control, with the reason and a review point.

  4. Rerun and confirm the gate is open

    Do not publish by bypassing the pipeline. The recorded run is the evidence.

  5. Close the loop

    If a defect escaped the suite, add the check that would have caught it; if a check cried wolf, tighten or retire it.

Performance and cost

Validation competes with the pipelines it protects. Almost all of its cost is scanning large tables, plus Spark session start-up. Measure before you optimize: duration_s in the results table is the baseline.

SELECT test_name,
       ROUND(AVG(duration_s), 1) AS avg_s,
       ROUND(MAX(duration_s), 1) AS max_s,
       COUNT(*)                  AS runs
FROM qa.validation_results
WHERE run_ts >= current_timestamp() - INTERVAL 14 DAYS
GROUP BY test_name
ORDER BY avg_s DESC
LIMIT 20;

Durations of checks that ran in parallel overlap, so their sum overstates the wall-clock time of the run. Use the run's started_at and finished_at for that.

LeverWhat to doCaution
Scan lessFor a per-load check, restrict the scan to the loaded partitions or time window through a source_filter and target_filter; run full-table checks on a slower schedule. Partitioning that matches the filter lets Spark skip files (see Delta Lake Partitioning Strategy).A windowed check cannot see damage outside its window.
Return numbers, not dataAggregate in SQL and bring back scalars and a handful of sample rows with LIMIT. Never collect() a table to compare it in Python.Collecting distinct values also hides duplicates.
Fuse scansWhen several checks read the same large table, compute their measures in one pass (see below).Fused checks are harder to read; do it only where scans dominate.
Use exact counts for equalityUse approx_count_distinct only for drift and profiling, where an approximation is acceptable.An approximate count cannot prove two numbers equal.
Bound concurrencyStart with a few workers (for example four) and measure. More threads than the cluster can run only queue.Concurrency multiplies when notebooks also run in parallel (see scheduling).
Reuse sessionsShare a Spark session between consecutive suites through a session tag in a pipeline with high concurrency mode.Shared sessions share state; unique temp view names keep suites apart.
Keep tables healthyCompact small files and vacuum within policy on Gold tables and on the results tables (table maintenance).Scan time on a badly fragmented table can dwarf the check logic.
Skip the pointlessUse depends_on so that an expensive check does not run when its prerequisite already failed.Only one level of dependency is supported by the harness.
Cache deliberatelyIf one check reads the same relation repeatedly, CACHE TABLE or DataFrame.cache() it and release it afterwards.A temporary view is not a cache. It is only a name for a query, and each use runs the query again.
 
@check("profile")
def profile(cfg):
    """One scan of the target: row count, key uniqueness, required columns and freshness."""
    key, ts = col(cfg["key"]), col(cfg["timestamp_column"])
    required = cfg.get("not_null", [])
    extra = "".join(f", count_if({col(c)} IS NULL) AS {col('n_' + c)}" for c in required)
    row = one_row(f"""
        SELECT COUNT(*) AS n_rows, COUNT({key}) AS n_keys, COUNT(DISTINCT {key}) AS n_distinct,
               timestampdiff(MINUTE, MAX({ts}), current_timestamp()) AS age_min{extra}
        FROM {quote_name(cfg['target'])}""")
    name = cfg["test_name"]
    out = [
        evaluate(new_result(cfg, test_name=f"{name}.rows", rule="ge",
                            expected=float(cfg.get("min_rows", 1)), actual=num(row["n_rows"]))),
        evaluate(new_result(cfg, test_name=f"{name}.unique_key", rule="eq",
                            expected=num(row["n_keys"]), actual=num(row["n_distinct"]),
                            message="distinct values compared with non-NULL key values")),
        evaluate(new_result(cfg, test_name=f"{name}.fresh", rule="le",
                            expected=float(cfg["max_age_hours"]),
                            actual=None if row["age_min"] is None else row["age_min"] / 60.0,
                            message="age in hours of the newest row")),
    ]
    for c in required:
        out.append(evaluate(new_result(cfg, test_name=f"{name}.{c}.not_null", rule="eq",
                                       expected=0.0, actual=num(row["n_" + c]))))
    return out

Troubleshooting

Sort the symptom first. It usually belongs to one of three families: no verdict at all (an environment problem), a verdict you do not believe (a check design problem), or a verdict that costs too much (a scan problem).

No verdict: environment and naming

SymptomLikely causeFix
Table or view not found, or schema not found, for a four-part nameThe notebook's default lakehouse is not schema-enabled, so schema-qualified names do not resolve as expected; the target lakehouse has no schemas; or a workspace or lakehouse name containing a space or hyphen is not back-quotedUse schema-enabled lakehouses (or no default lakehouse) when you address schemas in code, build names with quote_name, and put the fully resolved name in the check message. See naming.
Permission error reading another workspaceThe identity that runs the notebook in the pipeline cannot read the source itemGrant read access to that identity on the source items, and test with the same identity the pipeline uses, not your own.
T-SQL three-part name across workspaces failsThree-part names resolve inside one workspaceCreate a OneLake shortcut in the querying workspace, or run the check in Spark. See T-SQL versus Spark SQL.
Errors such as invalid cast input or divide by zero appear after a runtime upgradeANSI SQL mode is on by default in the Spark 4 line, so plain CAST and / fail instead of returning NULLUse try_cast, try_divide and NULLIF (the harness does), and run the self-test on both runtimes before moving.
Parameters are ignored and defaults are usedThe cell is not toggled as the parameter cell, names differ, or a value is not a simple typeToggle the parameter cell, print the resolved parameters at the top of the run, and pass structured values as JSON text.
Pipeline sees no exit valueThe notebook failed before reaching exit; exit is not in the last cell or is wrapped in a handler that swallows it; or the notebook type does not return oneKeep exit in its own final cell, route the activity's failure path to the same alert, and test the pipeline end to end once. See the pipeline page.
A reference to another notebook or file by path fails%run resolves notebooks in the same workspace; files from built-in resources use the -b option rather than a workspace pathReference notebooks by name inside one workspace, or package shared code as a library. See Shared Python Libraries.

Verdicts you do not believe

SymptomLikely causeFix
A check passes on obviously wrong dataEmpty source and target (0 = 0), a filter that removes everything, a table compared with itself, or a tolerance wider than the defectSet min_rows, review the configuration, run the self-test and compare both sides' row counts in the message.
The same data gives different verdicts on different daysExpressions that use the current date, late-arriving data, or an unordered samplePass as_of_date, use fixed windows, order samples, and add the late-arrival check.
A tiny numeric difference fails a checkFloating-point accumulation, decimal scale or rounding at different stagesRound both sides to the contract precision, prefer decimals for money, and set the tolerance in the unit of the last reported digit. See precision pitfalls.
Strings match in Spark and differ in T-SQL, or the reverseCollation, trailing spaces or Unicode normalizationCompare in the engine that produced the target, trim explicitly, or apply an explicit COLLATE.
Results appear twice for one runThe activity was retried or the notebook was rerun with the same run_idRetries to zero, or make the writer idempotent (see orchestration).
Key uniqueness reports a huge duplicate groupNULL keys are grouped togetherRead the completeness result for the key column; it reports the cause.
Drift check never fails, or fails every MondayNot enough history yet, or weekly seasonality in the baselineKeep min_history so the check stays quiet until it has a baseline, and compare with the same weekday.
A check starts failing right after an intended schema changeThe contract changed in the data but not in the checkChange the check in the same release, through change control. Never relax a check silently to restore green.

SymptomLikely causeFix

Session start dominates a short suiteEvery activity starts its own sessionUse a session tag with high concurrency mode, or run suites together with runMultiple.

Diagnostic queries

A failing count is a symptom; these find the rows. Use the same filters as the check, and keep the results to a sample.

-- In the source, not in the target
SELECT s.order_id
FROM DEV_SALES_SLV.LH_SALES_SLV.dbo.orders AS s
LEFT ANTI JOIN DEV_SALES_GLD.LH_SALES_GLD.dbo.fact_orders AS t ON t.order_id = s.order_id
WHERE s.order_status <> 'VOID'
LIMIT 20;

-- In the target, not in the source
SELECT t.order_id
FROM DEV_SALES_GLD.LH_SALES_GLD.dbo.fact_orders AS t
LEFT ANTI JOIN DEV_SALES_SLV.LH_SALES_SLV.dbo.orders AS s ON s.order_id = t.order_id
LIMIT 20;

-- Duplicated keys in the target
SELECT order_id, COUNT(*) AS copies
FROM DEV_SALES_GLD.LH_SALES_GLD.dbo.fact_orders
GROUP BY order_id
HAVING COUNT(*) > 1
ORDER BY copies DESC
LIMIT 20;

Common pitfalls

PitfallWhy it hurtsInstead
Treating a temporary view as a cacheEach use re-runs the query, so "read once" designs read many times and can see data that changed in betweenUse views as names; cache explicitly only where measured to help
Replacing COUNT(*) with DataFrame.count() for speedThey compile to the same plan, so there is nothing to gainChoose the form that is clearer; spend effort on scan size instead
Comparing a table with a result derived from itselfThe check can only passDerive expected values from the source side
Letting a check pass on empty input0 = 0 and an empty result are the most common silent failuresMinimum-row guards and fail-closed ERROR handling
Hard-coded dates or fiscal rangesThe check is correct for one period and wrong afterwardsDerive windows from as_of_date and parameters
Widening tolerance to get a green runThe suite stops testing what it was built to testAccount for expected rejects, and change tolerances only through the data owner
Collecting data to the driver to compare itIt does not scale and hides duplicates when compared as setsKeyed joins and EXCEPT ALL in Spark
Gating on a read through the SQL analytics endpoint right after a writeThe endpoint can lag the write and the gate reads the previous runGate on the exit value, or refresh first
Making every check a blocker on day oneOne false positive teaches everyone to bypass the gateShadow, warn, then block, as in the lifecycle
A framework that only the author understandsThe first absence turns every red run into a mysteryCheck notes, owner roles, the self-test and this page

Key takeaways

  • Give every decision one accountable role, and put checks and configuration through the same change process as the code they protect.
  • Introduce checks as shadow, then warning, then blocker; demote flaky blockers instead of muting them.
  • Test the framework with seeded defects and clean controls, and version it so that a change in verdicts can be traced to a change in the framework.
  • Most cost is scan cost: restrict scans, return numbers instead of data, fuse scans where they dominate, and bound concurrency.
  • Triage symptoms into no verdict, wrong verdict or slow, and diagnose with the matching table.
