Complex and extended checks

The first half covers the checks that make framework A heavier than the standard suite: recalculating a windowed, aggregated metric independently, validating enrichment joins, sentinel rows and derived calendar columns. The second half adds the checks that every framework should have and the source frameworks lacked: uniqueness, completeness, referential integrity, drift, layer reconciliation and late-arriving data.

How the code on this page fits

Every cell registers a check with the harness from Harness and core checks. Run cells 1 to 3 of that page first. The checks reuse quote_name, col, temp_views, one_row, new_result, evaluate, run_check, and the globals env, AS_OF and results_schema. Add the configuration rows to the CONFIG list and set suite to the suite name.

Complex metric validation (framework A)

The running example is a workforce fact table in the HR domain. Silver holds timesheet entries (timesheet_entries: employee, department, period, hours). Gold holds fact_workforce_fte, where full-time equivalent (FTE) is the hours worked in a fiscal period divided by the standard hours in a period, restricted to a rolling window of fiscal years. The validation recomputes that table from Silver and compares it key by key.

Dynamic fiscal-year filtering

Gold tables for planning and workforce reporting are usually windowed: current fiscal year, a year or two back for comparison, sometimes a year ahead for budget. The validation has to apply the same window to the Silver recalculation. Typing the year range into the check (for example a literal range of three fiscal years) makes the check correct on the day it is written and wrong when the fiscal year rolls over, and it is wrong silently: the new year's rows simply fall outside the checked range. Derive the window from the run's as_of_date instead.

A fiscal year is named for the calendar year in which it ends, and starts in a configurable month. For a fiscal year that starts in month S, a date belongs to fiscal year year(d) when S is 1 or the month is before S, and to year(d) + 1 otherwise. The helper below produces that as a SQL expression, so the engine evaluates it for the current date and for each row.

FISCAL_START_MONTH = 7              # month the fiscal year starts; the year is named for the year it ends in
HOURS_PER_PERIOD = "173.3333333"    # policy parameter: standard hours in one period (annual hours / 12)

def fiscal_year_sql(date_expr: str, start_month: int = FISCAL_START_MONTH) -> str:
    m = int(start_month)
    if not 1 <= m <= 12:
        raise ValueError("start_month must be between 1 and 12")
    return f"(year({date_expr}) + CASE WHEN {m} > 1 AND month({date_expr}) >= {m} THEN 1 ELSE 0 END)"

CURRENT_FY = fiscal_year_sql(AS_OF)   # evaluated by Spark for the run's as_of_date

def in_window(fiscal_year_expr: str, years_back: int, years_ahead: int) -> str:
    return (f"{fiscal_year_expr} BETWEEN {CURRENT_FY} - {int(years_back)} "
            f"AND {CURRENT_FY} + {int(years_ahead)}")

def scalar(sql: str):
    return spark.sql(sql).first()[0]

Parameters are part of the definition

The fiscal start month and the standard hours per period are business policy, not implementation details. The check must use the same values as the pipeline that builds Gold. Keep them in one place (a variable library, see Variable Libraries) and read them in both notebooks. If you copy the divisor into the check, you will eventually change one and not the other, and the check will fail for the right reason and look like a bug in the check.

Aggregation logic and the metric check

The check applies the Gold table's aggregation to Silver at a stated grain (the set of keys that identifies one Gold row), applies the same window to both sides, aggregates Gold at the same grain (so extra detail columns in Gold cannot cause false differences), and joins the two on the grain with a full outer join. It reports three things for each measure: grain rows present on only one side, grain rows whose measure differs by more than a cell tolerance, and the difference between the grand totals.

@check("metric")
def metric(cfg):
    grain = [col(k) for k in cfg["grain"]]
    grain_list = ", ".join(grain)
    on = " AND ".join(f"s.{g} <=> t.{g}" for g in grain)
    key_select = ", ".join(f"coalesce(s.{g}, t.{g}) AS {g}" for g in grain)
    src_where, tgt_where = cfg.get("source_filter", "TRUE"), cfg.get("target_filter", "TRUE")
    if cfg.get("window"):
        w = cfg["window"]
        src_where += " AND " + in_window(w["source_fiscal_year_expr"], w["years_back"], w["years_ahead"])
        tgt_where += " AND " + in_window(w["target_fiscal_year_expr"], w["years_back"], w["years_ahead"])
    src_rel = cfg.get("source_sql") or f"SELECT * FROM {quote_name(cfg['source'])}"   # may contain joins
    ms = cfg["measures"]
    differs = {m["name"]: (f"abs(coalesce(s.{col(m['name'])}, 0) - coalesce(t.{col(m['name'])}, 0)) "
                           f"> {float(m.get('cell_tolerance', 0.0))!r}") for m in ms}
    with temp_views(
        src=(f"SELECT {grain_list}, 1 AS _present, "
             + ", ".join(f"{m['source_expr']} AS {col(m['name'])}" for m in ms)
             + f" FROM ({src_rel}) x WHERE {src_where} GROUP BY {grain_list}"),
        tgt=(f"SELECT {grain_list}, 1 AS _present, "
             + ", ".join(f"SUM({col(m['target_column'])}) AS {col(m['name'])}" for m in ms)
             + f" FROM {quote_name(cfg['target'])} WHERE {tgt_where} GROUP BY {grain_list}"),
    ) as v:
        join = f"FROM {v['src']} s FULL OUTER JOIN {v['tgt']} t ON {on}"
        both = "s._present IS NOT NULL AND t._present IS NOT NULL"
        select = ["count_if(s._present IS NOT NULL) AS src_rows", "count_if(t._present IS NOT NULL) AS tgt_rows",
                  "count_if(t._present IS NULL) AS missing_in_target",
                  "count_if(s._present IS NULL) AS missing_in_source"]
        for n, pred in differs.items():
            select += [f"count_if({both} AND {pred}) AS {col(n + '__cells')}",
                       f"coalesce(sum(s.{col(n)}), 0) AS {col(n + '__src')}",
                       f"coalesce(sum(t.{col(n)}), 0) AS {col(n + '__tgt')}"]
        c = one_row("SELECT " + ", ".join(select) + " " + join)
        sample = []
        if c["missing_in_target"] or c["missing_in_source"] or any(c[n + "__cells"] for n in differs):
            sample_cols = ", ".join(f"s.{col(n)} AS {col(n + '__src')}, t.{col(n)} AS {col(n + '__tgt')}"
                                    for n in differs)
            bad = " OR ".join(["t._present IS NULL", "s._present IS NULL"] + list(differs.values()))
            sample = [r.asDict() for r in spark.sql(
                f"SELECT {key_select}, {sample_cols} {join} WHERE {bad} LIMIT 5").collect()]
    name = cfg["test_name"]
    out = [evaluate(new_result(
        cfg, test_name=f"{name}.grain", expected=0.0,
        actual=float(c["missing_in_target"] + c["missing_in_source"]),
        message=(f"grain rows source={c['src_rows']:,} target={c['tgt_rows']:,} "
                 f"missing_in_target={c['missing_in_target']:,} missing_in_source={c['missing_in_source']:,}"),
        detail=json.dumps({"sample": sample}, default=str)))]
    for m in ms:
        n = m["name"]
        out.append(evaluate(new_result(
            cfg, test_name=f"{name}.{n}.cells", expected=0.0, actual=float(c[n + "__cells"]),
            message=f"{c[n + '__cells']:,} of {c['src_rows']:,} grain rows differ by more than {m.get('cell_tolerance', 0.0)}")))
        out.append(evaluate(new_result(
            cfg, test_name=f"{name}.{n}.total", expected=num(c[n + "__src"]), actual=num(c[n + "__tgt"]),
            tolerance=float(m.get("total_tolerance", m.get("cell_tolerance", 0.0))),
            message=f"total source={c[n + '__src']} target={c[n + '__tgt']}")))
    return out

The measure expressions restate the definition as a business rule would: FTE = hours / standard hours per period, rounded to the scale Gold stores. Keep the divisor a decimal literal. Mixing doubles into the arithmetic makes equality brittle; compare at the stored scale with a tolerance of half a unit in the last digit (cell_tolerance), and apply a separate, small total_tolerance to the sums if rounding accumulates across many rows.

When the Gold row is built from joins (for example timesheets joined to an earnings-type table and filtered to productive and non-productive categories), put the same joins in source_sql instead of source. The query is wrapped as a subquery, so it can use joins, filters and derived columns, and the check stays the same.

FTE_SOURCE_SQL = f"""
    SELECT t.*, e.pay_category
    FROM {quote_name(f'{HRS}.timesheet_entries')} t
    LEFT JOIN {quote_name(f'{HRS}.earning_types')} e ON t.earning_code = e.earning_code
    WHERE e.pay_category IN ('PRODUCTIVE', 'NON_PRODUCTIVE')"""

Success criteria

  • Grain coverage: no grain row exists on one side only, within the window.
  • Every measure matches within its cell tolerance on every grain row.
  • Grand totals match within the total tolerance.
  • The window is derived from as_of_date; no year is typed into the check.

Enrichment-join coverage

A fact is often enriched by a left join to an attribute table, for example employee tenure bands taken from the latest headcount snapshot. Two things can go wrong without changing any single-table count in an obvious way: the lookup has duplicate keys and the join multiplies rows (fan-out), or the join silently stops matching (a changed key format, an empty snapshot) and the attribute becomes NULL for most rows. A check that only asks "is the column populated for more than zero rows" accepts both.

Derive the expectation instead. Run the same left join in Silver, compute what share of base rows match, and require Gold's populated share to equal it. Compare row counts before and after the join to catch fan-out.

@check("join_coverage")
def join_coverage(cfg):
    bk, lk, tc = col(cfg["base_key"]), col(cfg["lookup_key"]), col(cfg["target_column"])
    with temp_views(
        base=f"SELECT * FROM {quote_name(cfg['source'])}",
        lookup=cfg["lookup_sql"],                      # e.g. the latest snapshot of the attribute table
        tgt=f"SELECT * FROM {quote_name(cfg['target'])}",
    ) as v:
        row = one_row(f"""
            SELECT (SELECT COUNT(*) FROM {v['base']})                                     AS base_rows,
                   (SELECT COUNT(*) FROM {v['base']} b
                      LEFT JOIN {v['lookup']} l ON b.{bk} = l.{lk})                        AS joined_rows,
                   (SELECT try_divide(100.0 * count_if(l.{lk} IS NOT NULL), COUNT(*))
                      FROM {v['base']} b LEFT JOIN {v['lookup']} l ON b.{bk} = l.{lk})     AS expected_pct,
                   (SELECT try_divide(100.0 * count_if({tc} IS NOT NULL), COUNT(*))
                      FROM {v['tgt']})                                                     AS actual_pct""")
    name = cfg["test_name"]
    return [
        evaluate(new_result(cfg, test_name=f"{name}.fanout", expected=num(row["base_rows"]),
                            actual=num(row["joined_rows"]),
                            message=f"base={row['base_rows']:,} after join={row['joined_rows']:,}")),
        evaluate(new_result(cfg, test_name=f"{name}.coverage", rule="ge",
                            expected=num(row["expected_pct"]), actual=num(row["actual_pct"]),
                            tolerance=float(cfg.get("tolerance", 0.0)), tolerance_type="absolute",
                            message=f"{cfg['target_column']} populated: expected {row['expected_pct']}% "
                                    f"actual {row['actual_pct']}%")),
    ]

Success criteria: the join does not change the row count; the populated share in Gold is at least the share the join implies. Use rule: ge when extra matches are harmless and eq when Gold must reproduce the coverage exactly.

Sentinel-row (unknown member) union

Dimensions commonly union one synthetic row (key 0, description "Unknown") to the real rows so that facts with missing references still join. The expected row count is the source count plus one, and exactly one sentinel must exist. Two failure modes matter: the sentinel is missing (facts drop out of reports) and it is duplicated (every join against it doubles).

@check("sentinel_row")
def sentinel_row(cfg):
    with temp_views(
        src=f"SELECT * FROM {quote_name(cfg['source'])} WHERE {cfg.get('source_filter', 'TRUE')}",
        tgt=f"SELECT * FROM {quote_name(cfg['target'])}",
    ) as v:
        row = one_row(f"""
            SELECT (SELECT COUNT(*) FROM {v['src']}) + 1                                AS expected_rows,
                   (SELECT COUNT(*) FROM {v['tgt']})                                    AS actual_rows,
                   (SELECT COUNT(*) FROM {v['tgt']} WHERE {cfg['sentinel_predicate']})  AS sentinel_rows""")
    name = cfg["test_name"]
    return [
        evaluate(new_result(cfg, test_name=f"{name}.rows", expected=num(row["expected_rows"]),
                            actual=num(row["actual_rows"]),
                            message=f"source rows + 1 = {row['expected_rows']:,}, target = {row['actual_rows']:,}")),
        evaluate(new_result(cfg, test_name=f"{name}.sentinel", expected=1.0, actual=num(row["sentinel_rows"]),
                            message=f"{row['sentinel_rows']} sentinel row(s) matching {cfg['sentinel_predicate']}")),
    ]

Configure it with "sentinel_predicate": "project_key = 0" (or whatever identifies the unknown member). If the main data is filtered before the union (for example only one hierarchy of a project tree is kept), put the same filter in source_filter so the expected count follows the pipeline's intent.

Derived calendar columns

Labels and flags that were authored in a dataflow or in Power Query M (a period label, a "past period" flag, a default sort order, current-year flags) are easy to get subtly wrong when they are re-implemented, and they are easy to validate: restate each as a SQL expression and run the keyed transformation check on it. The wrapper below expands one configuration row into one transformation check per column.

@check("derived_columns")
def derived_columns(cfg):
    results = []
    for target_column, expr in cfg["columns"].items():
        sub = {**cfg, "check_type": "transformation", "test_name": f"{cfg['test_name']}.{target_column}",
               "expected_expr": expr, "target_column": target_column}
        results.extend(run_check(sub))          # an error in one column does not stop the others
    return results

Time-dependent columns drift between refreshes

A flag computed from the current date is correct only on the day Gold was refreshed. If the refresh ran yesterday and validation runs after midnight, is_past_period legitimately differs on the boundary day. Validate shortly after the refresh and pass the refresh date as as_of_date. Both sides then use the same "today", and the check still catches wrong logic.

Key uniqueness

Expected is zero surplus rows: the number of rows beyond the first for each key value. Run this before any keyed comparison and declare the keyed checks as depends_on it, so duplicates produce one red result instead of many confusing ones.

@check("unique")
def unique_key(cfg):
    keys = ", ".join(col(k) for k in cfg["key"])
    with temp_views(tgt=f"SELECT * FROM {quote_name(cfg['target'])} WHERE {cfg.get('target_filter', 'TRUE')}") as v:
        grouped = f"SELECT {keys}, COUNT(*) AS cnt FROM {v['tgt']} GROUP BY {keys}"
        row = one_row(f"""
            SELECT COALESCE(SUM(cnt), 0) AS total_rows, COALESCE(SUM(cnt - 1), 0) AS surplus_rows,
                   count_if(cnt > 1) AS duplicated_keys
            FROM ({grouped}) g""")
        sample = []
        if row["surplus_rows"]:
            sample = [r.asDict() for r in spark.sql(
                f"SELECT * FROM ({grouped}) g WHERE cnt > 1 ORDER BY cnt DESC LIMIT 5").collect()]
    return evaluate(new_result(
        cfg, expected=0.0, actual=num(row["surplus_rows"]),
        message=f"{row['duplicated_keys']:,} duplicated key value(s) in {row['total_rows']:,} rows",
        detail=json.dumps({"sample": sample}, default=str)))

NULL key values are grouped together by GROUP BY, so a table with many NULL keys reports them as one large duplicate. That is the right signal, and the completeness check below reports the cause.

Null and completeness

One scan computes the NULL count of every listed column. Each column becomes its own result, so a dashboard can show which column regressed. The rule is ge: expected is the minimum percent populated (100 for keys, lower for optional attributes), derived from the source rather than guessed.

@check("completeness")
def completeness(cfg):
    cols = cfg["columns"]
    floors = cfg.get("min_pct_by_column", {})
    aggs = ", ".join(f"count_if({col(c)} IS NULL) AS {col('n_' + c)}" for c in cols)
    with temp_views(tgt=f"SELECT * FROM {quote_name(cfg['target'])} WHERE {cfg.get('target_filter', 'TRUE')}") as v:
        row = one_row(f"SELECT COUNT(*) AS total, {aggs} FROM {v['tgt']}")
    results = []
    for c in cols:
        nulls, total = row["n_" + c], row["total"]
        pct = 100.0 * (total - nulls) / total if total else 0.0
        results.append(evaluate(new_result(
            cfg, test_name=f"{cfg['test_name']}.{c}", rule="ge",
            expected=float(floors.get(c, cfg.get("min_pct", 100.0))), actual=pct,
            message=f"{c}: {pct:.2f}% populated ({nulls:,} NULL of {total:,})")))
    return results

Format and domain integrity rules

A rule is a SQL predicate that is true for valid rows. The check counts rows for which the predicate is not true. NULL evaluates to "not true", so write col IS NULL OR ... when NULL is allowed; that makes nullability an explicit part of the rule rather than an accident of three-valued logic.

@check("rule")
def rule_check(cfg):
    with temp_views(tgt=f"SELECT * FROM {quote_name(cfg['target'])} WHERE {cfg.get('target_filter', 'TRUE')}") as v:
        row = one_row(f"""
            SELECT COUNT(*) AS total,
                   count_if(NOT coalesce(({cfg['valid_when']}), false)) AS violations
            FROM {v['tgt']}""")
        sample = []
        if row["violations"]:
            sample = [r.asDict() for r in spark.sql(
                f"SELECT * FROM {v['tgt']} WHERE NOT coalesce(({cfg['valid_when']}), false) LIMIT 5").collect()]
    return evaluate(new_result(
        cfg, expected=0.0, actual=num(row["violations"]),
        message=f"{row['violations']:,} of {row['total']:,} rows violate: {cfg['valid_when']}",
        detail=json.dumps({"sample": sample}, default=str)))

Referential integrity

Spark does not enforce foreign keys, so a fact can reference a dimension row that does not exist. The check counts fact rows whose key is missing from the dimension. The dimension side is de-duplicated first so a duplicate dimension key cannot multiply fact rows. NULL foreign keys are reported separately because whether they are acceptable is a modeling decision (often they should point at the sentinel row instead).

@check("referential")
def referential(cfg):
    fk, pk = col(cfg["fk"]), col(cfg["pk"])
    with temp_views(
        fact=f"SELECT {fk} FROM {quote_name(cfg['target'])} WHERE {cfg.get('target_filter', 'TRUE')}",
        dim=f"SELECT DISTINCT {pk} FROM {quote_name(cfg['dimension'])}",
    ) as v:
        row = one_row(f"""
            SELECT COUNT(*)                                          AS fact_rows,
                   count_if(f.{fk} IS NULL)                          AS null_fks,
                   count_if(f.{fk} IS NOT NULL AND d.{pk} IS NULL)   AS orphans
            FROM {v['fact']} f LEFT JOIN {v['dim']} d ON f.{fk} = d.{pk}""")
        sample = []
        if row["orphans"]:
            sample = [r.asDict() for r in spark.sql(f"""
                SELECT f.{fk}, COUNT(*) AS fact_rows FROM {v['fact']} f LEFT JOIN {v['dim']} d ON f.{fk} = d.{pk}
                WHERE f.{fk} IS NOT NULL AND d.{pk} IS NULL GROUP BY f.{fk} ORDER BY 2 DESC LIMIT 5""").collect()]
    violations = row["orphans"] + (0 if cfg.get("allow_null_fk", True) else row["null_fks"])
    return evaluate(new_result(
        cfg, rule="le", expected=float(cfg.get("max_orphans", 0)), actual=float(violations),
        message=f"{row['orphans']:,} orphaned and {row['null_fks']:,} NULL foreign key(s) in {row['fact_rows']:,} rows",
        detail=json.dumps({"sample": sample}, default=str)))

A documented ceiling (max_orphans) with severity warning is the honest way to handle a known legacy exception. It catches a regression without pretending the exception is not there.

Distribution drift

Some defects keep every count intact and change what the data means: a unit conversion applied twice, a currency column loaded in the wrong scale, an upstream system that starts sending zeros. The drift check compares a statistic (an average, a NULL percentage, a distinct count) with the mean and spread of the same statistic in recent runs, read from the results table itself. There is no separate baseline store to maintain, and runs that failed are excluded from the baseline.

@check("drift")
def drift(cfg):
    stat = one_row(f"""SELECT CAST({cfg['expr']} AS DOUBLE) AS value
                       FROM {quote_name(cfg['target'])} WHERE {cfg.get('target_filter', 'TRUE')}""")["value"]
    if stat is None:
        return new_result(cfg, status="ERROR", message="statistic is NULL")
    hist = spark.sql(f"""
        SELECT COUNT(*) AS n, AVG(actual) AS mean, STDDEV_SAMP(actual) AS sd
        FROM (SELECT actual FROM {quote_name(results_schema + '.validation_results')}
              WHERE test_name = :t AND environment = :e
                AND status IN ('PASS', 'WARN') AND actual IS NOT NULL
              ORDER BY run_ts DESC LIMIT {int(cfg.get('history_runs', 14))}) h""",
        args={"t": cfg["test_name"], "e": env}).first()      # parameter markers: Spark 3.4 and later
    value, severity = float(stat), cfg.get("severity", "warning")
    needed = int(cfg.get("min_history", 5))
    if hist["n"] < needed:                                    # still building the baseline
        return evaluate(new_result(cfg, severity=severity, expected=value, actual=value,
                                   message=f"building baseline: {hist['n']} of {needed} runs"))
    tolerance = max(float(cfg.get("sigmas", 3.0)) * float(hist["sd"] or 0.0), float(cfg.get("min_tolerance", 0.0)))
    return evaluate(new_result(
        cfg, severity=severity, expected=float(hist["mean"]), actual=value, tolerance=tolerance,
        tolerance_type="absolute", message=f"value={value:.4g} baseline={float(hist['mean']):.4g} "
                                           f"tolerance={tolerance:.4g} from {hist['n']} runs"))

Parameter markers for values, validation for names

Spark 3.4 and later (so Runtime 1.3 and Runtime 2.0) accept named parameter markers (:name) with an args dictionary, which is the right way to pass values such as a test name into SQL. Identifiers (table and column names) cannot be parameterized that way, which is why the harness validates and quotes them in quote_name and col.

Reconciliation between layers

A row-count comparison between Bronze and Silver is rarely meaningful on its own, because the Silver pipeline deduplicates and quarantines rows. Reconciliation states the equation: Bronze rows minus duplicates minus rejected rows equals Silver rows. Each term is a scalar query, and the check compares the two sides with the same tolerance logic as every other check. Because each term is explicit, a failure tells you which term is unexplained.

@check("reconcile")
def reconcile(cfg):
    terms = [(float(sign), float(scalar(sql))) for sign, sql in cfg["expected_terms"]]
    expected = sum(sign * value for sign, value in terms)
    actual = float(scalar(cfg["actual_sql"]))
    return evaluate(new_result(
        cfg, expected=expected, actual=actual,
        message="expected = " + " ".join(f"{'+' if s > 0 else '-'} {v:,.0f}" for s, v in terms)
                + f" = {expected:,.0f}; actual = {actual:,.0f}",
        detail=json.dumps({"terms": terms})))

BRZ = f"{env}_SALES_BRZ.LH_SALES_BRZ.dbo"
t_bronze, t_silver = quote_name(f"{BRZ}.orders_raw"), quote_name(f"{SLV}.orders")
t_rejects = quote_name(f"{SLV}.orders_rejected")

CONFIG += [
    {"suite": "reconcile", "test_name": "orders.bronze_to_silver", "check_type": "reconcile",
     "source": f"{BRZ}.orders_raw", "target": f"{SLV}.orders",
     "expected_terms": [
         [1,  f"SELECT COUNT(*) FROM {t_bronze}"],
         [-1, f"SELECT COUNT(*) - COUNT(DISTINCT order_id) FROM {t_bronze}"],
         [-1, f"SELECT COUNT(*) FROM {t_rejects}"],
     ],
     "actual_sql": f"SELECT COUNT(*) FROM {t_silver}"},
]

The same check type covers cross-layer balance reconciliation: use SELECT SUM(amount) terms for each side. When a layer is incremental, constrain every term to the same load window (a batch identifier or a date range), otherwise a late arrival in Bronze shows up as a difference that is not a defect.

Late-arriving data

Late-arriving rows are normal in event and transaction feeds. They become a defect when they arrive after the period they belong to was closed and published, because reports already issued no longer match the table. The check measures two things over a recent ingest window: the share of rows that arrived later than an allowed lag, and, optionally, how many arrived for a period that is already closed.

@check("late_arrival")
def late_arrival(cfg):
    ev, ing = col(cfg["event_column"]), col(cfg["ingest_column"])
    lag_h, window_h = float(cfg["max_lag_hours"]), int(cfg["window_hours"])
    closed = cfg.get("closed_before_sql")             # e.g. "date_trunc('month', current_date())"
    closed_expr = f"count_if({ev} < {closed})" if closed else "CAST(0 AS BIGINT)"
    row = one_row(f"""
        SELECT COUNT(*) AS rows_in_window,
               count_if(timestampdiff(MINUTE, {ev}, {ing}) / 60.0 > {lag_h}) AS late_rows,
               {closed_expr} AS into_closed
        FROM {quote_name(cfg['target'])}
        WHERE {ing} >= current_timestamp() - INTERVAL {window_h} HOURS""")
    total = row["rows_in_window"]
    late_pct = 100.0 * row["late_rows"] / total if total else 0.0
    name, severity = cfg["test_name"], cfg.get("severity", "warning")
    out = [evaluate(new_result(
        cfg, test_name=f"{name}.late_share", severity=severity, rule="le",
        expected=float(cfg.get("max_late_pct", 1.0)), actual=late_pct,
        message=f"{row['late_rows']:,} of {total:,} rows ({late_pct:.2f}%) arrived more than {lag_h:g} h after the event"))]
    if closed:
        out.append(evaluate(new_result(
            cfg, test_name=f"{name}.closed_periods", severity=cfg.get("closed_severity", "blocker"),
            expected=0.0, actual=float(row["into_closed"]),
            message=f"{row['into_closed']:,} row(s) arrived for an already closed period")))
    return out

What to do about late data is a design decision, not a validation one: reprocess a lookback window on every load, route late rows to a correction table, or accept restatement. The check's job is to make the volume visible and to stop a release when closed periods change without anyone deciding that they should.

Semantic model parity

A correct Gold table can still produce a wrong report: a measure with a filter nobody remembers, a relationship that fans out, a model that was never refreshed. A parity check evaluates a measure in the semantic model and compares it with an aggregate computed straight from the lakehouse. Semantic link runs the DAX query from the notebook, so the comparison fits the same harness and the same results table.

import sempy.fabric as fabric

@check("model_measure")
def model_measure(cfg):
    dax = f'EVALUATE ROW("value", {cfg["measure"]})'          # the measure, with no filters applied
    value = fabric.evaluate_dax(cfg["model"], dax, workspace=cfg.get("model_workspace")).iloc[0, 0]
    actual = None if value is None or value != value else float(value)       # BLANK or NaN becomes None
    expected = float(scalar(cfg["expected_sql"]))
    return evaluate(new_result(cfg, expected=expected, actual=actual,
                               message=f"model {cfg['model']} {cfg['measure']} = {actual}; lakehouse = {expected}"))

Key takeaways

  • Derive time windows from as_of_date; a typed-in fiscal range is a check that expires.
  • Recalculate metrics independently at a stated grain, apply the same window to both sides, and report grain coverage, cell differences and totals as separate results.
  • Derive expectations (join coverage, row equations) from the source instead of choosing round numbers or loosening tolerances.
  • Add uniqueness, completeness, referential and rule checks to every framework; they are cheap and catch what counts cannot.
  • Use drift and late-arrival checks as warnings that inform owners, and make uniqueness a dependency of keyed comparisons.
