Playbook 15 · QA Validation

Architecture and design principles

The three framework variants, what each can check, the four principles that keep the notebooks simple and safe to run in parallel, how the workspaces fit together, and the naming rules that decide whether a table reference resolves. The naming section includes the Fabric specifics that cause most first-run failures.

The three frameworks

All three frameworks share the same plumbing (parameters, helpers, configuration list, runner, results writer, exit value). What differs is the kind of statement each check has to make about the data, and therefore how much domain logic you restate in SQL. Pick by the hardest thing you need to prove, not by table count.

Framework A: complex metric validation (workforce headcount and FTE)

Purpose. Prove that a Gold measure that is the product of windowing, joins and aggregation equals what an independent calculation from Silver produces. The running example is a workforce fact table where full-time-equivalent (FTE) is hours worked divided by a standard number of hours per period.

  • Rolling fiscal-year window. The window is derived from an as-of date and the fiscal calendar, not typed in. See dynamic fiscal-year filtering.
  • Aggregation at a stated grain. Group by the keys that define one Gold row, compute the measure with an explicit divisor and rounding rule, then compare key by key.
  • Enrichment joins. A left join from a fact to an attribute table (for example employee tenure bands) must neither multiply rows nor lose coverage.
  • Sentinel rows. Dimensions that union an "unknown member" row to the real data must contain exactly one such row.
  • Derived calendar columns. Labels and flags that were authored in a dataflow or Power Query are re-expressed in SQL and compared.

Typical objects: dim_calendar, dim_department, dim_employee, dim_project, fact_workforce_fte, fact_workforce_fte_detail, fact_employee_tenure.

Framework B: standard validation suite

Purpose. Broad, cheap coverage for tables that are copied or lightly transformed between layers. Three or four check types applied consistently beat one clever check applied to one table.

  • Row count between source and target, with a stated filter when the pipeline legitimately drops rows.
  • Transformation checks for derived columns such as customer_label = customer_code || ' - ' || customer_name.
  • Schema contract for tables that downstream models depend on, including derived columns.
  • Freshness so that a green count on stale data does not pass.

Typical objects: dim_customer, dim_product, dim_region, fact_orders.

Framework C: financial statement reconciliation

Purpose. Validate fact and dimension tables behind a financial statement where totals have to tie out and the data has to be recent and well-formed.

  • Row count and transformation as in framework B, with null checks on the transformed column.
  • Freshness against a load timestamp with an explicit service level.
  • Integrity rules: period labels match a format (YYYY-MM), flags only hold allowed values (0 or 1), optional flag columns follow their nullability rules.
  • Balance reconciliation: sums of amounts by period and account tie out between layers within a tolerance.

Typical objects: fact_income_statement, dim_account, dim_business_unit, dim_fund.

Design principles

1. Self-contained notebooks

Each framework is one notebook that carries its own helpers, configuration and writer. It imports only what the Fabric runtime already provides (pyspark, the standard library, notebookutils). The reasons are operational: deployment is a single item, a review shows the whole behavior in one diff, and a notebook can be run from a pipeline or interactively without checking that a package or configuration file is present in the environment.

Self-contained is a starting point, not a dogma

The cost is duplicated helpers. When more than three notebooks carry the same quote_name, temp_views and evaluate code, move it to a versioned library in a Fabric environment (see Shared Python Libraries) and keep the checks themselves in the notebooks.

2. SQL first

State the comparison in Spark SQL and let the engine execute it. Python receives a handful of numbers (counts, sums, violation totals) and a small sample of offending rows; it never receives the data.

# Good: the engine counts, the driver receives two numbers
row = spark.sql(f"""
    SELECT (SELECT COUNT(*) FROM {v['src']}) AS expected,
           (SELECT COUNT(*) FROM {v['tgt']}) AS actual
""").first()

# Bad: moves every row to the driver and compares in Python
# silver_values = {r[0] for r in silver_df.collect()}

A common misconception about speed

Calling DataFrame.count() and running SELECT COUNT(*) compile to the same Spark plan, so switching between them does not make a check faster. What makes checks fast is scanning each table once, filtering early, avoiding collect() on large results and not running the same expensive query twice. Performance guidance covers the real levers.

SQL-first also keeps the logic portable: the statements can be pasted into a SQL cell or the lakehouse SQL editor for debugging, and many translate to T-SQL for warehouse checks (see T-SQL versus Spark SQL).

3. The temporary-view pattern

A check names the relations it compares as session-scoped temporary views whose names carry a random suffix, runs its SQL against those names, and drops them in a finally block. A view is just a named query, so creating one reads no data; the point is to define the filtered or projected relation once, keep the comparison SQL short, and make the statements easy to run by hand.

Unique names matter whenever more than one check can run in a session. Notebooks launched through notebookutils.notebook.run or runMultiple execute on the Spark session of the caller, and a thread pool inside one notebook shares one session by definition. Treat temp view names as shared in all of those cases; a static name such as tmp_src lets one check replace another's view mid-flight and produces results that are wrong but plausible.

import uuid

suffix = uuid.uuid4().hex[:10]            # not a timestamp: two threads can share a millisecond
src_view, tgt_view = f"qa_src_{suffix}", f"qa_tgt_{suffix}"
try:
    spark.sql(f"CREATE OR REPLACE TEMPORARY VIEW {src_view} AS SELECT * FROM `DEV_HR_SLV`.`LH_HR_SLV`.`dbo`.`employees`")
    spark.sql(f"CREATE OR REPLACE TEMPORARY VIEW {tgt_view} AS SELECT * FROM `DEV_HR_GLD`.`LH_HR_GLD`.`dbo`.`dim_employee`")
    # ... run the comparison SQL against src_view and tgt_view ...
finally:
    spark.catalog.dropTempView(src_view)
    spark.catalog.dropTempView(tgt_view)

Temp views are not a cache

A temporary view is re-planned and re-executed by every query that uses it. If a check needs to read the same large relation several times, cache the result (CACHE TABLE or DataFrame.cache()) or compute all the aggregates in one statement. Do not expect the view alone to give you a single read.

4. Structured results

Every check returns one or more Result objects with the same fields, and the notebook writes them in a single append to a Delta table. The fields are designed so that a failure can be understood from the row alone: what was compared, expected versus actual, the variance, the tolerance applied and the rule that decided the status. Results model and tolerances defines the schema.

Fail closed

A check that cannot run (missing table, permission error, syntax error) is recorded as ERROR and counts against the gate exactly like a failure. A validation framework that treats exceptions as "nothing to report" reports green on a broken pipeline.

Naming conventions and fully qualified names

Object names

Workspaces follow <ENV>_<DOMAIN>_<LAYER>[_<Qualifier>] and items follow <ARTIFACT>_<DOMAIN>_<LAYER>_<Function>, as in the rest of this site (DEV_HR_SLV, LH_HR_GLD, NB_HR_GLD_QaComplexMetrics). For the tables themselves, avoid encoding the layer, the source system or the pipeline in the table name: the layer is already in the workspace and lakehouse name. Using the same logical table name in Silver and Gold where it makes sense, and dim_ and fact_ prefixes in Gold, keeps the configuration for a check to two short strings. If your existing tables carry layer prefixes, put the mapping in the configuration rather than renaming tables for the sake of the framework.

Four-part names and cross-workspace queries

A table in a schema-enabled lakehouse is addressed as workspace.lakehouse.schema.table. Omitted parts are resolved from the notebook's defaults, so a bare table name means the dbo schema of the default lakehouse. Because validation reads two lakehouses that usually live in two other workspaces, always write all four parts in check configuration.

Key learnings

  • The name depends on the lakehouse type. Four parts for a schema-enabled lakehouse (workspace.lakehouse.schema.table), two or three for one without schemas. Writing dbo explicitly is harmless in both cases and future-proofs the code; leaving it out is only safe for bare names resolved through the default lakehouse.
  • Always include the workspace for cross-lakehouse queries. Without it Spark resolves against the notebook's own context and you get "table not found" for a table you can see in the portal.
  • Spark resolves identifiers case-insensitively by default, but OneLake paths and T-SQL collations may not. Copy names exactly as the lakehouse shows them and never rely on case to tell two tables apart.
  • The default lakehouse constrains what you can write. Attach the results lakehouse as the default (schema-enabled) and read everything else by four-part name.
  • Permissions are per user or identity. A four-part reference works only for tables the running identity can read. A scheduled run uses the identity of the pipeline's connection, which is not necessarily yours.
  • Keep names boring. Letters, digits and underscores in workspace, lakehouse, schema and table names avoid quoting problems entirely. Schema names in particular may contain only letters, numbers and underscores.
  • Consistency beats cleverness. One naming convention applied everywhere makes a configuration row readable by someone who has never seen the table.

Key takeaways

  • Choose the framework by the hardest claim you must defend; run the standard suite everywhere and add heavier frameworks for signed-off measures.
  • Keep logic in SQL, return numbers to Python, never collect data, and never treat a failed check as a skipped one.
  • Give every temp view a random suffix and drop it in finally; assume views are shared by every check in the session.
  • Always write four-part names in configuration, and run validation from a dedicated QA workspace with read-only access to the layers.
  • Write SQL that is independent of ANSI mode (try_cast, try_divide, NULLIF) so the same notebook behaves on Spark 3.5 and Spark 4 runtimes.
