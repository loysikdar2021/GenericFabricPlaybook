Playbook 15 · QA Validation

QA validation frameworks for Fabric data pipelines

A reusable, notebook-based way to prove that data survived each hop of a medallion pipeline: counts reconcile, transformations did what the specification says, schemas are intact, data is fresh and business metrics add up. Every check ends as a row in a results table that a pipeline can gate on, an alert can watch and a report can trend.

  • Audience data engineers, QA analysts, architects
  • Level intermediate
  • Languages Spark SQL, PySpark, a little T-SQL
  • Reading time 90 min

What the framework gives you

Most teams start validation the same way: someone writes an ad hoc notebook that compares two row counts after a deployment, eyeballs the output and moves on. It catches the first regression and then rots, because nothing records the result, nothing stops a bad load from being promoted and nobody can tell whether last week's check ran at all. This playbook describes the opposite approach: a small, deliberate framework where every check has the same shape and every run leaves evidence.

Self-contained notebooks
Each framework is one notebook with its logic, configuration and results writer inside it. There is no package to publish and no external configuration file to keep in sync. Once several notebooks copy the same helpers, promote them to a shared library (see Shared Python Libraries).
SQL-first checks
Comparisons, aggregations and set differences are expressed in Spark SQL and executed by the engine. Python only orchestrates: it builds statements, loops over configuration and writes results.
Temporary-view pattern
Each check declares the relations it compares as uniquely named, session-scoped temporary views, queries them, and always drops them. Checks can run in parallel in one Spark session without colliding.
One result shape
Every check reduces to expected versus actual, a variance, a tolerance and a status (PASS, WARN, FAIL, ERROR, SKIPPED), appended to a Delta results table with a run identifier.
Gate, alert, trend
A pipeline reads the notebook's exit value and decides whether to promote, fail and notify. A semantic model over the results tables shows pass rate, failures and drift over time.

Three frameworks, one pattern

The playbook documents three variants of the same pattern. They differ in how much business logic each check has to restate, not in plumbing. Architecture and design principles compares them in detail and explains how to choose.

When to use it, and when not to

Good fit

  • Layer-to-layer promotion (Bronze to Silver, Silver to Gold) with transformations you can restate in SQL
  • Release gates in a DEV to TST to PRD promotion path
  • Regression suites that run after every load or every deployment
  • Teams that want evidence in a table rather than a pasted result in a ticket
  • Reconciling a rebuilt Gold layer against the data it replaced (see Power BI to Fabric Migration for report-level UAT)

Poor fit

  • Rules that must be enforced on every write; use Delta constraints or materialized lake view constraints (compared here)
  • Exploratory profiling of unfamiliar data; use notebook profiling, Data Wrangler or Purview profiling
  • Business-steward-owned rules with scorecards and no code; Purview data quality fits better
  • Load or performance testing; this framework measures correctness, not throughput

Scope and prerequisites

In scope

  • Layer-to-layer validation of Silver-to-Gold transformations, with the same patterns applied to Bronze-to-Silver.
  • Validation types: row count, transformation, schema, freshness and complex metric checks, extended here with uniqueness, completeness, referential integrity, distribution drift, layer reconciliation and late-arriving data.
  • Environments: built and tuned in DEV, then promoted unchanged to TST and PRD with environment-specific names supplied as parameters.
  • Operations: orchestration from pipelines, promotion gates, alerting, reporting, governance of the framework itself.

Out of scope

  • Performance and load testing.
  • The UAT sign-off process and test-case management (covered in playbook 01).
  • Designing the medallion layers themselves (covered in Medallion Architecture).

Prerequisites

  • Workspaces and lakehouses for the layers you validate (for example DEV_HR_SLV with LH_HR_SLV and DEV_HR_GLD with LH_HR_GLD) and a place for results, ideally a small schema-enabled lakehouse in a dedicated QA workspace.
  • The identity that runs the notebook can read the source and target tables and write to the results lakehouse. In a pipeline that identity comes from the Notebook activity's connection.
  • A Fabric Spark runtime that supports four-part names and the SQL used here. The code is written to behave the same on Runtime 1.3 (Spark 3.5) and Runtime 2.0 (Spark 4.1): it avoids behavior that differs between them, such as ANSI mode being on by default in Spark 4. Prefer Runtime 2.0 for new work and run the self-test on both while you migrate.
  • Working knowledge of Fabric notebooks, Spark SQL and PySpark basics, plus enough domain knowledge to restate each transformation as a query.
  • A capacity with headroom for Spark jobs at the time validation runs (see performance guidance).

Verify against Microsoft Learn

Spark runtime versions, their release stage and the default for new workspaces change over time. Confirm the runtime you will use on Apache Spark runtimes in Fabric and read the migration notes for any runtime newer than the one you tested on.

Where checks sit in the medallion flow

A check is a statement about the relationship between two relations (or between one relation and a contract). Place checks on the hop where the relationship is created, so a failure points at the transformation that broke it. Schema and freshness checks are cheap enough to run on every hop.

What good looks like

  1. DesignPick the framework, define checks, tolerances and severities with the data owner.
  2. BuildWrite the notebook, run it in DEV, and prove each check can fail.
  3. OrchestrateCall it from the pipeline, gate promotion on the exit value, alert on blockers.
  4. OperateTrend results, retire noisy checks, govern change like any other code.
  • Every promoted dataset has at least one row-count, one schema and one freshness check, and every business-critical measure has a metric reconciliation.
  • Every check records expected, actual, variance and tolerance, so a failure explains itself without opening the notebook.
  • A failed blocker check stops promotion automatically, and the team is notified with the run identifier.
  • Each check has been shown to fail against a seeded defect, not just to pass against good data.

Key takeaways

  • Treat validation as a product: one result shape, one results table, one exit contract, and a gate that acts on them.
  • Keep the logic in SQL and the orchestration in Python; unique temporary views make checks safe to run in parallel.
  • Put each check on the hop that creates the relationship it verifies, and always include schema and freshness checks.
  • A check that has never failed is unproven. Seed a defect before you trust the suite.
  • Use native constraints for per-row rules enforced on write and this framework for cross-table, cross-layer and metric checks.
