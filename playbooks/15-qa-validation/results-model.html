Results model and tolerances

Define the shape of a result before you write any check. This page specifies the results and run tables, the status and severity model that drives promotion gates, and how to choose tolerances so that checks fail when the data is wrong and stay quiet when it is merely imperfect.

Every check is expected versus actual

The most useful design decision in the framework is that every check, however different its SQL, reduces to two numbers and a rule. A row count compares two counts. A uniqueness check expects zero duplicate keys and reports how many there are. A schema check expects zero missing columns. A freshness check expects data no older than a limit and reports its age. Once everything is a pair of numbers, one table, one status model and one tolerance mechanism cover all of them, and reports and alerts do not need to know what a check does.

No constraints on the results table, on purpose

The writer must never fail because of its own schema. A result that is slightly malformed is recoverable; a run whose results were not written at all is not. Enforce non-null columns in the notebook, keep the column order identical between the table and the DataFrame, and extend the schema only by adding columns.

validation_runs

One row per run, written after the results. It makes "what was the last run and did it block?" a one-row lookup instead of an aggregation, and it is what an alert or a dashboard card should read.

Status and severity

Status says what happened; severity says how much it matters. Keeping them separate lets the same failing check be a blocker in PRD and a warning in DEV without changing its logic.

Threshold and tolerance design

How a status is derived

The evaluator computes variance = actual - expected, converts it to a non-negative breach that depends on the rule, optionally expresses the breach as a percentage of expected, and then compares it with two limits.

  • tolerance is the breach you accept silently. The default is zero, and zero is correct for counts, key violations and schema checks.
  • fail_threshold is the breach beyond which the result is a failure. Set it only when you want an intermediate WARN band; leave it NULL otherwise.
  • tolerance_type is absolute (units of the metric) or percent (of expected). Percent is meaningless when expected is zero, so use absolute for violation counts.

Choosing tolerances

SituationRule and toleranceReasoning
Row count of a copy or lossless transformationeq, 0Any difference is a defect. A tolerance here hides lost rows.
Row count where the pipeline deliberately filters or dedupeseq, 0, with the same filter on the expected sideExpress the intended drop in the check (see reject accounting) rather than loosening the tolerance.
Sum of decimals recalculated independentlyeq, absolute, half a unit in the last stored decimal placeRounding order and engines differ at the last digit; nothing larger is explained by rounding.
Measure derived by division (for example FTE)eq, absolute, 10 to the minus (scale) divided by 2Compare at the scale you store. Never compare doubles for equality.
Freshnessle, limit in hours, optional fail_threshold at twice the limitA WARN band gives the on-call team time to react before consumers are affected.
Completeness or coveragege, minimum percent, observed in the sourceDerive the floor from the source data, not from a round number.

Known, documented exceptions (for example legacy orphans)le, the documented count, severity warningA ceiling catches regressions without pretending the exception does not exist. Record the owner and the reason in the configuration.

Never widen a tolerance to turn a check green

Changing a tolerance is a change to the definition of correct. Make it a reviewed change with a stated reason and an owner (see change control). A tolerance that was raised during an incident and never lowered is the most common way a validation suite quietly stops validating.

Reject accounting instead of fuzzy counts

When a pipeline legitimately drops rows (duplicates, rows failing a quality rule, late data routed to a quarantine table), do not compare raw counts with a loose tolerance. State the equation: expected = source rows - duplicates - rejected rows, where each term is its own count from the same snapshot. The check then passes with a tolerance of zero when the pipeline does what it claims, and fails when it drops anything unexplained. Layer reconciliation implements this.

Precision and timing pitfalls

  • Doubles. The results table stores numbers as doubles, which are exact for integers up to about 9 x 1015 and for decimals to roughly 15 significant digits. For balances beyond that, compute the variance in SQL as a decimal, compare there and store the comparison outcome.
  • Data in flight. A check that runs while a load is writing may read the source at one version and the target at another. Run validation after the load completes, or pin both sides to the same Delta version.
  • Time-dependent logic. Anything that depends on the current date (period flags, fiscal-year windows) must use the run's as_of_date parameter on the expected side and be validated shortly after the table is refreshed. See derived calendar columns.

Reading the results

These queries are the contract that dashboards and alerts build on. They run in a notebook SQL cell or in the lakehouse SQL editor.

WITH latest AS (
  SELECT run_id
  FROM qa.validation_runs
  WHERE suite = 'standard'
  ORDER BY started_at DESC
  LIMIT 1
)
SELECT test_name, check_type, severity, status, expected, actual, variance, message
FROM qa.validation_results
WHERE run_id IN (SELECT run_id FROM latest)
  AND status IN ('FAIL', 'ERROR')
ORDER BY CASE severity WHEN 'blocker' THEN 0 WHEN 'warning' THEN 1 ELSE 2 END, test_name;
SELECT CAST(run_ts AS DATE)                                  AS run_date,
       COUNT(*)                                              AS checks,
       count_if(status = 'PASS')                             AS passed,
       try_divide(count_if(status = 'PASS'), COUNT(*))       AS pass_rate
FROM qa.validation_results
WHERE suite = 'standard'
GROUP BY CAST(run_ts AS DATE)
ORDER BY run_date;
WITH ordered AS (
  SELECT test_name, status,
         LAG(status) OVER (PARTITION BY test_name ORDER BY run_ts) AS prev_status
  FROM qa.validation_results
  WHERE run_ts >= current_timestamp() - INTERVAL 14 DAYS
)
SELECT test_name, count_if(status <> prev_status) AS flips
FROM ordered
GROUP BY test_name
HAVING count_if(status <> prev_status) >= 3
ORDER BY flips DESC;

Retention and maintenance

  • Append-only. Never update or delete result rows to "fix" a history; add a new run instead.
  • Small files. One append per run creates small files. Schedule OPTIMIZE on both tables, and VACUUM within your retention policy, as part of regular lakehouse table maintenance.
  • Retention. Keep detailed results for as long as you need trends and audit evidence, and keep validation_runs indefinitely; it is tiny.
  • Evolution. Add columns; do not rename, retype or drop them. Dashboards and alerts depend on the existing shape.
  • Sensitive data. detail may carry sample rows. If the validated tables hold regulated or sensitive data (PII, financial, health), sample keys rather than values, or restrict access to the results lakehouse as tightly as to the data.

Key takeaways

  • Reduce every check to expected, actual, rule and tolerance; one schema then serves every report and gate.
  • Keep status (what happened) and severity (what it means) separate, and treat ERROR like FAIL for blockers.
  • Default tolerance to zero and express legitimate drops as arithmetic (reject accounting), not as slack.
  • Use a WARN band for operational signals such as freshness, and compare decimals with an absolute tolerance at the stored scale.
  • Changing a tolerance, a severity or a test name is a reviewed change, because it alters the meaning of history.
