Playbook 15 · QA Validation

Comparison with other tools

Building your own validation framework is a choice, not a default. Fabric and the open-source ecosystem already cover parts of the problem. This page says what each option does, where it stops, how to decide, and how to combine them so that one results table and one gate remain.

Where each option works

The options differ first in when they run. Some act inside the write or refresh and can reject rows. Some run as notebooks or jobs inside your pipeline and can stop a release. Some run in the catalog after the fact and report. Choosing means matching the moment to the failure you are trying to prevent.

Native Fabric and Microsoft options

Delta constraints

Delta tables support NOT NULL and CHECK constraints. A write that violates one fails, so bad rows never land. They are the cheapest control there is, because they cost nothing at run time that you schedule or monitor.

ALTER TABLE fact_orders ALTER COLUMN order_id SET NOT NULL;
ALTER TABLE fact_orders ADD CONSTRAINT order_amount_not_negative CHECK (order_amount >= 0);

SHOW TBLPROPERTIES fact_orders;      -- constraints appear as delta.constraints.<name>
ALTER TABLE fact_orders DROP CONSTRAINT order_amount_not_negative;
  • Good for: invariants of a single row that must never be violated by any writer: required keys, non-negative amounts, allowed ranges.
  • Stops at: one table, one row at a time. A constraint cannot compare two tables, check an aggregate, test freshness or tell you what changed. A failed write produces an error, not a history you can report on.
  • Watch out: adding a constraint checks the existing rows and fails if any violate it, and it raises the table's writer protocol version, which older writers may not support. Plan it as a table change, not a tweak.

Materialized lake view constraints

A materialized lake view can declare CHECK constraints with an action for rows that do not satisfy them. ON MISMATCH DROP removes the row and records the count in the view's data quality report. ON MISMATCH FAIL, the default, stops the refresh with an error. If a view has both, the failing action takes precedence.

CREATE MATERIALIZED LAKE VIEW IF NOT EXISTS silver.orders_clean
(
    CONSTRAINT order_id_present   CHECK (order_id IS NOT NULL) ON MISMATCH DROP,
    CONSTRAINT amount_not_negative CHECK (order_amount >= 0)  ON MISMATCH FAIL
)
COMMENT "Orders with row-level rules applied at refresh"
AS SELECT order_id, customer_id, order_date, order_amount
   FROM bronze.orders;
  • Good for: declarative cleansing in a medallion flow that already uses materialized lake views, with dropped-row counts visible without writing code.
  • Stops at: row-level rules. Constraints may use only deterministic built-in functions, so they cannot reconcile tables or compare against history. Dropping rows silently is a design decision: pair a DROP rule with a framework check that the number of dropped rows is within what you expect (see reject accounting).
  • Watch out: the definition cannot reference temporary views or user-defined functions, and session-level Spark settings are not applied in scheduled refreshes. Authoring with PySpark was in preview and refreshed in full when this page was written.

Verify against Microsoft Learn

Materialized lake views are evolving quickly: syntax, refresh behavior, schema requirements and which authoring paths are preview change between releases. Confirm the current state on the Spark SQL reference and data quality in materialized lake views before depending on a behavior.

Profiling in notebooks and Data Wrangler

Fabric notebooks can profile a DataFrame from the output table (the Inspect pane gives per-column statistics and distributions, limited to the rows the output widget holds, up to 10,000), and Data Wrangler summarizes missing values and column statistics and generates code. These are the right tools for understanding unfamiliar data and for deciding which checks to write. They work on a sample, are interactive, and leave no durable result, so they are not validations.

Microsoft Purview data quality

Purview Unified Catalog can profile Fabric lakehouse tables, apply data quality rules and run scans that produce quality scores for data products, owned by stewards in governance domains rather than by pipeline engineers. It answers "how healthy is this data product, and is it improving?" for the whole estate, in a place business owners already use.

  • Prerequisites to plan for: tables in Delta (or Iceberg) format; a Data Map scan of the Fabric tenant that uses a service principal; a separate data quality connection that uses the Purview managed identity; that identity added to the Fabric workspace as Contributor; and the scanned tables added to data products in a governance domain.
  • Good for: steward-owned rules, scorecards, trends and catalog integration across many sources, without code.
  • Stops at: it reports; by itself it does not stop a pipeline. It has no notion of your fiscal windows, keyed comparisons between layers or release gates, and its schedule is the scan's, not your load's. A Contributor grant to a service on a workspace is a significant permission and needs a security decision.

Verify against Microsoft Learn

Purview data quality for Fabric changes often: supported sources, authentication, programmatic access (a data quality API was in preview) and licensing. Read Set up data quality for Fabric Lakehouse data and its limitations section before committing, and test a small data product end to end.

Verify before you adopt

Great Expectations: the Fabric tutorial installs great-expectations<1.0 and says newer versions have different configuration and expectation APIs. Deequ and Soda: test the exact package version against your Fabric Spark runtime, including the Spark 4 line of Runtime 2.0, before you design around them. dbt: the tenant setting is named dbt jobs (preview); see dbt job in Microsoft Fabric for adapters, versions and limitations.

Why a library is not automatically better

  • Column rules are the easy part. Most libraries excel at "this column is never null, unique, in this set, in this range". The expensive defects in the three frameworks of this playbook are different: a Gold measure that no longer equals the Silver aggregate, a window that is off by one period, a join that fans out, a transformation that changes a label. Those need business-specific SQL, which any library can run only through a custom hook.
  • Results still need a home. A library gives you its result object. The gate, the history, the dashboard, the drift baseline and the alert still need one schema; that schema is the part of this playbook you keep regardless.
  • Two engines, two vocabularies. Every tool you add is another thing to learn, upgrade and secure, with its own idea of severity and tolerance.
  • But a framework you wrote is code you own. If your needs are mostly column rules over many tables, a library saves real effort. Use one.

Combining them behind one gate

The cleanest arrangement keeps one results schema and one gate, and treats every other tool as a producer of findings. Native constraints protect the tables, libraries and dbt supply extra column rules, Purview provides stewardship on top, and the framework turns everything that runs in the pipeline into validation_results rows.

The adapter below is deliberately tool-neutral. It defines the only contract: each finding has a name, a pass or fail, optionally a violation count, and a message. Write one small runner per tool that calls it and translates its output.

def adopt_findings(cfg: dict, findings: list) -> list:
    """Map findings from another tool to Result rows (expected 0 violations, actual = violations).

    Each finding: {"name": str, "ok": bool, "violations": int (optional), "message": str (optional)}.
    """
    results = []
    for f in findings:
        violations = f.get("violations")
        if violations is None:
            violations = 0 if f["ok"] else 1
        results.append(evaluate(new_result(
            cfg, test_name=f"{cfg['test_name']}.{f['name']}", expected=0.0, actual=float(violations),
            message=str(f.get("message", ""))[:400])))
    return results

RUNNERS = {}      # name -> function(cfg) returning findings; register one per external tool

@check("external")
def external(cfg):
    return adopt_findings(cfg, RUNNERS[cfg["runner"]](cfg))

def run_my_tool(cfg):
    # Call the other tool here against cfg["target"] and translate its output into findings.
    return [{"name": "email_format", "ok": True, "message": "all values match"},
            {"name": "country_in_set", "ok": False, "violations": 12, "message": "12 values outside the list"}]

RUNNERS["my_tool"] = run_my_tool

# Configuration row:
# {"suite": "standard", "test_name": "dim_customer.external", "check_type": "external",
#  "runner": "my_tool", "target": f"{GLD}.dim_customer", "severity": "warning"}

With this in place, a Great Expectations suite, a Soda scan or a Deequ verification run becomes a check in the same suite: it appears in the same report, obeys the same severity and dependency rules, and blocks or warns through the same gate. dbt tests run in their own job; if you want them to count, run that job ahead of the QA suite and either gate on its status or read its run results into the adapter. Check how your environment can orchestrate dbt jobs before you rely on it.

Defense in depth, cheaply

Put constraints on the few tables where an invalid row is never acceptable, because they cost nothing to run. Use the framework for everything that needs comparison, history or a release decision. Add a catalog tool when stewards need to own and see quality themselves, not as a substitute for the gate.

Before you adopt a tool

  • Runtime fit. Does the exact version run on the Fabric runtime you use, including the next one? Test it in a notebook or environment before design work.
  • Where results land. Can the output be turned into your results schema, so there is one gate and one report?
  • Can it stop a release? If it only reports, who acts on its findings, and how fast?
  • Identity and permissions. Which identity runs it, and what does it need on the data? Beware broad grants such as workspace roles for a service.
  • Owner and skills. Who writes and reviews rules in it, and can the on-call person read a failure?
  • Preview status. Is the feature generally available? If not, what is the exit plan?
  • Cost. Compute for scans, licensing for commercial features, and the people cost of a second vocabulary.
  • Fails closed. When the tool cannot run, does the gate stay shut, or does silence look like success?

Key takeaways

  • Match the tool to the moment: constraints refuse rows at write or refresh, pipeline tools can stop a release, catalog tools report.
  • Constraints are the cheapest control for single-row invariants and cannot compare tables or tell you about history.
  • Purview data quality suits steward-owned scorecards. It has real prerequisites and, on its own, does not gate a pipeline.
  • Libraries are strong at column rules and weaker at business reconciliation; verify versions against the Fabric runtime, and treat the dbt job feature and Great Expectations 1.x differences as things to test.
  • Keep one results schema and one gate, and adapt every other tool into it.
