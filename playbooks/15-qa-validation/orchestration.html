Orchestration, gating and reporting

A validation suite that nobody runs, or whose failure nobody acts on, is documentation. This page connects the notebooks to the rest of the platform: how a pipeline runs them and reads the verdict, how a failed gate stops promotion, how the right people hear about it, and how results are reported over time.

The validation pipeline

The standard shape is a short pipeline named per the house convention (for example PL_SALES_GLD_RunQa) with a Notebook activity, an If Condition on its exit value, and notification and failure activities. It can run on its own schedule, be invoked by the data pipeline that loaded the data, or be invoked as a spoke by an orchestration hub (see Cross-Workspace Pipeline Orchestration).

  1. Create the pipeline and its parameters

    Add pipeline parameters env and suite. Add a Notebook activity named Run QA suite and select the QA notebook (it can be in another workspace; the activity's connection identity must be able to run it).

  2. Pass base parameters to the notebook

    Map the notebook's parameter-cell variables to pipeline expressions. Parameters must be strings, numbers or booleans; the table below lists a working set.

  3. Add the gate

    Connect the activity's On success output to an If Condition that parses the exit value. Connect On fail to the notification and Fail path, because a notebook that crashed before returning a summary is also a failed gate.

  4. Publish on the true branch, block on the false branch

    True: publish and refresh. False: notify, then a Fail activity with a message that names the run, so the pipeline itself ends red and downstream triggers do not fire.

  5. Test the false branch on purpose

    Seed a defect in a copy of the data (or temporarily set a blocker's tolerance to an impossible value) and confirm the pipeline fails, the notification arrives and nothing was published.

Verify against Microsoft Learn

The exit value is read from activity('<name>').output.result.exitValue. Confirm that it is populated for the notebook type you use: community reports describe plain Python notebooks returning an empty exit value, while Spark notebooks return it. Test your first pipeline end to end. The activity is documented on Transform data by running a notebook, and parameter handling on Develop, execute, and manage notebooks.

Do not use retries to make a suite pass

Retrying a notebook activity runs the whole notebook again. With the same run_id the results are appended twice. Set retries to zero on the QA activity, or make the writer idempotent by deleting the run's rows before appending:

if not re.fullmatch(r"[A-Za-z0-9_:\-]+", run_id):
    raise ValueError(f"Unexpected characters in run_id: {run_id!r}")
for table in ("validation_results", "validation_runs"):
    spark.sql(f"DELETE FROM {results_schema}.{table} WHERE run_id = '{run_id}'")

Gating promotion on results

A gate is a decision with a cost: a false block delays a release, a false pass ships bad data. Three ways to implement it:

ApproachMechanismStrengthsWeaknesses
Exit value and If ConditionThe notebook exits with a JSON summary; the pipeline parses blocking_failuresExplicit, richer than pass or fail, no dependency on any table being readableKeep the payload small; confirm exit values propagate for your notebook type
Raise on blockerfail_on_blocker = True makes the notebook throw, so the activity failsSimplest; the failure path and alerts of the pipeline apply automaticallyNo structured summary; FAIL and ERROR look the same to the pipeline
Query the results tableA Lookup or Script activity reads validation_runs through the SQL analytics endpointDecoupled; any tool can gate on the same tableThe endpoint syncs metadata after the write, so a just-written run can be invisible; add a refresh step or poll

Use the first in pipelines, the second in tools that only understand "job succeeded or failed", and the third for gates that live outside Fabric. If you query through the SQL analytics endpoint, run the Refresh SQL analytics endpoint activity first; see SQL analytics endpoint metadata sync.

Release gates across environments

The same suite can gate a promotion from TST to PRD. Deploy to TST, run the QA pipeline there, and let the release continue only if the run completed. Deployment pipelines deploy items, not data, so each environment keeps its own results tables, and a QA notebook promoted with the release finds its own environment's tables through the env parameter (see Deployment Pipelines and Promotion and the Deployment Checklist).

Orchestrating this from a CI system means starting the QA pipeline through the Fabric job scheduler API, polling the job instance until it is no longer in progress, and treating anything other than Completed as a failed stage. Because the pipeline ends in a Fail activity when the gate is blocked, the job instance status is itself the gate.

Verify against Microsoft Learn

Check the current URL form, the request body for passing pipeline parameters, and the job status values on Job Scheduler: Run On Demand Item Job and REST API capabilities for Fabric Data Factory. The job type moved from a query parameter into the URL path in newer API versions.

Alerting on failure

Alert on state changes that need a human: the gate going from open to blocked, an ERROR in a blocker, or a freshness failure. Send a digest for WARN results rather than a message per check, or the channel becomes noise and gets muted, which is worse than no alert.

ChannelHowGood forLimits to know
Teams activityPipeline activity posts to a channel or group chat, message built with expressionsTeam-visible blocked-gate alertsUses a user connection; documented as inactive when the pipeline is deployed through CI/CD, so plan for it in release flows
Office 365 Outlook activityPipeline activity sends mailOwners and stakeholders who are not in TeamsSupports user, workspace identity and service principal authentication; the sender is the connection's identity; sensitivity labels are not supported
Fabric ActivatorAlert on a report visual (for example blocking failures greater than zero) and send Teams or e-mailAlerts that live with the reporting layer and need no pipeline changeEvaluates the visual's data on its own cadence; created in report edit mode

Do not copy notification activities into every pipeline. Create one shared notification pipeline that owns the connection and takes the channel, subject and body as parameters, and invoke it with the Invoke pipeline activity. Connections for these activities are scoped to the user who created them, so one shared pipeline with one shared connection is also easier to hand over and to redeploy.

A useful message answers the first three questions the reader will ask: what is blocked, how bad is it, and where to look.

Reporting results in a semantic model

Notifications tell you something is wrong now. A report tells you whether the suite is healthy over time, which checks are flaky, which tables drift, and what evidence exists for an audit. Build it on the results tables, not on notebook output.

Model design

  • Tables. Import validation_runs and validation_results, plus a date table. Relate validation_results[run_id] to validation_runs[run_id] (one to many). That only works if run_id is unique per suite execution, which is why the pipeline appends the suite name to it.
  • Storage mode. Use Direct Lake: the results are Delta tables in a lakehouse, and Microsoft's guidance favors Direct Lake on OneLake for new models. Direct Lake reads Delta tables, not SQL views, so shape the data in the tables rather than in views.
  • Freshness. Run the Semantic model refresh activity as the last step of the QA pipeline so the model reflects the run that just finished. Enable the activity's option to wait for completion if a later step, such as the semantic model parity check, depends on the refreshed model; otherwise the pipeline moves on while the refresh is still running.
  • Security. Results name tables, columns and sometimes sample values. Give the report the same audience restrictions as the data it describes.
Checks = COUNTROWS ( validation_results )

Passed = CALCULATE ( [Checks], validation_results[status] = "PASS" )

Pass Rate = DIVIDE ( [Passed], [Checks] )

Warnings = CALCULATE ( [Checks], validation_results[status] = "WARN" )

Blocking Failures =
CALCULATE (
    [Checks],
    validation_results[severity] = "blocker",
    validation_results[status] IN { "FAIL", "ERROR" }
)

Avg Check Seconds = AVERAGE ( validation_results[duration_s] )
Latest Run Id =
VAR LastStart =
    CALCULATE (
        MAX ( validation_runs[started_at] ),
        ALLEXCEPT ( validation_runs, validation_runs[suite], validation_runs[environment] )
    )
RETURN
    CALCULATE (
        SELECTEDVALUE ( validation_runs[run_id] ),
        ALLEXCEPT ( validation_runs, validation_runs[suite], validation_runs[environment] ),
        validation_runs[started_at] = LastStart
    )

Is In Latest Run =
IF ( SELECTEDVALUE ( validation_results[run_id] ) = [Latest Run Id], 1, 0 )

Latest Gate =
CALCULATE (
    SELECTEDVALUE ( validation_runs[gate] ),
    validation_runs[run_id] = [Latest Run Id]
)

Report pages worth building

  • Status. Cards for the latest gate and blocking failures per suite and environment; a table of failing checks in the latest run (filter Is In Latest Run equal to 1) with message and variance.
  • Trend. Pass rate and blocking failures by day, split by suite; average check duration to spot cost creep.
  • Check health. Checks that flip between PASS and FAIL (the flaky-check query from the results page), checks that have never failed, checks that always warn. Each is a candidate for tightening, removal or an owner conversation.
  • Drift. Actual against expected and tolerance for the drift checks, as a line with a band.
  • Evidence. A run-level page that can be exported for sign-off: run, environment, framework version, counts, all results.

Scheduling and capacity

Run the cheap suite often and the expensive suite when it matters. Validation is Spark work and consumes the same capacity as the pipelines it protects, so place it deliberately.

SuiteTriggerWhy
Smoke (counts, schema, freshness)After every load, in the loading pipelineCheap, and it is the gate for publishing the new data
Full (metrics, reconciliation, referential, rules)Nightly, or after the day's last loadHeavy scans over large facts; no need to run per micro-batch
Drift and late-arrivalDailyThey need history, and a daily cadence builds a usable baseline
Release suiteOn deployment to TSTThe release gate described above
  • Run after the load, not during it. Make the QA pipeline a dependent step of the load, or schedule it after the load's expected end. A check that reads a table mid-write compares two moments.
  • Reuse sessions. With high concurrency mode enabled for pipelines, a session tag lets notebook activities share a Spark session, which removes most of the start-up time for a short suite. Notebooks share a session only when they run as the same user, use the same default lakehouse and the same Spark configuration and libraries, and the number of notebooks per session is capped (five by default). Inline %pip installs are not supported in this mode, so put libraries in the environment. The unique temp view names make sharing safe.
  • Bound concurrency twice. max_workers limits queries inside one notebook; the DAG's concurrency limits notebooks inside runMultiple. They multiply.
  • Watch duration. duration_s in the results is your baseline. A check whose duration doubled is telling you the table grew or the plan changed.
run_tag = "run-001"   # replace with a pipeline-supplied value in real use

Child notebooks and lakehouses

A reference run is blocked when the child notebook's default lakehouse differs from the parent's. Give all QA notebooks the same default (results) lakehouse, or set useRootDefaultLakehouse as described in the NotebookUtils documentation.

Key takeaways

  • Validate before you publish: land data in staging, audit it, and publish only through an open gate.
  • Gate on the exit value, keep retries at zero (or make the writer idempotent), and test the blocked path on purpose.
  • Alert on state changes and send digests for warnings; centralize notification activities in one shared pipeline.
  • Report from the results tables through a Direct Lake semantic model, refreshed at the end of the QA pipeline.
  • Run cheap suites after every load and heavy suites on a schedule; cap concurrency at both levels.
