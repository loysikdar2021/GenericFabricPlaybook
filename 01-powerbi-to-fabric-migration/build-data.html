Playbook 01 · Power BI to Fabric

Build the data layers

The legacy estate did its ingestion and transformation inside Power Query and Dataflow Gen1. The new estate does it in a medallion architecture with a deliberate tool at each layer. This page maps old constructs to new ones, summarizes each layer for a migration, and covers dataflow options and orchestration. The deep dives live in the data engineering playbooks.

  • Phase II · Build
  • Audience data engineers, analytics engineers
  • Output Bronze, Silver and Gold layers with an orchestrated load

What replaces what

In a Power BI estate, one tool did several jobs: it connected to sources, cleansed data, applied business rules, joined tables, aggregated, and refreshed on a schedule. A migration separates those jobs and assigns each to the layer best suited to it. Use the query catalog and rebuild notes to decide where each rule lands.

One tool per layer

The recommended stack for a Power BI migration follows a clear progression: pipelines to ingest, Spark to conform, and a star schema served from the Warehouse. The choice of Gold technology follows the pattern decision: in the All-Lakehouse pattern, Spark builds Gold too.

Bronze: ingest with fidelity

The Bronze layer ingests source data as it is, reliably and repeatably. Its job is to be a trustworthy copy that you can reprocess from, not a place for business rules.

  • Land as Delta. Delta gives ACID transactions, schema enforcement and time travel, so the raw layer is auditable. Keep the source column names and types except where the format forces a change.
  • Add audit columns. Load identifier, source system and ingestion time on every row. They make lineage and reprocessing possible.
  • Load incrementally where the source allows. A watermark on a modified date or a change-tracking column replaces the legacy incremental refresh policy. Pipelines do not transform data; they move it.
  • Reach on-premises sources through a gateway. A pipeline connection can use an on-premises data gateway when the source is not reachable from the cloud. Plan the gateway capacity as part of the build, not at cutover.
  • Do not partition by default. A partition per day on a small table creates many small files and slows everything down. Partition only when a table is large and the partition column is low-cardinality and used in filters. Current Microsoft guidance favors liquid clustering as the default layout and treats partitioning as the exception, mainly for concurrent writers; see Delta partitioning.

Verify against Microsoft Learn

Layout guidance depends on the Fabric runtime version. Check Partitioning for Delta tables and Liquid clustering for the runtime you run, and test on your own data volumes.

Silver: conform and enforce quality

Silver turns raw data into clean, conformed, business-ready tables. This is where the rules recovered from the legacy queries are applied, tested and made reusable. Apache Spark, run from notebooks, is the strongest tool for it: cleansing nulls and types, parsing strings, joining systems (for example CRM and ERP), applying rules that SQL expresses poorly, and quarantining records that fail checks.

A pattern worth standardizing is the conformance notebook with a quarantine table. The example reads Bronze from another workspace by its OneLake path and writes to the attached Silver lakehouse.

from pyspark.sql import functions as F

bronze_path = ("abfss://DEV_SALES_BRZ@"
               "onelake.dfs.fabric.microsoft.com/"
               "LH_SALES_BRZ.Lakehouse/Tables/orders_raw")
bronze = spark.read.format("delta").load(bronze_path)

conformed = (
    bronze
    .withColumn("order_id",    F.col("OrderID").cast("bigint"))
    .withColumn("order_date",  F.to_date("OrderDate", "yyyy-MM-dd"))
    .withColumn("customer_id", F.upper(F.trim("CustomerCode")))
    .withColumn("net_amount",  F.col("Amount").cast("decimal(18,2)"))
    # Rule recovered from the legacy query catalog: exclude test accounts.
    .filter(~F.col("customer_id").startswith("TEST"))
)

# A rule that evaluates to NULL must count as a failure; otherwise the row
# disappears from both the good and the rejected output.
passes = F.coalesce(
    F.col("order_id").isNotNull()
    & F.col("order_date").isNotNull()
    & (F.col("net_amount") >= 0),
    F.lit(False),
)

good = conformed.filter(passes)
bad  = conformed.filter(~passes).withColumn("_rejected_reason", F.lit("failed conformance rules"))

good.write.format("delta").mode("overwrite").saveAsTable("orders")
bad.write.format("delta").mode("append").saveAsTable("orders_quarantine")

Each rule should trace back to a line in the specification package. A rule with no owner and no test is the next legacy mystery.

Gold: model the star schema

Gold takes conformed Silver data and builds the business-friendly star schema: central fact tables and surrounding dimensions. In the recommended Hybrid pattern the Gold layer lives in a Fabric Warehouse and is built with T-SQL. Use CREATE TABLE AS SELECT (CTAS) for initial loads and aggregates, T-SQL MERGE for upserts, and stored procedures to keep each load modular and reusable.

MERGE is a T-SQL feature in the Warehouse

Upserts in the Warehouse use the T-SQL MERGE statement. In Spark the equivalent is the Delta MERGE API or Spark SQL MERGE INTO. The two are different engines with different syntax, so state which one a developer is expected to use when you assign the work.

Slowly changing dimensions

Type 2 dimensions preserve history, which matters for accurate historical reporting. The two-step pattern below closes changed rows and inserts new versions in one transaction. It is easy to read and test, and the null-safe comparison avoids the classic bug where a change to or from a null goes unnoticed.

CREATE PROCEDURE gold.usp_Load_DimCustomer
AS
BEGIN
    SET NOCOUNT ON;
    BEGIN TRANSACTION;

    -- 1. Close current rows whose tracked attributes changed (null-safe comparison).
    UPDATE d
    SET    d.IsCurrent = 0,
           d.ValidTo   = CAST(SYSUTCDATETIME() AS datetime2(6))
    FROM   gold.DimCustomer AS d
    JOIN   stg.Customer     AS s ON s.CustomerId = d.CustomerId
    WHERE  d.IsCurrent = 1
      AND  EXISTS (SELECT s.CustomerName, s.Segment, s.Region
                   EXCEPT
                   SELECT d.CustomerName, d.Segment, d.Region);

    -- 2. Insert a current row for new customers and for those just closed.
    INSERT INTO gold.DimCustomer
        (CustomerKey, CustomerId, CustomerName, Segment, Region, ValidFrom, ValidTo, IsCurrent)
    SELECT  mx.MaxKey + ROW_NUMBER() OVER (ORDER BY s.CustomerId),
            s.CustomerId, s.CustomerName, s.Segment, s.Region,
            CAST(SYSUTCDATETIME() AS datetime2(6)),
            CAST('9999-12-31' AS datetime2(6)),
            1
    FROM    stg.Customer AS s
    CROSS JOIN (SELECT COALESCE(MAX(CustomerKey), 0) AS MaxKey FROM gold.DimCustomer) AS mx
    WHERE   NOT EXISTS (SELECT 1 FROM gold.DimCustomer AS d
                        WHERE d.CustomerId = s.CustomerId AND d.IsCurrent = 1);

    COMMIT TRANSACTION;
END;

A single MERGE can implement the same pattern when the source is arranged to produce both the closing and the inserting row, and either form is valid. Whichever you choose, run one writer per table at a time: concurrent modifications to the same table in a Warehouse can conflict, so the orchestration should serialize them (see below). Facts usually load by upsert on the business key or by partition-style replace of a recent window.

Verify against Microsoft Learn

T-SQL surface area, MERGE support and concurrency behavior are documented for the Warehouse and change as features ship. Re-check T-SQL surface area and Warehouse performance guidelines, and test the procedure with two concurrent runs before you rely on it.

What to do with Dataflow Gen1

Dataflow Gen1 is in a legacy state: it keeps running but receives no new feature investment. For workspaces on a Fabric capacity, Dataflow Gen2 is the recommended successor. Gen2 requires a Fabric capacity or trial, so workspaces that stay on Pro or Premium Per User licensing can continue with Gen1 while you plan the move.

After any move, update downstream consumers. Models and dataflows that read through the legacy Power BI Dataflows connector must switch to the Power Platform Dataflows connector, and a downstream DirectQuery model must change storage mode. Workspace Viewers can see an upgraded dataflow but cannot consume its tables through that connector, so review roles. Gen2 has a different compute and billing model: validate duration and CU use rather than assuming parity.

Verify against Microsoft Learn

Orchestrate the end-to-end flow

A single monolithic pipeline that chains every task is brittle and hard to change. The pattern that scales is a metadata-driven hub and spoke: a master pipeline (the hub) holds no data logic, and reads a control table that lists the modular child pipelines (the spokes), their order, dependencies and parameters. Adding a new source means adding spokes and rows, not editing the hub.

Control table and dependency management

The control table is the plan and the lock. A minimal shape is below; the full pattern, including asset discovery and parameters, is covered in Control-table-driven pipelines and Cross-workspace orchestration.

CREATE TABLE ctl.PipelineSteps
(
    StepId         int           NOT NULL,
    StepName       varchar(100)  NOT NULL,
    Layer          varchar(10)   NOT NULL,   -- BRZ, SLV, GLD, CNSM
    PipelineName   varchar(200)  NOT NULL,   -- the spoke to invoke
    DependsOnStep  int           NULL,       -- one parent for simplicity
    IsEnabled      bit           NOT NULL,
    Status         varchar(20)   NOT NULL,   -- Pending, Running, Succeeded, Failed
    LastRunId      varchar(100)  NULL,
    LastUpdated    datetime2(6)  NULL
);

The hub begins a run by resetting statuses, then loops: select enabled steps that are Pending and whose parent is Succeeded, set them to Running, invoke the child pipeline, and set the outcome. A failed step blocks its dependents and raises an alert. Because only one writer touches each table at a time, the pattern also prevents the Warehouse write conflicts described above.

Schedule and alert

  • Schedule the hub at the cadence the business needs, using the built-in scheduler. Align it with the refresh windows agreed during communication planning.
  • Failure notifications on the schedule. Open the pipeline, choose Schedule, and add users or groups under Failure notifications. This is the simplest alert and covers scheduled runs.
  • Activity-level alerts. Add an Office 365 Outlook or Teams activity on the failure path of a key activity. Check the limitations before relying on them: these activities need a connection, do not support workspace identity or service principals, and are documented as inactive when used in CI/CD.
  • Activator rules. Create rules on pipeline job events to send email or Teams messages, including for success and for pipeline changes.
  • Workspace monitoring. With workspace monitoring enabled, job logs land in an Eventhouse; one KQL-based alert can cover every pipeline failure in a workspace.
  • Route alerts to a monitored destination such as a team channel or a distribution list, never to an individual's mailbox.

Verify against Microsoft Learn

Activity limitations differ by authentication type and by CI/CD usage. See Create alerts for pipeline runs, Teams activity and Office 365 Outlook activity, and test the alert path in a non-production workspace.

Sequencing the build

Building every Bronze table, then every Silver table, then every Gold table delays the first thing a business owner can look at by months. A safer order is a vertical slice: take one high-value subject area from the matrix, build it end to end through a semantic model and report, reconcile it, and only then repeat. The first slice settles naming, folder layout, shared code, alerting and the reconciliation method; later slices reuse all of it.

  • Each Bronze table has audit columns and an agreed load pattern (full, watermark or mirrored).
  • Each Silver rule traces to the specification package and has a test or a data-quality check.
  • Rejected rows go to a quarantine table that someone reviews.
  • Gold tables are documented as star schemas, with surrogate keys and history behavior stated per dimension.
  • The hub pipeline runs the whole slice from the control table, and a forced failure raises an alert to a monitored destination.
  • The first slice reconciles to its baselines (see reconciliation) before the next slice starts.

Key takeaways

  • Unbundle the legacy tool: connections to Bronze, cleansing and rules to Silver, shaping to Gold, refresh to orchestration.
  • Pipelines ingest, Spark conforms, the Warehouse serves the star schema in the Hybrid pattern. Do not partition Bronze by default.
  • Upserts in the Warehouse use T-SQL MERGE or an UPDATE plus INSERT pair; in Spark they use Delta MERGE. One writer per table at a time.
  • Choose per dataflow: keep, Save As, upgrade, or replace. Plan consumers and connectors, not only the dataflow.
  • Drive orchestration from a control table, alert to a monitored destination, and build one vertical slice before scaling out.
