Playbook 01 · Power BI to Fabric

Semantic models and reports

With a governed Gold layer in place, the last build step is what users actually touch. This page covers the decoupled model-and-report architecture, how to choose a storage mode (including Direct Lake and its fallback), how to rebuild and secure the model, and how to deliver thin reports, by rebinding or rebuilding.

  • Phase II · Build
  • Audience BI developers, semantic model owners, report builders
  • Output certified semantic models and thin reports

One model, many thin reports

A migration is the best chance you will get to enforce a decoupled architecture. Each domain has a small number of certified semantic models, owned by a named team. Reports contain only visuals and connect live to those models. Excel, paginated reports and apps use the same models. The result is one definition of every measure, no silent forks of the business logic, and reports that can be rebuilt or retired without touching the data model.

Two practical notes. Start from a fresh model rather than repurposing a legacy file, and author it as a Power BI project (PBIP with TMDL) in Git so every change is reviewable. And do not rely on a default semantic model attached to a lakehouse or warehouse: default models are no longer created automatically and existing ones have been decoupled from their items, so create explicit, named, owned models.

Choose the storage mode

Storage mode is a property of each table in a semantic model. The choice drives refresh cost, latency, security design and what the model can contain. Four options matter in a migration.

Direct Lake and Import are both processed by the VertiPaq engine, which is why they perform alike. Models can combine modes; a model with Import and Direct Lake tables offers much of the scale and flexibility BI teams need.

Correcting a common assumption

A frequent design is "Hybrid pattern, so DirectQuery to the Warehouse endpoint". That is outdated. Direct Lake works with Warehouse tables as well as lakehouse tables, and DirectQuery is the slower option. Use DirectQuery only when the data cannot be copied, must be live, or must enforce source-side security.

Fallback and guardrails

The two Direct Lake options behave differently at their limits, and this is the most common surprise in testing.

Guardrails depend on the capacity SKU. Most are evaluated per query, and the model-size limit is evaluated for the whole model. A table that fits an F64 may not fit an F8.

Max memory is not a hard guardrail: exceeding it causes paging and slower queries rather than failure. Well-compacted Delta tables stay inside the file and row-group limits, which is another reason to run table maintenance on Gold (see Delta partitioning).

Rebuild the semantic model

Use the specification package from reverse-engineering as the blueprint. The rebuild is not a copy-and-paste exercise: every measure is a chance to simplify, rename consistently and document what it means.

  1. Create the model on the Gold layer. Connect to the Gold tables as Direct Lake, or as Import where the decision above says so. Name the model by convention, for example SM_SALES_CNSM_Orders.
  2. Build the star schema. Fact-to-dimension relationships with single-direction filters by default, a proper marked date table, and hidden keys. Check that the one-side columns are unique: Direct Lake queries fail when a one-side column contains duplicates.
  3. Recreate measures from the measure catalog. Keep the business meaning, rewrite the formula where a better pattern exists, give each measure a description, a format string and a display folder, and group time-intelligence logic in calculation groups where appropriate.
  4. Push logic upstream. Calculated columns and tables belong in Gold. On Direct Lake on SQL they are not supported, and on Direct Lake on OneLake they are limited, preview features.
  5. Add security from the security specification (see below).
  6. Run the Best Practice Analyzer and fix the performance and error-prevention findings. Then replay the golden baselines.
table 'Fact Sales'

    /// Net sales after returns and discounts. Test accounts are excluded upstream in Silver.
    measure 'Net Sales' = SUM('Fact Sales'[NetAmount])
        formatString: #,0.00
        displayFolder: Sales

    /// Net sales for the same period in the prior year.
    measure 'Net Sales PY' = CALCULATE([Net Sales], SAMEPERIODLASTYEAR('Date'[Date]))
        formatString: #,0.00
        displayFolder: Sales

Descriptions written in TMDL appear as tooltips for report builders and travel with the measure. They are also the cheapest way to make the next reverse-engineering exercise unnecessary.

Keep Import tables where Power Query is the right tool

A model can mix Direct Lake and Import. If an analyst needs a small lookup the lakehouse does not have, an Import table with Power Query is acceptable in a composite model on Direct Lake on OneLake. Record it as an exception so it does not become a hidden dependency.

Secure the model

Row-level security (RLS) and object-level security (OLS) are defined in the semantic model from the security specification you extracted. Where the legacy estate relied on security at the source, decide explicitly where each rule will live now, because the Direct Lake options treat SQL-level security differently.

Silent loss of source-side security

On Direct Lake on OneLake, row-level security defined only on the SQL analytics endpoint does not apply. A migration that moves a Warehouse-secured report to a Direct Lake on OneLake model without recreating the rule in the model exposes rows the old design hid. Treat every source-side rule in the security specification as a requirement to re-implement and test.

  • Dynamic RLS. Map users to the data they may see in a security table, and filter a dimension with the signed-in identity. Assign roles to Microsoft Entra security groups, never to individuals.
  • RLS applies to read access, not to editors. Roles restrict users who consume through read or Build permission, including workspace Viewers. Users with edit rights in the workspace are not restricted, so keep model workspaces tight and give consumers Viewer or app access.
  • Test with impersonation in Desktop, on the web, or through DAX queries run as a role, and record the results in the QA evidence.
  • Licensing interacts with the audience. Free-license viewers need the capacity to be F64 or larger, as covered under viewer licensing.
-- Role "Regional managers", table filter on 'Dim Region':
'Dim Region'[ManagerEmail] = USERPRINCIPALNAME()

The broader access model (workspace roles, app audiences, warehouse permissions) is in governance.

Verify against Microsoft Learn

RLS behavior with Direct Lake depends on the variant and on connection settings. Confirm in Integrate Direct Lake security and Specify a fixed identity for a Direct Lake model, and test with a real Viewer account.

Publish and certify

Publish the model to the central consumption workspace and promote it through the release path in environments and CI/CD. Once validated, endorse it as Certified so that everyone can find the authoritative version. The flow, the tenant settings and who may certify are in governance.

  • The model has a named owner and a contact in its description.
  • Measures have descriptions and consistent formats; hidden keys and technical columns are hidden.
  • Security roles are assigned to groups and tested with impersonation.
  • The Best Practice Analyzer output is reviewed and the exceptions are written down.
  • Baselines pass within the agreed tolerance.
  • For Import tables, a refresh schedule exists; for Direct Lake, the framing approach (automatic updates or a pipeline step) is decided.
  • The model is in Git and deploys through the pipeline, not by hand.

Build thin reports

Thin reports are report-only items that connect live to the certified model. Recreate the pages, visuals and interactions from the visual inventory, and apply the organizational theme and templates. Save reports as Power BI projects in PBIR format so that pages and visuals are separate, reviewable files, and commit them to Git.

  • Work from the inventory, not from memory. The visual inventory lists what each page contains; the baselines say what each number should be.
  • Avoid report-level measures unless a calculation is genuinely specific to one report; shared logic belongs in the model.
  • Follow the report standards. Layout, accessibility, naming and performance rules are in Power BI report development standards.
  • Handle paginated reports and apps separately. Operational and pixel-perfect reports follow paginated report migration; audiences and navigation follow organizational apps.

Rebind existing reports instead of rebuilding

When the matrix says Rebind, the report is kept and pointed at a new model. This is the fastest way to move a sound report to the new platform, provided the new model has the same table and field names the report uses. Test one report manually first; field differences show up as broken visuals.

Connect-PowerBIServiceAccount

$workspaceId = '<report-workspace-id>'
$newModelId  = '<new-semantic-model-id>'
$reports     = @('<report-id-1>', '<report-id-2>')   # rows marked Rebind in the matrix

foreach ($reportId in $reports) {
    $body = @{ datasetId = $newModelId } | ConvertTo-Json
    Invoke-PowerBIRestMethod -Method Post -Body $body `
        -Url "groups/$workspaceId/reports/$reportId/Rebind"
    Write-Output "Rebound $reportId"
}
  • Permissions. The caller needs Write permission on the report and Build permission on the target model.
  • Cross-workspace. If the model is in a different workspace, a shared model reference is created in the report's workspace. A report that had a live connection gets a direct binding to the target.
  • Not for paginated reports. The API does not support them; see the paginated playbook.
  • Verify afterwards. Open every page, check filters and bookmarks, and replay the baselines for the report's key visuals.

Verify against Microsoft Learn

See Reports: Rebind Report In Group for permissions and limitations. For reports stored as PBIR, the model reference lives in definition.pbir as a by-connection reference; see the project report folder.

Key takeaways

  • One certified model per domain, source-controlled and owned, with thin reports connected live to it.
  • Default to Direct Lake on OneLake for new Gold-layer models. Use Import when the data is outside OneLake, and DirectQuery only for live or restricted sources. Do not design for DirectQuery to the Warehouse.
  • Know the limit behavior: the OneLake variant errors, the SQL variant falls back to DirectQuery. Guardrails depend on the SKU.
  • Source-side row security is not applied in Direct Lake on OneLake. Re-implement every rule in the model and test as a viewer.
  • Rebind sound reports through the REST API; rebuild the rest from the visual inventory and baselines.
