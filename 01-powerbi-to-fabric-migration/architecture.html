Target architecture and environments

Medallion layers and where they live

The medallion pattern organizes data into layers that progressively improve structure and quality. In Fabric the layers are a convention you implement with items and workspaces, not a product feature. This playbook uses five layer codes so that workspace and item names read the same way across the whole estate.

LayerCodeContentsItem typesWritten byRead by
BronzeBRZSource data as delivered: unaltered, append-only history, minimal validation. Schema drift is tolerated and recorded.LakehousePipelines (Copy), mirroring, shortcutsData engineers
SilverSLVValidated, typed, deduplicated and conformed data. Business rules applied; bad records quarantined or flagged.LakehouseSpark notebooks, Spark SQLEngineers, data scientists, ad-hoc analysis
GoldGLDCurated business entities and conformed dimensions ready for reuse across domains.LakehouseNotebooks or T-SQLBI developers, data science
ConsumptionCNSMServing structures: the star-schema warehouse, semantic models, and any lakehouse built for data science.Warehouse, semantic model, lakehouseT-SQL, modeling toolsBI developers, report builders
DeliveryDLVThin reports, paginated reports and apps for end users.Report, paginated report, appReport developersBusiness users

Some organizations add a specialized "platinum" layer for narrowly shaped data products. Treat that as another layer with its own workspace and naming code, not as a different technology. Small estates can fold Gold into Consumption; do it deliberately and keep the star schema as the contract.

Correction to a common recommendation

Many guides tell you to land Bronze as partitioned Delta tables by default. Partitioning small or medium tables produces many small files and slows reads. Partition only large tables, on a stable, low-cardinality column that queries actually filter on, and compact regularly. See Delta Lake Partitioning Strategy and Medallion Architecture for the layer-level detail.

All-Lakehouse or Hybrid

The only real architectural fork is the technology used to shape the Gold and Consumption layers. Bronze and Silver are lakehouses in both patterns.

  • Pattern 1, All-Lakehouse. Gold is a lakehouse written by Spark. Consumers reach it through the lakehouse's SQL analytics endpoint (read-only T-SQL) or through a Direct Lake semantic model.
  • Pattern 2, Hybrid. Gold-and-above is a Fabric Warehouse built with T-SQL (CTAS, INSERT, UPDATE, DELETE, MERGE, stored procedures) from Silver lakehouse tables. Consumers use the warehouse's SQL endpoint, or a Direct Lake semantic model over its tables.

Both store their tables as Delta in OneLake and both can feed Direct Lake. The choice is therefore about who builds and maintains the transformation logic and which engine runs it, not about storage format.

Verify against Microsoft Learn

The Warehouse supports a subset of SQL Server T-SQL, and that subset grows. Check T-SQL surface area in Fabric Data Warehouse and Limitations before committing logic to a feature. Also check how a warehouse reads Silver in your topology (same-workspace cross-database queries, shortcuts, or pipeline copy).

How to decide

  • Start with the people who will maintain the star schema. If they are BI developers fluent in T-SQL and migrating from import models, choose Hybrid. If they are Spark engineers who also serve data science, choose All-Lakehouse. Forcing an unfamiliar paradigm on the team is the main risk in either direction.
  • Do not make it a religious choice. One domain can be Hybrid while another is All-Lakehouse. Both write Delta to OneLake and both feed the same kind of semantic model.
  • Keep Bronze and Silver as lakehouses. The Hybrid pattern is about Gold and above, not about replacing the lakehouse.
  • Write the decision down as an architecture decision record: context, options, decision, consequences, and who can revisit it.

Workspace strategy

Workspaces are the unit of access control, capacity assignment, Git connection and deployment. There are two common ways to cut them.

Option A: one workspace per environmentOption B: one workspace per layer per environment
ShapeDEV_SALES, TST_SALES, PRD_SALES hold every layer as items.DEV_SALES_BRZ through PRD_SALES_DLV: five layers by three environments.
StrengthsFew workspaces and pipelines; simple lineage; fewer cross-workspace references.Least-privilege access by layer; consumers never see raw data; independent capacities and release cadence; smaller blast radius; fits the hub-and-spoke orchestration.
CostsEveryone with access to the workspace sees every layer; one item-count ceiling; one Git repository folder for everything; any release deploys everything.More objects to manage; cross-workspace references (shortcuts, default lakehouse, pipeline targets) must be parameterized per environment.
Choose it whenOne small team owns the whole domain end to end.Several roles with different access, regulated or sensitive data, or a shared platform with many domains.

This playbook family uses Option B, because migrations usually exist to give business users governed access to curated data without handing them raw data. If you choose Option A, keep the same item names and the same environment suffixes so the rest of the guidance still applies.

Naming convention

Decide names once, enforce them in code review, and put them in the Git repository so the next team inherits them. Fabric item names are part of lineage, search and every error message.

Domains, capacity and access

  • Domains. Assign every workspace to a Fabric domain that matches the business area (Sales, Finance, HR). Domains give you federated ownership: domain admins can be delegated some governance settings, including who may certify items. See Governance.
  • Capacity. Assign by environment first: production workspaces to a production capacity, DEV and TST to a non-production capacity that can be paused. Isolate heavy engineering layers from interactive Delivery workspaces if they would otherwise compete.
  • Access. Use security groups, not individuals, and grant by layer.
LayerTypical audienceWorkspace roles
BRZ, SLVData engineers, platform teamAdmin and Member for engineers; no business users
GLDEngineers, BI developers, data scientistsContributor for BI developers; read access to tables through item permissions rather than workspace roles where possible
CNSMBI developers, semantic model ownersContributor or Member; Build permission on models for report builders
DLVReport developers; business users through appsContributor for developers; Viewer or app audiences for consumers

Report consumers never need access to the lakehouses behind a semantic model, provided the model uses an appropriate identity for reading data. See Semantic models and reports and the Tenant Settings Reference.

Environment and CI/CD foundation

Do this before the first rebuilt asset. Retrofitting source control onto a team that has been publishing PBIX files from desktops is harder than starting with it, and a team that bypasses Git undermines every deployment guarantee downstream.

  1. Provision the workspaces and assign capacity

    Create the workspaces for the domain with the naming convention, attach each to the right capacity, set the domain, and grant roles through security groups. Confirm the tenant settings that gate this work are enabled for the right people: creating Fabric items, creating workspaces, and synchronizing items with Git.

  2. Connect DEV to Git

    Connect each DEV workspace to its own folder in the repository, on the main branch. Use a short-lived feature-branch model (GitHub Flow or a simplified Git Flow): main is always releasable, work happens on feature or fix branches, and every change merges by pull request. Developers use "branch out" to get an isolated workspace for a branch, so one person's work-in-progress never breaks another's.

  3. Protect main

    Require pull requests, at least one reviewer from the owning team, and passing checks. Use a CODEOWNERS file to route reviews; see Pull-Request Notifications with CODEOWNERS and GitHub Integration and Branching.

  4. Create one deployment pipeline per domain and layer

    Assign the DEV, TST and PRD workspaces to the three stages of DPLY_<DOMAIN>_<LAYER>. Deployment pipelines compare stages, show differences and promote selected items. Details are in Deployment Pipelines and Promotion.

  5. Parameterize what differs between stages

    Deployment rules exist for only a few item types, so do not rely on them for everything. Prefer variable libraries for connection endpoints, workspace and lakehouse references, and feature switches. See Variable Libraries.

  6. Automate when the manual path is stable

    A workflow triggered by merges authenticates with a service principal and calls Fabric APIs, or uses the open-source fabric-cicd library, to publish from Git into TST and then, after approval, PRD. It costs more to set up and gives you an auditable, repeatable release. Start manual, then automate the path that is already boring.

Example: GitHub Actions with fabric-cicd

This sketch publishes one workspace folder to TST on merge and to PRD after an environment approval. The repository layout (workspaces/SALES_SLV) and secrets are placeholders.

name: deploy-sales-slv
on:
  push:
    branches: [main]
    paths: ["workspaces/SALES_SLV/**"]
permissions:
  id-token: write      # OIDC federation to Microsoft Entra ID
  contents: read
jobs:
  deploy-tst:
    runs-on: ubuntu-latest
    environment: tst
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install fabric-cicd azure-identity   # pin a tested version
      - uses: azure/login@v2
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          allow-no-subscriptions: true
      - run: >
          python .github/scripts/deploy.py
          --workspace-id ${{ vars.TST_SALES_SLV_WORKSPACE_ID }}
          --environment TST
          --folder workspaces/SALES_SLV
  deploy-prd:
    needs: deploy-tst
    runs-on: ubuntu-latest
    environment: prd     # configure required reviewers on this environment
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install fabric-cicd azure-identity
      - uses: azure/login@v2
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          allow-no-subscriptions: true
      - run: >
          python .github/scripts/deploy.py
          --workspace-id ${{ vars.PRD_SALES_SLV_WORKSPACE_ID }}
          --environment PRD
          --folder workspaces/SALES_SLV
import argparse

from azure.identity import AzureCliCredential
from fabric_cicd import FabricWorkspace, publish_all_items, unpublish_all_orphan_items

parser = argparse.ArgumentParser()
parser.add_argument("--workspace-id", required=True)
parser.add_argument("--environment", required=True)   # DEV, TST or PRD: selects parameter values
parser.add_argument("--folder", required=True)        # for example workspaces/SALES_SLV
args = parser.parse_args()

workspace = FabricWorkspace(
    workspace_id=args.workspace_id,
    environment=args.environment,
    repository_directory=args.folder,
    item_type_in_scope=["VariableLibrary", "Environment", "Notebook", "DataPipeline"],
    token_credential=AzureCliCredential(),   # uses the identity from azure/login
)

publish_all_items(workspace)
unpublish_all_orphan_items(workspace)        # deletes items no longer in Git: test before enabling in PRD

Verify against Microsoft Learn

Git integration supports a specific list of item types, and individual types move between preview and general availability. Check Overview of Fabric Git integration for the current list and the tenant settings it requires. For fabric-cicd, confirm the supported item_type_in_scope values and the parameter-file format in the library's own documentation, and make sure the service principal is allowed to call Fabric APIs under the tenant settings.

Key takeaways

  • Bronze and Silver are lakehouses in every pattern. The choice is who writes the star schema, and with what: choose by team skills and record it in a decision record.
  • Prefer one workspace per layer per environment for estates with several audiences; keep the naming convention identical either way.
  • Only DEV is Git-connected. TST and PRD are populated by a pipeline or a workflow, and rules or variables carry per-stage differences.
  • Protect main, route reviews with CODEOWNERS, and automate the release path only after the manual path is stable.
  • Do not partition Delta tables by default; partition only large tables on a stable filter column.
