The seventeen playbooks each solve one part of a Fabric platform. This page assembles them into one design: how data moves from sources to reports through isolated layer workspaces, how a hub decides when each layer runs, how a change travels from a feature branch to production, and which controls govern all of it. Every section links to the playbook that holds the detail.

The architecture in one view

Think of the platform as four planes that change at different speeds and are owned by different people. The data plane holds the data and the code that transforms it. The orchestration plane decides when that code runs and records what happened. The ALM plane decides which version of the code is running in each environment. The governance plane sets the tenant-wide rules and checks the results. Keeping them separate is what lets a data engineer change a Silver notebook without touching the schedule, and a release manager promote that change without editing the notebook.

Data plane: isolated medallion layers

The data plane is the medallion pattern with two extra layers. Bronze, Silver and Gold carry data from raw to business-ready; Consumption shapes it for each engine (T-SQL, Direct Lake, Spark); Delivery packages it for people. Each layer of each domain gets its own workspace, named <ENV>_<DOMAIN>_<LAYER>[_<Qualifier>], because the workspace is the unit to which Fabric attaches roles, capacity, the Git connection and the deployment stage. Items follow <ARTIFACT>_<DOMAIN>_<LAYER>_<Function> and carry no environment token, so they pair across stages.

Rules that keep the data plane sane

  • One-hop, downstream shortcuts. A shortcut lives in the downstream workspace and points one layer up. No skipping, no upward edges. See shortcut edge rules.
  • Authorization at the target. Reading a shortcut needs access at the target; a role in the reading workspace is not enough. Grant the production identity read access at every target it uses. See security controls.
  • Choose the load per table. Full or incremental, and which change signal, are per-table decisions recorded in the control table. See the load strategy cheat sheet.
  • Layout by default, partitioning by exception. Most tables need compaction and, where it helps, liquid clustering rather than partitions. See the partitioning decision tree.
  • Shared code ships as a wheel. Load and MERGE helpers live in a versioned library installed through each layer's Environment. See Shared Python Libraries and The Environment item.

Consumption and delivery

The consumption layer exists so that the meaning of the data is fixed in Gold and only its shape changes downstream. A warehouse serves T-SQL users and paginated reports; a semantic model serves interactive BI; an ML lakehouse serves data science. Delivery then packages reports into apps, so business users never need a role in a data workspace.

Orchestration plane: hub, spokes and control tables

A layered platform loses the one thing a single workspace gave for free: a place that knows what must run before what. The orchestration plane puts that knowledge in a dedicated hub workspace per environment, <ENV>_ORCH_HUB. Its master pipeline reads the task list from a control table, resolves stage-specific workspace and item IDs from a variable library, invokes each spoke pipeline with the Invoke pipeline activity (waiting on completion), and writes every outcome to a run log.

Solve logging and IDs on day one

Central run logging and environment-specific item IDs are the two things that are painful to retrofit. Create the run log table and the hub's variable library before the first spoke is wired in. See Logging, monitoring and CI/CD.

ALM plane: from feature branch to production

The ALM plane combines two Fabric mechanisms. Git integration versions item definitions: DEV workspaces follow main, and developers work in feature workspaces connected to short-lived branches. Deployment pipelines promote those definitions from DEV to TST to PRD, one pipeline per layer, named DPLY_<DOMAIN>_<LAYER>. GitHub enforces review with a ruleset on main and routes pull requests to owners with CODEOWNERS; GitHub Actions authenticates as a service principal through OIDC to build the shared library and call the deployment APIs.

Deploy, hydrate, verify

A deployment copies definitions, not data. Deploy layers in dependency order, run the loads in the target stage and verify each layer before deploying the next; otherwise the next layer reads empty tables and reports success. The release-day runbook is in Deployment Checklist, and the order rationale in Deployment order and layers.

Security and identity boundaries

The workspace is the coarse boundary and the one auditors ask about first: who holds which role in which layer. Inside it, OneLake security, SQL permissions and semantic model security narrow what a reader sees. Automation uses its own identities, never a person's.

Test the identity that runs production

A notebook that works interactively can fail on schedule because the identity differs and workspace roles do not extend across a shortcut. Some engines also evaluate shortcuts with the item owner's identity rather than the caller's. Test the scheduled run, with the production identity, in TST.

Governance plane: rules, quality and monitoring

Governance is not a separate project at the end; it is the set of controls the other three planes run inside. Tenant settings decide which features exist and for whom. Domains, endorsement, sensitivity labels and the OneLake catalog make content discoverable and classifiable. Validation frameworks decide whether a load is good enough to promote, and monitoring tells you whether the platform is healthy.

Each linked playbook page names the exact Learn article to check; re-read it before committing a design to a capability.

Key takeaways

  • Separate the planes: data, orchestration, ALM and governance change at different speeds and have different owners.
  • Make every layer of every domain a workspace, and keep shortcut edges one hop downstream, authorized at the target.
  • Put order and IDs in data: a control table and variable libraries let the hub and the promotion path run without edits.
  • Promote one layer at a time: deploy, hydrate, verify, then move on.
  • Take the decisions table to the first design workshop; the expensive rows are isolation level and repository layout.
